Review of the `rpcRequest` / `RpcOutcome` seam landed by `15.2a1` / `15.2a2` (commits `06237b2`,
`00ce7ec`, `adbc501`). The helper is the single owner of the outbound open / write / read /
release sequence for a FRET RPC; no production sender uses it yet — `15.2b-rpc-sender-migration`
is the ticket that moves the five senders onto it.

The analysis half of this review was done across `15.2a` and `15.2a2` (both ran out of budget);
this run applied the designed fixes, added the tests, and ran the gates.

## Review findings

### Checked

- `src/rpc/outcome.ts` (57 lines) and `src/rpc/request.ts` read in full, plus every primitive they
  compose: `openRpcStream`, `releaseRpcStream`, `readFramed`, `sendFramed`, `decodeJson`,
  `isUnsupportedProtocolError`, `isFrameTruncationError`, `deadline`, `abortReasonError`.
- Resource cleanup: the `finally` releases through `releaseRpcStream` *before* `d.cancel()`, so the
  bounded `close({signal})` still has a live deadline. Correct, and load-bearing — cancelling first
  silently removes the bound. The `skipped` path passes `undefined`, a no-op there.
- Single-clock argument: `readFramed` runs in `Infinity` mode with the RPC deadline as its sole
  signal, so the two-timer race that makes the release *arm* non-deterministic in
  `test/rpc.stream-errors.spec.ts` cannot occur here. That is what lets every case in
  `rpc.request.spec.ts` assert the arm, not merely the count.
- One `classify` shared across the open / write / read phases rather than one per phase: correct,
  because `negotiateFully: false` defers an `UnsupportedProtocolError` from the open to the first
  read, and a per-phase mapping would book a contact strike for what is membership evidence. The
  error identities are disjoint per phase, so folding is safe.
- Ordering inside `classify`: caller signal first, so a cancellation is never dressed as a network
  outcome. Ordering inside `decodeReply`: the busy shape is tested on the parsed value *before* the
  validator runs, so a validator never sees a busy reply.
- `test/rpc.request.spec.ts` read in full. The implementer's test inventory is accurate.
- `src/index.ts` re-exports `rpcRequest` / `RpcRequestOptions` / `RpcOutcome`;
  `test/package-exports.spec.ts` pins all three at runtime and at type level.
- `docs/fret.md` was already current for what `15.2a` landed — the stream-management section
  describes `RpcOutcome` + `rpcRequest` and names the pinning spec, and the leave section explains
  why `busy` being expressible does not yet make a rate-limited leave visible. Its remaining
  forward references ("the senders still arm both today", the pointers at
  `tickets/plan/15-rpc-shared-helper`) are still true while the senders are unmigrated, so they are
  correct rather than stale. Two clauses were added for what *this* review changed (below).

### Fixed in this pass

- **Write-only type hole (`src/rpc/request.ts`).** `rpcRequest<T = undefined>` took `decode` as
  optional and the write-only branch returned `{ kind: 'ok', value: undefined as T }`. So
  `rpcRequest<Snapshot>(node, peer, proto, { body })` — an explicit type argument with the
  validator forgotten — type-checked, returned `ok`, and the caller read a property off
  `undefined` at runtime. Fixed at rung 1 of the *Architecture first* ladder (make the bad state
  unrepresentable) rather than by a comment: the single exported signature is now two overloads
  over an unchanged implementation. Overload 1 takes no type parameter and pins `T` to `undefined`,
  so an explicit type argument cannot reach it; overload 2 requires `decode`. The bad call is now a
  compile error. Confirmed by `tsc --noEmit` rather than by tracing alone, since it leans on
  TypeScript's overload-assignability rules — the type-level pin in `package-exports.spec.ts`
  (which assigns `rpcRequest` to overload 1 verbatim) still holds.
- **Over-cap failure had no error identity (`src/rpc/protocols.ts`, `src/rpc/request.ts`).**
  `classify` routed the over-cap case by matching message text (`startsWith('payload too large')`)
  while both its neighbours matched on `err.name`. Root cause is one owner: `readFramed` raised the
  condition as a bare `new Error(...)` at two sites (the `onLength` hook and the
  `InvalidDataLengthError` rescue arm). Added `PayloadTooLargeError` beside the existing
  `FrameTruncationError` (same shape, stable `name`), thrown at both sites with the **message text
  byte-identical**, plus an `isPayloadTooLargeError` predicate beside `isFrameTruncationError`;
  `classify` now calls it. Keeping the text unchanged is what keeps the existing assertions in
  `payload-bounds-ttl.spec.ts`, `rpc.codec-properties.spec.ts`, `rpc.stream-errors.spec.ts` and
  `rpc.request.spec.ts` green.
  Scope stated honestly: **no reachable remote-influenced error was found that collides with the
  prefix today.** Everything reaching `classify` comes from libp2p's dial / `newStream` / stream
  machinery or from `readFramed` itself, and a validator's own throw goes through `decodeFailure`,
  never `classify`. So this retires "classify by message text" as a class in the newest code in the
  package; it does not repair a live misclassification.
- **A write-only request cannot observe `foreign-protocol` — now documented.** `openRpcStream` pins
  `negotiateFully: false`, deferring an `UnsupportedProtocolError` to the first read, and the
  write-only path returns `ok` right after the write. So sending to a peer that does not serve this
  network's protocol yields `ok` and produces no membership evidence. Checked against today's
  behavior and **not a regression**: `sendLeave` (the write-only sender `15.2b` migrates) also never
  reads, and its only caller `sendLeaveToNeighbors` (`src/service/fret-service.ts:1512`, `:1522`)
  merely logs a throw — no membership signal, no contact strike. Nothing is lost by the migration;
  the gap was simply unstated at the seam a future caller reads. Added a clause to
  `RpcRequestOptions.decode`'s doc comment cross-referencing the `negotiateFully: false` caveat, and
  a matching sentence in `docs/fret.md`.

### Tests added (4 cases; 31 → 35 in `test/rpc.request.spec.ts`)

All reuse the existing `makeStub` / `serves` / `countingNode` harness. They close three of the
implementer's own stated "Known gaps".

- **Both `undefined` arms of the `retry_after_ms` guard** (two cases, table-driven): only the
  well-formed 500 ms case was pinned, so `typeof retry === 'number'` had one live arm. Frames
  `{busy: true}` and `{busy: true, retry_after_ms: 'soon'}`; both assert `busy` with
  `retryAfterMs === undefined`, and neither may become a `decode-error`.
- **The 64 KiB `DEFAULT_MAX_BYTES` boundary.** Every other case passed an explicit `maxBytes`, so
  the default was only ever proved *present*. One request with `maxBytes` omitted against a frame
  declaring 65537 bytes asserts the exact message `payload too large: 65537 exceeds 65536 byte
  limit` — proving the default is wired to the cap the reader enforces, at the boundary itself.
- **Two concurrent `rpcRequest` calls over one node.** Pins that the helper holds no per-call state
  on the node — every clock, stream and counter is a local of the call. That is the claim `15.2b`
  relies on when five senders share it: both calls decode their own reply and each releases its own
  stream exactly once.

### Found and deliberately not changed

- **`skipped` release counters are vacuous.** No stream exists on that path, so `{closes: 0,
  aborts: 0}` is true by construction rather than by assertion. Nothing to add.
- **`releaseRpcStream`'s "bounded close rejected → fall through to `abort()`" arm is never taken
  through `rpcRequest`.** The stub's `close()` ignores the `{signal}` it is handed, and there is no
  real-transport case. That arm is covered directly in `test/rpc.protocols.spec.ts`; reproducing it
  through the helper would need a stub modelling signal-aware close rejection — a harness change
  disproportionate to re-covering an already-covered arm. Declined.
- **Not property-based.** `classify` has five branches and every one is covered by a hand-picked
  case. A generator over arbitrary error identities would re-derive the same five branches without
  reaching new state, so this was declined outright rather than filed as a `debt-` ticket.

### Tripwires

None recorded. The three conditional concerns considered — the double parse of the reply body in
`decodeReply` (once for the busy check, once by `decode`), the `Date.now()` RTT clock's ~15 ms
Windows granularity, and the drain-wait loop — are each already carried by a comment at their own
site stating the tradeoff, so there was nothing new to park.

### New tickets filed

None. All three findings were minor and fixed in this pass; the two structural ones were resolved
at the rung that retires the class (an unrepresentable bad state, and an error identity) rather
than filed as instances.
