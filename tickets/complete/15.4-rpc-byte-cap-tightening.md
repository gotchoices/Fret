## What shipped

- **maybeAct caps unified.** `maxBytesMaybeAct()` = `MAX_ACTIVITY_BYTES` (128 KiB) +
  `MAYBE_ACT_OVERHEAD_BYTES` (16 KiB) = 144 KiB, one number for both profiles, so the wire cap and
  `handleMaybeAct`'s own activity-size refusal are the same arithmetic and cannot disagree. This was
  the ticket's headline goal and it is correctly done.
- **Per-field caps exported** from `src/rpc/validate.ts`: `MAX_KEY_CHARS` 1024,
  `MAX_CORRELATION_ID_CHARS` 256, `MAX_BREADCRUMBS` 64, `MAX_DIGEST_CHARS` 4096,
  `MAX_REPLACEMENTS` 12, `MAX_SNAPSHOT_METADATA_BYTES_CORE/EDGE` 8 KiB / 4 KiB.
- **Neighbors cap narrowed** 128 KiB → 16 KiB Core / 8 KiB Edge; `rpcRequest`'s fallback cap
  64 KiB → 8 KiB; leave unchanged at 4096; ping unchanged at 1024.
- **Outgoing snapshot metadata is now size-checked** and omitted when over the profile cap.
- **Two new test blocks** in `test/rpc.codec-properties.spec.ts`: the frame prefix alone refuses an
  over-cap message per protocol (measured by counting source pulls), and the largest legal message
  of each protocol encodes under its wire cap.
- **`docs/fret.md` *Stream management*** updated to the shipped numbers.
- **Backlog ticket filed** for the deliberate gap: `MAX_ACTIVITY_BYTES` has no Edge/Core split.

## Review findings

Reviewed the full implement diff (`git diff 841a1c2..HEAD -- packages/fret/src`) before reading the
handoff, then the two new test blocks and the docs paragraph.

### Major — filed as `fix/15.5-neighbors-wire-cap-cross-profile`

**The neighbors byte cap reintroduces, for a different protocol, exactly the defect this ticket
retired for maybeAct.** Two arms at one decision site ("what is the neighbors byte limit"), so one
ticket:

- **Cross-profile refusal.** Each profile's cap was derived from the largest snapshot *that profile
  emits*, but an inbound cap must cover the largest snapshot *any peer* emits. A Core snapshot is
  ≈ 2.5 KiB of fixed fields plus up to 8 KiB of `metadata` = ≈ 10.5 KiB, against an Edge inbound cap
  of 8 KiB (`FretService.maxBytesNeighbors()`, `fret-service.ts:1023`). A Core node with more than
  ~5.5 KiB of application metadata can no longer announce to, or answer a neighbors request from,
  any Edge peer — refused at the length prefix, stream torn down, sender told nothing useful.
  `repro: static` (read from the code and the encoding arithmetic; not observed on a live pair).
- **Two caps for one message type on one node.** `fetchNeighbors` (`neighbors.ts:114`) hard-codes
  `maxBytes: 16 * 1024` and takes no profile input, while the announce handler is given
  `maxBytesNeighbors()`. An Edge node therefore accepts a 12 KiB snapshot it asked for and refuses
  the identical snapshot pushed at it.

Filed rather than fixed inline because choosing the corrected numbers is a design call (raise the
acceptance cap on both profiles, or make `metadata` profile-independent), not a mechanical edit.
Climbed the architecture ladder first: the durable fix is one cap decision that both read paths
consume plus a test comparing each profile's largest *emission* against the smallest *acceptance*
cap — that invariant retires the whole class, so the ticket asks for it rather than for two literal
edits. Site-claim grep over `tickets/{backlog,fix,plan,implement,review}` for `maxBytesNeighbors` /
`fetchNeighbors` found only this ticket, so it is filed fresh.

### Minor — fixed in this pass

- `request.ts`: the `DEFAULT_MAX_BYTES` doc comment claimed 8 KiB is "the smallest production
  per-protocol cap". It is not — `sendPing` passes 1024. Rewritten to say what the default actually
  is and why it is not the minimum.
- `validate.ts`: `MAX_SNAPSHOT_METADATA_BYTES_CORE`'s comment described it as "fixed fields of a
  Core neighbor snapshot plus its metadata allowance", but it is used solely as the metadata cap.
  Rewritten to state what it bounds and how it was sized.

### Tripwire — recorded, not ticketed

Over-cap `metadata` is dropped on every snapshot build (each announce, each served neighbors
request), so a persistently over-sized `setMetadata` value logs an error once per snapshot rather
than once per change, and the application is never told its metadata is not propagating. Fine while
metadata is a rarely-used diagnostic channel. Parked as a `NOTE:` at `FretService.snapshot`
(`fret-service.ts`, immediately above the metadata size check).

### Test coverage — gap noted, folded into the fix ticket

The new "largest legal message of each protocol encodes under its wire cap" block builds each
snapshot **without** a `metadata` field, so it does not exercise the part that overflows; and it
compares each profile's message against that same profile's cap rather than against the smallest cap
any peer could apply. That is what let the cross-profile break pass. The required test is specified
in the fix ticket rather than written here, since it cannot pass until the caps are corrected.

Otherwise the tests are good and are the strongest part of the diff: the prefix-refusal block
*measures* the refusal (counting pulls on an instrumented source) rather than inferring it from the
absence of a crash, and the at-cap/over-by-one activity test correctly separates the service-level
check from the wire-level one, asserting that nothing else in the diagnostics moved.

### Checked and clean — no findings

- **maybeAct arithmetic.** `MAYBE_ACT_OVERHEAD_BYTES` (16 KiB) genuinely covers the non-activity
  fields: key 1024 + correlation_id 256 + digest 4096 + 64 breadcrumbs × 64 + reserved signature 512
  + punctuation ≈ 10.5 KiB. The derivation is stated in the comment and pinned by a test that builds
  every field at its cap.
- **Leave (4096) and ping (1024)** — both unchanged, both now carry a stated derivation; 12
  replacements × 64 + envelope ≈ 912 bytes leaves ample headroom.
- **Resource cleanup / error handling** — the diff adds no new streams, timers, or catch sites; the
  metadata check is a pure local computation on an already-built object.
- **Type safety** — no `any` introduced; the exported constants are plain `const` numbers.
- **Source hygiene** — no file grew meaningfully; the largest addition is 127 test lines. Comments
  are derivations, not restatements of the code, which is the right density for this module.
- **Docs** — read `docs/fret.md` line 209 against the shipped code; the maybeAct and leave sentences
  are accurate. The neighbors sentence ("sized to its profile's snapshot caps") states the mistaken
  rule and is called out for correction in the fix ticket rather than patched here, since the
  numbers themselves are what change.
