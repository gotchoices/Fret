## Review findings

**Item 1 — `encodeJson` / `decodeJson` dropped `async`, call sites dropped `await`. Clean.**
Read line by line against the diff; `npx tsc --noEmit` was clean at the implement stage and is
clean now. The test-only `await`s left on the now-synchronous functions are legal and harmless.

**Item 2 — `PROTOCOL_*` constants derive from `makeProtocols('default')`. Clean.** Same review.

**Item 3 — success replies changed from `{ ok: true }` to `undefined`. Regression; reverted in
commit `9e1d510`.** At `547d506`, `yarn test` gave 1040 passing / 76 failing, all in
`test/rpc.handler-fuzz.spec.ts` and `test/rpc.codec-properties.spec.ts`, all on the leave /
announce reply path (`expected a reply frame, got eof`, plus ~60 cases of `Could not append value,
must be an Uint8Array or a Uint8ArrayList` from `it-length-prefixed` being handed the absent
reply). Both handlers return `{ ok: true }` again, each carrying a `NOTE:` recording the accepted
tradeoff and its revisit condition. The reasoning, recorded so it is not re-litigated: it is a
wire-format change rather than the low-risk tidy-up the ticket was scoped as; it collapses the
seam's `undefined`, which until then meant only "identity mismatch, drop", into meaning both
"drop" and "success"; the acknowledgement is observable by a non-FRET consumer, since the
protocols and the `registerRpcHandler` / `registerJsonHandler` seam are exported from the package
root; and `docs/fret.md` *Leave* parks planned work where `sendLeave` **does** read a reply so a
rate-limited leave can answer `busy`. The counter-argument — neither `sendLeave` nor
`announceNeighbors` reads a reply, so those bytes are provably unread by any FRET sender — is real
but does not outweigh those, and is recorded at both code sites as the revisit condition.

**Item 4 — `decodeJson` counts stripped NUL bytes and emits one `log.error`. Not a defect; parked
as a tripwire.** The concern was log amplification: `decodeJson` runs *before* the maybeAct token
bucket (`registerMaybeAct` decodes in its own handler body, then `handle()` takes the bucket), so a
peer can drive one line per NUL-padded message with nothing metering it. Settled by reading the
logger chain: `@libp2p/logger`'s `logger(name).error` is a `weald` debug instance named
`<name>:error`, and a weald debug instance's body opens with `if (!debug.enabled) return`, where
`enabled` derives from the `DEBUG` namespaces — with `DEBUG` unset it writes nothing.
Namespace-gated, not unconditional, so no ticket. **Tripwire parked** as a `NOTE:` at the
`decodeJson` site naming the revisit condition: FRET gaining a sink that records unconditionally
(a metrics counter, a structured logger, a file appender), at which point the line needs a bucket
in front of it. This also confirms rather than inherits the debug-gated claim the existing `NOTE:`
in `src/rpc/leave.ts` makes about its own mismatch log.

**Docs.** Treated as out of date until read. The *Wire formats* `decodeJson` paragraph in
`docs/fret.md` described the trim as silent; it now states the NUL count line and its namespace
gating. The *Leave* passages describing `registerLeave` as committing to `{ok: true}` are correct
again after the item-3 revert and were deliberately left alone. No other touched file has prose
that went stale.

**Test coverage added.** Item 4 shipped with no coverage — missing coverage, not a defect. Two
tests now sit in `packages/fret/test/rpc.codec-properties.spec.ts`, as a `describe` sibling
immediately after `decodeJson rejects what is not a message`, the block that already holds the
padding cases:
- NUL padding logs **once** with the **correct count**, covering padding at the start only, at the
  end only, and at both ends (three cases).
- Whitespace-only padding (tab / LF / CR / space, no NUL) logs **nothing**.

The capture mechanism is worth stating, since `log` is a module-private const in `protocols.ts`
and re-creating the logger in a test yields a *different* weald instance that intercepts nothing.
The tests enable the real namespace `optimystic:fret:rpc:handler:error` through
`@libp2p/logger`'s exported `enable()` (a declared dependency — `weald` itself is not) and capture
weald's node sink by temporarily replacing `process.stderr.write`, restoring both in a `finally`.
`enable()` writes `process.env.DEBUG` as a side effect, so the prior value is read first and
restored, and the assertions match `/stripped (\d+) NUL/` rather than pinning the whole formatted
string, which carries a namespace prefix and an elapsed `+Nms` suffix. Neither test can pass
vacuously: each asserts the exact line count as well as the parsed number.

**Validation.** `npx tsc --noEmit` clean. `yarn test` from `packages/fret`: **1120 passing, 0
failing** — the item-3 revert restored all 76 failures, and the four new cases account for the
rest of the delta. No pre-existing failures surfaced, so nothing was written to
`tickets/.pre-existing-error.md`.

**Tickets filed: none, and deliberately.** Item 3 was a real regression but was fixed inline in
this review pass, so there is nothing left to queue. Item 4 is conditional — fine as it stands,
work only if an unconditional log sink ever lands — which is a tripwire, not a ticket, and it is
recorded at the code site. Items 1 and 2 were clean. No finding at any site carried an
accepted-tradeoff `NOTE:` that this review had to weigh against.
