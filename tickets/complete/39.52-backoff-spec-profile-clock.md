### What was checked, and what was found

**Diff scope.** `git show 82ee97a --stat` touches exactly one source file,
`test/profile.behavior.spec.ts` (+21/−16), plus ticket-board moves. `failure-recovery.spec.ts` is
not in this commit; its assertions arrived in `d47b2f7` / `c03528b` and were reviewed here anyway.

**Public-surface use (clean).** The three converted sites in `profile.behavior.spec.ts` reach only
the documented `ProbeBackoff` surface — `capacity`, `size`, `record`, `factor` — through
`backoffOf` / `setBackoffOf`. No second cast was reintroduced. `test/helpers/backoff.ts` types its
parameter as the concrete `FretService`, which is what stops a spec handing it the
`Libp2pFretService` facade.

**The constant change is a real bug fix (confirmed at the source).** `BACKOFF_RETAIN_MS` →
`ProbeBackoff.DEFAULT_RETAIN_MS`: `ProbeBackoff` declares `DEFAULT_RETAIN_MS = 300_000` and
`FretService` no longer declares the constant, so the old `(CoreFretService as any).BACKOFF_RETAIN_MS`
read `undefined` and the untouched `advance(...)` line was stepping the clock by `NaN`.

**Fake `ProbeBackoff` is well-formed.** The one the sweep case installs (`capacity: 8,
retainMs: 300_000`) satisfies the class's own retention inequality (`retainMs > baseMs * maxFactor`
= 32_000), so it cannot silently reset a factor mid-case.

**Stale private reaches — swept, both files, none found.**
- `profile.behavior.spec.ts`: all 34 `as any` sites listed; none names `backoffMap`; the rest reach
  members that still exist. The sibling constant read in the sweep case is *not* a second instance
  of the fixed bug — `(CoreFretService as any).DEPARTURE_DEBOUNCE_MS` is declared at
  `src/service/fret-service.ts:246`.
- `failure-recovery.spec.ts`: 10 `as any` sites, naming six distinct private members. All six exist

  (2383), `reprobeExcludedTargets` (2586, its one parameter defaulted), `snapshot` (2777),
  `registerRpcHandlers` (1250), all in `src/service/fret-service.ts`.
- Repo-wide: `grep -rln "backoffMap\|BACKOFF_RETAIN_MS" test/ src/` from `packages/fret` returns
  exactly the five files in *Expected red suite* and neither file under review.

**Implementer's open question answered: the sweep case still discriminates, and the expired half is
what carries it.** `profile.behavior.spec.ts:425` (`expect(backoff.size).to.equal(0)`) is the
load-bearing assertion. `ExpiringMap.size` returns the raw backing-map size and deliberately counts
a retained-but-expired entry (`src/utils/expiring-map.ts:66`, with a comment saying exactly that),
so nothing but a `sweep`, a keyed lookup, or an eviction removes the entry. The case installs the
entry under the service's own id, and the only other remover in `sweepBoundedMaps` —
`ProbeBackoff.prune` — cannot drop it, since self is always in the routing store. With the sweep
disabled the entry survives and line 425 fails. The `record`-then-tick tail at 430–432 is a control
against a sweep that clears the map unconditionally, not the discriminating half; the case comments
already say this and they are accurate.

**`factor()` assertions in `failure-recovery.spec.ts` — each makes the claim its case wants.** The
prior run's ticket said "three `factor() === 0` assertions"; there is in fact **one** `=== 0` plus
two positive assertions. All three read correctly:
- `:182` `factor() === 0`, "the near pass records no backoff". `ProbeBackoff.factor` returns 0 only
  when *nothing is retained*, which is the strictly stronger reading — "no escalation was recorded
  at all" — and that is exactly what this case is pinning (that the near pass never calls `record`).
  The weaker `isBackedOff` / `penalty === 0` would pass against a recorded-then-closed window and so
  would not pin the shipped staging. Correct as written.
- `:256` `factor() === 1` and `:262` `factor() === 2` read a retained entry's escalation; both are
  positive assertions where the distinction does not arise.

**Docs.** `docs/fret.md` was checked rather than assumed. The change is test-only and introduces no
behavior; the document's existing statements about the near pass recording no backoff, and about
`DEFAULT_RETAIN_MS` living on `ProbeBackoff`, already describe the code as it now stands. No edit.
