## What shipped

`FretSimulation.handleRoute` chooses every hop with the shipped `chooseNextHop` cost path over the
deciding peer's own store. The candidate pool reads neither the global `alive` flag nor the
partition map — only `notDead`, which reflects what that peer's own failed contacts recorded. A
chosen hop is an *attempt*: a refused or dead target is struck through the shared
`recordContactFailure` (also used by the per-tick `contactSweep`) and the selector re-runs over the
remaining candidates, so only delivered hops count toward path length. `selfCoord` is supplied from
the second hop onward only, matching production's originator/forwarder split. `nearRadiusFor`
derives the near radius from `store.size()`, not from the harness's alive count.

## Review findings

**Confirmed correct, no change needed:**

- Pool is the deciding peer's store only, minus self and `visited`. No oracle read on any path.
- Selector call matches the signature: constant `linkQ`, no `backoffPenalty`, `confidence` 0.5,
  `selfCoord` from hop 2 onward.
- Termination: the outer loop either breaks or advances `current` with `hops++`, and every
  delivered hop also costs one `attempts++`, so `attempts >= hops` holds and the single
  `attempts < maxHops` bound is sufficient. `visited` excludes the current peer from its own pool,
  so no cycle. `tried` is per-hop, which is right — a peer that refused peer X may still be
  attempted from peer Y; that is a different peer's contact attempt.
- Edge cases, by reading plus the passing suites: an empty pool (ring smaller than m; a single
  live peer; every candidate unreachable) falls to `if (!next) break` and records one failure with
  its hop count — no throw, no spin. `chooseNextHop` returning `undefined` (nothing strictly
  improving) does the same, with no "closest anyway" fallback.
- Metrics: `recordRoute(success, hops)` pushes `hops` into `routingHops` always and into
  `successfulRouteHops` only on success, which agrees with the delivered-hops-only rule and with
  what `simulation.routing.spec.ts` measures.
- `docs/fret.md` already carries "The sim routes the way a node does" and the guard-spec bullet
  under *Testing strategy*, accurate at HEAD. It was written by the follow-on ticket's commit
  rather than by `4224f52`; the text is right, so nothing to change. Docs are not stale here.
- Two items an earlier review run listed as remaining cosmetic edits — a dead `hops < maxHops`
  term in the outer loop, and `nearRadiusFor` recomputed inside the retry loop — were already
  correct in the implement commit (`while (attempts < maxHops)`; the radius hoisted above the
  retry loop with a comment saying why). The note was stale, not a defect. No edit made.

**Found and fixed in this pass (minor):**

- *The new partition test's strike assertion was not attributable to the route it was testing.*
  `simulation.partition.spec.ts`, "a route across a fresh cut fails by refused contacts, not by an
  oracle filter", sampled `contactFailures > 0` as an absolute count after the route, while the
  `crossPartitionBlocked` check right above it correctly took a before-snapshot. Measured: the
  before-counts are in fact all zero today and the route leaves 15 of 20 cross entries at 1, so
  the assertion was passing for the right reason — but only by an unstated argument (nothing is
  unreachable before the cut, so nothing can strike) that a later edit would invalidate silently.
  Now snapshots per-entry counts before the route and asserts some entry's count *increased*.
- *`contactSweep`'s doc comment claimed one strike per entry per tick*, which the routing path's
  own strikes make untrue. Rewritten in a prior run of this review (see the tripwire below).

**Tripwires recorded, not filed as tickets:**

- *Strike spacing.* An entry can now take a sweep strike plus one strike per route at the same
  simulated timestamp, so it escalates to `dead` faster than the sweep alone would. Harmless while
  the specs schedule routes sparsely. Parked as a `NOTE:` in `contactSweep`'s doc comment, naming
  the fix (production's >= 500 ms check inside `recordContactFailure`, not re-derived per call site)
  should a suite ever fire many routes per tick at one unreachable window.
- *Which selector branch the sim exercises.* The near radius is exactly `4k/store.size()` of the
  maximum ring distance; with the sim's unbounded stores that lands around a third of maximum at
  the routing spec's sizes, so most candidates take the selector's *near* branch, where ordering is
  by distance alone and the connected allowance and backoff arm are inert. Production's own
  arithmetic, not a sim defect, but it bounds what "the sim exercises `chooseNextHop`" claims.
  Parked as a `NOTE:` at `nearRadiusFor`, cross-referencing the degenerate-eviction NOTE and
  `backlog/debt-sim-eviction-degenerate-blocks-metric-guard`.
