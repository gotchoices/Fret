Review of implement commit `4224f52` ("ticket(implement): sim-route-local-selector"), plus the
follow-on `5f906d6` ("ticket(implement): sim-routing-guard-spec") that landed on top of it and
consumes the same routing path.

The simulation used to decide each routing hop with information no real peer has — the global
list of live peers and the partition map. It now chooses hops the way a node does: from the
deciding peer's own routing table, through the same next-hop selector the service ships, and a
hop that cannot be reached is learned about only by trying it and failing.

## Review findings

### Checked and correct (read against the ticket's design, no change needed)

- Candidate pool is the deciding peer's own store only (non-dead entries, minus self and peers
  already visited); neither the global alive flag nor the partition map is consulted to build it.
- Hop choice goes through the shipped `chooseNextHop` cost path with a constant link quality and
  no backoff penalty, and supplies the peer's own coordinate from the second hop onward only —
  matching production's split between originating a lookup and forwarding one.
- A chosen hop is an attempt, not a delivery: a refused or dead target is struck through the
  shared `recordContactFailure` and the selector re-runs over the remaining candidates. Only a
  delivered hop counts toward path length.
- Near radius derives from the deciding peer's store size, clamped at half the ring; the global
  alive count is not read.
- The unfiltered-arrival check and its explanatory `NOTE:` are preserved unchanged.
- Both stale deferral comments referencing the old ticket are gone, rewritten rather than
  renumbered.
- `docs/fret.md` matches the implementation at HEAD. It was updated by the follow-on commit
  rather than by the implement commit under review; the text is accurate either way.

### Fixed in this review pass

- `contactSweep`'s doc comment claimed one strike per entry per tick, which the routing path's
  own strikes make untrue — an entry can take a sweep strike plus one per route in the same
  simulated tick. Comment rewritten to state that and to name the fix (production's ≥ 500 ms
  spacing check) should a suite ever fire many routes per tick at the same unreachable window.
- `handleRoute`'s outer loop tested `hops < maxHops && attempts < maxHops`. Every hop consumes an
  attempt, so the hop term could never fire and read as a second budget that was not one. Dropped;
  comment now says why the attempt budget bounds hops too.
- The near radius was recomputed on every contact retry although the store is fixed for the whole
  hop, allocating a big-integer division and a 32-byte coordinate per attempt. Hoisted above the
  retry loop.

### Adversarial check on the new partition test

`a route across a fresh cut fails by refused contacts, not by an oracle filter` was checked for
vacuous passing by mutation: filtering the candidate pool through the partition map (i.e. putting
the oracle back) makes the test fail on "a refused contact must strike that entry". So the test
does discriminate a locally-deciding router from an oracle-filtered one. The setup guard that
cross entries are still live before the route, and the uncommitted hardening that compares strikes
*relative* to a pre-route snapshot rather than absolutely, both hold up.

### Tripwires

None recorded — no concern found that is fine now and only becomes work under a stated future
condition. The one concern of that shape (routes striking faster than the sweep alone) is a
documented `NOTE:` at `contactSweep`, written in the same pass.
