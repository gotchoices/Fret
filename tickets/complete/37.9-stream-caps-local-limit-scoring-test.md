Test-only implementation. Two specs landed across this ticket and its predecessor
(`stream-caps-outbound-limit-test`); no `src/` file was changed by either.

- `test/rpc.stream-caps-outbound.spec.ts` — the wire half. Drives `maxOutboundStreams` on the
  *dialing* node and asserts refused requests surface as `local-limit`, on the memory transport
  and on TCP + noise.
- `test/rpc.stream-caps-local-limit-scoring.spec.ts` — the service half. Three cases on the memory
  transport (control ping, near-probe refusal, off-ring membership-probe refusal) against a
  `FretService` that is deliberately never started, with the local node's ping protocol registered
  directly at `maxOutboundStreams: 0` so the very first outbound stream is refused. Asserts no
  contact strike, no relevance decay, no backoff, membership untouched, and `diag.streamLimit`
  incremented once per refusal.

Docs: `docs/fret.md`'s *Stream management* section now cites both specs in the `local-limit`
paragraph — it previously named only `test/rpc.stream-caps.spec.ts`, so neither new file was
reachable from the document. That is the only file this review changed.

## Review findings

This review ran across five agent runs; the first four were each cut short by the token budget
before validation, so their partial conclusions are folded in below rather than lost.

### Checked and sound

- **Diff scope.** The implement stage is three commits (`b4e0fee`, `1523e36`, `1723f8e`); only
  `b4e0fee` touches code, adding one 212-line spec file. The handoff's "no `src/` file changed"
  claim is confirmed against the diffstat.
- **The rig really fires the ceiling it claims to.** `registerRpcHandler`
  (`src/rpc/protocols.ts:122-154`) forwards `maxInboundStreams` / `maxOutboundStreams` to
  `node.handle` verbatim — no `||`, no truthiness test, no default substitution — so a cap of `0`
  survives to libp2p, whose `findOutgoingStreamLimit` reads it under `!= null`. The refusals the
  spec drives are the outbound ceiling, not something else that happens to fail.
  `registerJsonHandler` forwards the same two fields identically, which is the production path.
- **The headline assertion is not vacuous — verified by mutation, not by reading.**
  `applyContactStrike` (`fret-service.ts:776-793`) guards on
  `now - e.lastContactFailureAt < CONTACT_FAILURE_MIN_SPACING_MS`, so the spec's rewind of that
  stamp to `0` makes the guard permissive and lets *every* refusal in the loop book a strike on a
  broken implementation. Confirmed by running the handoff's own suggested mutation: routing
  `local-limit` to `applyContactFailure` in `noteRpcFailure` turns both capped cases red with
  `contactFailures` at 3 (the clamped `deadAfterFailures`) against an expected 0. The mutation was
  applied from a scratch copy of the file and reverted; `git status` after the run showed only
  `tickets/.in-progress`.
- **Neither probe path short-circuits into `skipped`.** `probeNeighborLatency`
  (`fret-service.ts:2451-2500`) calls `sendPing` with only `{ signal, timeoutMs }` — no dial-mode
  option, no local dialability guard — so there is no path that would turn the outcome into
  `skipped` on an unstarted service. For the off-ring arm the passing `streamLimit` assertion is
  itself the proof: `diag.streamLimit` has exactly one owner (`countStreamLimit`), reachable only
  from a `local-limit` outcome, so `streamLimit` rising by 4 could not have happened had the arm
  produced `skipped` (which increments nothing) or any other variant.
- **Validation re-run by review, not taken on trust.** `npx tsc --noEmit` clean.
  `test/rpc.stream-caps-local-limit-scoring.spec.ts` + `test/rpc.stream-caps-outbound.spec.ts` +
  `test/dead-state.spec.ts` — 49 passing, 701 ms. The full suite (implementer-reported 1247
  passing / ~13 min) was deliberately **not** re-run: 13 minutes is past what a ticket agent
  should spend on one foreground command, and this diff adds one spec file and touches no `src/`,
  so nothing about it could break a spec outside its own file.
- **The two specs do not duplicate `test/dead-state.spec.ts`'s existing `local-limit` case.** That
  one hands `noteRpcFailure` a synthetic outcome object and pins the scoring rule; these pin that
  a *real* cap firing arrives as `local-limit` and reaches that rule. Neither subsumes the other.

### Fixed in this pass

- **Docs were stale.** `docs/fret.md`'s *Stream management* section described `local-limit` and
  cited `test/rpc.stream-caps.spec.ts` but named neither new spec, so a reader had no route from
  the design document to the tests that pin the behaviour. Added a citation for both, stating what
  each drives.

### Recorded, not filed

- **Case-ordering fragility (tripwire, already sited).** `capPingOutboundAtZero` installs a
  process-wide handler on the shared `local` node behind a `capped` latch that is never cleared,
  so the control case must run before the two capped cases. Mocha's default order holds today and
  the spec already carries a comment at the site saying the latch exists for `.only` runs. It only
  becomes work if someone reorders the cases or adds a third uncapped one — conditional, so it
  stays a comment at the site rather than a ticket. No new comment added; the existing one is the
  record.

### Filed / appended elsewhere

- **The write-only senders remain uncovered end to end**, as the handoff flagged
  (`announceNeighbors`, `sendLeave` reach the counter via `noteWriteOnlyOutcome`, not via
  `noteRpcFailure`). The site is **already claimed** by
  `tickets/backlog/debt-local-limit-arms-untested.md`, which tracks all seven outcome-observing

### Empty categories, with reasons

- **No major findings.** The change adds one test file and no production code, so it cannot
  regress behaviour; the only ways it could be wrong are a rig that does not exercise what it
  claims or an assertion that cannot fail. Both were checked directly — the cap-forwarding read
  and the mutation run above — and both hold.
- **No minor code findings beyond the docs fix.** Source hygiene is not in question: 212 lines,
  three cases, helpers named for what they do (`capPingOutboundAtZero`, the rewind in the loop),
  and the non-obvious rigging decisions (cap of 0 rather than concurrency, service deliberately
  unstarted, rewind rather than sleep) each carry a comment stating the reason rather than the
  mechanism.
- **No lint step exists** in this repo (see `AGENTS.md` — `yarn format` would rewrite every source

  instead; there is nothing else to run.
- **No pre-existing failures surfaced**, so `tickets/.pre-existing-error.md` was not written.

### Known gaps carried forward from the handoff, accepted

- Both probe passes are reached through a private-method cast rather than through a real
  stabilization tick, so the specs pin the scoring arms and not target *selection*.
  `test/dead-state.spec.ts` already pins the selection side.
- The service spec is memory-transport only; the scoring seam sits above the transport and the
  outbound spec covers TCP + noise for the wire behaviour, so a second transport here would
  re-pin libp2p rather than FRET.
- The spec never exercises `registerRpcHandlers` applying the shipped 256 — its sibling
  `test/rpc.stream-caps-profile.spec.ts` owns that half.
