## What shipped

`readFramed` (`packages/fret/src/rpc/protocols.ts`) no longer guesses at end-of-stream. It has two
implementations behind one signature, dispatched by `isMessageStream`:

- **A real libp2p stream** is read through `@libp2p/utils`'s `byteStream` (`readFramedFromStream`).
  The frame and the stream's own end-of-stream state are read from the same buffer, so a stream
  that genuinely ends mid-frame throws `UnexpectedEOFError` at once and a stream that is merely
  slow ends nothing. The 20 ms `EOF_POLL_MS` poll that used to stand in for stream-layer EOF
  detection — and that could fire while a complete reply was still in flight below it — is gone.
- **A plain async iterable** (test stubs, non-libp2p sources) keeps the `lp.decode` path and ends
  on iterator EOF alone, raising `FrameTruncationError`.

Both names are matched by `isFrameTruncationError`, so either still surfaces to a caller as
`decode-error`. `readFramed` also gained `timeoutMs = Infinity` ("no independent clock — bounded by
`opts.signal` alone"), and every sender now reads in that mode through `rpcRequest`, so an RPC has
exactly one clock and the release arm (`abort()` vs `close()`) is deterministic rather than a race
between two timers.

## Review findings

Reviewed over three passes; passes 1 and 2 were each cut short by a runner budget warning, and
pass 3 closed the remainder. Everything below is the whole record, not just pass 3.

### Checked and correct — no action

- **The dispatch predicate matches the library's own** (pass 1). `isMessageStream` checks
  `closeRead` + `addEventListener` + `removeEventListener` + `send` + `push` + `log` — exactly what
  `@libp2p/utils` itself checks across its two internal predicates (`isValid`, whose failure makes
  `byteStream()` throw `InvalidParametersError`; and `isStream`, which is what `isEOF` branches on;
  verified against `node_modules/@libp2p/utils/dist/src/stream-utils.js`). A stream passing
  `isMessageStream` therefore cannot make `byteStream()` throw and cannot land in `isEOF`'s
  multiaddr-connection branch. Necessary and sufficient; the iterable fallback is a safe (slower)
  path, not an accidental gap.
- **The new path genuinely closes the lost-event race** (pass 1). `AbstractMessageStream` overrides
  `addEventListener` so attaching a `message` listener while `readBuffer.byteLength > 0` schedules
  `dispatchReadBuffer()` on a microtask (so `byteStream()`'s own attach flushes bytes that arrived
  before the listener existed); `dispatchReadBuffer()`'s `finally` sets `readStatus = 'closed'` only
  once the buffer is empty *and* `remoteWriteStatus === 'closed'`; and `read()` tests `isEOF`
  synchronously at entry and again after each wake. One buffer, and the end-of-stream test and the
  byte supply are the same object. `readFramed`'s doc comment is accurate.
- **The 9-byte prefix cap and the over-cap short-circuit are correct** (pass 1). A 9-byte varint
  declares at least 2^56, over every FRET cap, so that throw is never premature; the one-body-byte
  over-read in the "complete but larger than 2^53" case is harmless because that path throws
  unconditionally.
- **The single-clock migration claim holds** (pass 2). Grep of `readFramed(` / `RPC_TIMEOUT_MS`
  across `packages/fret/src` finds exactly three call sites, and no site arms both an outer
  `deadline()` and a finite `readFramed` `timeoutMs`: `src/rpc/request.ts:276` passes `Infinity`
  with the RPC deadline as the sole clock, while `src/rpc/maybe-act.ts:26` and
  `registerJsonHandler` (`src/rpc/protocols.ts:209`) are inbound handlers on the finite 5 s default
  with no outer clock to collide with — `registerRpcHandler`'s close budget is armed only *after*
  `serve` returns.
- **`bs.unwrap()` in `readFramedFromStream`'s `finally` is inert, and the swallow hides nothing**
  (pass 2). `unwrap()` removes all three of its listeners before it calls `stream.push()`;
  `AbstractMessageStream.push` throws `StreamStateError` only when `readStatus` is `'closed'` or
  `'closing'` — the one case the comment names — and otherwise appends and returns immediately via
  the `listenerCount('message') === 0` branch: no dispatch, no `setTimeout`, no re-entry. Pushing
  bytes back onto a stream `releaseRpcStream` is about to close or abort is a no-op.
- **`signalFired` is genuinely a TypeScript narrowing workaround, as its comment claims** (pass 3,
  the item neither prior pass tested). Replacing it with a direct `signal?.aborted === true`
  produces `src/rpc/protocols.ts(564,7): error TS2367: This comparison appears to be unintentional
  because the types 'false | undefined' and 'true' have no overlap` — the entry guard's narrowing
  carried into the catch, which is exactly what the comment says. (The companion `d?.signal` check
  does *not* need the helper, since `d.signal` is never narrowed at entry; it is written through
  the same call for consistency, which is fine.) File restored, tree clean.
- **Both implementations re-read for signal handling and resource cleanup** (pass 3).
  `readFramedFromStream` forwards the read signal into every `bs.read`; `readFramedFromIterable`
  removes its abort listener in a `finally` (so a long-lived run signal does not accumulate one per
  RPC), issues `iter.next()` exactly once, and attaches a no-op catch to the abandoned read. Nothing
  to add.

### Tripwires recorded (conditional; not tickets)

Three `NOTE:` comments added to `packages/fret/src/rpc/protocols.ts` in this pass:

- **At the error-attribution ladder in `readFramed`'s catch** — the `signalFired` pair rewrites
  *every* error, `PayloadTooLargeError` and `FrameTruncationError` included, when a signal has
  fired. Reaching that needs the abort to land in a window spanning microtasks only, while a signal
  fires from a macrotask, so a read decoding a prefix cannot be interrupted there and a signal
  firing during a genuinely pending read rejects that read instead. Where reachable at all,
  cancellation-wins is the intended semantic. Revisit condition stated at the site.
- **At `readFramedFromStream`, on the `lpStream` duplication** — settled as keep-the-hand-roll, with
  the reasons at the site: the over-cap error text is pinned by tests and names the *declared*
  length, which `lpStream` discards behind its own `InvalidDataLengthError`; `lpStream`'s prefix
  loop breaks out on a null read leaving `dataLength` at −1 and then reads −1 bytes, so its
  clean-EOF-at-the-prefix path is not one to depend on; and the 9-byte short-circuit is ours. The
  `lengthDecoder` hook could capture the length but would still need a catch-and-rewrite.
- **At the same site, on per-byte prefix reads** — up to 9 awaits per frame, unmeasured, and
  `lpStream` reads the prefix the same way, so it is the library's shape too. Written as the weaker
  claim (microtask turns against a network round trip) rather than a measured magnitude.
