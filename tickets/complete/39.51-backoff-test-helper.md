## What landed

- **New `packages/fret/test/helpers/backoff.ts`** — `backoffOf(svc)` / `setBackoffOf(svc, pb)`,
  two accessors reaching a `FretService`'s private `backoff` field (a `ProbeBackoff`) through a
  test-only cast. `setBackoffOf` exists because the field is `readonly` in production, so a spec
  needs it to install a fake-clock instance.
- **`ring-membership.spec.ts`** — deleted the `Foreign re-probe backoff growth` block (5 cases,
  156 lines) that exercised the old `backoffMap` / `recordBackoff` / `getBackoffPenalty` /
  `pruneBackoffMap` surface on `FretService`. That surface no longer exists; the same behaviours
  are covered through the `ProbeBackoff` class in `probe-backoff.spec.ts`. The block held the
  file's only `ExpiringMap` use, so that import went with it.
- **`probe-backoff.spec.ts`** — two new cases: two failures inside one still-open window both
  escalate, and `clear()` truly forgets a peer rather than retaining it at factor 0.

### Deleted-coverage audit — one genuine gap, filed as an arm

Checked each of the 5 deleted cases against what `probe-backoff.spec.ts` actually asserts, rather
than taking the handoff's equivalence claim on trust. Four are genuinely replaced:

| Deleted case | Replacement |
|---|---|
| window grows on repeat | `doubles on each further failure: 1, 2, 4, 8, 16, 32` |
| caps at 32 | `caps at maxFactor and stays there across further records` |
| survives an expired window | `retains the escalation once the window closes` |
| resets after retention | `forgets the escalation once retainMs elapses…` + `measures retention from the last failure, not the first` |
| `BACKOFF_RETAIN_MS > base × maxFactor` | `shipped defaults › retention comfortably exceeds the longest backoff window` |

The fifth, `caps at factor 32 **and prunes** evicted peers`, asserted two things. The cap half is
replaced. The **prune half is not**: it pinned a *service-level wiring* fact — that the per-tick
sweep drops backoff entries for peers gone from the routing table — and the unit spec only pins
that `ProbeBackoff.prune(predicate)` honours the predicate it is handed, never that
`FretService` calls it with a store-membership one. `fret-service.ts:3152` could be deleted today
and the suite would stay green.

Not a new ticket: `39.6-probe-backoff-rewire-validation` already owns this site and already
prereqs this ticket, so per the site-claim rule the finding is **appended to it as an arm** rather
than filed fresh. It is cheap to close once 39.52 / 39.53 give that ticket the green suite it is
waiting on.

### Minor — fixed inline

- **`probe-backoff.spec.ts:83-86`, the new escalation case's closing assertion did not
  discriminate.** It advanced `BASE_MS - 1` and asserted still-backed-off, under a comment
  claiming this pinned that the second failure pushed `until` further out. It did not: both
  records land at the same instant, so under a hypothetical non-escalating second failure `until`
  would be that instant + `BASE_MS` and the assertion would pass identically. It could only ever
  restate the `factor === 2` line above it. Changed to `BASE_MS + 1`, which is false under
  factor 1 and true under factor 2, and rewrote the comment to say why that boundary and not a
  smaller one.
- **`helpers/backoff.ts` typed its parameter `unknown`.** The cast has to be written either way
  (the field is `private readonly`), but `unknown` means every argument compiles — including the
  `Libp2pFretService` facade, which has no `backoff` field, where the mistake would surface as an
  `undefined` at runtime. That is precisely the failure mode these helpers exist to remove from
  the specs. Retyped to the concrete `FretService` (`import type`, per `verbatimModuleSyntax`),
  and documented why at the site. Re-ran `tsc --noEmit` after: clean.
