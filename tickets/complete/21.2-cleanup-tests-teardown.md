## What shipped

`test/helpers/cleanup.ts` — a per-case teardown registry. A spec registers each libp2p node and
FRET service *as it builds it* rather than stopping it on the last statement of the case, so an
assertion that fails partway through still tears everything down. Without that, the nodes and
their stabilization timers stay live and `test/mocha-exit-watchdog.ts` fails the run a second time
with an open-handle dump, burying the assertion failure the developer actually needs to read.

Entries unwind newest-first (services before the nodes under them) and each step is best-effort:
one throwing `stop()` is logged and cannot strand the entries behind it.

`buildMesh` in `test/helpers/mesh.ts` takes the registry and registers `mesh.stop()` the moment the
mesh object exists, which is what makes the leak structurally unwritable for mesh-based specs — a
spec author cannot forget a teardown the helper owns. Five specs migrated onto it.

## Review findings

### Verified sound (read, reasoned about, no change needed)

- **Unwind ordering.** Every call site registers nodes before the services built on them, and the
  registry unwinds newest-first, so services stop before their nodes. Checked at each migrated site.
- **`starMesh` coverage.** `buildMesh` registers `mesh.stop()` before returning, so a throw from the
  `addServices` / `connect` calls `starMesh` makes afterwards still tears the mesh down.
- **`proactive-announce` two-mesh and stopped-node-2 cases.** Dropping the `skip: [2]` list is
  correct: `mesh.stop()` stops every service including node 2's, and each stop is best-effort, so
  re-stopping the already-stopped node 2 cannot throw.
- **`network.isolation` service-start ordering shift** (construct-and-start per index rather than
  construct both then start both). Neither case depends on it; in the same-network case the node
  that gets bootstrapped off now starts first, which is if anything the better order.

### Fixed in the review pass

Landed in `71213f3`:

- `test/profile.behavior.spec.ts` migrated off its own private teardown array onto
  `helpers/cleanup.ts` — it was the one migrated file still carrying a duplicate registry. Its
  `starRig` now hands the registry to `buildMesh` rather than registering `mesh.stop()` itself.
- `test/network.isolation.spec.ts`: `makePair` widened from `(cleanup, cfgA, cfgB)` to
  `(cleanup, cfg)` taking the mesh's own per-node config form, so both cases route through it
  instead of one re-inlining the three build calls.
- Trailing blank lines before a closing `})` swept in `profile.behavior.spec.ts` and
  `maybeact-dedup-phases.spec.ts`.

Landed in this pass:

- **`test/helpers/cleanup.spec.ts` written** — the helper had no direct test at all, which is the
  gap that mattered most, since five specs now depend on its exact semantics. Eight cases pin all
  three documented properties plus the hook: newest-first unwind; an async step is awaited before
  the one behind it starts; the registry is emptied by `run()` so a second `run()` is a no-op and a
  later case cannot re-tear-down an earlier one's resources; the registry is emptied *even when a
  step threw*; a throwing step is logged-and-continued rather than aborting the entries behind it,
  with both a sync throw and an async rejection reported in unwind order; `run()` never rejects.
  The `afterEach` that `useCleanup()` installs is pinned by a separate two-case `describe`, since a
  case cannot observe its own teardown — the first registers, the second asserts it ran.
- `test/network.isolation.spec.ts`: dropped two `(mesh.services[i] as any).getDiagnostics?.()`
  casts for direct typed calls. `getDiagnostics` is public on `FretService` and `Mesh.services` is
  typed `FretService[]`, so the cast bought nothing and suppressed real type checking. (These were
  carried over verbatim from the pre-migration code rather than introduced by it.)

### Considered and deliberately left alone

- **`buildMesh`'s construction-throw hole.** A throw from the node factory or `node.start()` on
  iteration *j* strands nodes `0..j-1`, because the mesh object does not exist yet so nothing is
  registered. The site already carries an explicit `NOTE:` at `mesh.ts:86` stating exactly this,
  why the loop is left plain (only reachable if in-memory node construction itself fails), and what
  to do if a watchdog dump is ever traced to it. Accepted tradeoff already recorded at the site —
  re-filing it would be re-discovering a settled decision.
- **`makePair` in `maybeact-dedup-phases.spec.ts`** has the same shape one level down: it registers
  `stopAll([requester, responder])` only after both nodes are constructed and started, so a throw
  from the second `createMemoryNode()` / `start()` strands the first. Same class and same
  unreachability as the above. Closing it is two `cleanup.add` calls instead of one, if a real
  watchdog dump ever points here.
- **`(p: any)` on `network.isolation.spec.ts:57` and the `.store` private-field reach on line 56.**
  `store` is genuinely `private` on `FretService`, so the cast is the only way in from a spec; the
  `(p: any)` is pre-existing and reaching through it would need a typed accessor on the service.
  Out of scope for a teardown ticket, and not worth a public accessor on the service purely for a
  test.

### Categories with nothing to report, and why

- **New tickets filed: none.** Both structural gaps found are the same construction-throw class,
  both are already recorded as accepted tradeoffs at their sites with a stated revisit condition
  ("if a spec ever reports a watchdog dump from a failed mesh construction"), and neither is
  reachable without in-memory libp2p node construction itself failing. Filing would re-open a
  decision a reader already meets at the code.
- **Tripwires recorded: none new.** The two conditional concerns above were already written as
  `NOTE:` comments by the implement stage, which is exactly where a tripwire belongs; this pass
  found no additional "fine now, only matters if X" concern.
- **Documentation: no change needed.** The change is confined to `packages/fret/test/`. The
  testing-strategy section of `docs/fret.md` describes what is tested (unit / integration /
  simulation / benchmarks), not the per-case teardown mechanism, and `AGENTS.md`'s exit-watchdog
  paragraph already describes the watchdog behaviour this helper exists to keep out of the way —
  both still read true. The helper's own doc comment is where a spec author meets it.
