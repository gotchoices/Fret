Phases 2 and 4 of the original `stabilize-tick-concurrency` design. Phase 1 (`runPooled`,
`src/utils/pool.ts`) landed separately as `pooled-task-runner`. Phase 3 (pooling the active-mode
warm-up paths) is `pool-warmup-paths`, still in `implement/`.

## What shipped

`stabilizeOnce` is two pooled phases under one tick-wide `deadline(STABILIZE_TICK_BUDGET_MS =
5000, runSignal)`:

- **Phase 1** pools the ≤ 4 near peers, chaining ping → snapshot-fetch *per peer* (`probeAndFetch`)
  because `fetchNeighbors` is connection-only and it is usually the ping that opens the connection.
  `enforceCapacity` and the single announce run once, after the pool drains — never inside a task.
- **Phase 2** pools the classification and re-probe targets. Each list is still *selected* under its
  own budget and ordering (`classifyTargets`, `reprobeExcludedTargets` → `reprobeOffRingTargets`);
  only execution is pooled.
- Every task is handed the tick signal explicitly and compares against it with `wasCancelled`, so a
  budget cut records no strike, backoff, relevance decay or `pingsFail`.
- Candidate lists rotate under truncation (unknowns by ascending `lastAccess`, re-probe arms by
  ascending backoff factor); the near list stays in ring order on purpose.
- Renames: `probeNeighborsLatency` → `probeNeighborLatency(id, signal)`, `mergeNeighborSnapshots` →
  `fetchAndMergeSnapshot(id, signal)`, `classifyUnknownPeers` → `classifyTargets`,
  `reprobeExcludedPeers` → `reprobeExcludedTargets`, `reprobeOffRing` → `reprobeOffRingTargets`,
  `probeMembership(id)` → `probeMembership(id, signal)`.
- New module-level `logRejected(results, ids, label)` next to `fulfilledValues`: a pooled task that
  *rejects* is logged with its peer id, so pooling does not turn the old `stabilize tick failed:`
  into silence.
- `docs/fret.md` gained a "One tick's RPCs run pooled" bullet and a rewritten cancellation bullet;
  stale method names fixed there and in five spec files' comments.

## Review findings

### Checked

- **The whole implement diff, read before the handoff summary** — `fret-service.ts` (`stabilizeOnce`
  and every helper below it), `live-member.ts`, `docs/fret.md`, `test/stabilize-concurrency.spec.ts`,
  and the five comment-only spec renames. `src/utils/pool.ts` appears in the diff range only because
  it belongs to the already-reviewed `pooled-task-runner`; not re-reviewed here.
- **Stale names.** Swept all `.ts` and `.md` in the repo for the five old method names. Zero hits —
  the rename is complete, including JSDoc `{@link}` targets and doc prose.
- **Cancellation equivalence with the deleted `this.stopped` guards.** `stop()` sets `stopped` and
  aborts `runAbort` together; the tick budget is a `deadline` child of `runSignal`, and `deadline`
  aborts synchronously when its parent is already aborted. `runPooled` checks `signal.aborted`
  before pulling each task, so unstarted tasks come back `skipped` (no scoring) and in-flight RPCs
  abort. The per-peer `if (this.stopped) break;` guards are genuinely subsumed. `budget.cancel()` is
  in the `finally`, and `deadline.cancel()` is idempotent, so the parent-abort path double-cancelling
  is fine — the exit watchdog stayed quiet across the full run.
- **Duplicate announces from the per-task `announced` lists.** Not possible: in both merge loops the
  `if (!this.store.getById(pid))` check and the `this.store.upsert(pid, coord)` are adjacent
  *synchronous* statements, so on a single-threaded loop a second task cannot also see the id as
  first-seen. The concatenated list is duplicate-free without extra bookkeeping.
- **`logRejected` index alignment.** `runPooled` always returns a dense array of `tasks.length`, even
  after an abort, so `ids[i]` names the right peer.
- **Tests.** The eight new cases pin what the design rests on and each assertion is load-bearing: the
  headline hung-peer case, high-water mark *equal* to the cap (an at-most assertion would also pass
  for a serial walk), per-peer ping-before-fetch under real overlap, pairwise disjointness of the
  four candidate sets, two truncation-is-not-evidence cases (cut mid-phase-1 and cut mid-phase-2),
  and `classifyTargets` rotation.
- **Gate.** `npx tsc --noEmit` clean, `yarn build` clean, `yarn test` → **648 passing, 0 failing**.
  There is no lint step in this repo — `yarn format` is forbidden by AGENTS.md (no prettier config,
  it would rewrite every file against the house tab style) and `yarn check` is the stated gate. No
  pre-existing failures surfaced, so nothing was written to `.pre-existing-error.md`.

### Fixed in this pass (minor)

- **`fetchAndMergeSnapshot`'s concurrency NOTE was too narrow.** It documented only "two near peers'
  snapshots can name the same third peer → concurrent `applyTouch`". The reachable case it missed is
  `applyTouch(X)` from peer Y's snapshot merge racing `applySuccess(X)` from peer X's *own* pooled
  task — a collision the tick's disjointness argument does not cover, because the ids a snapshot
  *names* are not one of the four candidate sets. Same accepted class (the pre-existing NOTE on
  `applySuccess` covers lost increments generally), but the statement is now correct. Comment only.
- **Phase 2 selected its targets even after the budget had expired** — three full store walks whose
  every task the pool then `skip`s. Added an `if (budget.signal.aborted) return;` before the
  selection. No behaviour change; it removes wasted work on exactly the ticks that are already
  struggling. Related to plan ticket `15-per-tick-hotpath-waste` point (d), which owns the three
  walks themselves; this does not pre-empt that work.

### Filed (major)

- **`bug-tick-budget-starves-phase-two`** (`backlog/`). One phase-1 task's worst case is 2 s (ping,
  `MAINTENANCE_RPC_TIMEOUT_MS`) + 5 s (snapshot fetch, the route-sized `RPC_TIMEOUT_MS` default) =
  7 s, against a 5 s `STABILIZE_TICK_BUDGET_MS` — and phase 2 is behind a barrier on phase 1. So one
  stalled near peer skips phase 2 for the whole tick, and a peer that answers the ping but stalls the
  fetch never accrues contact failures, stays a near peer, and repeats it every tick — starving the
  *only* path that re-contacts `dead` peers and classifies `unknown` ones. `repro: static`: derived
  from the constants and the call sites, not observed; the ticket names the harness case that would
  confirm it. Filed at the invariant rung ("the per-request limits inside one pooled task must sum to
  strictly less than the tick budget"), not as a point fix, and it lists the three candidate numbers
  to move with the tradeoff of each rather than picking one. Site-claim grep: `15-per-tick-hotpath-waste`
  is the only open ticket naming `fret-service.ts` and it owns a different concern (per-tick walk
  cost), so this is a fresh ticket, not an arm.

### Tripwires

None added by this review. The four the implementer parked (`classifyTargets` three store walks,
shared `backoffMap` across re-probe arms, per-mode tick budget, the two `fetchAndMergeSnapshot`
NOTEs) were re-read at their sites and are correctly scoped; one of them is widened above.

### Considered and declined

- **The high-water-`=== cap` assertion depends on `runPooled` spawning workers synchronously and each
  task reaching `newStream` with no intervening `await`.** Verified that path (`sendPing` →
  `openRpcStream` → `getConnections` → `newStream`) holds today, and `runPooled`'s own JSDoc already
  states the synchronous-start requirement with `test/pool.spec.ts` pinning it. The assertion's
  failure message says what to loosen. Left as-is — weakening it to `at.most` would forfeit the only
  proof that the tick actually overlaps.
- **`logRejected` has no test.** No pooled task can currently reject (each catches its own RPC
  failure and `noteRpcFailure` guards its own bookkeeping), so there is no honest trigger to write a
  test against. It is hardening against a future task bug. Manufacturing a rejection would test the
  stub, not the service.
- **The `snapshotsFetched` overcount** on a fetch cancelled mid-flight is documented as accepted at
  the site and `dead-state.spec.ts` asserts it, so changing it flips a test deliberately.
- **The lost-increment race on `applySuccess` / `applyFailure`** carries an accepted-tradeoff NOTE at
  its site with a stated revisit condition (the counters becoming load-bearing for quorum or fairness
  accounting). That condition has not tripped; not re-filed.

### Not covered

- **No test drives the tick through the real loop with a `stop()` mid-tick**, confirming both that
  the tick collapses and that the loop does not re-arm. The implementer flagged this and it is still
  true. Judged inferable rather than a gap worth a ticket: `stop()` semantics are pinned by
  `7.3-rpc-service-signals-lifecycle-tests`, the tick signal is a `deadline` child of the run signal,
  and the two truncation-is-not-evidence cases already exercise the abort path through the pool with
  the identical mechanism.
- **The active-mode interaction** (5 s tick budget against a 300 ms active interval) is unmeasured
  and stays a note at `STABILIZE_TICK_BUDGET_MS`. It was already true of the serial tick, and
  measuring it needs a load harness this repo does not have.
- **`docs/fret.md`'s *Operating profiles* pre-dial wording** is untouched; revising it belongs to
  `pool-warmup-paths`.
