## What landed

`runPooled<T>(tasks, { concurrency, signal? })` in `packages/fret/src/utils/pool.ts`, matching
the interface the implement ticket specified:

```ts
export type PoolResult<T> =
	| { status: 'fulfilled'; value: T }
	| { status: 'rejected'; reason: unknown }
	| { status: 'skipped' }

export interface PoolOptions {
	concurrency: number
	signal?: AbortSignal
}

export function runPooled<T>(
	tasks: ReadonlyArray<() => Promise<T>>,
	opts: PoolOptions
): Promise<Array<PoolResult<T>>>
```

A shared index cursor plus `min(concurrency, tasks.length)` worker loops. Each worker checks
`signal.aborted` before pulling a task; if aborted it marks that index `skipped` and keeps
draining the cursor rather than returning, so the result array is always dense and always
`tasks.length` long. Tasks that reject, and tasks that throw *synchronously* before returning a
promise, are both caught by the worker's `try`/`catch` — `runPooled` itself never rejects.

`concurrency` is clamped: non-finite (`NaN`, `Infinity`), zero, or negative → 1; fractional values
floor. `tasks.length === 0` short-circuits before any worker is spawned. Nothing in `src/`
imports it yet; `7.6-stabilize-tick-concurrency` is the consumer.

## Review findings

### Correctness of `runPooled` — nothing found

Read the implementation line by line against the interface before reading the handoff summary.
No defect found, and the claims it makes hold:

- **Density.** Every index 0…`len-1` is claimed by exactly one `cursor++` and every claim writes a
  result on all three paths (`skipped` / `fulfilled` / `rejected`), so the array cannot have holes.
- **Never rejects.** The only expression that can throw inside a worker is `tasks[index]!()` and
  its `await`, and both sit inside the `try`. A hole or a non-function in the `tasks` array throws
  a `TypeError` there and lands as `rejected`, which is the right answer, not an escape.
- **Bound.** At most `min(concurrency, tasks.length)` workers exist and each holds at most one task,
  so the in-flight count cannot exceed `concurrency`.
- **Clamp.** `Number.isFinite` rejects `NaN` and `Infinity` before `Math.floor`, which is the order
  that matters — `Math.floor(Infinity)` is `Infinity` and would have spawned an unbounded fleet.
  The `ExpiringMap` precedent the doc comment cites is real (`src/utils/expiring-map.ts`, capacity
  clamp with the same "unbounded is unwritable" reasoning).
- **No timers, no listeners**, so nothing for the mocha exit watchdog to catch — confirmed by the
  clean suite exit rather than by inspection alone.

Checked for a duplicate primitive before accepting a new one: `grep` over `src/` finds no other
bounded-concurrency helper and only one unrelated two-element `Promise.all`
(`service/fret-service.ts:933`). No DRY violation.

### Minor — fixed in this pass

- **The property test never asserted index alignment by value.** It checked length and that every
  result was `fulfilled`, but not that result *i* came from task *i*. That is the module's central
  claim, and the property test is the only case in the suite that actually generates out-of-order
  completion (the dedicated shape test runs four tasks at concurrency 2 in effectively index
  order). Each task already returned its own hop count, so the assertion was one line away.
  Added `expect(results.map(...)).to.deep.equal(delays)`.
- **No test for a signal already aborted before the call.** This is reachable in the intended
  consumer, not hypothetical: `deadline(ms, parent)` returns a synchronously-aborted signal when
  `parent` is already aborted (`src/utils/deadline.ts:50`), so a tick armed after `stop()` hands
  the pool exactly this. Added a test asserting no task runs and every index comes back `skipped`.
- **Fractional flooring had no test** — the implementer flagged this as an open question. Added one
  (`concurrency: 2.9` must saturate at 2, not 3).
- **The synchronous-worker-spawn invariant lived only in the handoff ticket.** `runPooled` is
  deliberately a plain function, not `async`, so the first `min(concurrency, len)` tasks have run
  up to their own first `await` by the time the caller's next statement executes. That is a real
  property, and TypeScript actively suggests undoing it (suggestion 80006, "may be converted to an
  async function"), so the reason belongs at the site, not in an archived ticket. Added a `NOTE:`.
  One correction to the handoff's framing: converting to `async` would **not** break it silently —
  the abort test asserts the synchronous start directly and would fail loudly.
- **`AGENTS.md` project-layout tree was stale.** It listed `utils/token-bucket.ts` as the only file
  in `src/utils/`; the directory holds four (`deadline`, `expiring-map`, `pool`, `token-bucket`).
  Pre-existing drift that this change widened, and that tree is the file agents are told to read
  instead of exploring. Updated to `utils/{token-bucket,expiring-map,deadline,pool}.ts`.

### Major — none

No finding rose to a new ticket. The module is 79 lines, one exported function plus one private
helper, no shared mutable state beyond the closure, and its only consumer is a ticket that already
owns its own integration tests. There is no class of defect here to retire with a type change,
a generalized test, or a boundary invariant.

### Tripwires — none recorded, and why

Two candidates were considered and deliberately **not** parked as `NOTE:`s, because neither is
conditional on anything a plausible caller could reach:

- *Abort drains the remaining cursor synchronously* (one array write per un-started index, in a
  tight loop with no `await`). At the intended call site's ~20 tasks this is unmeasurable, and even
  at 10⁶ tasks it is a few milliseconds of array writes. A `NOTE:` here would be noise.
- *No per-task timeout.* Deliberate, and already stated in the existing doc comment ("The pool
  never aborts on its own — cancellation is entirely the caller's"). `7.6` supplies the tick
  deadline. Nothing to add.

### Accepted tradeoffs — none pre-existing at this site

No `NOTE: accepted tradeoff` exists in `src/utils/`, so no finding was suppressed on that basis.
The new `NOTE:` added above is a design-invariant marker, not a declined finding.

### Docs

`docs/fret.md` deliberately **not** touched. `pool.ts` is an internal primitive with no importer
and no architectural surface yet — it appears nowhere in the ring, membership, stabilization or
wire-format models the design document describes. `7.6-stabilize-tick-concurrency` owns the design
document update, and its TODO already names the two sections to change (*Stabilization and churn
handling* for the tick's concurrency bound and budget, *Operating profiles* for Core 6 / Edge 2
governing maintenance RPCs). Documenting a bound here that the service does not yet apply would be
wrong the moment a reader checked it. `AGENTS.md` **was** updated, because it indexes source layout
rather than design, and a new source file is exactly what it is meant to track.

### Test coverage — assessed, then extended

The implementer's five cases covered happy path, mixed result shapes (including the sync-throw
error path), abort mid-run, and the degenerate-concurrency and empty-list edges. The three gaps
found were all in the *edge / regression* band rather than the happy path, and all three are fixed
above. Interaction coverage is deliberately absent and correctly so — there is no interaction to
test until `7.6` wires the primitive in, and re-testing the primitive from the integration side
would duplicate this suite. Suite is now 10 tests.
