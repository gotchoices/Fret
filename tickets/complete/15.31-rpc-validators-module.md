First of three tickets split out of `15.3-rpc-json-handler-seam`. Landed the **validator module
only**: `src/rpc/validate.ts`, holding every inbound wire-shape rule behind one uniform signature
`Parser<T> = (msg: unknown) => T | undefined`, where `undefined` means reject and any other return
is the message as normalized. Seven parsers (`parseRouteAndMaybeAct`, `parseLeaveNotice`,
`makeSnapshotParser`, `parsePingResponse`, `parseNearAnchor`, `parseMaybeActReply`) plus the
`sanitizeReplacements` helper, all exported from the package root.

`validateRouteAndMaybeAct` moved out of `maybe-act.ts` (renamed) and `sanitizeReplacements` out of
`leave.ts` — moves, not copies, with both importers updated and no compatibility re-export. Only
`parseRouteAndMaybeAct` has a production caller today; the other parsers are wired up by the two
sibling tickets, `15.32-rpc-json-handler-seam` and `15.33-rpc-reply-parsers-and-caps`.

Docs: `docs/fret.md` gained a *Wire-shape parsers* subsection under *Wire formats*, and the
*Cheap-guard rejections* bullet now names the new symbol and file.

## Review findings

Reviewed across four passes; the first three were each cut by the token budget before running the
gate, so this pass ran it first. Findings below are what the whole review produced.

### Gate — passes, and the handoff's failure claims are stale

Run from `packages/fret/`:

- `npx tsc --noEmit` — **0 errors.** The handoff reported 27 pre-existing errors in
  `test/rpc.stream-errors.spec.ts`; they are gone.
- `yarn build` — **passes** (exit 0).
- `yarn test` — **909 passing, 0 failing.** The handoff reported 31 pre-existing failures across
  four specs (`rpc.stream-errors`, `maybeact-dedup-phases`, `rpc.protocols`, `dead-state`), all
  asserting pre-`RpcOutcome` sender returns. The triage commit `e13eb11` landed those assertion
  fixes after the handoff was written, so nothing is outstanding and **no
  `tickets/.pre-existing-error.md` was written**. Nothing was skipped, disabled, or loosened.

### Correctness of the rules against the receivers they replace

The core review question, since five of seven parsers have no production caller yet and the rules
were written by reading the merge loops rather than by running against them. Compared line by line:

- **Snapshot id lists** match `mergeAnnounceSnapshot` and `fetchAndMergeSnapshot` exactly —
  truncate-then-drop-non-strings yields the same surviving set as today's `slice(0, cap)` plus a
  per-id parse inside a caught `try`. `makeSnapshotParser`'s caps come from `mergeSnapshotCaps()`
  (Core 16/16/8, Edge 8/8/6), which is the same number the merge loops slice to.
- **`parseLeaveNotice`'s two rejects are a strict subset of today's checks**, so it cannot refuse a
  notice the current receiver accepts: `from` must already equal the transport-authenticated
  `connection.remotePeer`, and `handleLeave` applies the stricter ±30 s timestamp bound.
  `sanitizeReplacements` matches `recordLeaveReplacements`, which still owns the dedup/self/dialable
  checks; the parser owns only the ≤ 12 bound and the parse-check.
- **`parseNearAnchor` cannot reject our own replies** — every producer (`buildNearAnchor`,
  `nearAnchorOnly`, `staticReject`) emits finite numerics — and its 8 / 16 caps cannot refuse our
  own output: `pickAnchors` returns ≤ 2 and `cohort_hint` is ≤ 8, so both caps are ≥ 2×.
- **`parseRouteAndMaybeAct` is a faithful move**, same checks in the same order, with exactly one
  added rule (`digest` capped at 4096 chars). The guard→parser conversion is safe at its call site:
  `handleMaybeAct`'s parameter is already declared `RouteAndMaybeActV1` (the cast happens upstream
  in `registerMaybeAct`), so no type narrowing was in use to lose.

**One rule found stricter than the code it replaces:** `parseSample` drops any entry whose
`relevance` is not finite, while both merge loops read only `s.id` and `s.coord` and never touch
`relevance`. Harmless until `15.33` rewires the loops, at which point it silently drops sample
entries today's receiver keeps. Filed as an arm on `tickets/implement/15.33-rpc-reply-parsers-and-caps`.

### Major — filed, not fixed here

Both were appended as arms to `tickets/implement/15.33-rpc-reply-parsers-and-caps.md` rather than
filed as new tickets, since both resolve at the site that ticket already owns:

- A `Parser<T>` returning `undefined` wired straight into `rpcRequest`'s `decode` yields
  `{kind:'ok', value: undefined}` — `decodeReply` has no undefined check, and `T` infers as
  `Reply | undefined`, so it does not fail at compile time either. Not a defect in this diff
  (nothing wires it yet), but it invalidates a premise stated in `15.33`'s own Design section.
- The `parseSample` `relevance` strictness above.

A third arm was appended to `tickets/implement/15.32-rpc-json-handler-seam.md`: the handler
migration must not hoist a parse ahead of the rate-limit bucket (bucket-first is load-bearing and
documented), and it must decide deliberately which diagnostics counter each rejection lands in —
a bad leave timestamp counts as `timestampBounds` today and would count as `malformed` through
`parseLeaveNotice`.

### Minor — fixed in this pass

- `parseRouteAndMaybeAct`'s return value is discarded at its only call site
  (`fret-service.ts:1153` uses the raw `msg` from there down). Correct today — it is the one parser
  that normalizes nothing and returns its own argument — but it breaks silently, with no compile
  error, the day someone adds a normalization to it. Recorded as a `NOTE:` tripwire at that call
  site rather than filed, since it is conditional on a change that has not happened.

### Considered and declined — no action

- **`{ ...msg }` then `delete out.field`** in `parseLeaveNotice`, `makeSnapshotParser` and
  `parseNearAnchor`. Behaviorally right (the encoder drops `undefined`-valued properties, so an
  absent optional must stay absent, and assigning `undefined` would not be the same thing).
  Cosmetic only, and no measurement was taken, so per the ticket rules it is not filed.
- **Uniform in signature but not in aliasing** — `parseRouteAndMaybeAct` returns its argument while
  the other message parsers return a shallow copy. Deliberate and documented at the function, and
  the cost of copying uniformly is an allocation per inbound message on the hottest path. The
  tripwire above covers the failure mode this creates.
- **`parseNearAnchor` rejecting a non-finite `estimated_cluster_size` / `confidence`** rather than
  defaulting to 0. The implementer flagged this as open. Reject is consistent with every other
  required scalar on this wire, and the caller's fallback is well-defined (an emptied anchor list
  already falls back to the local cohort). Kept.
- **`v` and `sig` unchecked, `metadata` values unchecked.** All three are stated in the module
  docstring with reasons (no version negotiation exists, message signing is unimplemented, metadata
  values are arbitrary JSON by the wire format's own definition). Agreed.

### Tests

Read as tests, not counted. The three tiers do different jobs and all three hold:

- **Tier 1 (never reject our own encoder's output)** pushes generated *legal* instances through the
  real `encodeJson` → `decodeJson` and asserts deep equality against the expected normalized value,
  not merely non-rejection. This is the over-strict direction, which hand-written cases cannot find.
  The legal arbitraries correctly avoid reusing this file's existing ones (which draw ids from
  `arbNastyString` on purpose) and build a pool of real Ed25519 peer ids instead.
- **Tier 2 (never throws)** runs all six parsers over arbitrary JSON, the illegal wire arbitraries,
  and 14 named hostile shapes including a null-prototype object.
- **Tier 3 (the table)** asserts normalized *values* — verified, this is the claim that matters,
  since truncation and drop-entry are invisible to a "did not reject" assertion. The
  truncate-before-filter case and the "emptied replacement list reports as absent, not `[]`" case
  are both pinned.

One gap worth stating rather than fixing: the Tier-1 properties have **no distribution assertion**
of their own, so nothing in that describe proves the all-optionals-absent shape was generated. The
`withOptionals` helper uses `fc.subarray`, which is uniform across subsets (so the empty subset
arrives roughly 1-in-16 over 200 runs), and the round-trip describe higher in the same file asserts
both regions empirically using the same helper and run budget. Coverage is therefore sound by
construction plus adjacent evidence, but not asserted at the site. Left as-is.

### Handoff's own "Known gaps" — dispositioned

- *No production caller for five of seven parsers* — addressed by the line-by-line comparison above;
  one discrepancy found and filed.
- *Caps exercised at Core numbers only* — the parser is cap-generic and the table derives its
  expectations from the `CAPS` constant, so Edge is covered by construction. Not worth an extra run.
- *Never-throws property covers values, not exotic objects* (throwing getters, `Proxy` traps) —
  correct and unreachable from `decodeJson`, which parses JSON. No action.
- *`parseMaybeActReply` does not recognise a busy reply* — **verified correct at the seam.**
  `rpcRequest` classifies `BusyResponseV1` before `decode` runs, confirmed by reading `decodeReply`
  in `src/rpc/request.ts`. `15.33` is where it gets exercised for real.
- *The 8 / 16 reply caps are argued, not measured under load* — confirmed at the shape level by
  reading the producers (above). Still true that nothing *pins* the producers at those numbers; a
  future change emitting 20 cohort hints would be silently truncated by the receiver. Not filed —
  it is conditional on a change nobody has proposed.

### Tripwires

- Pre-existing, parked by the implementer at `parseSample` in `src/rpc/validate.ts`: the
  skip-and-log emits one line per dropped sample entry, so a hostile peer costs `cap` lines per
  message. Harmless today (debug-gated logger, neighbors token bucket meters the messages).
  Indexed here, not re-analyzed.
- New, parked by this review at `fret-service.ts:1153`: the discarded parser return value, above.
