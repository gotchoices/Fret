## What shipped

`packages/fret/test/rpc.handler-fuzz.spec.ts` gained three things:

- **`body-level drop hooks: onMalformed reason vs identity mismatch`** — a table-driven describe
  over the two protocols with a request body on the `registerJsonHandler` seam (`leave`, and the
  *announce* half of `registerNeighbors`), five cases each. It pins the `reason` value by
  identity (`'decode'` for a body that is not JSON and for one that decodes to a non-object;
  `'parse'` for a decodable object the parser refuses) and pins the split against the identity
  path: an unparseable `from` counts malformed and never as a mismatch, a parseable-but-wrong
  `from` counts as a mismatch and never as malformed. Every case also asserts the drop is a close
  (`closes: 1, aborts: 0`), that no reply was written, and that the handler body never ran.
- **`registerNeighbors' defaulted snapshotParser`** — two cases for the trailing defaulted
  parameter, previously unreachable from production and untested. Shape checking is live in the
  default (a malformed snapshot still drops) and the `Infinity` caps truncate nothing (50
  successors, well past Core's cap of 16, arrive whole and in order).
- **One new wire-tier matrix row** (`leave: unparseable from`), which exercises the counter split
  through the real service diagnostics over the memory transport rather than through
  directly-passed hooks.

## Review findings

Ran the implement diff first, then read `src/rpc/protocols.ts` (`registerJsonHandler`),
`src/rpc/leave.ts`, `src/rpc/neighbors.ts`, `src/rpc/maybe-act.ts`, and the service's counter
wiring (`fret-service.ts` ~1029 and ~1060) before reading the handoff.

**Fixed in this pass (minor)**

- *The wire matrix decided which counter a row feeds by matching its name.* `runMatrix` computed
  the identity-vs-malformed split with `rows.filter(r => r.name.endsWith('from mismatch'))`. The
  two drop kinds are indistinguishable on the wire — both are a close with no reply — so the row
  *name* was the only thing carrying the accounting, and the next row named `... from mismatch`
  that was not an identity case would have silently misaccounted both totals at once. The
  implementer flagged this as a review focus rather than fixing it. Replaced with an explicit
  `counts?: 'malformed' | 'identityMismatch'` field stated per row, plus an assertion that every
  `reject`/`drop` row states one — so a future row that forgets its accounting fails loudly
  instead of being absorbed into the other counter's total. Same rung-1 move the workflow asks
  for: the bad state is no longer expressible, rather than guarded against per instance.

**Checked and found correct — the implementer's three suggested focus points**

- *Does announce's `parseReject` body reach the parser arm rather than the decode arm?* Yes. It
  is a well-formed JSON object, so `decodeJson` succeeds; `makeSnapshotParser` then refuses it on
  `from`. The test asserting `['parse']` by value is what proves the arm, and it would fail if the
  body took the decode path.
- *Is `peerIdStr(10 + i)` distinct across 50 successors?* Yes. `mh.fill(seed, 6)` writes the seed
  as a byte, and seeds 10..59 are all distinct values under 256.
- *Is the matrix row's placement consistent with `runMatrix`'s split?* It was, but only by name.
  Superseded by the fix above.

**Checked, nothing found**

- **Counter wiring.** Both service call sites pass `onMalformed` arms that increment
  `diag.rejected.malformed` and ignore the `reason` argument, exactly as the handoff states. The
  `reason` value is therefore invisible at the wire tier today, which makes the implementer's
  unit-tier/wire-tier split the right call rather than a shortcut.
- **Protocols correctly absent from the tables.** `ping` and the neighbors *request* take the
  reply-only overload of `registerJsonHandler` — they read no body, so they have no decode, no
  parse, and no `onMalformed`. `maybeAct` is on `registerRpcHandler` directly, not this seam.
- **The optional-hook path.** `registerJsonHandler` calls `opts.onMalformed?.(...)`. The defaulted
  `snapshotParser` cases exercise the `undefined` case for announce, since omitting the parser
  forces omitting the hook after it.
- **Resource cleanup and error handling.** Every new case asserts the release arm, not merely a
  release count. No new case can leak a rejection past the describe-level `unhandledRejection`
  guard, and none did.
- **Source hygiene.** Spec is 1109 lines with four clearly separated tiers, the new blocks sit
  where the handoff says they do, helpers are short and named, and the comments explain *why* a
  case exists rather than restating the assertion. No duplication introduced: the new describe
  reuses `fakeNode` / `inboundStub` / `framed` / `json` rather than growing parallel rigs.

**Filed as an arm on an existing ticket (major-adjacent, not new)**

- *One protocol reports no rejection counter at all for an undecodable body.* An undecodable
  `leave` or announce body drops and counts `malformed`; an undecodable `maybeAct` body throws,
  aborts the stream, and moves no counter. That is an unevenness in what `diag.rejected` promises,
  at the same site as the already-open `backlog/debt-rejection-diagnostics-conflated`, so it was
  appended there as a second arm rather than filed fresh. Not a defect in this ticket's work —
  the tests correctly pin today's behavior.

**Empty categories, with reasons**

- *No tripwires parked.* Nothing conditional surfaced. The one concern that looked like a
  candidate (the name-matched split) is not "fine now, matters if X later" — it is wrong the
  moment anyone adds a row, so it was fixed rather than demoted.
- *No new fix/plan tickets.* The one finding worth carrying had an open ticket at its site
  already; everything else resolved inline or checked out clean.
- *No docs update in this ticket.* `docs/fret.md` is stale on one line — the *Cheap-guard
  rejections* section still says the non-maybeAct handlers "are moved onto a shared JSON handler
  seam by `tickets/implement/15.32-rpc-json-handler-seam`", a ticket that has since landed and is
  in `complete/`. That line is owned by `implement/15.326-rpc-json-handler-docs`, which is still
  open and covers exactly this seam's documentation, so re-stating it here would duplicate it.
  No other documented behavior changed: this ticket added tests only.
