## What shipped

`DigitreeStore` maintains two O(1) tallies beside the tree and id index:
`membershipCounts` / `stateCounts`, bumped only by `tally(entry, ±1)` at the store's two
mutation seams — `put` (outgoing prior entry down, incoming entry up, so insert, re-key and
replace are one rule) and `remove` (inside the existing `if (p.on)` guard, so removing an
absent id is a no-op for the counts too). Readers `countByMembership(m)` / `countByState(s)`
return 0 for a label never seen.

Coverage: the existing `fast-check` model property (`checkInvariants`) recounts both tallies
from `list()` after **every** op of the 60-op arbitrary sequence, plus six targeted cases
(empty store, membership-only move, state-only move, remove decrements both, `importEntries`
replace recounts rather than sums, double-remove / never-inserted never goes negative).

Nothing consumes the readers yet — that is `implement/16.6-probe-pass-shared-walk`, which
this ticket was deliberately split from.

## Review findings

**Checked:** the full implement diff (`380e36f` store, `7d001e4` + `c3d152d` tests) read
before the handoff summary; both tally call sites against the seam invariant they ride;
whether any write path can bypass the seams; whether any caller mutates a stored entry in
place; the test property's op coverage; docs for every file the change touches.

**Correctness — no defects found, and here is the argument, not an impression.** The one way
this design fails silently is a `put` whose `prevEntry` is the *same object* as `entry` (the
decrement and the increment would then land on the same label, leaving the count stuck on the
old one). Every caller of `put` builds a fresh object: `upsert` spreads (`{...prev, coord,
lastAccess}`), `update` spreads (`{...cur, ...patch}`), `importEntries` constructs. And no
code outside the store mutates a stored entry field — verified by grep for `.state = `,
`.membership = `, `.relevance = `, `.lastAccess = `, `.metadata = `, the four failure
counters and the three health counters across `src/` and `test/`: the only hits are
`fret-service.ts` building *patch objects* for `update`, plus two unrelated (a validator's
local `out.metadata`, the simulator RNG's own `this.state`). `list()` does hand out live
references, so the seam-only rule is a convention the property test enforces rather than a
type guarantee — which is what the tripwire below is for.

**Minor (fixed in this pass):**
- `docs/fret.md` *Routing store (Digitree) & indices (A2)* still described the store as
  keeping exactly two views of its population. Added the third: the per-label counts, where
  they are maintained, why counting does not violate the store's network-agnostic rule (it
  tallies fields it already owns and still never asks what a label means), and why a zero
  count soundly proves a narrower compound predicate empty — the property `16.6` depends on.

**Major:** none. No new ticket filed.

**Tripwires (recorded, not ticketed):**
- `bumpCount` folds a would-be negative count into a `delete`, so a desync would surface as a
  silently-clamped zero rather than a throw. Unreachable while every write goes through
  `put`/`remove`, and the property test recounts after every op. Parked as a `NOTE:` at
  `bumpCount` in `packages/fret/src/store/digitree-store.ts` saying to make it throw if a
  write path ever lands outside those seams.

**Considered and declined (no action):**
- The tally overhead is unmeasured. It is two `Map` get/set per write with a fixed 3-key
  domain; there is no magnitude worth measuring, and the ticket that consumes the counts
  removes three full-table walks per tick in exchange.
- The readers are currently unused. That is the ticket's stated scope, not an oversight.

**Pre-existing failures:** none — the suite is fully green (see below), so nothing was
written to `tickets/.pre-existing-error.md`.
