**One finding, fixed inline (minor).** The security section asserted, without qualification, that
"Each bucket is taken **before** the handler's own validity checks, so invalid messages are metered
too." The shared seam parses *in the handler body*, before calling the service method that takes
the bucket — so for leave (`handleLeave`) and announce (`handleAnnounce`) the wire-shape parse now
runs unmetered. `15.32` recorded this at the leave site as an accepted tradeoff
(`fret-service.ts:1600`, with the bounding argument) but the design doc still stated the general
rule as absolute, and the paragraph this ticket rewrote is exactly what that sentence
cross-references. Fixed by stating the exception and its bound: only an O(message size) parser runs
unmetered, no hashing and no ring walk, already capped by the protocol byte cap (leave 4096;
announce truncates id lists and sample to the merge caps before vetting entries). maybeAct — the
expensive parse — keeps its bucket strictly first.

**Tripwire parked, not filed.** Announce has no equivalent of the leave site's accepted-tradeoff
`NOTE:`, even though its unmetered parse is the larger of the two (it walks up to the merge caps of
id and sample entries and base64-decodes each sample coordinate). It is bounded and cheap today, so
this is conditional, not a defect. Parked as the docs bullet above rather than as a code comment —
the concern spans two handlers and one seam, so it has no single code site — and deliberately not
filed as a ticket. Revisit condition: if a per-message inbound cost ever shows up in a profile, or
if a future parser on this seam does hashing or a ring walk.
