## Review findings

### Migration audit — clean

The two migration commits (`d93c54e`, `c71be3d`) were re-read line by line against their
pre-migration bodies. Faithful. Confirmed specifically:

- `addServices(...)` runs before `connect('star')` in both service-bearing rigs, matching the
  original order and the helper's documented construct-then-dial path.
- `bootstraps` preserved verbatim, including node 0 bootstrapping off itself — which is exactly
  why these rigs correctly do *not* use the shorter `starMesh` helper (that one gives node 0 an
  empty bootstrap list, so switching would have silently changed behavior).
- `mesh.stop({ skip: [n] })` skips both the service and the node at index `n`, and the services
  array is index-parallel to nodes, so it faithfully replaces the original "stop all but index N"
  teardown.
- The third rig builds no services, and `mesh.stop()` with an empty services array falls straight
  through to `stopAll(nodes)` as the original did.
- The long "what this rig can observe" comment on the fan-out rig survived intact.
- The remaining `createMemNode` / `stopAll` imports are genuinely still used by two out-of-scope
  describe blocks lower in the file, which build nodes by hand for real reasons (one grows nodes
  mid-test, one deliberately never starts its service) that the mesh helper does not express.

### One behavior difference, judged acceptable and not changed

The original teardown stopped surviving services concurrently via `Promise.all` and propagated a
throw; `mesh.stop()` stops them sequentially and swallows throws. That is the mesh helper's stated
best-effort teardown contract, and the assertion these tests actually make — that the *departing*
service's `stop()` does not throw — is still made directly and un-swallowed.

### Minor findings, all fixed inline

- **Redundant recompute (`churn.leave.spec.ts`).** The third rig called
  `mesh.nodes[1]!.peerId.toString()` twice where the mesh already precomputes that exact string as
  `mesh.ids[1]!` (and the same rig already used `mesh.ids[0]!` elsewhere). Replaced; provably
  identical, since `ids` is built as `nodes.map(n => n.peerId.toString())`.

- **Teardown-on-throw, `churn.leave.spec.ts`.** All three rigs called `mesh.stop()` as their last
  statement with no `afterEach`, so a rig whose assertion or `waitFor` gate threw left its libp2p
  nodes running and the mocha exit watchdog fired a second, unrelated-looking failure on top of the
  real one — costly in this file specifically, which already carries a comment about a past
  full-suite stall. Pre-existing (the hand-rolled rigs had the identical shape). **Fixed inline**
  rather than recorded as a tripwire, because the exact pattern already ships in this repo at
  `test/libp2p-memory.integration.spec.ts:87-104` — a hoisted `let mesh: Mesh | undefined` plus an
  `alreadyStopped: number[]` that the two `skip`-using rigs push to right after they stop their own
  node, and an `afterEach` calling `mesh?.stop({ skip: alreadyStopped })` and resetting both. A
  convention to follow, not a pattern to invent. Three narrowing errors fell out of hoisting
  (`mesh` is a captured `let`, so TypeScript discards its narrowing inside callbacks); fixed by
  using the `addServices` config callback's own mesh argument and by binding one local `const`.

- **Same-class teardown leak, `profile.behavior.spec.ts` — fixed this leg, and fixed one rung
  higher than the instance.** The four mesh-using cases (two under `Snapshot export caps`, two
  under `Snapshot receive caps`) had the identical end-of-body teardown and the identical leak on a
  throwing assertion, and were worse than the churn rigs: each also constructs a `FretService`
  directly rather than through `mesh.addServices`, so `mesh.stop()` never covered it, and the two
  receive-caps cases each build a whole separate node plus two services. Every `createService`-based
  case in the file (roughly twenty) had the same shape.

  Rather than fix four sites, the file now carries a **teardown registry**: a module-level
  `cleanups` array, an `onCleanup(fn)` registrar, and one `afterEach(runCleanups)` that unwinds in
  reverse construction order, best-effort per entry (a throwing `stop()` cannot strand the entries
  behind it — the same contract `mesh.stop()` already applies to its own services). Four small
  factories register on the caller's behalf — `createService`, `startService` (a service on a node
  the mesh does not own), `startNode` (a bare node), `starRig` (`buildMesh` + star dial) — so the
  leak is no longer expressible at a call site: constructing through a factory *is* registering.
  Every explicit trailing `stop()` pair is gone. This is the invariant that retires the class, so
  no ticket was filed for the instances. Reverse order is what keeps it correct: a service on a
  mesh node is registered after its mesh and therefore stops before it.

  Two incidental cleanups fell out: the four cases' hand-rolled
  `await new Promise(r => setTimeout(r, 2000))` now use a local `delay` helper matching the one in
  `churn.leave.spec.ts`, and `onCleanup(() => node.stop())` needed an `async` wrapper because
  `Libp2p.stop()` is typed `void | Promise<void>` (caught by `tsc`, not by a test).

  One assertion was added rather than merely moved: the receive-caps cases now assert the sender's
  store is non-empty. Previously `sender` was referenced only by its own trailing `stop()`; with
  that gone the binding would have been unused, and asserting the rig actually converged is the
  honest reason to keep it — an at-most cap over a sender that learned nothing passes vacuously.
