Half 2 of `plan/16.5-probe-pass-store-walks` (point (d) of `16-per-tick-hotpath-waste`). Half 1
(`16.5-probe-pass-store-counts`) added the store's O(1) per-label counts; this consumed them.

## What shipped

`FretService.phaseTwoTargets()` is now the tick's only phase-2 selector. It reads three O(1) store
counts — `countByMembership('unknown')`, `countByMembership('foreign')`, `countByState('dead')` —
and returns `[]` without walking when all three are zero. Otherwise it takes **one** `store.list()`
and hands that array to all three arms. `classifyTargets` / `reprobeExcludedTargets` take the walk
as a defaulted parameter (so bare `(svc as any)` test calls still work); `reprobeOffRingTargets`
takes it as a required first parameter. No budget, predicate or ordering changed — only the walk is
shared, never the candidate lists. `docs/fret.md`'s *Two phases* bullet and the A2 per-label-counts
bullet state the new zero/one-walk cost.

Five tests appended to `test/stabilize-concurrency.spec.ts` under "phase-2 target selection: shared
walk behind an O(1) count gate", counting `store.list` calls around each call.

## Review findings

### Checked

- **The implement diff read first** (`git show 773e903`), before the handoff summary — service,
  tests, docs.
- **The count gate's premise, at the store.** Read `src/store/digitree-store.ts` in full.
  `countByMembership` / `countByState` are bumped only in `put` (outgoing prior entry down,
  incoming up) and `remove`, and every mutation path — `upsert`, `update`, `setState`,
  `setMembership`, `importEntries` — funnels through `put`. The counts cannot lag a label change
  made through the public store API.
- **Soundness of "zero count ⇒ arm empty".** Each arm's predicate is a narrowing of exactly one
  counted single-field label (classify ⊂ `membership === 'unknown'`, foreign arm ⊂
  `membership === 'foreign'`, dead arm = `state === 'dead'`); the extra conditions — `id !== self`,
  `state !== 'dead'`, `getBackoffPenalty === 0`, connected/has-addresses — only remove candidates.
  A count wrong high costs one wasted walk; wrong low would silently stop the pass, and the counts
  themselves are pinned by the prior ticket's model-based property test
  (`test/digitree.invariants.spec.ts`).
- **Self does not break the zero-walk claim.** Self is seeded `member` and never marked `dead`, so
  it contributes to none of the three counters; the single-node case is genuinely zero walks, and a
  test pins it.
- **The prior run's open lead: does sharing one captured walk change behavior?** `store.list()`
  returns live entry references and `put` writes a *new* object, so an entry mutated after the walk
  would not be reflected in the shared array — where three separate walks would have seen it. Read
  the full bodies of `classifyTargets`, `reprobeExcludedTargets`, `reprobeOffRingTargets` and
  everything they call (`getBackoffPenalty`, `isConnected`, `hasAddresses`, `backoffMap.get`): all
  three arms are **pure selection**, no store writes anywhere; the writes happen later in the pooled
  `probeMembership`. The `// No prune here:` comment on `reprobeExcludedTargets` is a note that a
  prune *doesn't* run there, not evidence one does. Shared walk is behavior-identical today.
- **The `store.list` spy cannot leak across cases.** `walksDuring` restores the bound method in a
  `finally`, and `beforeEach` builds a fresh rig (fresh service *and* fresh store) per test, so even
  a leaked patch could not reach another case.
- **Docs beyond the two touched bullets.** Grepped `docs/fret.md` and `src/` for lingering
  three-walk claims — none; the superseded `NOTE:` inside `classifyTargets` was correctly deleted
  and the `stabilizeOnce` early-return comment now says "at most one store walk".
- **Validation.** `npx tsc --noEmit` from `packages/fret` — clean. `yarn test` — **1103 passing, 0
  failing**, all five new tests among them. There is no lint step in this repo (`yarn check` is the
