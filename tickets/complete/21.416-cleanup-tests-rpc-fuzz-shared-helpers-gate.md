### `verbatimModuleSyntax` — enabled, one line, no code changes

**Decision: enabled** in `packages/fret/tsconfig.json`.

The class of defect it retires is real and was hit during implementation: three names were imported
as *values* from the new helper but are declared there as types. `tsc --noEmit` is silent on that —
it is legal TypeScript — but the package runs tests through Node's type-stripping loader
(`register.mjs`), which strips type syntax **per file** and cannot know an imported name is
type-only in another module. The specifier survives stripping and the import throws at runtime:

```
SyntaxError: The requested module './helpers/rpc-fuzz.js' does not provide an export named 'InboundHandler'
```

The implementer fixed the three names. That fixes the instance, not the class: every future fixture
move across a module boundary in this suite reproduces it, and the type-checker stays silent every
time. `verbatimModuleSyntax` makes it TS1484, a compile error.

Measurement, and why it was safe to land here rather than defer: run 1 measured
`npx tsc --noEmit --verbatimModuleSyntax` at **0 errors**, so the package was already fully
compliant and the flag costs one line and no code changes. The open risk was the flag's *other*
effect — it changes import elision in the emitted `dist/` output — which is exactly what the
never-yet-run gate settles. `yarn build` and the suite both pass with it on. (Elision only ever
*narrows* here: with 0 errors, every type import was already written `import type`, so those emit
identically and value imports are untouched.)

The reasoning is recorded in `AGENTS.md` beside the `register.mjs` loader note, since that is where
a future reader meets the loader and would otherwise re-derive the runtime failure from scratch.
