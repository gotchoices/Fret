## Review findings

### What was checked

The whole implement diff, read before the handoff summary: `src/rpc/protocols.ts` (all three arms),
both touched test files, and the three `docs/fret.md` paragraphs. Aspect angles: single purpose,
DRY, modularity, scalability, maintainability, performance, resource cleanup, error handling, type
safety, source hygiene. Tests were read as a starting point rather than as coverage, and the docs
were treated as out of date until each touched paragraph was re-read against the new code.

**The implementer's central claim about libp2p holds against the real implementation, not only
against the test stub** — checked in `node_modules/@libp2p/utils/dist/src/abstract-stream.js` and
`abstract-message-stream.js`:

- `AbstractStream.close(options)` sets `writeStatus = 'closing'` *before* it awaits anything, then
  awaits `pEvent(this, 'idle', options)` / `pEvent(this, 'drain', options)` /
  `sendCloseWrite(options)`, each receiving the caller's `AbortOptions`. A close bounded by a
  signal therefore rejects with the write end left at `'closing'`, never `'closed'` — exactly the
  state `registerRpcHandler`'s catch arm tests for before aborting.
- `close()` early-returns when the write end is already `'closing'`/`'closed'`, so a stream a
  handler closed for itself is not released twice.
- `close()` does **not** abort the stream when it rejects; it leaves it half-open. The follow-up
  `abort()` in `releaseRpcStream` and in the handler seam is load-bearing, not belt-and-braces.
- `abort()` is self-guarded, so an extra abort is a no-op rather than a double release.
- **A bare `close()` really can block indefinitely.** `processSendQueue` sets
  `writableNeedsDrain = true` when the muxer stops accepting, and `close()` then awaits the
  `'drain'` event. With no `options.signal` nothing ends that wait, so a remote that accepts a
  stream and stops reading holds the closer forever once the flow-control window fills.
  (`checkWriteBufferLength` aborts only if `maxWriteBufferLength` is configured — a
  muxer-dependent backstop, not a budget.) This is what makes finding A real.

Two supporting checks: all five sender call sites release from a `finally` *before* `d.cancel()`,
so the ordering the seam's doc comment depends on is real (`ping.ts`, `neighbors.ts` ×2,
`maybe-act.ts`, `leave.ts`); and no caller passes `readFramed` a `timeoutMs` of `0` or negative
(`grep -rn "readFramed(" src test` — every site passes a module constant, a literal ≥ 150,
`Infinity`, or nothing).

### Findings and disposition

**A (major, fixed in this review) — the success-path close belonged to the seam, not to seven
handler bodies.** A bare `await stream.close()` in a handler body runs *before* the seam's budgeted
close and blocks on exactly the stalled remote the budget exists for, pre-empting it entirely.

- *Source:* the bare close is gone from all seven FRET handler bodies (`ping.ts`, `neighbors.ts`
  ×3, `leave.ts` ×2, `maybe-act.ts`); the two identity-mismatch drops are now a bare `return;`.
  Each file's "errors and stream release belong to `registerRpcHandler`" comment now says the close
  does too, and why. `registerRpcHandler`'s doc comment states that the seam always closes and that
  no FRET handler body closes for itself; its early-return sentence is now a statement about
  *external* consumers of the exported seam. `sendMaybeAct`'s half-close is bounded:
  `await stream!.close({ signal: d.signal })`.
- *Tests:* `'bounds a success-path close…'` in `test/rpc.handler-fuzz.spec.ts` previously drove a
  synthetic handler whose entire body was a comment, so it documented the gap rather than catching
  it. It now drives `registerPing`'s handler body verbatim over the `closeHangs: true` stub and
  additionally asserts the reply was written (`sends === 1`). It registers through
  `registerRpcHandler` directly, with a comment saying why: the close budget must be injected so
  the case does not spend the 5 s production default, and threading a `closeBudgetMs` through the
  `register*` helpers would change production signatures to serve a test. Two neighbouring cases
  were relabelled because their names asserted the old shape —
  `'lets an external seam consumer close for itself without a second release'` and
  `'closes a completed ping reply exactly once, from the seam'` — assertions unchanged. The four
  other real-handler cases asserting `{ closes: 1, aborts: 0 }` were re-read and confirmed still
  accurate, not assumed.
- *Docs:* the "Inbound handlers release their stream on every path" paragraph in `docs/fret.md`
  claimed the seam's close early-returns for a handler that closed for itself. Rewritten to the
  new reality.

**B (minor, fixed) — `sendMaybeAct`'s half-close was unbounded.** Now closed under the RPC
deadline's signal, with the reason in the surrounding comment.

**C (minor, fixed) — `readFramed` did not validate `timeoutMs`.** The entry guard tested
`timeoutMs === Infinity` exactly. `NaN` was worse than the handoff described: `Math.min(NaN, …)`
against the poll interval is `NaN` and `setTimeout(fn, NaN)` clamps to zero, so the poll loop spun
one iteration per event-loop turn, re-running `remoteFinishedWriting` for as long as the stream
stayed open — a hot spin, not a quiet hang. `0` and negatives fire the remaining-budget check
immediately, which is at least loud. Unreachable from any current caller, but `readFramed` is
exported from the package root, so a consumer computing a timeout from config can reach it. Fixed
with a `if (!(timeoutMs > 0)) throw` guard beside the `Infinity` clause — written `!(x > 0)` rather
than `x <= 0` so `NaN` is caught while `Infinity` still passes — plus a `@throws` entry in the doc
comment, and a test in `test/rpc.protocols.spec.ts` covering `NaN` / `0` / `-1` (refused at entry,
provably no byte pulled) and `Infinity` (still passes). This is rung 1 of *Architecture first*:
validating a seam's own input so the bad state cannot enter, rather than filing a bug against a
future caller.

**D (minor, fixed) — a close that exhausted its budget was logged as a handler error.**
`registerRpcHandler` now holds its close budget in a `let closeBudget: Deadline | undefined`
declared outside the `try`, and the catch arm logs
`'%s reply close exceeded %dms budget - remote stopped reading, aborting stream'` when
`closeBudget?.signal.aborted === true`, else the original `'%s handler error - %e'`. The abort arm
is unchanged. The discriminator is deliberately the budget **signal**, not
`err instanceof DeadlineExpiredError`: libp2p's `close()` rejects with whatever its internal
`pEvent` turns the abort into, so matching the error identity would depend on a wrapping detail we
do not own. Stated in both the doc comment and `docs/fret.md`.

### Tripwires (recorded at the code site, deliberately not filed as tickets)

- **Per-message close timer** — `registerRpcHandler` arms an `AbortController` + `setTimeout` for
  every inbound message on every protocol. Load-bearing now that no handler body closes for itself,
  but a per-message allocation. `NOTE:` at the `deadline(closeBudgetMs)` site in
  `src/rpc/protocols.ts`: if inbound cost ever shows up in a profile, measure the timer churn
  before the handler bodies.
- **Release-before-cancel ordering** — nothing fails if a future sender calls `d.cancel()` before
  `releaseRpcStream`; it still compiles, still passes, and the bound on the close silently
  disappears. `NOTE:` at the `releaseRpcStream` signature: all five senders get it right today; if
  a sixth is added or one is reordered, consider taking the `Deadline` itself so the cancel cannot
  precede the release.

### Considered and declined — no ticket filed

The implement handoff flagged "no end-to-end coverage of arms (b)/(c) over a real libp2p transport"
as a gap. No `debt-` ticket was filed, because the gap is materially smaller than the handoff
assumed: the test stub's contract was checked against libp2p's actual source rather than against
its interface docs, and each of the four behaviours the stub models (write-status transition
ordering, close's early-return, close-does-not-abort, abort's self-guard) is confirmed in
`abstract-stream.js`. What a real-transport test would add over that is muxer-level flow control,
which no arm of this diff branches on.
