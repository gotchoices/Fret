`packages/fret/test/rpc.stream-errors.spec.ts` — 28 cases, all passing. No behavioral source change:
the ticket was "pin what ships today, do not change sender behavior", and nothing in a sender was

## What it covers

Three failure shapes no other spec produced, driven against every sender that can meet them:

| Shape | Stub | Senders driven |
|---|---|---|
| Reset mid-stream (reply iterator *throws* after N bytes) | `resetsAfter(bytes?)` | ping, neighbors-fetch, maybeAct (+ zero-byte variant) |
| Clean EOF mid-JSON (short-but-complete buffer, `decodeJson` throws) | `halfThenEof(bytes)` | ping, neighbors-fetch, maybeAct |
| Partial then stall (bytes, then silence) | `partialThenStall(bytes)` | ping, neighbors-fetch, maybeAct |
| Caller cancels mid-stream (abort lands with bytes already buffered) | `partialThenStall(..., { onNext })` | ping, neighbors-fetch, maybeAct |

Plus: a reset while *writing* (announce swallows, leave propagates — both release); a reset queued
behind an over-cap chunk; the abandoned `iter.next()` rejecting after the read already ended; the
same failures observed at the service through `routeAct`'s forward and `probeNeighborLatency`; and
three cases over a real TCP + noise + yamux connection.

## Invariants pinned (must survive `15-rpc-shared-helper`)

- **A partial payload is never parsed as a whole message.** Every truncated-reply case asserts the
  ghost fields present in the truncated bytes (`ghost-succ`, `size_estimate: 42`, `ghost-anchor`)
  do **not** appear in the result.
- **The stream is released exactly once.** Which *arm* releases it is an invariant only where one
  clock exists — see finding 1.
- **No unhandled rejection escapes** — a suite-wide `process.on('unhandledRejection')` guard.
- **Our own cancellation is never evidence about the peer** — an abort landing *mid-stream* records
  no contact strike, no relevance decay, no backoff, no `pingsFail`; with a live-run reset as the
  non-vacuity contrast.
- **A reset is a failed contact; an undecodable reply never demotes to `foreign`.**

## Today's contract, pinned *and* labelled

Each carries an inline `TODAY'S CONTRACT — 15-rpc-shared-helper, arm "…"` comment saying what to
change and that the case must be **updated, not deleted**: `fetchNeighbors` fabricating an empty
snapshot on reset / truncation / cancellation; the three-way divergence on one piece of evidence
(ping `ok: false`, neighbors fabricates success, maybeAct throws); and the service consequence of
that divergence (a contact strike on the maybeAct path, none on the ping path).

### Fixed in this pass (minor)

1. **A flaky assertion, caught failing.** The three `partial then stall` cases asserted a fixed
   release arm (`{ closes: 0, aborts: 1 }`). That arm is not deterministic: `releaseRpcStream`
   aborts only if the deadline signal has already fired, and `readAllBounded`'s own `Date.now()`
   expiry can beat that `setTimeout`, in which case release goes through `close()`. It failed
   during this review with `{ closes: 1, aborts: 0 }` — the same two-clock race the file already
   documented for the *error type* (`expectStallRejection`) but had not noticed also decides the
   release arm. Replaced with `expectReleasedOnce(s, flushCloses)`, which asserts release-exactly-
   once and explains the race; the arm itself is now pinned only in the caller-cancellation cases,
   where the caller's signal is the sole clock. Re-ran the file five times: stable.
2. **A claim that mutation testing disproved.** The case "answers normally when the abandoned
   `iter.next()` rejects" claimed to pin `protocols.ts`'s `pending.catch(() => {})`. Deleting that
   line leaves the test passing, because `Promise.race` attaches its own reject reaction to
   `pending` in the same iteration — the promise is already handled and no unhandled rejection is
   reachable. Corrected both the spec's comment and the source comment (which made the same
   overstatement), and stated that the suite-wide guard is currently unarmed and kept as a net over
   future cases rather than as coverage of a line.
3. **A sixth hand-rolled ring-coordinate offset.** The spec's private `offsetCoord` re-implemented
   `test/helpers/ring.ts`'s `ringOffset` — the exact duplication `21-cleanup-tests` enumerates five
   existing sites of, and which that helper was created to retire. Deleted in favour of the import;
   its unused `-1` arm went with it.
4. **An inaccurate comment about the sibling spec.** The stub header claimed
   `rpc.protocols.spec.ts` "deliberately omits `close`/`abort`"; its `makeReleasable` stub
   (`rpc.protocols.spec.ts:212`) implements both. Restated accurately: that file splits release
   stubs from read stubs, and a failure *partway through a read* needs both in one stub.
5. **Closed the handoff's largest stated gap.** Gap 4 said "no real-transport reset mid-stream is
   covered at all — the helpers have no way to make a live peer reset a stream mid-write". Not so:
   a handler can call `Stream.abort(err)` after a partial send, which is precisely a mid-write
   reset. Added two live cases (`fetchNeighbors` and `sendPing` against a peer that resets
   mid-reply) and refactored the real-transport block onto shared setup. Both pass. This matters
   because the reset shape otherwise rested entirely on stubs, and the missed-EOF bug is the
   precedent for a stub-only suite agreeing with itself and not with libp2p. The live `sendPing`
   reset case tolerates both outcomes by design — whether the buffered bytes are delivered ahead of
   the reset is the muxer's choice — and says so.
6. **Docs.** `docs/fret.md`'s *Stream management* section described the read deadline but not what
   happens to a reply that fails partway through. Added the contract, named the spec that pins it,
   and stated the non-deterministic release arm plus the sender divergence as today's contract
   rather than as endorsement.

### Filed (major)

7. **Appended an arm to `tickets/plan/15-rpc-shared-helper`** rather than filing a new ticket — the
   root cause of finding 1 is that **one budget is measured by two independent clocks**: every
   sender arms `deadline(timeoutMs, signal)` and then hands `readAllBounded` the same `timeoutMs`
   again alongside that deadline's signal (`ping.ts:92`, `neighbors.ts:102`, `maybe-act.ts:65`).
   Which expires first decides both the error type and the release arm. Climbed the ladder before
   filing: this is a representation fix (the read should be bounded by the deadline already armed,
   never by a second copy of the budget), and ticket 15's shared `rpcRequest` helper is what makes
   the second call site — and therefore the class — unrepresentable. That ticket already owns the
   `releaseRpcStream` / `maybe-act.ts:64` sites, so a point ticket would have split one fix in two.

### Considered and not filed

- **`releaseRpcStream`'s un-aborted `await stream.close()` is unbounded** (handoff gap 2). Real —
  libp2p's `close()` resolves only once unsent data reaches the transport and accepts an
  `AbortOptions` nobody passes. Already pinned as an explicit arm of `15-rpc-shared-helper`
  (lines 40–67 of that ticket, with both sites named). Not re-filed; the Nth instance is evidence,
  not a new ticket.
- **Inbound handler error paths leak streams** (gap 5), **`fetchNeighbors` fabricating success**,
  **the ping/maybeAct divergence** (gap 3's second close included): all existing arms of ticket 15.
- **`sendMaybeAct`'s two `close()` calls** (gap 3). Harmless — the second is a no-op release — and
  the flush half-close is already ticket 15's `maybe-act.ts:64` arm. Now accounted for explicitly
  by `expectReleasedOnce`'s `flushCloses` parameter rather than baked into a magic number.
- **The byte-count assertion the ticket originally asked for** (gap 1). Left accepting either arm;
  it becomes deterministic when finding 7 lands, and the byte-count message is already pinned
  against the primitive at `payload-bounds-ttl.spec.ts:82`.
- **File size.** 1018 lines (`wc -l packages/fret/test/rpc.stream-errors.spec.ts`), against a
  suite maximum of 1039 (`dead-state.spec.ts`). In band; no split filed.

### Gaps deliberately left open

Gaps 5 (inbound handlers), 6 (asynchronous write failures / backpressure) and 7 (service-level
cancellation on the maybeAct forward mid-stream) from the handoff stand, each an existing arm of
`15-rpc-shared-helper` or of `8-concurrency-inflight-tests` rather than a new instance. Gap 8 (the
service cases monkey-patch `getConnections` and cast to private members) is the house test style —
`test/helpers/maintenance-rig.ts` uses the same device — and is left as-is. The stall shape has no
real-transport counterpart: it is a responder doing nothing, and asserting it costs a full RPC
budget of wall time per case; the spec says so at the point it would go.
