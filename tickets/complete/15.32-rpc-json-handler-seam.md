## What was built

`15.32-rpc-json-handler-seam` added `registerJsonHandler` (`src/rpc/protocols.ts`) — one seam that
reads an inbound framed body, decodes it, runs it through a parser from `src/rpc/validate.ts`, and
frames the reply — stacked on top of the existing `registerRpcHandler`, which still owns the
budgeted success close and the synchronous error `abort()`. Three of the five FRET handlers (leave,
neighbors request + announce, ping) were migrated onto it. maybeAct deliberately stayed off it,
because its rate-limit bucket has to be taken before any per-message work and the seam parses inside
the handler body.

The rule the seam states once, instead of per handler: **frame-level failure aborts** (truncation,
over-cap, reset — the stream is already broken), **body-level failure closes** (undecodable JSON,
non-object top level, parser rejection, identity mismatch — the peer framed correctly and is alive;
the message is worthless).

Code under review is committed at `377c8fe`. Two follow-on tickets own work deliberately *not* done
in this review: `15.325-rpc-json-handler-tests-docs` (test extension + the docs paragraphs) and
`15.33-rpc-reply-parsers-and-caps` (wiring the reply decoders onto their parsers).

### Major finding — filed as a fix ticket

**(A) A frame the remote actually wrote can be read as truncated.** Found while reading the
reply-only overload; reproduced with a real two-node pair (`15.32c`), diagnosed (`15.32d`), and
extended with the seam-await accounting (`15.32e`). `readFramed`'s end-of-stream recognition relies
on libp2p's one-shot `remoteCloseWrite` / `close` events, which a responder can miss if it closes
while the caller is still opening its stream; the 20 ms `EOF_POLL_MS` re-check then sees a
drained-and-remote-closed stream and raises `FrameTruncationError` even though a complete reply was
written. Whether it trips depends on how many microtasks elapse before the responder's first write,
and the seam itself spends two of them.

Filed as `tickets/fix/framed-read-false-truncation` (`repro: verified`), rooted at
`remoteFinishedWriting` / the `readFramed` poll loop and stated as a **boundary invariant** — *a
frame the remote actually wrote is never reported as truncated* — rather than as a point bug at the
seam, carrying the microtask-depth table and all three sightings. It also requires the direct
reply-only-overload test the implement handoff listed as a gap, since that test is the reproduction.

A site-claim grep over `tickets/{backlog,fix,plan,implement,review}` for
`readFramed|remoteFinishedWriting|EOF_POLL_MS` returned only `15.4-rpc-byte-cap-tightening`, which
was read in full and is **not** the theme ticket: its root site is `readFramed`'s `onLength`
declared-length cap and the per-protocol cap constants, not end-of-stream recognition.

The two reply-only `NOTE:` blocks (`src/rpc/ping.ts`, `src/rpc/neighbors.ts`) were rewritten
(`15.32f`) to state the hazard, the symptom, that the seam already spends two of the awaits itself,
and that the fix lives in `readFramed` — each pointing at the fix ticket's slug.

### Minor findings — fixed in this review pass

**(B) Three places claimed `registerRpcHandler` was exported from the package root; it was not.**
`src/index.ts` exported the outbound seam, `rpcRequest` and the seven wire-shape parsers, and no
handler-registration function at all — while `docs/fret.md:208`, the comment at `src/index.ts:163`,
and `test/rpc.handler-fuzz.spec.ts:323` each built an argument on the claim (the `close()`
early-return being "the *external*-consumer case").

Resolved by making the claim true rather than by correcting three sites to say the surface does not
exist. `registerRpcHandler` and `registerJsonHandler` are now exported from the package root, with
`JsonRequestHandlerOpts` / `JsonReplyOnlyHandlerOpts` beside them — without the option interfaces a
consumer can call the seam but cannot name what it is passing. The argument is the same one already
made for `openRpcStream` / `releaseRpcStream` under *Dialability*: a consumer wrapping its own JSON
protocol over the same libp2p node has exactly the drop/abort and stream-release problem this seam
solves, and the hand-rolled copy is what leaks inbound streams. `test/package-exports.spec.ts`
gained a third runtime `it` block in the shape of the existing two, plus type-level assertions
naming both option interfaces (which also pins which overload each selects). `docs/fret.md` updated
at both the *Stream management* claim and the *Dialability* reachability sentence.

**(C) `registerNeighbors`' trailing `snapshotParser` parameter defaults to `Infinity` caps**, so a
caller that omits it silently gets shape checking with no truncation. `FretService` always supplies
`makeSnapshotParser(this.mergeSnapshotCaps())`, so production is unaffected — this is a tripwire,
not a defect. **Decided: keep it defaulted**, and the existing comment at the parameter
(`src/rpc/neighbors.ts`) was re-tagged `NOTE:` so it joins the greppable tripwire set, stating why
(making it required means reordering the signature past the optional parameters and updating four
test call sites, for a case production cannot reach) and the revisit condition (a second production
caller, or an options-bag signature).

**(D) `docs/fret.md:139` carries a dead path** — under *Cheap-guard rejections* it points at
`tickets/implement/15.32-rpc-json-handler-seam`, which no longer exists, and still says maybeAct is
the only handler wired to its parser. **Left in place deliberately**: `15.325` is still queued in
`implement/` and its TODO explicitly owns rewriting that paragraph. Routing it here would duplicate
that work. The *second* stale docs claim, at line 208, was not covered by `15.325` and was fixed
here with (B).
