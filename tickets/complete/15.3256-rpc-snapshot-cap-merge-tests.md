## What shipped

One describe in `test/rpc.handler-fuzz.spec.ts` — `announce snapshot merge caps` — table-driven

and `over the memory transport`. **10 tests, 5 per profile** (the implementer wrote 12; review

Plus one refactor: `sampleCoord(byte)` and `wrongWidthCoord(byteLength)` hoisted from inside the
`announce snapshot field matrix` describe to module scope, so both describes share one copy of the
wrong-width-coordinate rule rather than two.

## The claim being pinned

`onAnnounce` receives an *already-parsed* snapshot, so the parse + hash + upsert loop a crafted
announce drives is `FretService.mergeAnnounceSnapshot` (`src/service/fret-service.ts:1771`),
bounded by `FretService.mergeSnapshotCaps()` (`:1751`) — core 16/16/8, edge 8/8/6. The *same*
object is handed to `makeSnapshotParser` at the single registration site (`:1033`), so the parser
truncates before the merge loop runs. The headline test is that **both routes cost the receiver the
same number of upserts**: an over-long list buys the sender no extra work whichever way it arrives.

Work is counted by wrapping `store.upsert` on the service's own store and recording each id in call
order. `mergeAnnounceSnapshot` calls it once for `from`, once per successor/predecessor, once per
sample entry — so the expected count is `1 + succ + pred + sample`. `applyTouch` opens with
`getById(id) ?? upsert(id, coord)` and the loop has always just upserted that id, so it does not
double-count; the exact-count assertions confirm that empirically rather than by reading.

## The tests, per profile

- **merges exactly `1 + successors + predecessors + sample` ids, however long the lists** — driven
  with 40 successors, 40 predecessors, 20 sample entries; asserts the count *and* the exact id
  sequence (first N of each list, in merge order).
- **never stores an id past the cap** — every over-cap id absent, *and* the last admitted id of
  each list present, so the absences are the cap working rather than nothing having been stored.
- **costs the same whether the parser truncated first or the merge loop did** — the same raw body
  merged untruncated into one service and, through `makeSnapshotParser(caps)`, into a second; the
  recorded id sequences must be identical. The ticket's actual claim.
- **drops a wrong-width sample coord at the parser** — a 16-byte coordinate; the bad entry absent
  from the parsed snapshot, the good entries surviving in order, so it never reaches `onAnnounce`.
- **skips a wrong-width sample coord in the merge loop when the parser is bypassed** — the arm the
  merge loop's per-entry try/catch exists for. Only that entry drops; `from`, the successor, the
  predecessor and both good sample entries are still upserted, and the merge does not fail.

## Rig notes for anyone extending this

- Services are constructed but **left unstarted** (`new CoreFretService(node, {...})`, node
  started). No stabilization loops, no registered handlers. The merge's detached tail is quiet:
  `announceToNewPeers` filters targets by `hasAddresses`, empty on an unstarted service, so it
  dials nothing; `enforceCapacity` early-returns far below the 2048 capacity. The mocha exit
  watchdog is clean, which is the check that would catch it otherwise.
- Privates are reached through a locally-declared `DrivableMerge` cast, not by widening the
  `DrivableService` interface the neighbouring describe declares.
- `mergeAnnounceSnapshot` is awaited **directly** rather than via `handleAnnounce`, which
  `detach`es it — that detachment is what makes counting via the public path non-deterministic.
- Peer-id seeds are allocated 60 / 61-100 / 101-140 / 141-160, all under 256 so `peerIdStr` keeps
  them distinct.

## Review findings

Reviewed the implement diff (`a8fbf45`) against `fret-service.ts:1745-1825` (`mergeSnapshotCaps`,
`mergeAnnounceSnapshot`), `fret-service.ts:2296-2320` (`fetchAndMergeSnapshot`),
`src/rpc/validate.ts:163-240` (`makeSnapshotParser`, `parseSample`),
`src/rpc/neighbors.ts:20-60` (the registration site and its `Infinity`-cap default), and the
pre-existing sibling spec `test/announce-rate-limit.spec.ts`.

**Fixed in this pass (minor).**

- *Duplicated assertion across specs.* The new `states its merge caps as the pinned per-profile
  literals` test (one per profile) is an exact duplicate of the pre-existing
  `announce merge caps match the neighbor-fetch merge caps (single source of truth)` in
  `test/announce-rate-limit.spec.ts:152`, which already deep-equals `mergeSnapshotCaps()` against
  the same two literals. Two copies of the same numbers is precisely the drift these tests exist to
  prevent. Deleted the new pair (12 tests to 10) and left a comment at the site naming
  `announce-rate-limit.spec.ts` as the owner of that claim. The caps are still pinned here
  indirectly and loudly: the count assertions are written against the literal table, so a caps
  change fails them.

**Filed as a ticket (major).**

- *The two snapshot merge loops are duplicated source, and have already drifted.*
  `mergeAnnounceSnapshot` (`:1797`) and `fetchAndMergeSnapshot` (`:2297`) contain line-for-line
  identical cap-slice, hash, `upsert`, `applyTouch` loops. The drift is not hypothetical: the
  fetch copy logs a failed id with `console.warn` where the announce copy uses the package logger,
  and the accumulators are named differently. Climbing the ladder before filing: the point finding
  here would have been "add a second counting test for the fetch path" (the gap the handoff itself
  names), but the invariant that retires the whole class is *one* loop applying the caps in one
  place — after which the counted path **is** the fetch path and no second test is needed. Filed
  as `backlog/debt-snapshot-merge-loop-duplication`. Site-claim grep over all open stages found no
  ticket already holding that site (`15.33-rpc-reply-parsers-and-caps` and
  `15.4-rpc-byte-cap-tightening` touch the parsers and the byte caps, not the merge loops).

**Recorded as tripwires, not tickets.**

- *Weaker overlapping coverage left in place.* `announce-rate-limit.spec.ts`'s `caps a core/edge
  announce to ...` tests assert `store.size()` after the same over-cap merge, which the new
  exact-id-sequence tests strictly subsume. They are not wrong and they use real generated Ed25519
  ids where the new tests use synthetic ones, so deleting them would trade breadth of input for
  tidiness. Left alone deliberately; the comment added at the new site points a future reader at
  the relationship. If the merge-loop extraction above lands and the counting tests move to cover
  both paths, that is the moment to collapse them.
- No `NOTE:` tripwire was added to source — the conditional concerns found here are about test
  placement, which has no single code site to hang a comment on, so both are recorded above.

**Checked and clean.**

- *Test correctness.* Peer-id seed ranges (60 / 61-100 / 101-140 / 141-160) are disjoint and all
  under 256, so `peerIdStr`'s `fill(seed)` keeps every id distinct; sample coords are distinct
  32-byte fills. `countUpserts` patches a per-service store instance and each test gets a fresh
  service from `beforeEach`, so the patch cannot leak between tests; the two-service test patches
  two separate stores. The `expected` literals and `capsOf` remain used after the deletion.
- *Resource cleanup.* Services are unstarted, so there is nothing to stop; `afterEach` stops the
  node. The two-services-on-one-node case is safe because nothing is registered until `start()`.
  The exit watchdog passes, which is what would surface a leaked timer or stream.
- *Docs.* Read `docs/fret.md`'s "Inbound snapshot-merge caps" bullet and the wire-format and
  wire-shape-parser sections against the change. The caps, the truncate-don't-reject rule and the
  skip-and-log-per-sample-entry rule are all already documented and still accurate; this ticket
  added tests for behaviour the document already describes, so no doc edit was owed and none was
  made.
- *Source hygiene.* No source files changed. The spec is 1827 to 1824 lines, long but organised by
  its stated three tiers plus the two service-tier describes; the hoisted helpers reduced
  duplication rather than adding it.
- *Type safety.* No `any`. Privates are reached through explicit local interfaces
  (`DrivableMerge`, `CountableStore`) and `as unknown as` casts, which is the pattern the
  neighbouring describe already uses.

**Gaps carried forward, honestly.**

- The neighbour-*fetch* merge path is still not counted — this is the ticket filed above, and it is
  the right shape of fix.
- The wire path into the merge is not exercised: these tests call the private merge directly, so
  `handleAnnounce`'s token bucket, the identity check and the `detach` are bypassed. Each is
  covered elsewhere (the sibling wire matrix, `announce-rate-limit.spec.ts`), but nothing asserts
  the halves compose end to end.
- Only `store.upsert` is counted, as a proxy for per-message work; hashing and `applyTouch` scoring
  are not counted separately. A refactor that batched upserts would fail these loudly rather than
  silently, but the proxy is still a proxy.
- No interaction with a near-full store — every test runs with `enforceCapacity` early-returning,
  so eviction mid-merge is untested.
- Sample entry ids in the short-coord tests are plain strings (`'good-1'`), correct because the
  sample merge path never parses a sample id — but it means these tests say nothing about
  sample-id validation, of which there is none.
