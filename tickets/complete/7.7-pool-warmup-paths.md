description: The two passes that warm up connections to nearby peers — one at start-up, one that runs every second while an operation is active — used to contact peers one at a time, so a few unresponsive neighbours held up all the rest. They now contact several at once, capped at the same limit the background maintenance cycle uses, and the per-second pass no longer wastes its allowance on peers it cannot reach.

Phase 3 of the `stabilize-tick-concurrency` work: the two connection warm-up passes were the last
serial dial chains in maintenance, and now share the stabilization tick's pooled fan-out.

## Final shape

**One shared fan-out, `FretService.pingWarmupTargets(ids, label, budget?)`** (`src/service/fret-service.ts`,
just above `preconnectNeighbors`):

- pooled through `runPooled` at `maintenanceConcurrency` (Core 6 / Edge 2);
- against the **run signal**, not a tick deadline — neither pass runs inside `stabilizeOnce`, so
  there is no tick budget to inherit. `MAINTENANCE_RPC_TIMEOUT_MS` (2000 ms) bounds each ping and
  `stop()` collapses the whole fan-out;
- `isDialable` filtered **before** both the task list *and* the caller's `budget` slice;
- `diag.pingsSent` still increments only after a completed `sendPing`; `wasCancelled(sig)` still
  guards each task's catch (these paths score nothing, so it suppresses only the log line);
- `logRejected` reused, its doc comment widened to cover maintenance pools generally.

Call sites: `preconnectNeighbors` (start-up, `min(6, m)` per side → 12 targets, no budget) and
`activePreconnectTick` (Core 6 / Edge 3 per second, budget passed). `sendAnnouncementsRateLimited`
deliberately untouched — still serial, as its comment records.

**Test harness extracted** to `test/helpers/maintenance-rig.ts` (`PeerRig`, `hangsUntilAbort`,
`stubStream`, `buildMaintenanceRig`), shared by `stabilize-concurrency.spec.ts` and
`preconnect-concurrency.spec.ts`.

## Review findings

Reviewed the implement diff (`a007c17`) against the source before reading the handoff summary.

### Fixed in this pass (minor)

- **The active tick spent its per-second budget on undialable peers.** `activePreconnectTick`
  sliced its Core 6 / Edge 3 budget off the *raw* ring walk and only then handed it to
  `pingWarmupTargets`, which filters `isDialable`. So a run of undialable near peers consumed the
  whole budget and the tick warmed nobody — the opposite of what a warm-up pass is for. The
  behaviour predates this ticket (the old serial loop had the same order), but the diff's own new
  doc text claims dialable peers are filtered "before the task list is built", so the code now
  matches its documentation: `pingWarmupTargets` takes an optional `budget` and applies it to the
  *dialable* list. Pinned by `active tick: spends its per-second budget on dialable peers,
  skipping undialable leaders`, which blocks the leading six peers **in ring order** (re-derived in
  the test, not seed order) so the old shape would have pinged zero and the new one pings six.
- **The active tick body was untestable** — an inline closure inside `startActivePreconnectLoop`,
  which is why the implementer could not close their own top-listed gap. Extracted to
  `private async activePreconnectTick()`, separating scheduling (generation guard, timer re-arm)
  from the work. Two tests now drive it directly (Core budget/dialable, Edge 3-budget-at-cap-2), so
  the budget and the pooling of the *narrower* pass are pinned rather than inferred from the wider
  one.
- **No coverage for a `stop()` landing mid-pass** (implementer's third listed gap). Added `a run
  cancelled mid-pass aborts the started pings and never dials the rest`: 12 hung peers, abort once
  the pool is provably full, assert exactly `concurrency()` peers were ever dialed (the rest
  `skipped`, never opened), every stream settled, `pingsSent === 0`.
- **`AGENTS.md` was stale in a way that actively misdirects.** It advertised `fret-service.ts` as
  "~1400 lines" (`wc -l` reports 2962) and listed key-region line hints that were off by roughly
  2× — "Stabilization: lines ~680–790" against an actual `stabilizeOnce` at 1849. Rewrote the
  region list against measured anchors and told the reader to grep the symbol rather than trust the
  number. Added `test/helpers/maintenance-rig.ts` to the tree.
- **`docs/fret.md`** *Active vs passive state* bullet updated for the dialable-before-budget rule
  and mid-pass cancellation.

### Verified, no change needed

- **The harness extraction is faithful.** Diffed `helpers/maintenance-rig.ts` against the rig as it
  stood in `a007c17^:test/stabilize-concurrency.spec.ts`: `hangsUntilAbort`, `sleep`, `stubStream`
  and `PeerRig` are byte-identical apart from two error/doc strings changing "stabilization tick" to
  "maintenance pass". `seedPeers` and `teardown` moved verbatim into the returned object. All eight
  stabilization tests are unchanged line-for-line and still pass.
- **`preconnectNeighbors`'s 12-seeded-peer "full pass" claim holds.** `m` is `ceil(k/2) = 8` for
  *both* profiles (not profile-tuned), so `min(6, m) = 6` per side and 6 right + 6 left covers all
  12 seeded peers exactly. The service is never started, so self is not in the store and cannot
  displace a target.
- **No lost-increment hazard.** `diag.pingsSent++` is the only shared mutation in a warm-up task,
  and JS runs the increment to completion between awaits. The disjointness argument the tick needs
  does not apply here: warm-up tasks score nothing against a peer.
- **`logRejected` is index-aligned** with the filtered `targets`, not the caller's `ids`. A
  rejection remains structurally unreachable (the task's own try/catch is total) — kept as the same
  bookkeeping-bug guard the tick uses.
- **`start()` was never blocked by the serial chain** — `preconnectNeighbors` is detached at
  `fret-service.ts:806`. The regression this ticket fixes is warm-up *latency*, not start-up
  latency. The doc text does not overclaim on this point.
- **`dead-state.spec.ts:890`** ("issues no dial from the preconnect pass when the run is cancelled")
  still passes, both halves intact.
- **`pingWarmupTargets`'s `label` parameter** is log-formatting only, so a mismatched label cannot
  change behaviour — not a defect, and not worth a guard.
