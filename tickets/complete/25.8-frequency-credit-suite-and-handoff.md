## What the change was

`accessCount` — the counter feeding the frequency term of a routing-table entry's relevance score
— used to be incremented both when we actually talked to a peer and when some *other* peer merely
mentioned it to us. A peer we had only ever been told about, repeatedly, could therefore outrank
one we had genuinely contacted and survive eviction in its place. The change makes the counter
count proven contact only, and routes every "someone named this peer" path through one seam,
`FretService.noteDiscovered`, which scores a brand-new entry once from empty counters and leaves an
id we already hold completely untouched.

### Tests (`packages/fret/test`) — one minor finding, fixed in this pass

- **Fixed (minor, DRY).** `relevance.properties.spec.ts` carried two tests asserting the same
  thing: `gossip vs proven contact` → "scores even a single success above 500 mentions, since
  mentions are flat" duplicated `initialRelevance` → "scores strictly below a single recordSuccess
  on the same fresh entry, same clock/model". Both built one fresh entry at `FIXED_NOW`, scored it
  both ways against fresh models, and compared. The later duplicate was deleted; the
  `initialRelevance` one is kept, being at the right subject. Suite count therefore moves 1207 →
  1206.
- **The two deliberately-opposite sparsity-model choices are both correct**, and each is justified
  at its site. `relevance.eviction.spec.ts` shares one model across its two arms because
  `enforceCapacity` ranks scores *as stored* and every stored score in a running service was written
  under one service-wide model — sharing is the property under test; its ordering (gossip scored
  first) is conservative, since the 500 successes each observe the distance and so score under a
  progressively *lower* sparsity bonus than the gossiped entry got, and frequency credit wins
  anyway. `relevance.properties.spec.ts` isolates a fresh model per call because it compares two
  *base* scores and a shared model would let the KDE difference decide the outcome instead of
  frequency credit.
- The eviction fixture derives its two relevances rather than hard-coding them, so it would fail if
  `recordSuccess` / `initialRelevance` were gutted; its final `have.members` assertion pins that the
  survivor won on relevance, not ring position (`contacted` sits *nearer* self than `gossiped`, so a
  ring-ordered loop would have chosen the opposite).
- `rpc.snapshot-merge-flatness.spec.ts` being core-profile-only is acceptable: every fixture id list
  there is one entry long, so the profile-split merge caps bound nothing that varies. Its second
  test ("still credits the announcing peer") is what stops the first from passing vacuously.
- **The handoff's stated coverage gap is already closed.** `churn.leave.spec.ts`'s "records a
  dialable replacement as an unclassified entry, scored once and only once" drives the leave
  replacement path through `noteDiscovered` *and* re-leaves the same id twice, asserting
  `relevance`, `accessCount` and `lastAccess` are all unmoved. No additional test was needed.
- `rpc.snapshot-merge-cap.spec.ts`'s fresh `GOOD_3`/`GOOD_4` pair for the fetch phase is a real fix,
  not churn: re-merging the announce body would have upserted nothing (`noteDiscovered` writes only
  for an unheld id) and the assertion would silently have measured that rule instead of the parser's
  drop.
