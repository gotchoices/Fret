### Confirmed correct — no change needed

- **`handleConnect`'s three-field patch** (`relevance`, `lastAccess`, `accessCount`) is exactly
  the set production's `touch` changes: no field dropped, none written that `touch` did not
  compute.
- **`scoreMerge`'s `observeDistance` then `initialRelevance` ordering** matches what production's
  `touch` / `recordSuccess` do internally (observe first, then read the bonus). The separate
  `observeDistance` call is required because `initialRelevance` deliberately does not observe —
  that is the documented deviation, correctly expressed.
- **No conflict with the contact sweep.** `scoreMerge` reads `scheduler.getCurrentTime()` while
  the sweep takes a `time` parameter, but on both paths that reach a merge those are the same
  number (`handleStabilize` and `deliverPendingMessages` each derive `time` from
  `getCurrentTime()`). Re-probe ordering is not perturbed: all three merge sites skip a locally
  `dead` entry and `scoreMerge` runs only where the upsert ran, so a merge never stamps
  `lastAccess` on a dead entry — that ordering stays owned by `recordContactFailure` and
  `reprobeDeadEntries`. Double-scoring in one tick is benign (same counters, same timestamp); the
  KDE being observed twice is the acceleration `scoreMerge`'s NOTE says the sim wants.
- **The two non-null assertions in `scoreMerge`** (`this.models.get(...)!`,
  `this.peers.get(storeOwnerId)!`) cannot throw: `this.peers` entries are never removed
  (`handleLeave` sets `alive = false`), and `addPeer` is the single construction seam for both
  maps. A candidate "departed store owner throws a TypeError" finding was investigated and
  dismissed — do not re-file it.
- **The `enforceCapacity` NOTE's list of scoring sites is complete.** Grepping every `.upsert(`
  in the harness returns exactly five sites: the `addPeer` self-seed (line ~206), the
  `handleConnect` bootstrap dials (~423), and the three merge sites (~381 in
  `processDeliveredMessage`, ~633 and ~643 in `exchangeNeighborsDirect`). All five are followed
  by a scoring call, so the NOTE's "every entry a store holds is scored at the site that put it
  there" holds, and "three merge sites" is the right count. The one exception is the accepted
  tradeoff already documented at `reprobeDeadEntries`, which restores an entry without scoring
  it. This matters beyond the NOTE itself: `28.5-sim-metric-guard-case` expects it.
- **The protection-set sentence still matches the code.** `enforceCapacity` builds
  `ringNeighborsBothSides(store, selfCoord, max(2, m), peerId, { filter: notDead })` and adds
  `peerId`, i.e. `2 * max(2, m) + 1` ids, and the eviction is a single ascending-relevance slice
  that cannot loop — so "protection outranks the cap" is literally true of the code.
- **Capacity is enforced on both stores the two-directional merge writes to**: the neighbor's
  store inside `exchangeNeighborsDirect`, and the peer's own store once after the exchange loop
  in `handleStabilize`.

### Fixed in this pass

- **Undocumented wall-clock / sim-clock mix.** `DigitreeStore.upsert` stamps `lastAccess` with
  `Date.now()`; every scoring site then patches it to sim time, so the *first* scoring of an entry
  computes recency over `max(0, simNow - wallClock)` — always 0, recency exactly 1.0 — while later
  re-scores decay against a real sim-time stamp. Benign, but not derivable from the code and the
  kind of thing the next reader re-derives from scratch. Written down as a `NOTE:` on
  `scoreMerge`'s doc block, which is the site every merge goes through.
- **DRY: the inline copy at `handleConnect`.** The three merge sites share `scoreMerge` while
  `handleConnect`'s proven-contact scoring is inline; both are "score one entry in one store",
  differing only in hearsay vs proven contact. A `scoreContact` sibling was considered and **not**
  extracted: there is exactly one proven-contact site, so the helper would have a single caller,
  and the refactor would need a full 5-minute test rerun for no behavior change. Instead a `NOTE:`
  at `handleConnect` names the pairing, points at `scoreMerge`'s doc block, and says to extract
  the pair if a second proven-contact site ever appears — which closes the actual risk (a future
  edit not noticing the inline copy) at the cost of a comment rather than a refactor.
- **`docs/fret.md`, *Testing strategy* → *Simulation*.** The doc said the per-tick contact sweep
  was what stopped entries tying at relevance 0. That was half the story after this diff. It now
  states all four scoring sites, names the `reprobeDeadEntries` exception, and records the
  deliberate gossip-fed-KDE deviation from production — which until now lived only in a code
  comment. No other claim the diff touches was found stale.

### Found and deliberately not changed

- **`addPeer` computes `normalizedLogDistance(peer.coord, peer.coord)`, a constant 0.** Left as
  written: the surrounding comment explains that self sits at distance 0 and that the KDE is
  deliberately not observed with it, so the expression reads as intent where a literal `0` would
  read as a magic number. Recorded here so the next reviewer does not re-decide it.
- **Source size.** `test/simulation/fret-sim.ts` measures **911 lines**
  (`wc -l test/simulation/fret-sim.ts`), up from 899 before this review's comment additions and
  ~830 before the implement diff, against six focused sibling modules of 51–220 lines. Not split:
  it is the harness's dispatch core by design, and the growth in this pass is documentation, not
  logic. An observation for whoever next adds behavior to it, not a ticket.

### Handed on rather than done (budget)

This session was budget-warned immediately after the gate. The one remaining item is already
covered by an open ticket, so nothing new was filed:

- **No test separates merge-site scoring from sweep scoring.** The implement handoff claimed no
  test asserts on a relevance value anywhere — that is now **stale**:
  `simulation.partition.spec.ts:476` ("contact scoring writes real relevance, reproducibly")
  asserts every entry's score is finite and non-zero across all stores and that the same seed
  reproduces the exact score set. What it does *not* do is tell the arms apart, so a merge site
  that silently stopped scoring would still leave non-zero values behind. That belongs with the
  parent `28-sim-relevance-scoring`, which owns the scoring model as a whole and can pin the arms
  apart in one place rather than bolting a second assertion onto a partition spec.
