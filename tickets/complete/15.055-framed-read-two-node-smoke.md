Test-only change (implement commit `ffce1eb`); no production source touched. A new spec stands up
two in-memory libp2p nodes, registers a reply-only JSON handler on one, and has the other issue a
real `rpcRequest` against it — so the reply travels through `readFramedFromStream`, the real
framed-read path, rather than a stub stream. It pins the positive invariant the framed-read work
needed: a reply that was actually written is never reported as truncated.

## Review findings

### Checked

- **Overload selection.** The reply-only `registerJsonHandler` overload is chosen correctly (the
  options bag carries no `parse` key) and the new tests send no request body, which matches.
  `rpcRequest` with a `decode` validator selects the typed overload (`src/rpc/request.ts:199-215`),
  so `res.value.cell` is genuinely typed rather than `unknown`.
- **Harness usage.** `await node.start()` after `createMemNode()` is the house pattern, not a double
  start. The single dial in `before` is required: `rpcRequest` → `openRpcStream` dials by bare peer
  id, which needs an address in the peerStore.
- **Path under test.** The `Infinity`-mode read is on the real path: a live libp2p stream takes
  `readFramedFromStream`, the implementation the framed-read work introduced.
- **The half-close assertion is not a flake.** A half-written frame throws `UnexpectedEOFError`,
  which `isFrameTruncationError` (`src/rpc/protocols.ts:328-331`) matches by name alongside
  `FrameTruncationError`, so `classify` maps either to `decode-error`. Neighbouring cases that
  accept two outcome kinds are the *reset* shapes, where a live muxer may or may not deliver the
  buffered bytes first; a clean half-close always delivers its bytes, so pinning one kind is right.
- **Timing bound safety.** Every `expectPrompt` call site measures over an already-established
  loopback connection (the dial happens in `serving`, outside the timed window), so the tightened
  bound is safe at each site.
- **Gate.** `npx tsc --noEmit` clean; `yarn test` — 961 passing, 0 failing (~4 min). No
  pre-existing failures surfaced, so no `.pre-existing-error.md` was written.

### Found and fixed inline (minor)

- **Duplicate case** in `test/rpc.stream-errors.spec.ts`. `expectPrompt` was tightened from
  `RPC_TIMEOUT_MS / 2` to `RPC_TIMEOUT_MS / 10` (reasoning moved into the helper's own doc comment),
  after which the case the implement stage added — "an end-of-stream read fails an order of
  magnitude inside its own budget" — asserted the same setup, same `decode-error` and same bound as
  the case directly above it, which additionally asserts stream release. Deleted the weaker one.
- **Missing macrotask arm** in `test/rpc.two-node-framed.spec.ts`. The `MICROTASK_DEPTHS` number
  list was replaced by a `TIMINGS` data list (`immediate`, `micro1`, `micro2`, `micro4`, `macro`).
  Microtask depths all resolve in the same tick, so none of them plainly opens the window the
  false-truncation bug needed (reader pulling before the writer has written); the added macrotask
  arm (`setTimeout(…, 0)`) does. Assertions stay `kind === 'ok'` and stay timing-agnostic.
- **Stale documentation** in `docs/fret.md`. The stream-read-deadline bullet still described a 20 ms
  `EOF_POLL_MS` poll that no longer exists (`grep -rn EOF_POLL_MS packages/fret/src` returns
  nothing). It now states the current mechanism — `readFramedFromStream` failing at the stream's own
  layer with `UnexpectedEOFError` — and cites both specs.
- **Testing-strategy section** of `docs/fret.md` said nothing about the new spec. Added a clause
  under *Integration tests* naming it and the invariant it pins; the stream-read-deadline bullet
  already cited it for the failure side.

### Major findings

None. Stated with the reason: the change is test-only, the production path it exercises was
reviewed in the framed-read work that introduced it, and no finding here had a class behind it that
would warrant an architecture climb.

### Tripwires

None parked this pass. Nothing found was of the "fine now, only matters if X later" shape — the
three findings were all present-tense defects and were fixed inline.

### Weaknesses carried forward

Honestly stated by the implement handoff and still true after this pass:

- Memory transport only — no TCP, noise or identify in the loop.
- Replies are ≤ 512 bytes, so a reply is never split across chunks; multi-chunk framed reads stay
  covered only by the stub-stream specs.
- The `/10` timing ratio is a judgement call, not a measurement.
- The timing spread is plausible rather than a proof that any particular reader/writer interleaving
  is exercised — the macrotask arm makes the pre-write read likely, not certain.
