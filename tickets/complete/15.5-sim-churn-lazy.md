`sim-route-local-selector`, `sim-routing-guard-spec`.

## What shipped

**`event-scheduler.ts`** — `'churn'` added to the `SimEvent['type']` union. No other scheduler
change.

**`fret-sim.ts`**
- `scheduleChurn()` emits bare `{ type: 'churn' }` events on the cadence
  `t = intervalMs; t < durationMs; t += intervalMs` and picks nobody. It previously drew every
  leaver from the *initial* population at setup, so a late joiner could never churn and a peer
  drawn twice produced a second no-op leave.
- New `handleChurn()` runs at fire time: `rng.pick` over the currently-alive peers →
  `handleLeave(id)` → `handleJoin()`. Late joiners eligible, duplicate picks impossible,
  population stationary.
- `handleEvent` switch gained `case 'churn'`.
- `SimConfig.churnRatePerSec` doc comment states the pairing.

**`simulation.spec.ts`** — the two `totalJoins !== n` throws on churn-enabled cases relaxed to
`< n`. The two `churnRatePerSec: 0` cases left exact. Suite timeout 60s → 180s with a `NOTE:`
giving the reason and the measured cost.

**`churn-scenarios.spec.ts`** — two new cases: *continuous churn keeps the population stationary*
(N=40 @ 2/s, asserts leaves, joins and final alive count exactly) and *churn replays identically
across runs at one seed* (N=30 @ 3/s, two runs, `JSON.stringify` compare plus a non-vacuity
guard).

Added during review (see findings): a corrected `churnEvents` formula in the first new case and a
tripwire `NOTE:` at `handleLeave`.

### Major — filed as `fix/15.55-sim-joiner-placement`

**Every mid-run joiner lands in a shrinking arc at the top of the ring.** `uniformCoord` divides
the ring by `this.nextPeerIndex`, but `handleJoin` increments that counter *before* placing, so a
joiner at index `i` lands at fraction `i/(i+1)` of the ring rather than being spread across the
population. Measured on the new stationary-population case (seed 6006, n=40, 2/s, 10s): 16 of the
40 alive peers (40%) sit inside the ring arc `[0.9756, 0.9831]` — 0.75% of the ring — while the
largest gap between adjacent live peers is 10.0% against a uniform 2.5%.

The defect is pre-existing in `uniformCoord`; what this ticket changed is its reach. Before, joins
only happened through the batch-join helpers in four test cases. Now every churn-enabled run
performs one join per churn event, so the degenerate placement dominates the headline N=100
scenario and every churn suite. The new stationary-population test passes because it counts peers
and never looks at where they sit.

Filed into `fix/` rather than `backlog/` because the two sibling tickets exist to measure routing
quality in this harness and would calibrate their thresholds against this ring. Filed at the
generalized rung as well as the point fix: the ticket asks for a max-ring-gap invariant test over
a mix of initial, batch and churn joins, which covers the batch-join paths that have the same
defect and no coverage today.

Site-claim check ran over all five open stage folders. `plan/21-cleanup-tests` mentions moving
`generateCoord` into its own module (a refactor) and the siblings mention coordinates only as
routing inputs; none claims this defect, so a fresh ticket was correct rather than an arm.

### Minor — fixed in this pass

- **`churnEvents` was computed with `floor`, which undercounts on a non-dividing interval.**
  `Math.floor(durationMs / interval) - 1` matches `scheduleChurn`'s loop only when the duration
  divides evenly. At rate 3 (interval 333ms) over 8000ms the loop fires 24 times and the formula
  returned 23. The case that used it happens to divide evenly, so it passed — but the second new
  case runs at exactly that rate and would have been wrong had it used the same helper. Corrected
  to `Math.ceil(durationMs / interval) - 1`, which is right in both cases, with a comment naming
  the loop it mirrors.

### Tripwire — recorded, not filed

- **Departed peers are never reclaimed.** `handleLeave` sets `alive = false` but leaves the peer
  in `peers` and its store in `stores`; both maps now grow linearly in run length × churn rate
  (measured 59 entries for a 40-peer 10s run at 2/s). Every hot path filters on `alive`, so this
  is memory, not per-tick cost, and it is genuinely conditional — it only becomes work if a long
  or high-rate run runs out of memory. Parked as a `NOTE:` at `handleLeave` in `fret-sim.ts`.

### Considered and left alone

- **The two relaxed assertions in `simulation.spec.ts` could be exact** (`totalJoins` is
  deterministically `n + churnEvents`). Left as `< n`: making them exact would duplicate
  `scheduleChurn`'s cadence arithmetic at two more sites, and the new
  *continuous churn keeps the population stationary* case already pins the exact pairing at one
  site. The implementer asked for a judgment on that coupling; this is it — one exact site, the
  rest as floors.
- **Hard equality on counts in the new cases** is the right coupling for the same reason: a margin
  would not catch an off-by-one in the leave/join pairing, which is the whole thing being tested.
- **Suite timeout raised to 180s rather than shortening the N=100 case.** Left as the implementer
  set it. The four suites together run 2m, which sits inside the runner's 10-minute idle timeout
  with room; shortening `durationMs` would change what the case measures and is a scope call.
- **`handleChurn` with an empty alive population** is un-exercised, as the handoff notes. Read the
  path: `rng.pick` returns `undefined` before consuming a draw, so the RNG stream is unshifted and
  the event degenerates to a plain join, which repopulates. Correct as written and deterministic;
  no test added because reaching it needs a batch-leave draining the ring while churn is
  scheduled, and the behavior there is obvious from the code.
- **Determinism of the lazy schedule** holds: `EventScheduler.schedule` re-sorts with
  `Array.prototype.sort`, which is stable in V8, and appends, so an event inserted mid-run sorts
  after existing events at the same timestamp. The new replay case pins this empirically.

### Observation for the sibling measurement ticket — no action here

Coverage reads exactly 87.5% in every scenario across all four suites — baseline, during a
partition cut, post-heal, post-burst, under continuous churn. A metric that never moves across
that range of conditions is more likely degenerate than genuinely flat. Not investigated further
and not filed: `sim-routing-guard-spec` is the ticket that owns simulation measurement, and it
should confirm the coverage metric responds to conditions before building thresholds on it.
