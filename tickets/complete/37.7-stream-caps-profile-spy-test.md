## What shipped

`packages/fret/test/rpc.stream-caps-profile.spec.ts` — 5 cases. It replaces `node.handle` /
`node.unhandle` on a memory-transport node with recorders and asserts what `FretService` actually
hands libp2p:

- **Profile split, per profile.** Calls the private `registerRpcHandlers()` directly and asserts
  the log carries **all five** protocols once each, every one at that profile's caps (Core
  `{128, 256}`, Edge `{32, 64}`). Asserted as a *set*, not a count — `registerNeighbors` registers
  two of the five, so a count could be satisfied by a duplicate.
- **start → stop → start, per profile.** The caps are applied inside `registerRpcHandlers`, which
  is on the `start()` path, and `stop()` unhandles all five — so a cap applied once at construction
  would silently vanish here.
- **Optional caps for an external caller.** Registers a consumer protocol through the
  root-exported `registerRpcHandler` with no cap fields; the claim is compile-time, the runtime
  half asserts `undefined` is forwarded rather than a default fabricated.

Expected numbers are pinned as literals, not read back out of `streamCaps()`.

## Review findings

The review ran in two passes (the first crossed its token budget after the reading and before the
commands; this ticket covers both).

**Read against source — all four claims confirmed, none taken on trust:**

- `FretService.streamCaps()` returns Core `{128, 256}` / Edge `{32, 64}` — matches the spec's
  literals and `docs/fret.md`.
- `registerRpcHandlers()` computes it once and passes it to all four registrars, on the `start()`
  path — so the lifecycle case tests a real risk, not a hypothetical one.
- `registerRpcHandler` forwards `{maxInboundStreams, maxOutboundStreams}` as `node.handle`'s third
  argument under exactly those names, **always as an object** (fields `undefined` when omitted) —
  which is why the external-caller case's `opts`-present-but-fields-`undefined` assertion is
  correct as written rather than accidentally passing.
- Helper imports (`NETWORK` / `P`, `createMemNode` / `stopAll`) all exist and are exported.

**Minor — fixed in this pass:**

- *Leaked stabilization loop on assertion failure.* The lifecycle case ran `svc.start()` with its
  assertions outside any `try`, so a failure between the first `start()` and the final `stop()`
  left the loop armed — which fails the repo's mocha exit watchdog for the **whole run**, not only
  that case. The body from the first `start()` is now inside the existing `try`/`finally`, with a
  comment at the site saying why.
- *Docs out of date.* `docs/fret.md`'s *Stream management* section named the sibling enforcement
  spec but not this one. It now names both, says which half each owns, and states the residual
  (below) inline.

**Major — none.** No finding warranted a new ticket. Nothing in the diff touches `src/`, the two
specs are complementary by construction rather than overlapping, and no invariant was found that a
type or property test could make unbreakable.

**Tripwires — two, recorded as `NOTE:` at the spec's header (not filed as tickets):**

- Neither spec asserts the *shipped* 128/256 and 32/64 are enforced end to end — this one proves
  they are *requested*, the sibling proves a rigged cap of 2 is *enforced*. Closing that needs 33+
  concurrent streams on one connection. Revisit condition recorded: only if a cap is ever suspected
  of being requested-but-ignored at its real magnitude.
- `registerJsonHandler`'s two option interfaces declare the same cap fields optional and `tsc` is
  the whole compile-time claim; no case *drives* them with the fields omitted. Revisit condition:
  if that seam ever grows a runtime default instead of forwarding `undefined`.

**Considered and dismissed — no action:**

- *The spy stubs are never restored.* Each case builds its own node in `beforeEach` and stops it in
  `afterEach`, so nothing leaks between cases, and the helper's doc comment already states it. Not
  a defect and not conditional — a future case reusing a node would have to opt into the reuse.
- *`node.handle` is stubbed, so the lifecycle case runs against a node with no live inbound
  handlers.* Deliberate and documented in the helper: unhandling what libp2p never saw would
  measure the registrar's tolerance rather than the service. The case's claim is about *which
  registrations happen across the cycle*, which the stub observes exactly.

**Source hygiene:** spec is 181 lines, one describe per profile driven from a table, one shared
assertion helper (`expectAllFiveAt`), no duplicated literals. Comments state *why* (why a set not a
count, why literals not `streamCaps()`, why the private method is called directly) rather than
restating the code. Nothing to split.
