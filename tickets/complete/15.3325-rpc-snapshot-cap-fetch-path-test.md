Test-only ticket. No production code changed at any stage — the size limits and the message parser
shipped under `rpc-snapshot-cap-announce-path-test`. The whole diff is one file,
`packages/fret/test/rpc.handler-fuzz.spec.ts`.

## What landed

Two coverage gaps closed, inside the block renamed from `announce snapshot merge caps` to
**`snapshot merge caps`** now that it covers both inbound routes. Each new test runs once per
profile, so four cases; the block went from 175 to 179 passing.

**`applies the same caps on the fetch path, and never upserts the snapshot sender`** — the fetch
route had no size-limit test at all, so the claim that it was covered rested on reading the code. It
now drives the private fetch method against a stub reply stream serving one over-long neighbour
list, counts the routing-table writes, and deep-equals the counted ids against the expected first-N
of each list.

**``drops a `relevance: null` sample entry on both merge paths``** — the strictness was pinned at the
parser only. One test now drives a three-entry sample through *both* routes and asserts the unusable
entry reaches neither, while both usable ones do.

Two block-scope helpers support them: `replyStream` (a one-frame stub stream) and `fetchMerged`
(installs the connection override and the write counter, drives the fetch, restores the override).

### The two mutation gaps the handoff flagged — both closed by observation

The handoff was honest that its two central assertions were argued structurally and never watched
to fail. Both were run:

- **Size limits.** Temporarily replaced `mergeSnapshotCaps()` with unlimited values and re-ran the
  block: **8 failing** — the new fetch test fails in both profiles, alongside the three announce-path
  limit tests. This is also the handoff's own suggested probe ("raise/lower a profile's limits and
  confirm both paths fail together"): they do, which is what makes the two routes one source of
  truth with two readers rather than two agreeing copies.
- **The connection override in `fetchMerged`.** Temporarily made it return no connection: **4
  failing** — both new tests, both profiles. So the override is load-bearing, exactly as the handoff
  claimed, and not scaffolding that could be deleted without noticing.

Both mutations were reverted from a byte-for-byte backup and the working tree confirmed clean
afterwards. Neither test is vacuous.

### Handoff claims verified rather than assumed

- The stub stream really does take the plain-iterable read path, not the real-stream one: the
  dispatch predicate requires six methods and the stub has one of them. The handoff's caveat is
  accurate, and its scoping decision (the subject is the size limit, not the framing) is right —
  real-stream read behaviour is owned by `test/rpc.two-node-framed.spec.ts` and
  `test/rpc.stream-errors.spec.ts`.
- The fetch route genuinely never stores the sending peer itself, so the expectation's missing
  leading entry is deliberate and correct, not an oversight.
- Driving the private method rather than the public sender is the right call: that sender's parser
  argument *defaults* to unlimited, so a test calling it directly would have proven nothing about
  the limits the service supplies.

### Fixed in this pass

- **The write-counter's stacking hazard was documented in the wrong place.** The helper stacks
  wrappers rather than replacing them, and nothing restores — so a test installing a second counter
  keeps feeding the first. The handoff called this "a real sharp edge for the next test added to
  this block" and noted it was documented at the call site only. That is precisely backwards: the
  next person to hit it is writing a *new* test and reading the helper, not reading the one existing
  test that works around it. Moved the warning onto the helper's own doc comment, stating the
  workaround, why it is left stacking (a restore handle would change all eight call sites for one
  caller's benefit, and each test gets a fresh service) and the condition to revisit. The handoff
  asked for a judgement call on changing the helper's shape; the judgement is no, recorded at the
  helper.

Nothing else needed fixing. No defect was found in the diff: the assertions are shaped correctly,
the fixtures are disjoint (and there is a test asserting that), and the two helpers are the right
size.

### Filed as a new ticket

- `backlog/debt-fetch-snapshot-failure-arms-untested` — the handoff's own gap ("no test covers a
  fetch reply the parser rejects"), widened to its real root. That reply is one of seven ways a
  neighbour-list fetch can fail, each with deliberately different bookkeeping, and only the success
  case is directly tested. Filing the one arm the handoff named would have been the instance; the
  class is the whole outcome switch, and the rule it implements is argued at length in `docs/fret.md`
  yet unpinned. Filed at that level, with the honest counter-argument that this is bookkeeping
  nothing user-visible depends on.

### An open ticket corrected rather than a new one filed

The site-claim grep found `backlog/debt-snapshot-merge-loop-duplication` already claiming
`fetchAndMergeSnapshot`. Reading it, **it had gone materially stale against the code** — and the two
tickets that made it stale are this one and its predecessor, so correcting it belongs to this pass:

- It describes both merge loops as applying the size limits inline and quotes the exact expressions.
  Those no longer exist; the limits moved into the parser under the predecessor ticket.
- Its central argument is that the invariant "the limits are applied in exactly one place" should be
  made structural. That invariant is *already* structural, by a different route.
- Its "what it buys the tests" section says the fetch path is an untested gap. This ticket closed it.

Left open — the plain duplication and the logging drift it documents are still real — but the body
now carries a "What has changed since this was filed" section, the overstated sections were cut, and
the `tradeoffs:` line points at it. A human triaging that ticket would otherwise have estimated it
against a codebase that no longer exists.

### Deliberately not filed, with reasons

- **Real-stream coverage of the fetch read path.** The stub exercises the iterable implementation,
  not the byte-stream one. Deliberate and correct scoping — two other specs own real-stream framing
  behaviour, and duplicating it here would restate their coverage under a ticket about size limits.
- **The sample fixtures use ids that are not parseable peer ids.** True, and pre-existing convention
  in this block (the wrong-width-coordinate tests do the same). It works because the sample loop
  never parses a sample id. Conditional rather than latent — it would only matter if an id-parse
  guard were added to those loops — and the block's existing helper comment already explains which
  fields need parseable ids. Not worth a ticket or a tripwire on top of that.

### Tripwires recorded

- The write-counter's stacking behaviour, parked as a `NOTE:` on the helper itself in
  `packages/fret/test/rpc.handler-fuzz.spec.ts` (see "Fixed in this pass"). Conditional: it only
  becomes work if a second test needs two counters, or if a test ever reuses a service.
