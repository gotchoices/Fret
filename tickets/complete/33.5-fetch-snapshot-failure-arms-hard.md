## Review findings

### Checked and confirmed correct — no change

- **The arms really are discriminated, in both directions.** Read `noteRpcFailure`
  (`fret-service.ts:873`) fresh this run rather than trusting the handoff table.
  `foreign-protocol` reaches `applyMembershipSignal(id, 'negotiate-failure')` and nothing else;
  `unreachable` / `timeout` reach `applyContactFailure` → `applyFailure` (`failureCount` +1,
  relevance recomputed) then `applyContactStrike` (`contactFailures` +1). Each test asserts on
  **both** channels — the one that must move and the one that must not — so the collapse the
  implementer asked about is caught: routing `foreign-protocol` into `applyContactFailure` fails on
  `negotiateFailures` not moving *and* on `contactFailures` moving. The same holds in reverse.
- **`failureCount` is the right proxy for "relevance was re-scored"** — the implementer's own open
  question, answered against the code rather than the docs. `applyFailure` calls `scoreFailure`,
  which **recomputes** relevance from the health counters; it does not scale the previous value
  down. On a freshly-seeded entry every counter is 0 and relevance is 0, so the post-failure value
  moves *upward* — asserting a decay would be asserting something false, and asserting an increase
  would pin an artifact of `seed()`. `failureCount` is the counter that drives the recompute and is
  direction-free. Keeping the seed as-is is correct; changing it to seed a success first would buy
  a weaker assertion coupled to the scoring formula's shape.
- **`foreign-protocol`'s second node correctly runs no FRET service.** An unstarted
  `CoreFretService` registers no handlers, so it is indistinguishable at the wire from a bare node.
  The arm needs "connected and reachable, no handler for this network's neighbors protocol", which
  is what the test builds.
- **The `decode-error` test pins the fetch path's silence, not `noteRpcFailure`'s decode arm.**
  Worth naming because the two differ deliberately: `noteRpcFailure`'s `decode-error` case *does*
  score (`noteAnsweredOnProtocol` + `applyFailure`), but `fetchAndMergeSnapshot` returns before
  calling it for `decode-error` / `busy`, preserving the old fabricated-empty-snapshot path's
  score-free behaviour. That divergence is documented at both sites and in `docs/fret.md`, and the
  test asserting "entry unchanged" is what pins the fetch path's half of it. Not a defect; recorded
  so a future reader does not read the test as a claim about `noteRpcFailure`.
- **Docs.** `docs/fret.md` describes the outcome variants, the evidence-strength ordering and the
  spacing rules; all of it still matches the code as read this run. This change is test-only and
  adds no behaviour to document, so no doc edit was warranted — checked rather than assumed.

### Minor findings — fixed in this pass

- **The timeout test's wall-clock bound could not fail for its stated reason.** It asserted
  `elapsed < REAL_TIMEOUT` (1000 ms) against an override of 50 ms. If the static override silently
  stopped taking effect the fetch would run the real 1000 ms deadline and land *at* the bound, so
  the test's discrimination rested on scheduler overhead pushing it over — not on the property it
  claims to pin. Tightened to `< REAL_TIMEOUT / 2`, which is 10x the override and far outside
  scheduler noise (measured 53 ms), so it now fails loudly if the override stops working while
  still not pinning the deadline's exact value.
- **The three stub helpers duplicated the connection override/restore.** `withStubReply`,
  `withFailingOpen` and `withHangingStream` each hand-rolled the same
  `getConnections` swap and `finally` restore. Factored into one `withConnection(newStream, fn)`
  seam. The three *behaviours* stay three separate functions on purpose — each must remain incapable
  of producing the others' stream behaviour, which is what makes the arms discriminable — but the
  scaffolding around them is now stated once, so a leaked override can only be introduced in one
  place.

### Major findings

None. No architectural issue was found: the tests read the same bookkeeping fields the service
writes, through the service's own public store accessor, and make no assumption the implementation
is free to change silently.

### Filed as a new ticket

- `tickets/backlog/debt-negotiate-failure-spacing-untested.md` — the implementer flagged both
  spacing guards as unexercised and asked for a judgement. Checked: the **contact-failure** guard is
  already covered (`test/dead-state.spec.ts`, "counts failures inside the spacing window as one
  observation"). The **negotiate-failure** guard is not — every test touching it rewinds
  `lastNegotiateFailureAt` so strikes count, so deleting the 500 ms check would leave the suite
  green while a single blip could write a peer off as foreign. That belongs at the counter's own
  site (`applyMembershipSignal`), not in this spec, where every test makes exactly one call and a
  burst test would be testing a different function. Site-claim grep run first: no open ticket
  touches it.

### Recorded as gaps, deliberately not filed

- The remaining items the handoff listed honestly — no test drives these arms through a real
  stabilization tick (covered at tick level by `test/stabilize-concurrency.spec.ts`), and
  `foreign-protocol` pins the single increment rather than the threshold-of-3 demotion (pinned in
  `test/ring-membership.spec.ts`). Both are coverage that exists elsewhere at the right altitude,
  not gaps.
- `extraNodes` is used by one test only. Left as-is: it is the correct teardown shape for a
  multi-node arm, costs one array, and removing it would be undone by the next such test.
