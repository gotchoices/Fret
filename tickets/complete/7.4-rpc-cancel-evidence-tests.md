Test half of the cancellation-evidence work for `rpc-service-signals` (Phase 4 of
`7-rpc-abort-deadlines`). The documentation half is `rpc-cancel-docs`, still in `implement/` and
independent (disjoint files).

## The rule that landed

`FretService.wasCancelled(sig)` is `sig?.aborted === true`, checked against the run signal the
**caller** captured before its loop — not the sender's own deadline, which is a child of it and so
also fires on a genuine timeout. When it is true the call site records nothing: no
`noteRpcFailure` (hence no contact strike, no relevance decay, and no membership evidence), no
`recordBackoff`, no `diag.pingsFail`. Without it a `stop()` landing on a busy tick manufactures
strikes against healthy neighbors and can mark them `dead`.

## What shipped

**Tests** — a `describe` block, "cancellation is not evidence about a peer", in
`packages/fret/test/dead-state.spec.ts` (10 tests). The service is constructed but never started —
a live stabilization loop would probe the synthetic peers and make every count non-deterministic —
and a local `cancelRun()` reproduces the state `stop()` leaves behind: a fresh `AbortController`,
aborted, assigned to the private `runAbort`, with `stopped` deliberately left `false` so what stops
each pass is the *signal* alone. `liveRun()` is the contrast. Each cancelled-path test asserts the
same shape via a shared `expectUnscored(id)` — entry still present, no contact strike, no relevance
decay, no membership evidence, not demoted, not `dead`, no backoff entry — plus the diagnostics
counter belonging to that call site.

Call sites driven: `probeNeighborsLatency`, `probeMembership` (the load-bearing backoff case),
`preconnectNeighbors` (counted by `dialProtocol` calls, since that site never increments
`pingsSent` for a failed ping either way), `mergeNeighborSnapshots`, `sendAnnouncementsRateLimited`,
the `routeAct` forward path, and both arms of `iterativeLookup` (hop probe and activity resend).

**Source, two changes:**

- `sendAnnouncementsRateLimited` — the top-of-loop check widened from `if (this.stopped)` to
  `if (this.stopped || this.wasCancelled(sig))`, and the `catch`'s `wasCancelled` return removed
  because it was unreachable on the cancellation path. Behaviour change: a cancelled run spends
  **zero** announce tokens instead of one per remaining target.
- `iterativeLookup` — a `NOTE:` at the final `yield { type: 'exhausted', hop }` recording that
  `exhausted` conflates "the ring offered no further hop" with "our own run was cancelled", and why
  widening `RouteProgress` (a public interface type) was rejected. `rpc-cancel-docs` already knows
  to check for this rather than adding it again.

## Recipes worth knowing before editing these tests

- **Real Ed25519 peer ids, never synthetic strings.** `sendPing` / `sendMaybeAct` call
  `peerIdFromString` on their first line, *outside* the try, so a synthetic id throws a *parse*
  error — the cancelled-path test would pass for the wrong reason and the contrast would record a
  strike unrelated to reachability. `unreachablePeer(coord?)` spins a mem node, stops it, and seeds
  its id at an optional coordinate.
- **`routeAct` forward path** is forced by hashing the key locally and seeding two member+dialable
  peers at `±1` from the key coordinate, with `want_k: 2`, so the cluster window of
  `max(2, min(2,2)) = 2` is filled by them and self (not in the store) is never in-cluster.
- **The activity-resend arm** needs a second node running a *started* `CoreFretService` on the same
  `networkName`. The generator is driven with explicit `.next()` calls and the controller aborted
  the moment `near_anchor` arrives, so the abort lands on the resend rather than the probe.

## Review findings

**Read first, in order:** the implement diff (source, then tests) with fresh eyes, then the handoff,
then every source site the diff names. Everything below was verified against the code rather than
taken from the handoff.

### Verified — the handoff's load-bearing claims all hold

- `announceNeighbors` catches and logs every error internally (`rpc/neighbors.ts:145-147`), so the
  removed catch-guard genuinely could not fire on cancellation. The top-of-loop check was the right
  place for the fix.
- That `catch` is still reachable, and the comment saying so is accurate:
  `peerIdFromString` runs before `announceNeighbors`'s own try (`rpc/neighbors.ts:133`), and a
  malformed id really can reach it — snapshot *sample* entries are pushed to the announce list by id
  with no `peerIdFromString` validation (`fret-service.ts:1990`), unlike successor/predecessor ids.
- `fetchNeighbors` fabricates an empty snapshot on every failure (`rpc/neighbors.ts:108-110`), so
  `mergeNeighborSnapshots`'s guard is dead on the cancel path and the test's `snapshotsFetched` +1
  expectation is correct rather than lenient.
- `sendPing` and `sendMaybeAct` both throw (no swallow), so the other six guards are live and none
  of these tests pass vacuously.
- `readAllBounded` **throws** on signal abort rather than returning a short buffer
  (`rpc/protocols.ts:186,204`), and `deadline()` yields a synchronously-aborted child for an
  already-aborted parent (`utils/deadline.ts:50-53`) while `openRpcStream` throws before dialing
  (`rpc/protocols.ts:283`). Two consequences: the "zero dials" assertion measures what it claims,
  and a *mid-flight* cancellation lands in the same `catch` as a pre-flight one — so the handoff's
  "the tests never open a stream" gap is a coverage gap over a shared code path, not exposure.
- Every outbound RPC call site in `src/service/` was enumerated (11 calls). Eight are run-signal
  scoped and all eight carry the guard; the two `sendLeave` sites deliberately carry
  `SHUTDOWN_BUDGET_MS` instead, because the fan-out runs *after* the run signal aborts. Nothing is
  missing a guard.
- The announce fix cannot silence a legitimate shutdown announce: `stop()` sends leave notices but
  no announces, and `proactiveAnnounceOnStart` runs after `runAbort` is minted.

### Fixed in this pass (minor)

- **`expectUnscored` asserted only one of `noteRpcFailure`'s two arms.** The unsupported-protocol
  arm (`fret-service.ts:633-635`) routes to `applyMembershipSignal('negotiate-failure')`, which
  touches `negotiateFailures` / `membership` and neither `contactFailures` nor `failureCount` — so a
  regression that moved a guard below `noteRpcFailure` would have been invisible whenever the
  cancelled call happened to fail that way. Added `failureCount`, `negotiateFailures`, and
  `membership` assertions, with a comment saying why. This also closes the gap the handoff itself
  flagged ("does not assert `negotiateFailures`").

### Considered and not filed, with reasons

- **The active-preconnect loop tick's guard is untested — and unreachable in production.** Reaching
  it needs an aborted run signal with `stopped === false` *and* `gen === runGen`, but every `stop()`
  sets `stopped` and bumps `runGen`, and the following `start()` bumps it again, so the tick's own
  generation check (`fret-service.ts:1351`) fires first and it never re-arms. Only the direct
  injection these tests use can reach it. A coverage gap over an unreachable branch, so no ticket
  and no fragile timer-driven test.
- **`snapshotsFetched` and `announcementsSent` both count calls that never opened a stream.** Same
  fabrication class, and the root cause is already claimed: `plan/8-rpc-shared-helper` carries
  "fetchNeighbors fabricates success on every failure" and the three-error-contract consolidation
  behind it. Not re-filed; the `NOTE:` at `fret-service.ts:1765-1778` remains the accepted-tradeoff
  write-up at the site.
- **`dialable()` is duplicated between two `describe` blocks** in this spec, each closing over its
  own `svc`. Two lines; hoisting would need a parameter. Below the churn threshold.

### Tripwire recorded

- `dead-state.spec.ts` is now the largest spec in the package at ~1030 lines (measured with
