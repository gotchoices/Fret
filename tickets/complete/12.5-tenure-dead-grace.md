## What landed

A contact-failure run now marks a peer `dead` only when it has reached `deadAfterFailures` (3) **and** lasted `deadGraceMs(provenTenure, maxDeadGraceMs)`. Before, three spaced failed contacts (3–4.5 s) killed every peer alike.

- **`src/store/tenure.ts`**: `DEAD_GRACE_MIN_TENURE_MS` (10 min), `DEAD_GRACE_TENURE_RATIO` (1/12), and `deadGraceMs(tenure, cap)`. It returns 0 below the floor, otherwise `min(cap, tenure/12)`. It is written so that a NaN tenure gives 0: a NaN grace would compare false forever and stop the peer ever being declared dead.
- **`PeerEntry.contactRunStartedAt`**: the unix ms of the first strike in the current run. It is not serialized, is 0 on upsert and on import, and `livenessPatch` clears it together with `contactFailures` and `lastContactFailureAt`.
- **`FretConfig.maxDeadGraceMs`**: default 300 000 ms, and `0` turns grace off. `requireDeadGraceMs` throws when the value is not finite, is below 0, or is above `TENURE_GAP_TOLERANCE_MS` (15 min).
- **`applyContactStrike`** follows the ticket's pseudo-code:
  - The run start is stamped on the first strike.
  - The grace condition sits on `toDead`.
  - `diag.deadGraceHeld++` counts each strike that reaches the threshold but is held.
  - **Narrowed change rule**: only a strike that raised the count, or the one that marks the peer dead, calls `noteChange`. A held strike at the clamped threshold is quiet. With grace 0 this picks out exactly the strikes today's rule counted.
  - A run that has failures but no start stamp (counter written outside this method, e.g. by tests) counts as long over, so it falls back to today's verdict.
- **`NOTE:`** at `markDeparted`: a leave notice still marks the sender dead at once, whatever its tenure. A leave that earns grace waits on leave authentication (`22-debt-leave-authentication`).
- **Docs** (`docs/fret.md`):
  - A new *Dead-verdict grace* sub-bullet under *Hard failure*: the rule, the worked values, what a peer in grace still is, the lateness bound, the off switch and validation, and the import behaviour.
  - The leave-notice exception.
  - The idle-backoff change list narrowed to "progressed its count or completed the run".
  - A pointer from the *Tenure* bullets.
  - `maxDeadGraceMs` under *Configuration*.
  - One sentence in the sim bullet saying grace is not mirrored there.
- **Test helper refactor**: `dialOnlyNode` moved out of `address-less-departure.spec.ts` into `test/helpers/libp2p.ts` as `createDialOnlyMemNode`, so the new spec does not copy it. The address-less spec is otherwise unchanged and still green.

## Known gaps / for the reviewer

- **The narrowed change rule has no test.** The ticket listed it as checked by reading the code, and its test list says "keep to these". The consequence is real, though: a held strike that was wrongly counted as a change would hold the idle backoff at 1.5 s for the whole grace. A cheap pin would be one more pass during grace in `dead-grace.spec.ts` that asserts no `noteChange` for the server (a spy on `noteChange`, or read the `IdleBackoff` change counter). The reviewer should decide whether it earns its place.
- **The "strike exactly at grace expiry is dead (≥)" case is only weakly pinned.** The spec rewinds the run start to `Date.now() − grace`, so it passes under `>=` every time. It catches a mutation to `>` only when the rewind and the strike land in the same millisecond. Pinning it deterministically would need the decision pulled out as a pure function, or an injected clock.
- **Config validation has no new test row.** The only constructor-validation spec is the `dialTimeoutMs` case in `maintenance-redial.spec.ts`, which is about redials. The ticket said not to create a spec for this, so `maxDeadGraceMs` validation was checked by reading the code only.
- **Recovery in (d) is shown by our own ping succeeding over the reconnected link, not by `peer:connect` or an inbound RPC.** The observer is unstarted, so it has no listeners or handlers. All three routes reach the same `noteProofOfLife` seam.
- **A leave-marked dead peer that the dead arm strikes again** gets a run start stamped (its `contactFailures` was 0). Nothing reads the stamp while the peer is dead, and proof of life clears it. The ticket said "run start untouched" for the dead arm, which holds whenever the count is already above 0.
- **`diag.deadGraceHeld` counts held strikes, not peers**: one per pass per held peer. This is documented on the field.

## Review findings

Read the `ticket(implement): tenure-dead-grace` diff first, then the handoff. Checked: `applyContactStrike` verdict and change rule, `livenessPatch` clearing, `contactRunStartedAt` lifecycle on every write path (grep: `applyContactStrike` is the only site that writes a non-zero run, `livenessPatch` the only one that clears it; `upsert` and `importEntries` seed 0, `update` spreads), `deadGraceMs` floor/ratio/cap/NaN, `requireDeadGraceMs` bounds, `markDeparted` NOTE, the facade's `getDiagnostics` typing (`ReturnType` of the core, so `deadGraceHeld` reaches it untouched), the sim's own liveness (`test/simulation/liveness.ts` — separate verdict, unaffected, and the doc says so), and every `docs/fret.md` section the change touches (Tenure pointer, idle-backoff change list, Hard failure grace bullet, leave exception, Configuration, sim bullet) — all match the code.

- **Correctness** — no defect found. Run-start fallback (count > 0, stamp 0 → reads as long over → today's verdict) is sound. Tenure really is frozen across a run: `noteProofOfLife` is the only tenure writer and always clears the run in the same write, so the grace cannot move mid-run. Held peers stay `completed` on every later strike, so the verdict lands on the first strike after the grace.
- **Narrowed change rule had no test (handoff gap 1)** — fixed. Added to `test/dead-grace.spec.ts`: one more pass during grace, asserting `deadGraceHeld` moves to 2 and the idle backoff's change counter does not (read the way `near-exchange.spec.ts` already reads `idle`). Mutation run: restoring the old rule (`if (e.state !== 'dead')`) reddens exactly that assertion; source restored. It earns its place: the regression is silent and costs a phone a 1.5 s loop for the whole grace.
- **`>=` at grace expiry only weakly pinned (gap 2)** — left. Pinning it needs an injected clock or a pure-function extraction, neither worth it for one comparison operator; the doc states the inclusive rule.
- **No `maxDeadGraceMs` validation test (gap 3)** — left: a three-condition guard with no branching beyond the throw, read and confirmed.
- **Interaction worth knowing, not a defect**: a held peer that is *dialable* (has addresses) is redialed each pass; a redial still in flight at pass end holds the loop at its base (existing pending rule), so against a down host whose dials time out rather than refuse, the loop may stay near the base during the grace — one shared dial per `dialTimeoutMs`, not a storm. The doc already says the loop "may" back off over the grace. No tripwire added: bounded by the existing redial dedup.
- **Relevance decay during grace** — each held strike still runs `applyFailure` (×0.7). Harmless: a held near peer is a live member inside the eviction protection set, and success scoring re-ups it on return. No action.
- **Test fragility checked**: in the spec, `serverFret.stop()` sends a leave notice to the observer, which is unstarted and so has no leave handler — the notice fails to negotiate, which is why the second outage is held rather than leave-killed. Holds by construction of the rig; left as is.
