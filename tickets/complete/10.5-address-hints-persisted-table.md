# Addresses in the saved routing table (restart half) — complete

Fixes gotchoices/sereus#18. Optimystic's db-p2p saves and restores the FRET table (`exportTable` / `importTable`). The table used to hold only peer ids. A restarted node's libp2p peerStore is empty, so a bare-id dial to a peer reachable only through a relay failed with `NoValidAddressesError`, and each ring came back holding only itself. The live half (`address-hints-live-exchange`) added `PeerEntry.addressRecord`. This ticket persists and restores it.

## What landed

- **Store** (`digitree-store.ts`): `SerializedPeerEntry.addressRecord?: SerializedAddressRecord` (`{ envelope: base64url, confirmedAt }`) and a named `PeerAddressRecord` type. `serializeAddressRecord` / `deserializeAddressRecord` own the format. The deserializer throws on an envelope that is not base64url and on a non-finite `confirmedAt`. `importEntries` decodes the field in its decode-everything-first pass, so a malformed record refuses the table before any write. `SerializedTable.v` stays 1. Both types are exported from the package root.
- **`address-records.ts`**: `ADDRESS_RECORD_PERSIST_MAX_AGE_MS` (14 days). `freshenExportedAddressRecord` applies the export rule: a peer connected at export gets `confirmedAt = now`, and a record older than 14 days is omitted. `vetPersistedAddressRecord` applies the import rule: corrupt → throw; stale → drop the field; a future `confirmedAt` → clamp to now.
- **Service**: `exportTable` applies the freshness rule. `importTable` vets every non-self entry, imports, enforces capacity, and then runs `consumeImportedAddressRecords`. That method passes each surviving record to `peerStore.consumePeerRecord` with the entry id as `expectedPeer`:
  - `true` → the address is marked known.
  - A throw (bad signature) → the record is stripped and counted in `diag.rejected.addressHint`.
  - `false` → the entry adopts the peerStore's record. This last case was added in review.
  - `rejectAddressHint` became `rejectAddressRecord(source, …)`, so the snapshot and import paths share one count-and-log point.
- **Docs**: `docs/fret.md` covers the serialized-table interface, *Routing table persistence* ("Addresses are restored too"), *Address hints* and *Security*. The `address-records.ts` line in AGENTS.md is updated too.

## Review findings

Read the diff of `ticket(implement): address-hints-persisted-table` first, then the handoff.

- **Correctness — defect found, fixed inline.** The implementer flagged this as a known gap. `importTable` run after `start()` replaces a live entry with the table's copy. When the peerStore already held a newer record (identify-mirrored), `consumePeerRecord` returned `false` and the entry kept the file's *older* record. The entry then forwarded that older record until the next `peer:update` for that peer. That event may never come, because the per-tick `seedFromPeerStore` adopt only fills entries holding nothing. The same happens with a peerStore that persists across restarts. Fix: new `FretService.adoptStoredPeerRecord`. On `false` it reads the peerStore entry, refreshes the address-known state, and runs the existing `adoptPeerRecord`, which applies the byte-equality and sequence rules. That costs one extra peerStore read, and only on the `false` arm. A test was added in `service.table-persistence.spec.ts`: "an entry whose imported record is older than the peerStore one adopts the peerStore one". Removing the new `else` branch makes it fail (checked). Docs updated in *Routing table persistence*. The `sealed` test helper moved up to the outer `describe` so both cases can use it.
- **Correctness — checked, nothing found:**
  - The structural pre-pass refuses the whole table before any write. The reproduction with its negative control, and the refused, stripped and dropped rows, all passed.
  - Non-object `addressRecord` values from JSON (a string, a number, `null`) are either refused by `deserializeAddressRecord` or treated as absent.
  - `peerIdFromString(id)` in the consume loop cannot throw, because the pre-pass already confirmed the signer equals the id.
  - Duplicate ids in the table are safe: the id set dedupes, and the loop reads whatever the store actually holds.
  - A record whose entry was evicted is skipped.
  - The "strip only if still the same record" guard is correct against a hint that lands during the await.
- **Error handling**: every failure is either counted and logged, or refuses the import with a descriptive message. None is swallowed. The new helper logs on a failed peerStore read.
- **Performance**: base64url is decoded twice per record on import (service pre-pass, then store). Accepted by the implementer as cheap and left alone. The serial consume latency already has a `NOTE:` tripwire at `consumeImportedAddressRecords`, so no new tripwire.
- **Type safety / hygiene**: no `any`. The named `PeerAddressRecord` replaced an inline type. Comments state reasons, not narration. No file-size change worth noting. `fret-service.ts` was already ~3800 lines and is tracked by existing size debt, not this ticket.
- **Tests**: the implementer's tests each pin a specified behaviour (the #18 reproduction, corrupt / forged / stale sorting, the store's structural rows, and the codec round-trip generator). None was cut. One test added, for the defect above.
- **Still unpinned (inspection only, left as-is)**: the future-`confirmedAt` clamp, and the evicted-entry skip. Both are one-line branches whose failure would be benign.
- **Docs**: re-read the *Address hints*, *Security*, *Serialized routing table* and *Routing table persistence* sections against the code. They are accurate after the edit above.
- **Validation**: `npx tsc --noEmit` clean, `yarn build` clean, `yarn test` **1303 passing, 0 failing** (log: `tickets/.logs/address-hints-persisted-table.review.test.log`).
- **Tickets filed**: none. **Tripwires added**: none.

## Handoff for the release after this lands (outside this repo)

Sereus's "strand peer book" (`packages/cadre-core/src/strand-peer-book*.ts`, protocol `/sereus/strand-peers/1.0.0`) should be removed once Optimystic raises its FRET floor to a release that includes this change. At that point Sereus passes `NodeOptions.persistence` to db-p2p for each strand node and relies on FRET's persisted records. Sereus's `joined-strand-store` stays. Order:
1. FRET release.
2. Optimystic raises its FRET floor and wires `persistence`.
3. A Sereus removal ticket is filed in the Sereus repo, and its maintainer is told.
