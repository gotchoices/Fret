## What shipped

`MAX_NEIGHBORS_BYTES` (16 KiB) is now the single inbound byte cap on the `/fret/1.0.0/neighbors`
protocol for both Edge and Core nodes. Previously the cap was profile-split, so a Core node with
more than ~5.1 KiB of application metadata overflowed an Edge peer's 8 KiB cap and could no longer
announce to — or answer a neighbors request from — any Edge peer, silently and in one direction
only. The per-entry *acceptance* counts (Core 16/16/8, Edge 8/8/6) and the *emission* caps
(Core 12/12/8, Edge 6/6/6) stay profile-split by design: those bound local work and local output,
while the byte cap bounds a message another peer sends and so must admit any profile's largest
legal emission.

Implement commit `555bdac`; review fixes in `e727d8f`, `d6ed9cb`, `55b067d`.

### What was checked, and found clean

- **The whole implement diff was read** — `src/rpc/validate.ts`, `src/rpc/neighbors.ts`,
  `src/rpc/request.ts`, `src/service/fret-service.ts`, both spec files, and the `docs/fret.md`
  paragraph.
- **The two arms the ticket claims to unify really are unified.** No stray byte literal survives on
  any neighbors path; every read resolves to the single constant `MAX_NEIGHBORS_BYTES` —
  `registerNeighbors`'s `maxBytes` default, `fetchNeighbors`'s `maxBytes`, and
  `FretService.maxBytesNeighbors()`.
- **`MAX_NEIGHBORS_BYTES` is not exported from the package root** — and neither are
  `MAX_ACTIVITY_BYTES` nor the metadata allowances. `src/index.ts` re-exports only the parsers and
  the `Parser` / `SnapshotCaps` types from `validate.ts`. That matches how every other cap is
  treated, so it is a deliberate shape rather than a gap; recorded here so the next reviewer does
  not raise it.
- **Both byte figures in the new doc comments are confirmed by measurement**, not by reading. The
  worst legal Core snapshot at the merge caps (16/16/8 ids, an 8 KiB metadata allowance, 256 bytes
  reserved for the unimplemented `sig`, and 53-character peer ids) encodes to 11,575 bytes, and the
  Edge equivalent at 8/8/6 with a 4 KiB allowance to 6,301 bytes. So the 11,575 / 3,371 / 6,301
  figures the comments assert are correct as written, and the "~4.8 KiB under 16 KiB" headroom claim
  holds. 53 characters is the conservative choice: a real Ed25519 peer id is 52 and the other key
  types are shorter.
- **The test coverage is adequate for what changed.** The encoding cases build both profiles at the
  wider *merge* caps rather than the narrower emission caps actually used today, which is the
  conservative direction and keeps them valid if emission is ever widened; and a third case asserts
  that both profiles resolve the same acceptance number, so re-splitting the cap per profile fails
  in the suite rather than silently on the wire.

### Findings, and what was done about each

- **Two stale statements in `docs/fret.md`** — both fixed inline in the review pass.
  - *Security and abuse considerations* said the inbound snapshot-merge caps bound work "regardless
    of the 128 KB byte limit". The neighbors protocol byte cap is 16 KiB, not 128 KB — 128 KiB is
    maybeAct's activity cap. Corrected, and the sentence now also states why the per-entry
    acceptance counts stay profile-split while the byte cap does not.
  - *Stream management* ended with a bare "Snapshot caps: … profile-bounded (Edge ≤ 6/6/6, Core ≤
    12/12/8)" sitting immediately below the paragraph that had just established a single,
    non-profile-split byte cap — readable as an acceptance number. Relabelled as *emission* caps and
    explicitly distinguished from both the acceptance counts and the byte cap.
- **`relevance` / `size_estimate` / `confidence` are measured at their short forms.** The encoding
  tests use ~11-character values where a JSON double can serialize to ~23 characters. Across 8
  sample entries plus the two scalar fields that is under ~150 extra bytes against ~4.8 KiB of
  headroom, so the invariant is not threatened and nothing was changed. Noted rather than filed.
- **Nothing validates an outgoing snapshot against the acceptance cap.** `announceNeighbors` is
  write-only, and the encoding tests are the whole guard. Judged **conditional, so recorded as a
  tripwire rather than a ticket**: emission is bounded by construction (fixed id counts, bounded id
  lengths, a metadata byte cap) and sits ~4.8 KiB under the limit, so a runtime check would buy
  nothing today. The tripwire is a `NOTE:` at the emission site in `FretService.snapshot`
  (`packages/fret/src/service/fret-service.ts`) stating the measured headroom and the condition that
  would make it real work — any growth in the emission caps, the metadata allowance, or the set of
  snapshot fields — along with why it matters at that site: an over-cap snapshot is refused at the
  receiver's length prefix, so it fails silently and one-directionally, the exact failure mode the
  single cap was introduced to end.
- **Two minor gaps the implementer disclosed were fixed** (committed in `d6ed9cb`): a
  `{@link MAX_NEIGHBORS_BYTES}` in `src/rpc/request.ts` that resolved to nothing because the symbol
  is not imported in that file (now plain backticked text with the value spelled out), and
  `metadataAtAllowance` in `test/rpc.codec-properties.spec.ts` asserting on `String.length` where
  the service measures encoded bytes (now `TextEncoder().encode(...).byteLength`, with a comment
  saying why the two must be the same quantity).

### Empty categories, stated with reasons

- **No major findings, so no new `fix/`, `plan/` or `backlog/` tickets were filed.** The change is
  small — it replaces two numbers with one — and the single behavioral question it raises
  (outgoing-side validation) resolved to a tripwire on the measurement above rather than to work.
- **No accepted-tradeoff `NOTE:` was found at any site the change touched**, so nothing here was
  previously declined by design and nothing needed re-checking against a revisit condition.
- **The implementer's repro caveat was not resolved, and deliberately so.** They noted that the
  pre-fix failure directly observed was the cap value itself, not the 11 KiB merge assertion behind
  it. That is still true. The measurements above establish the 11 KiB figure by encoding rather than
  by reproducing the original failure, which is the stronger evidence and makes re-observing it
  unnecessary.
