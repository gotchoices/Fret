## Why this is pre-existing

- **The senders already return `RpcOutcome` at HEAD, before any edit of mine.**
  `git show HEAD:packages/fret/src/rpc/ping.ts` declares
  `sendPing(...): Promise<RpcOutcome<{ ok: boolean; size_estimate?: number; confidence?: number }>>`.
  The same is true of `sendMaybeAct`, `fetchNeighbors` and `sendLeave`. That change landed in
  `75bf056 ticket(implement): 15.2b-rpc-sender-migration`.
- **The four failing specs were last touched before that migration.**
  `git log -1 --oneline -- packages/fret/test/rpc.stream-errors.spec.ts` →
  `4ac0480 ticket(implement): rpc-framing-tests-fuzz-docs-handoff`, two tickets earlier. So the
  migration changed the sender contract without updating the specs that assert it.
- **My ticket's diff cannot reach any of it.** `15.31` touched `src/rpc/validate.ts` (new),
  `src/rpc/maybe-act.ts` and `src/rpc/leave.ts` (moved two pure functions out), one import + one
  call site + two comments in `src/service/fret-service.ts`, `src/index.ts` (added exports), one
  comment in `src/rpc/protocols.ts`, and three spec files (`rpc.codec-properties`,
  `rpc.handler-fuzz`, `package-exports`). It changed no sender, no `rpcRequest`, and no outcome
  type, and none of the four failing files is in the diff. Every failing assertion is about the
  *shape a sender returns*, which `15.31` does not touch.

## What a fix looks like (not attempted here)

The specs are asserting today's *intended* contract in yesterday's *vocabulary* — several of them
carry `TODAY'S CONTRACT` comments naming the migration that would change them, e.g.
`rpc.stream-errors.spec.ts:364-368` predicts exactly this update. So this is a spec-update job:
branch on `res.kind` and read `res.value`, keeping each case's claim intact. Nothing was skipped,
commented out, or loosened.
