## Why this is pre-existing, not caused by the ticket in flight

- **The spec cannot reach the changed code.** The ticket
  (`1-bug-inbound-rpc-refused-on-relay-connections`) changed only the `node.handle` options built
  in `packages/fret/src/rpc/protocols.ts`. `message-bus.spec.ts` imports the deterministic
  simulation harness only (`simulation/*`, `helpers/ring.js`) — no libp2p node, no RPC handler
  registration, no stream. There is no path from the diff to this test.
- **It passes in isolation, but only barely.** Run alone it takes **238.5 s against its own
  300 s timeout** — 80% of the budget:

  ```
  node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/message-bus.spec.ts" --timeout 300000
    ✔ clustered placement: inter-cluster routing takes more hops (238554ms)
    20 passing (4m)
  ```

  So the failure is the margin closing under whole-suite load, not a behavioral break: the same
  case, same seeds, same assertions, pass when it gets the machine to itself.

## What this looks like to triage

This is a runtime-headroom problem in the case's rig, not a wrong answer — the five seeds it prints
all land well inside the assertion margin (clustered 4.8–7.1 hops vs uniform 2.0–3.1, margin 1.5).
The case builds a 300-peer ring with `capacity: 32` per store and pumps to a fixed time for each of
five seeds, which is where the four minutes go. Whoever picks this up should decide whether to buy
headroom (fewer seeds, smaller n, a longer timeout) or accept a four-minute case; the test itself
is discriminating and documented as such in `docs/fret.md` under *Testing strategy*, so it should
not be weakened without replacing what it measures.
