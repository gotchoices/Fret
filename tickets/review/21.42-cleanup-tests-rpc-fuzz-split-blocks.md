## What a reviewer should actually check

**Is it a pure move?** The bodies were extracted with `sed` line ranges and concatenated under a
new header — no reindentation, no edits inside any `it`. `git diff` on the source file should
show only deletions plus the import/header changes listed below. Worth spot-checking that the
`describe` nesting depth is identical (both new files wrap their content in one top-level
`describe` at the same one-tab depth the old nested blocks sat at, which is why no reindent was
needed).

**The `unhandledRejection` guard is copied, not shared — on purpose.** Each of the three files
registers its own `before`/`after`/`afterEach` guard scoped to its top-level `describe`. It
cannot be hoisted to a shared import and called at file top level: that would make it a mocha
*root* hook running against the entire suite. Each copy carries a comment saying so. If a
reviewer's instinct is "DRY this up", that instinct is wrong here and the comment explains why —
but check all three copies are actually equivalent (20 ms sleep, splice, deep-equal `[]`).

**Stranded imports were swept by grep, not by the compiler.** `packages/fret/tsconfig.json` has
`strict: true` but **no `noUnusedLocals`**, so `tsc` is silent on a leftover import — the source
ticket flagged this as conditional and the condition is false. Removed from
`rpc.handler-fuzz.spec.ts` after verifying zero remaining uses below the import block:
`createIdentifyNode`, `PeerId` (type), `waitFor`, `isFrameTruncationError`, `hashPeerId`,
`peerIdFromString`, and the now-unused module-scope `const dec = new TextDecoder()`. A reviewer
re-running that sweep is the cheapest real check available, since nothing automated covers it.

**Header comments are load-bearing here.** The source file's three-tier header now says two tiers
and points at both new files by name; each new file has a header saying what it owns and pointing
back. If a future split moves a block again, these three comments are what a reader hits first —
they must stay accurate.

**Imports each new file needed** (derived by grepping the extracted bodies for every symbol the
old import block named, then checking the ambiguous ones by eye — `framed` vs `sendFramed`, `dec`
vs `decodeFramed`, `registerRpcHandler` vs the service's `registerRpcHandlers`):

## Use cases the split is supposed to preserve

- A handle leak in the wire tier now fails `rpc.handler-fuzz.wire.spec.ts`'s own run rather than
  hiding inside a larger file — the exit watchdog judges that file alone. The two transport
  `describe`s still start real libp2p nodes per test; the split does not change how many run at
  once.
- `rpc.snapshot-merge-cap.spec.ts` drives `mergeAnnounceSnapshot` directly on unstarted services
  (announce path) and a stub reply stream (fetch path), so it needs no transport at all and is
  fast.
- The source file keeps every stub-stream and validator case, so it stays the fast file it was.
