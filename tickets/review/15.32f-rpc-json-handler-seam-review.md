## Finding (A) — diagnosis complete; only the ticket-writing is left

`15.32c` established the effect reproduces: changing exactly one thing in `registerPing`
(`serve: (connection) =>` → `serve: async (connection) =>`) turns *Leave amplification cap → the
classification pass probes and promotes a replacement recorded by a leave*
(`test/churn.leave.spec.ts:540`) from passing to failing on `pingsOk > 0`, in ~297 ms.

`15.32d` named the outcome variant and the mechanism with a standalone two-node scratch spec (two
`createMemNode`s, three `registerJsonHandler` reply-only protocols differing only in the `serve`
shape, driven by `rpcRequest`; the spec was deleted before handoff). **Result, deterministic,
6 calls per shape:**

| reply-only `serve` shape | `rpcRequest` outcome |
|---|---|
| `() => Promise.resolve(reply)` (today's `registerPing` / `registerNeighbors`) | `ok` |
| `async () => reply` | `ok` |
| `async () => { await Promise.resolve(); await Promise.resolve(); return reply }` | `decode-error` (`FrameTruncationError`) |

So the effect is **not** about `async` versus a bare arrow, and **not** the implementer's stated
`negotiateFully: false` theory. It is a threshold in how many microtasks elapse between the inbound
handler being invoked and its first `sendFramed` write: two extra ticks is enough, one is not. The
reply *is* written — the caller reads it as a **truncated frame**, i.e. the caller's `readFramed`
concludes the remote finished writing while the reply bytes are still in flight. That points at
`remoteFinishedWriting` and the `EOF_POLL_MS` poll in `packages/fret/src/rpc/protocols.ts`, not at
`openRpcStream` and not at the two handler bodies.

**New from `15.32e`, and load-bearing for how the ticket is written:** the reply-only arm of
`registerJsonHandler` is itself
`sendFramed(stream, await encodeJson(await opts.serve(connection)))` — **two awaits before the
first write already**, since `encodeJson` is async. So "today's shapes pass" is not a claim that
the seam writes promptly; it is a claim that the *current total* sits under the threshold, with the
seam consuming part of the margin. Any body-level await lands on top of an already-loaded budget.
Also relevant: `remoteFinishedWriting` (`src/rpc/protocols.ts:379`) reports finished on
`readBufferLength === 0 && (remoteWriteStatus === 'closed' || readStatus === 'closed')`, and
`readFramed`'s doc block claims that check is "race-free because the poll fires on a macrotask at
least one interval after any message dispatch" — the reproduction says that claim is false in at
least one ordering, so the ticket should quote it as the invariant being violated.

The churn-spec symptom follows exactly: `decode-error` is scored as proof of life
(`noteAnsweredOnProtocol` → `membership: 'member'`) but never reaches `applySuccess`, so `pingsOk`
stays 0 while the membership assertion still passes — precisely what `15.32c` observed. The
`registerPing` arrow change is a trigger, not the cause.

**This is a latent defect, not a tripwire.** Any handler body that awaits twice before writing
loses every reply, silently, on a healthy connection; nothing in the seam's contract forbids that,
and `pingReply` already awaits a caller-supplied `getSizeEstimate` provider (one hop today, and an
async provider is a legal implementation of `SizeEstimateProvider`).
