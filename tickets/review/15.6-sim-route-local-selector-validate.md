Confirmed correct against the ticket's design:

- Candidate pool is the deciding peer's own store only (`notDead`, minus self and `visited`);
  neither the global `alive` flag nor the partition map is read to build it.
- Hop choice goes through the shipped `chooseNextHop` cost path with a constant `linkQ`, no
  `backoffPenalty`, and `selfCoord` supplied from the second hop onward only — matching
  production's originator/forwarder split.

  shared `recordContactFailure` and the selector re-runs over the remaining candidates; only a
  delivered hop increments `hops`.

### Findings

**Fixed in the prior run (already in the working tree, uncommitted):** `contactSweep`'s doc
comment still claimed one strike per entry per tick, which the routing path's own strikes make
untrue — an entry can now take a sweep strike plus one per route in the same simulated tick, so
it escalates to `dead` faster than the sweep alone would. The comment is rewritten to say so and
to name the fix (production's >= 500 ms spacing check inside `recordContactFailure`) should a
suite ever fire many routes per tick at the same unreachable window. Harmless today because the
specs schedule routes sparsely.

**Remaining, both cosmetic — apply them in this pass:**

- In `handleRoute`'s outer loop, `hops < maxHops` is dead: every hop consumes an attempt, so
  `hops <= attempts` always holds and `attempts < maxHops` already bounds it. Drop the
  redundant term (or keep it and say in a comment why a reader should expect it to be
  unreachable) — a condition that can never fire reads as a second budget that is not one.
- `nearRadiusFor(store)` is recomputed inside the contact-retry loop although `store` is fixed
  for the whole hop; it allocates a BigInt division and a 32-byte coordinate per attempt. Hoist
  it above the retry loop.
