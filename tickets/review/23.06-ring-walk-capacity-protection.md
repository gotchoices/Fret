Implemented from `implement/23.06-ring-walk-capacity-protection`. First of three tickets split out
of the former `23.05-ring-walk-migrate-call-sites`; the other two (`23.07-ring-walk-leave-path`,
`23.08-ring-walk-remaining-sites`) are **not** implemented and their call sites still carry the
off-by-one described below. That is expected, not a gap in this ticket.

## What changed

`FretService.enforceCapacity` (`src/service/fret-service.ts`, ~line 499) previously called
`this.store.protectedIdsAround(self, max(2, m), isLiveMember)`. Both of that method's walks are
anchored exactly on self, and a ring walk anchored on a stored coordinate returns that entry as its
own first result on **both** sides — so self consumed one slot per side and only `m - 1` live
members were protected on each side. The m-th successor and m-th predecessor were therefore
evictable at capacity despite being genuine successor/predecessor-window members.

It now calls the shared helper `ringNeighborsBothSides(store, self, max(2, m), selfId,
{ filter: isLiveMember })`, whose `count` means *peers besides self* (it over-fetches
`count + 1 + |exclude|` per side and trims back), collects the result into a `Set`, and adds self's
own id explicitly.

- **Protected set is now `2 * max(2, m) + 1` ids** (self + m per side), was `2 * max(2, m) - 1`.
- A store at capacity has **two fewer eviction candidates** than before.
- `DigitreeStore.protectedIdsAround` is **deleted** (it had exactly one caller, and leaving it in
  place kept the over-fetch rule in two modules).
- The `NOTE:` block in `enforceCapacity` restating the arithmetic is updated (`2m - 1` → `2m + 1`,
  and the pathological condition `capacity < 2m - 1` → `capacity < 2m + 1`). Unreachable at the
  shipped numbers (m 8, capacity 2048).
- `docs/fret.md` *Relevance scoring and table management*: the victim-selection bullet and both
  sub-bullets rewritten for the new arithmetic. `docs/threat-analysis.md`: the two
  `protectedIdsAround` mentions repointed at `enforceCapacity`, so neither names a deleted method.

**Deviation from the implement ticket worth a reviewer's eye.** That ticket said to *delete* the
"off-by-one" bullet in `docs/fret.md`. It was **rewritten instead of deleted**, because the bullet
carried a second job the deletion would have lost: naming which self-anchored walks are still
unmigrated. It now states the `2m + 1` set as fact and points at `23.07-ring-walk-leave-path` and
`23.08-ring-walk-remaining-sites` for the sites that still have the old behavior (the stale
reference to the deleted `23.05` slug is gone). Judge whether that is the right call — deleting it
outright is still available if the reviewer prefers the doc to stay silent about unmigrated sites.

## Validation performed

- `yarn test` — **1157 passing, 0 failing.** No pre-existing failures surfaced;
  `tickets/.pre-existing-error.md` was not written.

`test/relevance.eviction.spec.ts` rewritten rather than re-baselined. It previously **pinned the
off-by-one as current behavior** (its headline case carried a comment explaining that the m-th
neighbor was deliberately unprotected). Now 12 cases, all passing:

- Fixtures moved from `capacity: 6` to `capacity: 8` where needed. With `m: 3` the protected set is
  7 ids, so a capacity of 6 makes protection exceed the cap and *every* case degenerates into the
  protection-beats-capacity outcome, asserting nothing about victim selection. 8 leaves three real
  evictions per fixture.
- **New:** `protects the m-th successor and m-th predecessor, the outermost member on each side` —
  the direct assertion the fix exists for. `succ-3` / `pred-3` are the two **lowest**-scoring
  entries in the table and survive while far peers scoring 1.0–3.0 are evicted, so protection is
  the only thing that could have saved them.
- **New:** `protects self when the ring walk returns nothing because no other peer is a live
  member` — the edge case the implement ticket called out (ring of one). Every other peer is
  `foreign`, so the filtered walk returns empty; self is the lowest-scoring entry (relevance 0) and
  survives only because it is added to the set explicitly rather than drawn from the walk.
- Updated: `drops a dead neighbor from protection…` now asserts the clockwise window reaches past
  the dead peer to **two** live members (`far-1`, `far-2`), not one.
- Updated: `does not protect an adjacent peer labelled foreign|unknown` now expects **three**
  clockwise far peers protected.
- Updated: `leaves the table over capacity when the protected set is larger than the cap` — with
  `m: 8` the floor is now **17** entries (self + 8 + 8) against a cap of 4, was 15.
- Unchanged and still passing: the pre-`start()` import case (no self entry, so the protected set
  is unchanged at 6 ids), the empty import, and the single-entry-at-capacity-1 case.

## Where a reviewer should push

- **Verify the arithmetic independently rather than trusting the fixture numbers.** Every expected
  member list above was derived by hand from `m`, the layout offsets, and the eviction order. A
  transposed expectation would still produce a green suite if the code has the matching off-by-one.
  The load-bearing claim is: protected = self + the `max(2, m)` nearest live members clockwise + the
  same counter-clockwise, window skipping past non-live-members rather than shrinking.
- **`Math.max(2, this.cfg.m)` is preserved verbatim from the old call.** The floor of 2 is not
  re-justified anywhere in this change; confirm it still means what it meant when protection was
  narrower, now that it buys two more slots per configuration.
- **`this.node.peerId.toString()` is called twice in `enforceCapacity`** (once as the helper's
  `selfId`, once for the explicit `add`). Cheap and obviously correct, but a local would read
  better; the surrounding file uses a `selfStr` local for exactly this in ~15 other methods.
- **Blast radius beyond eviction.** The claim is that `enforceCapacity` is the only caller affected,
  since `protectedIdsAround` had exactly one call site. Worth re-grepping the deleted symbol across
  `src/`, `test/`, `docs/` and `tickets/` to confirm nothing else referenced it — note
  `packages/fret/dist/` still contains a stale `protectedIdsAround` declaration from a prior build,
  which is build output and not part of the diff.
- **The three tickets are a chain and only the first has landed.** `docs/fret.md` now describes
  `enforceCapacity` as fixed while other self-anchored walks in the same service are still off by
  one. Confirm the doc reads coherently in that intermediate state — a reader should not conclude
  the whole class is fixed.
- No tripwires were recorded for this change; the pre-existing `NOTE:` blocks at `enforceCapacity`
  (protection-beats-cap, and the full-sort-to-drop-a-handful cost) were kept, with the first's
  arithmetic updated.
