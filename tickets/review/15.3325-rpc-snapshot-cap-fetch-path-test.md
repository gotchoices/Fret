## What landed

Two gaps closed, both inside the block previously titled `announce snapshot merge caps` and now
titled **`snapshot merge caps`** (it covers both inbound paths now). Both new tests run once per
profile, so four test cases in total.

**`applies the same caps on the fetch path, and never upserts the snapshot sender`**
The fetch path had no cap test at all — the claim that its removed slice was redundant rested on
reading the code. It now drives `fetchAndMergeSnapshot` (private, via a cast) against a stub reply
stream serving one framed over-cap snapshot, counts `store.upsert` calls with the block's existing
`countUpserts`, and deep-equals the counted ids against
`[...OVER_SUCC.slice(0, cap), ...OVER_PRED.slice(0, cap), ...OVER_SAMPLE.slice(0, cap).map(id)]`.

**`drops a `relevance: null` sample entry on both merge paths`**
The strictness was pinned at the parser only. One test now drives a three-entry sample
(`good-1`, `null-relevance`, `good-2`) through *both* merges and asserts the unusable entry is in
neither path's counted ids while both good ones are, and that it never reached the store.

Two helpers were added at block scope to support them: `replyStream` (≈12 lines, a one-frame stub
stream) and `fetchMerged` (installs the connection override + counter, drives the fetch, restores
`getConnections`).

## Why the assertions are shaped the way they are

Three of these are the difference between a test that proves something and one that passes
vacuously — check them first:

- **Deep-equal on the full id list, never `<= cap`.** A reply the parser refuses becomes
  `decode-error`, and `fetchAndMergeSnapshot` returns early having upserted nothing. A zero count
  looks exactly like a cap doing its job, so a `<=` assertion would pass on a fixture that was
  rejected for some unrelated reason.
- **No leading `FROM` in the fetch expectation.** Unlike the announce path's
  `1 + successors + predecessors + sample`, the fetch path never upserts `snap.from`. The test
  asserts `FROM`'s absence from the counted ids and from the store as its own expectation.
- **The `getConnections` override is load-bearing, not scaffolding.** `fetchNeighbors` dials
  `'never'`; with no connection the whole call is `skipped` and upserts nothing — again a zero
  count that reads as success. Delete the override and the fetch test should fail, not pass.

## Known gaps — reviewer, start here

Written honestly; these are the places this handoff is a floor rather than a finish line.

- **The cap assertions were not mutation-tested.** The deep-equal shape means a cap raised to
  `Infinity` must fail the assertion (40+40+20 ids merged instead of 16/16/8), and the reasoning is
  structural rather than observed — no run was made with the cap disabled to watch the test go red.
  Same for the `getConnections` override. Cheap to confirm: temporarily pass `Infinity` caps to the
  parser in `fetchAndMergeSnapshot` and re-run the spec.
- **`countUpserts` stacks wrappers rather than replacing them.** A second call wraps the first, so a
  counter installed earlier keeps recording while a later one is live. The
  `relevance: null` test works around this by copying the announce ids out (`[...counted]`) before
  driving the fetch. That is a real sharp edge for the next test added to this block, and it is
  documented at the call site only — worth a judgement call on whether `countUpserts` should return
  a restore handle instead.
- **`fetchMerged` restores `getConnections` but deliberately does not restore `store.upsert`,**
  matching every other test in the block (which install a counter and never restore). Consistent,
  but it is why the copy above is needed.
- **The fetch tests use a stub stream, not a real libp2p stream.** `readFramed` dispatches on
  `isMessageStream`, so these exercise the async-iterable implementation, not the byteStream one.
  That is the same shape `test/rpc.codec-properties.spec.ts`'s `replyStream` uses and is deliberate
  — the subject here is the cap, not the framing — but it means these tests say nothing about the
  real-stream read path.
- **`good-1` / `null-relevance` / `good-2` are not parseable peer ids.** They work because the
  sample arm of both merge loops decodes `coord` and never calls `peerIdFromString` on the id. That
  is pre-existing convention in this block (the wrong-width-coord tests do the same), but it means
  the sample tests would not catch an id-parse guard being added to those loops.
- **No test covers a fetch reply the parser *rejects* outright** (e.g. an unparseable `from`)
  reaching the `decode-error` arm and upserting nothing. The new test's comment names that arm as
  the reason for its assertion shape but does not exercise it.
