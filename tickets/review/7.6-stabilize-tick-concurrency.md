Phase 2 and 4 of the original `stabilize-tick-concurrency` design. Phase 1 (`runPooled`, `src/utils/pool.ts`)
landed as `pooled-task-runner` (`tickets/complete/7.5-pooled-task-runner.md`). Phase 3 (pooling the
active-mode warm-up paths) is `pool-warmup-paths`, a sibling `implement/` ticket with `prereq:` on this one —
not part of this review.

## What changed

**Before:** `stabilizeOnce` ran four passes serially — ping the ≤ 4 nearest live members, fetch a snapshot
from each, ping ≤ Core 8 / Edge 4 `unknown` peers, ping ≤ Core 2+2 / Edge 1+1 `foreign` and `dead` peers.
A tick's wall time was the *sum* of 14–20 round trips; one hung peer blocked every peer behind it, and a
tick under mass failure ran ~60 s Core / 50 s Edge against a 1.5 s passive interval.

**Now** (`fret-service.ts`, `stabilizeOnce` ~L1817 and the helpers below it):

- One tick-wide `deadline(STABILIZE_TICK_BUDGET_MS = 5000, runSignal)` — a child of the run signal, so
  `stop()` collapses an in-flight tick at once; expiry aborts in-flight RPCs and the pool `skip`s tasks not
  yet started.
- Two `runPooled` phases at `maintenanceConcurrency` (Core 6 / Edge 2 — the *Operating profiles* pre-dial
  numbers reused). **Phase 1** pools the near peers, chaining ping → snapshot-fetch *per peer*
  (`probeAndFetch`), because `fetchNeighbors` is connection-only and it is the ping that usually opens the
  connection. `enforceCapacity` runs once after phase 1 drains; first-seen ids are announced once — neither
  inside a pooled task. **Phase 2** pools the classification and re-probe targets, which are still
  *selected* under their own separate budgets/orderings (`classifyTargets`, `reprobeExcludedTargets` →
  `reprobeOffRingTargets`) — only execution is pooled.
- Every task is handed the tick signal explicitly (never defaulted from `runSignal`) and compares against
  it via `wasCancelled`, so a budget cut records no strike / backoff / relevance decay / `pingsFail`.
- Candidate lists rotate under truncation: unknowns by ascending `lastAccess`, re-probe arms by ascending
  backoff factor. Near list deliberately kept in ring order (closest first).
- Renames (old → new): `probeNeighborsLatency(ids)` → `probeNeighborLatency(id, signal)`,
  `mergeNeighborSnapshots(ids)` → `fetchAndMergeSnapshot(id, signal)`, `classifyUnknownPeers()` →
  `classifyTargets()` (select-only), `reprobeExcludedPeers()` → `reprobeExcludedTargets()` (select-only),
  `reprobeOffRing(pred, budget)` → `reprobeOffRingTargets(pred, budget)` (select-only), `probeMembership(id)`
  → `probeMembership(id, signal)`. Old per-peer `if (this.stopped) break;` guards subsumed by the pool's
  signal check.
- This run added `logRejected(results, ids, label)` (module-level, next to `fulfilledValues`): a pooled
  task that *rejects* is logged with its peer id. Every task catches its own RPC failures, so a rejection
  is a bookkeeping bug — but before pooling it surfaced as `stabilize tick failed:`; the pool must not turn
  that into silence.
- `docs/fret.md`: new "One tick's RPCs run pooled" bullet under *Stabilization and churn handling*;
  "Our own cancellation is not evidence" bullet rewritten (tick budget, `skipped`, `fetchAndMergeSnapshot`
  overcount note); stale names renamed throughout. Comment-only stale names fixed in
  `announce-rate-limit`, `churn.leave`, `membership-identify`, `ring-membership`, `seed-new-peers` specs and
  one JSDoc in `fret-service.ts`.

## Load-bearing invariants (assert, don't trust)

- The four candidate sets are pairwise disjoint by construction (near = live member; classify =
  `unknown` non-dead; foreign arm = `foreign` non-dead; dead arm = `dead`) — this is what makes pooling
  safe against the lost-increment race on `applySuccess` / `applyFailure`. Two near peers' snapshots *can*
  name the same third peer → concurrent `applyTouch`; documented as harmless (only `accessCount` can lose,
  and it only feeds a recomputed score) in the NOTE on `fetchAndMergeSnapshot`.
- `enforceCapacity` never runs inside a pooled task. `announced` is per task, concatenated, announced once.
- `stop()` sets `stopped` and aborts `runAbort` synchronously together, so the pool's signal check is
  equivalent to the deleted `stopped` guards.
- `budget.cancel()` in the tick's `finally` — mandatory (`deadline` leaks a timer otherwise; the exit
  watchdog would catch it).

## Known gaps / things a reviewer should poke at

- **No test drives the tick through the real loop with `runSignal` set** and a `stop()` mid-tick to
  confirm the tick collapses *and* the loop does not re-arm. `stop()` semantics are covered by the
  existing lifecycle specs (`7.3-rpc-service-signals-lifecycle-tests`), and the tick signal is a
  `deadline` child of the run signal, so this is inferred, not observed. Cheap to add via the `PeerRig`
  harness if the reviewer wants it: start the service, hang all peers, `stop()`.
- **High-water `=== cap` assertion** relies on `runPooled` spawning workers synchronously and each task
  reaching `newStream` synchronously (`sendPing` → `openRpcStream` → `getConnections` → `newStream`, no
  awaits before). It has held on 4 local runs; if a future refactor inserts an `await` on that path it
  will read low. The failure message says what to loosen.
- **`logRejected` has no test** — no task can currently reject (each catches its own RPC failure;
  `noteRpcFailure` guards its own bookkeeping), so there is no natural trigger. It is a hardening against
  future task bugs, not a behaviour change.
- **Snapshot-fetch overcount** (`snapshotsFetched` counts a fetch cancelled mid-flight because
  `fetchNeighbors` swallows the abort into an empty snapshot) is unchanged and documented as accepted on
  `fetchAndMergeSnapshot`; `dead-state.spec.ts` asserts the overcount so a fix there flips a test.
- **Active mode**: 5 s tick budget vs 300 ms active interval means active stabilization is effectively
  continuous under mass failure — was already true serially, noted on `STABILIZE_TICK_BUDGET_MS`. Not
  measured; tripwire only.
- **Timing slack in the headline test** (`budget + 1500`) is generous for CI; tightening it is a
  judgement call.
- Docs: *Operating profiles* pre-dial wording is untouched — that is `pool-warmup-paths`'s to revise.

## Tripwires parked (all `NOTE:` at site)

- `classifyTargets`: three full store walks per tick (O(table size)) — fine at C = 2048.
- `reprobeExcludedTargets`: arms share one `backoffMap`; needs separate maps if the two ever need
  independent cadence.
- `STABILIZE_TICK_BUDGET_MS`: tighten per mode only if active warm-up latency measurably suffers.
- `fetchAndMergeSnapshot`: two NOTEs — cancelled-fetch overcount; concurrent `applyTouch` on a shared
  third peer.
