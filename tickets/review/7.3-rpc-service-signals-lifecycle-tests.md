Service-level half of the test work for `rpc-service-signals` (Phase 4 of `7-rpc-abort-deadlines`).
The implementation under test was already landed (commits `4592351`, `6d93373`); this ticket added
only tests, plus one `NOTE:` tripwire in the service.

## What landed

**`packages/fret/test/service-lifecycle.spec.ts`** — three new tests appended to the existing
`FretService start/stop lifecycle` describe, plus imports (`PeerId`/`Stream` types,
`generateKeyPair`, `peerIdFromPrivateKey`, `waitFor`, `hashPeerId`) and a module-level read of the
service's `private static SHUTDOWN_BUDGET_MS` off the class (so the bound tracks the constant
rather than restating `3000`).

1. **`stays inside its shutdown budget when a dial hangs, and still notifies reachable neighbors`**
   Two in-memory nodes. The stopping node holds `svc`; the other runs its own started `FretService`
   on the same `networkName` and is dialed so it is `connected`. A third node is started, its
   multiaddrs merged into the stopping node's peerStore, then stopped — a **ghost**: libp2p holds
   an address for it, nothing answers. `svc.stabilizeOnce` is stubbed to a no-op so the tick's own
   probe passes do not race the assertions (`seedFromPeerStore` is deliberately left real — it is
   what puts both peers in the ring). `node.dialProtocol` is overridden to hang for the ghost id
   only, settling **solely** on signal abort (libp2p's `AbortOptions` contract; the pattern is
   `hangsUntilAbort` in `test/rpc.protocols.spec.ts`). Delivery is counted by wrapping the
   receiver's `handleLeave` — `registerLeave` bound a closure at `start()`, so a later override is
   picked up.
   Asserts: elapsed across `await svc.stop()` ≤ `SHUTDOWN_BUDGET_MS + 1500`; `ghostDials >= 1` (the
   hang was actually exercised — this is what keeps the elapsed bound from passing vacuously); and
   `leaves === 1` via `waitFor`, because `sendLeave` is write-only and does not await the remote
   handler. Measured elapsed: **~1534 ms** (the ghost costs one `LEAVE_NOTICE_TIMEOUT_MS`).

2. **`issues no dials and strikes nobody when stop() lands mid-tick`**
   Parks `seedFromPeerStore` — the only awaited seam ahead of every `runSignal` capture. `start()`
   awaits it once itself before arming the loop, so the stub parks on its **second** call (the
   tick's). The stub does no real seeding on purpose: the real one rebuilds `addressKnown`
   wholesale from the peerStore and would drop the synthetic target. A well-formed address-known
   `member` is seeded into the store first, and the test asserts it is in
   `getNeighbors(selfCoord, 'both', 8)` **before** unparking, so the passes have a genuine target.
   `stabilizeOnce` is wrapped (not replaced) to count completions.
   Asserts after unpark: `ticksCompleted === 1` (the tick resumed and ran to completion — kills the
   "never resumed" vacuity), **0 `dialProtocol` calls**, `pingsSent`/`pingsFail` unchanged,
   `contactFailures === 0`, `state !== 'dead'`, and `backoffMap.get(id) === undefined`.

3. **`mints a fresh run signal per start and leaves the stopped run aborted`**
   `runSignal` is `undefined` before the first `start()`, `.aborted === false` while running,
   `.aborted === true` after `stop()` (the aborted controller is deliberately kept), and
   `.aborted === false` again after a restart.

**`packages/fret/src/service/fret-service.ts`** — one added `NOTE:` block at the
`mergeNeighborSnapshots` call site in `stabilizeOnce` (~line 1764), recording the tripwire below.
No behavior change.

## Deviations from the ticket, and why

- **The ticket's `diag.snapshotsFetched` assertion was dropped** and replaced with a direct
  `dialProtocol` call counter. `fetchNeighbors` **catches** the abort and returns an empty snapshot
  rather than rethrowing, so `mergeNeighborSnapshots`'s `wasCancelled` break never fires and the
  counter still ticks for a fetch that opened no stream. Counting dials is the stronger and more
  literal form of "issues no dials" anyway. The reason the counter moves is written into the test
  as a `NOTE:` so a future reader does not "fix" it back.
- **The ghost is seeded through the peerStore, not via `(svc as any).setAddressKnown(...)`** as the
  ticket suggested. `seedFromPeerStore` rebuilds `addressKnown` wholesale every tick, so a directly
  poked entry is dropped before `stop()` runs. Merging real (now-dead) multiaddrs is both durable
  and closer to the real situation.

## Validation performed

- `cd packages/fret && npx tsc --noEmit` — clean.
- `cd packages/fret && yarn test` — **619 passing, 0 failing** (616 was the pre-`7.2` baseline;
  +3 from this ticket). No exit-watchdog complaint, so no timer leaked.
- **Mutation check (reverted).** Adding `this.runAbort = null` after the `abort()` in `stop()` —

## Known gaps — please treat as a floor, not a finish line

- **Test 1's shutdown bound is loose (4500 ms) and only one hanging peer is in play**, so what
  actually binds in the observed run is `LEAVE_NOTICE_TIMEOUT_MS` (1500 ms), not
  `SHUTDOWN_BUDGET_MS` (3000 ms). The whole-fan-out budget is therefore **not** directly pinned —
  it would take several ghosts to make it the binding constraint. Worth considering whether that is
  a second test.
- **No mutation check was run against test 1.** Tests 2 and 3 were verified against a real
  regression; test 1's non-vacuity rests on `ghostDials >= 1` plus the elapsed bound. The mutation
  that would prove it (dropping the signal from `openRpcStream`'s `NewStreamOptions`) makes the
  test hang to the mocha timeout rather than fail cleanly, and was skipped on budget.
- **Test 1 stubs `stabilizeOnce` to a no-op**, so the interaction between a live probe pass and the
  shutdown fan-out is not covered — only the fan-out in isolation.
- **Test 2 stubs `seedFromPeerStore` to do nothing**, which means self is never placed in the
  routing table for that run. Nothing asserted depends on self being present, but a reviewer adding
  assertions there should know the store is missing its self entry.
- **Test 1's elapsed assertion is wall-clock-sensitive.** It joins the small set of such assertions
  in the repo (see the NOTE at the top of the timeout block in `test/rpc.protocols.spec.ts`). If it
  ever flakes on a loaded box, raise the slack — do **not** swap it for a bare "stop() resolved",
  which is the assertion an unbounded dial would pass.
- **Nothing here covers the `stop()`-during-`announce` path** or the active-mode (300 ms) tick
  cadence; both were out of the ticket's scope.

## Review findings

- **Tripwire recorded, not filed as a ticket:** `fetchNeighbors` swallows an abort into an empty
  snapshot instead of rethrowing, so `mergeNeighborSnapshots`'s `wasCancelled` break is unreachable
  on the fetch path and a `stop()` mid-tick walks all four ids rather than stopping at the first.
  Harmless today — `openRpcStream` throws on an aborted signal before dialing, so no streams open,
  nothing merges, no strikes land, and the only effect is the `snapshotsFetched` overcount the
  neighbouring `NOTE:` already describes. Parked as a `NOTE:` at
  `packages/fret/src/service/fret-service.ts` (`stabilizeOnce`, the `mergeNeighborSnapshots` call
  site), stating the two conditions that would make it real: `fetchNeighbors` growing work ahead of
  the aborted-signal check, or the pass widening past its current 4 ids.
