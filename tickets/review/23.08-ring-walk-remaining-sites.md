## Behavior changes a reviewer should look at

These are the *point* of the ticket, not side effects — but each is a real change in what goes out
on the wire or what a predicate answers:

- **Announce now reaches both sides.** `announceTargetsAround`'s `fanout` slice runs over an
  interleaved list, so a Core fanout of 8 against `m = 8` is no longer successor-only. Departure
  announces (`announceOnDeparture`, anchored on the departed coordinate) get the same change.
- **Warm-up and near-neighbor windows each widened by one peer per side.** `count` means *peers
  besides self*, so where the old walks spent one slot per side on self they now return the m-th
  successor and m-th predecessor too. For `isNearNeighbor` that means the `wasNear` test at the
  `peer:disconnect` handler fires for two more peers than before.
- **The active warm-up tick's per-second budget now slices an interleaved list**, so its Core 6 /
  Edge 3 targets come from both sides rather than from the successor side first.

## Testing / validation

- `test/preconnect-concurrency.spec.ts` — the active-tick budget test used to rebuild
  `warmupTargetIds`' walk by hand (side-major, no self filter) to derive its expected target list.
  It now calls `ringNeighborsBothSides` directly, so it cannot drift from the pass again. Its own
  subject — pool concurrency and the dialable-first budget rule — is untouched and still passes.
- `test/size-estimator.spec.ts` — new parity case: *"the S/P window is 2m gaps at the default m"*.
  `windowGaps` is private and `G` is not exposed, so it is pinned through the confidence formula,
  which is closed-form in `G` on an evenly spaced ring (cv = 0 → dispersion = 1 − 1/√G). At
  G = 2m = 16 confidence is exactly 0.875; losing an anchor slot per side (G = 14) gives 0.8664 and
  double-compensating (G = 18) gives 0.8821, so the assertion discriminates in both directions.
  Worth re-checking that reasoning — it is the whole strength of the test.
- Suites most worth re-reading given the widened windows: `dead-state`, `failure-recovery`,
  `relevance.eviction`, `ring-membership`, `stabilize-concurrency`. All pass unchanged.

## Known gaps — flagged rather than papered over

- **`SizeEstimateOptions` grew a public field.** The helper drops the anchor entry by *id*, and
  `windowGaps` had no id to give it, so `selfId?: string` was added to `SizeEstimateOptions` and
  threaded from all four `FretService` call sites. That type is exported from the package root
  (`src/index.ts:142`), so this is a (backward-compatible, optional) public surface change the
  ticket did not anticipate. It defaults to `''`, which drops nothing by id — harmless on the
  whole-store fallback, which never walks the window, and every in-service `selfCoord` caller now
  passes it. Reviewer question worth asking: is threading the id the right shape, or should the
  estimator resolve the anchor entry from the store instead?
- **`size-estimator.ts` now imports from `src/service/`.** `ring-walk.ts` is a leaf (it imports only
  store types), so there is no cycle and `tsc` is clean, but the direction is estimate → service,
  which is inverted relative to the rest of the layout. Moving `ring-walk.ts` somewhere neutral is a
  reasonable review outcome; it was left where the other two tickets put it.
- **No new test asserts that announce reaches both sides.** That is the headline behavior change and
  it is currently covered only indirectly (by the helper's own `test/ring-walk.spec.ts` interleave
  assertions plus the unchanged announce suites). A test driving `announceTargetsAround` at
  `fanout = m` and asserting predecessors appear would be the direct pin.
- **`isNearNeighbor`'s widened window is unpinned.** No test asserts the m-th neighbor is now near.
- The `getNeighbors` `NOTE:` states that `both` at `wants = m` is successor-biased by the `wants`
  contract. That claim was read off the code, not driven by a test.

## Docs

`docs/fret.md` updated in three places: the *Network size estimation* paragraph now describes the
helper's rule instead of the local `m + 1`; a new bullet under *Dialability* describes the announce
target list as a two-sided window that is sliced; and the *Relevance scoring and table management*
caveat listing which sites remained unmigrated is deleted, replaced by a sentence naming
`getNeighbors` as the one deliberate exception.

### Verified correct so far

- The `G = 2m` claim holds arithmetically in both directions. With `selfId` supplied, each side
  is asked for `m + 1`: if self sits in the store the walk returns `[self, s1..sm]` and the drop
  reclaims the extra slot; if self is absent it returns `[s1..s(m+1)]` and the trim removes the
  surplus. Either way the window is self + m successors + m predecessors → 2m gaps. The
  over-fetch is exact, not merely generous.
- `exclude` is passed *into* the helper at all three sites that use it, never filtered off the
  result, and the helper's `+ exclude.size` over-fetch covers it.

### Candidate findings, none yet dispositioned

- **(likely major, architecture-ladder)** `SizeEstimateOptions.selfCoord` and `selfId` are two
  independent optional fields but are only meaningful as a pair. `collectGaps` passes
  `selfId ?? ''`, and an empty id matches no peer — so `selfCoord` *without* `selfId` silently
  takes the window path with the anchor entry left in place, spending one slot per side on self
  and yielding G = 2m − 2 (14 at the default m) instead of 2m. That is a quiet numeric
  degradation, not an error, and `SizeEstimateOptions` is exported from the package root, so an
  external caller can reach it. Ladder rung 1 applies: pairing them into one optional
  (`self?: { coord: Uint8Array; id: string }`) makes the half-specified anchor unrepresentable
  and retires the `?? ''` fallback. Confirm the four in-service call sites and the simulator
  before changing the shape.
- **(likely minor)** `announceNeighborsBounded` builds `exclude = new Set([selfId])` while the
  helper drops self unconditionally, so self is excluded twice and the over-fetch reach is
  inflated by one slot. Same double-count on the departure path, where the set is
  `{self, departedId}`. Harmless, but the redundancy invites a reader to think the helper does
  not drop self.
- **(likely minor)** Layering, already flagged in the handoff: `estimate/size-estimator.ts`
  imports `service/ring-walk.ts`. `src/ring/` already exists (`distance.ts`, `hash.ts`) and
  `ring-walk.ts` imports only store types, so `src/ring/ring-walk.ts` looks like the neutral home.
  Check every importer before moving.
- **(minor, DRY)** `this.node.peerId.toString()` is recomputed inside the `estimateSizeAndConfidence`
  options bag at ~line 2734 even though the enclosing method already binds `const selfId` a few
  lines above. Same recompute pattern at the other three estimator call sites.
