Reported as gotchoices/Fret#2 (p2p-fret 1.0.2, via sereus on phones): libp2p's `pbToPeer` and multiaddr parsing showed in an idle CPU profile because every stabilization pass ran `seedFromPeerStore()` (`peerStore.all()` decodes every record) and `seedFromBootstraps()` (re-parses up to 8 multiaddrs, re-hashes each id).

## What changed

**Pass body.** The loop closure now calls `runStabilizationPass()`: the address backstop if `Date.now() - lastPeerStoreWalkAt >= PEERSTORE_BACKSTOP_INTERVAL_MS` (300 000 ms, a `private static readonly` like the other tick constants, so specs can mutate it), then `stabilizeOnce()`. First-pass `ready()` resolution stays in the closure.

**`start()` order.** `attachPeerStoreListeners()` (the `peer:update` / `peer:identify` listeners, extracted from `start()`) → `seedFromPeerStore()` (the start walk) → `seedFromBootstraps()` → `enforceCapacity()` → `registerRpcHandlers()` → loop → `peer:connect` / `peer:disconnect` listeners as before.

**One creation helper.** `notePeerStorePeer(pid, protocols)`: on a store miss, hash and `noteDiscovered` (hearsay baseline `initialRelevance`, not the old bare `upsert` at relevance 0); a held entry is left completely alone (no `lastAccess` refresh); then `classifyByProtocols`. Used by both listeners and the start walk. Classification is folded in deliberately: for a held entry no `await` is taken before classifying, which `membership-identify.spec.ts`'s synchronous stale-update assertion depends on — a separate `await helper(); classify()` would defer classification a microtask and make that assertion pass vacuously.

**Start walk** (`seedFromPeerStore`, name kept for the dozen specs that call it): `readPeerStore()` (reconciles `addressKnown` synchronously after `all()` resolves) → per peer `notePeerStorePeer` + `adoptPeerRecord` when the entry holds no record → `seedSelf()`.

**Backstop** (`reconcileAddressesFromPeerStore`): `readPeerStore()` only — no creation, classification or record adoption.

**Event wins** (`readPeerStore`): each walk registers its own "touched" set in `addressWritesDuringWalks` before awaiting `all()`; `setAddressKnown` adds the id to every open set; after `all()` the rebuilt set takes each touched id's *current* membership, then swaps; the set is removed in a `finally`. Per-walk sets (not one field) so overlapping walks are exact; the `finally` means `stop()` needs no cleanup. `refreshAddressKnown`'s NotFound arm now routes through `setAddressKnown(id, false)`. `lastPeerStoreWalkAt` is stamped when a walk *begins* (so a failing `all()` is retried at the next interval, not every pass).

**Bootstraps** parsed once in the constructor (`parseBootstrapPeers(cfg.bootstraps.slice(0, 8))`, logging an unparseable entry once); `seedFromBootstraps()` hashes only on a store miss and calls `noteDiscovered`. Called once from `start()`, never from the pass.

**Docs** (`docs/fret.md`): *Dialability* address-set bullet rewritten (event-maintained, start walk + 5-min backstop, the three silent libp2p changes named, event-wins, the Fret#2 history); *Relevance scoring* creation sites + an **Eviction sticks** bullet; *Two phases* enforcement ownership per insert source; *Recovery*, *Leave*, *Mirroring*, *Evidence strength* (peerStore-protocols bullet), *Ring membership* durability sentence, *Replace by id* (imported label kept until next `peer:update` / probe), *A snapshot never speaks for self*. `docs/threat-analysis.md` §4.5 and the eclipse mitigations line updated too (not in the ticket's list; they described the per-tick walk).

## Things for the reviewer to look at

- **Behaviour change: hearsay baseline for peerStore-learned peers.** They used to be created at relevance 0 by bare `upsert` and re-`upsert`ed (lastAccess refreshed) every tick. Now `initialRelevance` once, and never touched again by the peerStore paths. The full suite passed with no eviction-test changes, but nothing new pins "peerStore peers get the baseline" (no test added per the ticket).
- **Listeners attach before the start walk.** They now run while `start()` is still awaiting, before `registerRpcHandlers`. They check `this.stopped` (already false by then) and do no RPC. The membership-identify poll-path test is now slightly weaker evidence: an event slipping into `start()` would also classify C `member`, so a green run no longer *proves* the poll alone did it. The ticket accepted this.
- **`classifyByProtocols` NOTE rewritten**: the stale-positive reset is now confined to `start()` and real changes; the backstop deliberately does not classify. `failure-recovery.spec.ts`'s service-only-outage test still re-walks per hand-driven tick, so it still exercises the reset path on identify nodes (unchanged, as the ticket asked). No memory-node demotion test added (per ticket).
- **By inspection only** (no deterministic test without mocking the peerStore): event-vs-walk race, `stop()` mid-walk, departed peers staying `dead` under a later `peer:update`, `importTable` after `start()` keeping the file's label, the discovery feedback loop being bounded at 4/s and creating nothing.
- **Listener-insert overshoot** between passes is unbounded in principle (one insert per first-time peerStore record per pass interval) and trimmed by the next pass's `enforceCapacity`. Documented under *Two phases* with the existing accepted-cost NOTE in `stabilizeOnce` widened to say so.
