## Phase 1 — new spec `packages/fret/test/simulation.routing.spec.ts`

Collector extension first (minimal): add `successfulRouteHops: number[]` to `SimMetrics`
(:6–25), init it in the collector's metrics literal (:79–98), push `hops` in `recordRoute` only
when `success`, spread-copy in `finalize` exactly like `coverageTimeSeries` (:171). Nothing else
in the collector changes.

- **Converged case**: seeded N≈200 uniform ring, m=8, k=15, no churn, run to convergence; then
  ~100 routes from random live sources to random target coordinates (32-byte coordinates drawn
  from a seeded `DeterministicRNG.nextBigInt(256)`). Assert routing success ≥ a threshold and
  p90 hop count ≤ an O(log N) bound.
- **Churn case**: same shape at moderate churn, lower success threshold.
- **Set both thresholds from measured values, minus a stated margin — measured numbers in a
  comment beside them.** A threshold picked before running proves nothing.
- **p90 over successful routes only** — `percentileSummary(metrics.successfulRouteHops)`;
  failure partials in `routingHops` would skew the bound.
- **Cover the originator-nearest case explicitly** — a route whose source is itself the peer
  nearest the target must succeed. This pins the "floor applies from hop 2 only" rule the
  prereq implemented.
- **Keep `capacity` unset.** With capacity set, eviction can fail routes that previously
  succeeded (expected, not a regression); the threshold must measure routing, not eviction.

### Phase 2 did not go as the ticket predicted, and that is the main finding

The ticket's suggested break — swap `minDistance` for `clockwiseDistance` — **does not move
either number**. Neither does substituting XOR. Measured, 100 routes per case:

| selector distance function          | success  | p90 hops  | max hops |
|-------------------------------------|----------|-----------|----------|
| `minDistance` (shipped)             | 95–100%  | 2         | 3        |
| preference inverted (farthest wins) | 99%      | 17–20     | 22       |
| `clockwiseDistance` substituted     | 100%     | 2         | 3        |
| XOR distance substituted            | 94–98%   | 2–3       | 3        |

Two things follow, both now written into the spec header:

1. **The hop-count bound carries the guard; the success rate does not.** The attempt budget
   absorbs a bad route until it stumbles onto the target, so success stayed at 99% even with
   the preference inverted. A guard built on success rate alone would have been vacuous.
2. **This harness cannot discriminate one plausible ring metric from another, and no threshold
   choice fixes that.** Its stores are unbounded and its gossip merges every neighbor's window
   each tick, so a peer knows a large near-uniform slice of the ring — 63% at n=200, 19% at
   n=1000, measured and logged by each case. Greedy routing over knowledge that dense arrives
   in one or two hops under any roughly-monotone metric, so there is no gap between plausible
   metrics left to measure. `clockwiseDistance` is in any case a *valid* ring metric (it is
   Chord's own), which is why it was never going to bite.

   The prerequisite for measuring metric quality is sparse, finger-shaped stores, which needs
   the sim's eviction to stop being degenerate — see the NOTE at
   `FretSimulation.enforceCapacity`: every entry ties at relevance 0, so eviction collapses to
   ring order and would evict a contiguous arc from every store. That is also why `capacity`
   stays unset here rather than being used as a sparsity knob.

So the retuning the old NOTE deferred ("retune once such a harness exists") is **still
deferred**, and the NOTE now says why in measured terms rather than for want of a harness.

### Follow-up worth filing

Sim eviction is degenerate (all relevance 0). Fixing it would give sparse stores, which is the
gate on: metric-quality guarding here, tuning `CONNECTED_SLACK_ORDERS`, and any hop-count
measurement that is more than a ceiling.
