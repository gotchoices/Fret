## What changed, and why it is supposed to be invisible

Three costs the stabilization loop paid on **every** tick were removed. Each is meant to be
behaviour-preserving; the tests exist to say so out loud.

**(a) Coordinate reuse in `seedFromPeerStore`** (`fret-service.ts` ~1867). The pass used to
re-derive `SHA-256(peer id)` for every peerStore entry, every tick. It now reads the ring
coordinate already in the routing table and hashes only on a miss. Sound because a ring coordinate
is a pure function of the peer id and nothing rotates it.

*This one has a real, deliberate behaviour change hiding inside it,* and it is the thing most worth
a reviewer's attention. The unconditional re-hash silently **repaired** a wrong coordinate for any
peer libp2p's peerStore also knew about. That accidental repair is gone. The only way a wrong
coordinate can enter the table is `importTable`, which trusts the persisted snapshot's `coord`
field — so the import-side check is now the *only* defense. That is recorded as an arm on
`tickets/backlog/plan/2-routing-table-export-integrity`, and cross-referenced both at the code site
and in the test's comment, so a future reader meets a decision rather than files a bug. If the
reviewer disagrees with that trade, this is the place to say so.

**(b) The `sender` / `senderCoord` rename** (`mergeAnnounceSnapshot`, ~1795). Five sites re-hashed
this node's own id instead of reading the cached `selfCoord()`. Four are mechanical. The fifth is
not: `mergeAnnounceSnapshot`'s locals were *named* `self` / `selfCoord` while holding the
**announcing peer's** id and coordinate. They were renamed so the next reader cannot "optimize" it
into the cached self coordinate — which would upsert every announcing peer at our own ring
position, collapsing the ring onto one coordinate.

**(c) Capacity enforced once per tick** (`stabilizeOnce` ~2039). The seeds no longer trim for
themselves; the tick owns one `enforceCapacity()` at the end of phase 1, plus one explicit call in
`start()` so the bound never depends on a timer being armed. Two orderings are load-bearing and
both are commented at the site: the call sits **after** the seeds and merges (so it sees every
insert the tick made) and **above** the `budget.signal.aborted` early return (so a truncated tick
still trims). The accepted cost — the table may sit over capacity for the span of phase 1, bounded
by the 5 s tick budget — is recorded as a `NOTE:` at the call site.

## What the tests do NOT pin — read this before trusting them

- **No hash-call counting.** The coordinate tests assert the *property* ("a stored coordinate
  survives a cycle"), not the cost. A regression that re-hashes redundantly on every tick but
  writes back the same coordinate would pass all six. The performance claim behind this whole
  ticket is therefore **unpinned by any test**; only the correctness of the result is pinned. If
  the reviewer wants the cost pinned, that is a new test (spy on `hashPeerId`), not a tweak.
- **The truncated-tick test's second assertion is unverified in the vacuous direction.** It asserts
  "no unknown peer was probed" as evidence phase 2 was cut off. Mutation 3 proves the *tick* is
  genuinely truncated, but I did **not** run the complementary experiment — raising the budget and
  confirming those unknowns *would* have been probed. So the assertion is known-meaningful as a
  truncation signal but not proven non-vacuous as a phase-2 signal. That experiment was dropped to
  a budget warning; it is cheap (raise `setTickBudget`, expect `probed` non-empty) and is the first
  thing I would do with more room.
- **The two "trims" tests do not discriminate old from new.** `one maintenance cycle trims` and
  `start() trims` would both have passed against the pre-change code, which enforced after every
  seed. They are behaviour-preservation tests by design — they pin that the bound still holds — not
  evidence the refactor happened. Only mutations 3/4/5 show them biting.
- **Only the `core` profile is exercised.** No test drives these paths as `edge`.
- **`STABILIZE_TICK_BUDGET_MS` is a static, overridden in a `beforeEach` and restored in an
  `afterEach`.** A leaked override would poison later specs. It did not leak in this run (full
  suite green), but if a future run shows unrelated *timing* failures in specs ordered after
  `per-tick-hotpath.spec.ts`, suspect that restore first.

## Test-side change worth a look

`buildMaintenanceRig` gained an optional second argument, `cfg?: Partial<FretConfig>`, spread into
the `FretService` constructor. Needed because a tick's capacity enforcement is only observable
below the 2048 default. No existing caller passes it, so existing rig users are unaffected — but it
is a shared helper, so the widening is worth a glance.
