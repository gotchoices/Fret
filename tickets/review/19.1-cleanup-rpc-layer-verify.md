## What the implement stage changed

Four items, 6 files, +32/-21; the diff matched the ticket's `files:` list exactly.

1. `encodeJson` / `decodeJson` (`src/rpc/protocols.ts`) dropped `async`; every production call
   site dropped its `await`.
2. `PROTOCOL_*` constants derive from `makeProtocols('default')` instead of restating literals.
3. `registerLeave`'s success reply and `registerNeighbors`' announce-handler success reply
   changed from `return { ok: true }` to `return undefined`.
4. `decodeJson` counts NUL bytes stripped by its interop-defensive trim and emits one
   `log.error` when the count is non-zero.

## Findings already established (do not re-derive)

### Items 1 and 2 — reviewed, clean

Read line by line against the diff. `npx tsc --noEmit` was clean at the implement stage.
Test-only `await`s left on the now-synchronous functions are legal and harmless.

### Item 3 — was a regression; **reverted in this pass**

`cd packages/fret && yarn test` at commit `547d506` gave **1040 passing, 76 failing**, all in
`test/rpc.handler-fuzz.spec.ts` and `test/rpc.codec-properties.spec.ts`, all on the leave /
announce reply path. Two failure shapes: `expected a reply frame, got eof`, and ~60 cases of
`Could not append value, must be an Uint8Array or a Uint8ArrayList` from `it-length-prefixed`'s
decoder being fed the absent reply.

Item 3 has been **reverted**: both handlers return `{ ok: true }` again, each with a
`NOTE:` recording the accepted tradeoff and its revisit condition. Reasoning, for the record:

- It is a **wire-format change, not a tidy-up**. The ticket was scoped as low-risk cleanup.
- It **collapses the seam's `undefined`**, which until now meant *only* "identity mismatch,
  drop", into meaning both "drop" and "success" — a real loss of distinguishability inside the
  handler.
- The acknowledgement is **observable by a non-FRET consumer**: the protocols and the
  `registerRpcHandler` / `registerJsonHandler` seam are exported from the package root.
- `docs/fret.md` *Leave* parks a planned change where `sendLeave` **does** read a reply so a
  rate-limited leave can answer `busy`; removing the reply path makes that work harder.

The argument for keeping the removal (neither `sendLeave` nor `announceNeighbors` reads a reply,
so the bytes are provably unread by any FRET sender) is real but does not outweigh the above.
It is recorded at both code sites as the revisit condition, so it need not be re-litigated.

**Consequence for the rest of this review:** `docs/fret.md`'s *Leave* passages describing
`registerLeave` as committing to `{ok: true}` are **correct again** and need no edit. Only
item 4's docs passage is stale (below).

### Item 4 — noted, not yet dispositioned

`decodeJson` runs **before** the maybeAct token bucket (`registerMaybeAct` decodes in its own
handler body, then `handle()` takes the bucket). So a peer can drive one `log.error` per
NUL-padded message with no rate limit in front of it. Whether that matters depends on whether
`@libp2p/logger`'s `.error` writes unconditionally or only under an enabled `DEBUG` namespace —
**not checked**. Note `src/rpc/leave.ts` already carries a `NOTE:` asserting the debug-gated
reading for its own mismatch log; confirm that claim rather than inheriting it.

- If `.error` writes unconditionally → log-amplification finding, file a ticket.
- If namespace-gated → park as a `NOTE:` tripwire at `decodeJson` and record it in findings.
