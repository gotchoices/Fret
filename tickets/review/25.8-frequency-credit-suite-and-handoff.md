## What the change is (for a reader with no context)

`accessCount` — the "how often have we dealt with this peer" counter that feeds the frequency
term of a routing-table entry's relevance score — used to be incremented both when we actually
talked to a peer and when some *other* peer merely mentioned it to us. So a peer we had only ever
been told about, repeatedly, could outrank one we had genuinely contacted, and be kept while the
real one was evicted. The change makes the counter count proven contact only, and routes every
"someone named this peer" path through one seam.

### Test half (`git diff d3d26fba^..47c1e8c -- packages/fret/test`) — sound; one DRY nit

- **The two deliberately-opposite sparsity-model choices are both correct, and each is justified
  at its site.** `relevance.eviction.spec.ts` shares one model across the two arms because
  `enforceCapacity` ranks scores *as stored* and every stored score in a running service was
  written under one service-wide model — sharing is the property under test. The order there
  (gossip scored first) is conservative: the 500 successes each observe the distance and so score
  under a progressively *lower* sparsity bonus than the gossiped entry got from the pristine
  model, and frequency credit wins anyway. `relevance.properties.spec.ts` isolates a fresh model
  per call because it compares two *base* scores and a shared model would let the KDE difference
  (`recordSuccess` observes the distance; `initialRelevance` does not) decide the outcome instead
  of frequency credit. Neither choice is a copy-paste slip.
- **The eviction fixture derives its two relevances rather than hard-coding them**, so it would
  fail if `recordSuccess` / `initialRelevance` were gutted — and its final `have.members`
  assertion pins that the survivor won on relevance, not on ring position (`contacted` sits
  *nearer* self than `gossiped`, so a ring-ordered loop would have made the opposite choice).
- **`rpc.snapshot-merge-flatness.spec.ts` being core-profile-only is acceptable.** Every fixture id
  list there is one entry long, so the profile-split merge caps bound nothing that varies; the
  profile loop next door exists for the cap file, whose subject *is* the bound. The file's second
  test ("still credits the announcing peer") is what stops the first from passing vacuously — it
  proves the merge is not a no-op.
- **The handoff's stated gap is smaller than it claimed.** `churn.leave.spec.ts`'s "records a
  dialable replacement as an unclassified entry, scored once and only once" now drives the leave
  replacement path through `noteDiscovered` *and* re-leaves the same id twice, asserting
  `relevance`, `accessCount` and `lastAccess` are all unmoved. That is exactly the leave-path
  coverage the handoff asked for; no additional test is needed.
- **`rpc.snapshot-merge-cap.spec.ts`'s fresh `GOOD_3`/`GOOD_4` pair for the fetch phase is a real
  fix, not churn**: re-merging the announce body would have upserted nothing (`noteDiscovered`
  writes only for an unheld id) and the assertion would silently have been measuring that rule
