## What this change is

Fourth and final carve-off of `25.5-frequency-credit-service-gossip`. Summary: `accessCount`
("frequency credit") now counts only proven contact (a completed RPC or direct interaction), not
hearsay (being named in a gossiped snapshot, a leave notice's replacement list, or the bootstrap
list). All such hearsay paths now go through one seam, `FretService.noteDiscovered`, which creates
a missing entry and scores it once from `initialRelevance` and leaves an already-held id
completely untouched — so mention count is not a lever that inflates a peer's eviction-time score.
See `docs/fret.md` → *Relevance scoring and table management* for the full rationale, already
updated.

### Code changed
- `noteDiscovered` on `FretService` — the hearsay-scoring seam.
- Five call sites moved onto it (two announce-merge loops, two fetch-merge loops, the leave-notice
  replacement handler).
- `applySuccess`'s `accessCount` patch (real contact increments it; hearsay does not).
- Two existing specs repaired for the new behavior: `test/churn.leave.spec.ts`,
  `test/rpc.snapshot-merge-cap.spec.ts`.

### Tests added (all three verified passing in this run's full-suite pass, not just standalone)
- **`test/relevance.properties.spec.ts`**, `describe('gossip vs proven contact')` (~line 467) — 2
  cases. Asserts 500 `recordSuccess` calls score strictly above an entry the gossip rule created
  and never re-scored, and that even a single success does too. Each case uses a fresh

- **`test/rpc.snapshot-merge-flatness.spec.ts`** — 2 cases, service-level (not unit-level). Merges

  named peer is hearsay). Core-profile only — every fixture list is one id long, so the

  reviewer's judgment call.
- **`test/relevance.eviction.spec.ts`**, new case `evicts a peer we were only ever told about
  before one we actually contacted` — `m: 3, capacity: 8`, one shared `createSparsityModel()`
  (deliberately opposite the properties spec's isolated-model choice — see rationale below),
  gossiped arm scored once via `initialRelevance`, contacted arm scored via 500 `recordSuccess`
  calls, measured 1.0800 vs 1.1681. Both peers placed outside the protection set, with the
  contacted peer nearer self in ring order than the gossiped one — so a ring-ordered (rather than
  relevance-ordered) eviction would take the wrong peer and fail the test.

## Points a reviewer should actually look at (not re-derivable from the diff alone)

- **`noteDiscovered` returning `boolean` was taken as the optional improvement from the source
  ticket.** The four merge loops (`src/service/fret-service.ts` announce id lists ~1974, announce
  sample ~1996, fetch ~2564, fetch ~2573) push to their `discovered`/`announced` array on that
  return value instead of a pre-`upsert` `getById`. Equivalent because self is always already
  seeded in the store, so the self early-return can't swallow a genuinely-new id — worth
  double-checking this reasoning holds.
- **An imported pre-change snapshot restores inflated frequency.** No schema change
  (`accessCount` already existed in `SerializedPeerEntry`), but the field's *meaning* shifted from
  "contacts + mentions" to "contacts only". Accepted as self-correcting (relevance is rewritten on
  next scoring call) and deliberately not migrated — reviewer should confirm this is an acceptable
  transition rather than silently wrong for a while after upgrade.
- **The already-held arm no longer refreshes `coord`.** The five switched sites passed a
  freshly-derived coordinate (`hashPeerId(peerIdFromString(pid))`), and a ring coordinate is
  *defined* as that hash — so the old refresh was writing back identical bytes. Real behavior
  difference (a no-op removed), not suspected to matter.
- **Not refreshing `lastAccess` on the already-held arm is intended, not a side effect.** It's the
  ordering key for the unknown-classification probe rotation (ascending `lastAccess`); the old
  refresh sank a heavily-gossiped unknown peer to the back of its own probe queue.
- **The cross-arm properties test asserts ordering only.** Its comment pins the *flatness* claim
  (repeated mentions don't inflate) on the service-level flatness spec instead. If
  `test/rpc.snapshot-merge-flatness.spec.ts` is ever removed, that comment needs correcting.
- **The eviction test shares one sparsity model; the cross-arm properties test isolates per-call
  models — deliberately opposite choices, each commented at its site.** `enforceCapacity` compares
  scores *as stored* under one service-wide model, so the eviction test needs to match that; the
  properties test is comparing base scores in isolation, where a shared model would let KDE
  occupancy state (not the gossip-vs-contact rule) decide the outcome. A reviewer who disagrees
  with either choice should say which and why.
- **The eviction test's derived margin (1.0800 vs 1.1681, ~8%) is narrower than the design
  ticket's originally measured 1.0449 vs 0.8619 (~21%)**, because the gossiped arm is scored first
  against the pristine model while every success is scored under rising KDE occupancy at the same
  x. This is the conservative order (harder to pass, not easier) and is commented at the site, but
  the margin is real and worth knowing if the test ever looks flaky under future tuning.
