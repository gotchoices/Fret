First of three tickets split out of `15.3-rpc-json-handler-seam`. This one built the **validator
module only** — pure functions, no handler seam, no sender wiring. Its two siblings are the
plumbing that makes the new parsers load-bearing:

- `15.32-rpc-json-handler-seam` — `registerJsonHandler`, migrating the inbound handlers onto it.
- `15.33-rpc-reply-parsers-and-caps` — wiring the reply parsers onto the senders' `decode`
  callbacks, building `makeSnapshotParser` from `mergeSnapshotCaps()`, removing the now-dead
  merge-loop slices.

**Consequence for review: four of the seven parsers currently have no production caller.** They are
exported, tested, and documented, but `makeSnapshotParser`, `parseLeaveNotice`, `parsePingResponse`,
`parseNearAnchor` and `parseMaybeActReply` are not yet invoked from `src/service/` or from any
sender. Only `parseRouteAndMaybeAct` is live (it is the renamed incumbent). So the highest-value
review question is not "does the code run" but **"does each rule match the receiver-side code it is
about to replace"** — the tables below name the exact sites to compare against.

## What landed

**New module `src/rpc/validate.ts`** holding every wire-shape rule, with one uniform signature:

```ts
export type Parser<T> = (msg: unknown) => T | undefined;   // undefined = reject this message
```

Not `msg is T`. Two of the shapes must *normalize* while they check (truncate an id list, drop a
sample entry, drop an advisory field), which a type guard cannot express without mutating its
argument. The module keeps the parser signature throughout rather than mixing the two forms —
including for `parseRouteAndMaybeAct`, which normalizes nothing.

Seven parsers plus one helper:

| Symbol | Rejects when | Normalizes |
|---|---|---|
| `parseRouteAndMaybeAct` | the incumbent checks, plus `digest` over `MAX_DIGEST_CHARS` (4096) | nothing — returns its argument |
| `parseLeaveNotice` | `from` not a parseable peer id; `timestamp` not finite | `replacements` → `sanitizeReplacements` |
| `makeSnapshotParser(caps)` | `from` not a parseable peer id; `timestamp` not finite | id lists truncated to `caps` then non-strings dropped; `sample` truncated then vetted per entry with skip-and-log; `size_estimate` / `confidence` / `metadata` dropped individually |
| `parsePingResponse` | `ok` is not a boolean | projects to `{ ok, size_estimate?, confidence? }` |
| `parseNearAnchor` | `estimated_cluster_size` or `confidence` not finite | `anchors` ≤ 8, `cohort_hint` ≤ 16, missing → `[]` |
| `parseMaybeActReply` | neither reply shape matches | discriminates on a string `commitCertificate`, else NearAnchor |
| `sanitizeReplacements` | (not a parser) | ≤ 12, parse-checked, `undefined` — never `[]` — when empty |

Shared primitives (`isPlainObject`, `isFiniteNumber`, `finiteNumberOr`, `isPeerIdString`,
`boundedStringArray`) stay module-scoped: implementation detail, not surface. `package-exports`
asserts two of them are *absent* from the root entry so that stays true.

**Moves, not copies.** `validateRouteAndMaybeAct` left `maybe-act.ts` (renamed
`parseRouteAndMaybeAct`) and `sanitizeReplacements` left `leave.ts`. No compatibility re-export —
both importers were updated (`src/service/fret-service.ts:22` + its call site at `:1153`,
`test/rpc.handler-fuzz.spec.ts:8`). The maybeAct-only `NOTE:` that said a later ticket would
generalize the validator is deleted, since this is that ticket.

**Exports.** Eight symbols from `src/index.ts` — the `Parser<T>` type and the seven values above —
with the same rationale as `registerRpcHandler` / `rpcRequest` / `openRpcStream`: a consumer
registering its own handler over the same node otherwise re-derives the rules by hand.

**Docs.** `docs/fret.md` gains a *Wire-shape parsers* subsection under *Wire formats* (the table
above plus the three decisions that are judgement rather than mechanics), and the *Cheap-guard
rejections* bullet now names the new symbol and file.

## Decisions a reviewer should weigh

Two were locked by the ticket before implementation and are **not** open:

- **Uniform `Parser<T>`, so `validateRouteAndMaybeAct` became `parseRouteAndMaybeAct`.** The call
  site is `if (!parse(msg))`, which behaves identically against an object-or-`undefined` return.
- **Export the parsers from the package root**, with matching spot-checks in `package-exports`.

Three were mine and are open to challenge:

- **`parseNearAnchor` rejects a non-finite `estimated_cluster_size` / `confidence`** rather than
  defaulting them to 0. The ticket said "finite" without saying which. I chose reject for
  consistency — every other *required* scalar on this wire rejects (`timestamp` on both snapshot and
  leave, the four maybeAct numerics) — and the caller's fallback is well-defined (an emptied anchor
  list already falls back to the local cohort). The argument against: a NearAnchor is a hint, and
  rejecting throws away usable anchors over an unusable advisory number. If a reviewer prefers
  default-to-0, it is a two-line change plus one test.
- **An absent `sample` normalizes to `[]`** (the ticket's table said so, but it is the one place the
  parser's output differs from its input for a fully legal message). Consumers written as
  `snap.sample ?? []` are unaffected; a consumer that distinguishes absent from empty would be. No
  such consumer exists today — `15.33` should confirm when it rewires the merge loops.
- **`parseRouteAndMaybeAct` returns its argument; the other two message parsers return a shallow
  copy** (spread, then fix the normalized fields). Deliberate — maybeAct normalizes nothing, so
  there is nothing to copy for, and copying only to look uniform would allocate per inbound message
  on the hottest path. Worth a second opinion: it means the module is uniform in *signature* but not
  in *aliasing*, and a caller that mutates a parsed maybeAct message mutates the decoded object.

Deliberately unchecked, and stated rather than overlooked:

- **`v` on every message.** Nothing negotiates versions; a hard reject on an unexpected `v` makes a
  future v2 rollout fail closed at exactly the peers that have not upgraded.
- **`sig` on the snapshot.** Message signing is unimplemented, so nothing reads it.
- **`metadata` values.** The rule is "non-null non-array object", matching the receiver's existing
  `isPlainObject` gate; the values inside are arbitrary JSON by the wire format's own definition.

## Testing, validation, usage

`test/rpc.codec-properties.spec.ts` gains a `wire-shape parsers` describe (41 tests) in three tiers.
The properties are the ones worth reading first — the table cases are the routine half.

**Tier 1 — "never reject what our own encoder produced" (6 property tests, 200 runs each).** For
each of the five wire types plus both reply shapes, generate a *legal* instance, push it through the
real `encodeJson` → `decodeJson`, and assert the parser returns non-`undefined` **and** deep-equals
the expected normalized value. This is the over-strict direction, which no hand-written case finds
because the cases are written by whoever wrote the rule. It is what catches, e.g., a parser that
demands `null` where `encodeJson` drops the property entirely.

The legal arbitraries could not reuse this file's existing ones: `arbNeighborSnapshot` and friends
draw ids from `arbNastyString` **on purpose** (they prove the codec is lossless, not that a
validator accepts them), so `from` is never a peer id. The new arbitraries draw from a pool of eight
real Ed25519 peer ids built in a `before()` hook, use the existing `arbCoordB64` for coordinates,
and reuse the file's `withOptionals` helper so the all-optionals-absent shape is actually generated
(`fc.record`'s `requiredKeys` measurably never produced it — that is documented at the helper).

**Tier 2 — "never throw, whatever arrives".** One property running all six parsers over arbitrary
JSON plus the deliberately-illegal wire arbitraries, plus 14 named hostile shapes (`null`,
`undefined`, bare arrays, `{ successors: 5 }`, `{ sample: [null, 7, { id: 1 }] }`, a
null-prototype object, …). A throw out of a parser is the exact failure the module exists to
prevent — it used to leak the inbound stream.

**Tier 3 — the per-field table (30 cases).** Asserts the *normalized value*, not merely "did not
reject", since truncation and drop-entry are invisible otherwise. Notable cases to re-read:

- `truncates *before* filtering` — 16 non-strings followed by 4 strings yields `[]`. If the
  per-entry filter ran first the four strings would survive, and a 100k-entry junk list would cost
  100k comparisons instead of 16.
- `drops a sample entry that fails any of its three checks, keeping the rest` — one good entry plus
  five differently-broken ones (non-string id, coord decoding to 3 bytes, non-finite relevance,
  undecodable coord, a bare `null`) leaves exactly the good entry, message accepted.
- `reports an emptied replacement list as absent, not as []` — the receiver's `if (!replacements)`
  guard is what keeps a leave notice out of the record-replacements loop entirely.
- `parsePingResponse demands a real boolean rather than coercing` — `1`, `0`, `'true'`, `null`,
  `{}` all reject. This is what `Boolean(r.ok)` in `sendPing` used to swallow.
- `rejects a message whose timestamp is not finite` includes the `null` case specifically: a legal
  non-finite arrives as `null` over JSON, so the finite check has to *reject* it, not throw on it.

`test/rpc.handler-fuzz.spec.ts` keeps its whole `validateRouteAndMaybeAct` table under the new name
and return convention (19 → 20 bad cases; the new one is an oversized `digest`, the cap this ticket
added). `test/package-exports.spec.ts` gains a spot-check per exported parser plus a type-level line
pinning `Parser<T>`, in that file's existing style.

**Manual usage sketch** (what `15.33` will write):

```ts
const parseSnapshot = makeSnapshotParser(this.mergeSnapshotCaps());
const snap = parseSnapshot(await decodeJson(bytes));
if (!snap) { this.diag.rejected.malformed++; return; }
// snap.successors / snap.predecessors / snap.sample are already capped and vetted —
// the merge loop's own `.slice(...)` and per-entry try/catch become dead code.
```

## Known gaps — please probe these

- **No production caller for five of the seven parsers.** The rules were written by reading the
  merge loops, not by running against them. The highest-value review is a line-by-line comparison of
  `makeSnapshotParser`'s table against `mergeAnnounceSnapshot` (grep the symbol; it was at
  `fret-service.ts:1745-1766`) and `fetchAndMergeSnapshot` (`:2234-2256`), and of `parseLeaveNotice`
  against `registerLeave` + `recordLeaveReplacements`. A rule that is subtly stricter than today's
  receiver will only show up as dropped peers after `15.33` lands.
- **Caps are exercised at Core numbers only.** The property tests instantiate
  `makeSnapshotParser({ successors: 16, predecessors: 16, sample: 8 })`. The parser is cap-generic
  and the table cases derive their expectations from the `CAPS` constant, so Edge (8/8/6) is covered
  by construction — but not by an actual run. Cheap to add if a reviewer wants it explicit.
- **The never-throws property covers values, not exotic objects.** `fast-check` generates plain JSON
  values; it does not generate objects with throwing getters or `Proxy` traps. Those cannot arrive
  from `decodeJson` (which parses JSON), so the gap is only reachable by a consumer calling an
  exported parser on a hand-built object. Stated, not defended.
- **`parseMaybeActReply` does not recognise a busy reply.** `BusyResponseV1` is classified by
  `rpcRequest` before `decode` runs, so this is correct at the seam as it exists — but it is an
  assumption about a file this ticket did not touch, and `15.33` is where it gets tested for real.
- **The 8 / 16 reply caps are argued, not measured under load.** They come from reading the
  producers (`pickAnchors` yields ≤ 2; `cohort_hint` is built from ≤ 4 and ≤ 8 ids), so they cannot
  refuse this node's own output. Nothing pins the producers *at* those numbers — a future change
  that emits 20 cohort hints would be silently truncated by the receiver. Worth a thought about
  whether the producer should assert its own bound.
- **Tripwire parked in code:** `NOTE:` at `parseSample` in `src/rpc/validate.ts` — the skip-and-log
  emits one line per dropped sample entry, so a hostile peer costs `cap` lines per message. Harmless
  today (debug-gated logger, neighbors token bucket meters the messages); collapse to one line per
  message if snapshot logging ever reaches an always-on sink.
