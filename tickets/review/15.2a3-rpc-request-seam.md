## Remaining work — apply these three fixes

Each is minor (fix-in-this-pass, not a new ticket). Ordered by risk.

**Fix 1 — close the write-only type hole in `rpcRequest` (`src/rpc/request.ts`).**
`rpcRequest<T = undefined>` takes `decode` as *optional*, and the write-only branch returns
`{ kind: 'ok', value: undefined as T, rttMs }`. So `rpcRequest<Snapshot>(node, p, proto, { body })`
— an explicit type argument with the `decode` callback forgotten — type-checks, returns
`kind: 'ok'`, and the caller reads a property off `undefined` at runtime. This is rung 1 of the
*Architecture first* ladder: make the bad state unrepresentable. Replace the single exported
signature with two overloads over the unchanged implementation signature:

```ts
// No decode → write-only. `T` is pinned to undefined, so an explicit type argument cannot reach
// this overload and a forgotten `decode` can no longer be typed as the reply.
export function rpcRequest(
	node: Libp2p, peer: string, protocol: string,
	opts?: RpcRequestOptions<undefined>
): Promise<RpcOutcome<undefined>>;
// With decode → the reply type comes from the validator.
export function rpcRequest<T>(
	node: Libp2p, peer: string, protocol: string,
	opts: RpcRequestOptions<T> & { decode: (bytes: Uint8Array) => T | Promise<T> }
): Promise<RpcOutcome<T>>;
export async function rpcRequest<T = undefined>(/* unchanged */) { /* unchanged body */ }
```

Overload resolution was traced against every existing call site before writing this down:

- `rpcRequest<PingReply>(…, { body, decode: decodePing })` — explicit type argument, so only the
  generic overload is a candidate; `decode` is present, so it matches.
- `rpcRequest(…, { body })` (the write-only tests) — no type argument, matches overload 1, yields
  `RpcOutcome<undefined>`.
- `rpcRequest(…, { body, decode: decodePing })` — overload 1 rejects it (a `decode` returning
  `PingReply` is not assignable to one returning `undefined`), so it falls through to overload 2
  with `T` inferred from `decode`.
- `rpcRequest<Snapshot>(…, { body })` — the bug case: overload 1 takes no type parameter so it is
  not a candidate, and overload 2 requires `decode`. Compile error. That is the fix.
- The `package-exports.spec.ts` type-level pin assigns `rpcRequest` to
  `(node, peer, protocol, opts?: RpcRequestOptions<undefined>) => Promise<RpcOutcome<undefined>>`,
  which is overload 1 verbatim, so the pin still holds. **Confirm with `npx tsc --noEmit` rather
  than trusting the trace** — it is the one part of the design that leans on TypeScript's
  overload-assignability rules.

**Fix 2 — give the over-cap failure a stable error identity (`src/rpc/protocols.ts` +
`src/rpc/request.ts`).** `classify` currently routes the over-cap case by matching message text
(`message.startsWith('payload too large')`), while both its neighbours match on `err.name`. The
root cause is one owner: `readFramed` raises the condition as a bare `new Error('payload too
large: …')` at two sites (the `onLength` hook, `src/rpc/protocols.ts:353`, and the
`InvalidDataLengthError` rescue arm, `:396`), so there is no identity to match on. Add a
`PayloadTooLargeError extends Error` beside the existing `FrameTruncationError` (same shape — set
`this.name`), throw it at both sites with the **message text unchanged**, export an
`isPayloadTooLargeError` predicate beside `isFrameTruncationError`, and have `classify` call that
instead of the prefix match. Keeping the messages byte-identical is what keeps the existing
assertions green — `test/payload-bounds-ttl.spec.ts`, `test/rpc.codec-properties.spec.ts`,
`test/rpc.stream-errors.spec.ts` and `test/rpc.request.spec.ts` all assert on the text, not the
type.

Scope note so this is not over-sold: no *reachable* remote-influenced error was found that collides
with the prefix today. Everything reaching `classify` comes from libp2p's dial / `newStream` /
stream machinery or from `readFramed` itself, and a validator's own throw goes through
`decodeFailure`, never `classify`. So this hardens the classification rule rather than repairing a
live misclassification — but it retires "classify by message text" as a *class* instead of leaving
one instance of it in the newest code in the package.

**Fix 3 — document that a write-only request cannot observe `foreign-protocol`.**
`openRpcStream` pins `negotiateFully: false`, deferring an `UnsupportedProtocolError` from the
stream open to the first read. The write-only path returns `ok` immediately after the write, so
sending to a peer that does not serve this network's protocol yields `ok` and produces no
membership evidence. **This was checked against today's behavior and is not a regression**:
`sendLeave` (the write-only sender `15.2b` migrates) also never reads, and its only caller
(`sendLeaveToNeighbors`, `src/service/fret-service.ts:1512` and `:1522`) merely logs a throw — it
applies no membership signal and books no contact strike. So nothing is lost by the migration; the
gap is simply unstated at the seam a future caller will read. Add one clause to
`RpcRequestOptions.decode`'s doc comment saying that with no `decode` the deferred negotiate
failure is never observed, so `foreign-protocol` is unreachable on that path, and cross-reference
the `negotiateFully: false` caveat already documented on `openRpcStream`.

## Remaining work — three cheap test cases

All in `test/rpc.request.spec.ts`, all reusing the existing `makeStub` / `serves` / `countingNode`
harness. They close three of the implementer's own "Known gaps".

- **`busy` with a missing or non-numeric `retry_after_ms`.** Only the well-formed 500 ms case is
  pinned; the `typeof retry === 'number'` guard's `undefined` arm is not. Frame `{busy: true}` and
  `{busy: true, retry_after_ms: 'soon'}`, assert `kind: 'busy'` with `retryAfterMs === undefined`
  in both.
- **The 64 KiB `DEFAULT_MAX_BYTES` boundary.** Every case passes an explicit `maxBytes`. Drive one
  request with `maxBytes` omitted against a stub whose frame declares more than 65536 bytes and
  assert `decode-error`, which also proves the default is wired to the cap rather than merely
  present.
- **Two concurrent `rpcRequest` calls over one node.** Cheap (two `serves()` stubs, one counting
  node, `Promise.all`) and it pins that the helper holds no per-call state on the node — the claim
  `15.2b` relies on when five senders share it.

## Findings dispositioned as no-change — record these in the `## Review findings` section

- **`skipped` release counters are vacuous.** No stream exists on that path, so `{closes: 0,
  aborts: 0}` is true by construction rather than by assertion. Nothing to add.
- **No real-transport case; `releaseRpcStream`'s "bounded close rejected → fall through to
  `abort()`" arm is never taken through `rpcRequest`.** The stub's `close()` ignores the `{signal}`
  it is handed. That arm is covered directly in `test/rpc.protocols.spec.ts`, and reproducing it
  through the helper would need a stub modelling signal-aware close rejection — a harness change
  disproportionate to re-covering an already-covered arm. Declined.
- **Not property-based.** `classify` has five branches and every one is covered by a hand-picked
  case; a generator over arbitrary error identities would re-derive the same five branches without
  reaching new state. Declined rather than filed as a `debt-` ticket.
