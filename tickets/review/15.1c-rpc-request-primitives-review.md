## Already verified (do not redo)

The implement diff was read in full: `src/rpc/protocols.ts` (three arms), both test files, and the
three `docs/fret.md` paragraphs.

**The implementer's central claim about libp2p holds against the real implementation, not only
against the stub** (checked in `node_modules/@libp2p/utils/dist/src/abstract-stream.js` and
`abstract-message-stream.js`):

- `AbstractStream.close(options)` sets `writeStatus = 'closing'` **before** it awaits anything,
  then awaits `pEvent(this, 'idle', options)` / `pEvent(this, 'drain', options)` /
  `sendCloseWrite(options)` — each receiving the caller's `AbortOptions`. A close bounded by a
  signal therefore rejects on that signal with the write end left at `'closing'`, never
  `'closed'` — exactly the state `registerRpcHandler`'s catch arm needs
  (`writeStatus !== 'closed'`) for its abort to run.
- `close()` early-returns when `writeStatus` is already `'closing'`/`'closed'`, so a handler that
  closed for itself is not released twice.
- `close()` does **not** abort the stream when it rejects — it leaves the stream half-open. So the
  follow-up `abort()` in both `releaseRpcStream` and the handler seam is load-bearing, not
  belt-and-braces.
- `abort()` is self-guarded, so an extra abort is a no-op rather than a double release.
- **A bare `close()` really can block indefinitely.** `processSendQueue` sets
  `writableNeedsDrain = true` when the muxer stops accepting (`onMuxerNeedsDrain` does too), and
  `close()` then awaits the `'drain'` event. With no `options.signal` there is nothing to end that
  wait, so a remote that accepts a stream and stops reading holds the closer forever once the
  flow-control window fills. (`checkWriteBufferLength` aborts only if `maxWriteBufferLength` is
  configured — a muxer-dependent backstop, not a budget.) This is what makes finding A below real.

**The ordering the doc comment depends on is real.** All five sender call sites release from a
`finally` *before* `d.cancel()`, so the deadline is still live when its signal reaches
`releaseRpcStream`: `ping.ts:127-128`, `neighbors.ts:108-109`, `neighbors.ts:146-147`,
`maybe-act.ts:106-107`, `leave.ts:89-90`.

**Arm (a)'s "the loop needs no change" is arithmetically correct.** With `timeoutMs = Infinity`:
`deadlineAt` is `Infinity`, `remaining <= 0` never fires, `Math.min(Infinity, EOF_POLL_MS)` is 20,
and the `read timed out` throw is unreachable.

**No caller passes `timeoutMs` of `0` or a negative** — `grep -rn "readFramed(" src test` shows
every call site passing a module constant, a literal ≥ 150, `Infinity`, or nothing.

## Remaining work

### Finding A (major, but a small edit — fix in this pass): the new close budget is unreachable in production

`registerRpcHandler` wraps the success path in a budgeted `stream.close({ signal: d.signal })`.
But **all five FRET handler bodies close the stream themselves first, with a bare, unbudgeted
`await stream.close()`**:

- `src/rpc/ping.ts:49`
- `src/rpc/neighbors.ts:39` (request), `:56` (identity-mismatch drop), `:61` (announce reply)
- `src/rpc/leave.ts:62` (identity-mismatch drop), `:68` (reply)
- `src/rpc/maybe-act.ts:33`

By the libp2p reading above, that bare close is the one that blocks when the remote stops reading
— and by the time it returns the write end is `'closed'`, so the seam's budgeted close early-
returns. The slow-loris write-side hole the implement ticket set out to close is therefore still
open for every production handler; the budget only bites for a handler that does *not* close, and
no such handler exists.

The two existing tests document the gap rather than catching it: `test/rpc.handler-fuzz.spec.ts`
exercises the budget with a handler whose body is a comment ("replied, no release", ~line 271),
and the next case asserts that a handler which closes for itself skips the budget (~line 289).

Fix — the invariant is "**releasing the inbound stream is the seam's job, not the handler's**",
which the seam's own doc comment already claims:

- Delete the `await stream.close()` from all seven sites listed above. The identity-mismatch
  early-returns become a bare `return;` — the seam still closes (a drop closes, never aborts, as
  today).
- Update `registerRpcHandler`'s doc comment: it currently says "`serve` normally closes on its
  own, and `close()` early-returns…". After this change the seam always performs the close, and
  the early-return sentence becomes a statement about *external* callers of the exported seam, not
  about FRET's own handlers.
- Update the two tests above so the budgeted-close case drives a **real** FRET handler (e.g.
  `registerPing`) over the `closeHangs` stub and asserts it settles and aborts; keep a
  handler-closes-for-itself case for the exported-seam contract, but label it as such.
- Update the "Inbound handlers release their stream on every path" paragraph in `docs/fret.md`,
  which currently says the close early-returns for a handler that replied and closed for itself.

### Finding B (minor, same class — fix in this pass): `sendMaybeAct`'s half-close is unbudgeted

`src/rpc/maybe-act.ts:102` does `await stream!.close()` inside the `try`, as the write-side flush
the responder waits on. Every other close in the sender path carries the deadline's signal; this
one does not, so on the same stalled-reader shape it hangs past `timeoutMs` with the deadline
armed and useless. One-line fix: `await stream!.close({ signal: d.signal })`. The surrounding
comment already explains why the close is inside the `try`; extend it to say the signal is what
keeps it inside the RPC's budget.

### Finding C (minor — fix in this pass): `readFramed` does not validate `timeoutMs`

The entry guard tests `timeoutMs === Infinity` exactly. A `NaN` is worse than the implement
handoff described ("runs unbounded with no error"): `Math.min(NaN, EOF_POLL_MS)` is `NaN` and
`setTimeout(fn, NaN)` clamps to zero, so the poll loop spins one iteration per event-loop turn,
re-running `remoteFinishedWriting` for as long as the stream stays open — a hot spin, not a quiet
hang. `0` and negatives make `remaining <= 0` fire immediately, which is at least loud.

Not reachable from any current caller (verified above), but `readFramed` is exported from the
package root, so a consumer computing a timeout from config can reach it. Add, next to the
existing `Infinity` clause: `if (!(timeoutMs > 0)) throw new Error(...)` — which covers `NaN`,
`0` and negatives while letting `Infinity` through. Rung 1 of *Architecture first*: validating a
seam's own input so the bad state cannot enter. Add a case to `test/rpc.protocols.spec.ts`
alongside the existing `Infinity`-requires-a-signal case (~line 509).

### Finding D (minor — fix inline or record why not): close-budget expiry looks like a handler fault

When the budgeted close expires, it rejects into `log.error('%s handler error - %e', protocol,
err)` carrying a `DeadlineExpiredError` (exported from `src/utils/deadline.ts`). An operator
cannot separate "the peer accepted our reply and stopped reading" from "the handler threw on a
malformed message", and those call for opposite responses. This matters *more* after finding A,
since the budget then actually fires in production. Cheap fix: test
`err instanceof DeadlineExpiredError` in the catch arm and log a distinct line; the abort arm is
unchanged.

### Tripwires to record (NOT tickets)

- **Per-message timer on every inbound RPC.** After finding A the seam arms and cancels a
  `deadline(closeBudgetMs)` — an `AbortController` plus a `setTimeout` — for every inbound
  message on every protocol, where before finding A it was armed and immediately cancelled. It is
  now load-bearing rather than overhead, but it is still a per-message allocation. Park a `NOTE:`
  at the close site saying the budget is armed per inbound message and what to measure if inbound
  cost ever shows up in a profile.
- **Release-before-cancel ordering.** Nothing fails if a future sender calls `d.cancel()` before
  `releaseRpcStream`; the bound silently disappears. Park a `NOTE:` at the `releaseRpcStream`
  signature (the `docs/fret.md` *Dialability* paragraph already states the rule in prose).
