### Verified in runs 1-4 — carry into `## Review findings`

The implement diff was read in full: `src/rpc/protocols.ts` (three arms), both test files, and the
three `docs/fret.md` paragraphs.

**The implementer's central claim about libp2p holds against the real implementation, not only
against the test stub** (checked in `node_modules/@libp2p/utils/dist/src/abstract-stream.js` and
`abstract-message-stream.js`):

- `AbstractStream.close(options)` sets `writeStatus = 'closing'` **before** it awaits anything,
  then awaits `pEvent(this, 'idle', options)` / `pEvent(this, 'drain', options)` /
  `sendCloseWrite(options)` — each receiving the caller's `AbortOptions`. A close bounded by a
  signal therefore rejects on that signal with the write end left at `'closing'`, never
  `'closed'` — exactly the state `registerRpcHandler`'s catch arm needs
  (`writeStatus !== 'closed'`) for its abort to run.
- `close()` early-returns when `writeStatus` is already `'closing'`/`'closed'`, so a handler that
  closed for itself is not released twice.
- `close()` does **not** abort the stream when it rejects — it leaves the stream half-open. So the
  follow-up `abort()` in both `releaseRpcStream` and the handler seam is load-bearing, not
  belt-and-braces.
- `abort()` is self-guarded, so an extra abort is a no-op rather than a double release.
- **A bare `close()` really can block indefinitely.** `processSendQueue` sets
  `writableNeedsDrain = true` when the muxer stops accepting (`onMuxerNeedsDrain` does too), and
  `close()` then awaits the `'drain'` event. With no `options.signal` there is nothing to end that
  wait, so a remote that accepts a stream and stops reading holds the closer forever once the
  flow-control window fills. (`checkWriteBufferLength` aborts only if `maxWriteBufferLength` is
  configured — a muxer-dependent backstop, not a budget.) This is what makes finding A real.

**The ordering the seam's doc comment depends on is real.** All five sender call sites release from
a `finally` *before* `d.cancel()`, so the deadline is still live when its signal reaches
`releaseRpcStream`: `ping.ts`, `neighbors.ts` (×2), `maybe-act.ts`, `leave.ts`.

**Arm (a)'s "the loop needs no change" is arithmetically correct.** With `timeoutMs = Infinity`:
`deadlineAt` is `Infinity`, `remaining <= 0` never fires, `Math.min(Infinity, EOF_POLL_MS)` is 20,
and the `read timed out` throw is unreachable.

**No caller passes `timeoutMs` of `0` or a negative** — `grep -rn "readFramed(" src test` shows
every call site passing a module constant, a literal >= 150, `Infinity`, or nothing.

### Findings and their disposition

**Finding A (major) — the success-path close belonged to the seam, not to seven handler bodies.**
A bare `await stream.close()` in a handler body runs *before* the seam's budgeted close and blocks
on exactly the stalled remote the budget exists for, pre-empting it entirely.

- *Source half, committed in `7ebd0be` (run 5):* the bare close is gone from all seven FRET handler
  bodies (`ping.ts`, `neighbors.ts` ×3, `leave.ts` ×2, `maybe-act.ts`); the two identity-mismatch
  drops are now a bare `return;`. Each file's "errors and stream release belong to
  `registerRpcHandler`" comment says the close does too, and why. `registerRpcHandler`'s doc
  comment: the "Success path" paragraph says the seam always closes and that no FRET handler body
  closes for itself; the early-return sentence is now a statement about *external* callers of the
  exported seam. `sendMaybeAct`'s half-close is `await stream!.close({ signal: d.signal })`, with
  the reason in the surrounding comment.
- *Test half, applied in run 7 (this run):* in `test/rpc.handler-fuzz.spec.ts`,
  `describe('registerRpcHandler release accounting')` —

    `/* replied, no release */`, so it documented the gap rather than catching it. It now drives

**Finding B (minor) — `sendMaybeAct`'s half-close was unbounded.** Fixed in run 5 (`7ebd0be`),
see above.

**Finding C (minor) — `readFramed` did not validate `timeoutMs`.** The entry guard tested
`timeoutMs === Infinity` exactly. `NaN` was worse than the implement handoff described ("runs
unbounded with no error"): `Math.min(NaN, EOF_POLL_MS)` is `NaN` and `setTimeout(fn, NaN)` clamps
to zero, so the poll loop spins one iteration per event-loop turn, re-running
`remoteFinishedWriting` for as long as the stream stays open — a hot spin, not a quiet hang. `0`
and negatives make `remaining <= 0` fire immediately, which is at least loud. Not reachable from
any current caller (verified above), but `readFramed` is exported from the package root, so a
consumer computing a timeout from config can reach it. *Applied in run 7:* a
`if (!(timeoutMs > 0)) throw` guard next to the `Infinity` clause — `!(x > 0)` rather than
`x <= 0` so it also catches `NaN`, with `Infinity` still passing — plus a `@throws` entry in
`readFramed`'s doc comment. This is rung 1 of *Architecture first*: validating a seam's own input
so the bad state cannot enter, rather than filing a bug against a caller. **Its test is the one
item still outstanding.**

**Finding D (minor) — a close that exhausted its budget was logged as a handler error.** Applied in
run 6 (committed `ed9c12b`): `registerRpcHandler` holds its close budget in a
`let closeBudget: Deadline | undefined` declared outside the `try`, and the catch arm logs
`'%s reply close exceeded %dms budget - remote stopped reading, aborting stream'` when
`closeBudget?.signal.aborted === true`, else the original `'%s handler error - %e'`. The abort arm
is unchanged. The discriminator is deliberately the budget **signal**, not
`err instanceof DeadlineExpiredError` as an earlier ticket suggested: libp2p's `close()` rejects
with whatever its internal `pEvent` turns the abort into, so matching the error identity would
depend on a wrapping detail we do not own. The doc comment states this, and run 7 added the same
sentence to the `docs/fret.md` paragraph.

### Tripwires (recorded as `NOTE:`s, not tickets — both applied)

- **Per-message close timer.** `registerRpcHandler` arms an `AbortController` + `setTimeout` for
  every inbound message on every protocol. Load-bearing (no handler body closes for itself any
  more) but a per-message allocation. Parked as a `NOTE:` at the `deadline(closeBudgetMs)` site in
  `src/rpc/protocols.ts` (run 6): if inbound cost ever shows up in a profile, measure the timer
  churn before the handler bodies and consider one shared timer wheel.
- **Release-before-cancel ordering.** Nothing fails if a future sender calls `d.cancel()` before
  `releaseRpcStream` — it still compiles, still passes, and the bound on the close silently
  disappears. Parked as a `NOTE:` at the `releaseRpcStream` signature in `src/rpc/protocols.ts`
  (run 7): all five senders get it right today; if a sixth is added or one is reordered, consider
  taking the `Deadline` itself so the cancel cannot precede the release. The prose rule was already
  stated in that function's doc comment and in the `docs/fret.md` *Dialability* paragraph, so this
  is a greppable marker at the site rather than new analysis.
