## What shipped

`DigitreeStore` (`packages/fret/src/store/digitree-store.ts`) now maintains two O(1) tallies
alongside the existing tree/id-index bookkeeping:

- `membershipCounts: Map<MembershipState, number>` / `stateCounts: Map<PeerState, number>`
  (~182-183), private, updated only at the store's two write seams.
- `bumpCount` / `tally` helpers (~190-199) — `tally(entry, +1)` on insert, `tally(entry, -1)`
  on remove/replace-of-prior.
- Public readers `countByMembership(m)` / `countByState(s)` (~201-209), `?? 0` on a label
  never seen.
- `put` (~219-236, the single write seam every mutating call funnels through) tallies the
  outgoing `prevEntry` and incoming `entry` on every write — insert, re-key (coordinate
  change), and replace (e.g. `importEntries` overwriting an id with a fresh snapshot record).
- `remove` (~278-287) tallies the entry out before `deleteAt`, inside the existing
  `if (p.on)` guard so a remove of an already-absent id is a no-op for the counts too.

No new write path was added — counts ride the same seam the tree/id-index invariant already
depends on, so anything that would desync tree/id-index would desync counts identically (see
the class comment at ~176-181).

## Test coverage (`test/digitree.invariants.spec.ts`)

Two layers, both passing (`yarn test` — full suite green, see Verification below):

1. **Extended the existing `fast-check` property** (`checkInvariants`, ~216-262): after the
   pre-existing neighborsRight/neighborsLeft distinct-count assertions, it now loops
   `STATES`/`MEMBERSHIPS` and asserts `store.countByState`/`countByMembership` against a
   manual `listed.filter(...)` recount. This runs on **every operation** of the 60-op
   property (arbitrary sequences of upsert/recoord/touch/import/reimport/remove/state/
   membership), so it's the main defense against an under-reporting tally surviving any
   op-sequence shape, not just the six hand-written cases below.
2. **New `describe('counts', ...)` block** (six `it()`s, between the pre-existing
   `importEntries` and `update` blocks): empty-store zeros; `setMembership` moves membership
   only; `setState('dead')` moves state only; `remove` of a dead+foreign peer decrements
   both; `importEntries` replacing an id recounts rather than sums (no double-counting on
   replace); double-remove / remove-of-never-inserted id never goes negative.

## Bug found + fixed during this pass

The `importEntries` recount test as originally written asserted the **incoming** serialized
`state` field (`'connected'`) took effect after import. It doesn't, on purpose:
`importEntries` hardcodes `state: 'disconnected'` on every record regardless of what the
snapshot says (docs/fret.md: "All imported entries have their state forced to
'disconnected' since connection liveness cannot survive a restart"). That's a **test bug**,
not a store bug — fixed by re-shaping the case to prove the recount using a state the import
*does* control the transition of (seed the existing entry to `'dead'` via `setState`, then
show import forces it to `'disconnected'` and the tally moves `dead → disconnected`, not
`dead` staying stuck or `connected` appearing). Membership isn't force-reset on import (it
reads `s.membership ?? 'unknown'`), so that half of the original test was already correct.
