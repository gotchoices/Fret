## Finding the ticket did not anticipate — read this before accepting its "what this unblocks"

The ticket says the guard unblocks tuning `CONNECTED_SLACK_ORDERS` / `QUALITY_SLACK_ORDERS`.
**It does not, and the arithmetic says why.** The sim's near radius is
`2·k·2^256 / store.size()`, so `store.size()` is the radius's own *denominator*: shrinking the
store makes the radius **larger**, not smaller. At `capacity: 32` with `k: 15` the radius works
out to 60/32 of the maximum ring distance, which clamps to half the ring — the largest a ring
distance can be — so **every** candidate takes the selector's near branch, where ordering is by
distance alone and both the connected allowance and the backoff term are inert.

Consequences, all now written into the code comments rather than left here:

- the new case discriminates the distance **metric**, which is exactly what it was asked to do,
  and it does so through pure distance ordering — arguably a cleaner isolation than the far
  branch would give;
- but it exercises none of the cost function's slack constants, so their tuning stays deferred.
  The deferral now has a measured reason instead of the retracted one. Exercising the far branch
  needs a *larger* capacity or a smaller β, not a sparser store.

The ticket's second unblock claim ("the selector's far-cost branch generally … sparse stores
shrink `store.size()`, which is that radius's own denominator") has the denominator right but
draws the opposite conclusion from it. Nothing was built either way — this is a note for whoever
picks up the slack-tuning work.

## Use cases to check when reviewing

- **Does the guard actually bite?** The honest check is to re-do the substitution: edit
  `minDistance` in `src/ring/distance.ts` to clockwise-only and confirm the new case fails on the
  p90 assertion; edit it to XOR and confirm it fails on the success assertion (and that the p90
  assertion passes, which is the point of having both). One cell costs ~5–7 s wall. The other
  three routing cases are expected to keep passing under both substitutions — that is the
  retracted claim, still true of them.
- **Seed sensitivity.** Thresholds were taken from the prereq's four-seed table, not re-derived.
  A reviewer wanting more confidence can run the new case at seeds 1 / 99 / 20260820 by editing
  `baseConfig`'s seed; the prereq measured 100% success and p90 7–8 on all four at cap 32.
- **Threshold placement.** 0.95 sits 5 points below shipped and 5 above the worst substituted
  (clockwise-only, 90%). 12 sits 50% above the shipped worst p90 (8) and 5 below clockwise-only's
  best (17). Whether that headroom is the right split is a judgement call worth a second opinion.
- **The `p90Hops >= 3` line.** It is a headroom claim, deliberately not a guard, and it is the
  assertion most likely to become flaky if the harness's convergence or scoring changes. Consider
  whether it earns its place.

## Known gaps — flagged, not papered over

- **The substitution is not a pure selector comparison, and the shipped comments say so.** There
  is no injection seam: `chooseNextHop` imports `minDistance` directly, and the relevance
  sparsity model (`normalizedLogDistance` in `src/store/relevance.ts`) reads it too, so a
  substituted run changes eviction shape as well as hop choice. Narrowing this needs an injection
  seam — a separate ticket, not filed here, and the guard is honest about the limitation rather
  than claiming isolation it does not have.
- **The guard's numbers were not independently re-measured.** They come from the prereq's table.
  The single confirming data point is that the shipped cap-32 row reproduced exactly on the first
  run of the new case; the substituted rows were not re-run in this ticket.
- **`max` hops is not asserted at all.** The shipped metric measured max 19 at cap 32 against
  clockwise-only's 23 — a gap too narrow to hold a threshold, so none was written. Only success
  and p90 carry the guard.
- **No new coverage of the far-cost branch**, per the finding above. The far branch remains
  unexercised by any simulation case.
