All three arms of the ticket landed in `src/rpc/protocols.ts`. No sender was touched — `ping.ts`,
`neighbors.ts`, `maybe-act.ts` and `leave.ts` still arm two clocks each; that migration is
`15.2b`. `test/rpc.stream-errors.spec.ts` passes unchanged, as the ticket predicted.

## What changed

### (a) `readFramed` accepts `timeoutMs = Infinity`

Means "no independent clock — bounded by `opts.signal` alone". Two behavior changes:

- **Throws at entry** when `Infinity` arrives with no `opts.signal`, before any byte is pulled
  from the stream. An unbounded read with nothing to end it is a caller bug that would present as
  a hang; loud beats hanging.
- The read loop itself is **unchanged** — verified, not assumed: `remaining` is `Infinity` so
  `remaining <= 0` is never true, `Math.min(Infinity, EOF_POLL_MS)` is still 20 ms, and the
  `read timed out after <timeoutMs>ms` throw is simply unreachable on this path.

Default is still `RPC_TIMEOUT_MS`; the signature is unchanged for existing callers.

### (b) `releaseRpcStream` bounds its `close()`

`await stream.close({ signal })` on the un-aborted path. When that bounded close **rejects** —
the signal fired mid-close, or the transport failed it — the stream is still unreleased, so the
catch arm falls through to a best-effort `stream.abort(...)`, mirroring the already-aborted path.
Without that follow-up the bound would free the *caller* and leak the stream slot, which is the
same finite-stream-cap ceiling the function exists to protect.

The abort reason is `abortReasonError(signal)` when the signal fired, otherwise the close's own
error — so the reason is informative in both shapes.

The doc comment now states the **ordering trap** `15.2b` must preserve: every sender calls
`releaseRpcStream` from a `finally` *before* `d.cancel()`, so the deadline is still live at that
point. Cancel first and the signal handed in can never fire, and the bound is silently gone.

### (c) `registerRpcHandler`'s success-path close is budgeted

The bare `await stream.close()` now runs under its own `deadline(closeBudgetMs)`, cancelled in a
`finally` (an uncleared timer fails the repo's mocha exit watchdog). `registerRpcHandler` grew a
fourth parameter, `opts: { closeBudgetMs?: number } = {}`, defaulting to `RPC_TIMEOUT_MS`. It is
**test-only** — no production caller passes it — and is safe to add because `registerRpcHandler`
is not exported from `src/index.ts`. Without it each test case would spend 5 s of wall clock.

When the budget expires the close rejects into the existing catch arm. The stream's `writeStatus`
is `'closing'` at that point, not `'closed'`, so the arm's guard holds and the abort runs —
asserted in the test rather than assumed, per the ticket. Aborting destroys the undelivered reply,
which is the right trade: the close never completed so nothing was committed, and the remote was
not reading.

The stale NOTE at the old close site ("if it ever is, pass an `AbortOptions` deadline") is gone;
the doc comment now states what the code does.

`protocols.ts` now imports `deadline` alongside `abortReasonError` from `../utils/deadline.js`.

## Tests added

`test/rpc.protocols.spec.ts` (5 new cases):

- `readFramed(..., Infinity)` with **no signal** throws at entry, and the stream is provably never
  pulled (a counting iterator asserts `pulls === 0`) — not merely "it threw".
- `readFramed(..., Infinity, { signal })` against a never-settling source is ended by the signal
  alone: the caller's reason surfaces verbatim, and the message is asserted **not** to contain
  `read timed out`, which is the whole point (no second clock to race).
- `readFramed(..., Infinity, { signal })` still returns a normally-completed frame — pins the
  "loop needs no change" claim rather than only the failure paths.
- `releaseRpcStream` against a `close()` that never resolves on its own: returns within the
  signal's budget, and the calls recorded are `['close', 'abort']` — the close was attempted (not
  skipped) and the failed close fell through to the release.
- `releaseRpcStream` against a close that rejects for a **non-signal** reason (transport gone):
  same `['close', 'abort']`, so the follow-up abort is not conditional on the signal.

`test/rpc.handler-fuzz.spec.ts` (2 new cases + stub extension):

- `inboundStub` gained `closeHangs` and a `closeAttempts` counter. Its `close()` now takes
  `AbortOptions`, sets `writeStatus = 'closing'`, and rejects only when the passed signal fires —
  never settling if no signal is passed, which is exactly the pre-fix hang the test rules out.
- Success tail against a remote that stops reading: the handler promise **settles** within the
  injected 100 ms budget, `closeAttempts === 1`, `{closes: 0, aborts: 1}`, and the stream ends
  `'aborted'`.
- A handler that closed for itself does **not** spend the budget: `close()` early-returns on a
  closed write end, so the budgeted close is a no-op and the committed reply is not re-released.

The existing `unhandledRejection` hook on that describe covers all of the above — no rejection
escaped any new case.

## Known gaps — treat as the starting line

- **No end-to-end coverage of (b) or (c) over a real transport.** Every new case drives stub
  streams. A real libp2p peer that accepts a stream and stops reading is the actual scenario, and
  nothing here proves libp2p's own `close({ signal })` honours the signal the way the stub does.
  The stub encodes the documented `AbortOptions` contract from `@libp2p/interface` v3.1.0; that is
  a reading of the interface, not an observation of the implementation. **Highest-value thing for
  a reviewer to check.**
- **No caller uses `Infinity` yet.** Arm (a) is unexercised in production until `15.2b` migrates
  the senders, so its only coverage is the three unit cases. Nothing yet proves the single-clock
  mode behaves well against a *real* stalled peer rather than a never-settling stub.
- **The `Infinity` entry check is `timeoutMs === Infinity` exactly.** A caller passing
  `Number.MAX_VALUE`, `-Infinity`, or `NaN` gets no entry guard. `NaN` is the interesting one:
  `deadlineAt` becomes `NaN`, `remaining <= 0` is false forever, and the read runs unbounded with
  no error. Pre-existing (the parameter was never validated) and untouched here — arguably worth a
  ticket if a reviewer agrees the seam should validate its own input.
- **The close-budget expiry logs as a generic handler error** (`log.error('%s handler error - %e')`)
  carrying a `DeadlineExpiredError`. Factually a handler error, but an operator reading logs cannot
  distinguish "peer stopped reading our reply" from "handler threw on a malformed message". Not
  fixed; flagged as a legibility question, not a defect.
- **`closeBudgetMs` is test-only by convention, not by type.** Nothing prevents a production caller
  from passing it. The doc comment says so; the type system does not.
- The elapsed-time bounds in the new cases are loose (`at.most(2000)` / `at.most(3000)` against
  100 ms budgets) to stay stable on a loaded CI box. They prove "bounded, not hanging" — they do
  not prove the budget is tight.
