### From pass 1 (diff read in full, fresh, before the handoff summary)

The cumulative implement diff is 8 commits (`7584e37`..`d0e7d8d`), touching only
`packages/fret/src/rpc/protocols.ts`, `packages/fret/package.json` (2 new dependencies:
`@libp2p/utils`, `uint8-varint`) and `yarn.lock`. No test file was touched by implement — that is
the companion ticket's scope.

- **The dispatch predicate matches the library's own.** `isMessageStream` checks `closeRead` +
  `addEventListener` + `removeEventListener` + `send` + `push` + `log` — exactly what
  `@libp2p/utils` itself checks across its two internal predicates (`isValid`, whose failure makes
  `byteStream()` throw `InvalidParametersError`; and `isStream`, which is what `isEOF` branches
  on). Verified against
  `packages/fret/node_modules/@libp2p/utils/dist/src/stream-utils.js`. So a stream passing
  `isMessageStream` cannot make `byteStream()` throw and cannot land in `isEOF`'s
  multiaddr-connection branch. **Necessary and sufficient; the iterable fallback is a safe (slower)
  path, not an accidental gap.**
- **The new path genuinely closes the lost-event race.** From
  `node_modules/@libp2p/utils/dist/src/abstract-message-stream.js`: `addEventListener` is
  overridden so attaching a `message` listener while `readBuffer.byteLength > 0` schedules
  `dispatchReadBuffer()` on a microtask (so `byteStream()`'s own attach flushes bytes that arrived
  before the listener existed); `dispatchReadBuffer()`'s `finally` sets `readStatus = 'closed'`
  only once the buffer is empty *and* `remoteWriteStatus === 'closed'`; and `byteStream.read()`
  tests `isEOF(stream)` synchronously at entry and again after each wake. One buffer, and the
  end-of-stream test and the byte supply are the same object. `readFramed`'s doc comment is
  accurate.
- **The 9-byte prefix cap and the `length >= 9` over-cap short-circuit are correct.** A 9-byte
  varint declares at least 2^56, over every FRET cap, so that throw is never premature. The
  one-body-byte over-read in the "complete but larger than 2^53" varint case is harmless because
  that path throws unconditionally.

### From pass 2

- **Typecheck passes.** `cd packages/fret && npx tsc --noEmit` → exit 0, clean. (`yarn test` was
  NOT run — see Still outstanding.)
- **The single-clock migration claim holds.** Grep of `readFramed(` / `RPC_TIMEOUT_MS` across
  `packages/fret/src` finds exactly three call sites, and no site arms both an outer `deadline()`
  and a finite `readFramed` `timeoutMs`:
  - `src/rpc/request.ts:276` — `readFramed(stream, maxBytes, Infinity, { signal: d.signal })`. The
    RPC deadline is the sole clock. Correct, and the `Infinity` mode exists for this.
  - `src/rpc/maybe-act.ts:26` and `src/rpc/protocols.ts:209` (`registerJsonHandler`) — inbound
    handlers, finite default 5 s, no signal. There is no outer clock to collide with: the only
    other deadline on the inbound path is `registerRpcHandler`'s close budget, which is armed
    *after* `serve` returns, so the two never overlap.
- **`bs.unwrap()` in `readFramedFromStream`'s `finally` is inert, and the swallow hides nothing.**
  `unwrap()` removes all three of its listeners (`message`, `close`, `remoteCloseWrite`) *before*
  it calls `stream.push(readBuffer)`. `AbstractMessageStream.push` throws `StreamStateError`
  only when `readStatus` is `'closed'` or `'closing'` — the one case the comment already names —
  and otherwise appends to the stream's own read buffer and returns immediately via the
  `listenerCount('message') === 0` branch: no dispatch, no `setTimeout`, no re-entry. So pushing
  bytes back onto a stream `releaseRpcStream` is about to `close()` or `abort()` is a no-op that
  leaves at most the already-received trailing bytes in a buffer that dies with the stream. **Not a
  wedge; no finding.** (The theoretical `checkReadBufferLength()` → `abort()` inside that branch
  needs a peer that already flooded past the stream's own buffer cap, and aborts a stream being
  released anyway.)

- **The error-attribution ladder at the bottom of `readFramed`** (`src/rpc/protocols.ts` ~564):
  the `signalFired(signal)` / `signalFired(d?.signal)` pair in the `catch`. Two questions:
  - (a) It rewrites *every* error — `PayloadTooLargeError` and `FrameTruncationError` included —
    when a signal fired concurrently. Pass 2's partial reasoning, offered as a starting point and
    not as a conclusion: an error thrown inside the read propagates to this `catch` across
    microtask boundaries only, while a signal fires from a macrotask (timer or external abort), so
    the interleaving needed to rewrite an over-cap error looks hard to reach; and where it *is*
    reachable, cancellation-wins is the defensible semantic (a cancelled caller does not care
    about the frame's declared size). Confirm or refute, then either leave it with a one-line
    `NOTE:` or fix.
  - (b) Whether `signalFired` is genuinely only a TypeScript narrowing workaround, as its comment
    claims. Confirm by replacing it with a direct `signal?.aborted === true` and observing the
    TS2367 — neither pass did this.
- **Decide the `lpStream` duplication.** `@libp2p/utils` exports `lpStream`, whose `read` runs the
  same byte-at-a-time varint loop `readFramedFromStream` hand-rolls (read it at
  `node_modules/@libp2p/utils/dist/src/stream-utils.js`, immediately after `byteStream`).
  Hand-rolling is defensible — the pinned error text
  `payload too large: <declared> exceeds <maxBytes> byte limit` needs the decoded length and
  `lpStream` surfaces only `InvalidDataLengthError`, and the 9-byte over-cap short-circuit is ours
  — but `lpStream` takes a `lengthDecoder` hook that could capture the declared length on the way
  past. Settle it: keep the hand-roll with a `NOTE:` stating why (both passes lean this way), or
  switch to `lpStream` plus a capturing `lengthDecoder`.
- **Per-byte prefix reads are one `await` each** (up to 9 per frame). Almost certainly noise
  against a network round trip — and note `lpStream` does the same thing, so it is the library's
  shape too. If you do not measure it, write the weaker claim; most likely a `NOTE:` tripwire at
  the site rather than a ticket.
