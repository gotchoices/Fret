### Confirmed sound: the dispatch predicate matches the library's own

`isMessageStream` in `protocols.ts` checks `closeRead` + `addEventListener` + `removeEventListener`
+ `send` + `push` + `log`. That is *exactly* what `@libp2p/utils` itself checks, in two internal
predicates combined — `isValid` (the five-function check, thrown as `InvalidParametersError` from
`byteStream()` when it fails) and `isStream` (`typeof obj?.closeRead === 'function'`, which is what
its `isEOF` branches on). Verified by reading
`packages/fret/node_modules/@libp2p/utils/dist/src/stream-utils.js` directly. So a stream that
passes `isMessageStream` cannot make `byteStream()` throw, and cannot land in `isEOF`'s
multiaddr-connection branch. The ticket's "suggested review focus" question about this predicate is
**answered: it is both necessary and sufficient**, and the iterable fallback for anything else is a
safe (if slower) path rather than an accidental gap.

### Confirmed sound: the new path genuinely closes the lost-event race

This is the substantive correctness question, and it checks out. Reading
`node_modules/@libp2p/utils/dist/src/abstract-message-stream.js`:

- `addEventListener` is overridden: attaching a `message` listener while `readBuffer.byteLength > 0`
  schedules `dispatchReadBuffer()` on a microtask. So `byteStream()`'s own listener attach flushes
  bytes that arrived before that listener existed — the buffered-but-undelivered case the old poll
  was papering over.
- `dispatchReadBuffer()`'s `finally` sets `readStatus = 'closed'` only once the buffer is empty
  *and* `remoteWriteStatus === 'closed'`.
- `byteStream.read()` tests `isEOF(stream)` (= `remoteWriteStatus !== 'writable' &&
  readBufferLength === 0`) synchronously at entry and again after each wake, and only then throws
  `UnexpectedEOFError`.

So the two buffers the old implementation was blind to (libp2p's stream-iterator queue and
`lp.decode`'s accumulator) are gone: there is one buffer, and the end-of-stream test and the byte
supply are the same object. The claim in `readFramed`'s doc comment is accurate.

### Noted, not yet dispositioned

- **`lpStream` already exists in `@libp2p/utils` and runs the same byte-at-a-time varint loop**
  that `readFramedFromStream` hand-rolls (see `lpStream.read` in `stream-utils.js`). Hand-rolling is
  *defensible* — the pinned error text `payload too large: <declared> exceeds <maxBytes> byte limit`
  needs the decoded length, and `lpStream` only surfaces `InvalidDataLengthError` — but `lpStream`
  takes a `lengthDecoder` hook that could capture the declared length on the way past. The next pass
  should settle it: keep the hand-roll with a `NOTE:` stating why, or switch to `lpStream` plus a
  capturing `lengthDecoder`. Leaning keep-with-`NOTE:` (the 9-byte over-cap short-circuit is ours
  too), but it was not decided.
- The 9-byte prefix cap and the `length >= 9` over-cap short-circuit were read and look correct: a
  9-byte varint declares at least 2^56, over every FRET cap, so that throw cannot be premature. The
  one-body-byte over-read in the "complete but larger than 2^53" varint case is harmless because
  that path throws unconditionally. Not independently tested.
