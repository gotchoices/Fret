## What changed

`readFramed` (`packages/fret/src/rpc/protocols.ts`) used to detect end-of-stream with a 20ms
poll (`EOF_POLL_MS`) racing libp2p's one-shot `remoteCloseWrite`/`close` events — a responder
that closed its write end while the caller was still opening its own stream could lose that
event, leaving a truncated-looking read that the poll would (usually) catch, but the mechanism
itself was fragile and mixed two different clocks (an outer per-call timeout plus the poll) with
the caller's own abort signal.

Landed fix, dispatched by a new `isMessageStream` predicate:

- **`byteStream` path** (`readFramedFromStream`, using `byteStream` from `@libp2p/utils`) — for
  real libp2p streams, reads frames at the same layer as the stream's own EOF state instead of
  polling for it.
- **`lp.decode` iterable path** (`readFramedFromIterable`) — for plain async iterables (used by
  most existing test stubs), no poll-less iterator loop.
- Single dispatching `readFramed` picks the path via `isMessageStream`, and unifies the clock:
  finite `timeoutMs` arms one `deadline(timeoutMs, signal)`; `timeoutMs = Infinity` reads under
  the caller's `signal` alone (mandatory in that mode — absence throws at entry, not a hang).
  Previously a caller could arm a whole-RPC deadline *and* hand `readFramed` the same timeout,
  racing two timers a tick apart; now there is one clock per call.
- Removed: `POLL_TICK`, `EOF_POLL_MS`, `ReadEndState`, `remoteFinishedWriting`, and their doc
  comments. `ABORTED` sentinel kept.
- New deps: `@libp2p/utils@^7.0.10` (byteStream), `uint8-varint@^2.0.4` (varint decode for the
  length prefix), both in `packages/fret/package.json` dependencies.
- `isMessageStream(s)` predicate = stream-utils' `isValid` five functions (`sink`, `source`,
  `close`, `abort`, `status`... — whatever `@libp2p/utils` exports as its stream validity check)
  **plus** `closeRead`. This is why every existing test stub still resolves to the iterable path:
  the stub streams in `rpc.request.spec.ts`'s drain tests define `addEventListener` but not
  `closeRead`/`push`/`log`; `rpc.stream-errors.spec.ts`'s stubs have none of the byteStream
  surface either. Only a stub that deliberately presents the full message-stream API would hit
  the new path — none currently do (see *Known gap* below).
- `signalFired(s)` — small module-level helper directly above `readFramed`'s doc comment. Exists
  purely to defeat a TypeScript narrowing false-positive: the entry-point check narrows the
  readonly `signal.aborted`, and a later re-read inside a catch block flags TS2367 ("this
  comparison appears unintentional") without a function-call boundary in between.

## Known gaps — flagged honestly, not papered over

- **No test in this suite forces the actual race the bug was about** (responder closes write end
  while caller is still opening its stream, on a *real* message-stream-shaped stub exercising the
  new `byteStream` path). Every existing stub resolves to the `lp.decode` iterable path per the
  predicate above, so today's green run proves the refactor didn't regress the old (iterable)
  path — it does **not** yet prove the new `byteStream` path handles the forced race correctly on
  its own dedicated test. That forced-race seam test is scoped to the companion ticket
  `implement/15.05-framed-read-tests-and-docs.md` (`prereq: framed-read-false-truncation`,
  already filed, already sequenced after this one). It also carries the close-then-read
  `sendRaw` restoration and the doc update below.
- **`docs/fret.md` still describes the old 20ms EOF poll** (`EOF_POLL_MS`) in the
  libp2p-integration section (search for "20 ms poll" / `EOF_POLL_MS` in that doc) — stale
  relative to the landed code. Doc fix is in scope for the companion ticket
  `15.05-framed-read-tests-and-docs.md`, not this one.
- This ticket's own validation is compile + existing suite only, per its scope — it did not add
  new tests. Reviewer: treat the "no regression in the iterable path" result as a floor, not a
  proof the byteStream path is exercised anywhere yet.

## Suggested review focus

- `isMessageStream` predicate correctness — is checking for `closeRead` + stream-utils' `isValid`
  actually sufficient/necessary to safely pick the byteStream path, or could a real libp2p stream
  fail this check and silently fall through to the iterable path (which would just work via
  `lp.decode`, but worth confirming that's an intentional safe fallback rather than an accidental
  gap)?
- `signalFired` — confirm it's genuinely just a narrowing workaround and not hiding a real
  double-check-race case.
- Single-clock dispatch in `readFramed` (finite vs `Infinity` mode) — confirm every call site
  that used to pass both an outer deadline and `timeoutMs` was migrated to pick exactly one.
