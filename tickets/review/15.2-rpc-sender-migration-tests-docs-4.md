## Findings carried forward (for the `## Review findings` section of the completion ticket)

- **Fixed inline (behavior + docs) — a completed round trip is membership evidence whatever the
  reply says.** `probeMembership` answered `ok: false`, `busy` and `decode-error` with backoff and
  *no* membership signal, while the evidence-strength table in `docs/fret.md` calls a completed
  outbound namespaced RPC strong proof that "the remote served this network's protocol just now".
  Both cannot be right, and the table is: reaching a reply at all means the peer negotiated
  `/optimystic/${networkName}/fret/...`, which only this network's peers serve, so reply *contents*
  are evidence about the peer's load or its encoder and never about which network it belongs to.
  The code was under-promoting, and it was not free: a mislabeled-`foreign` peer that answers
  `busy`, or a version-skewed peer whose replies never decode, could not be recovered by the
  foreign re-probe arm — the one pass that exists to recover it. Resolved at the class rather than
  per arm: one new seam `FretService.noteAnsweredOnProtocol` (membership signal + proof of life, no
  relevance credit and no latency sample for an unusable answer), called from `probeMembership`'s
  and `probeNeighborLatency`'s `ok: false` / `busy` arms and from `noteRpcFailure`'s `decode-error`
  arm — so every `decode-error` caller, routing paths included, inherits it. The passes that
  deliberately score nothing at all (the pooled warm-up fan-out, `fetchAndMergeSnapshot`'s
  answered-badly arm) are unchanged; the table says a completed RPC *may* set `member`, not that
  every site must, and that is now stated. Docs updated in three places: the `MembershipSignal`
  doc-comment table in `fret-service.ts`, the *Evidence strength* section, and the near-pass `busy`
  bullet under *Stabilization and churn handling*.
- **Settled, no action** — `iterativeLookup` dropping its `try`/`catch` around both `sendMaybeAct`
  calls. `rpcRequest` throws only for a malformed peer id; both send targets are filtered by
  `isDialable`, which admits only ids present in `addressKnown` (built from real peerStore ids) or
  accepted by `isConnected` (which swallows the parse error), so a remote-supplied unparseable
  anchor id can never reach the send. Parked as a tripwire `NOTE:` at `fret-service.ts`'s
  `anchorCandidates` filter.
- **Checked, no defect (handoff claim 1)** — the leave fan-out (`sendLeaveToNeighbors`,
  `fret-service.ts` ~1504-1553) still short-circuits on the shutdown budget: both loops keep
  `if (budget.signal.aborted) break;` at the top of each iteration, which is now the *only*
  short-circuit since `sendLeave` returns an outcome instead of throwing. Because the fan-out hands
  `sendLeave` the budget signal as its *caller* signal, a budget expiry surfaces as `cancelled`
  rather than `timeout`, so the new per-send log line stays quiet on an ordinary shutdown
  truncation.
- **Checked, no defect; one doc line fixed (handoff claim 2)** — the near pass's `busy` arm records
  backoff, and the worry that this excludes a busy near peer from the off-ring re-probe arms does
  not bite: those arms select `foreign`-non-dead and `dead` entries, while a near target comes from
  the member-gated `getNeighbors`, so the sets cannot overlap unless the peer is *later* demoted or
  killed — in which case a delay of at most one backoff window before its first re-probe is exactly
  what backoff is for. The routing cost penalty does see it, which is the intended effect.
