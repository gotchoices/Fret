## Verified facts (do not re-check these)

- **`src/store/relevance.ts` was consumed as-is** — it is not in the changeset.
- **Omitting `avgLatencyMs` from the success patch is correct**, not an oversight.
  `recordSuccess`'s own doc states callers supplying no sample must omit `avgLatencyMs` from any
  derived patch. The implementer passes `latencyMs: undefined` and omits the field, so
  `avgLatencyMs` stays `null` and `healthScore` takes the neutral 0.5 penalty — the documented
  behavior in `docs/fret.md` (*Unmeasured latency is `null`, not `0`*).
- **`lastAccess: time` in the failure patch is redundant but harmless.**
  `recordFailure(entry, x, model, time)` already returns `lastAccess: time`, so
  `scored.lastAccess === time`. Collapsing it to `scored.lastAccess` for symmetry with the success
  patch is a one-line cosmetic fix, not a defect.
- **Thread 1 (two clocks) is real and reachable — this is run 2's new finding.**
  `recordContactFailure` scores at its `time` argument; `recordContactSuccess` has no `time`
  parameter and scores at `this.now()` (`scheduler.getCurrentTime()`).
  Read `test/simulation/event-scheduler.ts`: `nextEvent()` assigns `currentTime = evt.time`, so
  inside `run()`'s loop the two clocks *do* agree — `handleRoute(peerId, coord, evt.time)` runs
  with `getCurrentTime() === evt.time`. **But two public paths break that agreement:**
  `processEvent(evt)` (documented as the manual-stepping entry point) calls `handleEvent`
  **directly**, never touching `currentTime`, so a caller-built event carries a `time` unrelated to
  the scheduler's; and `advanceTo(t)` fires due events and then sets `currentTime = t` — the
  *target*, not the last fired event's time — so events it returns are processed against a clock
  already advanced past them. Either way the failure path stamps the event's time while the success
  path stamps a different one, in a harness whose entire value is deterministic replay.
  **Disposition: minor, fix inline.** Give `recordContactSuccess` a `time` parameter, pass `time`
  at both `contactSweep` and `handleRoute` call sites, and delete the `now` dep from `LivenessDeps`,
  its private field, and the `fret-sim.ts` deps literal. That removes the asymmetry and the dep
  together. Re-run the partition spec afterwards — it is the deterministic-replay pin.
