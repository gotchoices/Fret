## What landed

The per-message caps on a received neighbor snapshot (Core 16 successors / 16 predecessors /
8 sample; Edge 8/8/6) were enforced **twice**: once by the snapshot parser wired in at each
call site, and again by a `slice(0, caps.*)` inside each of the two merge loops. Two copies of
one bound is how the two drift. The merge-loop copies are now gone; the parser is the single
enforcement point.

Concretely, in `packages/fret/src/service/fret-service.ts`:

- `mergeAnnounceSnapshot` — dropped `const caps = this.mergeSnapshotCaps()` and its three
  `slice` calls (successors, predecessors, sample).
- `fetchAndMergeSnapshot` — same three, same `const caps` line.
- Both loops **keep** their per-entry `try/catch`. That guard is not a cap: it catches a
  `base64urlToCoord` throw on a wrong-width sample coordinate, and `test/rpc.handler-fuzz.spec.ts`
  pins it directly on the parser-bypassed path.
- `mergeSnapshotCaps` gained a `NOTE:` stating that the parser is the single enforcement point
  and naming both call sites that draw their caps from it (`registerNeighbors` in
  `registerRpcHandlers` for the announce path; the `parse:` option to `fetchNeighbors` inside
  `fetchAndMergeSnapshot` for the fetch path).

No parser wiring was added — both halves were already at HEAD (announce landed in `15.32`, fetch
in `e598b35` / `15.331-rpc-reply-parser-senders`), which is what made the removal safe.

## Tests reworked

Removing the slices broke five existing tests, all of which drove a merge loop with a **raw,
unparsed** over-cap body and asserted the loop truncated it. That premise is gone. Each was
rerouted through the same parser production uses, built from the service's own
`mergeSnapshotCaps()` rather than from literals:

- `test/rpc.handler-fuzz.spec.ts`, `describe('announce snapshot merge caps')` — a `parsed(svc, body)`
  helper was added beside the existing `merge` / `capsOf` accessors; the two counting tests now go
  through it. The old `costs the same whether the parser truncated first or the merge loop did`
  test lost its premise and was **replaced** by its inverse, `leaves the cap entirely to the parser
  — a bypassed body is merged whole`: it hands the merge loop a raw body and asserts every id is
  merged, which is what turns "the cap lives at the parser" from a comment into an observed fact.
- `test/announce-rate-limit.spec.ts` — the ticket predicted only its `mergeSnapshotCaps()`
  deep-equal test was affected. **It was wrong**: two more tests there
  (`caps a core announce to 16/16/8`, `caps an edge announce to 8/8/6`) also drove the raw merge
  and also broke. A `throughParser(svc, snap)` helper was added and both were rerouted. Their
  literal expected sizes (41 / 23) are unchanged, so they still fail loudly if the caps drift.

One new test landed: `drops a sample entry whose relevance is not a finite number`, pinning the
deliberate decision that `parseSample`'s strictness is kept rather than relaxed (see below).

## What a reviewer should check

**The strictness decision, which this change extends to a second path.** `parseSample` drops any
sample entry whose `relevance` is not a finite number. The merge loops read only `id` and `coord`
and never touch `relevance`, so before this change a peer whose relevance encoded as `null` (a
`NaN` at the sender) merged fine on the fetch path. It no longer does. This is a **decision carried
forward from the `15.32` review, not an oversight**: the wire type declares `relevance: number` as
required, so a sender emitting `null` is malformed. The declined alternative was relaxing
`relevance` to a dropped-advisory field via `finiteNumberOr`, matching `size_estimate` /
`confidence` on the same message. Worth a second opinion, since it is the one behavior change here
that is visible to a peer rather than purely internal.

**Reachability of the removed slices.** The argument is that nothing calls either merge loop
without the parser in front of it. Announce: `registerNeighbors` parses in the handler body before
`onAnnounce` fires. Fetch: `fetchNeighbors`' `decode` runs `parseOrThrow(parse, ...)` before
`rpcRequest` returns `ok`. Both loops are `private`. Confirm there is no third caller.

**Known test gaps — deliberately not closed here, tracked as `rpc-snapshot-cap-merge-path-tests`
in `implement/`.** A budget warning cut this run short, so the tests that landed are a floor, not
the plan:

- The announce tests apply the parser **by hand** in the test body. That restates the wiring at
  `fret-service.ts:1033` rather than proving it — a future edit that unwires the parser there
  would leave these green. The plan was to drive the real registered handler via the
  `fakeNode()` / `invoke(protocol, stub, peer)` rig at the top of the fuzz spec.
- **`fetchAndMergeSnapshot` has no cap test at all.** Nothing in the suite drives the fetch path's
  truncation end-to-end, so the claim that its removed slice was redundant rests on reading the
  code, not on a test. This is the largest gap.
- The `relevance: null` drop is pinned at the parser directly, not through either merge path.

Two live complications the follow-up ticket will hit, both established this run and worth knowing
before re-deriving them: `handleAnnounce` **detaches** the merge (so the upsert count is not
deterministic without wrapping `mergeAnnounceSnapshot` on the instance to capture the promise it
returns), and the neighbors handler's `onInbound` → `noteInboundRpc` **also upserts `from`**,
detached, racing the merge's own first upsert. Pre-seeding `from` into the store makes that
short-circuit and the count deterministic.
