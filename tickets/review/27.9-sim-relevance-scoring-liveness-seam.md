## Verified facts (do not re-check these)

- **`src/store/relevance.ts` was consumed as-is** — confirmed by reading the diff stat: the file
  is not in the changeset.
- **Omitting `avgLatencyMs` from the success patch is correct**, not an oversight.
  `recordSuccess`'s own doc states: *"Callers that supply no sample must likewise omit
  `avgLatencyMs` from any patch they derive from the result."* The implementer passes
  `latencyMs: undefined` and omits the field. `blendLatency(avg, undefined)` returns `avg`
  untouched, so `avgLatencyMs` stays `null` and `healthScore` takes the neutral 0.5 penalty.
  This is the documented behavior in `docs/fret.md` (*Unmeasured latency is `null`, not `0`*).
- **`lastAccess: time` in the failure patch is redundant but harmless.** `recordFailure(entry, x,
  model, time)` already returns `lastAccess: time`, so `scored.lastAccess === time`. The explicit
  field restates it. Consider collapsing to `scored.lastAccess` for symmetry with the success
  patch — a one-line cosmetic fix, not a defect.

## Open threads a reviewer must still resolve

Ranked by how likely each is to be a real defect. None has been confirmed or refuted.

**1. The two scoring calls read two different clocks.** `recordContactFailure` scores at its
`time` argument; `recordContactSuccess` has no `time` parameter and scores at `this.now()`
(`scheduler.getCurrentTime()`). In `contactSweep` both are the same value. In `handleRoute` the
failure path uses the event's scheduled `time` while the success path re-reads the scheduler.
Whether those can diverge depends on whether the scheduler's current time equals the time stamped
on the event being processed — **unverified**; read `test/simulation/scheduler.ts` (or wherever
`getCurrentTime` lives) to settle it. If they can diverge, the fix is to give
`recordContactSuccess` a `time` parameter and delete the `now` dep entirely, which also removes
the asymmetry regardless of the answer. That asymmetry — a helper that ignores its caller's clock
while its sibling honors it — is worth removing on maintainability grounds even if no divergence
is reachable today.

**2. `coordOf(selfId)` uses a non-null assertion on `this.peers.get(selfId)`.** Both scoring
helpers call it. In `contactSweep` the sweeping peer is alive by construction. In `handleRoute`
the caller is `current`, a routing peer — **unverified** whether a peer can leave the `peers` map
between a route event being scheduled and being processed. If it can, this throws rather than
degrading. Read `handleLeave` and `handleRoute`'s entry guard to settle it. If unreachable,
replace the bang with a stated failure mode or a comment saying why; if reachable, it is a real
crash and needs a ticket.

**3. `reprobeDeadEntries` restores a dead entry to `disconnected` without scoring it.** Production's
dead arm treats a successful re-probe as proof of life and applies the success path. The sim's
re-probe now sits beside two scoring helpers and does not use either. Decide whether that is an
intended scope boundary (this ticket was the *liveness seam*, and the re-probe is arguably part of
it) or a gap the sibling merge-site ticket will not cover either.

**4. The per-tick whole-store scoring magnitude.** `contactSweep` calls `recordContactSuccess`
for every reachable non-dead entry every tick, so `accessCount` and KDE occupancy grow by one per
entry per peer per tick. Already recorded as a `NOTE:` at `recordContactSuccess` — so this is a
**tripwire already parked**, not a finding to re-file. Confirm the note states the revisit
condition adequately and move on.

**5. No test asserts the scoring does anything.** The implementer says so explicitly. The suite
proves nothing regressed; nothing proves relevance is now non-zero, or that two same-seed runs
agree on it. Decide the disposition: a cheap guard in the sim specs is minor-fix-inline territory
if it is genuinely a few lines; if it needs `capacity` set (which `backlog/debt-sim-eviction-degenerate-blocks-metric-guard`
says would measure eviction instead), it is a ticket arm on that existing backlog ticket rather
than a new one. Check that backlog ticket before filing anything.
