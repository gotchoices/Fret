Implemented half of the simulation relevance-scoring work: the per-peer sparsity model, the
liveness seam that scores proven contact, and the argument changes feeding it. The gossip-merge
scoring sites are the sibling ticket `sim-relevance-scoring-merge-sites`, still to come, and
nothing here depends on it.

Nothing in `src/` changed. `src/store/relevance.ts` was consumed as-is.

## What changed

**`test/simulation/liveness.ts`**

- `LivenessDeps` gained three members, wired through to private fields: `modelFor(selfId)`
  returning that peer's own sparsity model, `coordOf(id)` returning a peer's ring coordinate, and
  `now()` returning sim time.
- `recordContactSuccess(selfId, store, entry)` (new first argument) now scores on **every**
  call rather than only when a strike run existed. It computes the self-to-peer normalized log
  distance, calls `recordSuccess(entry, undefined, x, model, now)` — latency deliberately
  `undefined`, because the sim models no link latency and `avgLatencyMs` must stay `null`
  rather than become a fabricated 0 ms sample — and writes back relevance, lastAccess,
  accessCount, successCount and `contactFailures: 0`. The stale "Written only when there is one
  to clear" doc comment is gone.
- `recordContactFailure(selfId, store, entry, time)` (new first argument) keeps the strike
  arithmetic and the dead transition byte-for-byte, and additionally calls
  `recordFailure(entry, x, model, time)`, writing relevance and failureCount alongside. It now
  stamps `lastAccess` on every failure, where the old code stamped it only on the dead arm.
- `contactSweep` passes `selfId` through both calls.

**`test/simulation/fret-sim.ts`**

- New `private readonly models = new Map<string, SparsityModel>()` beside `stores`. One model
  per peer — a shared model would make every peer's sparsity bonus a function of every other
  peer's observations.
- `addPeer` creates the model. It is the single construction seam — both `initialize()` and
  `handleJoin()` route through it — so every peer gets exactly one, exactly once.
- The `LivenessDeps` literal in the constructor supplies the three new members.
- `handleRoute`'s two scoring calls pass `current` (the deciding peer) as first argument.

## What a reviewer should push on

- **The whole-store per-tick scoring magnitude.** `contactSweep` walks every entry in a peer's
  store each tick and calls `recordContactSuccess` for every reachable non-dead one. So
  `accessCount` and the KDE occupancy grow by one **per entry per peer per tick** — not once per
  modelled RPC. Production's sweep is genuinely proven contact, so sharing the seam is the intended
  design, but the sim's rate is far higher than production's. Consequence: frequency saturates fast
  on long runs. Recorded as a `NOTE:` at `recordContactSuccess`. Not measured against a specific
  run length — a reviewer wanting the number should count `store.size()` × ticks for the suite in
  question.
- **Two different clocks reach the two scoring calls.** Failure scores at the `time` argument
  the caller passes; success scores at `this.now()` (`scheduler.getCurrentTime()`), because
  `recordContactSuccess` has no `time` parameter. Both are sim-clock and deterministic, and in
  `contactSweep` they are the same value, but in `handleRoute` the failure path uses the event's
  scheduled `time` while the success path re-reads the scheduler. Worth confirming those cannot
  diverge; if they can, give `recordContactSuccess` a `time` parameter and delete the `now` dep.
- **`lastAccess` is now stamped on every failure, not only the dead one.** That reorders
  `reprobeDeadEntries`, which sorts ascending `lastAccess`. The partition spec passes, which is
  the evidence, but it is the change most likely to have moved a threshold quietly elsewhere.
- **`modelFor` and `coordOf` use non-null assertions** (`this.models.get(selfId)!`,
  `this.peers.get(id)!.coord`). `coordOf` matches the existing `enforceCapacity` idiom.
  `modelFor` is safe because `addPeer` is the only construction seam, and a departed peer keeps
  its model entry (same memory note `handleLeave` already carries for `stores`), so neither can
  be undefined today. A reviewer may still want a stated failure mode rather than a bang.
- **Churn tolerance.** `contactSweep` prunes departed ids mid-walk, so a scoring helper that
  re-read `getById` after a removal would meet `undefined`. Neither helper re-reads — both take
  the `entry` handed to them — so this is currently unreachable. Confirm that stays true if the
  merge-site ticket adds a helper.
- **`capacity` is unset in every existing sim spec**, so scoring writes relevance but nothing
  evicts on it, and no existing threshold moved. The eviction ranking stays degenerate until a
  spec sets `capacity` — see `backlog/debt-sim-eviction-degenerate-blocks-metric-guard`.

## Known gaps (not done here, by design)

- Gossip-merge scoring sites and the `enforceCapacity` comment rewrite belong to
  `sim-relevance-scoring-merge-sites`. That ticket also adds `initialRelevance`, `touch`,
  `observeDistance` and `normalizedLogDistance` to the `fret-sim.ts` relevance import, and
  scores the self entry that `addPeer` seeds. That self entry is **currently unscored** —
  relevance 0 from `upsert` — which is correct as of this ticket but is the first thing to check
  after the sibling lands.
- No test asserts relevance is now non-zero in the sim. The suite proves nothing broke; it does
  not prove the scoring is doing anything. A cheap guard (run a few ticks, assert some entry has
  relevance > 0 and that two same-seed runs agree on it) would turn this from "did not regress"
  into "works", and does not exist.
