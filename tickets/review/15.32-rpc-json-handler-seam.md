## What shipped

`registerJsonHandler` (`src/rpc/protocols.ts`, immediately after `registerRpcHandler`) — two
overloads stacked on `registerRpcHandler`, which still owns the budgeted success close and the
synchronous error abort:

- **Request form** (`{ maxBytes, parse, serve, onMalformed?, closeBudgetMs? }`) — reads the framed
  body, decodes it, runs a `Parser<T>` from `src/rpc/validate.ts`, then calls
  `serve(msg, connection)`. `serve` returning `undefined` drops without replying.
- **Reply-only form** (`{ serve, closeBudgetMs? }`) — reads no body at all. `'parse' in opts` is the
  runtime discriminator, and TypeScript narrows on it.

The **drop/abort rule** is documented once at the function: frame-level failures (truncation,
`PayloadTooLargeError`, a reset) propagate and abort; body-level failures (undecodable JSON,
non-object top level, parser rejection, identity mismatch) return normally so the seam closes, with
`onMalformed('decode' | 'parse')` counted first.

Migrated: `registerLeave`, `registerNeighbors` (both the request and the announce protocol),
`registerPing`. `registerMaybeAct` deliberately stays on `registerRpcHandler` — its rate-limit
bucket must precede all per-message work and the seam parses inside the handler body. A `NOTE:` at
its registration in `FretService.registerRpcHandlers` says so.

Signature additions (both trailing, so existing positional callers still compile):

- `registerNeighbors(..., snapshotParser = makeSnapshotParser({∞, ∞, ∞}), onMalformed?)`
- `registerLeave(..., onMalformed?)`

`FretService.registerRpcHandlers` supplies `makeSnapshotParser(this.mergeSnapshotCaps())` and wires
both `onMalformed` hooks to `this.diag.rejected.malformed++`.

## Behavior changes to check, not assume

1. **A leave/announce body that will not decode or parse is now a close-drop, not an abort.** This
   is the plan's intent ("a validator failure must be a drop, never an abort"). Two rows of the wire
   matrix in `rpc.handler-fuzz.spec.ts` flipped from `abort` to `drop`, and the unit-tier
   `aborts once on a non-JSON leave body` was renamed and flipped.
2. **Diagnostics shift.** A leave with a non-finite `timestamp` now counts `malformed` where it
   counted `timestampBounds` (the parser rejects before `handleLeave`'s freshness check). Same for
   an announce with a non-finite `timestamp` or an unparseable `from`. Announce and leave decode /
   parse failures now count `malformed` at all, which they never did before. Appending these new
   writers to `tickets/backlog/debt-rejection-diagnostics-conflated` is `15.325`'s job, not this
   ticket's.
3. **`parseLeaveNotice` now runs before `bucketLeave`.** A `NOTE:` at `handleLeave` states why that
   is acceptable (4096-byte cap, O(message size) parse, no hashing) and that the bucket must stay
   first *inside* `handleLeave`.
4. **Fixture ids.** `parseLeaveNotice` / `makeSnapshotParser` reject a `from` that is not a
   parseable peer id *before* the identity check, so the spec's placeholder ids (`'peer-a'`,
   `'peer-impostor'`, `'someone-else'`) no longer reach the path they were written to test. The spec
   now builds real ones with a local `peerIdStr(seed)` helper (identity multihash over a protobuf
   Ed25519 public key, base58btc-encoded). Used in three unit cases and in the two wire-matrix
   `from mismatch` rows. The matrix's diagnostics assertion now splits body-level drops into parser
   drops (`malformed`) and identity drops (`identityMismatch`) rather than attributing all of them
   to the latter.

## Two changes NOT in the original ticket

Both came out of test failures, both are real, and both want a reviewer's eye.

### (a) A reply-only `serve` must not be an `async` arrow — weakest part of this change

Migrating `registerPing` **alone** broke `test/churn.leave.spec.ts` → *the classification pass
probes and promotes a replacement recorded by a leave* (`pingsSent 1, pingsOk 0, pingsFail 1`).
Isolated by reverting `ping.ts` to HEAD with every other file migrated: that one file is the cause.

Root cause: `sendPing` writes **no request body**, and `openRpcStream` pins `negotiateFully: false`,
so the reply is the first thing on the stream. Wrapping the handler body in the seam added roughly
two extra microtask hops before the frame was written, and that was enough to lose it. HEAD was
already winning this race by a hair.

Fix: both reply-only serves (`ping.ts`, and the neighbors request in `neighbors.ts`) return the
inner promise directly instead of being `async` arrows, with a comment at each site saying why. That
restores HEAD's hop count.

**Review this hardest.** It is a latency-shaped fix for what is really a negotiation-timing
fragility in the bodyless-request pattern. Nothing enforces the hop count, so a later edit that adds
an `await` there can reintroduce it silently, and the only symptom is a `decode-error` / failed ping.
A durable fix is out of scope here — it means either `sendPing` writing a request body, or
`rpcRequest` completing negotiation before the responder can reply. If this is worth filing, the
root site is `src/rpc/request.ts` / `openRpcStream`'s `negotiateFully: false`, not the handlers.

### (b) The wire-tier harness now reads before releasing

`sendRaw` in `rpc.handler-fuzz.spec.ts` did `send` → `await stream.close()` → `readFramed`. With the
reply-only handlers even marginally slower, the reply landed after the close had torn the read side
down, and every reply-only row reported a spurious `eof`. `sendRaw` now starts the read first, then
half-closes concurrently, and awaits both — which is what `rpcRequest` does, and which also stops
the receiver's own budgeted close from stranding (it waits on the caller's write end). A comment at
the site explains both directions of the ordering constraint.

This narrows coverage: the "sender fully closes before reading" shape is no longer exercised.
Nothing in FRET does that, but it is a deliberate narrowing rather than an accident.

## Known gaps — a floor, not a finish line

- **No test asserts `onMalformed` fires with the right `reason`.** The wire matrix asserts the
  aggregate `diag.rejected.malformed` delta only; nothing distinguishes `'decode'` from `'parse'`.
- **No test covers the reply-only overload in isolation** — it is exercised only through ping and
  the neighbors request, and the `'parse' in opts` discriminator has no direct unit test.
- **`registerJsonHandler` is not exported from `src/index.ts`,** though `registerRpcHandler` is
  (external consumers wrap their own protocols over it). Whether the new seam should join it is an
  open call this ticket did not settle.
- **`mergeSnapshotCaps()` still returns a structural literal type**, not `SnapshotCaps`. Widening it
  is explicitly `15.33`'s item; it compiles today because the shapes match.
- **The `Infinity`-cap default parser on `registerNeighbors`** is exercised only by the existing test
  callers that omit the argument. Nothing asserts that "validate the shape, truncate nothing" is
  what those callers actually get.
- The ping fragility in (a) lives in code comments only. No test targets it; the churn.leave case
  caught it this time by accident of timing.
