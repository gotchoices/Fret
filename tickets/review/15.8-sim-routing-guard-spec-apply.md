## Established — do not re-derive

**Baseline: all four cases pass.** Ran
`node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/simulation.routing.spec.ts" --timeout 60000`
from `packages/fret` — 4 passing (45s). Logged figures: dense n=200 knows 60.0% / success 100% /
p90 2 / max 2; sparse n=1000 19.3% / 95% / 2 / 3; churn 17.0% / 99% / 2 / 3. All inside the
thresholds and inside the ranges the spec header claims.

**The fourth case is vacuous** (established by the prior run, by measurement): "a route whose
originator is already the peer nearest the target still succeeds" completes all 20 of its routes at
hop 0, and the selector is never called. Deleting the `hops > 0` split at
`test/simulation/fret-sim.ts:887` — the exact behavior the case says it catches — leaves it passing
20/20.

**Root cause, and why the rewrite directions in the previous ticket do not work either.** In
`FretSimulation.handleRoute` the anchor check (`test/simulation/fret-sim.ts:844-850`) runs *before*
any hop is chosen: if the deciding peer is the successor or predecessor of the target coordinate in
its own store, the route is recorded successful at once. The entry nearest a coordinate by
shorter-arc distance *is* either that coordinate's successor or its predecessor — so **locally
nearest implies hop-0 termination**, and the selector is never reached.

The strict-improvement floor only removes anything when no candidate is closer to the key than the
deciding peer, i.e. exactly when that peer is locally nearest. Therefore, in this harness:

- Routing from the globally nearest peer terminates at hop 0 — the present case.
- Routing from a near-but-not-nearest peer leaves a strictly closer candidate in the pool, so the
  floor excludes nothing and supplying `selfCoord` at hop 0 changes no outcome — the first rewrite
  direction the previous ticket suggested is vacuous for the same reason.
- The one corner where the split is observable is contrived: a store whose nearest entry to the key
  is `dead`, so the *unfiltered* anchor read does not fire while the *filtered* candidate pool holds
  only entries farther than self. That is partition mechanics, not originator behavior.

So the originator/forwarder split is **not observable in this simulation at all**. It is a fidelity
choice — the sim models production's rule — and production's floor is already pinned directly, as a
`fast-check` property over arbitrary pools, in `test/nexthop-cost.spec.ts`.

**Settled judgement calls** (both were left open by the previous ticket):

- *DRY — the spec's local ring arithmetic.* Keep it independent of `src/ring/distance.ts`: the
  scenario oracle must not be the code under test. But three of the local helpers are duplicates of
  *other test* helpers, which the independence argument does not cover — `toBigInt`
  (`simulation.routing.spec.ts:223`) duplicates the exported one at `test/helpers/ring.ts:43`;
  `ringDistance` (`:229`) duplicates spec-local `refMinDistance` at `test/ring.properties.spec.ts:57`;
  `coordFromBigInt` (`:50`) duplicates module-private `bigintToCoord` in `fret-sim.ts`, `toCoord` in
  `ring.properties.spec.ts:46` and `bigIntToCoord` in `size-estimator.spec.ts`. `test/helpers/ring.ts`
  exists precisely so specs stop hand-rolling coordinate arithmetic. Decision: land `toCoord` and
  `refMinDistance` there (documented as sharing no code with `src/`), import all three into the
  routing spec, and leave the other specs' copies alone — they are outside this diff.
- *`report()`'s `console.log`.* Not a finding. It is house style for the simulation specs
  (`churn-scenarios.spec.ts` and `sim-profiles.spec.ts` log the same way), and the spec header
  depends on it — it cites the per-case knowledge figure as how a reader re-derives the thresholds.
  Keep as is.

**Partition replay.** `test/simulation.partition.spec.ts:476` compares `JSON.stringify` of the whole
`SimMetrics` across two identically-scripted runs, so a newly added `successfulRouteHops` is present
and identical in both by construction — expected fine, still unrun here.
