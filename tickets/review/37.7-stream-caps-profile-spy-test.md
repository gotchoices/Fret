## What landed

One new spec, `packages/fret/test/rpc.stream-caps-profile.spec.ts` (5 cases, all passing).

It replaces `node.handle` / `node.unhandle` on a memory-transport node with recorders, then
asserts what `FretService` actually hands libp2p:

- **Profile split, per profile (`core`, `edge`).** Calls the private `registerRpcHandlers()`
  directly and asserts the registration log carries **all five** protocols — `neighbors`,
  `neighbors/announce`, `maybeAct`, `leave`, `ping` — once each, every one at that profile's caps
  (Core `{maxInboundStreams: 128, maxOutboundStreams: 256}`, Edge `{32, 64}`). The five are
  asserted as a **set**, not a count, because `registerNeighbors` registers two of them and the
  announce one only when `onAnnounce` is supplied; a count could be satisfied by a duplicate.
- **start → stop → start, per profile.** Drives the real lifecycle: asserts the caps after the
  first `start()`, that `stop()` unhandles all five and registers nothing, and that the second
  `start()` re-applies the same caps. Caps applied once at construction would silently vanish
  here.
- **Optional caps for an external caller.** Registers a consumer protocol through the
  root-exported `registerRpcHandler` with an options bag carrying **no** cap fields. Its real
  value is that it type-checks; the runtime half asserts omitting them forwards `undefined`
  rather than fabricating a default.

Expected cap numbers are pinned as **literals**, not read back out of `FretService.streamCaps()`,
so the expectation is not derived from the thing under test.

The "verify first" item from the implement ticket is answered and is now load-bearing rather than
merely believed: `registerRpcHandler` (`src/rpc/protocols.ts:154`) passes
`{maxInboundStreams, maxOutboundStreams}` as `node.handle`'s third argument under exactly those
names, and `registerJsonHandler` stacks on it and forwards the same two fields. That is why a spy
on `node.handle`'s third argument is a valid reading of the split.

## Known gaps — read these before signing off

- **A spy proves the value reached `node.handle`; it does not prove libp2p then enforced it.**
  That is the sibling spec's job: `test/rpc.stream-caps.spec.ts` (landed by
  `stream-caps-enforcement-test`) holds four concurrent requests against a handler registered at a
  rigged `maxInboundStreams: 2` and counts two admitted, two refused, over both memory and
  TCP+noise. Neither spec subsumes the other, and the new file's header comment says so; the pair
  is the whole claim. **Nothing anywhere asserts that the *shipped* 128/256 and 32/64 are
  enforced** — only that they are requested, and that *some* cap is enforced. Standing that up
  would need 33+ concurrent streams on one connection and was not attempted.
- **`node.handle` is stubbed, so no protocol is ever really registered in these cases.**
  `unhandle` is stubbed for the same reason (unhandling what libp2p never saw would measure the
  registrar's tolerance, not the service). Consequence: the lifecycle case exercises `start()` /
  `stop()` against a node with no live inbound handlers. Leave fan-out and stabilization still run
  against an empty store; nothing observed suggests that weakens the assertion, but it is a
  simulation of the lifecycle, not the lifecycle under load.
- **The spy stubs are not restored.** Each case builds its own node in `beforeEach` and stops it
  in `afterEach`, so nothing leaks between cases — but a future case reusing a node would inherit
  a recorder. Stated in the helper's doc comment.
- **The external-caller case pins optionality only for `registerRpcHandler`,** not for
  `registerJsonHandler`'s two option interfaces (`JsonRequestHandlerOpts` /
  `JsonReplyOnlyHandlerOpts`). Those fields are optional by declaration
  (`src/rpc/protocols.ts:171-182`) and `tsc --noEmit` is clean, so the compile-time claim holds —
  but no case *drives* `registerJsonHandler` with cap fields omitted. A reviewer wanting that
  symmetry would add one case.
- **`test/package-exports.spec.ts` was not modified.** It already guards the reachability of the
  root-exported `registerRpcHandler` / `registerJsonHandler` surface, and the new case imports
  `registerRpcHandler` from `../src/index.js` rather than from the module, so the root export is
  exercised — but the "still compiles for an external caller" claim rests on `tsc`, not on that
  spec.
