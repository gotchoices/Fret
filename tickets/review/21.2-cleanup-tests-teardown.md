Implement stage of `21.2-cleanup-tests-teardown` (arm 2 of 4 from `plan/21-cleanup-tests`).

## What shipped

**New `test/helpers/cleanup.ts`.** `useCleanup(): Cleanup` builds a per-case teardown registry and
installs the `afterEach` that unwinds it. A case calls `cleanup.add(fn)` *as it builds* each
resource instead of stopping it on the last line. Entries unwind newest-first (services before the
nodes under them) and each entry is best-effort: a throwing `stop()` is **logged** (`console.error`)
and cannot strand the entries behind it. That is the ticket's `Promise.allSettled` requirement
expressed as a sequential loop — teardown order is load-bearing here, so the steps cannot run
concurrently, and the failure is surfaced rather than swallowed.

Registering at *construction* time rather than at the end of the body is the load-bearing half: it
also covers a throw from the setup statements that follow. `useCleanup()` must be called inside the
`describe` it serves — called at module scope it attaches to mocha's root suite and the (empty,
harmless) hook then runs after every test in the whole run. That constraint is documented on the
function.

**`MeshOptions.cleanup`.** `buildMesh` / `starMesh` accept the registry and register `mesh.stop()`
the moment the mesh exists, so the leak is structurally unwritable for any spec that opts in — a
spec author cannot forget a teardown the helper owns.

**Migrated four specs** off last-line teardown: `maybeact-dedup-phases` (5 manual pairs + 1
hand-written `try/finally`), `proactive-announce` (5 sites incl. a `try/finally` and a stranding
`Promise.all([edgeMesh.stop(), coreMesh.stop()])`), `network.isolation` (2 sites; rewritten onto
`buildMesh` + `connect('line')`, which reproduces its B-dials-A-before-services order exactly),
`route.maybeact.integration` (1 site).

**Two stranding `Promise.all` teardowns removed.** `proactive-announce`'s two-mesh case now lets the
registry stop each mesh in turn. `stopAll` (`helpers/libp2p.ts`) and `mesh.stop()`'s service loop
now log their caught errors instead of discarding them silently.

## Known gaps — treat these as starting points, not a finished floor

- **`profile.behavior.spec.ts` was left on its own local registry.** It already had the correct
  pattern (that local registry is what `cleanup.ts` was extracted *from*), so it never leaked. It is
  now a duplicate of the shared helper, which is a live DRY violation. It was not migrated because
  its four setup helpers (`createService`, `starRig`, `startService`, `startNode`) sit at module
  scope and close over the module-level array, while `useCleanup()` must be called inside the
  `describe` — so the migration means moving those four functions inside the describe body too.
  Mechanical, ~35 lines of re-indentation, no behavior change. A reasonable inline fix for review.
- **`cleanup.ts` itself has no test.** Nothing asserts the reverse-order unwind, the
  registry-emptied-after-run behavior, or that a throwing step is logged-and-continued rather than
  aborting the remaining steps. The helper is exercised only indirectly by the specs that use it.
  Worth a small direct spec.
- **Deliberate-failure injection was run on one case, not five.** The hardest case was chosen
  deliberately (see above), and the mechanism is shared by all of them, but the other four files
  were not individually failure-injected.
- **`buildMesh`'s pre-existing construction-throw hole is unchanged.** Its existing `NOTE:` still
  stands: if the node factory or `node.start()` throws on iteration *j*, nodes `0..j-1` are stranded
  because the mesh object does not exist yet and so nothing has been registered. Unreachable unless
  in-memory node construction itself fails; out of scope here, but the registry does *not* close it.
- **`network.isolation.spec.ts` service-start ordering shifted slightly.** It previously constructed
  both services then started A then B; `addServices` constructs-and-starts index 0, then index 1, so
  svcB is now constructed after svcA has started. Both cases pass, but it is a real (small) change
  in the order the file used to exercise.
