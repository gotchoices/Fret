## What landed

`runPooled<T>(tasks, { concurrency, signal? })` in `packages/fret/src/utils/pool.ts`, matching
the interface specified in the ticket exactly:

```ts
export type PoolResult<T> =
	| { status: 'fulfilled'; value: T }
	| { status: 'rejected'; reason: unknown }
	| { status: 'skipped' }

export interface PoolOptions {
	concurrency: number
	signal?: AbortSignal
}

export function runPooled<T>(
	tasks: ReadonlyArray<() => Promise<T>>,
	opts: PoolOptions
): Promise<Array<PoolResult<T>>>
```

Shape, as specified: a shared index cursor plus `min(concurrency, tasks.length)` worker loops.
Each worker checks `signal.aborted` before pulling a task; if aborted it marks that index
`skipped` and keeps draining the cursor (rather than stopping), so the returned array is always
dense and `tasks.length` long. A task that throws synchronously is caught by the same
`try`/`catch` as an async rejection — nothing escapes `runPooled` itself, and the returned
promise never rejects.

`concurrency` is clamped: non-finite (`NaN`, `Infinity`), zero, or negative → 1; fractional
values floor (e.g. `2.9` → 2) via `Math.max(1, Math.floor(...))`, following the same pattern as
`ExpiringMap`'s capacity clamp. `tasks.length === 0` short-circuits to `Promise.resolve([])`
before any worker is spawned.

One implementation note worth flagging for review: `runPooled` is a plain (non-`async`)
function that spawns its worker loops synchronously, before returning — calling
`tasks[index]()` inside a worker runs the task body synchronously up to its first internal
`await`. This is what makes "already-started tasks settle on abort" deterministic to test
without extra scheduling ticks (see the abort test below), but it's a subtle enough property
that a future refactor to an `async function runPooled` wrapper would silently break it (the
first workers would no longer be guaranteed to have claimed a task by the time the caller's
next line runs). Worth an eye during review.

## Tests — `test/pool.spec.ts` (8 tests, all passing)

- **Concurrency bound** (`fast-check`, 200 runs): tasks self-report an in-flight counter;
  asserts `maxInFlight <= concurrency` for every generated `(concurrency, delays[])` pair, and
  asserts on the generated distribution — both the "more tasks than concurrency" region and the
  "bound actually saturated" region are proven reached, not just possible, matching the house
  pattern in `nexthop-cost.spec.ts` / `peer-discovery.spec.ts`. Resolution order is varied by
  giving each task a random number of `await Promise.resolve()` microtask hops rather than real
  timers, so the suite stays fast and leaves nothing for the mocha exit watchdog to catch.
- **Result shape**: one test mixing a resolving, an async-rejecting, a *synchronously-throwing*,
  and a second resolving task at `concurrency: 2`, asserting index-aligned status/value/reason
  for all four.
- **Abort mid-run**: `concurrency: 3` over 6 tasks gated by per-task deferred promises. Asserts
  the first 3 have already started (synchronously, before `controller.abort()` is even called —
  see the implementation note above), that aborting then releasing the gates yields `fulfilled`
  for those 3 and `skipped` for the other 3, and that no fresh index is ever pulled after abort.
- **Degenerate concurrency**: zero, negative, `NaN`, `Infinity` each clamp to a single worker
  (verified via the same in-flight counter, `maxInFlight === 1`). Fractional flooring (`2.9`→2)
  is exercised structurally by the clamp implementation but has no dedicated test — the ticket's
  test list only called out zero/negative/non-finite; flag if review wants an explicit case.
- **Empty list**: `runPooled([], ...)` resolves to `[]`.

## Known gaps / not covered

- **No test exercises `runPooled` at real scale (hundreds of tasks) or under a genuinely slow
  task** — everything here is microtask-timed for suite speed. The concurrency-bound property
  test is the closest thing to a stress test; it caps at 24 tasks / 6 concurrency per the
  `fast-check` generators.
- **Nothing in the service imports this yet.** `pool.ts` is untouched by every other module in
  `src/` (checked: no imports found outside its own test file), so this ticket has no
  integration risk of its own — all integration risk belongs to `7.6-stabilize-tick-concurrency`,
  which should test the wiring, not re-test the primitive.
- Not attempted: any behavior around a task's *own* internal timeout/cancellation — `runPooled`
  takes no opinion on that, by design (see the doc comment: "the pool never aborts on its own —
  cancellation is entirely the caller's").
