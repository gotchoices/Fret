**The implementer's central claim about libp2p holds against the real implementation, not only
against the stub.** The handoff called this "a reading of the interface, not an observation of the
implementation" and named it the highest-value thing for a reviewer to check. Checked, in
`node_modules/@libp2p/utils/dist/src/abstract-stream.js` and `abstract-message-stream.js`:

- `AbstractStream.close(options)` sets `writeStatus = 'closing'` **before** it awaits anything,
  then awaits `pEvent(this, 'idle', options)` / `pEvent(this, 'drain', options)` /
  `sendCloseWrite(options)` — each of which receives the caller's `AbortOptions`. So a close
  bounded by a signal does reject on that signal, and the write end is left at `'closing'`, never
  `'closed'`. That is exactly the state `registerRpcHandler`'s catch arm needs
  (`writeStatus !== 'closed'`) for its abort to run. The claim is sound.
- `close()` early-returns when `writeStatus` is already `'closing'` or `'closed'` — so a handler
  that closed for itself is not released twice, as documented.
- **`close()` does *not* abort the stream when it rejects.** It leaves the stream half-open. So the
  follow-up `abort()` added in both `releaseRpcStream` and the handler seam is load-bearing, not
  belt-and-braces: without it a bounded close that rejects frees the caller and leaks the stream
  slot. Both arms of the fix are justified.
- `abort()` is self-guarded (`if status is aborted / reset / closed, return`), so an extra abort
  is a no-op rather than a double release.

**The ordering the doc comment depends on is real.** All five sender call sites release from a
`finally` *before* `d.cancel()`, so the deadline is still live when its signal is handed to
`releaseRpcStream`: `ping.ts:127-128`, `neighbors.ts:108-109`, `neighbors.ts:146-147`,
`maybe-act.ts:106-107`, `leave.ts:89-90`. If a future sender inverts this the bound silently
disappears with no test failing — see the tripwire suggestion below.

**Arm (a)'s "the loop needs no change" is arithmetically correct.** With `timeoutMs = Infinity`:
`deadlineAt` is `Infinity`, `remaining` is `Infinity` so `remaining <= 0` never fires,
`Math.min(Infinity, EOF_POLL_MS)` is 20, and the `read timed out` throw is unreachable.

### 1. `readFramed` does not validate `timeoutMs`, and `NaN` is worse than the handoff said

The entry guard added by arm (a) tests `timeoutMs === Infinity` exactly. The handoff described the
`NaN` case as "the read runs unbounded with no error". Reading the loop, it is worse than that:
`Math.min(NaN, EOF_POLL_MS)` is `NaN`, and `setTimeout(fn, NaN)` clamps the delay to zero — so the
poll loop spins at roughly one iteration per event-loop turn, re-running `remoteFinishedWriting`
each time, for as long as the stream stays open. That is a hot spin, not a quiet hang.

Not reachable from any current caller (every call site passes a module constant), but `readFramed`
is exported from the package root, so a consumer computing a timeout from config can reach it.

Judgement to make: this is a one-line widening of a guard that already exists three lines above
(`if (!(timeoutMs > 0)) throw ...` covers `NaN`, `0` and negatives; the `Infinity` clause stays as
it is). Check first whether any test or caller deliberately passes `0` — the prior run did not get
to that grep. If nothing does, this is a minor finding to fix inline in the review pass rather
than a ticket. Per the *Architecture first* ladder it sits at rung 1/3 — validating a seam's own
input so the bad state cannot enter — which is why it is worth doing rather than filing.

### 2. Close-budget expiry is indistinguishable from a handler fault in the logs

Already flagged by the implementer and not fixed. When the budgeted success close expires, it
rejects into `log.error('%s handler error - %e', protocol, err)` carrying a
`DeadlineExpiredError`. Factually a handler error; but an operator cannot separate "the peer
accepted our reply and stopped reading" from "the handler threw on a malformed message", and those
call for opposite responses. Not a defect. Either fix inline (the catch arm can test
`err instanceof DeadlineExpiredError` and log a distinct line) or record why not.

### 3. Every inbound RPC now arms and cancels a timer, including the common no-op case

`registerRpcHandler` mints a `deadline(closeBudgetMs)` — an `AbortController` plus a `setTimeout`
— on the success path of every inbound message, then cancels it in a `finally`. When the handler
already closed its own write end (check whether the five FRET handlers do; the prior run did not
confirm this), `stream.close()` early-returns immediately and the timer is pure per-message
overhead.

This reads as a tripwire rather than work: correct today, and the allocation is small against a
Core inbound cap of 16 concurrent maybeAct. If it is confirmed that the handlers close for
themselves, the natural home is a `NOTE:` at the close site saying the budget is armed for the
minority path and what to measure if inbound cost ever shows up in a profile. Do not file a ticket
for it.
