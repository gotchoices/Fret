- `liveness.ts` — `LivenessDeps` gained `modelFor(selfId)` and `coordOf(id)`.

## Already done and verified — do not redo

- **Two clocks (fixed, run 3).** `recordContactSuccess` scored at an injected `now()` while
  `recordContactFailure` scored at its `time` argument; those disagree on the scheduler's
  `processEvent` and `advanceTo` paths. `recordContactSuccess` now takes `time`, both call sites
  pass it, and the `now` dep is gone from `LivenessDeps`, the private field and the deps literal.
  Verified: `npx tsc --noEmit` clean, and `simulation.partition.spec.ts` +
  `simulation.routing.spec.ts` green (13 passing, 46 s) including deterministic replay.
- **Non-null assertions (settled and documented, run 5).** `modelFor(selfId)` and `coordOf(id)`
  bang on `this.models.get` / `this.peers.get`. Both are **unreachable as crashes**: `handleLeave`
  only sets `alive = false` and nothing anywhere deletes from `peers`, `stores` or `models`, and
  both deps are only ever called with an id the harness is itself sweeping or routing from. A
  comment at the deps literal states that, and `handleLeave`'s existing "reclaim here if memory
  runs out" NOTE now warns that reclaiming would turn both into crashes. No ticket.
- **Docs corrected (run 5).** `docs/fret.md`'s *Testing strategy* routing bullet claimed the sim's
  eviction is degenerate because "every entry ties at relevance 0" — no longer true once the sweep
  scores every reachable entry. The bullet now says eviction is still degenerate but for the store
  *shape* (unbounded stores plus a per-tick full-window gossip merge), not for tied scores. The
  rest of that section was read and still matches the code.
- **Per-tick whole-store scoring magnitude** is parked as a tripwire `NOTE:` at
  `recordContactSuccess` with a revisit condition. Adequate; do not re-file.
- Omitting `avgLatencyMs` from the success patch is **correct** per `recordSuccess`'s own doc, not

- `npx tsc --noEmit` is clean at the current tree (checked after every edit above).

## Still to do

- **The one open behavior question: `reprobeDeadEntries` scores nothing.** It restores a dead entry
  to `disconnected` and clears `contactFailures`, but applies no success scoring — so a recovered
  entry keeps the relevance its failures decayed and never earns any back, while production's dead
  arm treats a successful re-probe as proof of life and scores it. The sim's re-probe now sits
  beside two scoring helpers and uses neither. **Prior analysis, so this need not be re-derived:**
  the one-line fix is to call `this.recordContactSuccess(selfId, store, entry, time)` on the
  reachable branch (it already zeroes `contactFailures`, so that patch member becomes redundant),
  ordered so the `state: 'disconnected'` write is not clobbered. Risk is not correctness but
  churn — it changes stored relevance, which feeds `lastAccess` ordering and any capacity-set
  spec, so it must not land without the full run below. If it is judged out of scope instead, say
  so at the site as a `NOTE:` with a revisit condition rather than leaving it silent.
- **No test asserts the scoring does anything.** The implementer says so. Nothing proves relevance
  is non-zero after a sweep, or that two same-seed runs agree on it. A few-line guard in a sim spec
  is inline-fix territory. Note there are three open downstream tickets on this exact theme —
  `tickets/implement/28-sim-relevance-scoring`, `27.95-sim-relevance-scoring-merge-sites`, and
  `28.5-sim-metric-guard-case` — so read those before writing anything, and prefer an arm on one of
