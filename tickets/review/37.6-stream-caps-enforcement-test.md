New spec `packages/fret/test/rpc.stream-caps.spec.ts`. No behavior change anywhere — the only
`src/` edit is a corrected comment (see *Documentation corrections*).

## What the test does

Two in-memory nodes, one connection, one handler registered directly through `registerRpcHandler`
at `maxInboundStreams: 2`. The handler parks on a gate, so admitted streams are all held open at
once; four concurrent `rpcRequest` calls (each with a `decode`, so the sender stays parked reading)
are fired over that single connection. A poll waits until every request has either entered the
handler or already failed — that sum is the observation window in which the cap is binding — then
the gate opens and the admitted requests complete.

The whole case runs twice, once per transport: `createMemNode` (memory + plaintext + yamux) and
`createMemoryNode` (TCP + noise + yamux). The second was added deliberately: "what does the sender
see" is a transport/muxer teardown question, so pinning it on one transport would pin one muxer's
shape rather than the behavior.

## The two observed facts (both measured, neither derived from libp2p source)

- **No off-by-one. `maxInboundStreams: N` admits exactly N concurrent inbound streams** per
  protocol per connection. At cap 2 with 4 concurrent requests: 2 admitted, 2 refused, on both
  transports. So the stream being admitted is not yet in the collection `countStreams` filters when
  `streamCount > limit` is evaluated.
- **A remote's inbound-cap refusal reaches the sender as `decode-error`, not `unreachable`.** Exact
  identity: `FrameTruncationError: stream ended before a framed message arrived`. The remote aborts
  the muxed stream, and what arrives is end-of-stream rather than a reset, so `readFramed` raises
  truncation and `classify()` takes the `isFrameTruncationError` arm.

The second fact **contradicts a claim that was written into both the code and the design doc**. The
practical difference matters: `noteRpcFailure` treats `decode-error` as relevance decay with **no
contact strike**, so a peer refusing at its inbound cap is *not* escalated toward `dead`. The harm
the residual warned about does not occur on either transport tested.

## Documentation corrections made

Both were stating the unverified prediction as fact, so they were corrected rather than left to be
re-discovered:

- `src/rpc/request.ts`, the `NOTE:` inside `classify()` — comment only, no code touched.
- `docs/fret.md`, *Stream management*: the "mirror case is a stated residual" paragraph, plus a new
  sentence in the backstop-arithmetic paragraph recording the no-off-by-one result.

Both now say **observed-not-guaranteed** and name the test, because the teardown shape belongs to
libp2p, not to us. `REFUSED_KIND` in the spec is the single constant that fails if a libp2p upgrade
turns that teardown back into a reset.

## Reviewer: known gaps, honestly

- **The ticket's "confirm nothing assumes the two directions are symmetric" item was not done.** The
  run crossed its token budget partway through, so no grep sweep for outbound/inbound symmetry
  assumptions was performed. `docs/fret.md` *asserts* the asymmetry is safe; that assertion is
  unverified by this ticket. If you want it closed, it is a read-only sweep over the `streamCaps()`
  callers and the four registrar functions.
- **`maxOutboundStreams` is not exercised at all.** This spec only drives the inbound cap. The
  outbound ceiling's sender-side arm (`local-limit` via `isStreamLimitError`) is asserted here only
  *negatively* — the refused outcomes must not be `local-limit`, which keeps the two arms from being
  conflated, but nothing positively drives a local ceiling firing.
- **The poll loop is the one timing-shaped construct.** It waits (20 ms steps, 5 s ceiling) until
  `entered + settled === CONCURRENT`. It is a convergence wait, not a fixed sleep, and the
  subsequent `admitted + refused === CONCURRENT` assertion fails loudly rather than silently
  passing if the ceiling is ever hit — but it is where flake would appear under a loaded CI box.
- **Both facts are single-library observations.** Two transports, one libp2p version, one muxer
  (yamux). Nothing here proves the behavior across muxers.
- The gate is opened in `after()` as well as in the case body, so a case failing before the release
  cannot strand a parked handler for the exit watchdog.
