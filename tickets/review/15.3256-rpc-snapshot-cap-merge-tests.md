## What shipped

One new describe in `test/rpc.handler-fuzz.spec.ts` — `announce snapshot merge caps` — table-driven
over both operating profiles, 6 tests each (12 total). It sits between the
`handleMaybeAct validator consequences` describe and `over the memory transport`.

Plus one small refactor: `sampleCoord(byte)` and `wrongWidthCoord(byteLength)` were **hoisted from
inside the `announce snapshot field matrix` describe to module scope** (just below `peerIdStr`).
Both describes now share one copy of the wrong-width-coordinate rule rather than two, which is the
drift these tests exist to catch.

## The claim being pinned

`onAnnounce` receives an *already-parsed* snapshot, so the parse + hash + upsert loop a crafted
announce drives is `FretService.mergeAnnounceSnapshot` (`src/service/fret-service.ts:1771`), bounded
by `FretService.mergeSnapshotCaps()` (`:1751`):

| profile | successors | predecessors | sample |
|---|---|---|---|
| core | 16 | 16 | 8 |
| edge | 8 | 8 | 6 |

The *same object* is handed to `makeSnapshotParser` at the single registration site
(`fret-service.ts:1033`), so the parser truncates before the merge loop ever runs. The headline
test is that **both routes cost the receiver the same number of upserts** — an over-long list buys
the sender no extra work whichever way the message arrives.

### How the work is counted

`store.upsert` is wrapped on the service's own store instance (`svc.getStore()`), recording each id
in call order. `mergeAnnounceSnapshot` calls it in exactly three places: once for `from` (`:1782`),
once per successor/predecessor after `hashPeerId` (`:1804`), once per sample entry after
`base64urlToCoord` (`:1815`). So the expected count is `1 + succ + pred + sample`.

`applyTouch` (`:497`) opens with `getById(id) ?? upsert(id, coord)` and the loop has always just
upserted that id, so it does not double-count. That was a read-derived assumption in the ticket; the
exact-count assertions now confirm it empirically (a doubled count would fail loudly).

## Use cases for validation

Run the spec alone:

```
cd packages/fret && node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/rpc.handler-fuzz.spec.ts" --timeout 30000
```

The 12 new tests, per profile:

- **states its merge caps as the pinned per-profile literals** — `mergeSnapshotCaps()` deep-equals a
  literal written in the test table, *not* read back from the thing under test.
- **merges exactly `1 + successors + predecessors + sample` ids, however long the lists** — driven
  with 40 successors, 40 predecessors, 20 sample entries. Asserts both the count and the exact id
  sequence (the *first* N of each list, in merge order).
- **never stores an id past the cap** — every over-cap id is absent from the store, *and* the last
  admitted id of each list is present, so the absences are the cap working rather than nothing
  having been stored.
- **costs the same whether the parser truncated first or the merge loop did** — the same raw body
  merged untruncated into one service and, through `makeSnapshotParser(caps)`, into a second; the
  recorded id sequences must be identical. This is the ticket's actual claim.
- **drops a wrong-width sample coord at the parser** — a 16-byte coordinate; the bad entry is absent
  from the parsed snapshot and the good entries survive in order, so it never reaches `onAnnounce`.
- **skips a wrong-width sample coord in the merge loop when the parser is bypassed** — the arm the
  merge loop's own per-entry try/catch (`:1817`) exists for. Only that entry drops; `from`, the
  successor, the predecessor and both good sample entries are all still upserted, and the merge does
  not fail.

### Rig notes for anyone extending this

- Services are constructed but **left unstarted** (`new CoreFretService(node, {...})` with the node
  started). No stabilization loops, no registered handlers. The merge's detached tail is quiet:
  `announceToNewPeers` (`:1726`) filters targets by `hasAddresses`, which is empty on an unstarted
  service, so it dials nothing; `enforceCapacity` (`:462`) early-returns far below the 2048 capacity.
  Confirmed in practice — the mocha exit watchdog is clean.
- Privates are reached through a locally-declared `DrivableMerge` cast, not by widening the
  `DrivableService` interface the neighbouring describe declares.
- `mergeAnnounceSnapshot` is awaited **directly** rather than going through `handleAnnounce`, which
  `detach`es it — that detachment is what makes counting via the public path non-deterministic.
- Peer-id seeds are allocated 60 / 61–100 / 101–140 / 141–160, all under 256 so `peerIdStr` keeps
  them distinct.

## Known gaps — treat the above as a floor

- **The neighbour-*fetch* merge path is not counted.** `fetchAndMergeSnapshot` slices to the same
  `mergeSnapshotCaps()` object, but nothing here proves *its* per-message cost is bounded. The
  equality claim proven here is announce-parser-vs-announce-merge only. This is the most obvious
  next test to want, and a reviewer may reasonably think it belongs in this describe.
- **The wire path into the merge is not exercised by these tests.** They call the private merge
  directly, so `handleAnnounce`'s token bucket, the identity check, and the `detach` are all
  bypassed. Those are covered by the sibling ticket's wire matrix, but nothing asserts the two
  halves compose — i.e. that a real over-cap announce arriving on the socket ends at these counts.
- **Only `store.upsert` is counted, as a proxy for per-message work.** Hashing (`hashPeerId`) and
  the `applyTouch` scoring are not counted separately. If a future refactor batched the upserts, the
  count assertions would fail loudly rather than silently — but the proxy is still a proxy.
- **No interaction with a near-full store.** Every test runs with `enforceCapacity` early-returning.
  A merge that pushes the store over 2048 (eviction mid-merge) is untested here.
- **Sample entry ids in the short-coord tests are plain strings** (`'good-1'`), not parseable peer
  ids. That is correct — the sample merge path never parses a sample id — but it means these tests
  say nothing about sample-id validation, of which there is none.
- The two hoisted helpers are now module-scope; if a reviewer disagrees with widening their scope,
  the alternative was a second copy of the wrong-width rule, which the ticket explicitly rejected.
