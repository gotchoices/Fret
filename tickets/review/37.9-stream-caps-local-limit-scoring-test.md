reviewer should read the two specs together.

## What the two specs are for

libp2p refuses an outbound stream when this node has already opened `maxOutboundStreams` of them
for one protocol on one connection. FRET calls that outcome `local-limit`. It is *our own* ceiling
firing before anything reached the wire, so it says nothing whatever about the peer. Two rules
follow, and both are easy to break silently:

- it must score nothing against the peer — no contact strike (three of those mark a healthy peer
  `dead` and drop it out of every ring view), no relevance decay, no backoff;
- it must increment `diag.streamLimit`, so a ceiling that fires is visible rather than silent.

### `test/rpc.stream-caps-outbound.spec.ts` (landed by the predecessor ticket)

The **wire** half: positively drives `maxOutboundStreams` and asserts the refused requests come
back as `local-limit`. Two cases, memory transport and TCP + noise. The requester registers the
protocol purely to declare its own outbound cap of 2 (libp2p reads the cap off the *dialing* node's
registrar), dials once, fires 4 concurrent requests at a parked handler on that one connection, and
asserts 2 refused as `local-limit` while the 2 admitted answer once released.

### `test/rpc.stream-caps-local-limit-scoring.spec.ts` (this ticket)

The **service** half: what `FretService` does with that outcome, driven by a cap that really fires
rather than by a hand-written outcome object. Three cases, all on the memory transport:

- *control* — the same ping over the same connection answers before the ceiling is installed
  (`pingsOk === 1`, membership stays `member`, `streamLimit === 0`). Without it the two capped
  cases would pass equally well against a rig whose dial was simply broken.
- *near probe* — `probeNeighborLatency` refused 4 times: `contactFailures === 0`, never `dead`,
  relevance / `failureCount` / `successCount` / `negotiateFailures` / `membership` all untouched,
  backoff map empty, `streamLimit` +4, and `pingsSent` / `pingsFail` both +0 (no ping was sent).
- *off-ring probe* — `probeMembership` refused 4 times: same no-strike result, plus an empty
  backoff map. That arm is where the backoff assertion is worth something: `probeMembership`'s
  `unreachable` / `timeout` / `foreign-protocol` arms strike **and** back off, so an empty map here
  is a fact about the `local-limit` arm rather than about a pass that never backs off.

## Rigging decisions a reviewer should weigh

- **Cap of 0, no concurrency.** `Connection.newStream` counts the stream it is opening *before*
  comparing (`streamCount > outgoingLimit`), so a cap of N admits exactly N and a cap of **0**
  refuses the very first outbound stream. Verified in `libp2p/dist/src/connection.js`:
  `findOutgoingStreamLimit` reads the registrar's `options.maxOutboundStreams` under `!= null`, so
  0 is honored and does not fall through to the default.
- **The local service is never started**, which is what leaves the ping protocol unregistered on
  the local node and lets the spec register it directly at a cap of 0 — no `unhandle` dance. The
  ticket's rigging note offered `unhandle` + re-`handle` after `start()`, or stubbing
  `streamCaps()`; not starting is cheaper than both, is the precedent `test/dead-state.spec.ts`
  already sets (a live stabilization loop would probe the peer on its own schedule and make the
  diagnostics non-deterministic), and both probe passes are driven explicitly anyway. The cost is
  that the spec never exercises `registerRpcHandlers` applying the *shipped* 256 — its sibling
  `test/rpc.stream-caps-profile.spec.ts` owns that half.
- **Spacing guard defeated by rewinding, not by sleeping.** `applyContactStrike` ignores a strike
  landing within 500 ms of the last counted one, so four back-to-back refusals would book at most
  *one* strike **even on a broken implementation** — the no-strike assertion would pass against
  exactly the bug it exists to catch. The ticket asked for ≥ 500 ms real spacing (> 1.5 s wall
  clock); the spec instead rewinds `lastContactFailureAt` to 0 between refusals, which defeats the
  guard completely rather than out-waiting it and does not depend on clock granularity on a loaded
  box. Same precedent as `test/dead-state.spec.ts`'s `unspace`. **This is the assertion most worth
  a reviewer's attention: if the rewind is wrong, the headline case is vacuous.** A quick check —
  route `local-limit` to `applyContactFailure` in `noteRpcFailure` and the near-probe case must go
  red with the peer `dead`.
- `REFUSALS` (4) is asserted `> cfg.deadAfterFailures` at runtime rather than trusted as a
  constant, so a config change cannot quietly make the case vacuous.

## Known gaps — deliberately not covered

- **Private-method access.** Both probe passes are reached through `svc as unknown as {…}` rather
  than through a real stabilization tick. Driving `stabilizeOnce` instead would prove the tick
  *selects* the peer as well, but couples the case to near/phase-2 target selection; the ticket
  asked for the scoring arms, and `test/dead-state.spec.ts` already pins the selection side.
- **Sender-side outcomes only.** libp2p's outbound-limit check runs *after* protocol negotiation,
  so a refused stream has already reached the remote and its handler may have been entered. The
  responder-side "entered" count is therefore not a usable observable on this arm, and neither
  spec uses it.
- **The two write-only senders are still uncovered end to end.** `announceNeighbors` and `sendLeave`
  route a `local-limit` through `noteWriteOnlyOutcome` → `countStreamLimit` rather than through
  `noteRpcFailure`. That path is unit-covered nowhere; only the two `noteRpcFailure` passes are
  driven here. Not filed as a ticket — say so if the reviewer disagrees.
- **The memory transport only** for the service spec. The outbound spec covers TCP + noise for the
  wire behavior, and the scoring seam sits above the transport, so a second transport here would
  re-pin libp2p rather than FRET.
- `test/dead-state.spec.ts` already has a `local-limit` case, but it hands `noteRpcFailure` a
  synthetic outcome object. It is not redundant with this spec and neither subsumes the other:
  that one pins the scoring rule, this one pins that a *real* cap firing reaches it as
  `local-limit` and not as some other variant.
