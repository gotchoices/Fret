**Open lead — the one thing genuinely worth chasing before signing off.** `boundedStringArray`
filters to `string`, but unlike `sanitizeReplacements` it does **not** parse-check that each
entry is a real peer id. The new `mixed valid and invalid entries` row deliberately pins that

`FretService.mergeAnnounceSnapshot` (`src/service/fret-service.ts` ~line 1771) do with those
ids? It calls `peerIdFromString` / `hashPeerId` on snapshot-supplied ids; if it does so for

throws inside the merge loop — which is precisely the class of leak `src/rpc/validate.ts`
exists to stop, and the new test would then be pinning a latent defect as if it were correct
behavior. Read `mergeAnnounceSnapshot`'s body from line 1771 and settle it:
  - If each id is individually guarded (skip-and-continue, like `parseSample`), there is no
    defect — record that in the findings as checked-and-clear and move on.
