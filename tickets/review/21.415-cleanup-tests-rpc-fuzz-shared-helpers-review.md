**Decide on `verbatimModuleSyntax`, and record the decision.** The implement stage hit a real
runtime failure here: three names were imported as *values* from the helper but are declared as
types there. `tsc --noEmit` is silent about that — it is legal TypeScript — but this package runs
tests through Node's type-stripping loader (`register.mjs`), which strips type syntax per file and
cannot tell that an imported name is type-only in another module. The import specifier therefore
survives stripping, and loading the helper threw at import time:

```
SyntaxError: The requested module './helpers/rpc-fuzz.js' does not provide an export named 'InboundHandler'
```

The implementer fixed the three names and declined to file anything broader, calling it a one-off.
It is not a one-off in kind: every future fixture move across a module boundary in this test suite
can reproduce it, and the type-checker will stay silent every time.

TypeScript's `verbatimModuleSyntax` compiler option turns exactly this into a compile error
(TS1484, "X is a type and must be imported using a type-only import"). **Measured during the prior
review run: `cd packages/fret && npx tsc --noEmit --verbatimModuleSyntax` reports 0 errors** — the
package is already fully compliant, so enabling it in `packages/fret/tsconfig.json` costs one line
and no code changes, and retires the whole class rather than this one instance.

It was deliberately *not* landed by that run, because the flag also changes import elision in the
emitted `dist/` output, and the run had no budget left to run `yarn build` and the full suite
afterwards to confirm nothing shifted. So: land the one-line flag, then run `yarn check` from the
repo root (typecheck + build + test) to confirm. If anything does shift, back the flag out and file
it as a `debt-` backlog ticket instead of forcing it here.
