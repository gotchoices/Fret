## What landed

Monotonic change counter snapshotted at `beginPass`; `noteChange` also zeroes `quietPasses` so the diag field reads 0 after any change. Not exported from the package root.
- **Service wiring**: `PASSIVE_INTERVAL_MS = 1500` / `ACTIVE_INTERVAL_MS = 300` statics; `FretConfig.maxPassiveIntervalMs` (default 60 000, `requirePositiveMs`); `idle` constructed in the constructor. The loop arms through a per-run `armLoop` closure (captures the generation, refuses once the run is over) stored with `stabilizeTimerDelayMs`; the timer callback nulls the handle *before* opening the pass, so `wakeLoop` reads "no timer" as "a pass is in flight". `runStabilizationPass` brackets the pass with `beginPass` / pending-redial check / `endPass`, writes `diag.loop`, and returns the settled delay. `wakeLoop` shortens a pending timer that is longer than the current target and never runs a pass at once. `setMode` is a change. `stop()` clears the timer and the closure and resets the backoff; `start()` resets it again (a pass in flight at `stop()` may close afterwards and would otherwise hand the next run a doubled delay).

## Deviations from the plan — read these first

Two policy rules were added that the plan did not have. Both were forced by measured regressions in the existing integration suite, not by taste; the traces are in the docs bullet and the code comments at `probeAndFetch`.

- **The near-exchange probe skip and the backoff do not stack.** `probeAndFetch` consults `nearExchange.canSkipProbe` only while `idle.quietPasses === 0`. Without this, six integration specs timed out (`fret.mesh`, `churn.leave`, three in `libp2p-memory.integration`, `proactive-announce`): a node whose neighbour keeps pinging it has a fresh heard stamp and a digest cached from that neighbour's announce, so it skipped three consecutive passes — and under the ladder those three skipped-and-quiet passes were 1.5 + 3 + 6 + 12 = 22.5 s, not 4.5 s, before the skip cap forced the first real probe and fetch. Rule: a pass the backoff already delayed verifies everything it came for. Consequence: on an idle strand a backed-off pass pings its neighbour every pass (one ping a minute per side at the cap), which is not a change, so the ladder still climbs. This also changes two numbers the plan stated: content re-check is once per interval (60 s at the cap), not ~4 min, and silent loss with no disconnect event is caught in about 65 s worst case at the cap (first strike within one interval, then two base intervals), not ~4 min. Docs and the `maxPassiveIntervalMs` doc comment carry the new numbers.
- **A skipped near probe marks the pass pending.** With the first rule alone, `proactive-announce`'s four-node line still failed: at the base, node 0 legitimately skipped its probe of node 1 on pass 2, that pass counted as quiet, and the re-check moved from 3.0 s to 4.5 s — past the spec's fixed 4 s sleep. The probe not sent is a check no event will make, so it is pending; the ladder starts only from a pass that actually verified its neighbours (the skip cap forces one within four base passes). The strand still reaches the cap: at most three held passes, then the first probing pass is quiet and the climb begins; backed-off passes never skip (rule one), so there is no oscillation.

Reviewer: both rules live at one site (`probeAndFetch`'s skip branch). Please judge whether they belong there or in `NearExchange.canSkipProbe` with the quiet count passed in; I kept the policy module clock- and loop-free and put the coupling in the service.

Other departures, smaller:

- **Lifecycle cadence comment.** The plan predicted passes at 0, 1.5, 4.5 s for the stubbed quiet pass; measured 0, 3, 9 s — the first pass of a run is quiet too and doubles. The `at.most(3)` assertion holds either way; the comment now carries the measured numbers.
- **Near-exchange backoff case uses a stranger's inbound ping, not `peer:connect`.** That rig never starts its services (so the hand-driven passes do not race a loop), and the connect listener is attached by `start()`. An RPC from a stranger creates an entry on B — row 4 of the table — and is read live (`idle.delayMs`) on both sides right after, before B's next pass labels the stranger and B's snapshot then names it, which would legitimately reach A. After one more B pass, `diag.loop.delayMs` on B is asserted at the base.
- **The loop arms from `idle.delayMs` at arm time**, not from the pass's return value: a change landing in the microtask gap between `endPass` and the arm has reset the delay but found no timer to shorten. The return value serves hand-driven callers.
- **`noteChange` logs every change**, debug-gated. On a busy Core node every `noteDiscovered` is a line; the plan asked for the log, but a reviewer may prefer logging only when the delay actually moved.

## Known gaps and tripwires

- **A permanently off-ring peer caps the ladder at ~24 s, not 60 s.** Selection-based pending means the ladder restarts at each probe of a dead or foreign peer, and climbs 46.5 s before a 32 s backoff window has passed, so a ring that lost a phone ungracefully and never evicts the entry settles at about five passes per window (~9 s apart) — six times fewer than before rather than forty. `NOTE:` at the pending site in `stabilizeOnce` says what to change (hold pending for the classify arm only; the dead/foreign arms' outcomes land in-pass). Docs state the arithmetic. Not pinned by a test.
- **`runStabilizationPass` has no try/finally around `endPass`**: a throw inside the pass leaves the delay at its pre-pass value and the loop arms at that (the loop's own catch logs it). `stabilizeOnce`'s reachable-throw analysis says nothing throws there; stated rather than guarded.
- **Not pinned**: `wakeLoop` shortening a long timer is covered only through the departure case (30 s timer → dead within 8 s); `setMode` waking the loop; `diag.loop` reading the base after `stop()`; `readPeerStore`'s dialability diff; `maxPassiveIntervalMs` validation (same helper as `dialTimeoutMs`); the "pass in flight at stop() closes afterwards" reset in `start()`.
- **Join latency**: a fresh ring's first snapshot exchange is unchanged (3 s on the line rig) thanks to the pending rule; a node whose passes are quiet while a neighbour is still learning sees that neighbour's new content one ladder step later than before. The integration specs' convergence gates (6–12 s) pass with margin; the `proactive-announce` line case is a fixed 4 s sleep against a measured ~3 s and was tight before this ticket too.

## Measuring success

On an idle two-member strand, passes should fall from ~20/min to ~1/min within about two minutes of the last change (ladder 1.5 → 3 → 6 → 12 → 24 → 48 → 60 s), and `diag.loop.delayMs` should read 1500 within one pass of a `peer:connect` or `peer:disconnect`. With `DEBUG=optimystic:fret:service:fret` each reset logs `change: <reason> - stabilization interval back to 1500 ms`, which is how to see what keeps a phone's loop awake.
