## What the review has established so far (do not redo)

Read of the implement diff (`git show 8ffff9d -- packages/fret/src/service/fret-service.ts`)
against `src/service/probe-backoff.ts`:

- **Every call site converted, semantics preserved.** The one substitution worth checking by hand
  was the off-backoff gate, which changed shape rather than being a rename: `getBackoffPenalty(id)
  === 0` became `!isBackedOff(id)`. These agree because a retained entry always carries
  `factor >= 1`, so an open window yields `penalty = min(1, factor/maxFactor) >= 1/32 > 0`, and
  `penalty === 0` therefore means exactly "no live entry, or window closed". The boundary is
  identical too — the old code treated `until < now` as expired, the new `isBackedOff` treats
  `until >= now` as open. `ProbeBackoff` documents this agreement at `isBackedOff` and pins it in
  its spec.
- **One instance held, as the ticket claimed.** `FretService` constructs a single `ProbeBackoff`;
  the `reprobeOffRingTargets` `NOTE:` recording the shared-map decision is carried forward with
  only its type name updated, and the decision text is unchanged.
- **The two reworded (rather than substituted) sites were checked and neither claim drifted** —
  the phase-2 selection-purity comment ("they read the backoff state") and the shared-instance
  `NOTE:`. This was the specific read-through the implement handoff asked a reviewer for.
- **Clock unification is an improvement, not a change in behavior.** The old code stamped windows
  with `Date.now()` while the backing `ExpiringMap` ran its retention TTL on its own default
  clock; `ProbeBackoff` drives both from one injectable `now`, which is what makes the escalation
  schedule steppable under a fake clock.
- **Docs sweep for the removed symbols is now complete** (done in this pass, see below).

## Added arm (from the `backoff-test-helper` review, 2026-08-22)

Deleting the old `Foreign re-probe backoff growth` block from `test/ring-membership.spec.ts` left
one thing uncovered that `test/probe-backoff.spec.ts` does **not** replace, because it is not a
`ProbeBackoff` behaviour at all.

The deleted case `backoff caps at factor 32 and prunes evicted peers` asserted two separate
things. The cap half is fully covered by the unit spec. The prune half asserted a *service-level
wiring* fact: that `FretService`'s per-tick sweep drops backoff entries for peers no longer in the
routing table. `probe-backoff.spec.ts` pins `ProbeBackoff.prune(predicate)` — that the method
honours whatever predicate it is handed, and that prune and sweep are orthogonal — but nothing now
pins that the service actually calls it, or that it passes a *store-membership* predicate.

The site is `packages/fret/src/service/fret-service.ts:3152`:

```
this.backoff.prune((id) => this.store.getById(id) !== undefined);
```

If that line were deleted or its predicate inverted, the whole suite would still pass today. Worth
one case in whichever spec ends up owning the tick's sweep, once 39.52 / 39.53 have converted the
stale casts and a green suite exists to add it to. Cheap to write: record backoff for an id that
is not in the store, run one tick, assert the entry is gone.
