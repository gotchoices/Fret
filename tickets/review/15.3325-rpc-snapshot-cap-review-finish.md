## What the change was

The per-message caps on a received neighbor snapshot (Core 16 successors / 16 predecessors /
8 sample; Edge 8/8/6) used to be enforced twice — once by the snapshot parser wired in at each call
site, and again by a `slice(0, caps.*)` inside each of the two merge loops in
`FretService`. The merge-loop copies were removed; `makeSnapshotParser` is now the single
enforcement point.

## Already done in the first review pass — do not redo

**Reachability of the removed slices: confirmed.** The implementer asked for a third-caller check
and there is none.

- Announce: `registerNeighbors` is called from exactly one place (`registerRpcHandlers`,
  `fret-service.ts:1033`) and is handed `makeSnapshotParser(this.mergeSnapshotCaps())`. Its
  `serve` receives the parsed snapshot, hands it to `handleAnnounce`, which is the only caller of
  `mergeAnnounceSnapshot`.
- Fetch: `fetchAndMergeSnapshot` is private, and its own `fetchNeighbors` call supplies
  `parse: makeSnapshotParser(this.mergeSnapshotCaps())`; `parseOrThrow` runs inside `decode` before
  `rpcRequest` can return `ok`.
- The `Infinity`-caps defaults on `registerNeighbors`' `snapshotParser` and `fetchNeighbors`' `parse`
  are test-only and already carry `NOTE:` blocks stating that and naming the revisit condition
  (a second production caller). Left alone deliberately.

**Minor findings, all fixed inline in this pass** (comment and documentation only — no behavior
change; `npx tsc --noEmit` clean afterwards):

- `makeSnapshotParser`'s docstring still described the merge loops as slicing "to exactly these
  caps", i.e. the drift-prevention comment described a copy of the bound that the change had just
  deleted. Rewritten to state the single-enforcement-point rule.
- Two comments in `fret-service.ts` said "the same caps the merge loop below slices to" /
  "the caps the announce merge slices to". Same problem, same fix.
- The sample-loop comment claimed the `try/catch` exists only for a parser-bypassed body. It also
  covers `upsert` / `applyTouch`, which the parser says nothing about. Widened.
- `docs/fret.md` claimed in two places that both merge loops slice — the security-considerations
  bullet under *Current state*, and the "Truncate, don't reject" bullet under *Wire-shape parsers*.
  Both now state where the bound actually lives.
- `parseSample`'s strictness about `relevance` — the one peer-visible behavior change in the diff,
  which the implementer flagged for a second opinion — was **upheld** and recorded at the code site
  as an accepted-tradeoff `NOTE:`. The line held: a required wire field that arrives malformed makes
  the entry unusable, whereas `size_estimate` / `confidence` are optional advisories and so are
  dropped field-wise. The NOTE names the declined alternative (`finiteNumberOr`), the cost, and a
  revisit condition.

**One handoff claim is wrong and the follow-up ticket repeats it.** The review ticket and
`implement/15.3324-rpc-snapshot-cap-merge-path-tests` both say `fetchAndMergeSnapshot` "has no cap
test at all". It has two, in `test/profile.behavior.spec.ts` under
`describe('Snapshot receive caps')` (~line 173): each stands up a real sender, calls
`fetchAndMergeSnapshot` on a real receiver, and asserts the store grew by at most the receiver's
profile caps. They are weak — `at.most` passes vacuously if the sender emits few peers, and the
sender's *outgoing* snapshot caps (Core 12/12/8) sit below the Core receiver's merge caps
(16/16/8), so the Core case cannot bind at all — but they exist and they exercise the path
end-to-end. Whoever works `15.3324` should treat its fetch-path item as *strengthening* these two
rather than writing from scratch, and fix the "no test at all" wording.
