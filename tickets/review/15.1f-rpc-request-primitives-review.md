**The implementer's central claim about libp2p holds against the real implementation, not only
against the test stub** (checked in `node_modules/@libp2p/utils/dist/src/abstract-stream.js` and
`abstract-message-stream.js`):

- `AbstractStream.close(options)` sets `writeStatus = 'closing'` **before** it awaits anything,
  then awaits `pEvent(this, 'idle', options)` / `pEvent(this, 'drain', options)` /
  `sendCloseWrite(options)` — each receiving the caller's `AbortOptions`. A close bounded by a
  signal therefore rejects on that signal with the write end left at `'closing'`, never
  `'closed'` — exactly the state `registerRpcHandler`'s catch arm needs
  (`writeStatus !== 'closed'`) for its abort to run.
- `close()` early-returns when `writeStatus` is already `'closing'`/`'closed'`, so a handler that
  closed for itself is not released twice.
- `close()` does **not** abort the stream when it rejects — it leaves the stream half-open. So the
  follow-up `abort()` in both `releaseRpcStream` and the handler seam is load-bearing, not
  belt-and-braces.
- `abort()` is self-guarded, so an extra abort is a no-op rather than a double release.
- **A bare `close()` really can block indefinitely.** `processSendQueue` sets
  `writableNeedsDrain = true` when the muxer stops accepting (`onMuxerNeedsDrain` does too), and
  `close()` then awaits the `'drain'` event. With no `options.signal` there is nothing to end that
  wait, so a remote that accepts a stream and stops reading holds the closer forever once the
  flow-control window fills. (`checkWriteBufferLength` aborts only if `maxWriteBufferLength` is
  configured — a muxer-dependent backstop, not a budget.) This is what makes finding A real.

**The ordering the seam's doc comment depends on is real.** All five sender call sites release from
a `finally` *before* `d.cancel()`, so the deadline is still live when its signal reaches
`releaseRpcStream`: `ping.ts`, `neighbors.ts` (×2), `maybe-act.ts`, `leave.ts`.

**Arm (a)'s "the loop needs no change" is arithmetically correct.** With `timeoutMs = Infinity`:
`deadlineAt` is `Infinity`, `remaining <= 0` never fires, `Math.min(Infinity, EOF_POLL_MS)` is 20,
and the `read timed out` throw is unreachable.

**No caller passes `timeoutMs` of `0` or a negative** — `grep -rn "readFramed(" src test` shows
every call site passing a module constant, a literal >= 150, `Infinity`, or nothing.

### Finding C (minor — not yet applied): `readFramed` does not validate `timeoutMs`

The entry guard tests `timeoutMs === Infinity` exactly. A `NaN` is worse than the implement handoff
described ("runs unbounded with no error"): `Math.min(NaN, EOF_POLL_MS)` is `NaN` and
`setTimeout(fn, NaN)` clamps to zero, so the poll loop spins one iteration per event-loop turn,
re-running `remoteFinishedWriting` for as long as the stream stays open — a hot spin, not a quiet
hang. `0` and negatives make `remaining <= 0` fire immediately, which is at least loud.

Not reachable from any current caller (verified above), but `readFramed` is exported from the
package root, so a consumer computing a timeout from config can reach it. Add, next to the existing
`Infinity` clause in `readFramed`'s entry guards: `if (!(timeoutMs > 0)) throw new Error(...)` —
which covers `NaN`, `0` and negatives while letting `Infinity` through. Rung 1 of *Architecture
first*: validating a seam's own input so the bad state cannot enter. Add a case to
`test/rpc.protocols.spec.ts` alongside the existing `Infinity`-requires-a-signal case (~line 509).
Document the new rejection in `readFramed`'s doc comment `@throws` list.
