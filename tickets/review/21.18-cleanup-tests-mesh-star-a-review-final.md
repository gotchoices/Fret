## Findings already established (fold these into the complete/ ticket verbatim)

**Migration audit — clean.** The two migration commits (`d93c54e`, `c71be3d`) were re-read line by
line against their pre-migration bodies. Faithful. Confirmed specifically: `addServices(...)` runs
before `connect('star')` in both service-bearing rigs, matching the original order and the helper's
documented construct-then-dial path; `bootstraps` preserved verbatim, including node 0 bootstrapping
off itself, which is exactly why these rigs correctly do *not* use the shorter `starMesh` helper
(that one gives node 0 an empty bootstrap list, so switching would have silently changed behavior);
`mesh.stop({ skip: [n] })` skips both the service and the node at index `n` and the services array
is index-parallel to nodes, so it faithfully replaces the original "stop all but index N" teardown;
the third rig builds no services, and `mesh.stop()` with an empty services array falls straight
through to `stopAll(nodes)` as the original did; the long "what this rig can observe" comment on the
fan-out rig survived intact; and the remaining `createMemNode` / `stopAll` imports are genuinely
still used by two out-of-scope describe blocks lower in the file, which build nodes by hand for real
reasons (one grows nodes mid-test, one deliberately never starts its service) that the mesh helper
does not express.

**One behavior difference, judged acceptable and not changed.** The original teardown stopped
surviving services concurrently via `Promise.all` and propagated a throw; `mesh.stop()` stops them
sequentially and swallows throws. That is the mesh helper's stated best-effort teardown contract,
and the assertion these tests actually make — that the *departing* service's `stop()` does not throw
— is still made directly and un-swallowed.

**Two minor findings fixed inline across legs two and three.**

- The third rig called `mesh.nodes[1]!.peerId.toString()` twice where the mesh already precomputes
  that exact string as `mesh.ids[1]!` (and the same rig already used `mesh.ids[0]!` elsewhere).
  Replaced; provably identical, since `ids` is built as `nodes.map(n => n.peerId.toString())`.
- **Teardown-on-throw, in `churn.leave.spec.ts`.** All three rigs called `mesh.stop()` as their last
  statement with no `afterEach`, so a rig whose assertion or `waitFor` gate threw left its libp2p
  nodes running and the mocha exit watchdog fired a second, unrelated-looking failure on top of the
  real one — costly in this file specifically, which already carries a comment about a past
  full-suite stall. This was pre-existing (the hand-rolled rigs had the identical shape) and the
  prior leg left it as an open question: fix inline, or record as a tripwire. **Decided: fixed
  inline**, because the exact pattern already ships in this repo at
  `test/libp2p-memory.integration.spec.ts:87-104` — a hoisted `let mesh: Mesh | undefined` plus an
  `alreadyStopped: number[]` that the two `skip`-using rigs push to right after they stop their own
  node, and an `afterEach` that calls `mesh?.stop({ skip: alreadyStopped })` and resets both. So it
  is a convention to follow, not a pattern to invent. Three narrowing errors fell out of hoisting
  (`mesh` is a captured `let`, so TypeScript discards its narrowing inside callbacks); fixed by
  using the `addServices` config callback's own mesh argument and by binding one local `const`.

**Validation run this leg:** `npx tsc --noEmit` clean; `churn.leave.spec.ts` + `profile.behavior.spec.ts`
together 50 passing, matching the 17 + 33 baselines exactly.
