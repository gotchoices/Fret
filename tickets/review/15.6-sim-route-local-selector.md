### What is wrong today

`handleRoute` (`fret-sim.ts:724–788`) reimplements hop choice and cheats twice: its candidate
filter drops any peer whose *global* `alive` flag is false and any peer the *global* partition
map (`reachable`) says is unreachable (lines 771–779) — neither visible to a real node — then
takes `candidates[0]` (line 783), the first element of a concatenated ring walk, with no
requirement that the hop be closer to the target than the current peer. And nothing under
`test/simulation/` imports the shipped routing code, so the sim's routing-success number cannot
guard `chooseNextHop` at all. Note `handleRoute`'s `maxHops` (line 734) *also* reads the global
`aliveCount()` oracle.

### Design — route on local knowledge, decide with the shipped selector

Replace the body of the hop loop in `handleRoute`:

- **Candidate pool** — current peer's own store only:
  `store.neighborsRight(targetCoord, m, notDead)` ∪ `store.neighborsLeft(targetCoord, m, notDead)`,
  minus `visited` and minus self. No `alive` read, no `reachable` read — delete both from the
  filter. (The `notDead` filter is fine: it reads only what the probing peer's own store
  recorded.)
- **Hop choice** — `chooseNextHop` from `../../src/selector/next-hop.js`, cost path:

  ```ts
  chooseNextHop(store, targetCoord, candidates, isConnected, linkQ, {
  	nearRadius: this.nearRadiusFor(store),
  	selfCoord: currentPeer.coord,   // from hop 2 onward only — see below
  	confidence: 0.5,
  })
  ```

  Signature confirmed (`next-hop.ts:160`): `(store, targetCoord, candidates, isConnected, linkQ,
  opts)`. Cost path activates on `opts.nearRadius`. Candidates resolve through `store.getById` —
  one absent from the current peer's store is silently skipped (true of this pool by
  construction; note it at the call site). Strict-improvement filter is
  `lexLess(s.dist, selfDist)` applied before the near/far partition; `isNear` is
  `dist <= nearRadius` inclusive; `linkQ` called on far candidates only.
  - `isConnected = (id) => currentPeer.connected.has(id)`.
  - `linkQ = () => 0` — sim models no latency; must be a *constant* or determinism breaks.
  - `backoffPenalty` omitted (sim has no backoff model).
  - `selfCoord` is the point: makes each hop strictly closer to the target than the peer that
    chose it — the production invariant `nexthop-cost.spec.ts` pins.
- **`nearRadiusFor(store)` helper** (new, private) — derived from **local** info only:
  `β · k · (2^256 / max(1, store.size()))` with β = 2, clamped to at most half the ring
  (`1n << 255n`), converted with the module-private `bigintToCoord` already at the bottom of
  `fret-sim.ts` (~line 897). Do **not** use `aliveCount()` — that is the oracle in a new place.
- **Contact attempt** — the chosen hop is a candidate, not a delivered message. Contact succeeds
  when `contactAllowed(current, next)` **and** the target peer is really alive. On failure,
  record a contact strike against `next`'s entry in `current`'s store — the same escalation
  `contactSweep` performs (`fret-sim.ts:577–590`: increment `contactFailures` clamped at
  `deadAfterFailures`; at threshold set `state: 'dead'` and stamp `lastAccess` with **sim time**,
  never `Date.now()`, or dead re-probe replay breaks) — then choose again from the remaining
  candidates. **Extract that arithmetic once**: private
  `recordContactFailure(store, entry, time)` / `recordContactSuccess(store, entry)`, called from
  both `contactSweep` and the routing path; a second copy is how the two drift.
  `store.update(id, {...})` is the mutation API.
- **Attempt budget** — bound total contact attempts (successful or not) by the existing
  `maxHops` budget so a route through a fully partitioned-away window terminates. `maxHops`
  reads `aliveCount()`: decide whether it keeps the oracle count (defensible — it is a
  test-harness budget, not a peer decision) or moves to `store.size()`; either way say so in a
  comment. The ticket mandates local derivation only for `nearRadius`.
- **Hop counting** — only a successful contact increments `hops`; a failed attempt spends
  attempt budget, not a hop, so `avgRoutingHops` stays a path-length measure.
- **Arrival test** — unchanged (lines 741–766), including the deliberately-unfiltered
  `successorOfCoord` / `predecessorOfCoord` reads and the `NOTE:` explaining why (a boundary
  peer must not crown itself anchor for a far-side coordinate while its store still names a dead
  entry closer to the key). Keep behavior and note.
- **Delete the two stale `24-sim-router-realism` comments** — in `contactSweep`'s doc comment
  (~line 553) and `handleRoute`'s candidate-filter comment (~lines 768–770). Those deferrals are
  discharged by this ticket; rewrite rather than renumber.

### Edge cases (cover in code; the measurement spec is the sibling ticket's job)

- **No strictly-improving hop.** `chooseNextHop` with `selfCoord` returns `undefined` when every
  candidate is behind the current peer. Correct production outcome — record the route as a
  failure and stop. No "closest anyway" fallback; that reintroduces the drift the floor prevents.
- **Originator vs forwarder.** Production supplies `selfCoord` only when *forwarding*; an
  originator aiming at a key's cluster is legitimately farther from the key than every cluster
  member. `handleRoute` starts at the originator, so the first hop must **not** apply the floor —
  pass `selfCoord` from the second hop onward, or the sim reports failures for routes production
  completes.
- **Ring smaller than m** (N=5, m=3 in `simulation.spec.ts`): walks overlap, pool can empty on
  hop 1 after filtering self and `visited` — must end as a defined failure or immediate arrival,
  never a throw or infinite loop.
- **Single live peer**: empty pool, arrival test false → one recorded failure, zero hops.
- **Every candidate unreachable (active partition)**: attempt budget terminates; each failed
  attempt strikes exactly once, so `deadAfterFailures` consecutive routes through the same window
  mark those entries `dead` and later routes skip them via `notDead`.
- **Routing during heal**: a dead entry re-probed back to `disconnected` becomes a candidate
  again; a route issued between heal and re-probe still fails. Both correct.
- **Metrics note**: `MetricsCollector.recordRoute(success, hops)` (`sim-metrics.ts:145`) pushes
  `hops` for failures too — unchanged here; the hops-on-success-only rule concerns what
  `handleRoute` passes in.
