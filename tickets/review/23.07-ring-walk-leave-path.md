## Findings so far

### 1. The interleave assertion is vacuous (test defect, not a code defect)

In `churn.leave.spec.ts`, case `draws every replacement from beyond that window, both sides`, the
two closing assertions claim to pin that the replacement list is drawn from both sides of the ring:

```
expect(from([9, 10, 11, 12]).length,
    'interleaved, so the cap does not empty the clockwise side first').to.be.greaterThan(0)
expect(from([13, 14, 15, 16]).length,
    'interleaved, so the cap does not empty the counter-clockwise side first').to.be.greaterThan(0)
```

Both hold for **any** ordering, including the side-major ordering the change replaced, so they
discriminate nothing. Worked through by hand on the rig the case actually builds (24 peers at
offsets `+1..+24`, `m = 8`):

- The S/P window is `{+1..+8} ∪ {+17..+24}` — 16 of the 24 peers. What is left outside it is a
  **single arc of 8**, `{+9..+16}`.
- Both walks lap that ring, so *each* side, after exclusion, returns that same 8-id arc — the
  clockwise one as `+9…+16`, the counter-clockwise one as `+16…+9`. The candidate pool is 8 ids
  however the two are combined.
- `maxReplacements` is 6. Taking 6 of 8 leaves 2 behind, so each 4-id half of the arc must
  contribute at least 2 no matter what order the 8 are in. Both assertions are arithmetic, not
  behavior.
- Concretely, side-major ordering yields `[+10, +9, +11, +12, +13, +14]` after the
  connected-first sort — `from([13..16])` is `{13, 14}`, length 2, and the assertion passes.

A second, smaller reason the first of the two assertions cannot fail: `OUTSIDE_RECEIVER` is `+10`,
which is a real dialed node and therefore the *only* connected candidate in the pool.
`computeReplacements` sorts connected-first, so `+10` is first in the list under every ordering,
and `from([9, 10, 11, 12])` is non-empty for that reason alone.

**Disposition: fix in this review pass.** Two ways, pick one:

- *Preferred — make it discriminate.* Enlarge the ring so the two sides yield genuinely disjoint
  candidate arcs. At `COUNT = 40` the window is `{+1..+8} ∪ {+33..+40}`, the clockwise pool
  (16 per side, post-exclusion) is `{+9..+24}` and the counter-clockwise pool is `{+40..+17}`.
  Side-major then fills all six slots from `{+9..+14}` and the counter-clockwise assertion fails,
  which is what the case is supposed to say. Check two things before committing to this: that
  `ghostPeerId()` is cheap enough at 40 (it is called once per seeded peer, and the existing rig
  already builds 24), and that `OUTSIDE_RECEIVER` stays inside the beyond-S/P fan-out's reach —
  `expandCohort` is asked for `ids.length + fanOut` = 20 ids, which the alternating walk fills from
  `{+1..+10} ∪ {+40..+31}`, so `+10` still qualifies.
- *Or* delete the two assertions and say plainly in the case's comment that the interleave itself is
  pinned by `test/ring-walk.spec.ts`, not here. Weaker, but honest; the rest of the case (all six
  replacements come from beyond the window) is real and does discriminate.

Note that the *sibling* case `caps the replacement list at six ids` (`k: 7`) has the same shape and
may carry the same vacuousness — the implementer retargeted its membership check from an eight-id
`eligible` array to a six-id `innermost` array and described that as a tightening. Re-derive it the
same way before accepting that claim; it was not checked in this run.

### 2. `computeReplacements`' comment overstates what the interleave buys

At `packages/fret/src/service/fret-service.ts` (in `computeReplacements`) the new comment ends:

> Interleaved, so the `maxReplacements` cap below takes from both sides rather than emptying the
> clockwise one first.

The cap is applied **after** a sort whose primary key is connected-first and whose secondary key is
relevance. The interleave therefore only decides order among candidates that tie on *both* — which
is the case in the specs (freshly `upsert`ed entries, relevance 0, none connected) but is not the
general case. On a live ring where connectedness and relevance differ, the cap takes the
best-connected and most-relevant six wherever they sit, and the interleave contributes nothing.

**Disposition: fix in this review pass** — one sentence, saying the interleave is the tie-break the
sort falls back on. The code is correct; only the comment claims more than it delivers.

### 3. Not defects — checked and clear

- **The `+ exclude.size` over-fetch is exact, not approximate.** `ringNeighborsBothSides` asks each
  side for `count + 1 + |exclude|`; `computeReplacements` passes an exclude of up to 2m = 16 against
  a count of `m * 2` = 16, so each side asks for 33 and can still yield 16 after every excluded id
  and self are dropped. A side the window blankets does not starve.
- **The send loop's ordering is a real improvement under a truncated budget.** `ids` is interleaved
  (`s1, p1, s2, p2, …`), and the loop breaks on `budget.signal.aborted`, so a fan-out that runs out
  of the 3 s `SHUTDOWN_BUDGET_MS` has still reached both sides. Under the old side-major array it
  would have spent the whole budget clockwise. Worth stating in the findings section of the
  `complete/` ticket — it is a second, unclaimed benefit of the change.
- **No overlap between who is notified and who is advertised.** Everything in `spSet` is a notice
  target (modulo the `isDoomedDial` skip) and `spSet` is the replacement walk's `exclude`, so a peer
  cannot be both. That is exactly what case `advertises no peer that is inside its own S/P window`
  pins, and that case *does* discriminate — it fails under the old code.
- **The unfiltered target walk vs. the live-member replacement walk compose correctly.** `spSet` may
  hold `dead` / `foreign` ids that the filtered replacement walk would never have returned anyway;
  they cost one over-fetch slot each and change no result.

## Implementer's handoff (verbatim, from the implement stage)

Build, type-check and the full test suite passed at `04c7c47` (`1161 passing`, 0 failing).

### What changed

One root cause, three readers, one array.

`sendLeaveToNeighbors` built its neighbor list with a side-major walk (all successors, then all
predecessors) and capped the *concatenation* at 8. At the shipped `k: 15` (so `m: 8`) those 8 slots
were spent entirely on the clockwise side, so:

- no predecessor was ever sent a leave notice, and
- the same truncated array was handed to `computeReplacements` as "our own S/P window", so six
  genuine predecessors read as *outside* it and were advertised to our own neighbors as
  replacements for us.

It is now a single `ringNeighborsBothSides(store, selfCoord, m, selfStr)` call bound to one name,
used unchanged by all three readers (send loop, replacement exclusion, beyond-S/P fan-out filter).
The `.slice(0, 8)` is gone — the fan-out was always clock-bounded by `SHUTDOWN_BUDGET_MS` (3 s)
overall and `LEAVE_NOTICE_TIMEOUT_MS` (1.5 s) per notice, with the existing `budget.signal.aborted`
break.

`computeReplacements` now uses the same helper at `m * 2` per side under `isLiveMember`, passing
`spNeighborIds` as the helper's `exclude` rather than filtering the walk's result. Its sort
(connected-first, then relevance) and its 6-cap are unchanged.

Two intended behavior changes beyond the bug fix:

1. **The beyond-S/P fan-out arm shrinks.** It filters on `!spSet.has(id)`, and `spSet` is now the
   true 2m window rather than one truncated side. Peers it used to reach now receive a notice as
   S/P members instead.
2. **Replacement ordering is now interleaved, not side-major** — a wire-visible change to what a
   departing node advertises. (Reviewer: see finding 2 — this is weaker than stated.)

### Testing

New: `describe('at the shipped k of 15')` inside `Leave notice replacements (sender side)` — four
cases over one departure at `k: 15`, `m = 8`, 24 seeded live members: notifies the predecessor side;
advertises no peer inside its own S/P window; draws every replacement from beyond that window on
both sides; sends each peer exactly one notice across both arms. The rig `makeSenderRig` was
generalized to take a list of ring offsets that get real dialable nodes (was: exactly one, at `+1`)
and to record every notice per receiver rather than the last one.

### Known gaps the implementer flagged for the reviewer

- **One existing spec's comment was corrected and its assertion relabeled.** In `caps the
  replacement list at six ids` (`k: 7`), the stale comment claimed the pool was eight ids; with the
  `+ exclude.size` over-fetch it is twelve (`{+5..+16}`). The membership check was retargeted from
  an eight-id `eligible` array to a six-id `innermost` array, which the implementer believes is
  stricter. The source ticket said the `k: 3` / `k: 7` specs must keep passing unchanged; the `k: 3`
  spec was not touched at all.
- **`OUTSIDE_RECEIVER` sits at `+10`, and the reason is subtle.** `+12` was tried first and the
  fan-out case failed: the beyond-S/P arm asks `expandCohort` for `ids.length + fanOut` = 20 ids,
  which the alternating walk fills from `{+1..+10} ∪ {+15..+24}`, so `+12` is outside the window
  *and* outside the fan-out and the case tested nothing. That coupling is real but implicit — a
  future change to `fanOut` or to `expandCohort`'s over-fetch would silently make the case vacuous
  again rather than fail.
- **The single-peer ring (self only) is verified by reasoning, not by a test.** The helper returns
  empty for a store with no other entries, so the send loop is a no-op and `computeReplacements`
  returns `[]`. Cheap to pin here if wanted.
- **The source ticket's `files:` named `packages/fret/test/leave-protocol.spec.ts`, which does not
  exist.** The leave specs live in `packages/fret/test/churn.leave.spec.ts`.
- **The serial-send tripwire is a `NOTE:` at `sendLeaveToNeighbors`, not a ticket** — 2m = 16
  notices at 1.5 s each against a 3 s budget is clock-bound well before it is target-bound, so
  pooling would not change what goes out today.
- **Not measured: the wire-level effect of the wider target list.** A departing node now sends up to
  16 notices where it sent up to 8. Every notice is `isDoomedDial`-filtered and the whole fan-out
  shares a 3 s budget, so the ceiling is unchanged in wall-clock terms, but how often the budget now
  truncates the list on a real ring was not measured and the leave path has no diagnostic counter
  that would show it.
