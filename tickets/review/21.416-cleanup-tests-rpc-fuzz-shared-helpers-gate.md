**2. Decide `verbatimModuleSyntax`, and record the decision.**

The implement stage hit a real runtime failure: three names were imported as *values* from the new
helper but are declared there as types. `tsc --noEmit` is silent — it is legal TypeScript — but
this package runs tests through Node's type-stripping loader (`register.mjs`), which strips type
syntax per file and cannot know an imported name is type-only in another module. The specifier
survives stripping and the import throws:

```
SyntaxError: The requested module './helpers/rpc-fuzz.js' does not provide an export named 'InboundHandler'
```

The implementer fixed the three names and called it a one-off. It is not a one-off *in kind*: every
future fixture move across a module boundary in this test suite reproduces it, and the type-checker
stays silent every time. `verbatimModuleSyntax` turns exactly this into a compile error (TS1484),
and the package is **already fully compliant** (measured: 0 errors), so enabling it in
`packages/fret/tsconfig.json` costs one line and no code changes — the invariant that retires the
class, rather than a ticket per instance.

It was not landed by either prior run because the flag also changes import elision in the emitted
`dist/` output, and neither run had budget to build and run the suite afterwards. So: add the one
line, then run `yarn check` (step 1 covers both at once). If the build or suite shifts, back the
flag out and file it as a `debt-` backlog ticket instead of forcing it here.
