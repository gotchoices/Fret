## What it covers

Three failure shapes no other test produced, each driven against every sender that can meet it:

| Shape | Stub | Senders driven |
|---|---|---|
| Reset mid-stream (reply iterator *throws* after N bytes) | `resetsAfter(bytes?)` | ping, neighbors-fetch, maybeAct (+ zero-byte variant) |
| Clean EOF mid-JSON (short-but-complete buffer, `decodeJson` throws) | `halfThenEof(bytes)` | ping, neighbors-fetch, maybeAct |
| Partial then stall (bytes, then silence) | `partialThenStall(bytes)` | ping, neighbors-fetch, maybeAct |
| Caller cancels mid-stream (abort lands with bytes already buffered) | `partialThenStall(..., { onNext })` | ping, neighbors-fetch, maybeAct |

Plus: a reset while *writing* (announce swallows, leave propagates — both release); a reset queued
behind an over-cap chunk; the abandoned `iter.next()` rejecting after the read already ended; and
the same failures observed at the service, through `routeAct`'s forward and
`probeNeighborLatency`.

Every stub stream implements `close()` **and** `abort()` with call counters — the existing stubs in
`rpc.protocols.spec.ts` deliberately omit both — because release-exactly-once is one of the
invariants.

## Invariants pinned (must survive `15-rpc-shared-helper`)

- **A partial payload is never parsed as a whole message.** Every truncated-reply case asserts the
  ghost fields present in the truncated bytes (`ghost-succ`, `size_estimate: 42`, `ghost-anchor`)
  do **not** appear in the result.
- **The stream is released exactly once**, and by the right call: `close()` when nothing aborted,
  `abort()` once a signal (deadline or caller) fired. Asserted as one `{ closes, aborts }` value
  per case.
- **No unhandled rejection escapes** — a suite-wide `process.on('unhandledRejection')` guard,
  checked in `afterEach` (after one tick) and removed in `after`. One case exists purely to arm it:
  a complete reply read via the end-state poll, whose abandoned `iter.next()` rejects 40 ms later.
- **Our own cancellation is never evidence about the peer** — an abort landing *mid-stream* (bytes
  already buffered) records no contact strike, no relevance decay, no backoff, no `pingsFail`; with
  a live-run reset as the non-vacuity contrast.
- **A reset is a failed contact; an undecodable reply never demotes to `foreign`.** Both service
  cases assert `negotiateFailures === 0` and `membership === 'member'`.

## Known gaps — treat the suite as a floor

1. **The byte-count assertion the ticket asked for is not deterministic at a sender, and the test
   says so.** `expectStallRejection` accepts either arm. Reason: the whole-RPC deadline is armed
   first and `readAllBounded`'s read deadline is computed from the *same* `timeoutMs` a moment
   later, so the deadline signal essentially always wins and the error is a `DeadlineExpiredError`
   carrying no byte count; the byte-count message (`read timed out after Xms (N bytes read)`) is
   reachable only when both land in the same millisecond, or from a direct `readAllBounded` call
   with a shorter read budget (already pinned at `payload-bounds-ttl.spec.ts:82`). Worth a
   reviewer's judgement on whether the sender-level byte count is worth making reachable at all.
2. **`releaseRpcStream`'s un-aborted arm is still untested and still unbounded** — `await
   stream.close()` with no signal against a remote that stopped reading. That is an open arm of
   `15-rpc-shared-helper` ("closing the stream is the one step the time limit does not cover"). Per
   the ticket, no test was written that would hang on it. A stub whose `close()` never resolves
   would hang the run today, which is exactly the finding.
3. **`sendMaybeAct` reports two `close()` calls, not one** — the request flush inside its `try`
   (`maybe-act.ts:64`) plus the release in its `finally`. Pinned as harmless, and the
   exactly-once invariant is therefore worded "closed or aborted, never leaked" rather than
   "close called once". A reviewer may reasonably want the second close made observably a no-op
   instead.
4. **One real-transport case only**: `fetchNeighbors` against a handler that writes half a
   snapshot and closes (asserts empty result, promptness well under the RPC budget, and that the
   outbound stream is gone from `Connection.streams`). Half-replies over a real transport for
   *ping* and *maybeAct* are not covered, and **no real-transport reset mid-stream** is covered at
   all — the helpers have no way to make a live peer reset a stream mid-write. So the reset shape
   rests entirely on stubs; the missed-EOF bug is the precedent for that being a real risk.
5. **Inbound handlers are not touched.** `15-rpc-shared-helper`'s "Handler error paths leak
   streams" arm stays unpinned: every handler's `catch` only logs, and nothing here asserts what a
   handler does with a truncated *request*.
6. **Write failures are synchronous only.** The announce/leave arms use a `send()` that throws
   immediately; a write that fails asynchronously (backpressure / drain, `15-rpc-shared-helper`'s
   backpressure arm) is not modelled.
7. **Service-level cancellation is covered on the ping path only** (`probeNeighborLatency` with the
   abort landing mid-read). The maybeAct forward's cancellation is covered in `dead-state.spec.ts`,
   but only *before the dial*, not mid-stream.
8. **The service cases lean on `getConnections` monkey-patching** (the same device
   `test/helpers/maintenance-rig.ts` uses) plus `as unknown as { … }` casts to reach private
   members. Consistent with the house test style, but it is stub-shaped coupling: a refactor that
   stops routing every outbound RPC through `openRpcStream`'s connection lookup silently
   disconnects these cases from the code.
9. Two logs were written to the git-ignored, self-pruning `tickets/.logs/`
   (`6.1-rpc-stream-error-tests.test.log`, `…full.log`). Nothing else was left in the tree.
