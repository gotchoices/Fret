difficulty: medium
---

Follow-on from `sim-joiner-placement`. That fix was real — mid-run joiners were all landing in a
shrinking sliver of the ring instead of spreading around it — but the guard shipped alongside it
measured the **largest gap** between adjacent peers, which does not move when joiners pile up
(the surviving evenly-placed initial peers still hold the largest hole down). On the pure
batch-join case the buggy and fixed placements produced bit-identical readings.

## What changed

**`test/simulation/fret-sim.ts`** — one new `PlacementStrategy` variant, `'clumped-joiners'`
(union at line 46; the `generateCoord` case at ~line 239). It reproduces the pre-fix placement
deliberately: initial peers spread evenly exactly as `'uniform'` does, joiners land at
`index / (index + 1)` of the ring. Written as the literal `index + 1` rather than read back off
the mutable `nextPeerIndex` counter, so the intent survives a future change to when that counter
is bumped. Nothing else in the simulator changed; `'uniform'`, `'clustered'` and `'skewed'` are
untouched.

**`test/churn-scenarios.spec.ts`** — the old largest-gap case is gone. Two cases replace it:

- `uniform placement keeps a batch of joiners spread across the ring` — `churnRatePerSec: 0`,
  one batch join of 10 at t=3000.
- `uniform placement keeps churn-driven joiners spread across the ring` — `churnRatePerSec: 2`,
  no batch join. Separate because `handleChurn` calls `handleJoin` for every leave, so
  churn-driven joins run the same placement path, and a statistic can pass on a mixture while
  being blind to one arm of it — which is exactly what happened before.

Both call one shared helper (`assertPlacementSeparates`) which, for each of five seeds, runs the
scenario **twice** — once under `'uniform'`, once under `'clumped-joiners'` — and asserts *both*
directions: the shipped placement reads at or under the threshold, the clumping placement reads
over it. The statistic is `maxPeersInOneSpacingArc`: scan an arc one even-spacing wide
(ringSize / peers) anchored at each peer in turn, wrapping, and take the largest count.

## Measured (this is the calibration, both arms)

Config `n: 40, k: 15, m: 8, durationMs: 10000`; seeds 8008, 8009, 8010, 4242, 99.

| join pattern | uniform (fixed) | clumped-joiners (the bug) |
|---|---|---|
| batch burst | 3, 3, 3, 3, 3 | 11, 11, 11, 11, 11 |
| steady trickle | 3, 3, 3, 4, 3 | 18, 18, 16, 16, 16 |

Worst fixed reading 4, best buggy reading 11, nothing in between. Threshold **7** sits 1.75x
above everything the fixed placement produced and 1.57x below everything the bug produced. Both
arms are in the source comment beside the threshold, not just the passing one.

These numbers reproduce the ticket's own measurements exactly, so the two independent
measurements agree.

## Acceptance — run, not assumed

- **Red arm:** the pre-fix line was restored by hand in `generateCoord`
  (`isJoin ? this.uniformCoord(index, this.nextPeerIndex) : ...`) and the two cases run.
  Both failed, at the first seed, with the readings the table predicts:
  `batch burst seed 8008: uniform placement packed 11 peers into one even-spacing arc, expected <=7`
  and `steady trickle seed 8008: ... packed 18 peers ..., expected <=7`. `0 passing, 2 failing`.
- **Green arm:** line reverted, same two cases, `2 passing`. Full file
  `test/churn-scenarios.spec.ts`: **9 passing (44s)**. `npx tsc --noEmit` clean.
- The hand-restore was reverted; `git diff` on `fret-sim.ts` is 19 insertions (the new strategy
  variant and its comment) and nothing else. Confirmed by grep — no leftover.
- Note the `'clumped-joiners'` arm makes this permanent: the guard's separating power is now
  re-proved on every run, so a future change that flattens the statistic fails here rather than
  passing quietly. The manual restore above is a second, independent check of the same thing in
  the direction a real regression would arrive from.

## One judgment call worth checking

The two placement cases run `stabilizationIntervalMs: 5000`, far coarser than the 500ms every
other case in this file uses, and coarser than the ticket's stated config. Reasoning:
stabilization changes neither a peer's ring coordinate nor its alive flag (`handleStabilize`
touches neighbor sets and stores only; coordinates are assigned in `addPeer`, aliveness cleared
in `handleLeave`), so it cannot move this statistic — it is pure wall time here. **Verified
empirically rather than argued**: the entire 20-run table above was measured at both 500ms and
5000ms and every one of the 20 readings was identical, while the two cases' cost went from 100s
to 3s. The file went from 37s (7 cases, before this ticket) to 44s (9 cases).

If a reviewer thinks the coarse cadence is too clever, reverting it to 500ms costs ~97s of suite
time and changes no assertion or reading; the comment at the call site states the reasoning and
the measurement.

## Known gaps — treat the tests as a floor

- **Threshold 7 is calibrated at exactly one config.** n=40 / k=15 / m=8 / 10s, five fixed seeds.
  It is not claimed to hold at other populations or run lengths; both cases hard-code the config,
  so nothing silently reuses the number elsewhere.
- **Five seeds is not a distribution.** The separation is wide (4 vs 11) and every reading is
  stable across seeds, but this is five samples, not a property test over generated seeds.
  Worth a reviewer's judgment on whether that warrants a `fast-check` property.
- **`maxPeersInOneSpacingArc` is O(peers^2)** — 50 peers, so ~2500 BigInt ops per reading, ~10
  readings per case. Negligible at this size; it would not be at simulator scale. Left simple on
  purpose, and it lives in the spec file, not in the simulator, so nothing else can pick it up.
- **The statistic is a maximum, so it is a floor on crowding, not a description of it.** A
  placement bug that spread joiners over two moderately dense slivers rather than one could in
  principle read under 7. The bug this ticket is about converges on a single point, so the
  maximum is the right lens for it; a different placement defect might need a different one.
- The `'clumped-joiners'` strategy is now public surface on `PlacementStrategy`. It is documented
  in place as a deliberate defect kept as a negative control, but it is nonetheless a value a
  future caller could pass by accident.
