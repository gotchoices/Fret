### How each is driven

- **`foreign-protocol`** — real two-node setup. A second `createMemNode()` is started, node A dials
  its multiaddr (so a real connection exists; `fetchNeighbors` is `dial: 'never'` and reuses it),
  and `fetchAndMergeSnapshot` is called against it. Nodes are tracked in a new `extraNodes` array
  and torn down by the existing `afterEach`.
- **`unreachable`** — `withFailingOpen` helper: a stub connection whose `newStream` throws. Counts
  opens, so the test cannot pass by silently taking the `skipped` arm.
- **`timeout`** — nested `describe` that overrides
  `(CoreFretService as any).MAINTENANCE_SNAPSHOT_TIMEOUT_MS` to 50 in `beforeEach` and restores the
  real 1000 in `afterEach`. `withHangingStream` opens fine and never yields a byte (`next()` returns
  a promise that never settles); `readFramed` races each read against its signal, so the fetch's own
  internal deadline ends it. Measured 53ms.

## Deliberate deviations from the ticket — reviewer should weigh these

**The contact-failure arms assert `failureCount` +1, not "relevance decayed".** The ticket asked for
"relevance decayed". That assertion is not writable as stated against a freshly-seeded entry:
`applyFailure` **recomputes** relevance from the health counters (`scoreFailure`) rather than
scaling the old value down, and `seed()` creates an entry whose counters are all zero and whose
relevance is 0 — so the post-failure relevance is a computed value that goes *up* from 0, not down.
Asserting a decrease would have failed; asserting an increase would pin an artifact of the seed
rather than the behavior. `failureCount` is the unambiguous, direction-free proof that `applyFailure`
ran. **A reviewer who disagrees should say so** — the alternative is to seed a success first so
relevance starts above the post-failure value, at the cost of more setup and a coupling to the
scoring formula's shape.

**`foreign-protocol`'s second node runs no `FretService` at all.** The ticket suggested constructing
one and not starting it. An unstarted service registers nothing, so it is indistinguishable from a
bare node at the wire while costing the test a construction it never uses. The arm needs exactly
"connected and reachable, no handler for `/optimystic/<network>/fret/1.0.0/neighbors`" — reasoning is
in a comment at the test.

**`foreign-protocol` asserts the single increment, not demotion to `foreign`.** Explicitly permitted
by the ticket ("less test code"). Consequence: the threshold-of-3 demotion path is not exercised
here. It is exercised elsewhere — `test/ring-membership.spec.ts` — but not through
`fetchAndMergeSnapshot`.

## Known gaps — treat the tests as a floor

- **The contact-failure spacing guard is not exercised.** `applyContactStrike` ignores a failure
  landing within `CONTACT_FAILURE_MIN_SPACING_MS` (500ms) of the last counted one. Every test here
  makes exactly one call against a fresh entry, so the guard never bites. A regression that removed
  the spacing check would leave all six tests green. Same for `applyMembershipSignal`'s
  `NEGOTIATE_FAILURE_MIN_SPACING_MS`. Worth a reviewer's judgement on whether that belongs here or
  is adequately covered where those guards live.
- **The timeout test's wall-clock assertion is coarse**, deliberately: `elapsed < REAL_TIMEOUT`
  (1000ms) against an override of 50ms. It proves the override took effect and the test is not
  waiting out the real default; it would *not* catch an override that silently became, say, 900ms.
  A tighter bound was avoided because it would pin scheduler timing rather than the arm.
- **No test drives these arms through a real stabilization tick.** All six call the private
  `fetchAndMergeSnapshot` directly via `as any`. The tick-level wiring (`probeAndFetch`, the pooled
  phase 1) is covered by `test/stabilize-concurrency.spec.ts`, not here.
- **`extraNodes` is a new teardown seam.** Only the `foreign-protocol` test uses it. If it goes
  unused again it is dead weight; if a future arm needs two nodes it is the right shape.
