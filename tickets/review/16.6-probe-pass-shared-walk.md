## What changed

`stabilizeOnce`'s phase-2 target selection was `[...this.classifyTargets(), ...this.reprobeExcludedTargets()]`
— three full `store.list()` materializations per tick (classify + the two `reprobeOffRingTargets`
arms), at up to ~3 ticks/second, all three returning `[]` in single-network steady state.

- **New `FretService.phaseTwoTargets()`** (`fret-service.ts`, immediately above `classifyTargets`)
  is the tick's only phase-2 selector. It reads three O(1) store counts —
  `countByMembership('unknown')`, `countByMembership('foreign')`, `countByState('dead')` — and
  returns `[]` without walking when all three are zero. Otherwise it takes **one** `store.list()`
  and passes that array to all three arms.
- **`classifyTargets(entries = this.store.list())`** and
  **`reprobeExcludedTargets(entries = this.store.list())`** now take the walk as a defaulted
  parameter; **`reprobeOffRingTargets(entries, isCandidate, budget)`** takes it as a required first
  parameter (it is private-called only from `reprobeExcludedTargets` — grep-confirmed). Bodies
  changed by one line each (`this.store.list().filter` → `entries.filter`). No budget, predicate or
  ordering changed.
- The superseded `NOTE:` inside `classifyTargets` (the one describing the three walks) is deleted,
  and the comment above the `budget.signal.aborted` early return in `stabilizeOnce` now says "at
  most one store walk" instead of "three".
- `docs/fret.md`: the *Two phases* bullet (Stabilization and churn handling) states the zero/one
  walk cost and why the counts are a sound proof; the A2 per-label-counts bullet points at it. The
  separate-budgets invariant wording is unchanged.

## Why a zero count is a sound proof

Each arm's predicate is a *narrowing* of one single-field label (classify ⊂ `unknown`, foreign arm
⊂ `foreign`, dead arm = `dead`); the extra conditions — `id !== self`, `state !== 'dead'`,
`backoffPenalty === 0`, dialability — only remove candidates. So `count === 0` ⇒ that arm selects
nothing. Three single-field counts suffice; no compound bookkeeping.

## Use cases to validate

- **Steady state is free.** A table of all-`member`, non-dead peers: `phaseTwoTargets()` returns
  `[]` and `store.list` is never called.
- **Single-node ring.** Self alone (seeded `member`, never dead) contributes to none of the three
  counters — zero walks, empty selection.
- **Re-arming.** An `unknown` promoted to `member` drops the count to zero and the next call walks
  nothing; a `member` escalated to `dead` through three spaced `applyContactStrike`s lifts the dead
  count and the dead arm selects it on the *very next call*, not one tick later.
- **Non-empty costs exactly one walk**, and the ids selected equal what the two selectors return
  when called separately (`classifyTargets()` + `reprobeExcludedTargets()` bare) — order included.
- **Bare selector calls still work.** `dead-state.spec.ts:592,607`, `failure-recovery.spec.ts:84`
  and `stabilize-concurrency.spec.ts:160,161` call these through `(svc as any)` with no arguments;
  that is what the defaulted parameter buys, and those three specs pass **unmodified**.
- **Disjointness unchanged.** A peer that is both `foreign` and `dead` still belongs to the dead arm
  alone; the four per-tick candidate sets (near / classify / foreign / dead) are still pairwise
  disjoint — the property that makes pooled probing safe against the lost-increment race on the
  score/strike counters.
- **Ordering unchanged.** `classifyTargets` still orders by ascending `lastAccess`; each re-probe
  arm by ascending backoff factor. The existing rotation test passes untouched.

## Known gaps / where to look hardest

- **The walk-count spy is a monkey-patch on the store instance** (`(store as any).list = …`).
  It is restored in a `finally` and the rig builds a fresh service per test, but it is the least
  robust part of the new tests — a reviewer should confirm it cannot leak across cases.
- **The `member → dead` test winds `lastContactFailureAt` back to 0 between strikes** rather than
  sleeping 500 ms three times. That deliberately bypasses the spacing guard (which is pinned
  independently in `dead-state.spec.ts`); the test is about the count gate, not the spacing.
- **No test drives the gate through a real `stabilizeOnce`** — all five call `phaseTwoTargets()`
  directly. The tick-level coverage that phase 2 still probes the right peers is the pre-existing
  disjointness / truncation / rotation tests, which pass unchanged.
- **The gate reads counts that a concurrent write could move between the three reads.** All of it
  is synchronous single-threaded JS with no `await` between the reads, so this is not reachable
  today; worth a glance if anyone ever makes `phaseTwoTargets` async.
- A count wrong *high* costs one wasted walk; wrong *low* silently stops the pass selecting. The
  counts themselves are the previous ticket's property test (`digitree.invariants.spec.ts`), not
  re-proved here.
