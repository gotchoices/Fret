Regression tests for the fix in `framed-read-false-truncation`, which made `readFramed`
(`packages/fret/src/rpc/protocols.ts:526`) dispatch on the source type and deleted the 20 ms
`EOF_POLL_MS` poll that used to raise `FrameTruncationError` for a reply that had in fact
arrived.

**One of the four tasks in the source ticket was not done** — see *Not done* below. It was split
into `implement/framed-read-two-node-smoke`, which is queued and independent of this review.

## What landed

### Forced-race seam test (the load-bearing guard)

`test/rpc.protocols.spec.ts`, inside the `RPC deadlines` describe block, beside the other
`readFramed` tests: *"readFramed returns a buffered frame even while the stream reports itself
finished"*.

A stub stream that holds `readBufferLength: 0` and `remoteWriteStatus: 'closed'` for the whole
test — the stream-level state the deleted poll read as truncation — while handing over a real
length-prefixed frame. The test asserts the decoded body comes back rather than a
`FrameTruncationError`.

Two structural properties make it a genuine regression guard rather than a shape assertion, and
both are worth a reviewer's attention because both are easy to break by "tidying":

- **All six functions `isMessageStream` (`protocols.ts:349`) requires are present** — `closeRead`,
  `addEventListener`, `removeEventListener`, `send`, `push`, `log`. Drop any one and the stub
  falls through to the *iterable* path, which the fix never touched, and the test silently stops
  testing the bug. The `expect(iterated).to.equal(false)` assertion is what pins this: it proves
  the stream path is what produced the frame.
- **The frame is dispatched synchronously, at listener-registration time.** `byteStream()`
  registers the `message` listener and `readFramed` then calls `bs.read({bytes: 1})`, whose body
  runs synchronously down to its end-of-stream gate — there is no `await` in between. With the
  stream reporting finished, that gate throws unless the bytes are *already* in the reader's
  buffer. A `setTimeout` delivery would arrive after the throw. The comment in the test says so
  explicitly, at length, because the obvious "cleanup" is to make it async.
  - Reviewer note: this is not gaming the harness. It models the real transport — bytes that
    already arrived are dispatched to a reader the instant it subscribes, and `readBufferLength: 0`
    is the correct post-dispatch state, since the bytes left the stream's buffer and now sit in
    the reader's. That equivalence is the thing to check, and it is the test's weakest joint.

The stub also carries a `[Symbol.asyncIterator]` yielding the same frame after ~50 ms, present
*only* so the stub would have failed under the pre-fix code (which raced `lp.decode` over the
iterable against the 20 ms poll; at 50 ms the poll won).

### Restored close-then-read shape in `sendRaw`

`test/rpc.handler-fuzz.spec.ts` (~line 1034). The half-close now runs **before** the read starts,
and the stale comment above it — which explained that "closing first can lose a reply" — is gone,
since that was a description of the now-fixed defect. `RawResult` and every caller are unchanged.

### Codec pull-count measurement re-checked, not assumed

`test/rpc.codec-properties.spec.ts` `countingSource` (~692) returns a plain async generator, so it
lacks the six message-stream functions and stays on the iterable path. Confirmed **by running it**,
not by reasoning: the whole file passes, including the property test asserting an over-cap frame
costs exactly one pull.

## Known gaps for the reviewer

- **The new test's failure under the pre-fix code was never executed.** The reasoning is written
  down (pre-fix `readFramed` raced `lp.decode` against the 20 ms poll; the stub's iterator yields
  at ~50 ms) and comes from reading `git show 377c8fe:packages/fret/src/rpc/protocols.ts`, but no
  run against that revision was performed. If a reviewer wants certainty that the guard bites,
  checking out the pre-fix `protocols.ts` and running this one test is the direct check.
- **One test, one seam.** The guard covers `readFramed` against a stub. It does not cover the same
  invariant over a real libp2p transport end to end; that is what the deferred smoke matrix was
  for.
- The `sendRaw` reordering changes the shape of every handler-fuzz case that goes through it
  (~12 call sites). They all pass, but the reordering is a behavioral change to the harness, not
  a comment edit — worth a skim that no case was passing for the old reason.
