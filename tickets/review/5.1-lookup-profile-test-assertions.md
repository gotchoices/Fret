diff against `src/` is a finding, not a change to review.

All five arms of the implement ticket landed and every new assertion holds against the service as

finding to report about the service.

## What changed

### `test/iterative-lookup.spec.ts`

- **`a digest-only probe ends exhausted, never completes, and collects real anchors`** (was
  `yields near_anchor or exhausted for a digest-only probe`). The old three-way disjunction
  (`near_anchor` | `exhausted` | `complete`) is gone. Now asserts, all four:
  - terminal event is exactly `exhausted`;
  - `complete` appears nowhere in the stream (a digest-only lookup has no activity to complete, and
    `complete` needs a commit certificate);
  - at least one `probing` event, and every `probing.peerId` is one of the two other nodes' ids —
    this is what stops a lookup that probed nobody from passing;
  - at least one `near_anchor` carrying **non-empty** `anchors` *and* non-empty `cohort_hint`,
    which distinguishes a real in-cluster reply from the empty `staticReject` shape a guard
    rejection returns.
  - Every failure message interpolates the event trail (`types.join(' -> ')`), so a future failure
    reports what actually happened rather than just `expected 'x' to equal 'exhausted'`.

- **`runs the activity on exactly one peer, and never on the initiator`** (was `returns complete
  when activity handler is set and in-cluster`). The old version installed handlers on all three
  nodes and then never counted invocations at all — zero or three deliveries both passed. Now:
  - per-service invocation counters;
  - lookup completes with the certificate the handler returned (`cert-ok`);
  - **total across all three services is exactly 1** — one peer performs the work, the certificate
    travels back, a forwarding hop must not re-run it;
  - **initiator's own count is 0** — `iterativeLookup` seeds `visited` with self and always sends,
    never performing the activity locally.
  - Asserts the count and the result, deliberately **not** a specific event sequence: the
    payload-inclusion heuristic can attach the activity to the very first probe on a tiny ring, in
    which case there is no `activity_sent` event at all.

- **Deleted `Breadcrumb rejection`** (1 test) and **`Correlation ID dedup`** (1 test). Both drove
  `routeAct`, which is the wrong entry point — the breadcrumb-loop guard and the dedup cache both
  live in `handleMaybeAct`, one layer above. A header comment at the top of the file now names
  where each behavior is actually pinned (`pick-anchors.spec.ts` and `maybeact-dedup-phases.spec.ts`
  respectively) so the next reader does not re-add them.

### `test/profile.behavior.spec.ts`

- **Deleted the `Preconnect budget` describe** (2 tests: Core 6, Edge 3). Both put an
  empty-store service into active mode and asserted `pingsSent <= budget` — with no peers the
  count is 0, so the assertion held for any budget. A comment in its place points at
  `preconnect-concurrency.spec.ts:173-216`, which seeds 16 peers through the shared maintenance rig
  and asserts `pingsSent` equals the budget **exactly** for both profiles.

### `test/fret.mesh.spec.ts`

Rewritten from a smoke test (`getDiagnostics()` is truthy — passes even if stabilization never
runs) into the real spec for the one thing this file uniquely covers: FRET over a **real TCP
transport**, with a third libp2p node hosting no FRET service as a negative control.

- Fixed `setTimeout(1500)` replaced with `waitFor` (`test/helpers/wait-for.ts`) on a convergence
  predicate, 20 s budget / 50 ms poll.
- Asserts `a` and `b` classify each other `member`, **and** both have `pingsOk > 0` — the proof
  that the label came from a completed namespaced RPC rather than from assumption. `pingsOk` is
  inside the `waitFor` predicate, not asserted after it, so the spec cannot race a label landing
  one tick ahead of the ping diagnostic it implies.
- Asserts the service-less node `c` is present in `a`'s store (entry exists) and its membership is
  **not** `member`. Deliberately not asserted `foreign` — that needs three time-separated
  negotiate failures (~7 s) and would make the spec slow and flaky.
- Membership is read through a helper that tolerates a missing entry (`getById(id)?.membership`)
  rather than throwing on `undefined`, because over TCP with no `identify` service the entry
  arrives asynchronously via `peer:connect`.
- Nothing is asserted about `a`'s `pingsFail`: `a` keeps failing to negotiate against `c` in the
  background, and that count depends on how many probe passes happened to run.

## Known gaps — please probe these

- **`total handler invocations === 1` is asserted on a live 3-node ring, not forced.** It holds
  because the ring routes the activity once and the certificate travels back. It is a genuine
  property, but it is proved by observation of a real mesh rather than by a stub that would make a
  double-delivery impossible to route. If you want the stronger guarantee, the forwarding hop
  would need a rig that can inject a duplicate.
- **The three `iterative-lookup` specs still use a fixed `await new Promise(r => setTimeout(r,
  2000))` warm-up** (lines 51, 94, 137) rather than a `waitFor` on convergence. Untouched on
  purpose: `plan/21-cleanup-tests` owns setup-boilerplate consolidation in this file, including its
  local `createNode`. Worth confirming you agree that boundary, because these three sleeps are the
  most plausible remaining flake source in the file — a slow CI box could in principle probe before
  the ring converges. Nothing in the run so far has flaked (each ran ~2.0 s, i.e. the sleep
  dominates).
- **`fret.mesh.spec.ts` ran in 1.58 s against a 20 s `waitFor` budget and a 30 s mocha timeout**, so
  headroom is large — but this is the only spec in the suite that binds real TCP sockets
  (`/ip4/127.0.0.1/tcp/0`), so it is the one most exposed to a constrained CI sandbox. If it ever
  hangs, look at socket binding before looking at the predicate.
- **The negative control asserts `!== 'member'`, not `=== 'unknown'`.** That is deliberate (see
  above) but it means the spec would still pass if `c` were somehow classified `foreign` early. If
  you think that distinction is worth pinning, it needs a longer, flakier wait — a tradeoff, not an
  oversight.
- **The deleted blocks' replacements were verified by reading, not by mutation testing.** I
  confirmed `pick-anchors.spec.ts:175` drives `handleMaybeAct` and asserts the empty static shape,
  and that `maybeact-dedup-phases.spec.ts` sends over the wire and covers both phases plus the
  refusal-is-not-cached rule. I did not break the guards to confirm those specs actually fail —
  worth a spot check if you want certainty that the coverage genuinely moved rather than
  disappeared.
- **`test/README.md` claims a fixed passing count and is now four further out of date.** Left
  untouched per the implement ticket; `plan/21-cleanup-tests` owns that file. Do not read the
  mismatch there as a regression.

  path and confirm the digest-only spec fails on `terminal event` rather than passing.
- Break the deliver-once claim: have a forwarding hop re-run the activity and confirm the total-1
  assertion fires.
- Break the initiator-never-acts claim: remove self from the `visited` seed
  (`fret-service.ts:2748`) and confirm `fired[0]` assertion fires.
- Break the mesh claim: register no RPC handlers on `b` and confirm the `waitFor` times out with
  its message rather than the spec passing on a truthy diagnostics object.
