## Finding (A) — diagnosis complete; only the disposition is left

`15.32c` established the effect reproduces: changing exactly one thing in `registerPing`
(`serve: (connection) =>` → `serve: async (connection) =>`) turns *Leave amplification cap → the
classification pass probes and promotes a replacement recorded by a leave*
(`test/churn.leave.spec.ts:540`) from passing to failing on `pingsOk > 0`, in ~297 ms.

`15.32d` then named the outcome variant and the mechanism with a standalone two-node scratch spec
(two `createMemNode`s, three `registerJsonHandler` reply-only protocols differing only in the
`serve` shape, driven by `rpcRequest`; the spec was deleted before handoff). **Result,
deterministic, 6 calls per shape:**

| reply-only `serve` shape | `rpcRequest` outcome |
|---|---|
| `() => Promise.resolve(reply)` (today's `registerPing` / `registerNeighbors`) | `ok` |
| `async () => reply` | `ok` |
| `async () => { await Promise.resolve(); await Promise.resolve(); return reply }` | `decode-error` (`FrameTruncationError`) |

So the effect is **not** about `async` versus a bare arrow, and it is **not** the implementer's
stated `negotiateFully: false` theory. It is a threshold in how many microtasks elapse between the
inbound handler being invoked and its first `sendFramed` write: two extra ticks is enough, one is
not. The reply *is* written — the caller reads it as a **truncated frame**, i.e. the caller's
`readFramed` concludes the remote finished writing while the reply bytes are still in flight. That
points at `remoteFinishedWriting` and the `EOF_POLL_MS` poll in
`packages/fret/src/rpc/protocols.ts`, not at `openRpcStream` and not at the two handler bodies.

The churn-spec symptom follows exactly: `decode-error` is scored as proof of life
(`noteAnsweredOnProtocol` → `membership: 'member'`) but never reaches `applySuccess`, so `pingsOk`
stays 0 while the membership assertion still passes — precisely what `15.32c` observed. The
`registerPing` arrow change is a trigger, not the cause; it merely pushed that path over the
two-tick threshold.

**This is a latent defect, not a tripwire.** Any handler body that awaits twice before writing
loses every reply, silently, on a healthy connection; nothing in the seam's contract forbids that,
and `pingReply` already awaits a caller-supplied `getSizeEstimate` provider (one hop today, and an
async provider is a legal implementation of `SizeEstimateProvider`).

Disposition, per *Architecture first*:

- Climb to the **boundary invariant** rung. The root site is `readFramed`'s end-of-stream
  recognition in `src/rpc/protocols.ts`; the ticket is the invariant ("a frame the remote actually
  wrote is never reported as truncated"), pinned by a direct test that varies the responder's
  pre-write microtask depth (0, 1, 2, 4 awaits) against a real two-node pair — the scratch spec
  above is the skeleton, and it fails at the seam rather than three subsystems away.
- File it into `tickets/fix/` (reproducible defect, root site named) with `repro: verified` and the
  table above. Run the site-claim grep over `tickets/{backlog,fix,plan,implement,review}` for
  `readFramed` / `remoteFinishedWriting` first — `15.4-rpc-byte-cap-tightening` touches
  `readFramed`'s caps and may already be the theme ticket to append an arm to.
- Then update or replace the two reply-only `NOTE:` blocks (`src/rpc/ping.ts`,
  `src/rpc/neighbors.ts`) so they state what was actually established: the hazard is microtask
  depth before the first write, the failure surfaces at the caller as a truncated read, and the fix
  lives in `readFramed` — not "keep this arrow non-async" folklore.

Do **not** re-run the reproduction; it is settled. Spend the budget on filing and on (B)–(D).
