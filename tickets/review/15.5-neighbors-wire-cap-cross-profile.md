description: A lightweight node and a server-grade node could refuse each other's neighbor-list messages because each sized its incoming-message limit for what it would send itself. The limit is now one network-wide number, so both accept the same messages.
files: packages/fret/src/rpc/validate.ts, packages/fret/src/rpc/neighbors.ts, packages/fret/src/rpc/request.ts, packages/fret/src/service/fret-service.ts, packages/fret/test/rpc.codec-properties.spec.ts, packages/fret/test/profile.behavior.spec.ts, docs/fret.md
difficulty: medium

## What changed

The neighbors per-message byte cap was one number per operating profile — Core 16 KiB, Edge
8 KiB — each derived from the largest snapshot *that profile emits*. But the cap governs an
**incoming** message, so it has to cover the largest message any peer may legitimately send, and
Edge and Core nodes talk to each other. A Core node with more than ~5.1 KiB of application
metadata (`setMetadata`) therefore emitted a legal snapshot that every Edge peer refused at the
length prefix — silently, one-directionally, and with no way for the sender to learn why.

Second arm, same root cause: one node read neighbor snapshots on two paths with two different
numbers. The announce (inbound push) path used the profile number; the fetch (reply to our own
request) path hard-coded 16 KiB and took no profile input. So an Edge node **accepted** an 11 KiB
Core snapshot when it asked for one and **refused** the identical snapshot when the same peer
pushed it.

Fix — one acceptance number, profile-split emission budgets:

- **`MAX_NEIGHBORS_BYTES = 16 * 1024`** added to `src/rpc/validate.ts`, beside the maybeAct
  constants, with the derivation in its doc comment (Core worst legal emission 11,575 bytes at the
  merge caps: 16/16/8 id lists + 8 KiB metadata + 256 bytes reserved for the unimplemented `sig`;
  ~4.8 KiB headroom).
- Every neighbors read path now takes that constant — `FretService.maxBytesNeighbors()` (profile
  branch deleted, kept as a method for symmetry with `maxBytesMaybeAct()`), `fetchNeighbors`'
  `maxBytes`, and `registerNeighbors`' `maxBytes` default. No literal byte count survives on any
  neighbors path.
- `MAX_SNAPSHOT_METADATA_BYTES_CORE` / `_EDGE` are unchanged in value; their doc comments were
  rewritten from "sized against the profile's neighbors wire cap" (the mistaken rule) to what they
  actually are — *emission budgets* — naming the invariant they must keep:
  `largest emission of any profile <= MAX_NEIGHBORS_BYTES`.
- `DEFAULT_MAX_BYTES` in `src/rpc/request.ts` stays 8 KiB; its comment no longer justifies the
  value by "matching the neighbors cap on the Edge profile" (which no longer exists) and now
  stands on its own terms — a conservative floor for a direct consumer who passed no cap.
- `docs/fret.md`, *Stream management*: the "16 KiB Core / 8 KiB Edge, sized to its profile's
  snapshot caps" sentence is replaced with the corrected rule. The *Operating profiles* and
  *Security* sections were swept; neither restated the per-profile neighbors number (their
  snapshot-cap statements are about **emission** caps and are still correct).

### The tests that pin the relation

`test/rpc.codec-properties.spec.ts`, *the largest legal message of each protocol encodes under its
wire cap*:

- Both snapshot cases now carry `metadata` at that profile's **full** allowance, sized so
  `JSON.stringify(metadata)` equals the allowance exactly — that is the quantity
  `FretService.snapshot` measures, so sizing the whole snapshot instead would measure the wrong
  thing. Helper `metadataAtAllowance` asserts the sizing itself.
- Both assert against `MAX_NEIGHBORS_BYTES`, not a per-profile number. Id lists stay at the
  *merge* caps (Core 16/16/8, Edge 8/8/6) rather than the narrower emission caps the service
  currently uses — the conservative direction, commented as such.
- New case *both profiles accept neighbors messages up to the same cap* constructs a Core and an
  Edge service and requires both `maxBytesNeighbors()` to be `MAX_NEIGHBORS_BYTES`, so
  re-introducing a profile split fails here rather than on the wire.

Arm B behavioral pin, in *merges an under-cap announce and refuses an over-cap one* (the `WireRig`
receiver is Edge): an announce padded to ~11 KiB — over the old Edge cap of 8 KiB, inside a legal
Core emission — must be acknowledged and merged by the Edge receiver. The 70 KiB over-cap case
stays as the refusal side. The inline `expect(maxBytes, ...)` in that test and the frame-prefix
case-table entry now read `MAX_NEIGHBORS_BYTES`.

`test/profile.behavior.spec.ts`: the two cases asserting Core 16384 / Edge 8192 are collapsed into
one asserting both profiles return `MAX_NEIGHBORS_BYTES`.

### Repro confirmation, stated precisely

I re-applied the old profile branch and ran the announce test: it fails. But it fails at the
**first** assertion in that test (`neighbors wire cap`, expected 16384, actual 8192, around line
916), which precedes the 11 KiB merge case — so what was directly observed failing pre-fix is the
cap value, not the merge assertion behind it. The merge assertion's pre-fix behavior is
*inferred*: an ~11.3 KiB frame against an 8192-byte cap is refused by `readFramed` at the prefix,
`sendRaw` returns `undefined`, and `to.not.equal(undefined)` fails. A reviewer wanting the
stronger observation can delete or reorder that first assertion while the branch is restored.

## Known gaps and things to look at

- **Nothing checks an outgoing snapshot against the acceptance cap before writing it.**
  `announceNeighbors` is write-only. The encoding test above is the entire guard that a legal
  emission fits, which is why it must build the largest legal message rather than a typical one.
  Deliberate per the plan, but it means a future widening of the emission caps or the metadata
  allowance is caught only by that test, never at runtime.
- **The Edge worst-case figure (6,301 bytes) in the `_EDGE` doc comment is inherited from the
  plan's measurements, not re-measured here.** The new tests prove both profiles land *under*
  16 KiB; they do not pin either exact byte count. Same for the 3,371-byte fixed-field figure in
  the `MAX_NEIGHBORS_BYTES` derivation — worth a spot-check if a reviewer wants the arithmetic
  independently confirmed.
- **`metadataAtAllowance` equates characters with bytes.** It asserts on
  `JSON.stringify(value).length` while `FretService.snapshot` measures
  `TextEncoder().encode(...).byteLength`. The payload is pure ASCII so the two coincide, but a
  future edit that puts non-ASCII in that helper would make the test measure a smaller quantity
  than the service does.
- **`src/rpc/request.ts` references `{@link MAX_NEIGHBORS_BYTES}` in a doc comment without
  importing it**, so the link does not resolve to a symbol. Cosmetic; `tsc` does not check it.
  Worth a look if the project ever runs an API-doc generator.
- **Over-cap metadata is still silently dropped from the outgoing snapshot** with an error log,
  and the peer never learns of it. Pre-existing, already recorded as a `NOTE:` at
  `FretService.snapshot`, and explicitly out of scope here.
- Message signing (`tickets/backlog/impl/5-message-signatures`) will populate the snapshot's
  currently-empty `sig`. The 256-byte reservation is inside the derivation and is called out in
  the constant's doc comment, so signing should not disturb the number — but that is arithmetic,
  not a measurement of a real signature.

No pre-existing test failures were encountered.
