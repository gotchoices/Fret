## What landed

The three outbound RPCs that read a reply now validate it with the parser written for it in
`15.31`, instead of casting the decoded JSON. Previously each sender did `decodeJson<T>(b)` — a
bare cast — so any field of any type reached the caller as if it were a well-formed reply.

### The decision the ticket left open: **adapter**, not an `rpcRequest` change

Took the ticket's recommended option. `parseOrThrow<T>(parse: Parser<T>, msg: unknown): T` lives
beside the parsers in `src/rpc/validate.ts` and throws a named `ReplyRejectedError` when the parser
returns `undefined`. Each sender's decode is now
`async (b) => parseOrThrow(parseX, await decodeJson(b))`.

Why not the alternative (`rpcRequest` treating a returned `undefined` as `decode-error`): it is
simpler at three call sites but makes `undefined` unreturnable as a legitimate reply for every
consumer of a publicly exported helper. `rpcRequest` is untouched by this ticket.

The error carries a stable `name` and ships with `isReplyRejectedError(err)` — identity, not
message text — matching the `isFrameTruncationError` / `isPayloadTooLargeError` house rule.

### Sender by sender

| Sender | Before | Now |
|---|---|---|
| `sendPing` | `decodeJson<PingResponseV1>` then `{ ok: Boolean(r.ok), … }` | `parsePingResponse`. **The `Boolean` coercion is gone** — `ok: 1` / `ok: 'true'` is now `decode-error`, not a confident `ok: true` about a peer that never said so |
| `sendMaybeAct` | bare cast to `NearAnchorV1 \| {commitCertificate}` | `parseMaybeActReply` |
| `fetchNeighbors` | bare cast to `NeighborSnapshotV1` | caller-supplied parser on the options bag: `opts.parse?: Parser<NeighborSnapshotV1>` |
| `announceNeighbors`, `sendLeave` | write-only | unchanged — no `decode`, no parser |

`fetchNeighbors`' `opts.parse` follows the `registerNeighbors` precedent exactly: same
`makeSnapshotParser({successors: Infinity, predecessors: Infinity, sample: Infinity})` default
("validate the shape, truncate nothing"), same `NOTE:` saying the default is reachable only from
tests. It went on the **options bag** rather than as a positional parameter, so the three existing
test call sites (`test/ring-membership.spec.ts:871`, `test/rpc.protocols.spec.ts:632`,
`test/rpc.stream-errors.spec.ts`) needed no edit at all.

`FretService.fetchAndMergeSnapshot` supplies `makeSnapshotParser(this.mergeSnapshotCaps())` — the
same numbers the merge loop below it slices to, so the parser truncates ahead of the parse-and-hash
loop instead of after it, and the two cannot drift.

### Reply caps — confirmed, as the ticket asked

`parseNearAnchor` caps `anchors` at 8 and `cohort_hint` at 16. Checked against the producers in
`fret-service.ts`:

- `pickAnchors` (`:2453`) returns `[first, second].filter(Boolean)` — **at most 2**. Called from
  both `nearAnchorOnly` (`:2437`) and `buildNearAnchor` (`:2605`).
- Widest cohort-hint producer is `buildNearAnchor` (`:2609`): `right.slice(0,4) ∪ left.slice(0,4)`
  — **at most 8**. `nearAnchorOnly` (`:2441`) emits at most 4.

So the caps are 4× and 2× the largest legal output. A cap provably cannot refuse our own reply, and
there is a test pinning the widest case.

### Exports and docs

`parseOrThrow`, `ReplyRejectedError`, `isReplyRejectedError` and the `SnapshotCaps` type are
exported from the package root beside the parsers (passing a parser in raw is a silent bug for a
consumer too, not a compile error). `docs/fret.md`'s *Wire-shape parsers* section had a paragraph
saying the parsers were "not yet wired" and naming this ticket — replaced with the wired contract,
the sender→parser table, and the adapter rationale.

## Use cases the reviewer should exercise

- **A peer whose encoder is subtly wrong.** Serve a ping reply of `{ok: 1, ts: 1}`. Expect
  `decode-error`, not `ok`. The service scores that as relevance decay only — proof of life, no
  contact strike — so a version-skewed peer stays in the ring and is re-probed.
- **A peer sending a snapshot whose `from` is not a peer id.** `fetchNeighbors` now returns
  `decode-error` where it used to return `ok` with an unusable snapshot. This is the one place the
  change has real blast radius (see gaps) — worth confirming against the merge path.
- **Caller-supplied caps actually truncate.** `fetchNeighbors(..., {parse: makeSnapshotParser({successors: 2, predecessors: 1, sample: 0})})`
  against a reply with 4 successors → `ok` with exactly 2.
- **A busy reply is still busy.** `rpcRequest` tests the busy shape on the parsed body *before*
  `decode` runs, so a validator never sees one. Wiring a parser must not turn "I'm overloaded" into
  `decode-error` — the service scores those differently (busy records backoff; decode-error decays
  relevance).
- **No sender ever throws.** `rpcRequest` never throws for a network outcome; a validator must not
  change that. The malformed-reply property drives 120 field-type mutants per sender.

## New tests

`test/rpc.codec-properties.spec.ts` gained a "Phase 5 — the parsers as *wired*" block (new
top-level `describe` at the end of the file). It serves one canned framed reply through a stub
node and drives the real senders. Three senders in one table, so the properties cover all three by
construction rather than as three near-copies:

- legal reply from our own encoder → `ok`, value deep-equals the normalized expectation
- 120 field-type mutants per sender → `ok` with a real object, or `decode-error` with **no `value`
  property at all** — never a throw, never an `ok` carrying `undefined`
- non-object bodies (`null`, `5`, `'nope'`, `[1,2]`, `true`) → `decode-error` for all three
- a busy body → `busy`, for all three
- `ok: 1` on ping → `decode-error` (the coercion regression test)
- caller-supplied caps truncate
- the widest legal NearAnchor our own producers can emit survives the reply caps

`test/package-exports.spec.ts` asserts the three new root exports and that `parseOrThrow` throws
the named error on rejection / returns the normalized value on a pass.

**The assertions are on the `ok` value, not merely on `kind`.** That is deliberate and is the point
of the adapter decision: written against a parser wired in raw, the malformed property fails
(`kind` is `ok`, `value` is `undefined`); a `kind !== 'ok'` assertion would pass vacuously against
any throwing validator, including a broken one.

## Known gaps — treat these as the starting point

- **Behavior change with real blast radius, only partly measured.** `fetchNeighbors` previously
  returned `ok` for *any* JSON object. It now rejects a snapshot whose `from` is not a parseable
  peer id or whose `timestamp` is not finite. The full suite is green, so no test depended on the
  old leniency — but that is a floor, not proof. A live peer running a materially different
  encoder now lands in the `decode-error` arm of `fetchAndMergeSnapshot`, which logs and scores
  nothing. I did not exercise a real two-node interop case beyond what the suite already covers.
- **`yarn build` not run separately.** `npx tsc --noEmit` compiles the same sources with the same
  config, but the emit step and `dist/` output were not exercised in this run.
- **The mutant generator is shallow.** It replaces one *top-level* field with a wrong-typed value.
  It does not fuzz nested shapes (a `sample` entry with a bad `coord`, a `cohort_hint` holding
  objects) — those are covered as *parser* properties elsewhere in the file, but not as *wired*
  ones. If the reviewer wants depth, that is where to add it.
- **`fetchNeighbors`' `Infinity`-caps default is reachable only from tests**, exactly like
  `registerNeighbors`' — a `NOTE:` says so at the site. A second production caller that forgets
  `opts.parse` silently gets no truncation. Kept defaulted so the three existing test call sites
  need no edit; the options bag makes it cheap to make required later.
- **`sendLeave` / `announceNeighbors` read no reply at all**, so a busy or malformed answer from
  those protocols is still invisible. That is the pre-existing write-only gap documented in
  `docs/fret.md` (parked with the leave-authentication work), untouched here.
- **`15.332-rpc-snapshot-cap-single-point` is unblocked.** It owns the remaining service wiring,
  the dead-slice removal and the cap single-point work. Note this ticket already added the
  `makeSnapshotParser(this.mergeSnapshotCaps())` call at `fetchAndMergeSnapshot` — the merge loop's
  own `slice(0, caps.*)` immediately below it is now redundant, which is precisely the dead slice
  15.332 removes. **Do not remove it here**; it is that ticket's arm, and removing it needs the
  single-point argument made once rather than twice.
