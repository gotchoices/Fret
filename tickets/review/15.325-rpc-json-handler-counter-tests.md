Implemented `15.325-rpc-json-handler-counter-tests`. Test-only change — **no source file was
touched**. All work landed in `packages/fret/test/rpc.handler-fuzz.spec.ts`.

## What the rule under test is

`registerJsonHandler` (`src/rpc/protocols.ts`) has three ways to drop an inbound message body,
and they report to two *different* counters on the service:

- `decodeJson` throws (not JSON at all, or JSON that is not an object) → `onMalformed('decode')`
- the wire-shape parser refuses the decoded object → `onMalformed('parse')`
- `serve` returns `undefined` — the message's self-declared `from` is not the peer the transport
  authenticated → **neither** `onMalformed` arm; the handler body calls `onIdentityMismatch`

`FretService.registerRpcHandlers` wires the first two to `diag.rejected.malformed` and the third
to `diag.rejected.identityMismatch`. Nothing pinned which `reason` string each path passed, so
`'decode'` and `'parse'` could have been swapped with no test noticing.

## What was added

**New sibling describe `body-level drop hooks: onMalformed reason vs identity mismatch`**
(unit tier, stub streams, between the existing `registerRpcHandler release accounting` block and
`decodeJson top-level shape`). Table-driven over the two protocols that have a request body on
this seam — `leave` and the *announce* half of `registerNeighbors` — five cases each:

- `'decode'` for a body that is not JSON
- `'decode'` for a body that decodes to a non-object (`null`)
- `'parse'` for a decodable object the parser rejects (`from` is not a parseable peer id)
- unparseable `from` → `onMalformed('parse')` fires, `onIdentityMismatch` does **not**
- parseable-but-wrong `from` → `onIdentityMismatch` fires, **neither** `onMalformed` arm does

Every case also asserts the drop is a **close** (`closes: 1, aborts: 0`), that no reply frame was
written, and that the handler body callback (`onLeave` / `onAnnounce`) never ran.

**New nested describe `registerNeighbors' defaulted snapshotParser`** — two cases. The trailing
`snapshotParser` parameter defaults to `Infinity` caps and every production caller supplies one,
so the default was unreachable outside tests and untested. Omitting it also forces omitting
`onMalformed` (the parameter after it), so the rejection is asserted through observable effects:

- a snapshot with an unparseable `from` still drops (close, no reply, `onAnnounce` never ran) —
  shape checking is live in the default
- 50 successors (well past the largest production cap, Core 16) arrive **whole and in order** —
  the default truncates nothing

**One new row in the wire-tier `malformedMatrix()`**: `leave: unparseable from`. Distinct from the
existing `leave: from mismatch` row — this one is a parser rejection, so `runMatrix`'s existing
accounting (which splits on rows whose name ends `from mismatch`) counts it toward `malformed`
and *not* toward `identityMismatch`. That is the counter split asserted through the **real
service diagnostics** over the memory transport, not just through directly-passed hooks.

## Honest gaps — treat these as the starting point

- **The full suite (`yarn test`) was not run.** The implement run hit the runner's token budget
  right after discovery finished, so validation was scoped to the one spec file that changed.
  The change is test-only and adds no source edit, so cross-suite risk is nil in principle —
  but the reviewer should run `yarn test` once rather than take that on trust.
- **Decision made: unit tier for the reason values, wire tier for the counter split.** The ticket
  left this open. Rationale: `runMatrix`'s aggregate accounting already fails if the service
  cross-wires the two hooks (a `malformed` increment landing on `identityMismatch` breaks both
  totals at once), so the service wiring needed only one extra row, while the `reason` *value*
  is invisible at the wire tier — the service's hook ignores its argument today — and can only be
  asserted where the hook is passed directly.
- **The `reason` assertions are `deep.equal` on an ordered array**, not a call count. That is
  deliberate (a swapped pair must fail), but it also means a future seam that reports a reason
  twice for one message fails these cases — which is the intended reading, not a brittleness.
- **`sig`, `v` and metadata shapes are untested here** — that is the sibling ticket
  `15.3255-rpc-json-handler-field-matrix-tests`, which edits the same file. Expect a merge
  conflict surface if both land unsequenced; the sibling already carries this as its `prereq:`.
- **ping and the neighbors *request* have no body-level drop path at all** (reply-only overload,
  no decode, no parse, no `onMalformed`), so they are correctly absent from these tables. Any
  "malformed message" case for those two is necessarily frame-level and aborts — already covered
  by the existing matrix rows.
- No tripwires were parked and no `NOTE:` comments were added — nothing conditional surfaced.
