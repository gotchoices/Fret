One new spec file, 39 tests, ~1050 lines. **No `src/` file was changed** — the ticket's own
constraint, and nothing found during the work needed it. Every property that exposed a limit of the
codec is pinned as today's behavior with a `NOTE:` saying so, rather than papered over.

## What landed

`packages/fret/test/rpc.codec-properties.spec.ts`, in four groups matching the ticket's phases.

**Round-trip (Phase 1).** `fast-check` arbitraries for all five wire types — `NeighborSnapshotV1`,
`RouteAndMaybeActV1`, `NearAnchorV1`, `LeaveNoticeV1`, `SerializedTable` — driven through
`encodeJson` → `decodeJson` and asserted to deep-equal the input. Plus the coordinate codecs
(`base64urlToCoord`/`coordToBase64url`, `hexToCoord`/`coordToHex`): round-trip over arbitrary
32-byte coordinates, and *rejection* over arbitrary strings that do not decode to exactly 32 bytes.
Plus `readAllBounded` reassembly over arbitrary chunk boundaries, including zero-length chunks.

**Byte caps (Phase 2).** `readAllBounded`'s consumption is *measured*, not inferred: the source is
an async iterable that counts how many times it was pulled. A 4 MB source against a 256 KB cap is
pulled exactly 5 times (`ceil(maxBytes/chunkSize) + 1`), not 64. Then the same claim at the handler
level over a real memory-transport connection, for maybeAct, announce and leave.

**Token buckets (Phase 3).** All five inbound buckets: drain → reject → refill, each protocol's own
observable form of rejection, `diag.rejected.rateLimited` counted exactly once per rejection, bucket
independence, Core-vs-Edge, and the interactions (bucket before validator; a `busy` is never
cached).

## Use cases for validating this work

Run it: `cd packages/fret && node --import ./register.mjs node_modules/mocha/bin/mocha.js "test/rpc.codec-properties.spec.ts" --timeout 90000`

Things worth trying to break, in rough order of how much they'd tell you:

- **Raise the maybeAct wire cap** (`maxBytesMaybeAct` in `fret-service.ts`) above 300 KB. The test
  `answers an under-cap maybeAct and refuses an over-cap one before the service sees it` must fail —
  its teeth are `expect(getDiagnostics().rejected).to.deep.equal(before)`, and a raised cap lets the
  300 KB body reach `handleMaybeAct`, which increments `payloadTooLarge` for an activity over 128 KB.
- **Move the token-bucket check in `handleMaybeAct` below `validateRouteAndMaybeAct`.** Two tests
  must fail: `takes the token before validation…` and the existing
  `spends a token per malformed message` in `rpc.handler-fuzz.spec.ts`.
- **Make `cacheResponse` store a `busy` reply.** `never caches a busy reply…` must fail.
- **Delete the length check in `base64urlToCoord` or the regex in `hexToCoord`.** The two
  accepts-exactly / rejects-the-rest properties must fail.
- **Make `readAllBounded` buffer the whole source before comparing against `maxBytes`.** The three
  consumption-bound tests must fail on the pull count while still throwing the same error — which is
  the distinction the ticket asked to measure rather than assume.

## Findings and deliberate non-fixes

Three JSON-codec limits surfaced. None is a defect in `src/`; each is pinned as a test with a
`NOTE:` in the spec stating it is today's contract rather than an endorsement.

- **`-0` serialises as `0`.** No FRET field distinguishes them today (relevance, latency and
  estimates are all magnitudes). Tripwire, parked at the test site: becomes work only if a field
  ever needs signed zero.
- **`NaN` / `±Infinity` serialise as `null`.** Unreachable in routing logic —
  `validateRouteAndMaybeAct` rejects a non-finite `ttl` / `want_k` / `min_sigs` / `timestamp`
  outright. Parked the same way.
- **A `metadata` value of `undefined` is dropped.** Stated as the contract: absence is what the wire
  can express, `null` is the value that round-trips.

A reviewer may reasonably want the first two mirrored as `NOTE:` comments at `encodeJson` in
`src/rpc/protocols.ts`, which is where a future reader of the codec would look. I did not add them
because the ticket said explicitly that nothing here changes `src/`.

Two existing asymmetries pinned as contract, both cross-referenced to `plan/15-rpc-shared-helper`
rather than changed here:

- **The maybeAct wire cap and the service's activity cap disagree by 4× on Core** (512 KB at the
  wire vs a fixed 128 KB checked in `handleMaybeAct` *after* the whole body is buffered). Pinned by
  comment, per the ticket's instruction; it is an open arm of that plan ticket.
- **A rate-limited leave is indistinguishable from an accepted one on the wire.** `handleLeave`
  returns early inside the service while `registerLeave` has already committed to sending
  `{ok: true}`, so the sender never learns its notice was dropped and will not retry. Asserted
  explicitly, with a comment that it is today's contract. `plan/15-rpc-shared-helper`'s
  discriminated result type is what would let leave report busy.

**A testing-methodology finding worth a second opinion.** `fc.record`'s `requiredKeys` option is not
usable for "present or absent with even weight": measured over 400 samples of a record with four
optional keys, fast-check 4.5.3 produced the all-present shape 182 times and the **all-absent shape
zero times**. My first draft used it and the distribution assertions correctly failed. The file now
uses a `withOptionals` helper built on `fc.subarray`, which is uniform across subsets including the
empty one. **I did not survey the other specs for the same pattern** — if `requiredKeys` is used
elsewhere to model optionality, those properties may silently never exercise the omitted-field case.

## Known gaps — treat the tests as a floor

- **Handler-level byte caps are exercised on the Edge profile only** (256 KB maybeAct / 64 KB
  neighbors), to keep payload sizes and wall time down. The Core arithmetic is identical but
  untested; the leave cap is a fixed 4096 and so is profile-independent.
- **"Refused before a full parse" is proved at two different strengths.** The unit tier genuinely
  measures consumption (pull counting). The wire tier proves only that no service-side diagnostic
  moved — strong evidence the read was refused before any handler work, but not a direct
  measurement of bytes consumed on the receiver.
- **Refill is asserted at the bucket level for all five buckets, but only through a handler for
  ping.** The other four could in principle refill while their handler still refused; nothing here
  would catch that.
- **`readAllBounded` reassembly is driven from plain async iterables, not real streams**, so it does
  not cover transport-level framing. That is deliberate (the ticket asked for it this way, and
  `rpc.stream-errors.spec.ts` owns the transport cases), but it means the property is a *codec*
  guard, not a wire guard, until length-prefix framing lands.
- **Core-vs-Edge is asserted for the maybeAct bucket only**, not all five.
- **The `SerializedTable` store property asserts a fixpoint and id preservation**, not field-by-field
  normalization — `digitree.persistence.spec.ts` already pins the concrete normalization rules, and
  the ticket asked to add on top rather than restate.
- **Per-peer rate limiting is deliberately untested.** It does not exist; `docs/fret.md` lists it
  under *Not yet implemented* and `tickets/backlog/impl/4-per-peer-rate-limiting` owns it. The spec
  says so in a header comment so the gap is not read as missing coverage.
- The two wire rigs duplicate small `openStreams` / `sendRaw` helpers that `rpc.handler-fuzz.spec.ts`
  also defines. Extracting them into `test/helpers/` would have meant editing that spec, which is
  outside this ticket; worth doing when someone next touches both.

## Test status

- `cd packages/fret && npx tsc --noEmit` — clean.
- `cd packages/fret && yarn test` — **813 passing, 1 failing**, and the one failure was this spec's
  own generator: `fc.jsonValue()` emits `-0` at arbitrary nesting depth inside `metadata`, which
  collides with the `-0` loss pinned separately. Fixed by building the JSON-value arbitrary
  explicitly (`arbJsonValue`, via `fc.letrec`) so its number leaves exclude `-0`.
- **After that fix I re-ran the new spec three times (39 passing each) and `tsc` clean, but did not
  re-run the whole suite** — the run crossed the token budget. The fix is confined to one arbitrary
  in the new file and touches nothing else, so a full-suite regression from it is implausible, but
  it is unverified and a reviewer should run `yarn test` once.
- No pre-existing failures were observed, so no `tickets/.pre-existing-error.md` was written.
