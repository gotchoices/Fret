## What landed

### Arm 1 — two-node framed read/reply smoke matrix (new file)

`packages/fret/test/rpc.two-node-framed.spec.ts`.

Two in-memory nodes (`createMemNode`, torn down with `stopAll`). The responder registers eight
**reply-only** JSON protocols through `registerJsonHandler` — the options bag has no `parse` key,
which is the discriminator the overload narrows on. Each handler awaits a fixed number of extra
microtasks before returning, crossed with whether the reply carries a payload field:

| axis | values |
|---|---|
| microtasks awaited before replying | 0, 1, 2, 4 |
| reply shape | carries a `body` string (512 chars), or is a bare `{ ok, cell }` |

The requester dials once in `before` and drives each cell with `rpcRequest`, passing a validating
`decode` (so the typed-reply overload is selected, not the write-only one). One `it` per cell so a
failure names its own cell.

**Assertion is `kind === 'ok'` only**, per the ticket's scope discipline — nothing is keyed on how
many microtasks the handler awaited. Two extra assertions ride along and are *not* depth-indexed:
the answer's `cell` matches the protocol it was requested on (proves cells aren't crossing), and
the `body` field round-trips (present on the body arm, `undefined` on the other).

### Arm 2 — prompt-failure timing assertion (existing file)

`packages/fret/test/rpc.stream-errors.spec.ts`, new case in the `over a real transport` block:
`an end-of-stream read fails an order of magnitude inside its own budget`.

A real responder writes half a framed snapshot and half-closes. The read must reject in under
`RPC_TIMEOUT_MS / 10` (500 ms of a 5000 ms budget). The pre-existing `expectPrompt` helper only
bounded at `RPC_TIMEOUT_MS / 2`, which is what a *slow answer* looks like, not what a *prompt
failure* looks like — a read that sat out most of its deadline passed every existing case. This
is the property the deleted 20 ms EOF poll used to provide, and which the stream-layer read is
claimed to give for free; nothing measured it until now.

The bound is a ratio, deliberately not a tight millisecond bound. Observed elapsed on this
machine: the neighbouring `expectPrompt` case reports 38 ms against the same shape.

## Use cases / what to poke at

- **Break the invariant and watch it fail.** The file's whole reason to exist is that a reply the
  responder really wrote must never come back as `decode-error` or `timeout`. Forcing
  `readFramed` to treat a still-open stream as ended should turn every cell red.
- **The reply-only overload.** Adding a `parse` key to any `registerJsonHandler` call in the new
  file should be a compile error at the `serve` signature (one arg vs two), which is the point of
  the discriminator.
- **The typed-reply overload.** Dropping `decode` from the `rpcRequest` call should stop compiling
  where `res.value.cell` is read — `T` pins to `undefined` on the write-only overload.

## Known gaps — honest list

- **The timing axis is not proven to be load-bearing.** Depths 0/1/2/4 are varied but the test
  cannot show the scheduler actually interleaved differently between them; the original failing
  cell was never stable across runs, which is exactly why the ticket forbade a depth-indexed
  assertion. So this arm is a smoke net over a plausible timing spread, not a proof that any
  specific interleaving is exercised. If the false-truncation bug regressed in a form only one
  interleaving reaches, this may or may not catch it.
- **Memory transport only.** `createMemNode` uses `/memory` + `plaintext`; no TCP, no noise, no
  identify. A framing bug that only appears under a real socket's chunk boundaries would not show
  up here. `rpc.stream-errors.spec.ts` uses `createMemoryNode` (TCP + noise) for its real-transport
  block, so that shape has some coverage there — but not for the *success* path this file drives.
- **Reply sizes are small.** The largest body is 512 bytes, so every reply lands in one chunk.
  Multi-chunk replies (where the reader must reassemble across pulls) are untested by this file.
- **`RPC_TIMEOUT_MS / 10` is a judgement call, not a measured floor.** Chosen as "an order of
  magnitude", per the ticket. Observed cost is ~40 ms, so there is ~12× headroom; if CI is far
  slower than this machine the margin shrinks proportionally, since the bound is absolute (500 ms)
  while the work is not.
- **Full-suite runtime is ~4 minutes** and includes long simulation specs that print large result
  objects. Nothing to do with this change; noted so the reviewer is not surprised.
