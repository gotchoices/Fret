## What landed (confirmed by reading the diff)

**Arm 1 — `packages/fret/test/rpc.two-node-framed.spec.ts` (new, 114 lines).** Two `createMemNode`
nodes (memory transport + plaintext + yamux), torn down with `stopAll`. The responder registers
eight reply-only JSON protocols via `registerJsonHandler`; each handler awaits 0/1/2/4 extra
microtasks before returning, crossed with whether the reply carries a 512-char `body`. One `it`
per cell, driven by `rpcRequest` with a validating `decode`. Assertion is `kind === 'ok'`, plus
two timing-agnostic riders (the answer's `cell` matches the protocol requested, and `body`
round-trips).

**Arm 2 — `packages/fret/test/rpc.stream-errors.spec.ts` (+25 lines).** One new case in the
`over a real transport` block ("an end-of-stream read fails an order of magnitude inside its own

under `RPC_TIMEOUT_MS / 10` (500 ms of 5000). Asserts `decode-error`.

## Verified — settled, do not re-check

- **The reply-only overload is used correctly.** `registerJsonHandler` discriminates on
  `'parse' in opts`; the new file's options bags have no `parse` key, so the reply-only branch
  runs. It reads no request body, which matches the new tests sending no `body`.
- **`rpcRequest` with `decode` selects the typed overload** (`src/rpc/request.ts:199-215`), so
  `res.value.cell` is genuinely typed rather than `undefined`.
- **`await node.start()` after `createMemNode()` is the house pattern**, not a double start.
- **The single dial in `before` is required** — `rpcRequest` → `openRpcStream` dials by bare peer
  id, which needs an address in the peerStore.
- **The `Infinity`-mode read is on the path under test.** `rpcRequest` calls
  `readFramed(stream, maxBytes, Infinity, …)`; a real libp2p stream takes `readFramedFromStream`,
  the implementation the framed-read work introduced — not the test-stub iterable path.
- **Open question 1 is settled: `decode-error` is the right assertion and is not a flake.**
  A half-written frame makes the body read throw `UnexpectedEOFError`, and
  `isFrameTruncationError` (`src/rpc/protocols.ts:328-331`) matches **both**
  `FrameTruncationError` and `UnexpectedEOFError` by name, so `classify` maps either one to
  `decode-error`. The neighbouring case that accepts *either* name asserts on the error's `name`,
  not on the outcome kind. The cases that accept two *kinds* are the **reset** shapes, where a
  live muxer may or may not deliver the buffered bytes before failing the read; a clean half-close
  always delivers its bytes, so pinning one kind here is correct.
- **Open question 2 is settled: arm 2 *is* a near-duplicate, and tightening the shared helper is
  the better fix.** `expectPrompt` (inside `describe('over a real transport')`) bounds elapsed at
  `RPC_TIMEOUT_MS / 2`. The new case has the identical setup to the case directly above it (same
  protocol, same `halfThenClose(HALF_SNAPSHOT)`, same `fetchNeighbors`, plus an explicit
  `timeoutMs: RPC_TIMEOUT_MS` that only restates the default) and differs solely in bounding at
  `/10`. All three `expectPrompt` call sites run on loopback TCP with the connection already
  established before the measurement starts (the dial happens in `serving`, outside the timed
  window), so `/10` = 500 ms is safe for each. Tightening the helper makes every call site assert
  the real property and retires the duplicate.

## Found — one documentation staleness

`docs/fret.md` line 205 still describes a **20 ms `EOF_POLL_MS` poll** inside `readFramed` as the
mechanism that recognises end-of-stream promptly. `grep -rn "EOF_POLL_MS" packages/fret/src`
returns **nothing** — the poll was deleted by the framed-read work (the stream-errors spec itself
refers to "the deleted 20 ms EOF poll"). The paragraph needs those sentences replaced with the
current mechanism: the read fails at the stream's own layer, which is exactly the property arm 2's
timing case pins. Minor fix for this pass, not a ticket.

## Weaknesses the handoff already states honestly (do not re-derive)

Memory transport only (no TCP/noise/identify); replies ≤ 512 bytes so never multi-chunk; the
`/10` ratio is a judgement call; the microtask depths are a plausible timing spread rather than a
proof that any particular interleaving is exercised.

Three edits, one doc check, then the gate.

- **Tighten `expectPrompt` to `RPC_TIMEOUT_MS / 10`** in `rpc.stream-errors.spec.ts`, moving the
  new case's reasoning comment (half the budget is what a *slow* answer looks like, not what a
  prompt failure looks like; the ratio is deliberately loose against CI scheduler noise) into the

  the case above it asserts the same shape, the same `decode-error`, the same bound, *and* stream

- **Add one macrotask arm to `rpc.two-node-framed.spec.ts`.** Microtask depths 0–4 all resolve
  within the same tick, so none of them plainly opens the window the false-truncation bug needed
  (a reader pulling before the writer has written); a handler deferring past a *macrotask*
  (`setTimeout(…, 0)`) does. Cheapest shape: replace `MICROTASK_DEPTHS` with a data list of
  `{ name, wait }` timings — immediate, 1/2/4 microtasks, one macrotask — so the cell name comes
  from the timing's name and the loops are otherwise unchanged. The assertion stays `kind === 'ok'`
  and stays timing-agnostic, so this does not violate the parent ticket's scope discipline. Cost is
  one extra protocol registration and one extra RPC on the existing connection.
