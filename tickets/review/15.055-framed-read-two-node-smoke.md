## What the prior run verified

- **The reply-only overload is used correctly.** `registerJsonHandler`'s implementation
  (`src/rpc/protocols.ts`) discriminates on `'parse' in opts`; the new file's options bags have no
  `parse` key, so the reply-only branch — `sendFramed(stream, await encodeJson(await
  opts.serve(connection)))` — is what runs. It reads no request body, which matches the new tests
  sending no `body`.
- **`rpcRequest` with `decode` selects the typed overload** (`src/rpc/request.ts:199-215`), so
  `res.value.cell` is genuinely typed rather than `undefined`. The handoff's claim holds.
- **`await node.start()` after `createMemNode()` is the house pattern**, not a double-start bug —
  every other spec in `test/` does the same.
- **The single dial in `before` is required**, not incidental: `rpcRequest` → `openRpcStream` dials
  by bare peer id, which needs an address in the peerStore.
- **The `Infinity`-mode read is on the path under test.** `rpcRequest` calls
  `readFramed(stream, maxBytes, Infinity, { signal: d.signal })`, and a real libp2p stream takes
  `readFramedFromStream` (via `isMessageStream`), which is the `byteStream` implementation the
  framed-read work introduced. So the new file does exercise the intended code, not the
  test-stub `readFramedFromIterable` path.

## Open questions the prior run did not settle

Both are cheap; neither is known to be a defect.

- **Is `expectKind(res, 'decode-error')` in arm 2 the right — and stable — expectation?** A
  half-written frame makes `readFramedFromStream`'s body read throw `UnexpectedEOFError`, which
  propagates out of `readFramed` and is caught by `rpcRequest`'s `classify(...)` on the *read* arm,
  not by `decodeReply`. Read `classify` in `src/rpc/request.ts` and confirm it maps a truncation to
  `decode-error`. Note the neighbouring pre-existing case in the same file deliberately accepts
  *either* `FrameTruncationError` or `UnexpectedEOFError` because the live-muxer shape varies; the
  new case pins one outcome exactly. Decide whether that is a tighter-but-correct assertion or a
  flake waiting for a slower machine. (The suite reportedly ran green, so it is at least not
  broken here.)
- **Is arm 2 a near-duplicate of the case beside it, and should `expectPrompt` have been tightened
  instead?** The handoff's own argument is that `expectPrompt`'s `RPC_TIMEOUT_MS / 2` bound is too
  loose to mean "prompt". If that is true it is true for *every* call site of that helper, not only
  this one shape — so tightening the shared helper may retire the whole class where a second
  bespoke case covers one instance. Read `expectPrompt` and its call sites before deciding; if
  tightening it is safe, that is the better fix and it is small enough to do inline in this pass.

## Weaknesses the handoff already states honestly (do not re-derive)

Memory transport only (no TCP/noise/identify); replies ≤ 512 bytes so never multi-chunk; the
`/10` ratio is a judgement call with ~12× observed headroom; and the microtask depths are a
plausible timing spread rather than a proof that any particular interleaving is exercised.

One reviewer observation to weigh rather than restate: **microtask depths 0–4 all resolve within
the same tick**, so it is not obvious any of them opens the window the false-truncation bug needed
(a reader pulling before the writer has written). A single extra arm deferring past a *macrotask*
(`setTimeout(0)` / `setImmediate`) would plainly open that window, and it costs no flake risk —
the assertion stays `kind === 'ok'` and stays depth-agnostic, so it does not violate the parent
ticket's scope discipline. Treat as a candidate minor fix, not a required one.
