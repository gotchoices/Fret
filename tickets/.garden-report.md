Three things from that run are worth your attention:

**1. The suite was flaky, and now is less so.** A triage pass ran the full suite twice on an
unchanged tree and got *different* failures each time, while each failing spec passed alone —
real wall-clock timers with sub-2× margins, on a box loaded by three other tess runners. All
three were then fixed rather than loosened: the dedup-cache TTL got an injectable clock, the
simulation budget got a genuine speedup (below), and the third turned out not to be a timing
problem at all — the dialability spec rested on a wrong premise about self's ring position.
**This means the flake caveat applies to `82cdb3f`, not to current HEAD** — the fixes landed
after it, so releasing from a later commit is the more reliable choice, not the riskier one.

**2. A hot-path performance defect, found by profiling the timing-out simulation.**
`coordToHex` in `src/ring/hash.ts` allocated two throwaway strings per byte — 64 per
coordinate — and measured **38% of total CPU** in the N=100 run. `DigitreeStore` embeds the
hex coordinate in every tree key, so it runs on every store write and every ring walk, under
neighbor exchange, cohort assembly, next-hop selection and size estimation alike. Now a
256-entry lookup table: identical output, allocations gone. **Check whether this retires
`plan/16-store-perf-allocation`** before promoting that ticket — it describes the same waste.

**3. A real leaked async operation in the service.** The suite hung after passing. The ticket
was filed honestly as `severity: cosmetic` ("nobody has found what yet", and `--exit` was
already masking it), but the follow-up pass found the cause:
`mocha-exit-leak-proactive-announce` — a proactive announce left running, holding the Node
process open. That is service-side, not test hygiene, so it deserves a look even though it
surfaced as a test symptom. A watchdog also landed so a future leak shows up instead of
disappearing behind `--exit`.
