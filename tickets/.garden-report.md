### What shipped

`registerRpcHandler` now builds its `node.handle` options through a private `handleOptions()`:

```ts
function handleOptions(caps: StreamCaps): StreamHandlerOptions {
	const options: StreamHandlerOptions = { runOnLimitedConnection: true };
	if (caps.maxInboundStreams !== undefined) options.maxInboundStreams = caps.maxInboundStreams;
	if (caps.maxOutboundStreams !== undefined) options.maxOutboundStreams = caps.maxOutboundStreams;
	return options;
}
```

Two defects at one site: the missing relay opt-in on the *answering* side (the dialing side in
`openRpcStream` was already correct), and the two cap keys being passed as `undefined`, which
spread over libp2p's registrar defaults and replaced 32/64 with no cap — dormant for FRET's own
registrations, live for outside callers of the exported seam.

### The triage commit is the one to know about

`9512f0f` is **not** part of the relay ticket. The implement agent hit a pre-existing
`message-bus` clustered-placement timeout, filed `.pre-existing-error.md` per the rules, and the
runner's triage pass fixed the root cause: `DigitreeStore`'s `byId` map now holds the **entry
object** rather than its tree key (so `getById` is a map read instead of a full tree descent), and
the `makeKey` cache is re-keyed from entry-object identity onto the **coordinate array's**
identity, guarded by the entry id.

That is a real hot-path change, so it was gated separately. The reasoning recorded at the site is
measured, not asserted: every write path hands `put` a freshly-spread entry, so an entry-keyed
cache was a guaranteed miss on every write and left a dead weak-table record behind each time —
measured on the 300-peer bounded-store simulation (3.4M writes, 66M extractor calls) at 25–35 s
entry-keyed, 9 s with no cache at all, 3.3–4.3 s coordinate-keyed. An entry-keyed cache was several
times *worse* than none. The store invariant is unchanged in substance and all four `byId` sites
(`put`, `remove`, `getById`, `size`) agree; `test/digitree.invariants.spec.ts` is the model-based
property test that covers it.

### Pre-1.0 (must land before `v1.0.0`)

The band is short on purpose: a ticket qualifies only if landing it *after* 1.0 would be a
breaking change or a broken promise. All four are small.

- `1-debt-profile-payload-caps-unimplemented` — `docs/fret.md` claims two behaviours the code does
  not have: profile-dependent activity payload caps (both profiles accept 128 KiB), and
  "refcount-based" active mode (`setMode` is a plain flag; nothing counts operations or returns to
  passive on its own). One ticket, two arms, same decision each time: build it or delete the claim.
- `2-debt-readme-1.0-accuracy` — the README tells readers to run `yarn lint` (no such script) and
  `yarn format` (which `AGENTS.md` explicitly forbids: no prettier config, so it rewrites all 21
  source files against the house tab style). It also says nothing about security posture, which is
  the first thing an evaluator of a p2p library needs.
- `3-debt-public-api-and-wire-contract-for-1.0` — ~39 exports across five groups and no statement
  of which the semver promise covers; `getDiagnostics` is reachable but deliberately off the
  public interface; and the wire compatibility rule (`v` is ignored, new fields must be optional
  and additive, a breaking change takes a new protocol id) lives in a design-doc comment rather
  than anywhere a consumer looks. Four queued tickets are about to add wire fields.
- `4-debt-import-table-coordinate-verification` — `importTable` trusts the `coord` in the file
  instead of re-deriving it from the peer id beside it. Width and encoding are checked; *identity*
  is not, so a well-formed coordinate for the wrong peer sorts an entry to an arbitrary ring
  position and silently corrupts every ordered read. Pre-1.0 because adding the check later turns
  imports that used to succeed into failures.

### The contestable call, flagged

**Message signing is post-1.0** (`21-feat-message-signatures`). The argument: transport identity
verification has landed, so every message carrying a `from` is checked against the
noise-authenticated `connection.remotePeer` — a peer cannot forge another peer's identity. What
signing would add is protection against a peer lying about *third parties*, and FRET is already
built not to trust hearsay: a gossiped id creates an unscored `unknown` entry that no ring view
admits until a probe vets it. So signatures are defence-in-depth rather than a hole, and 1.0 can
honestly target deployments where the transport is authenticated and peers are semi-trusted.

If you disagree, it is a one-file rename — the reasoning above is what to argue with, and
`2-debt-readme-1.0-accuracy` is where the resulting posture gets written down either way.
