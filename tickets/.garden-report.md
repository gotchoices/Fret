## Session 2 (2026-08-20): the sim guard, and one security fix

### The simulation now routes the way a node does

`15.6-sim-route-local-selector` + `15.7-sim-routing-guard-spec`, both hand-implemented after the
runner timed out on the first and burned five budget-stalls on the second.

`FretSimulation.handleRoute` used to reimplement hop choice against the harness's all-seeing view
— it filtered candidates by the global `alive` flag and the global partition map, then took
`candidates[0]` with no requirement that the hop be closer to the target. So **no simulation
number could fail when the routing math was wrong.** Now every hop is chosen by the shipped
`chooseNextHop` over the deciding peer's own store, and a chosen hop is a contact *attempt*: a
refusal strikes that entry through the same escalation the per-tick sweep uses (one shared
`recordContactFailure`) and the selector runs again over what is left.

### The guard, and what it actually guards

`test/simulation.routing.spec.ts` — four cases, thresholds set from measured runs over four seeds.
**The break test did not behave as the ticket predicted, and that is the finding:**

| selector distance function          | success  | p90 hops  |
|-------------------------------------|----------|-----------|
| `minDistance` (shipped)             | 95–100%  | **2**     |
| preference inverted (farthest wins) | 99%      | **17–20** |
| `clockwiseDistance` substituted     | 100%     | 2         |
| XOR distance substituted            | 94–98%   | 2–3       |

So the **hop bound** carries the guard and the success rate does not — the attempt budget absorbs
a bad route until it stumbles onto the target. And the spec **cannot** discriminate one plausible
ring metric from another: the sim's stores are unbounded and near-uniform (63% of the ring known
at n=200, 19% at n=1000), so greedy routing arrives in one or two hops under any roughly-monotone
metric. `clockwiseDistance` was never going to bite — it is a *valid* ring metric, Chord's own.
Written into the spec header, `docs/fret.md`, and the `NOTE:` above `CONNECTED_SLACK_ORDERS`,
which now defers retuning for a measured reason rather than for want of a harness. Prerequisite
filed as `backlog/debt-sim-eviction-degenerate-blocks-metric-guard`.

### Security: sample ring coordinates are re-hashed, not trusted

`complete/5-sample-coordinate-verification`. Snapshot successor/predecessor lists always
re-hashed their ids; the `sample` list was decoded straight off the wire. So a
transport-authenticated peer could place **any other peer's id at any ring coordinate**, no id
grinding — making that id a neighbor, anchor and cohort member for keys it must never serve.
Both merge paths now derive the coordinate from `s.id`. Verified to bite: revert the two lines and
all four tests in `test/sample-coordinate-verification.spec.ts` fail.

Consequence worth knowing: a sample entry whose id will not parse is now dropped rather than
merged at a wire-supplied coordinate. That churned six fixtures using synthetic ids, fixed in
`f11e4f1`.

## What landed

### The RPC consolidation (`plan/15-rpc-shared-helper`), complete through its core

The refactor its own ticket described as "deletes roughly half of the rpc directory", deferred
behind the optimystic build and picked up once the beta was tagged:

| Piece | Result |
|---|---|
| Length-prefix framing | `readAllBounded` gone; `sendFramed` / `readFramed`, `FrameTruncationError`, `UnexpectedEOFError` |
| `rpcRequest` + `RpcOutcome<T>` | one discriminated outcome type for every sender |
| Sender migration | all five senders onto the seam |
| Validators module + JSON handler seam | per-message shape validation, `registerJsonHandler` |
| Byte-cap tightening | every wire cap derived from the largest legal message of its protocol |

**The behavioral result that matters.** The three inconsistent sender failure contracts are gone —
`maybeAct` threw, `fetchNeighbors` fabricated an empty snapshot, `ping` returned `ok: false`, all
for identical evidence. Every sender now returns one `RpcOutcome<T>` (`ok` | `skipped` |
`cancelled` | `timeout` | `unreachable` | `foreign-protocol` | `decode-error` | `busy`), and
`noteRpcFailure` branches on `kind` instead of sniffing an error's identity. So **a peer that opens
a stream and merely replies *badly* is no longer booked as unreachable, and three bad answers can
no longer mark a live peer `dead`.**

### Two real bugs, both `repro: verified`, neither in the released beta

1. **Framed reads reported healthy replies as truncated.** `readFramed` could conclude the remote
   had finished writing while its reply bytes were still in flight, raising `FrameTruncationError`
   on a healthy connection carrying a complete reply; the trigger was how many microtasks elapsed
   inside the inbound handler before its first write. On a live ring that discards a good peer's
   good reply and decays its relevance. The fix is structural: the 20 ms `EOF_POLL_MS` poll and
   `remoteFinishedWriting` are **deleted**, and a real libp2p stream now reads prefix and body
   through `@libp2p/utils`'s `byteStream`, which rejects with `UnexpectedEOFError` the instant the
   stream ends short — the frame is read at the layer that owns the stream's EOF state. Pinned by a
   new `test/rpc.two-node-framed.spec.ts` driving real replies at immediate, several-microtask and
   past-a-macrotask timings, requiring that a reply really written is never reported cut off.
2. **Edge and Core nodes could refuse each other's neighbor lists.** Each node sized its *accept*
   limit for messages it would send itself rather than for the largest a peer might legitimately
   send it. Now one network-wide number. It only became visible because the caps had just been
   tightened — at the old 512 KB the asymmetry was invisible.

## Four operational traps worth keeping

Hit each of these at least once today; each cost real time.

1. **Tickets that cannot be scheduled.** A name like `15.2b-` has no valid numeric prefix, so tess
   treats it as *unnumbered* and sorts it after every numbered sibling — it starves. Same for a
   stage transition that emits its output with no prefix at all (`Sequence: --` in the banner).
   Splits should suffix with a **decimal** (`15.21`), never a letter.
2. **Chain affinity outranks stage order and sequence.** A ticket parked in `review/` sat unpicked
   for an hour while the runner worked `implement/`, because the `live` strategy prefers finishing
   the chain it is in. Not fixable by renaming or by `--stages` order — stop the runner at a clean
   tree, run one scoped to the stage you want drained, then restore the broad invocation.
3. **A clean `npx tsc --noEmit` does not mean the suite passes.** A ticket was abandoned with seven
   failing tests and a clean typecheck. Use a review ticket's recorded gate in `complete/`, or run
   `yarn check` yourself when the runner is idle.
4. **Growing resume notes are a spin signal.** One ticket reached ~260 lines of stacked, mutually
   contradictory confirmations and ran **24 times** without transitioning — each run spent its whole
   budget re-reading. Rewritten to verified-state-plus-remaining-work, it finished in two runs.
   Distinguish this from a long ticket carrying genuine research (see `15.7` above), which should be
   split, not trimmed.

One more: a transient API failure makes tess **defer that ticket for the rest of the run**.
Restarting the runner is what clears it.

5. **Don't edit the working tree while a runner is live.** `git add` in a runner's commit step
   sweeps up whatever else is uncommitted, so unrelated work lands under a ticket's commit
   message. Cost twice on 2026-08-20. Either stop the runner or stage nothing until it idles.
6. **A ticket's suggested break test can be wrong.** `15.7` specified swapping `minDistance` for
   `clockwiseDistance` to prove the guard bites; it proves nothing, because clockwise distance is
   a valid ring metric. Run the break, read the numbers, and if they do not move, that is the
   finding — not a threshold to loosen until it passes.
