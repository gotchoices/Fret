Test + docs half of `7.2-rpc-service-signals` (Phase 4 of `7-rpc-abort-deadlines`). Split out
so each run fits its token budget. Assumes the service edits from `rpc-service-signals` have
landed: `FretService` has a run-scoped `runAbort` controller minted in `start()` and aborted in
`stop()`, every outbound call site passes `{ signal: this.runSignal }` (pings/announces at 2000 ms),
`sendLeaveToNeighbors` runs on its own `SHUTDOWN_BUDGET_MS` (3000) deadline with 1500 ms per
notice, and a `wasCancelled(sig)` guard skips `noteRpcFailure` / `recordBackoff` /
`diag.pingsFail++` when the *caller's* signal aborted.

## Tests to add

### Service-level (`test/service-lifecycle.spec.ts` — has the start/stop harness and the
`(svc as any)` override pattern for driving a tick body directly)

- **`stop()` resolves within `SHUTDOWN_BUDGET_MS` + slack even when a dial hangs, and leave
  notices still reach the reachable neighbors.** Two real in-memory nodes (`createMemNode` in
  `test/helpers/libp2p.ts`) plus one seeded unreachable id whose dial hangs. The hanging-dial stub
  pattern lives in `test/rpc.protocols.spec.ts` (`hangsUntilAbort(opts)`, ~line 255–273: a stub
  that settles **only** on signal abort — libp2p's `AbortOptions` contract). At the service level
  the simplest route is to override `node.dialProtocol` on the stopping node for the ghost id
  only, or wrap `sendLeave` via a stub in the module seam if one exists; `test/churn.leave.spec.ts`
  shows how leave delivery is asserted end to end (`handleLeave` on the receiver). Assert wall
  time with `Date.now()` and a generous ceiling (`SHUTDOWN_BUDGET_MS + 1500`), and assert the
  reachable peer's service saw the leave (departing id removed from its store / `handleLeave`
  counter).
- **`stop()` mid-tick issues no new dials.** Park `stabilizeOnce` (the existing "does not re-arm
  the stabilization timer when stop() lands mid-tick" test shows the park/unpark pattern), call
  `stop()`, then unpark and assert `diag.pingsSent` did not grow — an already-aborted signal makes
  `openRpcStream` throw before dialing.
- **A start→stop→start cycle mints a fresh controller.** After the second `start()`,
  `(svc as any).runSignal.aborted === false`. The implementation chose to **keep** the aborted
  controller after `stop()` (it is replaced only by the next `start()`), so assert
  `runSignal.aborted === true` after `stop()` — `undefined` only before the first `start()`.
- **Regression: a `stop()` landing mid-tick must not dial or strike from the *rest* of the tick.**
  `stabilizeOnce` has no `stopped` re-check between its passes, and each pass captures
  `this.runSignal` itself, so the park point in the test above must be **before** those captures —
  park `seedFromPeerStore` (or `seedFromBootstraps`), not `probeNeighborsLatency` — or the test
  does not exercise the case. With the park there, assert after unparking: `diag.pingsSent`
  unchanged, `diag.snapshotsFetched` unchanged, and no peer gained a `contactFailures` strike or a
  `backoffMap` entry. (This is the hole the review of 7.2 closed by not nulling `runAbort`; without
  a test it can silently regress to a null and go unnoticed.)

### Cancellation is not evidence (`test/dead-state.spec.ts` — has `seedPeer` / `strike` /
`unspace` helpers and the "through a real outbound RPC call site" block driving
`probeNeighborsLatency` against an `unreachablePeer()`)

- Seed a member peer, start a probe whose dial hangs (or simply abort the run signal **before**
  calling `probeNeighborsLatency([id])` — the already-aborted path is deterministic), then assert:
  `contactFailures` unchanged (0), `state !== 'dead'`, `backoffMap.get(id)` undefined,
  `diag.pingsFail` unchanged. Repeat through `probeMembership(id)` (which also records backoff on
  the un-guarded path — that is the assertion that matters there).
- **Contrast case, so the guard is not over-broad:** the same peer with the run signal live and the
  RPC's own `timeoutMs` firing (unreachable id, `timeoutMs` small) **does** strike — i.e. the
  existing "marks an unreachable neighbor dead after a run of failed pings" test still passes with
  the guard in place. Do not weaken it.
- Same two assertions through `routeAct`'s forward path if a cheap harness exists
  (`test/route.maybeact.integration.spec.ts`); otherwise state the gap in the handoff.
- The other four guarded call sites carry the same rule and none is covered above; add at least a
  cheap one each (abort the run signal first, then call the method, then assert nothing was
  scored): `mergeNeighborSnapshots`, `sendAnnouncementsRateLimited`, `preconnectNeighbors`, and
  `iterativeLookup`. For `iterativeLookup` the assertion is that a cancelled walk yields
  `{ type: 'exhausted' }` and strikes nobody.
- **Open design question to answer while writing that last one, in the ticket or in the docs:** a
  caller cannot today tell "the ring had no more hops" from "the service shut down under you" —
  both surface as `exhausted`, and on the activity-resend arm the activity was never delivered.
  Either add a `RouteProgress` variant (`{ type: 'cancelled' }`) or state explicitly in
  `docs/fret.md` that `exhausted` covers cancellation and that callers must re-check service state.
  Do not leave it implicit.

## Docs (`docs/fret.md`)

- *Stream management*: the read-deadline bullet currently says "Stream read deadline: one overall
  budget per read (`readAllBounded`, 5s default, uniform across the four RPCs today)". Restate it as
  a whole-RPC budget covering dial + open + read (`RPC_TIMEOUT_MS`), and name the per-call-site
  overrides (2 s on maintenance pings and announces, 5 s on `sendMaybeAct` because it is a route
  budget, `SHUTDOWN_BUDGET_MS` / 1.5 s per notice on the leave fan-out). Keep the "no per-chunk idle
  timer" reasoning intact.
- *Stabilization and churn handling*: next to the `deadAfterFailures` discussion, add the rule that
  **our own cancellation is not evidence about the peer** — a run-signal abort (`stop()`, or a
  future per-tick budget) records no contact failure, no backoff, no ping-failure diagnostic; only
  the RPC's own timeout does. Note *why* the caller's signal discriminates (the sender's deadline is
  a child of it).
- *Service shell & lifecycle (A1)*: one line on the run-scoped `AbortController` beside the run
  generation paragraph — minted with `runGen` on `start()`, aborted right after the loop timers on
  `stop()`, before the leave fan-out.
