The deterministic simulation harness (`packages/fret/test/simulation/fret-sim.ts`) is a real asset,
but three things make its routing-success number oracle-assisted rather than evidence about the
shipped code. This ticket fixes all three in one pass, because they share one file and any one of
them alone would force re-calibrating the same thresholds twice.

### What is wrong today

1. **`handleRoute` reimplements hop choice, and cheats twice while doing it** (`fret-sim.ts`
   ~825–870). Its candidate filter drops any peer whose *global* `alive` flag is false and any
   peer the *global* partition map says is unreachable — neither of which a real node can see —
   and then it takes `candidates[0]`, the first element of a concatenated ring walk, with no
   requirement that the hop be closer to the target than the current peer already is.
2. **Nothing under `test/simulation/` imports the shipped routing code.** `grep -L
   'minDistance|chooseNextHop|clockwiseDistance'` over that directory matches every file. So when
   `consolidate-ring-distance` replaced the distance function behind every next-hop decision, the
   churn scenario still reported 90% routing success — it would have reported the same had the
   metric been left broken. Making the sim router merely *more realistic* would not fix this; it
   has to route through the shipped `chooseNextHop`.
3. **Churn is materialised at setup and under-delivers** (`scheduleChurn`, ~286–297). Every
   leaver is drawn once, up front, from the initial population: late joiners can never churn, and
   a peer picked twice produces a second `leave` event that is a no-op. Effective churn therefore
   runs below the configured rate, and it is leave-only — the config field is documented as
   "peers leaving/joining per second" but no join is ever paired with a leave, so at
   `churnRatePerSec: 5` over 10 s the N=100 scenario silently loses half its population.

Assume `6-sim-partition-merge-tests` has landed (it has: `reachable`/`partition`/`heal`, the
per-peer `contactFailures` escalation in `contactSweep`, the bounded dead re-probe, and the
reachable-population coverage denominator are all in the file). Its `state !== 'dead'` filter is
*not* the oracle this ticket retires — it reads only what the probing peer's own store recorded.
The global `alive` and `reachable` reads inside `handleRoute` are.

### Design

**Route on local knowledge, decide with the shipped selector.**

Replace the body of the hop loop in `handleRoute` with:

- **Candidate pool** — the current peer's own store only:
  `neighborsRight(targetCoord, m, notDead)` ∪ `neighborsLeft(targetCoord, m, notDead)`, minus
  `visited` (the breadcrumb trail) and minus self. No `alive` read, no `reachable` read. This
  mirrors production, which composes its exclusions *into* the walk rather than filtering the
  result.
- **Hop choice** — `chooseNextHop` from `src/selector/next-hop.js`, on the cost path:

  ```ts
  chooseNextHop(store, targetCoord, candidates, isConnected, linkQ, {
      nearRadius,                 // see below
      selfCoord: currentPeer.coord,
      confidence: 0.5,
  })
  ```

  - `isConnected = (id) => currentPeer.connected.has(id)`.
  - `linkQ = () => 0` — the sim models no latency; a constant is honest, and it must be a
    *constant* rather than a random draw or determinism breaks.
  - `backoffPenalty` is omitted (the sim has no backoff model; `contactFailures` is escalation,
    not backoff).
  - Supplying `selfCoord` is the point: it is what makes each hop strictly closer to the target
    than the peer that chose it, which is the production invariant `nexthop-cost.spec.ts` pins
    and which the sim currently does not honour at all.
  - `nearRadius` must be derived from **local** information: `β · k · (2^256 / max(1, store.size()))`
    with β = 2, clamped to at most half the ring (`1n << 255n`), converted with the existing
    `bigintToCoord`. `store.size()` is this peer's own view of the population — the sim's stand-in
    for `n_est`. Do **not** use `aliveCount()`; that is the same oracle in a new place.
- **Contact attempt** — the chosen hop is a *candidate*, not a delivered message. Attempt it:
  the contact succeeds when `contactAllowed(current, next)` and the target peer is really alive.
  On failure, record a contact strike against `next`'s entry in `current`'s store (the same
  escalation `contactSweep` performs, at `deadAfterFailures` marking it `dead` and stamping
  `lastAccess` with sim time) and choose again from the remaining candidates. This is how the
  oracle is *replaced* rather than deleted: a peer still learns that a hop is unusable, but only
  from its own failed contact. Bound the retries by an attempt budget (reuse the existing
  `maxHops` budget for total contact attempts, successful or not) so a route through a fully
  partitioned-away window terminates.
- **Hop counting** — only a successful contact increments `hops`; a failed attempt spends the
  attempt budget, not a hop, so `avgRoutingHops` stays a path-length measure.
- **Arrival test** — unchanged. Today's test already reads only the current peer's own store, and
  the deliberately-unfiltered `successorOfCoord` / `predecessorOfCoord` reads there carry a
  `NOTE:` explaining why (a boundary peer must not crown itself anchor for a far-side coordinate
  while its store still names a dead entry closer to the key). Keep both the behavior and the
  note.

**Factor the escalation once.** `contactSweep` and the routing path now both need "one failed
contact against this entry" and "this entry answered". Extract a private
`recordContactFailure(store, entry, time)` / `recordContactSuccess(store, entry)` pair and call it
from both; a second copy of the strike-to-`dead` arithmetic is exactly how the two drift.

**Schedule churn lazily, and make it churn.**

- Add `'churn'` to `SimEvent['type']` in `event-scheduler.ts`.
- `scheduleChurn` schedules bare `{ type: 'churn' }` events at each interval and picks nobody.
- `handleChurn()` runs at fire time: pick one peer from the *currently* alive population
  (`rng.pick`), leave it via the existing `handleLeave`, then add one fresh peer via the existing
  join path. Late joiners are now eligible, a duplicate pick is impossible, and the population is
  stationary instead of draining.
- Pairing a join with each leave is a deliberate semantic decision, not a drive-by: the field is
  documented as "peers leaving/joining per second", and a leave-only reading makes any
  success threshold at `churnRatePerSec: 5` a measurement of population collapse rather than of
  routing under churn. State this in the field's doc comment.
- Consequence: `metrics.totalJoins` now exceeds `config.n` whenever churn is on. Three call sites
  assert equality and must be relaxed to `>=` or to an exact expected count:
  `simulation.spec.ts` (N=25 @ 0.25/s, N=100 @ 5/s), `message-bus.spec.ts:166` (0.5/s),
  `churn-scenarios.spec.ts:209` (1/s). Every other sim spec runs `churnRatePerSec: 0` and is
  untouched by this half.
- RNG draws move from setup time to fire time, so every seeded run's numbers shift. Determinism
  is preserved (same seed → same stream), which is what the partition suite's replay test pins;
  the *values* in threshold assertions are what change.

### Edge cases & interactions

- **No strictly-improving hop.** `chooseNextHop` with `selfCoord` returns `undefined` when every
  candidate is behind the current peer. That is the *correct* production outcome
  (`exhausted` / a `NearAnchor` reply), not a bug to route around — record the route as a failure
  and stop. Do not fall back to "closest anyway"; that reintroduces the drift the `selfCoord`
  floor exists to prevent.
- **Originator vs forwarder.** Production supplies `selfCoord` only on the *forwarding* path; an
  originator aiming at a key's cluster is legitimately farther from the key than every cluster
  member. The sim's `handleRoute` starts at the originator, so the first hop must **not** apply
  the floor — pass `selfCoord` from the second hop onward, or the sim will report failures for
  routes that production completes. Cover this explicitly with a case where the source is itself
  the peer nearest the target.
- **Ring smaller than m.** N=5, m=3 (`simulation.spec.ts`) — the two walks overlap and return the
  same handful of ids including self. Filtering self and `visited` can empty the pool on hop 1;
  assert the route ends as a defined failure (or an immediate arrival), never a throw or an
  infinite loop.
- **Single live peer / everyone else dead.** Candidate pool empty, arrival test false → one
  recorded failure, zero hops.
- **Every candidate unreachable (active partition).** The attempt budget must terminate the loop;
  each failed attempt must strike exactly once, so `deadAfterFailures` consecutive routes through
  the same window mark those entries `dead` and later routes skip them via `notDead`. Assert the
  strike count, not just the termination.
- **Routing during a partition must still fail across the cut.** `simulation.partition.spec.ts`
  asserts an A→B route fails during a cut *by exhaustion*. With the `reachable` pool filter gone,
  that outcome must now arise from failed contact attempts instead. Re-run that suite and confirm
  the assertion still passes **for the right reason** — check `crossPartitionBlocked()` actually
  increments during the route, which under the old pool filter it did not.
- **Routing during a heal.** A dead entry re-probed back to `disconnected` becomes a candidate
  again; a route issued between the heal and the re-probe still fails. Both are correct; pin the
  ordering so it is not mistaken for flakiness later.
- **Determinism.** Two runs at one seed must produce byte-identical metrics after both changes.
  The replay case in `simulation.partition.spec.ts` covers the partition schedule; add a churn
  replay case, since lazy scheduling is precisely what could introduce order-dependence.
- **`chooseNextHop` reads coordinates from the store, not from `SimPeer`.** Any candidate id must
  have an entry in the *current peer's* store or the selector silently skips it — which is
  already true of the pool by construction, but a future change that hands it ids from elsewhere
  would degrade to "no hop" with no error. Note it at the call site.
- **Capacity eviction interaction.** With `capacity` set, an evicted entry disappears from the
  pool mid-run; a route can then fail where it previously succeeded. Expected, not a regression —
  keep the routing spec's capacity unset so the threshold measures routing, not eviction.
- **Sim-clock stamps only.** `store.update(..., { lastAccess: time })` must use scheduler time,
  never `Date.now()`, or the dead re-probe ordering stops replaying. The routing path now writes
  `lastAccess` too and inherits this rule.
