## Phase 0 — route on local knowledge (skip only if already done)

Check first: `grep -n chooseNextHop test/simulation/fret-sim.ts`. A hit means the sibling landed —
skip to phase 1. No hit means do this phase here.

Replace the hop loop body in `handleRoute`:

- **Candidate pool — the current peer's own store only.**
  `store.neighborsRight(targetCoord, m, notDead)` ∪ `store.neighborsLeft(targetCoord, m, notDead)`,
  minus `visited` and minus self. **Delete the `alive` read and the `reachable` read from the
  filter** — neither is visible to a real node. `notDead` stays: it reads only what this peer's own
  contact attempts recorded.
- **Hop choice — the shipped selector, cost path:**

  ```ts
  chooseNextHop(store, targetCoord, candidates, isConnected, linkQ, {
  	nearRadius: this.nearRadiusFor(store),
  	selfCoord: currentPeer.coord,   // from hop 2 onward only — see below
  	confidence: 0.5,
  })
  ```

  `isConnected = (id) => currentPeer.connected.has(id)`. `linkQ = () => 0` — the sim models no
  latency and it **must be constant or determinism breaks**. Omit `backoffPenalty` (no backoff
  model). Note at the call site that a candidate absent from this peer's store is skipped by the
  selector — true of this pool by construction.
- **`nearRadiusFor(store)`** (new private helper) — local info only:
  `β · k · (2^256 / max(1, store.size()))` with β = 2, clamped to at most half the ring
  (`1n << 255n`), converted via the existing module-private `bigintToCoord`.
  **Do not use `aliveCount()`** — that is the oracle in a new place.
- **Contact attempt.** The chosen hop is a candidate, not a delivered message. Contact succeeds when
  `contactAllowed(current, next)` **and** the target peer is really alive. On failure, record a
  contact strike against `next`'s entry in `current`'s store — the same escalation `contactSweep`
  performs — then choose again from the remaining candidates. **Extract that arithmetic once**:
  private `recordContactFailure(store, entry, time)` / `recordContactSuccess(store, entry)`, called
  from both `contactSweep` and the routing path. A second copy is how the two drift.
- **Attempt budget.** Bound total contact attempts (successful or not) by the existing `maxHops` so
  a route through a fully partitioned-away window terminates. `maxHops` reads `aliveCount()`; decide
  whether it keeps the oracle count (defensible — a test-harness budget, not a peer decision) or
  moves to `store.size()`, and say which in a comment. Local derivation is mandated only for
  `nearRadius`.
- **Hop counting.** Only a successful contact increments `hops`; a failed attempt spends attempt
  budget, not a hop, so `avgRoutingHops` stays a path-length measure.
- **Arrival test unchanged** (~lines 786–812), including the deliberately-unfiltered
  `successorOfCoord` / `predecessorOfCoord` reads and the `NOTE:` explaining why. Keep both.
- **Delete the two stale `24-sim-router-realism` comments** named above — rewrite, don't renumber;
  those deferrals are discharged here.

Edge cases to cover in code:

- **No strictly-improving hop** — `chooseNextHop` with `selfCoord` returns `undefined`. That is the
  correct production outcome: record the route as a failure and stop. No "closest anyway" fallback;
  that reintroduces the backwards drift the floor prevents.
- **Originator vs forwarder** — production supplies `selfCoord` only when *forwarding*. An
  originator aiming at a key's cluster is legitimately farther from the key than every cluster
  member, so **the first hop must not apply the floor**: pass `selfCoord` from hop 2 onward, or the
  sim reports failures for routes production completes.
- **Ring smaller than m** (N=5, m=3 in `simulation.spec.ts`) — walks overlap; the pool can empty on
  hop 1 after filtering self and `visited`. Must end as a defined failure or an arrival, never a
  throw or an infinite loop.
- **Single live peer** — empty pool, arrival test false → one recorded failure, zero hops.
- **Every candidate unreachable (active partition)** — the attempt budget terminates; each failed
  attempt strikes exactly once, so `deadAfterFailures` consecutive routes through the same window
  mark those entries dead and later routes skip them via `notDead`.
- **Routing during heal** — a dead entry re-probed back to `disconnected` is a candidate again; a
  route issued between heal and re-probe still fails. Both correct.

## Phase 1 — new spec `packages/fret/test/simulation.routing.spec.ts`

- **Converged case**: seeded N≈200 uniform ring, m=8, k=15, no churn, run to convergence; then ~100
  routes from random live sources to random target coordinates (32-byte coordinates drawn from a
  seeded `DeterministicRNG`). Assert routing success ≥ a threshold and p90 hop count ≤ an O(log N)
  bound.
- **Churn case**: same shape at moderate churn, lower success threshold.
- **Set both thresholds from measured values, minus a stated margin — put the measured numbers in a
  comment beside them.** A threshold picked before running proves nothing.
- **p90 over successful routes only.** `recordRoute` pushes `hops` for failures too, so failure
  partials skew the bound. Take the percentile over successful routes' hop counts explicitly; if
  per-route success/hops pairs are not reachable from `SimMetrics`, extend the collector minimally
  (e.g. a `successfulRouteHops` array) rather than inferring.
- **Cover the originator-nearest case explicitly** — a route whose source is itself the peer nearest
  the target must succeed. This is what pins the "floor applies from hop 2 only" rule above.
- **Keep `capacity` unset.** With capacity set, eviction can fail routes that previously succeeded
  (expected, not a regression); the threshold must measure routing, not eviction.
