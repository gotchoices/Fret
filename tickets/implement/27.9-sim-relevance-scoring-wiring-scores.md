**Determinism is the sharp trap.** All four scoring entry points default `now = Date.now()`.
Every call must pass sim time explicitly or same-seed replay diverges — surfacing as flaky
thresholds, not errors. `recencyScore`'s half-life is 60 s against sim runs of 4–60 s, so
recency is a live term. Writing `lastAccess: simTime` in scoring patches *improves* determinism
(`upsert` stamps wall-clock) but reorders `reprobeDeadEntries`, which sorts ascending
`lastAccess` — re-run `test/simulation.partition.spec.ts`.

## Edit 2 — `test/simulation/fret-sim.ts`

- Imports: `import { createSparsityModel, initialRelevance, touch, observeDistance,
  normalizedLogDistance } from '../../src/store/relevance.js'` plus `import type { SparsityModel }`.
- New field beside `private readonly stores`: `private readonly models = new Map<string,
  SparsityModel>()`. One model **per peer** — a shared model would make every peer's bonus a
  function of every other peer's observations. The model consumes no RNG, so it must not perturb
  same-seed replay (the partition spec pins this). Departed peers keep their model entry, same
  memory note as `stores` carries in `handleLeave`.
- The `LivenessDeps` object literal in the constructor gains: `modelFor: (selfId) =>
  this.models.get(selfId)!`, `coordOf: (id) => this.peers.get(id)!.coord`, `now: () =>
  this.scheduler.getCurrentTime()`.
- `handleRoute`'s two scoring calls (`recordContactFailure` / `recordContactSuccess`, near the
  end of the file) gain `current` as their first argument.
- Five upsert sites. Suggested helper: a private `scoreMerge(storeOwnerId, store, id)` for the
  two hearsay sites, so bus mode and instant mode cannot diverge.
  1. `addPeer` (self-seed, `store.upsert(peer.id, peer.coord)`): create the model first
     (`this.models.set(peer.id, createSparsityModel())`), then after the upsert score the self
     entry with `initialRelevance` at `x = normalizedLogDistance(peer.coord, peer.coord)`
     (= 0 distance) and `now = this.scheduler.getCurrentTime()`; patch `{ relevance,
     lastAccess: now }`. Self is eviction-protected anyway — this only avoids the 0 sentinel.
  2. `handleConnect`'s bootstrap sample (`store.upsert(other.id, other.coord)`): real contact ->
     `touch`. After the upsert: `const e = store.getById(other.id)!; const t = touch(e, x, model,
     simNow); store.update(other.id, { relevance: t.relevance, lastAccess: t.lastAccess,
     accessCount: t.accessCount })`. `x` is measured self (the connecting peer's coord) -> other.
  3. `processDeliveredMessage`'s `neighbor-response` merge loop: hearsay -> `initialRelevance`
     **plus an explicit `observeDistance(model, x)`**, and re-score even when the entry already
     existed. Patch `{ relevance, lastAccess: time }`. The dead-entry skip immediately above must
     skip scoring too — scoring sits after that `continue`, so it does naturally; keep it that way.
  4. `exchangeNeighborsDirect`'s two merge loops: same as 3, per receiving store/model side (the
     peer's store scores with the peer's model and the peer's coord; `nstore` with the
     neighbor's). The dead-skip is already inline in each loop's condition — score only when the
     upsert ran.
  5. Route success/failure — lands via Edit 1's seam; only the `current` argument changes here.
- **Required deviation from production; record it as a `NOTE:` at the merge sites (3 and 4).**
  The sim's kernel density estimate is fed by gossip because the sim has orders of magnitude
  fewer contact events per peer than a real node does. Production's hearsay rule (score once at
  creation, never observe the distance) degenerates here: only-proven-contact feeds at most
  about `maxConnections` observations per peer, so at `alpha = 0.03` occupancy stays near 0, the
  ratio stays above `sMax^(1/beta) ~= 2.63`, and every entry clamps at `sMax = 1.8` and ties —
  the same degeneracy one layer down. Re-scoring an already-held entry on each merge (a
  deviation from production's leave-it-alone rule for gossip) lets the bonus track growing
  occupancy.
- **One paragraph of `enforceCapacity`'s comment.** Its `NOTE:` currently says eviction is only
  *ranked* by relevance once something scores entries, and names this ticket. Once scoring
  lands, rewrite that paragraph to say eviction is now genuinely relevance-ranked and that
  protection outranks the cap. `28.5-sim-metric-guard-case` expects that rewrite.

## Edge cases (settled design; verify, don't re-derive)

- `capacity < 2m + 1`: protection outranks the cap — the store stays over capacity; the
  slice-based eviction cannot loop and must never evict a protected id. (Already true of the
  landed code; keep it true.)
- store smaller than `m`: the walk returns fewer per side; protection must not assume `m`.
- churn: `contactSweep` prunes departed ids, so a scoring call must tolerate `getById` returning
  `undefined` (relevant if a helper re-reads after a remove).
- a merge that skips a locally-`dead` entry skips its scoring too — otherwise the skip's point
  (no resurrection, deterministic `lastAccess`) is lost.
- bus mode and instant mode take the same scoring path (sites 3 and 4 must not diverge — hence
  the shared-helper suggestion).
- `capacity` unset (every existing sim spec): scoring writes relevance but nothing evicts —
  **no existing threshold may move**.
