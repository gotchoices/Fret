## The rule under test

`wasCancelled(sig)` (`fret-service.ts:666`) is `sig?.aborted === true`, checked against the signal
the **caller** captured before its loop — not the sender's own deadline, which is a *child* of it
and so also fires on a genuine timeout. When true, the call site records nothing: no
`noteRpcFailure` (hence no contact strike, no relevance decay), no `recordBackoff`, no
`diag.pingsFail`.

## Where the guard genuinely fires

`sendPing` (`src/rpc/ping.ts:77`) and `sendMaybeAct` (`src/rpc/maybe-act.ts:48`) have **no catch** —
they let the abort propagate. `openRpcStream` (`src/rpc/protocols.ts:283`) throws immediately on an
already-aborted signal, before dialing. So these six sites reach their `catch` and the guard works:

| Site | line | What it skips when cancelled |
|---|---|---|
| `preconnectNeighbors` | 1298/1305 | `return` before `pingsSent++` |
| active-preconnect loop tick | 1331/1338 | `break` |
| `probeNeighborsLatency` | 1781/1798 | `return` before `pingsFail++` / `noteRpcFailure` |
| `probeMembership` | 1930/1946 | `return` before `pingsFail++` / `noteRpcFailure` / `recordBackoff` |
| `routeAct` forward path | 2228/2248 | skips `noteRpcFailure` + `recordBackoff` |
| `iterativeLookup` (hop + activity resend) | 2550/2701/2724 | `break` → falls to `yield { type: 'exhausted', hop }` |

## Two sites where the guard cannot fire

Both senders swallow every error internally, so the `catch` block holding `wasCancelled` is never
entered on the cancellation path. The previous ticket asserted the opposite for both.

**`mergeNeighborSnapshots` (1962/1993) — already a documented, accepted behaviour. Do not re-file
and do not try to fix it here.** `fetchNeighbors` (`src/rpc/neighbors.ts:86`) catches everything and
returns a fabricated empty snapshot, so `diag.snapshotsFetched++` still runs for a fetch that never
opened a stream. This is written up at the call site (`fret-service.ts:1764–1772`) and the existing
lifecycle test deliberately does not assert the counter
(`test/service-lifecycle.spec.ts:435–439`). Consequence for this ticket: **do not assert
`snapshotsFetched` unchanged.** Assert the things that are true — no strike, no backoff, nothing
merged — and pin the overcount explicitly (`+1`) with a comment saying the expectation flips to
"unchanged" if `fetchNeighbors` ever distinguishes "skipped" from "empty".

**`sendAnnouncementsRateLimited` (1240/1251) — an undocumented gap, and the one judgement call this
ticket has to make.** `announceNeighbors` (`src/rpc/neighbors.ts:126`) catches and logs, so the
`if (this.wasCancelled(sig)) return` at 1251 is unreachable on abort: the loop keeps taking an
announce token and incrementing `diag.announcementsSent` for every remaining target. In production
the damage is bounded because `stop()` sets `this.stopped` in the same tick and the loop's existing
top-of-loop `if (this.stopped) break` catches it on the next iteration — but that leaves the
captured-signal case the guard exists for (a `stop()` + `start()` landing mid-loop, where `sig` is
aborted while `stopped` is already back to `false`) with no stop at all.

Recommended fix, and what the test should then assert: widen the existing top-of-loop check to
`if (this.stopped || this.wasCancelled(sig)) break`, which makes the site's documented behaviour
real for one line of code. The assertion becomes **zero** announce tokens taken (not one), paired
with a non-cancelled contrast run that takes one per live target so it cannot pass vacuously. If you
decide against the fix, that is a legitimate call — then write the test against real behaviour and
add a `NOTE:` at 1251 in the shape of the `fetchNeighbors` one above, so the next reader meets the
gap at the code.

## Test scaffolding (all verified)

Add a new `describe` block to `packages/fret/test/dead-state.spec.ts`. The file already has
`coordAt(value)` at module scope; `seedPeer` / `strike` / `unspace` and an `unreachablePeer()`
factory (line 675) live *inside* existing blocks, so copy what you need.

**Get an aborted run signal without starting the service.** A started service runs a stabilization
loop that probes the synthetic peers and makes ping counts non-deterministic — every existing block
in this file constructs the service and deliberately does not start it. Reproduce the state `stop()`
leaves behind:

```ts
/** The state `stop()` leaves behind: a run signal already aborted, kept rather than nulled. */
function cancelRun(svc: CoreFretService): void {
	const ac = new AbortController()
	ac.abort(new Error('service stopped'))
	;(svc as any).runAbort = ac
}

/** A live run, for the contrast cases — `runAbort` is null until the first `start()`. */
function liveRun(svc: CoreFretService): AbortController {
	const ac = new AbortController()
	;(svc as any).runAbort = ac
	return ac
}
```

`cancelRun` deliberately leaves `this.stopped` false, so what stops each pass is the *signal*. That
`stop()` really produces this state is asserted separately in `test/service-lifecycle.spec.ts:452`
("mints a fresh run signal per start and leaves the stopped run aborted"), so this block need not
re-prove it.

**Trap: use real Ed25519 peer ids, not synthetic strings.** `sendPing`/`sendMaybeAct` call
`peerIdFromString` on their first line, outside the `try`, so a synthetic id like `'peer-a'` throws a
*parse* error. The cancelled-path test would then pass for the wrong reason, and the contrast case
would record a strike that has nothing to do with reachability. Use the `unreachablePeer()` recipe
from line 675 (spin a mem node, stop it, keep its id) and `(svc as any).setAddressKnown(id, true)`
where the site needs dialability.

Shape of each test: seed a member peer, `cancelRun(svc)`, drive the method, assert **nothing was
scored** — `contactFailures === 0`, `state !== 'dead'`, `(svc as any).backoffMap.get(id) ===
undefined`, and the relevant `getDiagnostics()` counter unchanged.

## Tests to add

- `probeNeighborsLatency([id])` — the headline case. `pingsSent` and `pingsFail` both unchanged.
- `probeMembership(id)` — the one that also records backoff on the unguarded path; the
  `backoffMap.get(id) === undefined` assertion is what matters here.
- **Contrast case, so the guard is not over-broad:** the same unreachable peer with the run signal
  *live* (`liveRun`) and the RPC's own budget firing **does** strike once. The existing test "marks
  an unreachable neighbor dead after a run of failed pings" (line 684) already pins the full run —
  **do not weaken it**; add one explicit single-strike contrast inside the new block so the pair
  reads together.
- `preconnectNeighbors()` — `pingsSent` unchanged, no strike.
- `mergeNeighborSnapshots([id])` — no strike, no backoff, nothing merged; `snapshotsFetched` pinned
  at `+1` per the accepted behaviour above.
- `sendAnnouncementsRateLimited([a, b], snap)` — stub the bucket the way the existing announce test
  does (line 643): `;(svc as any).bucketAnnounce = { tryTake: () => { takes++; return true } }`.
  Assert per the decision recorded above, plus a non-cancelled contrast so it is not vacuous.
- `routeAct(msg)` — force the not-in-cluster forward path. Recipe: import `hashKey` from
  `../src/ring/hash.js`, compute the key's coordinate yourself, seed two member+dialable peers at
  coordinates one byte either side of it, and send `want_k: 2` (so `inClusterWindow` is
  `max(2, min(2, 2)) = 2`, and the two seeded peers fill the cohort ahead of self). Assert the reply
  is a `NearAnchorV1` (the honest "did not forward"), that `diag.maybeActForwarded` incremented (this
  is what proves the forward path was actually taken, rather than the test passing because the
  message was answered in-cluster), and that no seeded candidate was struck or backed off.
- `iterativeLookup(key, opts)` — hop arm. Drain the generator; assert the **last** yielded progress
  is `{ type: 'exhausted' }` and that no contacted peer gained a strike or a backoff entry. It also
  yields `probing` first, so collect all and inspect the tail.
- `iterativeLookup` — **activity-resend arm** (2701), the one the design question below is about.
  Reachable with two real nodes, and the previously-feared blocker does not apply: on a small ring
  `shouldIncludePayload` returns false regardless of distance, because
  `probability * confidence >= 0.5` needs `confidence >= 0.5` and confidence is
  `0.5*sizeFactor + 0.5*dispersion` with `sizeFactor = count / 2m` — roughly 0.4 with four members
  (`src/service/payload-heuristic.ts:31`, `docs/fret.md` "Confidence calculation"). So the payload
  is withheld on the probe and the resend arm is taken. Recipe: node A holds the service under test
  (**not** started), node B runs a started `CoreFretService` on the same `networkName` so its
  maybeAct handler answers; A dials B and seeds B into A's store as a dialable member; `liveRun(A)`;
  drive the generator with explicit `.next()` calls and abort the controller as soon as
  `near_anchor` arrives. Assert `activity_sent` really was yielded (otherwise the arm was never
  reached and the test is vacuous), that the walk then ends in `exhausted`, and that neither B nor
  the chosen anchor was struck or backed off.

## Open design question — answer it while writing the `iterativeLookup` tests

A caller cannot today tell "the ring had no more hops" from "the service shut down under you": both
surface as `exhausted`, and on the activity-resend arm the activity was never delivered.

**Recommended resolution (do this unless you find a reason not to):** document rather than widen the
type. `RouteProgress` (`src/index.ts:78`) is part of the public `FretService` interface
(`iterativeLookup` is declared there at line 121), so adding a `{ type: 'cancelled' }` variant is an
API change well beyond a test ticket, and every existing consumer would have to learn it. Instead
add a `NOTE:` at the `iterativeLookup` cancellation site naming the fact. The matching prose lives in
the `rpc-cancel-docs` ticket, which owns `docs/fret.md`; if you land the `NOTE:` here, say so in the
handoff so that ticket does not duplicate it.
