## Three sections of `docs/fret.md` to update

**Stream management.** The bullet currently reads "Stream read deadline: one overall budget per read
(`readAllBounded`, 5s default, uniform across the four RPCs today)". That is stale: the budget now
covers the **whole RPC** — dial + stream open + write + read. Restate it as such, naming
`RPC_TIMEOUT_MS` (5000, exported from `src/rpc/protocols.ts:15` so the four outbound RPC families
cannot drift apart), and name the per-call-site overrides:

- `MAINTENANCE_RPC_TIMEOUT_MS` = 2000 (`fret-service.ts:292`) on maintenance pings and announces.
- 5 s left at the default on `sendMaybeAct`, deliberately, because it is a *route* budget not a link
  one — the call returns only once the entire remaining route has completed downstream, so
  tightening it truncates healthy long routes (`src/rpc/maybe-act.ts:43-46`).
- `SHUTDOWN_BUDGET_MS` = 3000 (`fret-service.ts:301`) for the whole leave fan-out, with
  `LEAVE_NOTICE_TIMEOUT_MS` = 1500 (line 303) per notice so one stalled peer cannot eat it whole.
  That fan-out cannot reuse the run signal — it runs *after* that aborts, by design.

Keep the existing "no per-chunk idle timer" reasoning intact; it is still correct and still
load-bearing.

**Stabilization and churn handling.** Next to the `deadAfterFailures` discussion, add the rule that
**our own cancellation is not evidence about the peer**: a run-signal abort (`stop()`, or a future
per-tick budget) records no contact failure, no backoff, and no ping-failure diagnostic; only the
RPC's own timeout does. Say *why* the caller's signal is the discriminator — the sender builds its
deadline as a *child* of the caller's signal, so the child fires in both cases while the caller's
fires only on ours. That is also why no new error type was needed: the caller already holds the
discriminating fact.

State honestly that the rule is enforced at six of the eight guarded call sites and **not** at the
two whose sender swallows its own errors (`fetchNeighbors` behind `mergeNeighborSnapshots`,
`announceNeighbors` behind `sendAnnouncementsRateLimited`) — see the `NOTE:` at `fret-service.ts:1764`
for the accepted-tradeoff write-up of the first. If `rpc-cancel-evidence-tests` lands the one-line
fix it proposes for the announce site, drop it from that list rather than describing a gap that no
longer exists; check the code before writing the sentence.

**Service shell & lifecycle (A1).** One line beside the run-generation paragraph on the run-scoped
`AbortController`: minted with `runGen` on `start()` (`fret-service.ts:771`), aborted right after the
loop timers on `stop()` (line 880) and before the leave fan-out — which carries its own budget, which
is why aborting does not silence it. The aborted controller is deliberately kept rather than nulled,
so a late read from an interrupted tick still reports "cancelled" instead of "no signal at all".

## The `exhausted`-vs-cancelled fact to write down

A caller cannot today tell "the ring had no more hops" from "the service shut down under you": both
surface as `RouteProgress { type: 'exhausted' }`, and on the activity-resend arm the activity was
never delivered.

The resolution is to document rather than widen the type — `RouteProgress` (`src/index.ts:78`) is
part of the public `FretService` interface, so a `{ type: 'cancelled' }` variant is an API change
every consumer would have to learn. So state explicitly in `docs/fret.md` (in the A5 /
RouteAndMaybeAct pipeline section) that `exhausted` covers cancellation, and that a caller must
re-check service state before concluding the ring was exhausted — in particular that an undelivered
activity is a possible outcome.

The matching code `NOTE:` at the `iterativeLookup` cancellation site belongs to
`rpc-cancel-evidence-tests`. If that ticket has already landed it, do not duplicate it; if it has
not, add it here so the fact is not left implicit in either place.
