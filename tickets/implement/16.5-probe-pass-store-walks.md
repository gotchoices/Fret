Planned out of `plan/16.5-probe-pass-store-walks` (itself point (d) of `16-per-tick-hotpath-waste`).
The design question that ticket existed to settle — *where do the counts live* — is settled below;
implement exactly that, do not re-open it.

### The waste being removed

`stabilizeOnce` selects its phase-2 probe targets with

```ts
const targets = [...this.classifyTargets(), ...this.reprobeExcludedTargets()];
```

which is **three full `store.list()` walks per tick** (`fret-service.ts` ~2189, ~2240, ~2241) — one
per candidate set, each materializing an array of every entry (up to capacity 2048) and then
filtering it down:

- `classifyTargets`: `membership === 'unknown' && state !== 'dead'`
- `reprobeOffRingTargets` foreign arm: `membership === 'foreign' && state !== 'dead'`
- `reprobeOffRingTargets` dead arm: `state === 'dead'`

In single-network steady state every peer is `member` and non-dead, so all three lists come back
**empty** and the tick paid three full-table materializations to learn there was nothing to do — at
up to ~3 ticks/second in active mode. A `NOTE:` at `classifyTargets` records this at the code site;
this ticket is that NOTE's fix, and the NOTE comes out with it.

### The decision (settled — do not re-litigate)

**Counts are maintained inside `DigitreeStore`.** Verified by reading
`src/store/digitree-store.ts:186-252,470-506`:

- `put` (line ~190) is the **only** insert/replace path. `upsert` (~206), `update` (~233),
  `setState` (~264), `setMembership` (~268) and `importEntries` (~503) all funnel through it —
  `setState`/`setMembership` delegate to `update`, which builds `{ ...cur, ...patch }` and calls
  `put`. **Nothing mutates an entry in place.** Confirmed by grep over `src/`: every label change
  is built as a patch object (`fret-service.ts:627, 653, 656, 799, 815`) and handed to the store.
- `remove` (~246) is the only delete path.

So the counts are derivable at exactly two sites (`put`, `remove`) and cannot drift — the
"make the bad state unrepresentable" rung rather than a hand-maintained tally in `FretService`
keyed off every call site that flips a label. That is why this is in the store.

**Rejected alternative, recorded with its reason:** ship only the shared-walk half (one walk per
tick instead of three, no new store state, no invariant to keep). Rejected because the seam *is*
single-point, so the counts carry no drift risk worth avoiding, and the shared-walk-only option
leaves steady state paying one full walk per tick forever instead of zero — which is the actual
complaint. Both halves ship together; the shared walk is what the non-empty case falls back to.

**Network-agnostic rule is not violated.** `docs/fret.md` says the store "stores and exposes both
fields and never branches on them". A tally over a field the store already owns is bookkeeping, not
policy: the store never asks *whether* a label means anything, and the API takes the label as a
**parameter** rather than privileging a particular value. Say this in a comment at the counters, in
one sentence — the next reader will ask.

### Shape

**Half 1 — O(1) counts in the store.**

```ts
// in DigitreeStore
private readonly membershipCounts = new Map<MembershipState, number>();
private readonly stateCounts = new Map<PeerState, number>();

/** How many entries currently carry `m`. O(1). */
countByMembership(m: MembershipState): number;
/** How many entries currently carry `s`. O(1). */
countByState(s: PeerState): number;
```

Maintained at the two seams and nowhere else:

- `put`: read the previous entry **by id** (`getById(entry.id)`) before writing; if present,
  decrement its `membership` and `state` tallies; then increment the new entry's. A re-key is
  therefore net-zero when the labels are unchanged, and a same-key replace is handled by the same
  code path — there is no coordinate-move special case, exactly as `put` already has none.
- `remove`: decrement the removed entry's tallies.

Do **not** add a third maintenance point. If you find yourself needing one, the seam assumption
broke and the ticket needs re-planning, not a patch.

**Half 2 — one shared walk, gated on the counts.** Add a private selector-driver on `FretService`,
called from `stabilizeOnce` in place of the two-selector spread:

```ts
private phaseTwoTargets(): string[] {
    // Zero counts prove the compound candidate sets are empty, so the tick walks nothing.
    if (this.store.countByMembership('unknown') === 0
        && this.store.countByMembership('foreign') === 0
        && this.store.countByState('dead') === 0) return [];
    const entries = this.store.list();   // one walk, shared by all three arms
    return [...this.classifyTargets(entries), ...this.reprobeExcludedTargets(entries)];
}
```

The counts are **supersets** of each arm's compound predicate (`unknown` ⊇ `unknown && !dead`,
`foreign` ⊇ `foreign && !dead`, `dead` = `dead`), which is what makes a zero count a *sound proof*
that the compound set is empty. Three single-field counts are therefore enough; no compound
bookkeeping.

Each selector keeps its **own budget, ordering and predicate** — the separate budgets are a
documented invariant (`docs/fret.md`: a large foreign population must not starve dead recovery), so
only the *walk* is shared, never the candidate lists.

Give the selectors the entry array as a **parameter defaulting to `this.store.list()`**:

```ts
private classifyTargets(entries: PeerEntry[] = this.store.list()): string[]
private reprobeExcludedTargets(entries: PeerEntry[] = this.store.list()): string[]
private reprobeOffRingTargets(entries: PeerEntry[], isCandidate: (e: PeerEntry) => boolean, budget: number): string[]
```

The default matters: `test/dead-state.spec.ts:592,607`, `test/failure-recovery.spec.ts:84` and
`test/stabilize-concurrency.spec.ts:160,161,239,246` call these selectors bare through
`(svc as any)`, and they must keep working unchanged. The count gate lives in `phaseTwoTargets`
(the only production caller), not inside the selectors, so a bare test call still exercises the
real selection logic.

Body change inside each selector is one line: `this.store.list().filter(...)` → `entries.filter(...)`.

### Edge cases & interactions

- **Self is counted like any other entry.** It is seeded `member` and never marked dead, so it
  contributes to none of the three gated counters. A single-node ring must early-return on all
  three and must not underflow. Test it.
- **A peer that is both `foreign` and `dead` belongs to the dead arm alone** (documented
  disjointness, pinned by `test/stabilize-concurrency.spec.ts`). The superset counts must not
  resurrect it into two arms — the arms' own predicates already enforce this (`foreign && !dead`),
  and the shared walk must not change them.
- **The four per-tick candidate sets stay disjoint** — near / classify / foreign / dead. That
  disjointness is what makes pooled probing safe against the lost-increment race on the score and
  strike counters, so the shared walk must not merge or duplicate ids across arms.
- **Ordering must survive the refactor.** `classifyTargets` orders by ascending `lastAccess`; each
  re-probe arm orders by ascending backoff factor; both preserve the connected-then-reachable
  grouping via stable sort. These exist to stop a budget-truncated tick re-deriving the same head
  every tick (`bug-discovery-scan-starves-ring-tail` was the same class of defect). The existing
  rotation tests must still pass untouched.
- **Re-key must not double-count or lose a count.** `upsert` preserves an existing entry's
  `membership` and `state` and refreshes only `coord` and `lastAccess`, and a coordinate change is
  a drop-and-place inside `put` — so the decrement/increment pair must bracket the whole `put`
  body, not just the insert.
- **`importEntries` replaces by id**, including replacing an existing entry that carries *different*
  labels. It routes through `put` per record, so this is covered by the seam — but assert it: import
  a table that flips a `member` to `foreign` and recount.
- **Eviction** (`enforceCapacity` → `store.remove`) must decrement.
- **`stop()` / restart** leaves the store instance and its entries in place (`fret-service.ts:166`
  is a `readonly` field, never cleared), so counts stay consistent trivially. No work here; just
  don't add a reset that clears one structure and not the other.
- **A count wrong in the *low* direction is a correctness bug, not a perf regression**: it makes a
  probe pass silently stop selecting, and a dead peer that is never re-probed never recovers (the
  dead arm is documented as the only path back for a peer that recovers but never dials us). A count
  wrong in the *high* direction merely costs a wasted walk. Aim the tests at the low direction.
- **Entries handed out by `getById` / `list` are live references**, so a future caller that mutated
  a label in place would corrupt the counts silently. No such site exists today (verified by grep).
  Do not add one; the invariants property test below is what catches a future one. Leave a one-line
  `NOTE:` at the counters saying the counts assume all writes go through the seam.
- Interactions: `plan/17-store-perf-allocation` also edits `digitree-store.ts` but targets the key
  builder (~152) and the wrap-around walks (~310-395) — different functions from the write seam;
  expect no conflict. `implement/16-per-tick-hotpath-waste` edits `stabilizeOnce`'s
  `enforceCapacity` call two lines above the target selection; trivial merge at worst.
  `plan/23-fret-service-decomposition` may relocate these selectors; a count-based early return
  travels with them either way.

### Test plan

- **`test/digitree.invariants.spec.ts` — the property that retires the class.** The existing
  model-based test already drives an arbitrary op sequence over `upsert` / `recoord` / `touch` /
  `import` / `reimport` / `remove` / `state` / `membership`, checking invariants after **every** op.
  Extend `checkInvariants` with: *for every `MembershipState` and every `PeerState`, the store's
  count equals a full recount of `store.list()`*. One added block covers the whole op space,
  including re-key and replace-by-import, and fails for any future write path that bypasses the seam.
- Targeted store cases (cheap, and they name the failure directly):
  - `setMembership('unknown' → 'member')` moves both counters by one; `setState(→ 'dead')` moves the
    state counter and leaves membership alone.
  - `remove` of a dead foreign peer decrements both.
  - `importEntries` replacing an existing id with different labels leaves the counts equal to a
    recount (not the sum of both records).
  - Counts on an empty store are 0 for every label, and never negative after removing an absent id.
- Service-level, aimed at the low direction (`test/stabilize-concurrency.spec.ts` or a sibling):
  - **`unknown → member` re-arms the early return**: with one unknown peer, `phaseTwoTargets()`
    selects it; after the classification probe succeeds, the count drops to zero and
    `phaseTwoTargets()` returns `[]` — assert it walked nothing, e.g. by spying on `store.list`
    (wrap it and count calls) rather than by timing.
  - **`member → dead` lifts the dead count off zero and the arm walks again on the very next tick,
    not one tick later**: run a contact-failure run to the `deadAfterFailures` threshold, then
    assert `phaseTwoTargets()` immediately selects that peer.
  - **Single-node ring**: all three counts 0, `phaseTwoTargets()` returns `[]`, `store.list` not
    called.
  - **Steady state costs zero walks**: a table of all-`member`, non-dead peers → `store.list` call
    count is 0 across a tick's phase-2 selection.
  - **Non-empty state costs exactly one walk**: one unknown + one foreign + one dead present →
    `store.list` called once, and the three arms return the same ids they did before the refactor.
- Regression: `test/dead-state.spec.ts` and `test/failure-recovery.spec.ts` call the selectors bare
  and are the specs most likely to bite; they must pass **unmodified** (that is what the defaulted
  parameter buys).
