## Design

### One enforcement point, not two

Every `slice(0, caps.*)` in both merge loops is dead once the caps live only at the parser. Remove
them, and add a `NOTE:` at `mergeSnapshotCaps` stating that the parser is the single enforcement
point and that both call sites (`fret-service.ts:1033` announce registration, the `parse:` option
in `fetchAndMergeSnapshot`) get their caps from this one method — leaving both is how two copies of
a cap drift apart.

### `parseSample` is stricter than the merge loops it replaces — keep the strictness, pin it

`parseSample` (`src/rpc/validate.ts`) drops any sample entry whose `relevance` is not a finite
number. Both merge loops read only `s.id` and `s.coord` and never touch `relevance`, so a peer whose
relevance encodes as `null` (a `NaN` at the sender) has that entry dropped. Already live on the
announce path since `15.32`; this ticket extends it to the fetch path.

Decision carried forward from the `15.32` review: **keep the strictness and pin it with a test.**
The wire type declares `relevance: number` as required, so a sender emitting `null` is malformed.
The alternative — relaxing `relevance` to a dropped-advisory field via `finiteNumberOr`, matching
`size_estimate` / `confidence` on the same message — is the option being **declined**, not an
oversight.

A sample entry whose `coord` decodes to the wrong byte length must likewise be dropped by the
parser rather than reach `upsert`, where the store's write seam throws.

## Key tests to expect

Both merge paths, driven the way production drives them — through the parser — and asserting on
**counted loop work** (a spy wrapping `store.upsert`, the pattern `countUpserts` in that block
already uses) rather than on the absence of a crash. A cap that silently stopped applying would
leave a passing no-crash test and an unbounded per-message cost.

- **Announce path.** Drive the real registered handler so the test proves the *wiring* at
  `fret-service.ts:1033` rather than restating it. `handleAnnounce` `detach`es the merge, so the
  count is not deterministic on its own — wrap `mergeAnnounceSnapshot` on the instance to capture
  and await the promise it returns, which leaves the snapshot argument still coming through the
  real parser. (The `fakeNode()` / `invoke(protocol, stub, peer)` rig at the top of the fuzz spec
  is the cheap way in; a started service on a mem node drags stabilization and peerStore seeding
  into the upsert counter and is not worth it.)
- **Fetch path.** Fully deterministic and needs no such trick: stand up a stub node that serves one
  framed over-cap snapshot reply (`test/rpc.codec-properties.spec.ts:~1927` has the
  `nodeReplying(replyStream(reply))` shape to copy), `await fetchAndMergeSnapshot(id, undefined)`,
  and count. This is the test that proves the removed fetch-side slice was redundant.
- A `relevance: null` sample entry is dropped on **both** paths — one test covering both, not one
  now and one later.
