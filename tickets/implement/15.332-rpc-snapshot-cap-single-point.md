## Design

### One enforcement point, not two

Once `fetchNeighbors` is given `makeSnapshotParser(this.mergeSnapshotCaps())`, **both** merge paths
are parser-covered, so every `slice(0, caps.*)` in both merge loops is dead. Remove them, and add a
`NOTE:` at `mergeSnapshotCaps` stating that the parser is now the single enforcement point —
leaving both is how two copies of a cap drift apart.

Removal is only safe with both halves covered. The announce half already is; this ticket's
`fetchNeighbors` wiring closes the fetch half. **If for any reason the fetch half does not land,
do not remove the slices** — say so in the handoff instead.

### `parseSample` is stricter than the merge loops it replaces — keep the strictness, pin it

`parseSample` drops any sample entry whose `relevance` is not a finite number. Both merge loops
read only `s.id` and `s.coord` and never touch `relevance`, so a peer whose relevance score encodes
as `null` (a `NaN` at the sender) has that sample entry dropped. On the announce path this is
**already live behavior** (`15.32`); this ticket extends it to the fetch path.

Decision, carried forward from the `15.32` review: **keep the strictness and pin it with a test**,
covering both merge paths in one test rather than one now and one later. The wire type declares
`relevance: number` as required, so a sender emitting `null` there is malformed. (The alternative
— relaxing `relevance` to a dropped-advisory field via `finiteNumberOr`, matching how
`size_estimate` / `confidence` are handled on the same message — is the option being declined, not
an oversight.)

A sample entry whose `coord` decodes to the wrong byte length must likewise be dropped by the
parser rather than reach `upsert`, where the store's write seam throws.

## Key tests to expect

Extend `test/rpc.handler-fuzz.spec.ts`:

- A snapshot carrying more ids than the profile cap, arriving on **both** merge paths (announce and
  fetch): assert the parse+hash+upsert loop runs exactly `caps.*` times, **by counting the loop's
  work** — a spy on the store's `upsert` or on the hash — rather than by inferring it from the
  absence of a crash. This is the test that proves the removed slices were redundant.
- The `relevance: null` sample entry dropped on both merge paths.
