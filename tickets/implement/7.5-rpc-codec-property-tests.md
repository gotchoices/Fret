The second half of the fuzz tier from `plan/7-rpc-codec-fuzzing`. `7-rpc-handler-fault-isolation`
makes malformed input safe to *receive*; this ticket proves the codec is lossless, that the byte
caps bite before a full parse, and that the token buckets bound what they claim to bound. Nothing
here changes `src/` — if a property fails, that is a finding to file, not to fix inline (unless it
is a one-line fix at a site this ticket already names).

`fast-check` 4.5.3 is already a devDependency and is used this way in
`test/nexthop-cost.spec.ts`, `test/peer-discovery.spec.ts`, `test/cohort.properties.spec.ts` and
`test/digitree.invariants.spec.ts` — follow those: assert on the *generated distribution* so the
interesting region is provably reached, rather than trusting the generator to have visited it.

### Round-trip

`encodeJson` / `decodeJson` are the whole codec (JSON over UTF-8, no framing yet). The property is
that they compose to the identity on every value the wire formats in `docs/fret.md` admit.

- Build one arbitrary per wire type — `NeighborSnapshotV1`, `RouteAndMaybeActV1`, `NearAnchorV1`,
  `LeaveNoticeV1`, `SerializedTable` — from the field types the document states, including the
  optional fields (`sample`, `size_estimate`, `confidence`, `metadata`, `wants`, `digest`,
  `activity`, `breadcrumbs`, `replacements`, `membership`, `avgLatencyMs`'s `null`).
- Property: `decodeJson(await encodeJson(x))` deep-equals `x`.
- Deliberately include the values JSON quietly mangles, since finding them is the point:
  `avgLatencyMs: null` must survive as `null` and not become `0` or vanish; a `metadata` value of
  `undefined` is dropped by `JSON.stringify` and the arbitrary should either exclude it or the
  property should state that dropping is the contract; non-ASCII and lone-surrogate strings in
  peer-id and metadata positions; `-0`; integers beyond `Number.MAX_SAFE_INTEGER` in
  `timestamp` / `size_estimate`.
- Coordinate codecs are the other half of the round trip and have their own known-sharp edges
  (`docs/fret.md`, *Digitree implementation*): over arbitrary 32-byte coordinates,
  `base64urlToCoord(coordToBase64url(c))` and `hexToCoord(coordToHex(c))` both return `c`; and
  over arbitrary *strings*, both reject anything that does not decode to exactly `COORD_BYTES`
  rather than returning a plausible near-zero coordinate.
- `readAllBounded` reassembly: a message split at arbitrary chunk boundaries must come back
  byte-identical. Drive it from a plain async iterable — it accepts one — so no transport is
  involved. This is the property that would catch a framing regression when
  `plan/15-rpc-shared-helper` adds length prefixes.

Check `test/digitree.persistence.spec.ts` before writing the `SerializedTable` arbitrary: if it
already pins export/import equivalence for concrete tables, add only the generated-input property
on top rather than restating it.

### Oversized payloads are refused before a full parse

"Before a full parse" has to be measured, not asserted by absence of a crash. `readAllBounded`
throws `payload too large` as soon as the *cumulative* length crosses `maxBytes`, so the
observable claim is about how much of the source it consumed:

- Unit-level: hand `readAllBounded` an async iterable that counts the chunks pulled from it,
  yielding (say) 64 KB chunks totalling 4 MB against a 256 KB cap. Assert it throws, and that it
  pulled no more than `ceil(maxBytes / chunkSize) + 1` chunks — i.e. it stopped at the cap rather
  than draining the source. Assert the same for a source whose chunks are much larger than the cap
  (one 4 MB chunk trips it on the first pull).
- Handler-level, over a real connection: a maybeAct body larger than the profile cap
  (`maxBytesMaybeAct` — Core 512 KB, Edge 256 KB) must not reach the service's activity path, and
  the receiver must end with no additional open inbound stream (that release is
  `rpc-handler-fault-isolation`'s wrapper doing its job; this is the test that exercises it under
  the byte cap rather than under a decode error). Assert the same for `maxBytesNeighbors`
  (Core 128 KB / Edge 64 KB) on the announce path and the fixed 4096-byte cap on leave.
- Note in the spec, without testing it, that the wire cap (512 KB) and the service's activity cap
  (128 KB, checked in `handleMaybeAct` after the whole body is buffered) disagree by 4×. That gap
  is an open arm of `plan/15-rpc-shared-helper` ("tighten each RPC's max-bytes to the real
  ceiling"); pin today's numbers and cross-reference, do not change them here.

### Token buckets

Five inbound buckets, all constructed in `FretService`'s constructor and profile-tuned
(capacity / refill-per-second): `bucketNeighbors` 20/10 Core, 8/4 Edge; `bucketMaybeAct` 32/16,
8/4; `bucketPing` 30/15, 10/5; `bucketLeave` 20/10, 8/4; `bucketAnnounceInbound` 20/10, 6/2.

- Draining a bucket produces the documented rejection, and the rejection is *observable in the
  way that protocol makes it observable* — which differs, and the differences are the contract
  worth pinning:
  - maybeAct, neighbors, ping answer `{ v: 1, busy: true, retry_after_ms }` with
    `retry_after_ms > 0`.
  - leave returns early inside `handleLeave` while the RPC handler still sends `{ok: true}`, so a
    rate-limited leave is indistinguishable from an accepted one on the wire and is visible only
    as `diag.rejected.rateLimited`. Assert that asymmetry explicitly, with a comment that it is
    today's contract rather than an endorsement.
  - inbound announce drops the message and increments the same counter.
- `diag.rejected.rateLimited` increments exactly once per rejection, on every one of the five
  paths.
- The buckets are independent: draining `bucketMaybeAct` must leave ping, neighbors, leave and
  announce answering normally.
- Refill: after the documented refill interval a drained bucket admits requests again. Use the
  bucket's own `retryAfterMs()` to decide how long to wait rather than a hard-coded sleep, and
  keep the wait well under the 10-minute runner idle timeout.
- Profile: the Edge capacities above are smaller than Core's, so the same burst that a Core node
  absorbs must be rejected by an Edge one. `test/profile.behavior.spec.ts` is the existing home
  for profile assertions — check whether the bucket sizes are already pinned there and reference
  rather than duplicate.

**Per-peer buckets are out of scope and stay out.** `docs/fret.md` lists per-peer rate limiting
under *Not yet implemented*, and `tickets/backlog/impl/4-per-peer-rate-limiting` already owns it.
Only the global buckets exist, so only those get tested; say so in the spec so the next reader does
not read the gap as missing coverage.

### Edge cases & interactions

- **A drained bucket must not swallow the reply.** Every rate-limited path still has to answer or
  close; assert no inbound stream is left open by a burst that empties a bucket, same invariant as
  the malformed matrix.
- **A rejected message is never cached.** A `busy` response is not a terminal answer, so a retry
  after refill must get real work done rather than a cached `busy`. This is the phase-collision
  rule from `docs/fret.md` applied to the rate-limit path.
- **The bucket is taken before validation, and validation before routing.** A malformed message
  that arrives while the bucket is empty must be answered `busy`, not rejected as malformed —
  the ordering `rpc-handler-fault-isolation` establishes. One test, both tickets' contract.
- **Determinism.** These specs must not depend on a live stabilization loop: construct the
  `FretService` without `start()` where the test only needs handlers, or stub `stabilizeOnce`, as
  `test/rpc.stream-errors.spec.ts` does. A background tick spending bucket tokens makes every
  count here flaky.
- **Timers.** Bucket refill tests use real time; keep them short and make sure nothing is left
  armed at the end, or the `mocha-exit-watchdog` fails the run.
- **Generated-distribution assertions.** Each `fast-check` property asserts on its own generated
  sample — e.g. that the oversized region and the under-cap region were both produced, and that
  optional fields were both present and absent across runs — so a future generator change cannot
  silently narrow coverage.
