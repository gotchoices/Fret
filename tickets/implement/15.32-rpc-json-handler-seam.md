## Design

### `registerJsonHandler` — the decode/validate/reply layer

Two overloads over `registerRpcHandler`, because two of the five protocols read no request body
(ping, and the neighbors *request*), and forcing a body-less protocol through a decode step would
be worse than the repetition it removes.

```ts
// Request-reading protocols: announce, leave, maybeAct.
export function registerJsonHandler<Req, Res>(
	node: Libp2p,
	protocol: string,
	opts: {
		maxBytes: number;
		parse: Parser<Req>;
		/** Return `undefined` to drop without replying (the identity-mismatch case). */
		serve: (msg: Req, connection: Connection) => Promise<Res | undefined> | Res | undefined;
		/** Counter hook for a body-level drop; the service wires it to `diag.rejected.malformed`. */
		onMalformed?: (reason: 'decode' | 'parse') => void;
		closeBudgetMs?: number;   // test-only pass-through to registerRpcHandler
	}
): Promise<void>;

// Reply-only protocols: ping, neighbors request.
export function registerJsonHandler<Res>(
	node: Libp2p,
	protocol: string,
	opts: {
		serve: (connection: Connection) => Promise<Res> | Res;
		closeBudgetMs?: number;
	}
): Promise<void>;
```

Body: `readFramed`, then `decodeJson`, then `parse`, then `serve`, then
`sendFramed(await encodeJson(res))` when `serve` returned a value.

### The drop/abort rule (state it once, at the function)

- **Frame-level failure aborts.** A truncation, a `PayloadTooLargeError`, a reset — the stream is
  already broken or the remote is misbehaving at the framing layer. These propagate out of
  `registerJsonHandler` and `registerRpcHandler`'s error arm aborts, exactly as today.
- **Body-level failure closes.** Undecodable JSON, a non-object top level, a parser rejection, an
  identity mismatch. The peer framed correctly and is alive; the message is worthless. The handler
  returns normally without replying, so the seam's budgeted `close()` runs. `onMalformed` is called
  first so the drop is counted.

This is the plan's *"a validator failure must be a drop, never an abort"*, and it subsumes the
existing identity-mismatch behavior (which already returns without replying) rather than adding a
second path beside it.

### Ordering that must not move

- The rate-limit bucket stays **first**, before any per-message work, on every gated protocol
  (maybeAct, announce, leave). `registerJsonHandler` runs the parse *inside* the handler body, so a
  bucket taken at the top of `serve` would be too late for maybeAct. **maybeAct therefore stays on
  `registerRpcHandler`** and keeps its parser call inside `handleMaybeAct` — which is what it
  already does. Fewer moving parts than a `preParse` hook, and it keeps the bucket-then-parse-then-guards
  order visibly in one function. State this in a `NOTE:` at the maybeAct registration so the
  asymmetry reads as deliberate.
  - **`handleLeave` takes `bucketLeave` before any validation today** and must keep doing so. A
    guard that runs before the bucket is an unmetered pre-filter: a flood of malformed messages
    would cost the receiver per-message work while never spending a token. Since `registerJsonHandler`
    parses before `serve` runs, check where `bucketLeave` sits relative to the new parse and keep
    the bucket first — moving it into the seam, or accepting that the leave parse is now pre-bucket,
    is a decision to make deliberately and record, not to make by accident.
- **Diagnostics counters shift meaning when a handler moves onto a parser.** Today a leave notice
  with an out-of-bounds timestamp increments `diag.rejected.timestampBounds`; routed through
  `parseLeaveNotice` the same message is a structural reject and counts as `malformed`. Decide
  deliberately which counter each rejection lands in and say so in the handoff — an operator
  reading these counters is the only local signal for several of these paths.
- The static zero-computation reject reply (`staticReject()`) is what a maybeAct parser failure
  answers with, and it still increments `diag.rejected.malformed`. Do not compute real anchors on a
  rejection.
- `validateTimestamp`'s ±30 s window equals `DEDUP_TTL_MS` on purpose. The parsers check that
  `timestamp` is a finite **number**; they do **not** check freshness. Freshness stays where it is
  in `fret-service.ts` (grep `validateTimestamp`).
- Identity mismatch stays a **close-drop** and still increments `diag.rejected.identityMismatch`.
  It runs inside `serve` (which owns `connection`), after the parser has vouched that `from` is a
  parseable peer id — so a `from` that is a valid peer id but not the authenticated sender is still
  dropped by the identity check, not by the parser.
- Ping and the neighbors request take the reply-only overload and read no body: they must not gain
  a `readFramed` call, and their existing `onInbound` membership promotion must still fire.
- The announce handler's snapshot parser comes from the caller. Until `15.33` builds it from
  `mergeSnapshotCaps()`, wire it from the same source the service already uses for its announce
  merge slice — do **not** inline a second copy of the Core 16/16/8 / Edge 8/8/6 numbers. (Find it
  with `grep -n "predecessors" src/service/fret-service.ts` around the announce/fetch merge loops.)

### Diagnostics

Body-level drops increment `diag.rejected.malformed`, which today only maybeAct writes. Do **not**
add new counters — `tickets/backlog/debt-rejection-diagnostics-conflated` already tracks the
conflation of distinct rejection reasons into shared counters, and this work adds two more writers
to an existing one rather than a new axis. (Appending the new writers to that ticket is
`15.325`'s job, so it lands with the docs edits.)

### Other edge cases

- **Release-exactly-once must hold unchanged** for every new drop path. A parser rejection returns
  normally, so one budgeted close and no abort. A truncated frame, so one abort and no close.
- A `serve` returning `undefined` writes nothing; the seam's close is what makes the drop a close.
  Verify a handler body still never calls `close()` itself — a bare close pre-empts the seam's
  budget (see the `registerRpcHandler` doc comment).
- A `sample` entry whose `coord` decodes to the wrong byte length must be dropped by the parser, not
  reach `upsert` — the store's write seam throws on a non-32-byte coordinate, and a throw inside the
  merge loop is exactly the leak the seam was built to stop. `makeSnapshotParser` already does this.
