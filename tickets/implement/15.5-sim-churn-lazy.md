### What is wrong today

`scheduleChurn` (`fret-sim.ts:286–296`) materialises every leave at setup: it draws each leaver
from the initial population once, up front. Late joiners can never churn; a peer drawn twice
produces a second no-op leave; and no join is ever paired with a leave even though the config
field `churnRatePerSec` (`fret-sim.ts:58`) is documented "peers leaving/joining per second". At
`churnRatePerSec: 5` over 10 s the N=100 scenario silently loses half its population, so any
threshold under churn measures population collapse, not behavior under churn.

Current body — replace it wholesale:

```ts
private scheduleChurn(): void {
	const intervalMs = Math.floor(1000 / this.config.churnRatePerSec)
	for (let t = intervalMs; t < this.config.durationMs; t += intervalMs) {
		const alive = Array.from(this.peers.values()).filter((p) => p.alive)
		if (alive.length === 0) continue
		const leaving = this.rng.pick(alive)
		if (leaving) {
			this.scheduler.schedule({ type: 'leave', peerId: leaving.id }, t)
		}
	}
}
```

### Design

- **`event-scheduler.ts:3`** — add `'churn'` to the `SimEvent['type']` union (one word). The
  scheduler re-sorts its array per insert with `Array.prototype.sort`, which is stable, so
  same-timestamp events keep insertion order — up-front lazy churn events stay deterministic
  relative to stabilize events at the same timestamp. No other scheduler change.
- **`scheduleChurn`** — keep the cadence (`for t = intervalMs; t < durationMs; t += intervalMs`,
  relative `schedule`), but emit bare `{ type: 'churn' }` events and pick nobody.
- **`handleEvent`** (`fret-sim.ts:335–352`, a switch) — add `case 'churn': this.handleChurn(); break`.
- **`handleChurn()`** (new) — runs at fire time: pick one peer from the *currently* alive
  population (`this.rng.pick(aliveArray)` — `DeterministicRNG.pick` exists, returns `undefined`
  on empty), leave it via the existing `handleLeave(id)` (`fret-sim.ts:446`), then add one fresh
  peer via the existing `handleJoin()` (`fret-sim.ts:481` — it already composes
  `nextPeerIndex++` + `addPeer` + `handleConnect`). Late joiners now eligible, duplicate picks
  impossible, population stationary.
- **Document the pairing** on the `churnRatePerSec` field doc comment: each churn event removes
  one live peer *and* adds one fresh joiner — a deliberate semantic decision matching the field's
  documented meaning, not a drive-by; leave-only churn made every threshold at
  `churnRatePerSec: 5` a measurement of population collapse.
- **Relax `totalJoins` equality assertions.** `metrics.totalJoins` now exceeds `config.n`
  whenever churn is on. Confirmed sites in `simulation.spec.ts`: line 51 (N=25 @ 0.25/s) and
  line 67 (N=100 @ 5/s), both `if (metrics.totalJoins !== n) throw` style — relax to
  `totalJoins < n` throw (or exact expected count). Lines 19 and 35 (N=5, N=10) run
  `churnRatePerSec: 0` and stay exact — leave untouched. Two more suspected sites, **the only
  files not yet read**: `message-bus.spec.ts:166` (0.5/s) and `churn-scenarios.spec.ts:209`
  (1/s) — read those two files, verify, relax the same way.
- **RNG draws move from setup time to fire time**, so every seeded run's numbers shift.
  Determinism preserved (same seed → same stream). Any threshold assertions in the churn suites
  (`churn-scenarios.spec.ts` especially) may need re-calibration — set new values from measured
  runs, minus a margin, with the measured number in a comment beside each.
- **Add a churn replay/determinism case** (suggest `churn-scenarios.spec.ts`): two runs at one
  seed with churn > 0 must produce byte-identical metrics (`JSON.stringify` compare of
  `sim.run()` results). Lazy scheduling is precisely what could introduce order-dependence; this
  pins it.
