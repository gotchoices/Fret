Second of three tickets split out of the former `implement/23.05-ring-walk-migrate-call-sites`,
stopped by a budget warning before any code was written. Order: `23.06-ring-walk-capacity-protection`
→ this → `23.08-ring-walk-remaining-sites`.

Read `ringNeighborsBothSides` (`packages/fret/src/service/ring-walk.ts`) and its doc comment first —
it states the contract this ticket assumes. Note in particular that it has **no `limit` parameter**
by design: a caller that wants a budget slices its own result, and must decide explicitly whether it
is bounding *who we contact* or *what our window is*.

## Root cause — one site, two symptoms

`sendLeaveToNeighbors` (`packages/fret/src/service/fret-service.ts`, walk at ~1612-1616) builds one
list and uses it for two different jobs:

```
const ids = Array.from(new Set([
    ...this.store.neighborsRight(selfCoord, this.cfg.m),
    ...this.store.neighborsLeft(selfCoord, this.cfg.m)
])).filter((id) => id !== selfStr).slice(0, 8);
const spSet = new Set(ids);
```

Because the walk is side-major (all successors, then all predecessors) and `.slice(0, 8)` is applied
to the concatenation, at the shipped `k: 15` (so `m: 8`) the list is *successors only* — the
predecessor side is cut off entirely except where the two walks overlap. Two consequences:

- **Leave notices never reach the predecessor side.** The literal `8` was never the real bound
  anyway: the fan-out is already clock-bounded by `SHUTDOWN_BUDGET_MS` (3 s) overall and
  `LEAVE_NOTICE_TIMEOUT_MS` (1.5 s) per notice, with `if (budget.signal.aborted) break` in the loop.
- **`spSet` is wrong.** It defines what "outside our own S/P window" means, and it is derived from
  the sliced list — so six genuine predecessors pass `computeReplacements`' "outside our window"
  filter and are advertised to the departing peer's neighbors as *replacements* for itself. Latent
  rather than observed (the clockwise pool filled all six replacement slots first in the measured
  run), but a single **connected** predecessor sorts to the front of that ordering and ships.

Conflating "who we notified" with "what our window is" is the root cause. One array with two readers
is what stops them diverging again.

## Third reader of `spSet`

The same method's bounded fan-out beyond S/P filters `expanded.filter((id) => !spSet.has(id) && ...)`.
Widening `spSet` correctly **shrinks** that extra fan-out — those peers now receive a notice as S/P
members instead. Intended, and worth an assertion so a later reader does not mistake it for a
regression.

## Verified call sites

- `fret-service.ts` `sendLeaveToNeighbors` ~1600 — walk ~1612-1616, `.slice(0, 8)`,
  `spSet = new Set(ids)` ~1617, send loop, then the `fanOut` arm (`Core 4 / Edge 2`) filtering on
  `!spSet.has(id) && this.isConnected(id)`.
- `fret-service.ts` `computeReplacements` ~1584 — its own walk at ~1586-1589 asks each side for
  `m * 2` under `isLiveMember`, excludes `selfStr` and `spNeighborIds`, fully re-sorts
  (connected-first, then relevance) and `.slice(0, 6)`. The re-sort and the 6-cap stay; only the
  walk is migrated.

## Edge cases this ticket owns

- **`exclude` blanketing one side.** `computeReplacements` excludes up to 2m ids via
  `spNeighborIds`. The helper's `+ exclude.size` over-fetch is what stops that side starving —
  assert it at *this* call site, not only in the helper's own spec.
- **Ring of exactly one peer (self).** The helper returns empty and the send loop is a no-op; verify
  rather than assume.
- The leave *targets* stay **unfiltered** by membership (that walk defines the S/P set the
  replacement list excludes, and is not a list we advertise), while `computeReplacements` stays
  `isLiveMember`-scoped. Do not accidentally unify the two predicates while sharing the helper.
