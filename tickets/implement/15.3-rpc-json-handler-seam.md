First of two tickets split out of `plan/15.3-rpc-message-validators` (itself the third of the
`15-rpc-shared-helper` split). This one is the **shape** half: one JSON handler seam, one validator
module, all five inbound handlers and all four outbound reply decoders moved onto them. The
**byte-cap** half — deriving each protocol's real ceiling and making the maybeAct wire cap and the
service's activity cap one number — is `15.4-rpc-byte-cap-tightening`, which depends on this.

## Already landed — do not re-implement

- `registerRpcHandler(node, protocol, serve, opts)` (`src/rpc/protocols.ts`) is the transport /
  lifecycle seam every inbound handler already goes through. It owns the budgeted success close and
  the synchronous error `abort()`, and it branches on the **write-end** status (not `status`) to
  decide whether the handler already released the stream. **Stack on top of it; do not replace or
  re-derive it.** Pinned by `test/rpc.handler-fuzz.spec.ts`.
- `rpcRequest` (`src/rpc/request.ts`) is the single owner of the outbound open/write/read/release
  sequence. Its `decode` callback is exactly where a reply validator belongs: a throw from `decode`
  is already classified `decode-error` (proof of life, never a contact strike) by `decodeFailure`.
  A busy reply is tested *before* `decode` runs, so a reply validator never sees one.
- `validateRouteAndMaybeAct` (`src/rpc/maybe-act.ts`) is the style to copy — field types, finite
  numbers, a base64url-decodable `key`, caps on `key` (1024) / `correlation_id` (256) /
  `breadcrumbs` (64). Its **position** is load-bearing: after the rate-limit bucket, before every
  other guard (`docs/fret.md`, *Cheap-guard rejections*). Preserve both.
- `sanitizeReplacements` (`src/rpc/leave.ts`) — caps at 12, drops non-strings, drops ids that do not
  parse as peer ids. The other model to copy.
- `mergeSnapshotCaps()` (`src/service/fret-service.ts`) is already the single source of truth for
  the per-message merge caps (Core 16/16/8, Edge 8/8/6), shared by `fetchAndMergeSnapshot` and
  `mergeAnnounceSnapshot`. Reuse it; do not introduce a second copy of those numbers.

## Design

### Validators are parsers, not type guards

Every validator has the shape:

```ts
type Parser<T> = (msg: unknown) => T | undefined;   // undefined = reject this message
```

**Not** `msg is T`. Two of the five messages must *normalize* as they check — truncate an over-long
id list, drop a malformed sample entry, drop an advisory field of the wrong type — and a type guard
cannot express that without mutating its argument. Returning the normalized message makes the
narrowing and the normalization one step, so no caller can consume an unnormalized value.

They live in one new module, `src/rpc/validate.ts`, with the shared primitives (`isPeerIdString`,
`boundedStringArray`, `finiteNumberOr`). `validateRouteAndMaybeAct` **moves** there from
`maybe-act.ts` and `sanitizeReplacements` **moves** there from `leave.ts` — one module so a reader
finds every wire-shape rule in one place, and so the maybeAct-only `NOTE:` in that function
(“`plan/15-rpc-shared-helper` generalizes this”) can be deleted rather than restated.

All are pure and O(message size): no hashing, no ring walks, no libp2p dialing. `isPeerIdString`
calls `peerIdFromString` in a `try`, which is parse-only and already what `sanitizeReplacements`
does.

### `registerJsonHandler` — the decode/validate/reply layer

Two overloads over `registerRpcHandler`, because two of the five protocols read no request body
(ping, and the neighbors *request*), and forcing a body-less protocol through a decode step would
be worse than the repetition it removes.

```ts
// Request-reading protocols: announce, leave, maybeAct.
export function registerJsonHandler<Req, Res>(
	node: Libp2p,
	protocol: string,
	opts: {
		maxBytes: number;
		parse: Parser<Req>;
		/** Return `undefined` to drop without replying (the identity-mismatch case). */
		serve: (msg: Req, connection: Connection) => Promise<Res | undefined> | Res | undefined;
		/** Counter hook for a body-level drop; the service wires it to `diag.rejected.malformed`. */
		onMalformed?: (reason: 'decode' | 'parse') => void;
		closeBudgetMs?: number;   // test-only pass-through to registerRpcHandler
	}
): Promise<void>;

// Reply-only protocols: ping, neighbors request.
export function registerJsonHandler<Res>(
	node: Libp2p,
	protocol: string,
	opts: {
		serve: (connection: Connection) => Promise<Res> | Res;
		closeBudgetMs?: number;
	}
): Promise<void>;
```

Body: `readFramed` → `decodeJson` → `parse` → `serve` → `sendFramed(await encodeJson(res))` when
`serve` returned a value.

### The drop/abort rule (state it once, here)

- **Frame-level failure aborts.** A truncation, a `PayloadTooLargeError`, a reset — the stream is
  already broken or the remote is misbehaving at the framing layer. These propagate out of
  `registerJsonHandler` and `registerRpcHandler`'s error arm aborts, exactly as today.
- **Body-level failure closes.** Undecodable JSON, a non-object top level, a parser rejection, an
  identity mismatch. The peer framed correctly and is alive; the message is worthless. The handler
  returns normally without replying, so the seam's budgeted `close()` runs. `onMalformed` is called
  first so the drop is counted.

This is the rule the ticket's *“a validator failure must be a drop, never an abort”* asks for, and
it subsumes the existing identity-mismatch behavior (which already returns without replying)
rather than adding a second path beside it.

### Per-message parsers, and the reject rule for every field

`v` is deliberately **not** checked on any message. Nothing negotiates versions today, and a hard
reject on an unexpected `v` would make a future v2 rollout fail closed at exactly the peers that
have not upgraded. Stated, not overlooked.

**`NeighborSnapshotV1`** — `makeSnapshotParser(caps)`, a factory the service builds from
`mergeSnapshotCaps()` so the truncation caps and the merge caps cannot drift:

| field | rule | on violation |
|---|---|---|
| `from` | string **and** parses as a peer id | reject message |
| `timestamp` | finite number | reject message |
| `successors`, `predecessors` | absent → `[]`; array → **truncate to `caps.successors` / `caps.predecessors` first**, then drop non-string entries | truncate / drop entry |
| `sample` | absent → `[]`; array → truncate to `caps.sample`, then **skip-and-log per entry**: `id` string, `coord` decodes via `base64urlToCoord` to exactly 32 bytes, `relevance` finite | drop entry |
| `size_estimate`, `confidence` | optional finite numbers | drop the field (advisory; already gated by "both positive" downstream) |
| `metadata` | non-null non-array object | drop the field (matches today's receiver check) |
| `sig` | unchecked (unused; message signing is unimplemented) | — |

Truncate rather than reject for the id lists: the merge loops already `slice` to these exact caps,
so truncating at the parser changes **no** behavior — it only moves the cost before the parse+hash
loop instead of after. Rejecting the whole message would be a new behavior that punishes an honest
peer running a larger profile. The per-entry skip-and-log on `sample` is today's rule and is kept
deliberately (`importTable`'s all-or-nothing rule is the *other* case and is not touched).

Once the parser truncates, the `slice(0, caps.*)` calls in `mergeAnnounceSnapshot` and
`fetchAndMergeSnapshot` are dead. **Remove them** and state in a `NOTE:` at `mergeSnapshotCaps`
that the parser is now the single enforcement point — leaving both is how two copies of a cap drift.
This is only safe because *both* merge paths are parser-covered after this ticket: the announce path
by the inbound handler's parser, the fetch path by `fetchNeighbors`' reply parser below.

**`LeaveNoticeV1`** — `from` string and parseable peer id, `timestamp` finite; either wrong →
reject message. `replacements` → the moved `sanitizeReplacements`.

**`RouteAndMaybeActV1`** — the existing checks, unchanged, plus one gap the plan named: `digest` is
type-checked but uncapped. Add `MAX_DIGEST_CHARS = 4096`, alongside the existing key/correlation-id
caps. The handler still decodes `key` exactly once after the parser passes and hands the bytes to
`routeAct` / `nearAnchorOnly`.

**Reply shapes get parsers too.** The plan left this open; resolve it as **yes**. The machinery is
already there (`rpcRequest`'s `decode`), a rejection lands as `decode-error` — proof of life, never
a contact strike — and the cost is one pass over a small message. Without it a sender still reads
`r.ok`, `.anchors`, `.commitCertificate` off an unchecked cast.

- `PingResponseV1`: `ok` must be a **boolean** (replacing today's `Boolean(r.ok)` coercion — a legal
  value always encodes as a boolean, so the coercion only ever hid a malformed peer);
  `size_estimate` / `confidence` optional finite, dropped individually if not.
- `NearAnchorV1`: `anchors` and `cohort_hint` arrays of strings, capped at **8** and **16** — twice
  the largest lists the producers emit (`pickAnchors` yields ≤ 2, `cohort_hint` ≤ 8), so the cap
  cannot refuse our own legal output; `estimated_cluster_size` and `confidence` finite. Missing
  arrays normalize to `[]`, since an emptied anchor list already falls back to the local cohort.
- The maybeAct reply is `NearAnchorV1 | { commitCertificate: string }`: discriminate on
  `commitCertificate` being a string first, else parse as a NearAnchor.
- `fetchNeighbors` uses the **same snapshot parser** as the announce handler, built from the same
  `mergeSnapshotCaps()`. Its signature must therefore take the parser (or the caps) rather than
  hard-coding one — the service is the only place that knows the profile.

### Ordering that must not move

- The rate-limit bucket stays **first**, before any per-message work, on every gated protocol
  (maybeAct, announce). A malformed flood is metered like any other. `registerJsonHandler` runs the
  parse *inside* the handler body, so a bucket taken at the top of `serve` would be too late for
  maybeAct — instead keep maybeAct's bucket where it is (inside `handleMaybeAct`) and have the
  parser run there too, i.e. **maybeAct's parse stays in the service handler, not in the seam.**
  Pass `parse: (m) => m as RouteAndMaybeActV1` is *not* acceptable; instead give the seam an
  optional `preParse` hook the service uses to take the bucket before the parser runs, or register
  maybeAct through `registerRpcHandler` directly and call the parser in `handleMaybeAct`. **Choose
  the second**: it is fewer moving parts, it keeps the bucket→parse→guards order visibly in one
  function, and maybeAct is the only protocol whose bucket must precede its parse. State this in a
  `NOTE:` at the maybeAct registration so the asymmetry reads as deliberate.
- The static zero-computation reject reply (`NearAnchor` with empty `anchors` / `cohort_hint` and
  `estimated_cluster_size` / `confidence` of 0) is what a maybeAct parser failure answers with, and
  it still increments `diag.rejected.malformed`. Do not compute real anchors on a rejection.
- `validateTimestamp`'s ±30 s window equals `DEDUP_TTL_MS` on purpose. The parser checks that
  `timestamp` is a finite **number**; it does **not** check freshness. Freshness stays where it is.
- Identity mismatch stays a **close-drop** and still increments `diag.rejected.identityMismatch`.
  It runs inside `serve` (which owns `connection`), after the parser has vouched that `from` is a
  string — so a `from` that is a valid peer id but not the authenticated sender is still dropped by
  the identity check, not by the parser.

### Diagnostics

Body-level drops increment `diag.rejected.malformed`, which today only maybeAct writes. Do **not**
add new counters — `tickets/backlog/debt-rejection-diagnostics-conflated` already tracks the
conflation of distinct rejection reasons into shared counters, and this ticket adds two more
writers to an existing one rather than a new axis. Note the new writers in that ticket's body.

## Edge cases & interactions

- **Round-trip property must hold**: every value `encodeJson` can produce from a legal message must
  survive its own parser. In particular `undefined` is dropped on encode, so an optional field can
  only ever arrive *absent* — a parser that rejects a missing optional, or that requires `null`
  where `undefined` was meant, breaks a valid round trip. Also: a legal `-0` arrives as `0` and a
  legal non-finite arrives as `null`; no field admits either, but a `Number.isFinite` check on a
  `null` must reject rather than throw.
- An array at exactly the cap (kept whole), one over (truncated to the cap, message still accepted),
  and one entry that fails to parse inside an otherwise valid array (that entry dropped, message
  still accepted). All three for `successors`, `predecessors` and `sample`.
- A `from` that is a valid peer id but not the transport-authenticated sender: dropped by the
  identity check, `diag.rejected.identityMismatch` still increments — **not** by the parser.
- A `sample` entry whose `coord` decodes to the wrong byte length must be dropped by the parser, not
  reach `upsert` — the store's write seam already throws on a non-32-byte coordinate, and a throw
  inside the merge loop is exactly the leak the seam was built to stop.
- **Release-exactly-once must hold unchanged** for every new drop path. A parser rejection returns
  normally → one budgeted close, no abort. A truncated frame → one abort, no close.
- A `serve` returning `undefined` writes nothing; the seam's close is what makes the drop a close.
  Verify a handler body still never calls `close()` itself — a bare close pre-empts the seam's
  budget (see the `registerRpcHandler` doc comment).
- Ping and the neighbors request take the reply-only overload and read no body: they must not gain
  a `readFramed` call, and their existing `onInbound` membership promotion must still fire.
- `fetchNeighbors`' parser now rejects snapshots the old cast accepted. That is a `decode-error`,
  which the service treats as proof of life — confirm no call site books a contact strike on it.
- A `null` inside a `successors` array is a string check failure (drop entry), not a throw.

## Key tests to expect

Extend `test/rpc.handler-fuzz.spec.ts`:

- For **every** wire message and every field: wrong type, missing, and over cap → the message is
  dropped without throwing out of the handler, without leaking the stream, and the existing
  release-exactly-once invariants hold (close on a body-level drop, abort on a frame-level failure —
  assert the *arm*, not merely the count).
- A snapshot carrying more ids than the profile cap: assert the parse+hash+upsert loop runs exactly
  `caps.*` times, **by counting the loop's work** (a spy on the store's `upsert` / the hash) rather
  than by inferring it from the absence of a crash.
- `from` that is not a parseable peer id → dropped, `diag.rejected.malformed` incremented,
  `identityMismatch` **not** incremented.
- `from` that is a parseable peer id but not the authenticated sender → dropped,
  `identityMismatch` incremented, `malformed` **not** incremented.
- A `sample` entry with a short `coord` → that entry dropped, the rest of the snapshot merged.

Extend `test/rpc.codec-properties.spec.ts`:

- The round-trip property: for generated legal instances of all five wire types plus both reply
  types, `parse(await decodeJson(await encodeJson(v)))` is never `undefined`. This is the property
  that a validator never rejects what the encoder produced from a legal value, and it is what
  catches an over-strict parser before it ships.
- A generated *illegal* instance (fuzzed field types) never throws out of a parser — it returns
  `undefined` or a normalized value.
