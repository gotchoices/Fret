## The invariant to restore

**A frame the remote actually wrote is never reported to the caller as truncated.**

`readFramed` (`packages/fret/src/rpc/protocols.ts`) can raise `FrameTruncationError` on a healthy
connection carrying a complete reply. Fix it at the seam. Do not fix it by constraining handler
bodies.

## Root cause — a layering blind spot, confirmed against the libp2p source

`remoteFinishedWriting` (~line 379) asks the **stream** whether more bytes can arrive:

```ts
readBufferLength === 0 && (remoteWriteStatus === 'closed' || readStatus === 'closed')
```

`readFramed` then treats a `true` as proof that the **decoder** can no longer complete a frame.
Those are different questions, and there are *two* buffers between them. From
`node_modules/@libp2p/utils/dist/src/abstract-message-stream.js:81` — `[Symbol.asyncIterator]`
subscribes to `message` / `close` / `remoteCloseWrite` at iteration start and pushes each message
into an `it-pushable`:

```
stream.readBuffer --message event--> it-pushable --> lp.decode buffer --> our `pending`
        ^                                 ^                 ^
        |                                 |                 |
 only hop remoteFinishedWriting sees      +--- invisible ---+
```

Every byte that has left `readBuffer` but not yet resolved `pending` sits in a buffer
`remoteFinishedWriting` cannot see. Draining the microtasks — which the poll's macrotask delay was
supposed to guarantee — is exactly what *moves* bytes into that blind spot. So `readFramed`'s
"race-free because the poll fires on a macrotask" paragraph is false, and its own doc block states
the invariant the code violates.

A reply-only handler answers on stream *open*, so its bytes are typically already delivered before
the caller starts reading — which is why the buffered-bytes short-circuit (`readBufferLength > 0`),
not the close-status check, is what makes this path work at all when it works.

## Reproduction (verified in an earlier run, deterministic within a run)

Two `createMemNode`s, five reply-only protocols registered via `registerJsonHandler`, differing
only in how many `await`s the `serve` callback performs before returning; driven by `rpcRequest`,
6 calls per cell, crossed with a with-body / without-body axis. Measured outcomes:

| `serve` shape | no body | with body |
|---|---|---|
| `() => Promise.resolve(reply)` | ok | ok |
| `async () => reply` | ok | ok |
| 1 extra `await` | ok | ok |
| 2 extra `await`s | **decode-error** | ok |
| 4 extra `await`s | ok | **decode-error** |

6/6 identical per cell, repeatable within the run.

### The failing cell MOVES between runs — do not build a depth-indexed test

The ticket originally recorded "2 ticks fails, 1 passes"; a previous fix run measured
"1 fails, 2 and 4 pass"; another run measured "2 fails without a body, 4 fails with one". Same
code, same repro shape. **There is no threshold and no stable hole.** Microtask depth only shifts
*where* the poll tick lands relative to the buffer handoff; it is a phase alignment, not a monotone
quantity. Consequences for the implement work:

- Do not reason about "make the write happen sooner" or "raise the budget".
- **Do not ship a depth-sweep matrix as the regression test** — whichever depths you pick may all
  pass on the CI machine while the defect is untouched. A depth sweep is fine as a smoke test, but
  the load-bearing test must *force* the race deterministically (see below).

## Prior-run findings (source-verified)

The interrupted run read `protocols.ts`, `request.ts`,
`node_modules/@libp2p/utils/dist/src/stream-utils.js` (the whole file), and
`node_modules/@libp2p/utils/dist/src/abstract-message-stream.js` (the whole class). These findings
are from the actual installed source (`@libp2p/utils@7.0.10`), not the docs.

**Why same-layer reading is genuinely race-free** (this settles fix shape (a) as correct):

- `push()` appends to `stream.readBuffer` and defers dispatch — `setTimeout(dispatchReadBuffer, 0)`
  when a `message` listener exists, or until `addEventListener('message', ...)` runs (which queues
  a microtask dispatch) when none does.
- `dispatchReadBuffer()` consumes `stream.readBuffer` and dispatches the `message` event to
  listeners **in one synchronous block**, and in its `finally` sets `readStatus = 'closed'` once
  the buffer is empty and `remoteWriteStatus` is closed. So at any observable instant, bytes are
  either in `stream.readBuffer` (visible via `readBufferLength`) or already delivered to subscribed
  listeners — there is **no invisible intermediate** at the message-event layer. A reader that
  subscribes at entry and keeps its decode buffer at that layer therefore closes the blind spot by
  construction.
- `byteStream()` (stream-utils.js) subscribes at construction and re-checks `isEOF` synchronously
  at each read boundary *before* awaiting, so it never hangs on a lost one-shot close event and
  needs **no poll timer at all** — `EOF_POLL_MS` genuinely retires on this path. Its `isEOF` is
  `remoteWriteStatus !== 'writable' && readBufferLength === 0`, applied at the same layer as its
  own buffer.

**`lpStream` as-is is NOT viable — two contract breaks read straight from its source:**

- Clean EOF before any prefix byte, or mid-varint EOF: `lpStream.read` breaks out of its varint
  loop with `dataLength = -1` and then calls `bytes.read({ bytes: -1 })`, which returns an
  **empty buffer** instead of throwing. Truncation at the prefix would silently read as an empty
  message — breaking the `FrameTruncationError` contract (and an empty frame is a *valid* value
  for `readFramed` today).
- `maxDataLength` auto-derives `maxLengthLength`; an over-cap declared length whose varint is
  longer than that throws `InvalidDataLengthLengthError` **before the declared length is known**,
  so `PayloadTooLargeError` could not always report the declared length. (The ticket's earlier
  claim that `InvalidDataLengthError` fires before the prefix is consumed is wrong — it fires
  after the prefix, before any body byte, and its message does carry the length — but the
  `maxLengthLength` case above still loses it.)

**Correct construction for fix shape (a):** use `byteStream()` (or an in-house equivalent at the
same layer — see the dependency question below) and read the varint prefix byte-by-byte ourselves,
mirroring `lpStream.read`'s loop:

- prefix byte read returns `null` (clean EOF) → `FrameTruncationError`;
- varint decoded → check `declared > maxBytes` → `PayloadTooLargeError` with the declared length,
  before any body byte — same guarantee `onLength` gives today;
- guard the prefix length (uint8-varint `decode` throws `RangeError` on a partial varint —
  `continue`; cap accumulated prefix bytes at ~9 so a garbage stream cannot loop);
- body via `bytes.read({ bytes: declared })` — a truncated body throws `UnexpectedEOFError`, which
  `isFrameTruncationError` already matches by name (both names already occur today, per its doc).

**Hazards found for the implementer:**

- `byteStream.unwrap()` removes its listeners and then pushes unread trailing bytes back via
  `stream.push()`, which **throws `StreamStateError` when `readStatus` is `'closed'`** — likely
  exactly when trailing bytes exist (remote wrote garbage after the frame, then closed). The
  cleanup `finally` must wrap `unwrap()` in a try/catch; the catch is safe because listeners are
  removed before the push.
- Trailing bytes after the frame ARE pulled into `byteStream`'s buffer on this path (message
  events deliver whatever arrives), unlike today's "never pulled" doc line. The pull-count
  measurement in `test/rpc.codec-properties.spec.ts` drives an async-iterable source, which stays
  on the iterable path, so the *measured* guarantee ("an over-cap message costs only the prefix")
  should be unaffected — but the docs wording in `docs/fret.md` ("any bytes after the frame
  ignored (never pulled)") needs a caveat for the real-stream path, and the test needs re-checking
  rather than assuming.
- **Two implementations behind one signature.** The plain async-iterable path keeps an
  iterator-based read (no stream state to consult; `remoteFinishedWriting` already returns false
  there, so today's poll only ever served real streams). That fallback loop can drop the poll and
  race `pending` vs one deadline timer vs abort. The dispatch predicate should mirror what
  `byteStream` itself requires (stream-utils' `isValid`: `addEventListener` / `removeEventListener`
  / `send` / `push` / `log`); note `drainCapable` in `request.ts` documents that plain test stubs
  lack `addEventListener`, so existing stub-driven tests take the iterable path unchanged.
- **Timeout plumbing on the stream path:** `byteStream.read` takes a `signal` (raced via
  `raceSignal`). Finite `timeoutMs` → arm `deadline(timeoutMs, opts.signal)` as a child, map its
  expiry to the existing `read timed out after ${timeoutMs}ms` error and a caller-signal abort to
  `abortReasonError(signal)` (check which of the two fired, caller signal first). `Infinity` mode →
  pass `opts.signal` straight through, keeping the mandatory-signal entry throw. Preserve the
  entry-time `timeoutMs` validation and the already-aborted check verbatim.
- **Dependency question, must be settled first:** `@libp2p/utils` is **not** a direct dependency
  of `p2p-fret` — only transitive (installed at 7.0.10 via libp2p 3.x). Either add
  `"@libp2p/utils": "^7.0.10"` to `dependencies` (it is the same package libp2p itself uses, so no
  new tree), or implement the ~60-line byteStream-equivalent in-house at the message-event layer.
  Adding the dependency is preferred — it reuses maintained code and its `isEOF` is the exact
  same-layer check — but confirm the peer-range story (libp2p is a peerDependency; pin `@libp2p/utils`
  to a caret range compatible with libp2p 3.x's own).

## Fix shapes, in preference order

### (a) Preferred — read frames at the same layer as the EOF check *(settled by the findings above; do this one)*

libp2p ships `lpStream` / `byteStream` (`node_modules/@libp2p/utils/dist/src/stream-utils.js`),
which reads length-prefixed frames straight out of the stream's **own** `readBuffer` and applies
its EOF test at that same layer:

```js
function isEOF (obj) { return obj.remoteWriteStatus !== 'writable' && obj.readBufferLength === 0 }
```

No pushable, no second decoder buffer, no poll — the blind spot does not exist because there is
only one buffer. This *deletes* the layering violation rather than patching around it, and it also
retires `EOF_POLL_MS` and the RTT floor its `NOTE:` documents.

Costs to weigh and report honestly in the review handoff:

- `readFramed` also accepts plain async iterables (tests, non-libp2p sources) — see `ReadEndState`,
  every field optional. That path has no `readBuffer`, so it must keep an iterator-based
  implementation; the fix becomes two implementations behind one signature, chosen on whether the
  argument is a real `Stream`.
- The declared-length cap must still be raised at the prefix, before any body byte is pulled
  (`PayloadTooLargeError`, currently the `onLength` hook). Use the byte-by-byte prefix read
  described in the findings above — `lpStream` as-is breaks the truncation contract.
- `readFramed` and `sendFramed` are pinned public exports (`test/package-exports.spec.ts`). The
  signature must not change.

### (b) Account for bytes the decoder still holds

Keep the iterator pipeline, but stop `remoteFinishedWriting` being the terminal authority: track
bytes delivered into the decode pipeline against bytes accounted for by frames yielded, and refuse
to raise truncation while undelivered bytes could still complete a frame. Exact accounting needs
the declared length (available in `onLength`) plus the varint prefix width; before `onLength` has
fired the count is not exact, so this shape needs care not to trade a false truncation for a hang
on a genuinely truncated stream.

### (c) Last resort — grace tick after a positive poll

On a positive poll, race `pending` against one more short tick before raising. Cheapest, but it
re-introduces a timing argument, which is the class of bug this ticket exists to remove. Take it
only if (a) and (b) are both shown impractical, and say so explicitly in the handoff.

## Tests the fix must land

- **A forced-race seam test.** Deterministically drive the case rather than hoping a depth lands in
  the window: e.g. a stub stream whose `readBufferLength` reads 0 and `remoteWriteStatus` reads
  `'closed'` while a complete frame is still in flight through the pipeline, asserting `readFramed`
  returns the frame instead of throwing. This is the regression guard; site it at the seam. Under
  fix shape (a) the stub must present the message-stream surface (`addEventListener` etc., plus
  `closeRead` so stream-utils' `isEOF` takes its stream branch) and deliver the frame via a
  `message` event after `readFramed` is entered.
- **A two-node smoke matrix** over pre-write microtask depth (0,1,2,4) crossed with
  with-body / without-body, asserting every cell returns `ok`. Skeleton is the repro above. Keep
  it, but treat it as a smoke test — its failing cell is not stable.
- **Restore the close-then-read shape.** `sendRaw` in `test/rpc.handler-fuzz.spec.ts` (~line 651)
  was narrowed to start its read before the half-close, and its comment documents this defect as a
  test-shape constraint. Once the invariant holds, restore the "sender fully closes before reading"
  shape and cover it. Delete the now-false comment.
