Continuation of `7-rpc-abort-deadlines` (Phases 1–2 of that ticket are **landed**; this ticket is
the test half that was cut when the run hit its token budget). Companion ticket
`7.2-rpc-service-signals` carries the service-side work and is independent of this one — the two
touch disjoint files (`test/` here, `src/service/fret-service.ts` + `docs/` there).

### What already exists (do not re-implement)

- `src/utils/deadline.ts` — `deadline(ms, parent?): Deadline` (`{ signal, cancel() }`),
  `DeadlineExpiredError`, and `abortReasonError(signal)`. Built from `AbortController` +
  `setTimeout` + a parent `abort` listener, deliberately **not** `AbortSignal.timeout` /
  `AbortSignal.any` (absent on React Native / Hermes). An already-aborted `parent` yields an
  already-aborted child **synchronously**. `cancel()` is idempotent and clears both the timer and
  the parent listener.
- `RPC_TIMEOUT_MS = 5000` exported from `src/rpc/protocols.ts`.
- `openRpcStream(node, pid, protocols, opts)` — `opts.signal` is forwarded into **both**
  `newStream` and `dialProtocol` (merged into `streamOpts`, which is now typed `NewStreamOptions`
  rather than `as const`), and an already-aborted signal **throws before any dial**.
- `readAllBounded(stream, maxBytes, timeoutMs, opts)` — `opts.signal` races alongside the existing
  deadline/poll race via a resolve-with-sentinel arm (never a rejecting promise, so a losing abort
  cannot become an unhandled rejection), and the listener is detached in a `finally`.
- `releaseRpcStream(stream, signal)` in `protocols.ts` — `stream.abort(err)` (synchronous) when the
  signal aborted, `await stream.close()` otherwise. Every sender's `finally` calls it, then
  `d.cancel()`.
- All five senders take a trailing `opts: { signal?: AbortSignal; timeoutMs?: number } = {}`
  (`announceNeighbors` merges the two fields into its existing `{ dial }` bag):
  `sendPing`, `fetchNeighbors`, `announceNeighbors`, `sendMaybeAct`, `sendLeave`. Each builds
  `deadline(opts.timeoutMs ?? RPC_TIMEOUT_MS, opts.signal)` at entry and cancels it in `finally`.
- `sendPing`'s RTT clock now starts **after** `openRpcStream` resolves (the dial is not round-trip
  time). This removes that item from `8-rpc-shared-helper`'s list.

`cd packages/fret && npx tsc --noEmit` is clean and `yarn test` is **590 passing / 0 failing** with
these changes in the tree, so the existing suites already act as the no-regression gate. What is
missing is any test that exercises the *new* behavior.

### Tests to write

**`test/deadline.spec.ts` (new)** — unit tests for the helper:

- fires after `ms` (signal becomes aborted; reason is a `DeadlineExpiredError`);
- `cancel()` before `ms` leaves the signal un-aborted **and clears the timer** — the suite passing
  the repo's mocha exit watchdog *is* the timer assertion, so no separate handle probe is needed;
- parent abort propagates to the child immediately;
- `cancel()` after a parent abort is safe;
- an already-aborted parent yields an already-aborted child **synchronously** (assert without
  awaiting a tick);
- double `cancel()` is a no-op.

**`test/rpc.protocols.spec.ts` (extend)** — the file already has a stub-node harness
(`makeConnection` / `makeNode`, recording `newStream` and `dialProtocol` calls with their opts
bags). Add:

- `openRpcStream` forwards `signal` into `newStream` (connection path);
- `openRpcStream` forwards `signal` into `dialProtocol` (dial-fallback path);
- an already-aborted signal throws and `dialProtocol` is **never called** (assert the recorded
  dial-call array stays empty).

**New RPC-timeout cases** against the same stub harness — these are the ticket's headline bug, so
**assert elapsed wall time, not merely that the promise rejected**:

- a `dialProtocol` that never resolves → `sendPing(node, peer, protocol, { timeoutMs: 100 })`
  rejects in ≈100 ms (before this work: never);
- a stream that opens but never yields a chunk → same.

Give the timing assertions enough slack for a loaded CI box (an upper bound of a few hundred ms
against a 100 ms budget) — the property under test is "bounded at all", not scheduler precision.

### Notes for whoever picks this up

- The stub streams in `rpc.protocols.spec.ts` are bare objects (`{ id: 'stub-stream' }`) with no
  `close`/`abort`. `releaseRpcStream` swallows the resulting `TypeError` by design, so a
  timeout-path test does not need to stub those methods — but a test that wants to *assert*
  `abort()` was preferred over `close()` on the aborted path does, and that assertion is worth
  having.
- `fetchNeighbors` swallows every failure into a fabricated empty snapshot (a pre-existing
  behavior, tracked as `8-rpc-shared-helper`'s "fetchNeighbors fabricates success" arm). A timeout
  test against it must therefore assert on the fabricated snapshot plus elapsed time, not on a
  rejection. There is a `NOTE:` at the function saying so.
