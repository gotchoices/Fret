### The fetch path itself

Confirmed by reading `fetchAndMergeSnapshot` (`fret-service.ts:2283`):

- It passes `parse: makeSnapshotParser(this.mergeSnapshotCaps())` to `fetchNeighbors`
  (`fret-service.ts:2290`). That is the fetch path's single enforcement point.
- **It never upserts `snap.from`.** Unlike the announce path's `1 + successors + predecessors +
  sample`, the expected fetch-path upsert count is exactly
  `successors + predecessors + sample` — no `+ 1`. Getting this wrong is the most likely way to
  write a test that fails for the wrong reason. `FROM` appearing anywhere in the counted ids is
  itself worth asserting against.
- Merge order is `[...successors, ...predecessors]` in one loop, then `sample` in a second
  (`:2313`–`:2330`) — the same order the announce assertions already use, minus the leading `FROM`.
- It returns `announced: string[]`, the ids it saw for the first time. On an unstarted service with
  an empty store that equals the merged id list, so it is a cheap second assertion.
- **A rejected reply is a silent zero.** The `switch (out.kind)` at `:2292` returns early for
  `decode-error` (which is what a body the parser refuses becomes) having upserted nothing. Assert
  the counted ids deep-equal the expected list, never merely `<= cap`, or a malformed fixture
  passes as a cap doing its job.
- Its tail calls `calibrateSizeFromSnapshot` (`fret-service.ts:1739`), which only calls
  `reportNetworkSize` — no store writes, so it does not disturb the count. `overCapBody()` carries
  no `size_estimate` / `confidence`, so it is a no-op there anyway.
- `fetchAndMergeSnapshot(id, signal)` is private; call it via a cast, with `undefined` for the
  signal. It is `async` and awaits its own merges, so no detach trick is needed — this path is
  fully deterministic and needs none of the announce path's complications.
- The reply body's `from` is **not** identity-checked on the fetch path (that check lives in the
  announce handler's `serve`). The parser only requires it to parse as a peer id, so `overCapBody()`
  is usable as-is and the `id` argument passed to `fetchAndMergeSnapshot` need not equal it.
- `fetchNeighbors`' `opts.parse` **defaults to `Infinity` caps** ("validate the shape, truncate
  nothing"). That default is what a test gets if it calls `fetchNeighbors` itself — which is
  exactly why this test must drive `fetchAndMergeSnapshot`, not the sender.
- `test/announce-rate-limit.spec.ts:154-162` owns the caps-are-one-source-of-truth claim
  (a deep-equal against the literal Core/Edge numbers). Leave it alone; do not restate those
  numbers anywhere else.

### What the stub stream must actually satisfy

`fetchAndMergeSnapshot` → `fetchNeighbors` (`src/rpc/neighbors.ts:99`) → `rpcRequest`
(`src/rpc/request.ts:228`). The fetch call is the *simplest* of the five senders — it writes
nothing and half-closes nothing:

- `fetchNeighbors` passes `dial: 'never'`, `maxBytes: 128 * 1024`, and a `decode` of
  `parseOrThrow(parse, await decodeJson(bytes))`. No `body`, no `halfCloseBeforeRead`.
- `rpcRequest` therefore runs exactly: `openRpcStream` → (no write) → `readFramed(stream,
  131072, Infinity, {signal})` → `decodeJson` → busy-shape test → `decode` → `finally`
  `releaseRpcStream(stream, d.signal)` → `d.cancel()`.
- **`sendFramed` is never called on this path**, so the stub's `send` is never invoked. Keep it
  (`send: () => true`) to satisfy the `Stream` type; no assertion depends on it.
- `releaseRpcStream` reaches its un-aborted arm (the deadline has not fired) and calls
  `stream.close({ signal })`, so the stub needs a `close` that resolves. `abort` is reached only
  if that close rejects; a no-op keeps the path quiet.
- `readFramed` dispatches on `isMessageStream`; a plain stub yielding `Uint8Array` chunks takes
  the async-iterable implementation — the shape `test/rpc.codec-properties.spec.ts`'s
  `replyStream` already proves works. One `json(body)` frame, then `{ done: true }`.

### What `getConnections` must return

`openRpcStream` (`src/rpc/protocols.ts:651`) filters `node.getConnections(pid)` for
`c?.status === 'open' && typeof c?.newStream === 'function'`, then prefers a non-limited
connection. `isLimitedConnection` (`:617`) reads `c.limits`, then `c.remoteAddr?.toString?.()`, so
a bare `{ status: 'open', newStream }` is **not** limited and is chosen — the stub needs no
`limits` and no `remoteAddr`. `newStream` is called as
`newStream([protocol], { runOnLimitedConnection: true, negotiateFully: false, signal })` and must
return (or resolve to) the stub stream.

**Without the override the test silently proves nothing.** `dial: 'never'` maps to
`requireExisting: true`, so no connection yields `undefined` → `{kind: 'skipped'}` →
`fetchAndMergeSnapshot` returns `[]` having upserted nothing. That zero count looks exactly like a
cap doing its job — which is why this ticket already insists on a deep-equal against the full
expected id list rather than a `<= cap` assertion.
