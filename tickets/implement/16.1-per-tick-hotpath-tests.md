## What already landed (so you can read the diff, not re-derive it)

Three behavior-preserving changes, all in `fret-service.ts`, all verified by `npx tsc --noEmit`:

- **(a) `seedFromPeerStore` reuses the stored ring coordinate.** It now does
  `this.store.getById(pidStr)?.coord ?? (await hashPeerId(p.id))`, so the SHA-256 is paid only for
  a peer the routing table has never seen. A `NOTE:` at that line records why reuse is sound (the
  coordinate is `SHA-256(peer id)` and nothing rotates it) and the revisit condition (if ring
  coordinates ever rotate per epoch, reuse becomes wrong).
- **(b) Five sites now call the cached `this.selfCoord()`** instead of re-hashing this node's own
  peer id: the announce fan-out, the start-up warm-up pass, the leave fan-out, the self-upsert
  inside `seedFromPeerStore`, and `snapshot()`. Separately, two locals in `mergeAnnounceSnapshot`
  were renamed `self` / `selfCoord` → `sender` / `senderCoord`; that method deals with the
  *announcing* peer's coordinate, not ours, and the old names invited exactly the wrong
  substitution. The `hashPeerId` call there is unchanged and must stay.
- **(c) Capacity is enforced once per tick.** The trailing `enforceCapacity()` was removed from
  `seedFromPeerStore` and `seedFromBootstraps`; `stabilizeOnce` keeps the one call at the end of
  its first phase (it sees every insert the tick made, seeds included), and `start()` gained one
  explicit call right after its direct `seedFromPeerStore()` so the bound does not depend on a
  timer being armed. Comments at all four sites state the rule and the accepted cost.

## The one deliberate behavior change

Change (a) removed an *accidental* repair. Previously, re-hashing every tick silently overwrote any
routing-table coordinate that did not equal `SHA-256(peer id)` — for those peers libp2p's own peer
store also knew about. The only way such a coordinate enters the table is `importTable`, which
trusts a persisted snapshot's coordinate field. That repair is now gone, and the import-side check
is the only remaining defense. An arm recording this has already been appended to
`tickets/backlog/plan/2-routing-table-export-integrity`, and that arm forward-references a test from
this ticket by name — so writing it closes the loop.

## Tests to write

Suggested home: a new `packages/fret/test/per-tick-hotpath.spec.ts`. Check the existing specs listed
in `files:` first — several already build the rigs you need, and reusing one beats a new harness.

**Coordinate reuse (a)**

- A peer already in the routing table is not re-hashed by a maintenance cycle. Either count
  `hashPeerId` calls, or — simpler and closer to the real property — write a coordinate that is
  deliberately *not* the peer's id hash, run a cycle, and assert it survived.
- The tampered-coordinate case above is the one the backlog arm names. Assert it deliberately, with
  a comment cross-referencing `tickets/backlog/plan/2-routing-table-export-integrity`, so a future
  reader meets the decision rather than filing it as a bug.
- A peer appearing in the libp2p peer store for the first time still lands at `SHA-256(id)`. This is
  the miss path, and it is what makes the reuse safe.

**The rename (b)**

- After a snapshot announce is merged, the announcing peer is stored at the *announcer's* own ring
  coordinate — not at this node's. Cheap, and it pins the trap the rename exists to prevent.

**Capacity enforcement (c)**

- Seed the libp2p peer store with more peers than the configured capacity, run one maintenance
  cycle, and assert the routing table is at or under capacity once the cycle completes.
- Same over-capacity setup, then `start()`, and assert the table is trimmed **without** waiting for
  a maintenance cycle to fire. This is the case the explicit `start()` call exists for.
- A cycle that runs out of time still enforces: the enforcement sits above `stabilizeOnce`'s
  budget-expiry early return, and a comment there says so. Worth a test if one is cheap to drive
  from the existing concurrency rig; skip it rather than building a new harness for it, and say so
  in the handoff.

**Regressions to confirm, not rewrite**

`test/relevance.eviction.spec.ts`, `test/stabilize-concurrency.spec.ts` and
`test/sample-coordinate-verification.spec.ts` should all pass untouched. If one needs editing,
that is a signal worth reporting in the handoff, not a formality.
