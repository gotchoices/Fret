## What already landed (read `git show 01e05c0 -- packages/fret/src/service/fret-service.ts`)

Three behavior-preserving changes, all in `fret-service.ts`, all verified by `npx tsc --noEmit`:

- **(a) `seedFromPeerStore` reuses the stored ring coordinate.** It now does
  `this.store.getById(pidStr)?.coord ?? (await hashPeerId(p.id))`, so the SHA-256 is paid only for
  a peer the routing table has never seen. A `NOTE:` at that line records why reuse is sound (the
  coordinate is `SHA-256(peer id)` and nothing rotates it) and the revisit condition (if ring
  coordinates ever rotate per epoch, reuse becomes wrong).
- **(b) Five sites now call the cached `this.selfCoord()`** instead of re-hashing this node's own
  peer id: the announce fan-out, the start-up warm-up pass, the leave fan-out, the self-upsert
  inside `seedFromPeerStore`, and `snapshot()`. Separately, two locals in `mergeAnnounceSnapshot`
  were renamed `self` / `selfCoord` → `sender` / `senderCoord`; that method deals with the
  *announcing* peer's coordinate, not ours, and the old names invited exactly the wrong
  substitution. The `hashPeerId` call there is unchanged and must stay.
- **(c) Capacity is enforced once per tick.** The trailing `enforceCapacity()` was removed from
  `seedFromPeerStore` and `seedFromBootstraps`; `stabilizeOnce` keeps the one call at the end of
  its first phase (it sees every insert the tick made, seeds included), and `start()` gained one
  explicit call right after its direct `seedFromPeerStore()` so the bound does not depend on a
  timer being armed. Comments at all four sites state the rule and the accepted cost.

## The one deliberate behavior change

Change (a) removed an *accidental* repair. Previously, re-hashing every tick silently overwrote any
routing-table coordinate that did not equal `SHA-256(peer id)` — for those peers libp2p's own peer
store also knew about. The only way such a coordinate enters the table is `importTable`, which
trusts a persisted snapshot's coordinate field. That repair is now gone, and the import-side check
is the only remaining defense. An arm recording this has already been appended to
`tickets/backlog/plan/2-routing-table-export-integrity`, and that arm forward-references a test from
this ticket by name — so writing it closes the loop.

## Rig facts (established last run — do not re-derive)

Line numbers are approximate; grep the symbol.

- **A "maintenance cycle" is not `stabilizeOnce` alone.** The loop tick body
  (`startStabilizationLoop`, ~1932) is `seedFromPeerStore()` → `seedFromBootstraps()` →
  `stabilizeOnce()`. `stabilizeOnce` never seeds. So a test for (a) or (c) must drive
  `await (svc as any).seedFromPeerStore()` and then `await (svc as any).stabilizeOnce()`, or
  factor the three into a local `cycle()` helper in the spec.
- **`test/helpers/maintenance-rig.ts` (`buildMaintenanceRig(profile)`) is the rig to reuse.** It
  returns `{node, svc, store, rig, ping(), neighbors(), concurrency(), setTickBudget(ms),
  seedPeers(count, membership, patch?), teardown()}`. It overrides `node.getConnections` so every
  peer id resolves to one open stub connection (so every peer is dialable and connected), and
  `rig.behavior.set(id, 'hangs')` makes a peer's RPCs never answer. The service is deliberately
  **not** started, so passes are driven directly with no loop racing the assertions.
- **Gap in that rig, and the one piece of new harness needed:** `seedPeers` writes to the FRET
  `DigitreeStore` only. `seedFromPeerStore` enumerates `node.peerStore.all()`, so peers seeded that
  way are invisible to it. Tests for (a) and (c) need entries in the **libp2p peerStore** —
  `await node.peerStore.merge(pid, { multiaddrs: [...] })` (or `save`) against a real `PeerId` from
  `peerIdFromPrivateKey(await generateKeyPair('Ed25519'))`. Add a small helper next to the spec (or
  extend the rig with a `seedPeerStore` sibling) rather than a whole new harness.
- **`test/sample-coordinate-verification.spec.ts` is the lighter pattern** for the (b) rename test:
  `createMemNode()` + `new CoreFretService(node, {profile:'core', k:7})` + a direct
  `await (svc as any).mergeAnnounceSnapshot(from, snap)`, then read `svc.getStore().getById(id)`.
  No connection stubbing needed — that path does no I/O.
- **Capacity knobs.** `enforceCapacity` (~470) protects `self` plus up to `max(2, m) - 1` live
  members per side, and **protection outranks the cap**, so a test asserting "at or under capacity"
  must keep `capacity >= 2m - 1` (default m = 8 → protected set up to 15). Either pass a small `k`
  (m = ceil(k/2)) or a capacity comfortably above 15 — e.g. `{k: 7, capacity: 20}` seeded with 40
  peers. Getting this wrong makes the test fail against *correct* code; the over-capacity-by-
  protection case is already pinned in `test/relevance.eviction.spec.ts`, so do not re-pin it.
- **Budget-expiry-still-enforces (c, third case) is cheap with this rig after all** — the prior
  run's "skip it rather than build a harness" caveat does not apply. `setTickBudget(50)` plus
  `rig.behavior.set(id, 'hangs')` on the near peers is exactly the shape
  `stabilize-concurrency.spec.ts` already uses, and `enforceCapacity` sits *above* the
  `budget.signal.aborted` early return, so it still runs. Assert the table is trimmed even though
  the tick was cut. Note `setTickBudget` mutates a static and is restored by `teardown()`.
- **`start()` needs a real node** (it calls `registerRpcHandlers`); `createMemNode` is fine, and
  `svc.stop()` + `stopAll([node])` in a `finally`.

## Tests to write

Suggested home: a new `packages/fret/test/per-tick-hotpath.spec.ts`.

**Coordinate reuse (a)**

- A peer already in the routing table is not re-hashed by a maintenance cycle. Write a coordinate
  that is deliberately *not* the peer's id hash, run a cycle, assert it survived. (Closer to the
  real property than counting `hashPeerId` calls, and needs no module stubbing.)
- That tampered-coordinate case is the one the backlog arm names. Assert it deliberately, with a
  comment cross-referencing `tickets/backlog/plan/2-routing-table-export-integrity`, so a future
  reader meets the decision rather than filing it as a bug.
- A peer appearing in the libp2p peer store for the first time still lands at `SHA-256(id)`. This is
  the miss path, and it is what makes the reuse safe.

**The rename (b)**

- After a snapshot announce is merged, the announcing peer is stored at the *announcer's* own ring
  coordinate — not at this node's. Cheap, and it pins the trap the rename exists to prevent.

**Capacity enforcement (c)**

- Seed the libp2p peer store with more peers than the configured capacity, run one maintenance
  cycle, assert the routing table is at or under capacity once the cycle completes.
- Same over-capacity setup, then `start()`, and assert the table is trimmed **without** waiting for
  a maintenance cycle to fire. This is the case the explicit `start()` call exists for.
- A cycle whose budget expires still enforces (see *Rig facts* — drive it, don't skip it).

**Regressions to confirm, not rewrite**

`test/relevance.eviction.spec.ts`, `test/stabilize-concurrency.spec.ts` and
`test/sample-coordinate-verification.spec.ts` should all pass untouched. If one needs editing,
that is a signal worth reporting in the handoff, not a formality.
