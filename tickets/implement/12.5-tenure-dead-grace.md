## Why

Asked by the maintainer; this is the second half of `peer-session-tenure`, which records each peer's locally-proven tenure (how long this node has continuously observed it up). Today `applyContactStrike` (in `fret-service.ts`) marks a peer `dead` on its `deadAfterFailures`-th (3) failed contact spaced at least 500 ms apart. One strike lands per stabilization pass, so that is 3–4.5 s after the peer goes silent, for every peer.

`dead` excludes the peer from every ring view at once: successor/predecessor windows, cohorts, routing candidates, the size estimate and outgoing snapshots. For a server that is down for three minutes of maintenance, that means the ring re-forms around its gap. Its cohorts gain a replacement member, which at the storage layer above FRET means a sync to a peer that will be displaced again minutes later. Then everything flips back. For a phone that has been up five minutes, a fast verdict is right: it is probably gone for good.

### Why a time grace, not a larger strike count

Strikes arrive at the pass rate, so scaling `deadAfterFailures` by tenure only stretches 4.5 s to perhaps 12 s. That still marks the server dead long before a few minutes of maintenance end. The quantity that has to scale is *time*. So the rule becomes: a peer is marked `dead` when its contact-failure run has reached the threshold **and** the run has lasted at least `deadGraceMs(tenure)`.

## The design

### Grace function (pure, in `src/store/tenure.ts` beside the tenure helpers)

```ts
/** Below this proven tenure a peer gets no grace: newcomers keep today's verdict exactly. */
export const DEAD_GRACE_MIN_TENURE_MS = 10 * 60_000;
/** Grace earned per unit of tenure: a peer up for T is given T/12 to come back. */
export const DEAD_GRACE_TENURE_RATIO = 1 / 12;
export function deadGraceMs(tenureMs: number, capMs: number): number;
// tenureMs < MIN → 0; else min(capMs, tenureMs · RATIO)
```

Worked values at the default 5-minute cap: tenure 5 min → 0 (phone: unchanged, 3–4.5 s); 10 min → 50 s; 30 min → 2.5 min; 1 h or more → 5 min.

The 1/12 ratio is a judgement call, not a measurement, and the docs must say so. It is Lindy-shaped: the longer we have seen a peer up, the longer an absence is still plausibly "brief". The 10-minute floor is what keeps the user's example phone (on for 5 minutes) on today's fast path.

### Config

`FretConfig.maxDeadGraceMs`, default `300_000` (5 min). It is validated like `dialTimeoutMs` and `maxPassiveIntervalMs`: a finite number ≥ 0, and the constructor throws otherwise. **`0` disables grace entirely.** That is the off switch, with no separate boolean, the same convention as `maxPassiveIntervalMs`. The constructor also throws if it exceeds `TENURE_GAP_TOLERANCE_MS` (15 min). A grace longer than the tolerance could hold a peer "not dead" across a silence long enough that its session would restart on return, which contradicts itself.

### Run start stamp

Add `contactRunStartedAt: number` to `PeerEntry` (unix ms of the first strike counted in the current run; 0 = no run). Treat it exactly like `lastContactFailureAt`:
- not serialized
- 0 on `upsert` and on import
- cleared to 0 by `noteProofOfLife` alongside `contactFailures` and `lastContactFailureAt`, in the same patch

### `applyContactStrike`

This method stays synchronous. Its doc comment explains why, and grace must not add an await.

```
spacing guard (unchanged)
failures   = min(contactFailures + 1, threshold)          (unchanged)
runStart   = contactFailures === 0 ? now : contactRunStartedAt
grace      = deadGraceMs(provenTenureMs(e), cfg.maxDeadGraceMs)
toDead     = failures >= threshold && now - runStart >= grace && state !== 'dead'
patch      = { contactFailures: failures, lastContactFailureAt: now, contactRunStartedAt: runStart, ...(toDead ? { state: 'dead' } : {}) }
held       = failures >= threshold && !toDead && state !== 'dead'     → diag.deadGraceHeld++
change     = state !== 'dead' && (failures > e.contactFailures || toDead)
```

The `change` line **narrows** today's rule. Today every strike on a non-dead peer calls `noteChange`. With grace, a peer can sit at the clamped threshold for minutes. Counting each of those strikes as a change would pin the idle-backoff loop at 1.5 s for the whole grace, plus a redial per pass to a server we already know is down. So only a strike that progressed the count, or the transition to dead, is a change. Consequence: once the threshold is reached, the grace-held strikes that follow are quiet. The loop may back off, and the dead verdict then lands **at most one passive interval after the grace expires** (worst case 60 s at the default cap; in practice less, since a maintenance redial still in flight holds the loop at the base). Do not add a "pending" hold for grace-held peers: the point of the backoff is not to spin on a peer we have already judged. State the lateness bound in the docs.

`tenure` is frozen during the outage (no proof of life arrives), so grace is stable across the run. No need to snapshot it at run start.

### What a peer in grace is

It is still a live member: still in ring views, cohorts, routing candidates and snapshots. This is the intended tradeoff, and the docs must say so plainly:
- **Routing** routes around it without help. The routing paths record probe backoff on failure, and the next-hop cost lets a backed-off peer concede ~64 orders of ring distance (see `farWeights` in `src/selector/next-hop.ts`), so a hop through a grace-held peer is avoided whenever any reasonable alternative exists.
- **Cohorts** keep it as a member for up to the grace. The layer above already has to tolerate unavailable cohort members (`minSigs = k − x`, and expand outward), and that is cheaper than two membership changes plus a sync.
- **Other nodes** form their own verdicts from their own tenure records. Our snapshot keeps naming the peer during grace, which costs a receiver nothing it would not already spend probing it.
- **Recovery** during grace: any proof of life clears the run (`noteProofOfLife`, unchanged apart from also clearing the new stamp), and the session continues. No dead state is ever entered. That is the maintenance case working.

### Unchanged on purpose

- A **leave notice** still marks the sender dead immediately, whatever its tenure. It is the peer's own statement that it is going. A "back in N minutes" leave flavour needs leave authentication first (`tickets/backlog/22-debt-leave-authentication.md`). Add a one-line `NOTE:` at the leave handler's dead-marking site.
- **Self** is never struck (existing guard).
- The **dead re-probe arm, classification and negotiate-failure runs** are untouched.
- The **simulation harness** keeps its own escalation (`test/simulation/liveness.ts`). Grace is not mirrored there, since sim peers have no wall-clock tenure. Mention it in one docs sentence.

## Edge cases & interactions

- **Phone with tenure under 10 min**: grace 0, so the verdict is exactly today's. `test/address-less-departure.spec.ts` and `test/dead-state.spec.ts` are the regression guard and must stay green unchanged; their peers have little or no tenure. *Existing tests.*
- **Grace disabled (`maxDeadGraceMs: 0`)**: today's behaviour for every peer. With grace 0 the strike that reaches the threshold also transitions to dead, so "the count progressed, or the peer went dead" selects exactly the strikes today's rule counted as changes. *Inspection.*
- **Strike exactly at grace expiry** (`now − runStart === grace`): dead (≥). *Test row.*
- **Spacing guard vs run start**: a strike discarded by the 500 ms spacing does not set `runStart`. *Inspection* (the guard returns first).
- **Peer already dead and struck again** (dead arm): unchanged. No change is noted, the run start is untouched, and `held` is not counted. *Inspection.*
- **Concurrent strikes**: the method is synchronous, so there is no lost update. *Inspection.*
- **Recovery mid-grace then a new outage**: the run start is cleared by proof of life, so the new run measures its own grace. *Covered by the integration test.*
- **Imported table**: the run start is 0, and tenure is carried (previous ticket), so a long-tenured peer that is down at our restart still gets grace. If our downtime was more than 15 min its session restarts on first proof, but while it stays silent its frozen tenure stands. Intended: we have no evidence it left. *Inspection.*
- **Config validation**: negative, NaN, Infinity or over-tolerance values throw. *One assertion row in the existing constructor-validation spec, if one exists* (grep `maxPassiveIntervalMs` under `test/`). Otherwise inspection; do not create a spec for it.
- **Idle backoff interplay**: covered by the narrowed change rule above. The address-less departure case relies on strikes being changes while the count progresses, and that still holds.
