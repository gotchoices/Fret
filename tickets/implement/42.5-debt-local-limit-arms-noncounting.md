## What to build

### The non-counting rows

- **`cancelled` must stay distinguishable from `local-limit`.** `classify` (`src/rpc/request.ts`)
  checks the caller's signal first, so a refusal landing during a `stop()` classifies `cancelled`,
  not `local-limit` — and then `diag.streamLimit` does **not** increment. This is the case where a
  naive "count it wherever we see a stream error" implementation over-counts, which is why the row
  is worth its weight.
- **`skipped` never reaches the counter either** — the dial *mode* forbade dialing, so no stream
  was ever attempted. Same assertion shape: counter unchanged, peer untouched.

Both rows assert the same peer-state invariants the counting rows do (no `contactFailures`, no
`failureCount`, unchanged `relevance` / `membership` / `state`, no `ProbeBackoff` entry) **plus**
`diag.streamLimit` unchanged — the delta is the counter, so the assertion must be a strict
equality against the pre-call reading, not a "did not decrease".

## Edge cases & interactions

- **Driving `cancelled` needs the caller's own signal to have fired**, not the RPC deadline —
  those are different outcomes (`cancelled` vs `timeout`). The discriminator is that the sender
  builds its deadline as a *child* of the caller's signal, so abort the caller's controller
  before the call and the child fires with it.
- **Driving `skipped`** means a dial mode that yields no stream (`dial: 'never'` /
  `requireExisting` with no open connection), not a broken dial — a broken dial is `unreachable`.
- Do not weaken any assertion the counting rows already make in order to share a helper between
  the two row kinds; a shared helper that only checks "counter did not decrease" would make the
  counting rows vacuous.
