description: Each kind of network message is allowed up to half a megabyte on the wire, far more than any real message needs, and one of them is checked against two different size limits that disagree by four times. Work out what each message can actually be at its largest and use that one number.
prereq: 15.3-rpc-json-handler-seam
files: packages/fret/src/rpc/protocols.ts, packages/fret/src/rpc/{neighbors,leave,maybe-act,ping}.ts, packages/fret/src/service/fret-service.ts, packages/fret/test/rpc.codec-properties.spec.ts, packages/fret/test/rpc.handler-fuzz.spec.ts, docs/fret.md
difficulty: easy
----

Second of two tickets split out of `plan/15.3-rpc-message-validators`. `15.3` gave every message a
parser with stated per-field caps; this one turns those caps into the wire byte cap, so an
over-sized message is refused **at the length prefix** — before a single body byte is pulled — and
so the maybeAct wire cap and the service's own activity cap stop being two numbers.

## Why this is cheap now

`readFramed` already enforces `maxBytes` in the decoder's `onLength` hook, which fires the moment
the unsigned-varint prefix arrives. An over-cap message therefore already costs the receiver only
the prefix. What is missing is that the caps themselves are round numbers nobody derived: the wire
admits 4–100× what any legal message can be, so the early refusal almost never fires.

## Today's numbers, and what is wrong with them

| protocol | Core | Edge | problem |
|---|---|---|---|
| maybeAct | 512 KiB | 256 KiB | wire admits 512 KiB while `handleMaybeAct` refuses an `activity` over a fixed 128 KiB *after* the whole body is buffered — **two numbers, disagreeing 4× on Core** |
| neighbors / announce | 128 KiB | 64 KiB | thousands of peer ids fit under the cap; the parser now caps the lists at 16/16/8 (Core) |
| leave | 4096 (fixed) | 4096 | already about right — but never derived |
| ping reply | 1024 | 1024 | already right |

## The arithmetic (state it in the code, not only here)

Budget one peer id at **64 bytes** of JSON: base58btc peer ids are ≤ 53 characters for every key
type FRET meets, plus quotes and a comma. Use 64 as the per-id line item so the arithmetic has
headroom without needing a re-derivation per key type.

**leave** — 12 replacements × 64 = 768, `from` 64, `timestamp` 16, `v` and JSON punctuation ≈ 64.
Total ≈ **912 bytes**. Keep 4096; it is ~4.5× headroom over the maximum, which is the right shape
for a fixed-size message. Add the arithmetic as a comment beside the constant so the number stops
looking arbitrary.

**neighbors / announce** — Core: (16 + 16) ids × 64 = 2048; 8 sample entries × (id 64 + base64url
coord ≈ 48 + relevance ≈ 20 + keys ≈ 40) = 1440; `from` 64; `timestamp` 16; `size_estimate` +
`confidence` ≈ 40; `sig` — reserve 256 (the field exists, message signing is unimplemented);
punctuation ≈ 128. Fixed total ≈ **4 KiB Core / 2.5 KiB Edge**.

`metadata` is the term that dominates and the one this ticket must pin down: it is
`Record<string, unknown>` of the *sender's* application metadata, so it is unbounded by
construction. **First action of this ticket: confirm whether `FretService.snapshot()` actually
populates `metadata`.**

- If it does not, the field is receive-only, and the cap is the fixed total plus a stated metadata
  allowance.
- If it does, add an outgoing size guard so our own cap can never refuse our own message.

Either way declare `MAX_SNAPSHOT_METADATA_BYTES` explicitly (proposed **8 KiB Core / 4 KiB Edge**)
and set the wire cap to fixed-total + metadata allowance, rounded up: **16 KiB Core / 8 KiB Edge**.
That is an 8× tightening from today with ~2× headroom over the derived maximum.

**maybeAct** — the two numbers become one. Non-activity fields: `key` 1024, `correlation_id` 256,
`digest` 4096 (the cap `15.3` adds), 64 breadcrumbs × 64 = 4096, `signature` — reserve 512
(unimplemented), numbers and punctuation ≈ 256. Overhead total ≈ **10.5 KiB**; declare
`MAYBE_ACT_OVERHEAD_BYTES = 16 * 1024`. Then:

```
MAX_ACTIVITY_BYTES = 128 * 1024                        // unchanged, both profiles
maxBytesMaybeAct() = MAX_ACTIVITY_BYTES + MAYBE_ACT_OVERHEAD_BYTES   // 144 KiB, both profiles
```

`handleMaybeAct`'s `msg.activity.length > 128 * 1024` check reads `MAX_ACTIVITY_BYTES` — the same
constant the wire cap is derived from, so the two can no longer disagree.

**The Core/Edge split disappears for maybeAct, deliberately.** The activity cap was never
profile-split (it is a fixed 128 KiB in `handleMaybeAct` on both profiles), so the *wire* split was
cosmetic: an Edge node accepting a 200 KiB message only to refuse its 128 KiB-plus activity a moment
later. Making the wire cap follow the activity cap makes the refusal honest. `docs/fret.md` states
"stricter payload caps" as Edge's intended posture and that intent is **unimplemented** — file it
rather than silently implementing it here, because lowering Edge's activity cap changes what
activities an Edge-hosted cluster will accept and that is a routing-behavior decision, not a cap
cleanup. See the backlog ticket named below.

Note `msg.activity.length` counts UTF-16 code units of a base64url string, which for base64url is
one byte per character — so the string-length check and the byte cap are commensurable here. State
that in the comment; it is the assumption that makes one constant serve both.

## Edge cases & interactions

- **A cap must never refuse our own legal output.** For every protocol, construct the largest legal
  message the local profile can emit and assert it encodes to fewer bytes than the cap. This is the
  test that catches an over-tightened cap before a deployment does.
- **The two profiles must each be checked**, since Edge's caps are smaller but its message
  *maximum* is smaller too — the headroom ratio, not the absolute number, is what matters.
- Refusal happens at the prefix: assert an over-cap message costs the receiver the prefix only, by
  **counting pulls** on a source that reports them (`test/rpc.codec-properties.spec.ts` already has
  this instrument), not by inferring it.
- An over-cap message reaching a *sender* (a reply larger than the cap) is a `PayloadTooLargeError`
  → `decode-error` → proof of life, never a contact strike. Confirm no call site books a strike.
- `rpcRequest`'s `DEFAULT_MAX_BYTES` is documented as "the smallest production per-protocol cap
  (neighbors on the Edge profile)". After this ticket that is 8 KiB, not 64 KiB — update the
  constant *and* its doc comment together, or the comment becomes a lie about a number a consumer
  relies on.
- Both merge paths (`mergeAnnounceSnapshot`, `fetchAndMergeSnapshot`) are parser-covered after
  `15.3`, so the byte cap is a second line of defense, not the only one. Do not weaken either.
- Leave stays a single fixed 4096 on both profiles; the message has no profile-dependent term.

## Key tests to expect

- Per protocol per profile: the largest legal message encodes under the cap (see above).
- Per protocol: a message one byte over the cap is refused after the receiver pulls only the length
  prefix — measured by pull count.
- A maybeAct message whose `activity` is exactly `MAX_ACTIVITY_BYTES` is accepted; one byte over is
  refused, and refused *at the prefix* if the whole message thereby exceeds the wire cap, otherwise
  by `handleMaybeAct` with `diag.rejected.payloadTooLarge`. Pin which boundary catches which case —
  they are adjacent and it is exactly where a future edit will get it wrong.
- The existing handler-fuzz release-exactly-once invariants hold at the new caps (a
  `PayloadTooLargeError` is frame-level → abort arm).
