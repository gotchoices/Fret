Second of two tickets split out of `plan/15.3-rpc-message-validators`. `15.3` gave every message a
parser with stated per-field caps; this one turns those caps into the wire byte cap, so an
over-sized message is refused **at the length prefix** — before a single body byte is pulled — and
so the maybeAct wire cap and the service's own activity cap stop being two numbers.

## Why this is cheap now

`readFramed` already enforces `maxBytes` in the decoder's `onLength` hook, which fires the moment
the unsigned-varint prefix arrives. An over-cap message therefore already costs the receiver only
the prefix. What is missing is that the caps themselves are round numbers nobody derived: the wire
admits 4–100× what any legal message can be, so the early refusal almost never fires.

## The arithmetic (state it in the code, not only here)

Budget one peer id at **64 bytes** of JSON: base58btc peer ids are ≤ 53 characters for every key
type FRET meets, plus quotes and a comma. Use 64 as the per-id line item so the arithmetic has
headroom without needing a re-derivation per key type.

**leave** — 12 replacements × 64 = 768, `from` 64, `timestamp` 16, `v` and JSON punctuation ≈ 64.
Total ≈ **912 bytes**. Keep 4096; it is ~4.5× headroom over the maximum, which is the right shape
for a fixed-size message.

**neighbors / announce** — Core: (16 + 16) ids × 64 = 2048; 8 sample entries × (id 64 + base64url
coord ≈ 48 + relevance ≈ 20 + keys ≈ 40) = 1440; `from` 64; `timestamp` 16; `size_estimate` +
`confidence` ≈ 40; `sig` — reserve 256 (the field exists, message signing is unimplemented);
punctuation ≈ 128. Fixed total ≈ **4 KiB Core / 2.5 KiB Edge**. Plus `MAX_SNAPSHOT_METADATA_BYTES`
(8 KiB Core / 4 KiB Edge) → wire cap **16 KiB Core / 8 KiB Edge**, an 8× tightening from today with
~2× headroom over the derived maximum.

**maybeAct** — the two numbers become one. Non-activity fields: `key` 1024, `correlation_id` 256,
`digest` 4096, 64 breadcrumbs × 64 = 4096, `signature` — reserve 512 (unimplemented), numbers and
punctuation ≈ 256. Overhead total ≈ **10.5 KiB**, rounded up to `MAYBE_ACT_OVERHEAD_BYTES = 16 KiB`.
`MAX_ACTIVITY_BYTES = 128 KiB` unchanged both profiles. `maxBytesMaybeAct() = MAX_ACTIVITY_BYTES +
MAYBE_ACT_OVERHEAD_BYTES` = 144 KiB, both profiles — deliberately no Core/Edge split, since the
activity cap itself was never profile-split; see the docs step above for why that split is parked
as a backlog idea rather than implemented here.

`msg.activity.length` counts UTF-16 code units of a base64url string, which for base64url is one
byte per character — so the string-length check and the byte cap are commensurable with one
constant serving both.

## Edge cases & interactions

- **A cap must never refuse our own legal output.** For every protocol, construct the largest legal
  message the local profile can emit and assert it encodes to fewer bytes than the cap.
- **The two profiles must each be checked** — the headroom ratio, not the absolute number, is what
  matters.
- Refusal happens at the prefix: assert an over-cap message costs the receiver the prefix only, by
  counting pulls on a source that reports them, not by inferring it.
- An over-cap message reaching a *sender* (a reply larger than the cap) is a `PayloadTooLargeError`
  → `decode-error` → proof of life, never a contact strike.
- Both merge paths (`mergeAnnounceSnapshot`, `fetchAndMergeSnapshot`) are parser-covered after
  `15.3`, so the byte cap is a second line of defense, not the only one.
- Leave stays a single fixed 4096 on both profiles; the message has no profile-dependent term.
