New test, inserted at the end of each per-profile `describe` inside

> `it('applies the cap through the handler the service actually registers', ...)`

It is **unvalidated** — neither `tsc --noEmit` nor `yarn test` has been run against it. Treat it
as a draft that is very likely correct rather than as finished work.

What it does, and why each step is there:

- Replaces `handle` on the already-started real mem node with a recorder, then calls the private
  `registerRpcHandlers()` through a cast. A real node (not the module's `fakeNode()`) because
  that stub has no `peerId` and `enforceCapacity` / `applyTouch` both reach
  `selfCoord()` → `hashPeerId(this.node.peerId)`. `start()` is deliberately not called —
  stabilization and the peerStore seed would drag their own upserts into the counter.
- Seeds `FROM` into the store before installing the upsert counter, so the announce handler's
  `onInbound` → `noteInboundRpc(from)` (detached, racing the merge) short-circuits on its
  `if (!getById(id))` guard.
- Wraps `mergeAnnounceSnapshot` on the instance to capture and await the promise `handleAnnounce`
  detaches. The snapshot still arrives through the real parser.
- Invokes the recorded `PROTOCOL_NEIGHBORS_ANNOUNCE` handler with `inboundStub([json(overCapBody())])`
  and a connection whose `remotePeer` is `FROM` — it must equal the body's `from` or the handler
  drops the message without replying and the count is silently 0.
- Asserts the counted upserts equal `1 + successors + predecessors + sample` and match the
  expected ids in merge order, and that nothing past each cap reached the store.

It reuses the block's existing fixtures unchanged (`FROM`, `OVER_SUCC`, `OVER_PRED`,
`OVER_SAMPLE`, `overCapBody()`, `countUpserts()`, `DrivableMerge`, the `profiles` table) plus the
module-scope `InboundHandler`, `inboundStub`, `json`, `P`. Nothing was moved to a wider scope, so
the fetch-path ticket may still need to hoist something.
