### Run-scoped cancellation

`FretService` gains one run-scoped controller:

- `private runAbort: AbortController | null = null` — minted in `start()` **immediately after
  `this.runGen++`** (line ~700), aborted in `stop()` **immediately after `this.clearLoopTimers()`**
  (line ~801), i.e. *before* `removeNodeListeners()` / `unregisterRpcHandlers()` and before the
  leave fan-out. Background maintenance RPCs die at once and do not compete with teardown.
- Exposed as `private get runSignal(): AbortSignal | undefined { return this.runAbort?.signal }`.
- A start→stop→start cycle must mint a **fresh** controller. A reused, already-aborted one silently
  cancels every RPC of the new run — the same class of bug the `runGen` generation counter exists
  to prevent, which is why the mint mirrors its placement.

The leave fan-out must **not** use `runSignal` (it runs *after* the abort, by design).
`sendLeaveToNeighbors` (~1282) builds its own `deadline(SHUTDOWN_BUDGET_MS)` and passes that signal
plus `timeoutMs: 1500` per notice, cancelling it in a `finally`, and breaks out of both loops once
that signal aborts (otherwise every remaining `sendLeave` throws immediately and only logs noise).

- `SHUTDOWN_BUDGET_MS = 3000` — the fan-out is `announceFanout`-bounded (Core 8 / Edge 4) and
  `isDoomedDial`-filtered, so 3 s is generous for the reachable targets while capping a `stop()`
  that would otherwise serialize several dead dials.
- `LEAVE_NOTICE_TIMEOUT_MS = 1500` per notice.

Both belong next to the other `private static readonly` service constants
(`DEPARTURE_DEBOUNCE_MS`, `BACKOFF_BASE_MS`, …) so they are stated once.

### Per-call-site budgets

Every existing outbound call site passes `{ signal: this.runSignal }`; the ping and announce paths
additionally pass a tighter `timeoutMs`.

| call site | line (approx) | sender | `timeoutMs` |
|---|---|---|---|
| `preconnectNeighbors` | 1213 | `sendPing` | 2000 |
| active preconnect tick | 1239 | `sendPing` | 2000 |
| `probeNeighborsLatency` | 1657 | `sendPing` | 2000 |
| `probeMembership` | 1801 | `sendPing` | 2000 |
| `sendAnnouncementsRateLimited` | 1164 | `announceNeighbors` | 2000 |
| `mergeNeighborSnapshots` | 1830 | `fetchNeighbors` | default (5000) |
| `sendLeaveToNeighbors` | 1300, 1309 | `sendLeave` | 1500 (+ own shutdown deadline) |
| `routeAct` forward path | 2090 | `sendMaybeAct` | default (5000) |
| `iterativeLookup` probe | 2478 | `sendMaybeAct` | default (5000) |
| `iterativeLookup` activity resend | 2539 | `sendMaybeAct` | default (5000) |

2000 ms on the ping and announce paths: a ping is a ~50-byte round trip and an announce is a
fire-and-forget push with no reply of substance, so 5 s there only ever means "this peer is gone" —
and these are exactly the paths that must not hold a maintenance tick open. `sendMaybeAct` keeps
5000 because it returns only once the *whole remaining route* has completed downstream, so its
budget is a route budget, not a link budget; tightening it is out of scope.

### Cancellation is not evidence about the peer

**This is the correctness crux and the single highest-value assertion in this ticket.**

Today every thrown error from an outbound RPC reaches `noteRpcFailure` (~589), which routes
anything that is not an unsupported-protocol error into `applyContactFailure` — a strike toward
marking the peer `dead` after 3 spaced failures. Two aborts must be told apart:

- **The RPC's own `timeoutMs` fired** → the peer accepted nothing / answered nothing within the
  budget. Genuine unreachability; keeps today's semantics (a contact failure).
- **A caller signal fired** (`stop()`, or a future per-tick budget) → *we* gave up, and the peer
  said nothing either way. This must record **nothing**: no `applyContactFailure`, no
  `applyFailure`, no `recordBackoff`, no `diag.pingsFail` increment.

Without this, a `stop()` or a busy tick manufactures strikes against healthy neighbors and can mark
them `dead` — inverting the intent of the whole change.

No new error types are needed, because the *caller* holds the signal it passed. Add one guard:

```ts
/** True when `err` is (or follows) our own cancellation — not evidence about the peer. */
private wasCancelled(sig: AbortSignal | undefined): boolean { return sig?.aborted === true; }
```

Document at the guard **why the caller's signal and not the sender's**: the sender's internal
deadline signal is a *child* of the caller's, so the child aborts in both cases while the caller's
aborts only when we cancelled. Checking the caller's is what discriminates them.

Apply it at every catch site that scores a peer, capturing the signal in a local **before** the
loop so a mid-loop mint cannot change what is being compared:

- `probeNeighborsLatency` (~1668) — guard `diag.pingsFail++` and `noteRpcFailure`; `return` rather
  than `continue`, since every remaining call in the loop would abort too.
- `probeMembership` (~1812) — guard `diag.pingsFail++`, `noteRpcFailure`, **and `recordBackoff`**:
  a cancelled probe must not push a peer into a longer backoff window it never earned.
- `routeAct`'s forward-path catch (~2104) — guard the log, `noteRpcFailure`, and `recordBackoff`;
  fall through to the existing `buildNearAnchor` reply.
- `iterativeLookup`'s activity-send catch (~2550) and outer hop catch (~2570) — same guard; on the
  outer one, leave the walk (so the trailing `yield { type: 'exhausted', hop }` runs) rather than
  burning the remaining attempts on a signal that is already aborted.
- `preconnectNeighbors` (~1213) and the active preconnect tick (~1239) score nothing, so the guard
  is only about log noise there — still worth an early `return`.
- `mergeNeighborSnapshots` (~1830) and `sendAnnouncementsRateLimited` (~1164) score nothing either
  (both swallow internally), but should `break` their loops once cancelled.

## Edge cases & interactions

- **`deadline.cancel()` on every path** — success, throw, and abort. A leaked timer fails the mocha
  exit watchdog rather than merely leaking, so it surfaces as a whole-suite failure with a
  confusing message.
- **`stop()` ordering.** Abort *after* `clearLoopTimers()` and *before* the leave fan-out.
  Asserting `stop()` still delivers leave notices is a **required** test: aborting one step too
  early silently deletes the graceful-departure protocol.
- **Already-aborted signal at entry** — `deadline(ms, parent)` with `parent.aborted` already true
  produces an aborted signal synchronously and `openRpcStream` throws before dialing (both already
  implemented), so a `stop()` racing a tick issues no dials. Worth an assertion at the service
  level too.
- **Inbound handlers stay out of scope.** `readAllBounded`'s handler-side use keeps its 5 s budget
  and no signal; the slow-loris `NOTE:` at `readAllBounded` still stands.
