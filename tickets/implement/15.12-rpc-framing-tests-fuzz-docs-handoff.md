### `test/stabilize-concurrency.spec.ts` — 3 failures, one likely root cause

1. "one unresponsive near peer costs the tick its budget, not the other peers their probe and
   fetch" — `three pings answered: expected 0 to be 3` (spec line ~94).
2. "pings a near peer before fetching its snapshot, for every near peer, while peers overlap" —
   `expected +0 to equal 4` (line ~143).
3. "records nothing against a peer whose membership probe the budget aborts mid-flight" —
   `no ping failure counted: expected 4 to equal 0` (line ~224).

Hypothesis (unverified — check first): this spec's stub peers reply to pings with RAW
unframed JSON, so the migrated `sendPing`'s `readFramed` never sees a complete frame → every
ping times out (0 answered) and failures get scored (4 vs 0). Fix shape: wrap stub replies in
`lp.encode.single(...)` (see `framed()` helper in `rpc.handler-fuzz.spec.ts` for the pattern).
This spec was never in any framing ticket's file list — it was missed, not half-done.

### `test/rpc.stream-errors.spec.ts` — 2 failures, "over a real transport" describe

4. "fetchNeighbors answers promptly, and empty, for a peer that writes half a snapshot and
   closes" — `took 5014ms of a 5000ms budget: expected 5014 to be ≤2500` (expectPrompt,
   line ~928/941).
5. "sendPing collapses a real half-reply and a real reset into ok: false" —
   `DeadlineExpiredError: deadline expired after 5000ms`.

The unit-level sections of this file were migrated (its other ~40 tests pass); the
real-transport section's half-reply writers likely still write UNFRAMED partial JSON. Under
framing, unframed bytes look like a garbage/incomplete varint prefix or an incomplete frame,
and "promptly on close" only holds if the writer actually closes its write end so `readFramed`
throws `FrameTruncationError`. Check what those writers send: they should send a PARTIAL FRAME
(e.g. `lp.encode.single(body).subarray(0, n)` for n < full length) then close/reset, which
gives the prompt truncation/`ok:false` the tests expect. A writer that closes but readFramed
still hits the 5 s deadline would be a real product bug — verify which before editing the test.
