## The test to write

Register a handler at a deliberately small cap — call `registerRpcHandler` **directly** with e.g.
`maxInboundStreams: 2` — and drive N+1 concurrent inbound streams on **one** connection between two
in-memory nodes. Assert the excess stream is refused, and record what the sender's `RpcOutcome`
actually is.

This one case pins three things at once: that the caps reach `node.handle` at all; the exact
off-by-one; and that a remote's inbound refusal surfaces to the sender as `unreachable` — the
residual the sibling `local-limit-rpc-outcome` ticket documented — so if a future libp2p version
*does* propagate the reason, this test fails and the residual gets revisited.

**The off-by-one must be pinned by observation, not by reading libp2p's source.** The comparison is
`streamCount > limit` over `connection.streams` filtered by protocol and direction (`countStreams`
in libp2p's `connection.js`), and whether the stream being admitted is already in that collection at
check time was never verified — so whether the cap admits `limit` or `limit + 1` concurrent streams
is *unknown*. Write the assertion against what the run does. Do not derive the number from the
library source and then assert it.

### How to drive the sender

Call `rpcRequest` (`src/rpc/request.ts`) directly rather than a FRET sender — it returns
`RpcOutcome<T>` and **never throws for a network outcome**, which is exactly what the assertion
needs to read. Two things that matter for holding N+1 streams open at once:

- Pass a `decode` validator so the sender *reads a reply* and therefore stays parked while the
  gated `serve` body holds it. Without `decode` the request is write-only and returns `ok` right
  after the write, so nothing is held.
- Establish the connection first (dial once), so every subsequent `openRpcStream` reuses that one
  connection — the cap is per protocol **per connection**, so a second connection would silently
  invalidate the case.

### The expected-outcome residual, and why it must not be derived

`classify()` in `src/rpc/request.ts` carries a `NOTE:` stating that a **remote's** inbound-cap
refusal is *not* distinguishable — it reads as a reset and lands in the `unreachable` arm. That is
the residual this test exists to pin. Assert what the run actually produces; if it turns out not to
be `unreachable`, that is the finding, not a test to bend.

Likewise the off-by-one: write the assertion from the observed number of admitted concurrent
streams. Do not read it out of libp2p's `countStreams`.
