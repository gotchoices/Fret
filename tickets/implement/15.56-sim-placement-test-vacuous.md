Follow-on from `sim-joiner-placement` (fixed and shipped). That fix was real: peers joining the
simulation part-way through a run were all being placed into a shrinking sliver of the ring
instead of spread around it. The test added alongside it does not detect that.

## What is wrong

The last case in `test/churn-scenarios.spec.ts`,
`it('uniform placement keeps joiners spread across the ring')`, measures the **largest gap**
between adjacent peers on the ring and fails if it exceeds 10x even spacing.

Largest gap is the wrong statistic. Piling every joiner into one sliver makes that sliver
*denser*; the surviving evenly-placed initial population still holds the largest hole down. So
the number barely moves — and on some seeds it moves the *wrong way*.

## Measured

Both arms were run by temporarily restoring the pre-fix placement (see *Restoring the old
placement* below), over five seeds (8008, 8009, 8010, 4242, 99) and three join patterns.
"even spacing" = ringSize / (alive peers).

**Largest gap / even spacing** — the statistic in the test today:

| join pattern | post-fix (current code) | pre-fix (the bug) |
|---|---|---|
| batch burst only (`churnRatePerSec: 0`) | 1.25, 1.25, 1.25, 1.25, 1.25 | 1.25, 1.25, 1.25, 1.25, 1.25 |
| steady trickle only (churn 2/s, no batch) | 3.00, 3.00, 2.57, 3.69, 2.55 | 4.02, 3.00, 6.00, 5.00, 5.00 |
| both (the config the test uses today) | 5.00, 2.81, 3.65, 3.50, 3.75 | 6.25, 5.00, 3.75, 7.50, 5.00 |

On the pure batch-join case — the exact case the original ticket was about — the two arms are
**bit-identical**. On the other two the ranges overlap and are partly inverted (pre-fix 3.75 sits
below post-fix 5.00). No threshold on this statistic separates the arms on any of the three
patterns. The test's own 10x threshold is never approached by either arm.

**Peers inside one even-spacing-wide arc** — the proposed replacement. Scan an arc of width
ringSize / n anchored at each peer in turn (wrapping), count the peers inside, take the maximum:

| join pattern | post-fix (current code) | pre-fix (the bug) |
|---|---|---|
| batch burst only | 3, 3, 3, 3, 3 | 11, 11, 11, 11, 11 |
| steady trickle only | 3, 3, 3, 4, 3 | 18, 18, 16, 16, 16 |
| both | 4, 4, 4, 4, 4 | 24, 24, 25, 26, 24 |

Worst post-fix reading across all fifteen runs: **4**. Best (lowest) pre-fix reading: **11**.
Nothing in between, so a threshold of **7** sits 1.75x above everything the fixed code produced
and 1.57x below everything the bug produced. Coefficient of variation of the gaps also separates
(0.60–0.90 vs 1.03–1.41) but with barely 1.15x of margin, so it is not the one to pick.

Base config for every run above: `n: 40, k: 15, m: 8, stabilizationIntervalMs: 500,
durationMs: 10000`; batch arms call `scheduleBatchJoin(10, 3000)`; churn arms set
`churnRatePerSec: 2`. Alive population at the end is 50 (batch and both) or 40 (trickle) —
churn pairs each leave with a join, so the count holds.

## Why the trickle case matters separately

`handleChurn` calls `handleJoin` for every leave, so churn-driven joins run through the same
placement path as a batch join. The current test's config mixes both, which means neither is
isolated: a statistic could pass on the mix while being blind to one arm. The measurements above
show the batch-only arm is exactly where the current statistic is at its blindest. Cover the two
patterns as separate cases rather than one mixed one — the mixed case adds no coverage the two
separate ones lack.

## Restoring the old placement

The pre-fix behavior is one line in `generateCoord` (`fret-sim.ts`, the `'uniform'` case). Today:

```ts
return isJoin ? this.randomCoord() : this.uniformCoord(index, this.config.n)
```

Pre-fix, joiners went through `uniformCoord(index, this.nextPeerIndex)`. `handleJoin` does
`const index = this.nextPeerIndex++` before creating the peer, so `nextPeerIndex` is `index + 1`
at that moment and each joiner landed at `index / (index + 1)` of the ring — 40/41, 41/42, … —
all converging on the same point near the ring's top, in a sliver that narrows with every join.

## Make the negative control permanent

The reason a vacuous guard shipped is that "put the bug back and watch it go red" was a manual
step done once at authoring time, with nothing in the repo holding it. Prefer making it an
assertion instead of a ritual: add a `PlacementStrategy` variant (`PlacementStrategy` is the
exported union at `fret-sim.ts:46`, already carrying `'clustered'` and `'skewed'` for modelling
pathological topologies) that reproduces this clumping deliberately — joiners at
`index / (index + 1)` of the ring, initial peers placed evenly as now — and have the spec assert
**both** directions: the fixed placement reads under the threshold, the clumping placement reads
over it. Then the guard proves its own separating power on every run, and the numbers in the
tables above stay checkable rather than becoming folklore.

If that variant is judged too much surface for the simulator, the fallback is the manual restore
above — but then the acceptance step below is mandatory and must be reported as actually run, not
assumed.

## Expected behavior

- The spec fails when the old placement is in effect and passes on current code, with the margin
  stated above, for **both** join patterns.
- The threshold appears in the source next to the assertion together with the measurement that
  produced it — both arms, not just the passing one. The comment beside the current assertion
  cites only post-fix readings, which is precisely how a guard with no separating power reads as
  calibrated.
- The old largest-gap assertion goes away. Leaving it beside a working statistic implies it
  contributes something; it does not, and the tables above are the evidence.
