`stabilizeOnce` (`service/fret-service.ts:1758`) runs four passes, each a plain `for` loop with an
`await` inside, so every RPC waits for the one before it:

| pass | line | RPCs per tick (Core / Edge) |
|---|---|---|
| `probeNeighborsLatency` — ping the 4 nearest live members | 1785 | 4 / 4 |
| `mergeNeighborSnapshots` — fetch a snapshot from those same 4 | 1967 | 4 / 4 |
| `classifyUnknownPeers` — ping unclassified peers | 1833 | 8 / 4 |
| `reprobeExcludedPeers` → `reprobeOffRing` — ping `foreign` (2/1) then `dead` (2/1) | 1878 / 1905 | 4 / 2 |
| **total** | | **20 / 14** |

Serial execution means the tick's wall time is the *sum* of 14–20 round trips. Each is already
individually bounded (`MAINTENANCE_RPC_TIMEOUT_MS` = 2000 ms for a ping at `fret-service.ts:292`,
the 5 s `RPC_TIMEOUT_MS` default for a snapshot fetch), so the tick is bounded at roughly 60 s
Core / 50 s Edge — bounded, but far past the 1.5 s passive tick interval, and the loop awaits the
tick before re-arming (`startStabilizationLoop`, 1705).

Expected behavior: a maintenance tick completes in bounded, *useful* time — on the order of the
slowest single peer rather than the sum of all of them — and a peer that hangs delays nobody else.

### Concurrency bound

These are the numbers `docs/fret.md` *Operating profiles* already commits to ("max 4–6 concurrent"

inlined.

### Tick budget

`private static readonly STABILIZE_TICK_BUDGET_MS = 5000;` — put it beside the other budget
constants (`MAINTENANCE_RPC_TIMEOUT_MS` / `SHUTDOWN_BUDGET_MS`, `fret-service.ts:283–303`).

`stabilizeOnce` opens `deadline(STABILIZE_TICK_BUDGET_MS, this.runSignal)` at the top and
`cancel()`s it in a `finally`. (`deadline` is already imported at `fret-service.ts:28`.) That
signal goes to every pooled call *and* to every RPC in the tick, so when the budget expires:
in-flight RPCs abort, not-yet-started tasks come back `skipped`, and the tick returns.

The existing cancellation discriminator keeps working unchanged and is why this is safe:
`wasCancelled(sig)` (`fret-service.ts:666`) is checked against the signal the caller passed, and
each sender builds its own deadline as a *child* of it — so a tick-budget expiry reads as "our own
cancellation" and records no strike, no backoff, no `pingsFail`, exactly as a `stop()` does today.

5000 ms is chosen as the same magnitude as the single-RPC default budget: a tick may be consumed by
one round of slow peers, never by several rounds of them. Skipped work is not lost — the next tick
(1.5 s passive / 300 ms active) re-derives its candidates from the store and picks it up.

NOTE-worthy at the code site: active mode ticks every 300 ms, so a 5 s budget makes active
stabilization effectively continuous under failure. That is true today as well (the loop awaits the
tick before re-arming); tighten the budget per-mode only if warm-up latency ever measurably suffers.

### Restructured tick

```
stabilizeOnce():
  sweepBoundedMaps()
  budget = deadline(STABILIZE_TICK_BUDGET_MS, runSignal)
  try:
    near = live-member neighbours, dialable, self excluded, ring order, first 4
    # Phase 1: per-peer chain — ping THEN fetch for the same peer.
    results = runPooled(near.map(id => () => this.probeAndFetch(id, budget.signal)), pool)
    enforceCapacity(); announceToNewPeers(flatten(fulfilled results))
    # Phase 2: classification + re-probe arms, pooled together.
    targets = [...classifyTargets(), ...reprobeExcludedTargets()]
    runPooled(targets.map(id => () => this.probeMembership(id, budget.signal)), pool)
  finally:
    budget.cancel()
```

Two structural points that are load-bearing:

- **The ping and the snapshot fetch for one peer stay in that order.** `fetchNeighbors` is
  connection-only (`requireExisting: true`, `src/rpc/neighbors.ts:97`), so it returns an empty
  snapshot unless a connection already exists — and today it is the preceding ping that usually
  opens it. Fusing them per peer preserves that dependency while parallelising *across* peers,
  which is strictly better than today's "all pings, then all fetches". Splitting the phases apart
  and pooling each separately would break it for any peer whose ping lands late.
- **The three candidate *lists* are still selected independently** — `classifyUnknownPeers` keeps
  its Core 8 / Edge 4 budget, and each `reprobeOffRing` arm keeps its own Core 2 / Edge 1. Only
  their *execution* is merged. `docs/fret.md` states the separate-budgets rule explicitly ("so a
  large foreign population cannot starve dead recovery"); merging the candidate lists would
  silently repeal it.

### Anti-starvation ordering

If the tick budget truncates, the tasks that never ran are the *tail* of the list — and since each
pass re-derives the same list in the same order next tick, a fixed order starves the tail
indefinitely. (This is the failure mode `bug-discovery-scan-starves-ring-tail` fixed in the
discovery scan; do not re-introduce it here.)

- `reprobeOffRing` already sorts by ascending backoff factor, and a probed peer's factor grows, so
  it self-rotates.
- `classifyUnknownPeers` currently slices its unknowns in store order (`this.store.list().filter(…)`
  at 1840). Change it to order by **ascending `lastAccess`** (least-recently-touched first) before
  slicing. A probed unknown either succeeds (`applySuccess` updates `lastAccess`) or records backoff
  (dropping it off the candidate list entirely), so it rotates to the back with no new bookkeeping.
- The near-probe list keeps **ring order** (closest neighbour first) deliberately: those four are
  the peers ring correctness depends on most, and rotating them would sometimes skip the immediate
  successor. Truncation there hits the 4th-closest and self-corrects next tick.

## Edge cases & interactions

- **Concurrent scoring of the same peer.** `applySuccess` / `applyFailure` / `applyTouch`
  (`455`–`513`) read an entry, `await selfCoord()`, then write a value derived before the await —
  two chains touching one peer lose an increment (already documented in the NOTE on `applySuccess`,
  and why `applyContactStrike` is deliberately await-free). The four candidate sets are **disjoint
  by construction**: near-probe is live-member-gated (`membership === 'member' && state !== 'dead'`),
  classify is `unknown` and non-`dead`, the foreign arm is `foreign` and non-`dead`, the dead arm is
  `dead`. Assert that disjointness in a test rather than trusting it — it is the invariant that
  makes this ticket safe, and a future selection change could break it silently.
  - Still-reachable interleaving: two *different* peers' snapshot merges can name the **same** third
    peer, so concurrent `applyTouch(pid)` on it is genuinely possible. Harmless (the lost field is
    `accessCount`, feeding a relevance score recomputed on every call), but say so at the site
    instead of leaving it implied.
- **`enforceCapacity` must not run concurrently with itself.** It awaits `selfCoord()`, then lists,
  sorts, and removes; two overlapping runs would sort stale snapshots and can over-evict. Keep it
  out of the pooled tasks — one call after the phase-1 pool drains.
- **`announced` accumulation.** Collected per task and concatenated by the driver; do not let pooled
  tasks push into one shared array *and* trigger the announce, or a peer is announced once per task.
- **Cancelled tasks must not score.** A `skipped` result and an abort-caused rejection are both "we
  gave up", never a contact failure or a backoff. A tick that truncates must leave the routing
  table's health counters untouched.
- **`stop()` mid-tick.** The tick deadline is a child of the run signal, so `stop()` collapses the
  whole tick at once. The existing per-peer `if (this.stopped) break;` guards (1850, 1922) move into
  the pool's signal check; do not silently drop them.
- **Run generation.** The tick already captures `gen` and exits on mismatch; pooled tasks must
  observe the same rule (via the run signal) so a start→stop→start cannot leave a previous run's
  tasks mutating the new run's store.
- **`runSignal` is `undefined` before the first `start()`** (`fret-service.ts:648`). `deadline(ms,
  undefined)` is fine, and several tests drive these methods on a never-started service — do not
  add a non-null assertion.
- **A task that throws synchronously** must be caught by the worker, not escape the pool —
  `probeAndFetch` reaches `peerIdFromString`, which throws on a malformed id. (`runPooled` already
  guarantees this; the note is here so the call site is not re-hardened redundantly.)
- **No timers left behind.** `runPooled` creates none; the tick's `deadline` must be `cancel()`ed in
  a `finally` or the mocha exit watchdog fails the suite.
- **Diagnostics counters** (`diag.pingsSent` / `pingsOk` / `pingsFail` / `snapshotsFetched`, declared
  at `fret-service.ts:305`) are plain `++` on a single-threaded event loop, so concurrency does not
  corrupt them — but a truncated tick now under-counts relative to today. That is correct (the RPCs
  did not happen) and worth a sentence at that declaration.

Harness notes gathered during investigation, so this does not have to be re-derived:

- Every outbound RPC funnels through `openRpcStream` (`src/rpc/protocols.ts:277`), which consults
  `node.getConnections(pid)` first and falls back to `node.dialProtocol`. So a real `createMemNode`
  with `getConnections` overridden to return a stub open connection gives per-peer control of both
  the ping and the fetch in one place — and is the only way to exercise `fetchNeighbors`, which is

  ignores the signal never settles and the deadline cannot unblock the test. Copy `hangsUntilAbort`
  from `test/rpc.protocols.spec.ts:260`.
- Overriding `getConnections` also makes `isConnected` (`1129`) true for every peer, which is what
  these tests want.
- Peers must be real Ed25519 ids (`createMemNode()` then stop, or `peerIdFromPrivateKey(await
  generateKeyPair('Ed25519'))`) — `sendPing`/`fetchNeighbors` call `peerIdFromString` first.
