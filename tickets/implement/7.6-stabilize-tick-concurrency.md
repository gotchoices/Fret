## What the change does (for the reviewer / the spec author)

`stabilizeOnce` used to run four passes serially — ping the 4 nearest live members, fetch a
snapshot from those 4, ping up to Core 8 / Edge 4 `unknown` peers, ping Core 2+2 / Edge 1+1
`foreign` and `dead` peers — so a tick's wall time was the *sum* of 14–20 round trips (bounded at
~60 s Core / 50 s Edge, far past the 1.5 s passive interval; the loop awaits the tick before
re-arming).

Now: one tick-wide `deadline(5000, runSignal)`; two `runPooled` phases at `maintenanceConcurrency`
(Core 6 / Edge 2). Phase 1 chains ping→fetch **per peer** (`fetchNeighbors` is connection-only, and
the ping is what usually opens the connection), pooled across peers. Phase 2 pools the
classification and re-probe *targets*, which are still **selected** under their own independent
budgets/orderings (Core 8 / Edge 4 unknowns by ascending `lastAccess`; Core 2 / Edge 1 per re-probe
arm by ascending backoff factor). Tick expiry aborts in-flight RPCs, `skipped`s the rest, and —
because every task compares against the signal it was handed via `wasCancelled` — records no
strike, no backoff, no `pingsFail`, exactly like a `stop()`. `stop()` collapses the tick at once
(the tick deadline is a child of the run signal). The old per-peer `if (this.stopped) break;`
guards are subsumed by the pool's signal check (`stop()` sets `stopped` and aborts `runAbort`
synchronously together).

Load-bearing invariants (assert, don't trust):

- The four candidate sets are disjoint by construction (near = live member; classify = `unknown`
  non-dead; foreign arm = `foreign` non-dead; dead arm = `dead`), which is what makes pooling safe
  against the lost-increment race on `applySuccess` / `applyFailure`.
- `enforceCapacity` runs once, after phase 1 drains — never inside a pooled task.
- `announced` is per task, concatenated by the driver, announced once.
- The near list keeps ring order (closest first) deliberately; the other lists rotate.

Harness notes (verified):

- Every outbound RPC funnels through `openRpcStream` (`src/rpc/protocols.ts:277`): it throws on an
  already-aborted signal *before* dialing (283), consults `node.getConnections(pid)` first (284)
  and falls back to `node.dialProtocol` (296). So a real `createMemNode` with `getConnections`
  overridden to return a stub open connection (`{ status: 'open', remoteAddr, newStream }`) gives
  per-peer control of both the ping and the fetch in one place — and is the only way to exercise
  `fetchNeighbors`, which is `requireExisting: true` and otherwise returns an empty snapshot.
  Overriding `getConnections` also makes `isConnected` true for every peer, which these tests want.
- Neither `sendPing` nor `fetchNeighbors` *writes* to the stream — they open and read. A stub
  stream needs only `[Symbol.asyncIterator]` yielding one `Uint8Array` (JSON via `encodeJson`)
  then `{ done: true }`, plus a `close()` (`releaseRpcStream` swallows a missing one). Ping reply:
  `{ ok: true, ts: Date.now() }`; snapshot reply: a `NeighborSnapshotV1`
  (`{ v: 1, from, timestamp, successors: [], predecessors: [], sample: [] }`).
- A "hanging" peer stub must **reject when the passed `signal` aborts** — copy `hangsUntilAbort`
  from `test/rpc.protocols.spec.ts:260`. A stub that ignores the signal never settles.
- Stub connection / node shapes: `test/rpc.protocols.spec.ts:34–71`. Dial counting:
  `test/dead-state.spec.ts:815–824`. `cancelRun` / `liveRun` helpers at `dead-state.spec.ts:760–771`
  set `(svc as any).runAbort`.
- Peers must be real Ed25519 ids — `peerIdFromPrivateKey(await generateKeyPair('Ed25519'))` from
  `@libp2p/crypto/keys` / `@libp2p/peer-id` (no node creation needed) — because `sendPing` /
  `fetchNeighbors` call `peerIdFromString` first. Give each a coord via `hashPeerId(pid)`, `upsert`,
  `setMembership(id, 'member')`, and `(svc as any).setAddressKnown(id, true)` so it is dialable.

  `(CoreFretService as any).STABILIZE_TICK_BUDGET_MS = …` (it is `private static readonly`; restore
