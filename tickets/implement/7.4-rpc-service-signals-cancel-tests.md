## The rule under test

`wasCancelled(sig)` (`fret-service.ts` line ~666) is `sig?.aborted === true`, checked against the
signal the **caller** captured before its loop — not the sender's own deadline, which is a *child*
of it and so also fires on a genuine timeout. When it is true the call site records nothing: no
`noteRpcFailure` (hence no contact strike, no relevance decay), no `recordBackoff`, no
`diag.pingsFail`.

### The eight guarded call sites (all verified present)

| Site | line | What it skips when cancelled |
|---|---|---|
| `sendAnnouncementsRateLimited` | ~1240/1251 | `return`s out of the fan-out |
| `preconnectNeighbors` | ~1298/1305 | `return` |
| active-preconnect loop tick | ~1331/1338 | `break` |
| `probeNeighborsLatency` | ~1772/1789 | `return` before `pingsFail++` / `noteRpcFailure` |
| `probeMembership` | ~1921/1937 | `return` before `pingsFail++` / `noteRpcFailure` / `recordBackoff` |
| `mergeNeighborSnapshots` | ~1953/1984 | `break` |
| `routeAct` forward path | ~2219/2239 | skips `noteRpcFailure` + `recordBackoff` |
| `iterativeLookup` (hop + activity resend) | ~2541/2692/2715 | `break` → falls to `yield { type: 'exhausted', hop }` |

`routeAct` is **public** (`async routeAct(msg: RouteAndMaybeActV1)`, line ~2152), so it can be
driven directly — no integration harness needed.

## Tests to add (`packages/fret/test/dead-state.spec.ts`)

Add a new `describe` block. The file already has `coordAt(value)`, and — inside its existing
blocks — `seedPeer` / `strike` / `unspace` helpers and an `unreachablePeer()` factory (~line 675)
that returns a real Ed25519 id nobody holds an address for.

**Get an aborted run signal without starting the service.** A started service runs a stabilization
loop that probes the synthetic peers and makes ping counts non-deterministic — every existing
block in this file constructs the service and deliberately does not start it. Reproduce exactly
the state `stop()` leaves behind:

```ts
/** The state `stop()` leaves behind: a run signal that is already aborted, kept rather than nulled. */
function cancelRun(svc: CoreFretService): void {
    const ac = new AbortController()
    ac.abort(new Error('service stopped'))
    ;(svc as any).runAbort = ac
}
```

That `stop()` really produces this state is asserted separately, in the lifecycle tests
(`7.3-rpc-service-signals-lifecycle-tests`) — so this block does not need to re-prove it.

Tests, each: seed a member peer (dialable via `(svc as any).setAddressKnown(id, true)` where the
site needs it), `cancelRun(svc)`, drive the method, then assert **nothing was scored** —
`contactFailures === 0`, `state !== 'dead'`, `(svc as any).backoffMap.get(id) === undefined`, and
the relevant `getDiagnostics()` counter unchanged.

- `probeNeighborsLatency([id])` — the headline case.
- `probeMembership(id)` — the one that also records backoff on the unguarded path; that is the
  assertion that matters here.
- **Contrast case, so the guard is not over-broad:** the same unreachable peer with the run signal
  *live* and the RPC's own budget firing **does** strike. The existing test "marks an unreachable
  neighbor dead after a run of failed pings" (~line 684) already pins this — **do not weaken it**;
  add one explicit single-strike contrast inside the new block so the pair reads together.
- `mergeNeighborSnapshots([id])` — assert `diag.snapshotsFetched` unchanged and no strike. (This
  site never called `noteRpcFailure`; the guard's job is to `break` instead of warn-spamming the
  rest of the list.)
- `sendAnnouncementsRateLimited([a, b], snap)` — the assertion is that it stops rather than
  burning a token per target. Stub the bucket the way the existing announce test does (~line 643):
  `;(svc as any).bucketAnnounce = { tryTake: () => { takes++; return true } }` and assert
  `takes === 1` plus `diag.announcementsSent` unchanged.
- `preconnectNeighbors()` — `diag.pingsSent` unchanged, no strike.
- `routeAct(msg)` — build a `RouteAndMaybeActV1` whose key is far from self so the not-in-cluster
  forward path is taken, with member+dialable candidates seeded. Assert the reply is a
  `NearAnchorV1` (the honest "did not forward") and the chosen hop was not struck or backed off.
- `iterativeLookup(key, opts)` — drain the generator; assert the **last** yielded progress is
  `{ type: 'exhausted' }` and that no contacted peer gained a strike or a backoff entry. Note it
  also yields `probing` first, so collect all and inspect the tail.

## Open design question — answer it while writing the `iterativeLookup` test

A caller cannot today tell "the ring had no more hops" from "the service shut down under you":
both surface as `exhausted`, and on the activity-resend arm the activity was never delivered.

**Recommended resolution (do this unless you find a reason not to):** document rather than widen
the type. `RouteProgress` (`src/index.ts` line ~79) is part of the public `IFretService` surface
(`iterativeLookup` is declared there at line ~123), so adding a `{ type: 'cancelled' }` variant is
an API change well beyond a test-and-docs ticket, and every existing consumer would have to learn
it. Instead:

- State explicitly in `docs/fret.md` that `exhausted` covers cancellation, and that a caller must
  re-check service state before concluding the ring was exhausted — in particular that an
  undelivered activity is a possible outcome.
- Add a `NOTE:` at the `iterativeLookup` cancellation site naming the same fact, so the next
  reader meets it at the code.

Do not leave it implicit either way.

## Docs (`docs/fret.md`)

- *Stream management* — the bullet currently reads "Stream read deadline: one overall budget per
  read (`readAllBounded`, 5s default, uniform across the four RPCs today)". Restate it as a
  **whole-RPC** budget covering dial + stream open + read (`RPC_TIMEOUT_MS`, exported from
  `src/rpc/protocols.ts`), and name the per-call-site overrides: 2 s on maintenance pings and
  announces (`MAINTENANCE_RPC_TIMEOUT_MS`), 5 s left on `sendMaybeAct` because it is a *route*
  budget not a link one, and `SHUTDOWN_BUDGET_MS` (3 s) / 1.5 s per notice on the leave fan-out.
  Keep the "no per-chunk idle timer" reasoning intact.
- *Stabilization and churn handling* — next to the `deadAfterFailures` discussion, add the rule
  that **our own cancellation is not evidence about the peer**: a run-signal abort (`stop()`, or a
  future per-tick budget) records no contact failure, no backoff, no ping-failure diagnostic; only
  the RPC's own timeout does. Say *why* the caller's signal is the discriminator — the sender's
  deadline is a child of it, so it fires in both cases while the caller's fires only on ours.
- *Service shell & lifecycle (A1)* — one line beside the run-generation paragraph on the
  run-scoped `AbortController`: minted with `runGen` on `start()`, aborted right after the loop
  timers on `stop()` and before the leave fan-out (which carries its own budget, which is why
  aborting does not silence it).
