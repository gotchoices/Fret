## The helper

New `test/helpers/backoff.ts` — the intent is **one** cast in the whole test tree reaching
probe-backoff state, replacing ~28 spread across eight spec files:

```ts
export function backoffOf(svc: unknown): ProbeBackoff
export function setBackoffOf(svc: unknown, pb: ProbeBackoff): void
```

`setBackoffOf` exists because the production field is `readonly`; the cast is test-only and is what
lets a spec install a fake-clock instance. Import `ProbeBackoff` with `import type` where only the
type is needed — `verbatimModuleSyntax` is on (see AGENTS.md).

Don't reintroduce a second cast to reach `ProbeBackoff` internals from a spec. If a spec wants
something the public surface above does not expose, that is a signal the class interface is wrong —
raise it in the handoff rather than casting around it.

## Two cases to add to `probe-backoff.spec.ts`

Both came out of the review of `probe-backoff-class`: they are behaviours the class has today that
the spec describes nowhere.

- **Two failures inside one still-open window escalate.** `record` looks only at whether an entry
  is retained, not at whether its window is still open, so a second failure at the same instant
  doubles `factor` and pushes `until` further out. That is faithful to the service code it was
  extracted from — the >= 500 ms spacing rule guards `contactFailures`, never the backoff map — but
  nothing asserts it, so a future "ignore a failure inside the open window" change would pass the
  suite. Pin today's behaviour.
- **`factor` after `clear` is 0, and the next failure restarts at 1.** The existing `clear` case
  checks `factor` is 0 but never records again, so it does not distinguish "forgotten" from
  "retained at 0". Add the follow-up `record` assertion, mirroring what the retention-expiry case
  already does.
