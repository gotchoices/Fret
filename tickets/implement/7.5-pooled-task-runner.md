### Interface

New `src/utils/pool.ts`, alongside `token-bucket.ts` / `expiring-map.ts` / `deadline.ts` (match
`deadline.ts`'s doc-comment density — it is the closest sibling in size and role):

```ts
export type PoolResult<T> =
	| { status: 'fulfilled'; value: T }
	| { status: 'rejected'; reason: unknown }
	/** Never started — the pool's signal aborted before a worker reached it. */
	| { status: 'skipped' };

export interface PoolOptions {
	concurrency: number;
	signal?: AbortSignal;
}

/**
 * Run `tasks` with at most `concurrency` in flight. Never rejects; results are
 * index-aligned with `tasks`.
 */
export function runPooled<T>(
	tasks: ReadonlyArray<() => Promise<T>>,
	opts: PoolOptions
): Promise<Array<PoolResult<T>>>;
```

Index-aligned results (rather than `Promise.allSettled`'s array over a filtered subset) are what
let a caller attribute a result back to its peer, which every intended call site needs.

`skipped` is a distinct status rather than a rejection because it is **not** evidence about the
peer — the same rule the RPC cancellation work established (see *Our own cancellation is not
evidence about the peer* in `docs/fret.md`), restated in the type so a caller cannot score a peer
we never contacted.

### Shape

A shared index cursor plus `min(concurrency, tasks.length)` worker loops; each worker checks
`signal.aborted` before pulling the next index and marks that index `skipped` rather than running
it. Because every worker keeps draining the cursor, the returned array is always dense and always
`tasks.length` long, even after an abort.

- `concurrency` is clamped to ≥ 1, and a non-finite value (`NaN`, `Infinity`) clamps to 1 as well —
  `ExpiringMap`'s capacity clamp is the precedent for treating "unbounded" as unwritable.
- No timers of its own. Cancellation is entirely the caller's signal.
- A task that throws **synchronously** (before returning a promise) must be caught by the worker,
  not escape the pool. The intended caller has one — `peerIdFromString` throws on a malformed id
  from the first line of `sendPing`.

### Tests — `test/pool.spec.ts`

The repo already uses `fast-check`; see `test/nexthop-cost.spec.ts` and
`test/peer-discovery.spec.ts` for the house pattern of asserting on the *generated distribution*
so the interesting region is provably reached.

- Never exceeds `concurrency`: instrument tasks with an in-flight counter and assert the observed
  maximum, as a `fast-check` property across task counts and resolution orders — assert on the
  distribution so the `tasks > concurrency` region is provably exercised.
- Results are index-aligned and carry the right status for a mix of resolving, rejecting, and
  synchronously-throwing tasks.
- Aborting mid-run: already-started tasks settle, the remainder are `skipped`, the returned array
  is still full length, and the call never rejects.
- `concurrency` of 0, negative, or non-finite is clamped to 1; empty task list resolves to `[]`
  without spawning workers.
- No stray timers: the suite must exit clean under the repo's mocha exit watchdog.
