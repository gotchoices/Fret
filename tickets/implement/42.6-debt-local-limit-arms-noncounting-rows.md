## Edge cases & interactions

- **Driving `cancelled` needs the caller's own signal to have fired**, not the RPC deadline — those
  are different outcomes (`cancelled` vs `timeout`). The sender builds its deadline as a *child* of
  the caller's signal, so aborting the caller's controller before the call fires the child with it.
  The spec's private-surface cast already exposes signal-taking passes (`probeNeighborLatency`,
  `probeMembership`) to drive this through.
- **Driving `skipped`** means a dial mode that yields no stream (`dial: 'never'` / `if-addressed`
  with nothing dialable), not a broken dial — a broken dial is `unreachable`. Note the spec's rig
  dials the remote in its `before`, so a `dial: 'never'` request against that peer finds a live
  connection and succeeds; the row needs a peer with no open connection.
- Do not weaken any assertion the counting rows already make in order to share a helper between the
  two row kinds. A shared helper that only checked "counter did not decrease" would make the
  counting rows vacuous.
- The existing rows use `REFUSALS` (4) drives per row with `rewindSpacing()` between them, to
  defeat the 500 ms contact-failure spacing guard; the non-counting rows should follow the same
  shape so a booked strike would provably have reached `dead`.

### `rpcRequest` has **two** cancellation exits, and they are not equally strong

`packages/fret/src/rpc/request.ts`:

- **Entry exit** — `if (opts.signal?.aborted === true) return { kind: 'cancelled' }`, sitting inside
  the `try` right after `deadline()` is armed. This fires *before any dial is issued*, so the
  outbound stream cap never gets a chance to refuse. Passing an already-aborted controller to
  `probeNeighborLatency(peerId, ac.signal)` therefore takes this exit: the row would assert
  "`diag.streamLimit` unchanged" against a call where **no stream was attempted at all**, which is
  much closer to the `skipped` row than to the case the ticket wants.
- **`classify` exit** — `classify(err, callerSignal, deadlineSignal)` tests `callerSignal?.aborted`
  as its *first* line, ahead of the `isStreamLimitError` arm. This is the exit the ticket is aiming
  at: the ceiling really refuses, the error really is `TooManyOutboundProtocolStreamsError`, and it
  is still classified `cancelled`, so `countStreamLimit` is never reached. This is the arm a naive
  "count it wherever we see a stream error" implementation over-counts.

**Unsolved: how to land the abort deterministically between those two exits.** The window is
narrow and the next run must pick a shape and state it in the spec's comment rather than leave it
to timing:

- `openRpcStream` (`src/rpc/protocols.ts:712`) *also* opens with
  `if (opts.signal?.aborted === true) throw abortReasonError(opts.signal)`, and the signal it is
  handed is `d.signal` — a child of the caller's — so an abort arriving between the two exits
  surfaces as an abort error, not as the stream-limit error. `classify` still answers `cancelled`
  and `streamLimit` still does not move, so the *assertions* hold either way; what varies is
  whether the row proves the strong claim (a real refusal suppressed by cancellation) or the weak
  one (a cancelled call counts nothing).
- Options to weigh, in rough order of preference: (a) assert on the outcome only — drive the row
  through a private surface that returns the `RpcOutcome` so the spec can require `kind ===
  'cancelled'` *and* `streamLimit` unchanged, and say in the comment that which error was
  suppressed is not pinned; (b) hand `rpcRequest` a hand-rolled `AbortSignal`-shaped object whose
  `aborted` getter reads false once and true after — deterministic, but it is a fake signal, which
  the rest of this spec deliberately avoids (every other row forces a *real* refusal); (c) find a
  seam where the cap fires first and the abort lands during the `finally`. (b) trades away the
  spec's stated "no hand-written outcomes" discipline, so prefer (a) unless it turns out the
  private surfaces all swallow the outcome.
