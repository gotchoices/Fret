## What to build

### The two non-counting rows

Extend the existing spec's table rather than starting a new file. Both rows assert the same
peer-state invariants the counting rows already do (no `contactFailures`, no `failureCount`,
unchanged `relevance` / `membership` / `state`, no `ProbeBackoff` entry) **plus** `diag.streamLimit`
unchanged — the delta is the counter, so that assertion must be a strict equality against the
pre-call reading, never a "did not decrease".

- **`cancelled` must stay distinguishable from `local-limit`.** `classify` (`src/rpc/request.ts`,
  the `callerSignal?.aborted` check at the top) tests the caller's signal first, so a refusal
  landing during a `stop()` classifies `cancelled` and `diag.streamLimit` does **not** increment.
  This is the case a naive "count it wherever we see a stream error" implementation over-counts,
  which is what makes the row worth its weight.
- **`skipped` never reaches the counter either** — the dial *mode* forbade dialing, so no stream
  was ever attempted.

## Edge cases & interactions

- **Driving `cancelled` needs the caller's own signal to have fired**, not the RPC deadline — those
  are different outcomes (`cancelled` vs `timeout`). The sender builds its deadline as a *child* of
  the caller's signal, so aborting the caller's controller before the call fires the child with it.
  The spec's private-surface cast already exposes signal-taking passes (`probeNeighborLatency`,
  `probeMembership`) to drive this through.
- **Driving `skipped`** means a dial mode that yields no stream (`dial: 'never'` / `if-addressed`
  with nothing dialable), not a broken dial — a broken dial is `unreachable`. Note the spec's rig
  dials the remote in its `before`, so a `dial: 'never'` request against that peer finds a live
  connection and succeeds; the row needs a peer with no open connection.
- Do not weaken any assertion the counting rows already make in order to share a helper between the
  two row kinds. A shared helper that only checked "counter did not decrease" would make the
  counting rows vacuous.
- The existing rows use `REFUSALS` (4) drives per row with `rewindSpacing()` between them, to
  defeat the 500 ms contact-failure spacing guard; the non-counting rows should follow the same
  shape so a booked strike would provably have reached `dead`.

### Both rows drive `sendPing` directly and hand the outcome to the observing site

The spec's existing table already has this shape — the row named *"the shared noteRpcFailure seam
the five inheriting sites route into"* calls `sendPing(...)` and passes the returned `RpcOutcome`
into `priv().noteRpcFailure(peerId, out)`. The two non-counting rows are the same shape with a
different outcome, so they need **no** new private surface and no widening of the `priv()` cast.
This is option (a) from the previous note ("assert on the outcome only"), and it turns out to need
no service pass at all — `sendPing` *returns* the outcome, so the row can require the exact `kind`
before scoring it.

Say in each row's comment that it is one of the two rows that does not go through a service pass,
and (for the `cancelled` row) that *which* error was suppressed is deliberately not pinned.

- **`cancelled` row.** Mint an `AbortController`, abort it, then
  `await sendPing(local, peerId, P.PROTOCOL_PING, { timeoutMs: 2000, signal: ac.signal })`, assert
  `out.kind === 'cancelled'`, then `await priv().noteRpcFailure(peerId, out)`. That takes
  `rpcRequest`'s **entry** exit (`if (opts.signal?.aborted === true) return { kind: 'cancelled' }`,
  inside the `try` right after `deadline()` is armed) rather than the `classify` exit, so no stream
  is opened. The previous note flagged that as "closer to the `skipped` row than to the case the
  ticket wants" — it is, and it is still the row worth having, because what the row pins is that
  the **outcome** `cancelled` counts nothing at `noteRpcFailure`, which is the arm a naive "count
  it wherever we see a stream error" implementation gets wrong. Chasing the narrow window between
  the two exits was the thing that ate two runs' budget; do not chase it a third time. Instead,
  state the residual in the spec comment: *the row pins the outcome, not which error was
  suppressed; the `classify` exit (a real refusal reclassified `cancelled` because the caller's
  signal fired first) is not driven by any row.* That residual also belongs in the docs sentence
  as an unpinned arm, alongside the two already declared there.
- **`skipped` row.** Third node: a bare `createMemNode()` that is **never dialed**, with just
  `store.upsert(id, await hashPeerId(node.peerId))` + `store.setMembership(id, 'member')`.
  `dial: 'never'` maps to `requireExisting: true`, `openRpcStream` returns `undefined` with no open
  connection, and `rpcRequest` returns `{ kind: 'skipped' }` — needs no address, so the node need
  not be reachable. Then hand that outcome to `priv().noteRpcFailure(thirdId, out)`.
  Assert against the **third** peer's entry, not the capped remote's.
  Remember to `stopAll` it in `after`.

### Row placement and assertion shape

Both rows sit **outside** the existing `arms` table, in their own `describe` block — the table's
rows are all driven twice (control pass then capped pass) and both of these rows want neither: no
cap is involved, and there is nothing to control against. Put the block **after** the capped block
so it cannot perturb the table's diagnostics deltas, and read `svc.getDiagnostics()` immediately
before each row's own loop.

Assertions per row, over `REFUSALS` (4) drives with `rewindSpacing()` between them, same as the
table: `contactFailures === 0`, `state !== 'dead'`, `membership` / `relevance` / `failureCount` /
`successCount` unchanged against a pre-loop copy of the entry, `negotiateFailures === 0`,
`backoffOf(svc).factor(id) === 0`, and — the delta that makes these rows non-counting —
`after.streamLimit - before.streamLimit === 0`, a **strict equality** against the pre-call reading,
never a "did not decrease". Note `rewindSpacing()` writes `lastContactFailureAt` on `peerId`; the
`skipped` row needs its own rewind against the third peer's id (or just inline
`store.update(thirdId, { lastContactFailureAt: 0 })`).

Do not share a helper with the counting rows: a helper checking only "counter did not decrease"
would make the counting rows vacuous.
