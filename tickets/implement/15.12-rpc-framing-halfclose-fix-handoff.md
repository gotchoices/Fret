## Root cause — CONFIRMED by repro (run 9). Do not re-investigate.

Repro (handler `stream.send(partialFrame); await stream.close()`; dialer never writes, iterates
raw stream) showed: partial chunk delivered at +41ms, then the dialer's raw stream async
iterator NEVER ends — watchdog at +8s sees `status open, write writable, read closed`.

Mechanism, from `node_modules/@libp2p/utils/dist/src/abstract-message-stream.js`:
- The stream's `[Symbol.asyncIterator]` (line ~81) ends its pushable off the one-shot
  `remoteCloseWrite` / `close` **events**, subscribed when iteration *starts*.
- A fast responder's FIN is processed while the dialer is still inside `openRpcStream`, before
  any listener exists → `onRemoteCloseWrite` (line ~293) dispatches `remoteCloseWrite` into the
  void. The stream stays `open` (our write end never closed), so no `close` event ever comes.
- Buffered data IS delivered later (message dispatch is deferred until a listener attaches), and
  the dispatch-finally then sets `readStatus = 'closed'` **silently** (line ~406–408, no event).
- Result: `lp.decode`'s pending `next()` in `readFramed` never settles; the read sits the whole
  5 s deadline. Ping test then trips its own deadline util (`DeadlineExpiredError`), snapshot
  test blows the promptness budget.

This is a FRAMING REGRESSION, not pre-existing: pre-framing `readAllBounded` (see
`git show 14c2444:packages/fret/src/rpc/protocols.ts`) carried a deliberate workaround for this
exact lost event — a 20 ms EOF poll (`EOF_POLL_MS`, `POLL_TICK` sentinel) racing the read, whose
`remoteFinishedWriting(stream)` duck-type check recognised "end-of-stream whose event we never
received". The framing migration (f5f2eb6) deleted `readAllBounded` and dropped the poll. The
old doc comment even flagged this: "the durable fix is to subscribe before writing so the event
is never missed at all (see the framing/iterator-priming arm on tickets/plan/8-rpc-shared-helper)"
— the framing ticket shipped without the priming, and without the poll.

## The fix (designed run 9, not yet applied) — restore the EOF poll inside `readFramed`

In `packages/fret/src/rpc/protocols.ts`:

- Re-add from 14c2444 (adapt doc comments): `EOF_POLL_MS = 20`, a `POLL_TICK` symbol
  (`Symbol('readFramed.poll')`), the `ReadEndState` interface, and `remoteFinishedWriting`:

```ts
interface ReadEndState {
	readBufferLength?: number;
	remoteWriteStatus?: string;
	readStatus?: string;
}
function remoteFinishedWriting(stream: unknown): boolean {
	const s = stream as ReadEndState | null;
	if (typeof s?.readBufferLength !== 'number') return false;
	if (s.readBufferLength > 0) return false;
	return s.remoteWriteStatus === 'closed' || s.readStatus === 'closed';
}
```

- Restructure `readFramed`'s single race into a poll loop (old `readAllBounded` shape). The
  `TIMED_OUT` sentinel becomes unused — delete it; the deadline is enforced at loop top and the
  poll interval is `Math.min(remaining, EOF_POLL_MS)`, so overshoot ≤ 20 ms. Keep the exact
  timeout message `read timed out after ${timeoutMs}ms` (asserted in tests). Sketch:

```ts
	const deadlineAt = Date.now() + timeoutMs;
	const pending = iter.next();
	pending.catch(() => {});   // keep the belt-and-braces NOTE comment
	type RaceResult = IteratorResult<Uint8ArrayList> | typeof POLL_TICK | typeof ABORTED;
	try {
		while (true) {
			const remaining = deadlineAt - Date.now();
			if (remaining <= 0) throw new Error(`read timed out after ${timeoutMs}ms`);
			let timer: ReturnType<typeof setTimeout> | undefined;
			const poll = new Promise<typeof POLL_TICK>((resolve) => {
				timer = setTimeout(() => resolve(POLL_TICK), Math.min(remaining, EOF_POLL_MS));
			});
			const racers: Array<Promise<RaceResult>> = [pending, poll];
			if (abortWait != null) racers.push(abortWait);
			let result: RaceResult;
			try {
				result = await Promise.race<RaceResult>(racers);
			} catch (err) {
				// keep the existing InvalidDataLengthError → payload-too-large translation
				...
			} finally {
				clearTimeout(timer);
			}
			if (result === ABORTED) throw abortReasonError(signal!);
			if (result === POLL_TICK) {
				if (remoteFinishedWriting(stream)) {
					throw new FrameTruncationError('stream ended before a whole framed message arrived');
				}
				continue;
			}
			if (result.done === true) {
				throw new FrameTruncationError('stream ended before a framed message arrived');
			}
			return result.value.subarray();
		}
	} finally {
		if (onAbort != null && signal != null) signal.removeEventListener('abort', onAbort);
	}
```

Why this is race-free (state it in the readFramed doc comment): the poll fires on a macrotask
≥ 20 ms after any message dispatch, so all microtasks (stream iterator → `lp.decode` → pending
resolution) have drained; if `readStatus === 'closed'` (only set after the read buffer fully
dispatched AND remote write closed) and `pending` is still unresolved, the buffered bytes could
not complete a frame — genuine truncation. A merely-slow stream reports neither a closed remote
nor an empty-final buffer, so it keeps being read (no idle-timer regression). Plain async
iterables (stub tests) have no `readBufferLength` → `remoteFinishedWriting` returns false →
behavior unchanged. Keep the old NOTE about the poll adding up to one interval of floor under
measured ping RTT.

Effects: the two group-B tests should pass promptly (`sendPing` maps `FrameTruncationError` via
`isFrameTruncationError` → `{ok:false}`; `fetchNeighbors` → empty snapshot). The passing reset
test is unaffected (reset dispatches a `close`-path event into an attached iterator).
