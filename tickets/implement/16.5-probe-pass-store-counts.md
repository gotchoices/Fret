### What this ticket adds

O(1) per-label counts inside `DigitreeStore`:

```ts
// in DigitreeStore
private readonly membershipCounts = new Map<MembershipState, number>();
private readonly stateCounts = new Map<PeerState, number>();

/** How many entries currently carry `m`. O(1). */
countByMembership(m: MembershipState): number;
/** How many entries currently carry `s`. O(1). */
countByState(s: PeerState): number;
```

Nothing reads them yet — the reader is the follow-on ticket. That is deliberate: the counts are
inert bookkeeping until half 2 gates on them, so landing them alone cannot change behaviour.

### Why the counts live in the store (settled)

**Verified by reading the file at this commit, not assumed:**

- `put` (`digitree-store.ts` ~line 190) is the **only** insert/replace path. `upsert` (~206),
  `update` (~233), `setState` (~264), `setMembership` (~268) and `importEntries` (~503) all funnel
  through it — `setState` / `setMembership` delegate to `update`, which builds `{ ...cur, ...patch }`
  and calls `put`; `importEntries` calls `this.put(entry)` once per record after decoding every
  coordinate up front. **Nothing mutates an entry in place.** Every label change in `src/` is built
  as a patch object and handed to the store.
- `remove` (~246) is the only delete path.

So the counts are derivable at exactly two sites and cannot drift — the "make the bad state
unrepresentable" rung, rather than a hand-maintained tally in `FretService` keyed off every call
site that flips a label.

**The network-agnostic rule is not violated.** `docs/fret.md` says the store "stores and exposes
both fields and never branches on them" — and the class doc-comments on `MembershipState` /
`negotiateFailures` / `contactFailures` repeat it. A tally over a field the store already owns is
bookkeeping, not policy: the store never asks *whether* a label means anything, and the API takes
the label as a **parameter** rather than privileging a particular value. Say this in a comment at
the counters, in one sentence — the next reader will ask.

### Maintenance rule

Maintained at the two seams and nowhere else:

- `put`: read the previous entry **by id** (`getById(entry.id)`) before writing; if present,
  decrement its `membership` and `state` tallies; then increment the new entry's. A re-key is
  therefore net-zero when the labels are unchanged, and a same-key replace is handled by the same
  code path — there is no coordinate-move special case, exactly as `put` already has none. The
  decrement/increment pair must bracket the **whole** `put` body (a coordinate change is a
  drop-and-place inside it), not just the insert.
- `remove`: decrement the removed entry's tallies.

Do **not** add a third maintenance point. If you find yourself needing one, the seam assumption
broke and this needs re-planning, not a patch.

### Edge cases

- **Self is counted like any other entry.** It is seeded `member` and never marked dead. A
  single-node store must report 0 for `unknown` / `foreign` / `dead` and must not underflow.
- **Counts on an empty store are 0 for every label**, and removing an absent id is a no-op that
  never goes negative.
- **`importEntries` replaces by id**, including replacing an existing entry that carries *different*
  labels. It routes through `put` per record, so the seam covers it — but assert it rather than
  assuming.
- **`stop()` / restart leaves the store instance and its entries in place** (`fret-service.ts:166`
  is a `readonly` field, never cleared), so counts stay consistent trivially. No work here; just
  don't add a reset that clears one structure and not the other.
- **Entries handed out by `getById` / `list` are live references**, so a future caller that mutated
  a label in place would corrupt the counts silently. No such site exists today (verified by grep
  over `src/`). Leave a one-line `NOTE:` at the counters saying the counts assume all writes go
  through the seam; the property test below is what catches a future one.
- **A count wrong in the *low* direction is a correctness bug once half 2 lands, not a perf
  regression** — it makes a probe pass silently stop selecting, and a dead peer that is never
  re-probed never recovers. Aim the tests at the low direction.

  builder (~152) and the wrap-around walks (~310–395) — different functions from the write seam;
  expect no conflict.
