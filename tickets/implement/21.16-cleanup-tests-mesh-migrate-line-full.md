export type Topology = 'star' | 'line' | 'full'
export async function buildMesh(count: number, opts?: { factory?: NodeFactory }): Promise<Mesh>

interface Mesh {
	readonly nodes: Libp2p[]
	readonly ids: string[]            // nodes[i].peerId.toString(), precomputed
	readonly services: FretService[]  // empty until addServices()
	connect(topology: Topology): Promise<void>

`connect('line')` delegates to the existing `connectLine` in `helpers/libp2p.ts` rather than
re-implementing it, so the dial direction is unchanged: node `i` dials node `i-1`.
`connect('full')` dials `nodes[i] -> nodes[j]` for every `j > i`, matching the nested loop in
`proactive-announce.spec.ts` today.

## Site-by-site notes — `proactive-announce.spec.ts`

All four rigs construct services **first**, then dial. Preserve that: dialing after `start()`
means the ring is discovered through `peer:connect`, and several specs in the suite comment
that this ordering is deliberate. It is the one way this refactor can silently change behaviour.

- **`:19-33`** — 3 nodes, services, then a genuine **line**. This is the only real line loop the
  original survey found (it also listed three other files as "line", but they are stars and
  belong to the sibling ticket). → `connect('line')`.
- **`:51-66`** — 5 nodes, services, then **full mesh**, and node 2 is stopped mid-test so
  teardown skips it. → `connect('full')` and `mesh.stop({ skip: [2] })`.
- **`:96-125`** — two independent 6-node meshes (edge and core) whose node creation, service
  construction and full-mesh dialing are all *interleaved* in shared loops. This is the rig that
  gains most: it becomes two `buildMesh(6)` calls, each with its own `addServices` and
  `connect('full')`. Interleaving is not load-bearing — the two meshes never touch — but say so
  in the handoff, since un-interleaving is the one non-mechanical judgement in this ticket.
- **`:158-174`** — 4 nodes, services, then an **unrolled line** (`1->0`, `2->1`, `3->2`).
  → `connect('line')`.
