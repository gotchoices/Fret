## The settled rule

**Frequency counts proven contact. Being named by someone else creates an entry and nothing
more.** A gossiped id we hold no entry for is created and given a one-off baseline score from its
own (empty) counters. An id we already hold is left **completely alone** — same score after a
thousand mentions as after one. So mention count is not a lever an attacker (or a chatty honest
peer) can pull.

### Why a baseline rather than "gossip gets nothing at all"

The obvious minimal fix — make the merge paths a bare `upsert` with no scoring, matching the rule
already documented for leave-notice replacements — **starves discovery at capacity**. Stored
relevance is only ever written by a scoring call, so a never-scored entry sits at `relevance = 0`;
`enforceCapacity` sorts ascending and evicts the lowest unprotected entry, so on a full table
every newly discovered peer is evicted before the classification pass can probe it, and the table
can never learn a new peer again. A fixed baseline avoids that while still being flat in mention
count, which is the property the leave-replacement rule actually wanted.

## Shape

```ts
/**
 * Record that some *other* peer named this id. Creates the entry with a one-off baseline
 * score; an id we already hold is left untouched, so mention count is not a score lever.
 */
private async noteDiscovered(id: string, coord: Uint8Array): Promise<void>
```

Body sketch (verified against the store API at HEAD):

- return immediately if `id === this.selfIdStr` — self is seeded `member` and its local entry is
  authoritative (same reasoning as `importTable` dropping self's record).
- return immediately if `this.store.getById(id)` already exists — **no `upsert`**. `upsert`
  refreshes `lastAccess`, which is both the recency input *and* the ordering key for the
  unknown-classification probe rotation ("ascending `lastAccess`"); refreshing it on gossip would
  sink a heavily-gossiped unknown peer to the back of its own probe queue.
- otherwise `const entry = this.store.upsert(id, coord)` (returns the created `PeerEntry`), then
  `const x = normalizedLogDistance(await this.selfCoord(), coord)`, then
  `this.store.update(id, { relevance: initialRelevance(entry, x, this.sparsity) })`.
- **No `try`/`catch`.** A wrong-width coordinate throws at the store's write seam by design, and
  the merge loops' existing per-entry `try`/`catch` must still see it.

Returning `boolean` ("newly created") instead of `void` is a reasonable improvement — the four
merge call sites each currently do their own `if (!this.store.getById(pid))` lookup purely to
build the `discovered` / `announced` array, and the boolean would fold that into one lookup. Take
it or leave it; if taken, say so in the review handoff.

## Edge cases & interactions

- **Lost-increment race.** `applySuccess` reads, awaits `selfCoord()`, then writes a value derived
  before the await; two concurrent chains lose one increment. `accessCount` now rides that same
  path. Same tolerance as `successCount` — these counters only feed a score recomputed on every
  call — but the existing NOTE on `applySuccess` names the counters explicitly and must name this
  one too. Do **not** make it read-modify-write; the pooled tick's candidate sets are disjoint by
  construction (`docs/fret.md`, *Stabilization and churn handling*).
- **Import/export.** `accessCount` is already in `SerializedPeerEntry`; no schema change. An
  imported entry keeps its `accessCount`, which now means "contacts", not "mentions" — so a
  pre-change snapshot restores inflated frequency. Acceptable and self-correcting (relevance is
  rewritten on the next scoring call); state it in the review handoff rather than adding a
  migration.
- **Dead / foreign peers.** Rule 2 of the prereq ticket (failures accrue no frequency) means a
  peer stuck in the dead re-probe arm no longer climbs.

## Tests

In `test/relevance.properties.spec.ts` (fixed clock `FIXED_NOW`, fixed `x`, fresh model per call):

- `recordSuccess` × 500 scores **strictly above** an entry created by `noteDiscovered` and then
  named 500 more times. (Today: below — the reported inversion.) Express the gossip side as
  `initialRelevance` once + nothing thereafter, since `noteDiscovered` is private to the service.
- `noteDiscovered` × 500 == `noteDiscovered` × 1, exactly — flat in mention count. At the unit
  level this is the same statement; assert it at the **service** level instead, by merging the
  same announce snapshot 500 times and reading the stored relevance, so the flatness is pinned on
  the wired path rather than on the function.

In `test/relevance.eviction.spec.ts` — a service-level eviction test: a peer with many recorded
successes must **survive** a capacity squeeze against a never-contacted peer named in many
snapshots. That is the user-visible half the plan ticket could only measure at the function level.
`enforceCapacity` compares *stored* scores taken under different KDE states, so hold the model
fixed or assert an ordering robust to it (the plan ticket measured 1.0449 vs 0.8619 on a shared
model: same ordering, lower magnitudes).

That spec already has everything the rig needs — build on these rather than a fresh one:
`seededService({m, capacity})` (starts then immediately stops, so no tick scores underneath the
assertions), `place(svc, peers)` for direct store writes, `enforce(svc)` (an empty `importTable`
purely to trigger the private `enforceCapacity`), `survivors(svc)`, and the `ringOffset` /
`serializedPeer` / `tableOf` helpers.
