----
description: The background maintenance cycle contacts each neighbor one at a time, so one slow or unresponsive peer delays every other peer in the cycle; run them side by side with a cap on how many at once, and give the whole cycle an overall time limit.
prereq: rpc-abort-deadlines
files: packages/fret/src/utils/pool.ts (new), packages/fret/src/service/fret-service.ts, packages/fret/test/pool.spec.ts (new), packages/fret/test/stabilize-concurrency.spec.ts (new)
difficulty: medium
----

`stabilizeOnce` (`service/fret-service.ts:1637`) runs four passes, each a plain `for` loop
with an `await` inside, so every RPC waits for the one before it:

| pass | RPCs per tick (Core / Edge) |
|---|---|
| `probeNeighborsLatency` — ping the 4 nearest live members | 4 / 4 |
| `mergeNeighborSnapshots` — fetch a snapshot from those same 4 | 4 / 4 |
| `classifyUnknownPeers` — ping unclassified peers | 8 / 4 |
| `reprobeExcludedPeers` — ping `foreign` (2/1) then `dead` (2/1) | 4 / 2 |
| **total** | **20 / 14** |

Serial execution means the tick's wall time is the *sum* of 14–20 round trips. With
`rpc-abort-deadlines` landed each of those is individually bounded (2 s for a ping, 5 s for a
snapshot fetch), so the tick is bounded at roughly 60 s Core / 50 s Edge — bounded, but far
past the 1.5 s passive tick interval, and the loop awaits the tick before re-arming.

Expected behavior: a maintenance tick completes in bounded, *useful* time — on the order of
the slowest single peer rather than the sum of all of them — and a peer that hangs delays
nobody else.

### Bounded-concurrency pool

New `src/utils/pool.ts`, alongside `token-bucket.ts` / `expiring-map.ts` / `deadline.ts`:

```ts
export type PoolResult<T> =
	| { status: 'fulfilled'; value: T }
	| { status: 'rejected'; reason: unknown }
	/** Never started — the pool's signal aborted before a worker reached it. */
	| { status: 'skipped' };

export interface PoolOptions {
	concurrency: number;
	signal?: AbortSignal;
}

/**
 * Run `tasks` with at most `concurrency` in flight. Never rejects; results are
 * index-aligned with `tasks`.
 */
export function runPooled<T>(
	tasks: ReadonlyArray<() => Promise<T>>,
	opts: PoolOptions
): Promise<Array<PoolResult<T>>>;
```

Index-aligned results (rather than `Promise.allSettled`'s array over a filtered subset) are
what let a caller attribute a result back to its peer, which every call site here needs.
`skipped` is a distinct status rather than a rejection because it is **not** evidence about
the peer — the same rule `rpc-abort-deadlines` establishes for cancellation, restated in the
type so a caller cannot score a peer we never contacted.

Shape: a shared index cursor plus `min(concurrency, tasks.length)` worker loops; each worker
checks `signal.aborted` before pulling the next index and marks the remainder `skipped`.
`concurrency` is clamped to ≥ 1. No timers of its own — cancellation is the caller's
`deadline`.

### Concurrency bound

One private getter on `FretService`:

```ts
/** Max outbound maintenance RPCs in flight. Core 6 / Edge 2 — the pre-dial concurrency
 *  the Operating profiles section of docs/fret.md already states for each profile. */
private get maintenanceConcurrency(): number { return this.cfg.profile === 'core' ? 6 : 2; }
```

These are the numbers `docs/fret.md` *Operating profiles* already commits to ("max 4–6
concurrent" Core, "max 2 concurrent" Edge) — reused rather than re-invented. Edge's 2 is
deliberately conservative and does mean an Edge tick under mass failure truncates on the
tick budget more often than a Core one; that is the profile's stated posture ("conservative
pre-dial budget… fewer probes per window"), not an oversight.

### Tick budget

`private static readonly STABILIZE_TICK_BUDGET_MS = 5000;`

`stabilizeOnce` opens `deadline(STABILIZE_TICK_BUDGET_MS, this.runSignal)` at the top and
`cancel()`s it in a `finally`. That signal goes to every pooled call *and* to every RPC in
the tick (as the `signal` option added by `rpc-abort-deadlines`), so when the budget expires:
in-flight RPCs abort, not-yet-started tasks come back `skipped`, and the tick returns.

5000 ms is chosen as the same magnitude as the single-RPC default budget: a tick may be
consumed by one round of slow peers, never by several rounds of them. Skipped work is not
lost — the next tick (1.5 s passive / 300 ms active) re-derives its candidates from the
store and picks it up.

NOTE-worthy at the code site: active mode ticks every 300 ms, so a 5 s budget makes active
stabilization effectively continuous under failure. That is true today as well (the loop
awaits the tick before re-arming); tighten the budget per-mode only if warm-up latency ever
measurably suffers.

### Restructured tick

```
stabilizeOnce():
  sweepBoundedMaps()
  budget = deadline(STABILIZE_TICK_BUDGET_MS, runSignal)
  try:
    near = live-member neighbours, dialable, self excluded, ring order, first 4
    # Phase 1: per-peer chain — ping THEN fetch for the same peer.
    results = runPooled(near.map(id => () => this.probeAndFetch(id, budget.signal)), pool)
    enforceCapacity(); announceToNewPeers(flatten(results))
    # Phase 2: classification + re-probe arms, pooled together.
    targets = [...classifyTargets(), ...foreignTargets(), ...deadTargets()]
    runPooled(targets.map(id => () => this.probeMembership(id, budget.signal)), pool)
  finally:
    budget.cancel()
```

Two structural points that are load-bearing:

- **The ping and the snapshot fetch for one peer stay in that order.** `fetchNeighbors` is
  connection-only (`requireExisting: true`), so it returns an empty snapshot unless a
  connection already exists — and today it is the preceding ping that usually opens it. Fusing
  them per peer preserves that dependency while parallelising *across* peers, which is
  strictly better than today's "all pings, then all fetches". Splitting the phases apart and
  pooling each separately would break it for any peer whose ping lands late.
- **The three candidate *lists* are still selected independently** — `classifyUnknownPeers`
  keeps its Core 8 / Edge 4 budget, and each `reprobeOffRing` arm keeps its own Core 2 /
  Edge 1. Only their *execution* is merged. `docs/fret.md` states the separate-budgets rule
  explicitly ("so a large foreign population cannot starve dead recovery"); merging the
  candidate lists would silently repeal it. Refactor each pass to return its target ids
  rather than performing the probes, and let the tick drive them.

`mergeNeighborSnapshots` becomes a per-peer `fetchAndMergeSnapshot(id, signal):
Promise<string[]>` returning the newly-announced ids; the tick concatenates them and does one
`enforceCapacity()` and one `announceToNewPeers(...)`, exactly as the loop does today.

### Anti-starvation ordering

If the tick budget truncates, the tasks that never ran are the *tail* of the list — and since
each pass re-derives the same list in the same order next tick, a fixed order starves the
tail indefinitely. (This is the failure mode `bug-discovery-scan-starves-ring-tail` just
fixed in the discovery scan; do not re-introduce it here.)

- `reprobeOffRing` already sorts by ascending backoff factor, and a probed peer's factor
  grows, so it self-rotates.
- `classifyUnknownPeers` currently slices its unknowns in store order. Change it to order by
  **ascending `lastAccess`** (least-recently-touched first) before slicing. A probed unknown
  either succeeds (`applySuccess` updates `lastAccess`) or records backoff (dropping it off
  the candidate list entirely), so it rotates to the back with no new bookkeeping.
- The near-probe list keeps **ring order** (closest neighbour first) deliberately: those four
  are the peers ring correctness depends on most, and rotating them would sometimes skip the
  immediate successor. Truncation there hits the 4th-closest and self-corrects next tick.

### Also pooled

Both warm-up paths are the same serial-dial-chain shape and take the same treatment:

- `preconnectNeighbors` (`~1201`) — up to 12 serial pings at `start()`; this is precisely the
  "serial dial chain" the *Active vs passive state* section of `docs/fret.md` says active mode
  exists to avoid.
- the active preconnect tick (`~1226`) — Core 6 / Edge 3 pings per second, serial.

Both get `runPooled` at `maintenanceConcurrency`, the run signal, and the 2000 ms ping budget.

**Not pooled:** `sendAnnouncementsRateLimited` (`~1158`) stays serial. Its loop `break`s the
moment the announce token bucket is empty, and that "stop as soon as we are out of budget"
ordering is the rate limit — parallelising it would issue the whole fan-out before the bucket
could stop it. It is already bounded per-RPC by `rpc-abort-deadlines`. State this at the site
so the next reader does not "finish the job".

## Edge cases & interactions

- **Concurrent scoring of the same peer.** `applySuccess` / `applyFailure` / `applyTouch` read
  an entry, `await selfCoord()`, then write a value derived before the await — two chains
  touching one peer lose an increment (already documented in the NOTE on `applySuccess`, and
  why `applyContactStrike` is deliberately await-free). The four candidate sets are **disjoint
  by construction**: near-probe is live-member-gated, classify is `unknown` and non-`dead`,
  the foreign arm is `foreign` and non-`dead`, the dead arm is `dead`. Assert that disjointness
  in a test rather than trusting it — it is the invariant that makes this ticket safe, and a
  future selection change could break it silently.
  - Still-reachable interleaving: two *different* peers' snapshot merges can name the **same**
    third peer, so concurrent `applyTouch(pid)` on it is genuinely possible. Harmless (the
    lost field is `accessCount`, feeding a relevance score recomputed on every call), but say
    so at the site instead of leaving it implied.
- **`enforceCapacity` must not run concurrently with itself.** It awaits `selfCoord()`, then
  lists, sorts, and removes; two overlapping runs would sort stale snapshots and can over-evict.
  Keep it out of the pooled tasks — one call after the phase-1 pool drains, as today.
- **`announced` accumulation.** Collected per task and concatenated by the driver; do not let
  pooled tasks push into one shared array *and* trigger the announce, or a peer is announced
  once per task.
- **Cancelled tasks must not score.** Inherited from `rpc-abort-deadlines`: a `skipped` result
  and an abort-caused rejection are both "we gave up", never a contact failure or a backoff.
  A tick that truncates must leave the routing table's health counters untouched.
- **`stop()` mid-tick.** The tick deadline is a child of the run signal, so `stop()` collapses
  the whole tick at once. The existing per-peer `if (this.stopped) break;` guards move into the
  pool's signal check; do not silently drop them.
- **Run generation.** The tick already captures `gen` and exits on mismatch; pooled tasks must
  observe the same rule (via the run signal) so a start→stop→start cannot leave a previous
  run's tasks mutating the new run's store.
- **Empty and single-element candidate lists.** `runPooled([], …)` resolves to `[]` without
  spawning workers; `concurrency` larger than the task count spawns only as many workers as
  tasks. Both are the common case in a small ring.
- **A task that throws synchronously** (before returning a promise) must be caught by the
  worker, not escape the pool — `probeAndFetch` calls `peerIdFromString`, which throws on a
  malformed id.
- **No timers left behind.** `runPooled` creates none; the tick's `deadline` must be
  `cancel()`ed in a `finally` or the mocha exit watchdog fails the suite.
- **Diagnostics counters** (`diag.pingsSent` / `pingsOk` / `pingsFail` / `snapshotsFetched`)
  are plain `++` on a single-threaded event loop, so concurrency does not corrupt them — but a
  truncated tick now under-counts relative to today. That is correct (the RPCs did not happen)
  and worth a sentence wherever the counters are documented.

## Tests

- `test/pool.spec.ts`
  - Never exceeds `concurrency`: instrument tasks with an in-flight counter and assert the
    observed maximum, over a `fast-check` property across task counts and resolution orders
    (the repo already uses `fast-check`; assert on the generated distribution so the
    `tasks > concurrency` region is provably reached).
  - Results are index-aligned and carry the right status for a mix of resolving, rejecting,
    and synchronously-throwing tasks.
  - Aborting mid-run: already-started tasks settle, the remainder are `skipped`, the returned
    array is still full length, and the call never rejects.
  - `concurrency` of 0 or negative is clamped to 1; empty task list resolves to `[]`.
- `test/stabilize-concurrency.spec.ts`
  - **Headline regression test.** Four near peers where one hangs its dial forever; assert the
    tick resolves within the tick budget + slack, and that the other three were both pinged
    and snapshot-fetched. Today the hung peer blocks all of them.
  - Max in-flight outbound RPCs during a tick never exceeds `maintenanceConcurrency`, asserted
    for both profiles (Core 6 / Edge 2) via an instrumented stub node.
  - Ping-before-fetch ordering is preserved per peer.
  - Disjointness: build a store holding a member, an unknown, a foreign, and a dead peer;
    assert the four selectors return pairwise-disjoint id sets.
  - Truncation is not evidence: force the tick budget to expire (tiny budget, hanging peers)
    and assert no peer gained a contact-failure strike, a backoff entry, or a `dead` label.
  - Rotation: with more unknowns than the per-tick classify budget, two consecutive ticks
    probe different peers (least-recently-touched first).
- No-regression gate: `churn-scenarios`, `churn.leave`, `dead-state`, `ring-membership`,
  `membership-identify`, `fret.mesh`, `libp2p-memory.integration`, `profile.behavior`,
  `service-lifecycle` all exercise the stabilization tick end-to-end and must pass unchanged.
