description: A lightweight node and a server-grade node can refuse each other's neighbor-list messages, because each node sizes its incoming-message limit for messages it would send itself rather than for the largest message a peer might legitimately send it. Make the accept limit one network-wide number.

## The defect, with measured numbers

FRET runs two operating profiles, Edge (lightweight) and Core (server-grade). The neighbors
protocol's per-message byte cap is currently one number per profile — Core 16 KiB, Edge 8 KiB
(`FretService.maxBytesNeighbors`, `fret-service.ts:1023`) — and each number was derived from the
largest snapshot *that profile emits*. A cap on an **incoming** message has to cover the largest
message any peer may legitimately send, and both profiles talk to each other.

Encoded sizes, measured by running `JSON.stringify` + `TextEncoder` (which is exactly what
`encodeJson` does, `src/rpc/protocols.ts:246`) over the worst legal snapshot shape — realistic
53-char peer ids, a 32-byte base64url coordinate per sample entry, 256 bytes of reserved `sig`,
and `metadata` grown until `JSON.stringify(metadata)` hits the profile's allowance exactly, which
is the quantity `FretService.snapshot` measures against the cap:

| shape | bytes |
|---|---|
| Core fixed fields only, emission caps 12/12/8 | 2,923 |
| Core fixed fields only, merge caps 16/16/8 | 3,371 |
| **Core + 8 KiB metadata, emission caps** | **11,127** |
| Core + 8 KiB metadata, merge caps | 11,575 |
| Edge fixed fields only, emission caps 6/6/6 | 1,969 |
| Edge + 4 KiB metadata, emission caps | 6,077 |
| Edge + 4 KiB metadata, merge caps 8/8/6 | 6,301 |

Against an **Edge inbound cap of 8,192**: a Core node overflows it by 2,935 bytes at its own
legal worst case. The threshold is exact — the snapshot costs `,"metadata":` (12 bytes) on top of
the measured metadata blob, so `2923 + 12 + M > 8192` gives **M > 5,257 bytes**. A Core node whose
application calls `setMetadata` with more than ~5.1 KiB of JSON can no longer announce to, or
answer a neighbors request from, *any* Edge peer. Edge to Core is fine (6,301 < 16,384), so the
failure is one-directional, and it is silent: the Edge node refuses at the length prefix and tears
the stream down, the Core node sees a failed RPC and cannot learn that its message was merely too
big for that peer.

With no metadata set the fixed fields fit either way, which is why a default single-profile test
run never sees it. The encoding tests that shipped with the cap change
(`test/rpc.codec-properties.spec.ts:1031`) build the snapshot **without** `metadata` and compare
each profile's message against *its own* cap — so they miss both the field that overflows and the
cross-profile relation entirely.

### Arm B — one node, one message type, two disagreeing caps

The same node reads neighbor snapshots on two paths with different numbers:

- announce (inbound push): `registerNeighbors` is handed `this.maxBytesNeighbors()`
  (`fret-service.ts:1035`) — 16 KiB Core, 8 KiB Edge.
- fetch (reply to our request): `fetchNeighbors` hard-codes `maxBytes: 16 * 1024`
  (`src/rpc/neighbors.ts:114`) and takes no profile input at all. `registerNeighbors`' own
  `maxBytes` default (`neighbors.ts:22`) is a third copy of the literal, reachable only from tests.

So an Edge node **accepts** an 11 KiB Core snapshot when it asked for one, and **refuses** the
identical snapshot when the same peer pushes it. Same decision — "what is the neighbors byte
limit" — hence one ticket with two arms.

## Root cause

One name answers two different questions. `maxBytesNeighbors()` is read as "how big may a neighbors
message be", but the profile split inside it only makes sense for *emission* ("how big may **my**
snapshot be"), while every one of its call sites is an *acceptance* decision ("how big may a
**peer's** snapshot be"). Acceptance is a property of the network, not of the local profile.

## Decision: one acceptance cap, profile-split emission budgets

Of the two directions the fix ticket left open, take the first — **raise acceptance to cover the
largest Core snapshot, on both profiles** — and keep the metadata allowances as they are.

The decisive argument is arm B: **Edge already exposes a 16 KiB neighbors read today**, on the
fetch path. Unifying at 16 KiB therefore adds no worst case Edge does not already carry; it only
makes the announce path agree with the number the fetch path has been using all along. The stated
cost of direction 1 ("costs Edge a larger worst-case read buffer") turns out to be already paid.
Capping metadata to one profile-independent number (direction 2) would take metadata room away
from Core applications to buy a reduction Edge does not actually get.

Concretely:

- **`MAX_NEIGHBORS_BYTES = 16 * 1024`**, one number for both profiles, living in
  `src/rpc/validate.ts` beside `MAX_ACTIVITY_BYTES` / `MAYBE_ACT_OVERHEAD_BYTES` — the module that
  already owns every derived wire cap. Derived, not picked: Core worst legal emission is 11,575
  bytes at the merge caps, leaving ~4.8 KiB of headroom. Say so in the doc comment, with the
  arithmetic, the way the maybeAct constants do.
- Every neighbors read path takes that constant and **no literal byte count survives**: the
  `fetchNeighbors` `maxBytes`, the `registerNeighbors` `maxBytes` default, and
  `FretService.maxBytesNeighbors()`. Mirror how `src/rpc/maybe-act.ts:19,53` already imports its
  cap from `validate.ts` rather than restating it.
- Keep `maxBytesNeighbors()` as a method (drop only the profile branch), for symmetry with
  `maxBytesMaybeAct()` and because `test/profile.behavior.spec.ts` reaches for it.
- `MAX_SNAPSHOT_METADATA_BYTES_CORE` (8 KiB) and `_EDGE` (4 KiB) are unchanged in value but their
  doc comments are now wrong: they claim to be "sized against the profile's neighbors wire cap",
  which is the mistaken rule. They are **emission budgets** — a profile's own choice of how much
  application metadata it will carry — and the invariant they must satisfy is
  `largest emission of any profile <= MAX_NEIGHBORS_BYTES`, not `<= that profile's cap`.

Two things this deliberately does **not** change:

- Nothing checks an outgoing snapshot against the acceptance cap before writing it —
  `announceNeighbors` is write-only. The pinning test below is the whole guard, which is why it
  must build the largest legal emission rather than a typical one.
- Over-cap metadata is still dropped from the outgoing snapshot with an error log and the peer
  never learns of it. That is already recorded as a `NOTE:` at `FretService.snapshot` and is out of
  scope here.

## The test that pins the relation

The requirement the current tests fail to express: **each profile's largest legal emission must fit
the smallest cap any peer may apply.** With one acceptance number that reads as "every profile's
worst case is under `MAX_NEIGHBORS_BYTES`", and a future re-split of the number fails it.

In `test/rpc.codec-properties.spec.ts`, under *the largest legal message of each protocol encodes
under its wire cap*:

- Extend both snapshot cases with `metadata` at that profile's **full** allowance
  (`MAX_SNAPSHOT_METADATA_BYTES_CORE` / `_EDGE`), sized so `JSON.stringify(metadata)` equals the
  allowance exactly — that is the quantity `FretService.snapshot` measures, so a test that sizes
  the whole snapshot instead is measuring the wrong thing.
- Assert both against `MAX_NEIGHBORS_BYTES`, not against a per-profile number. Keep the id-list
  lengths at the *merge* caps (16/16/8 Core, 8/8/6 Edge) rather than the emission caps
  (12/12/8, 6/6/6) as the existing cases do — it is the conservative direction and it keeps the
  test valid if the emission caps are ever widened to the merge caps. Say that in a comment.
- Add a guard that both profiles' `maxBytesNeighbors()` return `MAX_NEIGHBORS_BYTES`, so
  re-introducing a profile split fails here rather than on the wire.

For arm B, the behavioral pin belongs on the existing edge-profile `WireRig`
(`test/rpc.codec-properties.spec.ts:795`, whose `svc` is Edge), in *merges an under-cap announce
and refuses an over-cap one*: an announce padded to ~11 KiB — over today's Edge cap of 8 KiB, under
the new one — must be **accepted and merged** by an Edge receiver. That case fails on today's code,
which is the repro; the existing 70 KiB over-cap case stays as the refusal side.

Also update, in the same file, the frame-prefix case table entry
`{ label: 'neighbors announce (8 KiB, edge)', cap: 8 * 1024 }` (~line 1014) and the inline
`expect(maxBytes, 'edge wire cap').to.equal(8 * 1024)` (~line 912).

## Other sites the change breaks

- `test/profile.behavior.spec.ts:305-317` — two cases asserting Core 16384 / Edge 8192. They
  become one case asserting both profiles return the same constant.
- `src/rpc/request.ts:21-27` — `DEFAULT_MAX_BYTES` stays 8 KiB, but its doc comment justifies the
  value as "matching the neighbors cap on the Edge profile", which will no longer exist. Re-justify
  it on its own terms (a conservative floor for a consumer who passed no cap) or restate it against
  whatever number it should actually track.
- `docs/fret.md`, *Stream management*, the sentence "Neighbors is 16 KiB Core / 8 KiB Edge, sized
  to its profile's snapshot caps" — encodes the mistaken rule verbatim. Replace with the corrected
  one: one acceptance number for both profiles, derived from the largest snapshot any profile can
  emit, with the emission budgets (snapshot caps and metadata allowances) staying profile-split.
  Check the *Operating profiles* and *Security and abuse considerations* sections for any second
  statement of the per-profile neighbors cap while there.

## Forward-looking note (not scope)

`tickets/backlog/impl/5-message-signatures` will populate the snapshot's `sig` field, which is
empty today; the sizing above already reserves 256 bytes for it, and 16 KiB leaves ~4.8 KiB of
headroom, so signing does not disturb this number. Mention the reservation in the constant's doc
comment so whoever lands signing sees that it was accounted for.
