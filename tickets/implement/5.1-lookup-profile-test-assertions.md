Tests only — no production code changes. Four arms; two are deletions, because the behavior in
question already has a stronger spec and the weak one is a duplicate that hides that fact. If an
assertion below cannot be made to hold, that is a finding about the service: report it in the
review handoff rather than loosening the assertion.

### 1. The lookup's terminal event is deterministic, and it is not a three-way choice

`iterative-lookup.spec.ts:34-61` accepts a final event of `near_anchor` **or** `exhausted` **or**
`complete`. Reading `iterativeLookup` (`fret-service.ts:2721`), only `complete` returns early —
every other path falls out of the attempt loop and yields `exhausted` as the last event
unconditionally (`fret-service.ts:2931`). And a digest-only lookup can never yield `complete`,
because `complete` requires a commit certificate. So the disjunction admits outcomes the code
cannot produce and would also admit a lookup that never probed anyone.

Rewrite to state the contract:

- The final event is `exhausted`, exactly.
- No `complete` event occurs anywhere in the stream (there is no activity to complete).
- At least one `probing` event, and every `probing.peerId` is one of the other nodes' ids.
- At least one `near_anchor` whose `anchors` and `cohort_hint` are non-empty — each responder is
  in-cluster on a three-node ring, so it answers with real hints rather than the empty
  `staticReject` shape.

### 2. The activity handler fires exactly once, and on a peer other than the initiator

`iterative-lookup.spec.ts:63-97` installs a handler on all three nodes, then asserts only that the
event list includes one of `complete` / `activity_sent` / `near_anchor` — it never counts handler
invocations at all, so a lookup that delivered the activity zero times or three times passes.

Rewrite:

- Count invocations per service.
- Assert the lookup ends `complete` with the certificate the handler returned.
- Assert the total across all three services is exactly 1 — one peer performs the work and the
  certificate travels back; a forwarding hop must not re-run it.
- Assert the initiator's own count is 0. `iterativeLookup` never performs the activity locally, it
  always sends (see the `visited` set seeded with self at `fret-service.ts:2748`), and that is a
  real property worth pinning.

The third test in that describe (`still delivers activity when the initiator is the peer nearest
the key`, line 104) is already written this way — match its shape.

### 3. Delete two blocks that test the wrong entry point

Both of these call `routeAct` for behavior that lives in `handleMaybeAct`, so they assert nothing
about their stated subject, and both subjects already have a proper spec:

- **`Breadcrumb rejection` (`iterative-lookup.spec.ts:149-176`)** — the breadcrumb-loop guard is
  `handleMaybeAct`'s (`fret-service.ts:1141`); `routeAct` has no self-in-trail check. The test
  passes because a three-node ring puts the node in-cluster, so `routeAct` returns a `NearAnchor`
  for an unrelated reason and `'anchors' in res` holds. Real coverage:
  `pick-anchors.spec.ts:175` (`the breadcrumb-loop reply is a static rejection, not a ring walk`),
  which drives `handleMaybeAct` and asserts the reply is the empty static shape.
- **`Correlation ID dedup` (`iterative-lookup.spec.ts:178-209`)** — the dedup cache is read and
  written in `handleMaybeAct` (`fret-service.ts:1144`, `:1167`); `routeAct` never touches it. Both
  calls therefore do the full work and the test's only assertion is that each returned *some*
  `NearAnchor`. Real coverage: the whole of `maybeact-dedup-phases.spec.ts`, which sends over the
  wire (its header comment says exactly why: "`routeAct` alone never touches the cache") and pins
  the digest-phase replay, the activity-phase replay, the phase split, and the
  refusal-is-not-cached rule.

Delete both describes. Leave a short comment at the top of `iterative-lookup.spec.ts` naming where
each behavior is now pinned, so the next reader does not re-add them. Do not attempt to "fix" them
by re-pointing at `handleMaybeAct` — that just duplicates the two specs above.

### 4. Delete the tautological preconnect-budget block

`profile.behavior.spec.ts:359-386` puts an empty-store service into active mode and asserts
`pingsSent <= budget`. With no peers the count is 0, so the assertion holds for any budget, and its
own comment admits it ("With an empty store, diag.pingsSent should be 0").

The originating review asked for these to be re-seeded past the budget so the count saturates. That
spec already exists: `preconnect-concurrency.spec.ts:173-216` seeds 16 peers through the shared
maintenance rig and asserts `pingsSent` equals **exactly** the budget for both profiles (Core 6 at
line 200, Edge 3 at line 213), plus that the budget is spent on dialable peers rather than wasted
on undialable leaders. Rebuilding that here would be a second copy of a stronger test, so delete
the `Preconnect budget` describe and leave a one-line pointer to
`preconnect-concurrency.spec.ts` in its place.

### 5. The TCP mesh smoke test asserts only that a diagnostics object exists

`fret.mesh.spec.ts:47` reads `getDiagnostics()` and throws if it is falsy. Nothing else in the file
is asserted, so the whole spec passes if stabilization never runs.

This file is worth keeping and is worth more than a smoke test: it is the only spec running FRET
over a **real TCP transport** (everything else uses the in-memory transport), and node `c` is
started with no FRET service at all — an accidental but useful negative control. After a `waitFor`
gate on convergence, assert:

- Each of the two FRET nodes has classified the other `member` in its store, and has a non-zero
  ping/snapshot diagnostic to show it got there through real RPC rather than by assumption.
- Node `c` is **never** classified `member` by node `a`, despite being connected to it. It serves
  none of this network's protocols, so no evidence path can promote it (see *Evidence strength* in
  `docs/fret.md`). Assert the entry exists and its membership is not `member`; do **not** assert it
  reaches `foreign`, which needs three time-separated negotiate failures (~7 s) and would make the
  spec slow and flaky.

Replace the `setTimeout(1500)` with a `waitFor` on that convergence predicate
(`test/helpers/wait-for.ts`).

## Edge cases & interactions

- **`exhausted` is the unconditional terminal event.** Any assertion of the form "the last event is
  X" is only meaningful for `complete`; for everything else assert on the *stream*, not the tail.
- **The payload-inclusion heuristic may put the activity on the first probe.** On a tiny ring
  `shouldIncludePayload` can be true immediately, in which case the lookup completes at hop 0 with
  no `activity_sent` event at all. So assert the invocation count and the `complete` result — never
  that a specific event sequence occurred.
- **A busy responder is retired for the rest of the lookup** (it lands in `visited`), so a spec
  that exhausts a rate-limit bucket earlier in the same file can turn a completing lookup into an
  exhausted one. Each lookup spec builds its own mesh; keep it that way.
- **Node `c` in the TCP spec has no FRET service**, so `a` will keep failing to negotiate against
  it in the background. That is expected noise, not a failure — do not assert on `a`'s
  `pingsFail`, which would couple the spec to how many probe passes happened to run.
- **Membership assertions need the peer to be in the store first.** Over TCP with no `identify`
  service configured, entries arrive via `peer:connect` as `unknown` and are promoted by a
  successful namespaced RPC. A `waitFor` predicate that reads membership must tolerate a missing
  entry (return false) rather than throwing on `undefined`.
- **`waitFor` predicates must describe convergence the ring cannot reach alone** — a node's store
  holds its own entry from `start()`, so any self-inclusive count is already true at t=0 and waits
  on nothing. That helper's doc comment spells out the trap.
- **Deleting a describe changes the suite's test count.** `test/README.md` claims a fixed passing
  count and is already stale; `plan/21-cleanup-tests` owns that file. Do not update it here, and do
  not let a count mismatch there be read as a regression.
