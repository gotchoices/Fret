Two things the original ticket's sketch did not have, both needed by real call sites:

- **`opts.factory`.** The specs use *two different* node factories and they are not
  interchangeable: `createMemNode` is the memory transport (no `identify`) and `createMemoryNode`
  is TCP. `buildMesh` defaults to `createMemNode`; pass `{ factory: createMemoryNode }` for the
  TCP ones (`maybeact-dedup-phases`, `payload-bounds-ttl`, `iterative-lookup`).
- **`connect` and `addServices` are separate calls, caller-ordered.** This is the whole reason
  there is no one-shot `buildMesh({topology, service})`. See the correction below.

## The one way this refactor can silently change behaviour

Specs differ in whether they dial before or after constructing services, and the difference is
real: dialing first means `start()`'s `seedFromPeerStore` already sees the connections; dialing
after means the ring is discovered through `peer:connect`. Several specs comment on this
explicitly (`libp2p-memory.integration.spec.ts` and `iterative-lookup.spec.ts` both say "start
services BEFORE connections so peer:connect handlers fire"). **Preserve each spec's existing
order exactly** — read the surrounding comment before moving a line.

Known orders, from the survey:

- `churn.leave.spec.ts` — services first, then star.
- `iterative-lookup.spec.ts`, `libp2p-memory.integration.spec.ts`, `peer-discovery.spec.ts`,
  `maybeact-dedup-phases.spec.ts` — services first, then star.
- `profile.behavior.spec.ts` — star first, then services.

## Site-by-site notes

- **`profile.behavior.spec.ts`** (four rigs at ~128, ~152, ~180, ~214). These build 15 or 22
  nodes, dial a star, and then construct a service on **node 0 only** (two of them add a
  separate off-mesh receiver node afterwards). So `addServices` does **not** apply — use
  `buildMesh(n)` + `connect('star')` and leave the bespoke single-service construction alone.
  This is the largest mechanical win in the ticket and the lowest risk.

  services at all. The rest of the file (the `Leave amplification cap` rigs from ~200 down) is
  two-node pair setup and is explicitly **out of scope** — leave it.
- **`maybeact-dedup-phases.spec.ts:199`** and **`payload-bounds-ttl.spec.ts:191`** — TCP factory.
  `payload-bounds-ttl`'s rig is only 2 nodes; migrate it only if it reads better, and skip it

- **`peer-discovery.spec.ts:~495`** — note this file uses semicolons, unlike the rest of the
  suite. Match the file, not the house style.
