## What is stale, and why

Two things landed after the affected paragraphs were written:

- `15.331-rpc-reply-parser-senders` wired every reply parser into its sender. The *Wire-shape
  parsers* section may still contain a sentence saying `parsePingResponse` "exists but is not yet
  wired" and that `sendPing` still coerces its reply with `Boolean(r.ok)`. Both are now false —
  `sendPing` parses. **Read the section before editing; the sender table may already be correct,
  in which case only the stale sentence needs to go.**
- `15.332` makes the wire-shape parser the single point where a neighbor snapshot's
  successor / predecessor / sample lists are truncated. Until then the same caps were also applied
  by a `slice` inside each of the two merge loops (`mergeAnnounceSnapshot` and
  `fetchAndMergeSnapshot` in `packages/fret/src/service/fret-service.ts`).

## Requirements

- Under *Wire formats* / *Wire-shape parsers*: state that every inbound message **and every reply**
  has exactly one parser, and for each one what a field violation does — the four outcomes the code
  actually implements are **reject the message**, **truncate the list**, **drop the entry**, and
  **drop the field**. The section already carries a parser table; the point is that a reader can
  read the rule for any field off it without opening the source.
- Delete the stale `parsePingResponse` / `Boolean(r.ok)` sentence described above.
- Under *Security and abuse considerations*, the *Inbound snapshot-merge caps* bullet currently says
  both merge loops slice remote lists to the per-profile bounds. Restate it: the caps
  (Core 16/16/8, Edge 8/8/6) are enforced **once, at the parser**, which is supplied those numbers
  by `FretService.mergeSnapshotCaps()` at both registration sites — so the merge loops no longer
  truncate and there is no second copy of the numbers to drift.
- Do not restate the cap numbers anywhere else in the document; one statement of them is the point
  of the change being documented.
