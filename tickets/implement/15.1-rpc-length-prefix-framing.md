`docs/fret.md` has always specified "length-prefixed UTF-8 JSON" for all four protocols. The
implementation ships **bare** JSON and infers message end from stream close. This ticket closes
that gap. Sibling tickets `15.2-rpc-request-helper` and `15.3-rpc-message-validators` build on it.

**`lp.decode` semantics, verified by reading `dist/src/{decode,encode}.js`:**

- `lp.encode.single(bytes)` → `Uint8ArrayList` (prefix + body), suitable for one `stream.send`.
- `lp.decode(source, opts)` is an async generator yielding one `Uint8ArrayList` per framed
  message. Options: `maxDataLength`, `maxLengthLength` (default 8), `onLength(len)`,
  `lengthDecoder`.
- A **zero-length message is yielded** (as an empty list): the LENGTH and DATA branches run in
  the *same* loop iteration, so `dataLength = 0` yields immediately. The ticket's "empty
  `Uint8Array` → `decodeJson` throws `empty response`" path works as specified.
- **Clean EOF after the prefix was consumed but before any body byte arrives does NOT throw
  `UnexpectedEOFError`** — the internal buffer is empty at that point, and the EOF check is
  `buffer.byteLength > 0`. The generator just completes. So `readFramed` must treat
  *iterator-done-before-the-first-message* as an error; that one check covers both
  "ends before the prefix" and "prefix arrived, body never did, remote closed cleanly".
  (`UnexpectedEOFError` does fire for a partial varint or partial body still buffered.)
- A varint of ≥ 9 bytes → internal `RangeError` → `InvalidDataLengthLengthError`. Surfaces as a
  rejection of `next()`, not a hang — the edge case the ticket asks to confirm.

**One real design wrinkle — the `payload too large` message needs the declared length, and
`InvalidDataLengthError` doesn't carry it.** The library's `maxDataLength` check throws *before*
`onLength` fires and before the prefix is consumed, so catching `InvalidDataLengthError` leaves
`${declared}` unknown for the required message
`payload too large: ${declared} exceeds ${maxBytes} byte limit`. Two viable resolutions, pick one:

1. **Recommended: enforce the cap in `onLength` instead.** Pass a loose `maxDataLength`
   (e.g. `Number.MAX_SAFE_INTEGER`) and throw the exact `payload too large` error from
   `onLength` when `len > maxBytes`. `onLength` runs immediately after the varint parse and
   before any body byte is consumed or any further source pull — same pull-count semantics as
   the library's own check (the counting-source test still sees exactly one pull for a
   prefix-only chunk), and the library's varint parser is still doing all parsing (no house-rule
   violation). Still catch `InvalidDataLengthError` as a defensive mapping in case a huge 8-byte
   varint (> 2^53) trips the library first.
2. Custom `lengthDecoder` recording the decoded value, keeping `maxDataLength: maxBytes` — but
   that needs `uint8-varint` as a third direct dependency, which the ticket's settled dependency
   list doesn't include. Only take this route if (1) proves unworkable.

## Why the current reader is wrong (verified, not inferred)

Read `node_modules/@libp2p/utils/dist/src/abstract-message-stream.js` if you want to see it:

- `[Symbol.asyncIterator]` (line ~81) creates a pushable and subscribes to `message`, `close` and
  `remoteCloseWrite` **at iteration start**. `remoteCloseWrite` is a one-shot dispatch, not sticky.
- Bytes that arrived before iteration are held in `readBuffer`, and `addEventListener` (line ~225)
  re-dispatches them in a `queueMicrotask` when the first `message` listener is added. **So the
  data does arrive** — it is only the end-of-stream signal that is lost.
- Every FRET sender opens, writes, closes, and only then begins reading. A responder that replies
  quickly closes before the subscription exists, so `output.end()` never runs and the iterator
  never yields `done`.
- `readAllBounded` recovers this by racing each `iter.next()` against a 20ms timer and consulting
  `readBufferLength` / `remoteWriteStatus` / `readStatus`. Correct, but it reaches into stream
  internals a read helper should not know, and it puts a ~20ms floor under every measured RPC
  round trip — which feeds `applySuccess`'s latency EMA, and therefore peer health scoring and
  eviction order.
- The byte cap can also only be enforced *after* the fact: `readAllBounded` compares cumulative
  length after each chunk, so an over-sized body is partly pulled through the receiver's memory
  before being refused.

A length prefix makes the reader authoritative: it stops on byte count, so the lost close event
becomes irrelevant, the poll and its 20ms floor are deleted outright, and the cap is checkable
before a single body byte is pulled.

## Decisions (settled — do not re-open)

**Prefix encoding: unsigned varint, via `it-length-prefixed`.** It is the ecosystem-standard
implementation, already resolved in this tree at 10.0.1 (with `uint8arraylist` 2.4.8), and it is a
full parser rather than a hand-roll — the house rule forbids the alternative. Its decoder checks
`maxDataLength` *immediately after parsing the varint and before consuming the body* (see
`dist/src/decode.js`), which is exactly the "refuse without reading the body" semantics wanted. It
also carries `maxLengthLength` (default 8) against a varint bomb, and throws `UnexpectedEOFError`
when the source ends with a partial frame still buffered.

- Add `it-length-prefixed` and `uint8arraylist` to `packages/fret/package.json` `dependencies` at
  the versions above. They are currently only transitively hoisted; relying on that is how a build
  breaks on someone else's lockfile.

**Write is one `send`, never two.** `@libp2p/interface` v3's `Stream.send` takes
`Uint8Array | Uint8ArrayList`, and `lp.encode.single(bytes)` returns a `Uint8ArrayList`. So the
prefix and body go out in a single `send` call. This is deliberate: `15.2` owns the write-side
backpressure arm (`send()` returning `false`, `writableNeedsDrain`, the `drain` event), and
splitting one `send` into two would make that worse before it is fixed.

**Trailing bytes after the first complete message are ignored.** The reader takes the first framed
message and stops; it never looks for a second. Reading further to prove there is nothing there
would mean waiting for end-of-stream again, which is the whole problem being deleted. Every FRET
exchange is one message per direction per stream, and the stream is released immediately after.

**`decodeJson`'s NUL/tab/LF/CR/space trim stays, and its justification changes.** With framing,
padding a muxer adds outside the counted body is no longer reachable — the reader hands over
exactly `dataLength` bytes. The trim remains load-bearing for a *sender* that frames padding
*inside* the count (an encoder that writes `JSON + "\n"` is the realistic case), which is an
interop concern rather than a muxer one. Update the comment on `decodeJson` and the note at
`test/rpc.codec-properties.spec.ts:322` to say that; keep both padding tests as they are.

**`readAllBounded` is deleted, not re-pointed.** It is exported from the package root
(`src/index.ts:150`) and pinned by `test/package-exports.spec.ts:60`. Keeping the name with framed
semantics would silently break a consumer holding the old contract, and `AGENTS.md` says not to
worry about backwards compatibility yet. Replace it in the export surface with the framed pair:

```ts
/** Write one length-prefixed message. Single `send`; see the backpressure note in 15.2. */
export function sendFramed(stream: Stream, body: Uint8Array): boolean

/**
 * Read exactly one length-prefixed message, bounded by `maxBytes` and one overall deadline.
 * Throws on: a prefix declaring more than `maxBytes` (before pulling the body), a stream that
 * ends before the prefix or before the body is complete, the deadline, or `opts.signal`.
 */
export function readFramed(
	stream: AsyncIterable<Uint8Array | Uint8ArrayList>,
	maxBytes: number,
	timeoutMs?: number,
	opts?: { signal?: AbortSignal }
): Promise<Uint8Array>
```

Both are exported together for the same reason `openRpcStream` / `releaseRpcStream` are: a
consumer given only the reader hand-rolls the writer, and the framing has to match.

**The over-sized refusal keeps today's error shape.** `it-length-prefixed` throws
`InvalidDataLengthError('Message length too long')`. `readFramed` must catch it and rethrow the
existing message so callers and tests are unchanged:
`payload too large: ${declared} exceeds ${maxBytes} byte limit`.

**The poll machinery is deleted:** `remoteFinishedWriting`, `EOF_POLL_MS`, `POLL_TICK`, the
`ReadEndState` interface, and the `pending`-held-across-ticks bookkeeping. With no poll there is
nothing to abandon, so `readFramed` races the source's `next()` against the deadline timer and the
abort promise only. Keep the `ABORTED` resolve-not-reject sentinel (an abort that loses the race
must not surface as an unhandled rejection) and keep the defensive `.catch(() => {})` on the
pending read with its existing NOTE.

**`sendMaybeAct`'s half-close stays** (`maybe-act.ts:64`). Framing means the responder no longer
*needs* it to know the request ended, but it is still the write-side flush, and it is what makes
the stream's write end closed when `registerRpcHandler`'s release rules are evaluated — rules
pinned by `test/rpc.handler-fuzz.spec.ts`. Removing it would force those rules to be re-derived,
which this ticket must not do.

## Edge cases & interactions

- Prefix + whole body in one chunk; prefix split across two chunks; body split across many chunks.
  The same message split at **every** offset must decode identically.
- Prefix arrives, body never does → must hit the deadline, not hang.
- Prefix declaring 0 bytes → `readFramed` returns an empty `Uint8Array`; `decodeJson` then throws
  its existing `empty response`. That is the right shape — do not special-case it earlier.
- Prefix declaring more than `maxBytes` → refused with the message above, having pulled only the
  prefix.
- A varint that never terminates → `it-length-prefixed`'s `maxLengthLength` guard
  (`InvalidDataLengthLengthError`). Confirm it surfaces as an error rather than a hang.
- Stream ends with a partial frame buffered → `UnexpectedEOFError`. Must be an error, never a
  short-but-valid message: `test/rpc.stream-errors.spec.ts`'s invariant "a partial payload is
  never parsed as a whole message" has to survive unchanged.
- **Stream whose read end is already closed when iteration starts.** `abstract-message-stream.js`
  line ~82 returns immediately with no data when `readStatus` is neither `readable` nor `paused`
  (reachable via `onTransportClosed` / `onRemoteReset` with an empty read buffer). `readFramed`
  must treat "ended before the prefix" as an error, not as an empty message.
- Cancellation: `opts.signal` firing must throw, and must stay distinguishable by the caller
  exactly as today (the sender's deadline is a child of the caller's signal — the "our own
  cancellation is not evidence" rule in `docs/fret.md` depends on this being unchanged).
- `registerRpcHandler`'s inbound release rules must not need re-deriving.
  `test/rpc.handler-fuzz.spec.ts` is the check; it should stay green with no edits to the seam.
- The three `rpc.stream-errors.spec.ts` failure shapes (reset mid-stream, clean close mid-JSON,
  stall after a partial payload) must still yield an error and release the stream exactly once.
  The existing caveat holds: when the read ends on the RPC's own budget, only the release *count*
  is an invariant, not which arm ran.
- `fetchNeighbors` still swallows every failure into a fabricated empty snapshot — that is `15.2`'s
  arm. Do not change it here, but check that a framing error still lands in that catch rather than
  escaping.

## Key tests to expect

- **Chunk-boundary property.** For a generated message, splitting the framed bytes at every
  possible offset (or a `fast-check`-generated set of split points) decodes to an identical value.
- **Round-trip property over all five wire types**, extending `test/rpc.codec-properties.spec.ts` —
  which already proves the JSON codec's three stated losses. Framed encode → framed decode is the
  identity on the same generated instances.
- **Over-sized prefix refused after pulling only the prefix**, measured by counting pulls on a
  source that reports them — the same technique the existing cap test uses, not an inferred claim.
- **No 20ms floor.** Drive a real ping against a fast responder on the in-memory transport and
  assert the measured RTT is comfortably under the deleted `EOF_POLL_MS` (a `< 10ms` bound over a
  few iterations). This is the headline symptom, so assert it rather than inspecting the diff.
- **Ends-before-prefix and ends-mid-body** both throw, and neither returns a partial buffer.
