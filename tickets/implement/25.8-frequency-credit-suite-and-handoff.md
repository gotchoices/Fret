## Carry into the review handoff

Verbatim from the source ticket — these are the points a reviewer should actually look at, none of
them re-derivable from the diff alone:

- **`noteDiscovered` returning `boolean` was the optional improvement in the source ticket, and it
  was taken.** The four merge loops (announce id lists ~1974 and sample ~1996; fetch ~2564 and
  ~2573 in `src/service/fret-service.ts`) now push to their `discovered` / `announced` array on
  that return value instead of a pre-`upsert` `getById`. Behavior is equivalent because self is
  always already in the store (seeded `member`), so the self early-return cannot swallow a
  genuinely-new id.
- **An imported pre-change snapshot restores inflated frequency.** `accessCount` is already in
  `SerializedPeerEntry`, so there is no schema change, but the field now means "contacts" where it
  used to mean "contacts + mentions". Accepted and self-correcting — relevance is rewritten on the
  next scoring call — and deliberately not migrated.
- **The already-held arm no longer refreshes `coord`.** The five switched sites all passed a
  coordinate freshly derived from the peer id (`hashPeerId(peerIdFromString(pid))`), and a ring
  coordinate is *defined* as that hash, so the refresh was writing back identical bytes. Stated
  because it is a real behavior difference, not because it is suspected to matter.
- **Not refreshing `lastAccess` on the already-held arm is the intended change, not a side effect.**
  It is the ordering key for the unknown-classification probe rotation (ascending `lastAccess`), so
  the old refresh sank a heavily-gossiped unknown peer to the back of its own probe queue.
- **The cross-arm test asserts ordering only.** Its comment says the flatness of repeated mentions
  is pinned on the wired announce-merge path — true, in `test/rpc.snapshot-merge-flatness.spec.ts`.
  If that file is ever dropped, the comment must be corrected.
- **The new flatness spec is core-profile only.** Stated in its header comment: every list in its
  fixture is one id long, so the profile-split merge caps are inert. Worth a reviewer's judgement
  on whether that is the right call.
- **The eviction test shares one sparsity model where the cross-arm test isolates them**, and the
  two comments say why each is right for its own subject (`enforceCapacity` compares scores as
  *stored*, under one service-wide model; the properties test is comparing base scores, so a shared
  model would let KDE state decide). A reviewer disagreeing with either should say which.
- **The eviction test's derived numbers (1.0800 / 1.1681) are closer together than the design
  ticket's measured 1.0449 / 0.8619**, because the gossiped arm is scored first from the pristine
  model while every success is scored under rising occupancy at the same x. That is the
  conservative order and it is commented at the site, but it does mean the margin is ~8%, not ~21%.
