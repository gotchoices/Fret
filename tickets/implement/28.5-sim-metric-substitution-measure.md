## Why this is needed

`test/simulation.routing.spec.ts` guards routing *direction* (inverting the selector's
preference moves p90 hops from 2 to ~19) but not metric *quality*. On unbounded stores,
substituting `clockwiseDistance` or XOR for `minDistance` moved neither the success rate nor
the p90 hop count — every peer knows a large near-uniform slice of the ring, so greedy routing
lands in 1–2 hops under any roughly-monotone metric.

The prereq work (`sim-capacity-sweep`, landed) gave the sim real relevance scoring and a
capacity-bounded eviction, so stores can now be made sparse. Sparse stores should give a bad
metric somewhere to fail. Nobody has measured whether they actually do.

## The one design correction that must survive

The parent ticket said "assert p90 hops >= 3". **That is a lower bound and cannot bite** — a
worse metric makes routes *longer*, moving p90 up and away from it. `p90 >= 3` is a *headroom*
claim ("this case is genuinely multi-hop"), the same role `knowledgeFraction < 0.5` plays in the
existing n=1000 case. The biting assertion has to be a p90 **upper** bound, or a success floor a
substituted metric actually breaches. So the capacity must be picked from the substituted-metric
numbers — which is exactly what this ticket measures.

## Shipped-metric baseline already measured (prereq's capacity sweep)

n=1000, `profileMix: { edge: 1, core: 0 }`, 100 routes, 4 s convergence, seeds 1 / 4242 / 99 /
20260820, `churnRatePerSec: 0`. Every store saturates at the cap, so knowledge = `capacity / n`.

| cap | knowledge | success | p90 hops |
|---|---|---|---|
| 20 | 2.0% | 89–97%  | 15–19 |
| 24 | 2.4% | 99–100% | 12–15 |
| 28 | 2.8% | 98–100% |  9–12 |
| 32 | 3.2% | 100%    |  7–8  |

Runtime: one n=1000 run ≈ 11 s wall; one n=200 run ≈ 1.5 s.

Run from `packages/fret`:

```

```

Run that **one** command three times:

- unmodified
- with `minDistance` in `src/ring/distance.ts` returning `clockwiseDistance(a, b)`
- with `minDistance` returning a XOR fold

Three process runs, not nine. There is no injection seam — `chooseNextHop` imports `minDistance`
directly (`src/selector/next-hop.ts:2`, used at `:206`, `:214`, `:289`) — so temporarily editing
`distance.ts` is how the 2026-08-20 table was produced too.

**Caveat that must be recorded with the numbers:** `minDistance` is not selector-only. The
relevance sparsity model (`normalizedLogDistance`) and the sim's `nearRadiusFor` read it as well,
so substituting it changes eviction shape *and* hop choice. Acceptable for a bite demonstration
(the original table was produced the same way), but it must be stated in the caption or a future
reader will read the rows as a pure selector comparison. Do **not** try to narrow the
substitution to the selector; adding an injection seam is a separate ticket.
