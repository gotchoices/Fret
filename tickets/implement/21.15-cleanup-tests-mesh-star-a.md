## The helper (already landed, do not redo)

`packages/fret/test/helpers/mesh.ts` exists, type-checks, and is proven end-to-end by
`test/route.maybeact.integration.spec.ts`, which was migrated onto it and passes. Read that spec
first — it is the worked example. Surface:

```ts
export type Topology = 'star' | 'line' | 'full'
export async function buildMesh(count: number, opts?: { factory?: NodeFactory }): Promise<Mesh>

interface Mesh {
	readonly nodes: Libp2p[]
	readonly ids: string[]            // nodes[i].peerId.toString(), precomputed
	readonly services: FretService[]  // empty until addServices()
	connect(topology: Topology): Promise<void>
	addServices(cfg: Partial<FretConfig> | ((i: number, mesh: Mesh) => Partial<FretConfig>)): Promise<void>
	stop(opts?: { skip?: number[] }): Promise<void>
}
```

`buildMesh` defaults to `createMemNode` (memory transport, no identify). Both files in *this*
ticket use `createMemNode`, so **neither needs `opts.factory`.**

`connect` and `addServices` are separate, caller-ordered calls on purpose: dialing before
constructing services means `start()`'s `seedFromPeerStore` already sees the connections; dialing
after means the ring is discovered through `peer:connect`. **Preserve each rig's existing order
exactly** and keep the surrounding comment that explains it.

### `profile.behavior.spec.ts` — the largest mechanical win, lowest risk

Four rigs. All are **star first, then a bespoke service on node 0 only**, so `addServices` does
**not** apply: use `buildMesh(n)` + `await mesh.connect('star')` and leave the single-service
construction alone.

- `~128` `Edge snapshot caps ...` — 15 nodes, star, then `new CoreFretService(nodes[0], {profile:'edge', k:15, m:8})`.
- `~152` `Core snapshot caps ...` — 15 nodes, same shape, core profile.
- `~180` `Edge truncates received ...` — 22 nodes, star, sender service on node 0, then a **separate
  off-mesh receiver node** created and dialed to `nodes[0]` afterwards. The receiver is not part of
  the mesh; leave it hand-rolled and keep its own `receiverNode.stop()`.
- `~214` `Core truncates received ...` — same 22-node + off-mesh-receiver shape.

Teardown in all four is `await svc.stop(); await stopAll(nodes)` -> becomes `await mesh.stop()` for
the mesh half only. The bespoke service is **not** in `mesh.services`, so `mesh.stop()` will not
stop it — stop it explicitly, as today.

Everything else in this file builds a **single** node via the local `createService()` helper and is
out of scope.

### `churn.leave.spec.ts` — three rigs, top of file only

- `~63` `a graceful stop sends leave notices ...` — 4 nodes, **services first, then star**. Mid-test it
  does `await services[2].stop(); await nodes[2].stop()`, and tears down "all but index 2" at the
  end — that is exactly `await mesh.stop({ skip: [2] })`.
- `~99` `fan-out notifies peers beyond immediate S/P` — 8 nodes, `profile: 'core'`, services first
  then star; stops index 3 mid-test -> `await mesh.stop({ skip: [3] })`. Keep the long `NOTE:` about

- `~144` `oversized replacements array is truncated` — 3 nodes, **star only, no services at all**.
  `buildMesh(3)` + `connect('star')` + `mesh.stop()`.

Both service-bearing rigs use `bootstraps: [nodes[0].peerId.toString()]` for **every** node

(`() => ({ profile: 'edge', k: 7, bootstraps: [mesh.ids[0]!] })`); changing it changes what the rig
exercises.

The rigs pass their local `services` array into the file-level `allConverged` / `anyProgressed`
gates. `mesh.services` is a live array populated by `addServices`, so passing `mesh.services` works —
but confirm the gates still get the ids they need (`nodes.map(n => n.peerId.toString())` -> `mesh.ids`).

**Out of scope in this file:** everything from `describe('Leave amplification cap')` (~185) down —
