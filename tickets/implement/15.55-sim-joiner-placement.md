## Root cause (confirmed, see original fix ticket body for full measurement)

`packages/fret/test/simulation/fret-sim.ts`, `uniformCoord` (~line 237):

```ts
private uniformCoord(index: number): Uint8Array {
	const coord = new Uint8Array(32)
	const bigIndex = BigInt(index)
	const range = (1n << 256n) / BigInt(Math.max(1, this.nextPeerIndex))
	const val = bigIndex * range
	...
}
```

`handleJoin()` (~line 506) does `const index = this.nextPeerIndex++` — increments *before*
placing — so a joiner's coordinate divides by its own (post-increment) index instead of the
population it should be spread across. Every mid-run joiner lands at fraction
`index / (index + 1)` of the ring, converging on 1.0 and packing ever more tightly as the run
goes on. `scheduleBatchJoin` has the identical defect (it fires `'join'` events which call the
same `handleJoin()`).

`initialize()` is unaffected: `nextPeerIndex` is fixed at `config.n` for that whole loop (only
`handleJoin` mutates it), so initial peers land at genuinely uniform `0/n, 1/n, … (n-1)/n`.
`'clustered'` and `'skewed'` placement don't read `nextPeerIndex` and are unaffected.

## Chosen fix

Per the original ticket's own suggestion: stop using index arithmetic for joiners entirely.
Initial population keeps deterministic uniform spacing (`index / n`, where `n` is the *fixed*
`config.n`, not the mutable `nextPeerIndex`). Any joiner (churn join or batch join — both funnel
through `handleJoin()`) gets a **seeded random coordinate** instead — closer to how a real
network places a peer (hash of its id) and removes the dependence on a mutable counter entirely.

### Concrete edits to `fret-sim.ts`

1. Add a peer-source distinction so coord generation knows initial-vs-join without inferring it
   from `nextPeerIndex`:
   - `createPeer(index: number, isJoin: boolean)` — threads a new `isJoin` param down.
   - `addPeer(index: number, isJoin: boolean = false)` — same.
   - `initialize()`'s loop: `this.addPeer(i)` (unchanged call, `isJoin` defaults false).
   - `handleJoin()`: `const index = this.nextPeerIndex++; const peer = this.addPeer(index, true)`.

2. `generateCoord(index: number, isJoin: boolean)`:
   ```ts
   private generateCoord(index: number, isJoin: boolean): Uint8Array {
   	const placement = this.config.placement ?? 'uniform'
   	switch (placement) {
   		case 'uniform':
   			return isJoin ? this.randomCoord() : this.uniformCoord(index, this.config.n)
   		case 'clustered':
   			return this.clusteredCoord()
   		case 'skewed':
   			return this.skewedCoord()
   	}
   }
   ```

3. `uniformCoord` takes the population explicitly instead of reading the mutable field, so it can
   no longer observe `nextPeerIndex` at all:
   ```ts
   private uniformCoord(index: number, population: number): Uint8Array {
   	const coord = new Uint8Array(32)
   	const bigIndex = BigInt(index)
   	const range = (1n << 256n) / BigInt(Math.max(1, population))
   	const val = bigIndex * range
   	for (let i = 0; i < 32; i++) {
   		coord[31 - i] = Number((val >> BigInt(i * 8)) & 0xffn)
   	}
   	return coord
   }
   ```

4. New method, reuses the existing RNG (same one `clusteredCoord`'s center picks and
   `skewedCoord` already draw from, so determinism/replay is preserved):
   ```ts
   /** Seeded-random ring position for a mid-run joiner — models placement by hash of peer id. */
   private randomCoord(): Uint8Array {
   	return bigintToCoord(this.rng.nextBigInt(256))
   }
   ```
   (`bigintToCoord` already exists as a module-level helper at the bottom of the file — reuse it,
   don't duplicate the byte-packing loop.)

No other call sites construct `SimPeer`/call `createPeer`/`addPeer` — confirmed by reading the
whole file during the fix-stage investigation.

Shape:
```ts
it('uniform placement keeps joiners spread across the ring', () => {
	const sim = new FretSimulation({
		seed: <fixed>,
		n: 40,
		k: 15,
		m: 8,
		churnRatePerSec: 2,
		stabilizationIntervalMs: 500,
		durationMs: 10000,
		placement: 'uniform', // (default, but explicit)
	})
	sim.initialize()
	sim.scheduleBatchJoin(10, 3000)
	while (sim.scheduler.pending() > 0) {
		const evt = sim.scheduler.nextEvent()
		if (!evt || evt.time > 10000) break
		sim.processEvent(evt)
	}

	// Read alive peers' coords, sort on the ring, measure max gap between adjacent peers.
	const alive = Array.from(sim.getPeers().values()).filter((p) => p.alive)
	const coordsBig = alive.map((p) => coordToBigInt(p.coord)).sort((a, b) => (a < b ? -1 : a > b ? 1 : 0))
	const ringSize = 1n << 256n
	let maxGap = 0n
	for (let i = 0; i < coordsBig.length; i++) {
		const next = coordsBig[(i + 1) % coordsBig.length]!
		const cur = coordsBig[i]!
		const gap = i === coordsBig.length - 1 ? ringSize - cur + next : next - cur
		if (gap > maxGap) maxGap = gap
	}
	const uniformSpacing = ringSize / BigInt(coordsBig.length)
	// "small multiple" per the ticket — pick a measured, generous bound (e.g. 8x) rather than
	// a tight one; random placement has real variance (birthday-paradox-style gaps are
	// expected occasionally), this test's job is to catch the *systematic* packing defect,
	// not to assert near-perfect uniformity.
	const maxAllowed = uniformSpacing * 8n
	if (maxGap > maxAllowed) {
		throw new Error(`Largest gap ${maxGap} exceeds ${maxAllowed} (8x uniform spacing ${uniformSpacing})`)
	}
})
```
Needs a small helper `coordToBigInt(coord: Uint8Array): bigint` (big-endian assemble) — check
whether one already exists in the test helpers (`test/simulation/` — `bigintToCoord`'s inverse)
before writing a new one; if not, a short local helper in the spec file is fine.

**Before picking the `8x` (or whatever) multiplier**: run the test once with logging of the
actual max gap / uniform spacing ratio across a couple of seeds and set the bound from what's
actually measured, generous enough not to flake on RNG variance — don't just guess a constant.
This mirrors how the original fix ticket's own numbers were measured (10.0% vs 2.5% ideal gap),
so pick a bound with the same rigor.
