### Parser behavior per field (from `makeSnapshotParser` / `parseSample`, verified)

None of these fields can reject the message. Each is neutralized on its own.

- `sample` — non-array (including missing) → `[]`. Otherwise `slice(0, cap)` first, then each
  entry must be a plain object carrying `id: string`, `coord: string`, a finite `relevance`, and
  a `coord` that survives `base64urlToCoord` (which requires exactly 32 decoded bytes). A failing
  entry is **skipped and logged** — never a message-level reject.
- `size_estimate` / `confidence` — `finiteNumberOr(..., undefined)`; when the value is not a
  finite number the key is **deleted** from the outgoing object, not set to `0` or `undefined`.
  Present-and-absent are different things to the receiver, which gates on "both positive" before
  feeding the size estimator.
- `metadata` — kept only when it is a non-null, non-array object; otherwise **deleted**.
- `sig` and `v` are deliberately unchecked. Do not add rows asserting they reject. A row
  asserting a wrong-typed `sig` or an unexpected `v` still *serves* documents that decision and
  is welcome.

`snapshot(over)` (the base body builder in the drop-hooks describe) sets `sig: ''` and both id
lists but carries none of these fields, so "missing" rows are the base body unchanged and
"present" rows are a plain override.

A valid 32-byte `coord` for a sample entry comes from `coordToBase64url` over a 32-byte
`Uint8Array` — `COORD_BYTES` in `src/ring/hash.ts` is 32, and `coordToBase64url` is already
imported by the spec. A too-short or too-long array is what makes the wrong-width row fail
`base64urlToCoord`.

## Tests to add

Append rows to the existing announce table. Every row is a **normalize** row: the message is
still answered `{ok: true}`, the seam closes (never aborts), `reasons` stays empty, `onAnnounce`
runs exactly once, and the assertion is on **what reached `onAnnounce`** — not merely that it
ran. Assert the release *arm*, not only the count.

- `sample`: non-array (number, string, object, `null`) and missing → `[]`.
- `sample` per-entry vetting, one row each, each asserting the bad entry is **absent while its
  siblings survive** (so the row proves a skip, not a message-level drop): entry that is not a
  plain object (number / string / `null` / array); `id` missing or not a string; `coord` missing
  or not a string; `relevance` missing, a string, or `null`; `coord` that decodes to the wrong
  width (both too short and too long are worth a row, since that is the check
  `base64urlToCoord` actually performs).
- `sample` over cap: 10 well-formed entries against the cap of 8 keeps exactly the first 8, in
  order.
- `size_estimate` and `confidence`, each: wrong type (string), `null`, and missing → the key is
  **absent** from the snapshot `onAnnounce` received (`'size_estimate' in snap === false`), not
  present-and-zero. One row each for a valid finite value surviving unchanged, so the deletion
  rows are not vacuously passing.
- `metadata`: array, `null`, number, string, and missing → key **absent**. A plain object
  survives unchanged.
- Optional, documenting the deliberate non-checks: a wrong-typed `sig` and an unexpected `v`
  still normalize and serve.
