## What already landed

- `FretService.streamCaps()` (`fret-service.ts`, immediately after `mergeSnapshotCaps()`) returns
  `{ maxInboundStreams: 128, maxOutboundStreams: 256 }` for the `core` profile and
  `{ maxInboundStreams: 32, maxOutboundStreams: 64 }` otherwise. Hard-coded literals, no config
  knob, doc comment saying it is the single source of the numbers.
- `registerRpcHandler` (`protocols.ts`) takes `opts: { closeBudgetMs?: number } & StreamCaps` and
  passes `{ maxInboundStreams, maxOutboundStreams }` as `node.handle`'s third argument.
  `StreamCaps` is a new exported interface in the same module (both fields optional).
- Both `registerJsonHandler` option interfaces (`JsonRequestHandlerOpts`,
  `JsonReplyOnlyHandlerOpts`) carry the two optional numbers beside `closeBudgetMs`, and the
  implementation forwards all three.
- Each of the four registrar functions gained **one optional trailing parameter**,
  `streamCaps: StreamCaps = {}`, forwarded verbatim: `registerNeighbors` (into **both** protocols
  it registers — the reply-only `PROTOCOL_NEIGHBORS` and, under `if (onAnnounce)`,
  `PROTOCOL_NEIGHBORS_ANNOUNCE`), `registerLeave`, `registerPing`, `registerMaybeAct`.
- `registerRpcHandlers` (`fret-service.ts`) computes `const streamCaps = this.streamCaps()` at its
  top and passes it as the last argument to all four registrar calls. It is on the `start()` path,
  so a start→stop→start cycle re-applies it.
- `docs/fret.md` *Stream management* — the "FRET passes no `maxInboundStreams`" bullet is replaced
  with the implemented split, the inflight-binds-first ordering, the per-node-vs-per-connection
  arithmetic, and the Core↔Edge asymmetry note. The dead `debt-inbound-stream-caps-unimplemented`
  pointer is gone.

## The two tests to write

### Cap enforcement plus the sender-side outcome

Register a handler at a deliberately small cap (call `registerRpcHandler` directly with, say,
`maxInboundStreams: 2`) and drive N+1 concurrent inbound streams on **one** connection between two
in-memory nodes (`test/helpers/libp2p.ts`). Assert the excess stream is refused, and record what
the sender's `RpcOutcome` actually is.

This one case pins three things at once: that the caps reach `node.handle` at all; the exact
off-by-one; and that a remote's inbound refusal surfaces to the sender as `unreachable` — the
residual the sibling `local-limit-rpc-outcome` ticket documented — so if a future libp2p version
*does* propagate the reason, this test fails and the residual gets revisited.

**The off-by-one must be pinned by observation, not by reading libp2p's source.** The comparison is
`streamCount > limit` over `connection.streams` filtered by protocol and direction (`countStreams`
in libp2p's `connection.js`), and whether the stream being admitted is already in that collection at
check time was never verified — so whether the cap admits `limit` or `limit + 1` concurrent streams
is *unknown*. Write the assertion against what the run does. Do not derive the number from the
library source and then assert it.

### Profile split

A cheap spy on `node.handle` asserting the service passes Core 128/256 and Edge 32/64 through for
**all five** protocols — in the spirit of the acceptance-cap specs in
`test/rpc.snapshot-merge-cap.spec.ts`. This is what actually pins the profile split.

It must also cover the **start→stop→start** case: `stop()` unhandles all five protocols and
`start()` re-registers them, so assert the caps are still applied after a full cycle rather than
assuming it.
