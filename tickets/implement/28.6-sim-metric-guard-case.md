## Measured substitution table

Measured 2026-08-21 by `28.5-sim-metric-substitution-measure`. All runs: `n: 1000`,
`profileMix: { edge: 1, core: 0 }`, `k: 15`, `m: 8`, `churnRatePerSec: 0`,
`stabilizationIntervalMs: 500`, 4 s convergence, 100 routes, `capacity` set as shown. p90 and
max are over **successful routes only** (`successfulRouteHops`), which matters below. One cell
costs ~5–7 s wall.

**Caveat — these rows are not a pure selector comparison.** The substitution was made by editing
`minDistance` in `src/ring/distance.ts`, because there is no injection seam (`chooseNextHop`
imports it directly). `minDistance` is not selector-only: the relevance sparsity model
(`normalizedLogDistance`) and the sim's `nearRadiusFor` read it too, so each substituted row
changes *eviction shape* as well as hop choice. That is acceptable for demonstrating that a wrong
metric is detectable, and it is how the 2026-08-20 table in the spec doc-block was produced too,
but do not describe these rows as isolating the selector. Narrowing the substitution needs an
injection seam, which is a separate ticket.

### The finding that changes the guard's shape

**A hop bound alone cannot catch XOR — it catches only clockwise-only. The success floor is what
catches XOR.** XOR's p90 is *lower* than the shipped metric's (5–7 vs 7–8 at cap 32), not higher,
because p90 is taken over successful routes only and XOR simply *fails* the hard routes: 60–77%
success against the shipped 100%. Its surviving routes are the easy ones, so the hop distribution
it reports is flattering. Clockwise-only fails the other way — it keeps most routes alive (83–90%)
but drags them the long way round the ring, p90 17–21 against the shipped 7–8.

So the two substituted metrics are caught by **two different assertions**, and the case needs both:

- a p90 hop **upper** bound catches clockwise-only,
- a success **floor** catches XOR (and clockwise-only again, more weakly).

### Recommendation — `capacity: 32`, assert `success >= 0.95` and `p90 <= 12`

Cap 32 opens the widest gap on both axes and is the only cap where the shipped metric measured
100% success on every seed (no variance to leave room for):

| axis | shipped (4 seeds) | worst substituted | recommended threshold |
|---|---|---|---|
| success | 100% | 90% (clockwise-only, seed 1) | `>= 0.95` — 5 points below shipped, 5 above worst substituted |
| p90 hops | 7–8 | 17 (clockwise-only, seed 20260820) | `<= 12` — 50% above shipped worst, 5 below substituted best |

Cap 28 also works but is tighter on both axes (shipped success dips to 98%, shipped p90 reaches
12 against a clockwise-only floor of 17), so it leaves less room for seed variation than 32 does.

Headroom claim worth keeping alongside, not as the guard: at cap 32 the shipped p90 is 7–8, so
`p90 >= 3` holds comfortably and states that this case is genuinely multi-hop — the same role
`knowledgeFraction < 0.5` plays in the existing n=1000 case. Knowledge is 3.2% here (every store
saturates at the cap, so knowledge is `capacity / n`).

**A usable gap does exist**, so the "ship no threshold" branch of this ticket does not apply.

## The guard

A new case **inside `test/simulation.routing.spec.ts`** — not a new spec file. That spec's
doc-block is one of the places stating the limit being closed, so the case and the retracted
caveat get edited together.

- capacity-bounded sparse ring at the cap the prereq recommends, `n: 1000`,
  `profileMix: { edge: 1, core: 0 }`.
- **The biting assertion is a p90 hop *upper* bound** set inside the gap the prereq measured
  between the shipped metric and the substituted ones — or the success floor, if a substituted
  metric drops success below 95%. A `p90 >= 3` assertion is a *headroom* claim only (a worse
  metric moves p90 up, away from it), so keep it if useful but do not count it as the guard.
- **If the prereq reports no usable gap at any cap, ship no threshold.** Record its numbers in
  the spec doc-block, repoint the stale references to say what is now actually true, and hand off
  saying the guard is not writable and why. That is a complete outcome for this ticket.

### Traps

- **The new case cannot reuse `MAX_P90_HOPS`** (`simulation.routing.spec.ts:86`). It is 6 and
  every existing case asserts p90 *at most* 6; this case's shipped p90 is 7–12. It needs its own
  case-local constant, named and commented as a separate bound, **not** a loosening of the shared
  one.
- The spec already has every helper needed — no new scaffolding. `measureRouting(config)` at
  `:97` returns `{ successRate, p90Hops, maxHops, attempts, knowledgeFraction }`; plus
  `baseConfig(overrides)`, `pump(sim, uptoMs)`, `report(label, result)`. The `describe` block sets
  `this.timeout(120000)`, and a single-seed n=1000 run is ≈ 11 s.
- `SimConfig.capacity?: number` already exists (`test/simulation/fret-sim.ts:83`) and is honoured
  at all four `enforceCapacity` call sites, so the new case is a config override, not a harness
  change.

## What this unblocks — state in the handoff, do not build

- Tuning `CONNECTED_SLACK_ORDERS` / `QUALITY_SLACK_ORDERS` in `src/selector/next-hop.ts`. A slack
  is a tie-break between candidates close in distance; with routes two hops long there are no
  ties to break, which is why that `NOTE:` has deferred the tuning twice.
- The selector's far-cost branch generally: per the `nearRadiusFor` `NOTE:`, the sim's radius
  lands near a third of maximum distance at current store sizes, so most candidates take the
  *near* branch, where the connected allowance and backoff term are inert. Sparse stores shrink
  `store.size()`, which is that radius's own denominator.
