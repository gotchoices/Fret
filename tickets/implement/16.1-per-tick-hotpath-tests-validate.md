## Facts worth not re-deriving

- A "maintenance cycle" is the loop tick body — `seedFromPeerStore()` -> `seedFromBootstraps()`
  -> `stabilizeOnce()`. `stabilizeOnce` never seeds. The spec has a local `cycle()` helper for it.
- `buildMaintenanceRig`'s `seedPeers` writes to the FRET store only, so those peers are invisible
  to `seedFromPeerStore`. The spec's own `seedPeerStore()` helper writes to the **libp2p**
  peerStore (`node.peerStore.merge(pid, { multiaddrs: [...] })`), which is what that pass walks.
- Peers seeded through the peerStore land `unknown`, so a tick's phase 2 tries to classify them
  with real dials. The spec clamps `FretService.STABILIZE_TICK_BUDGET_MS` to 50 ms in a
  `beforeEach` and restores it in an `afterEach` to keep that deterministic and fast. It is a
  static, so a leaked override would poison later specs — if the suite shows unrelated timing
  failures *after* this file, suspect that restore first.
- Capacity numbers: `enforceCapacity` protects self plus up to `max(2, m) - 1` live members per
  side and protection outranks the cap, so the spec uses `k: 7` (m = 4, protected set ≤ 7) with
  `capacity: 20` and 40 seeded peers. Do not lower the capacity — the over-capacity-by-protection
  case is already pinned in `test/relevance.eviction.spec.ts` and must not be re-pinned here.
