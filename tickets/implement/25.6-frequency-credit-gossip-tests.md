### Service-level flatness test

`noteDiscovered` × 500 == `noteDiscovered` × 1 is trivially true at the unit level, so assert it on
the **wired** path: merge the same announce snapshot 500 times into one service and read the named
peer's stored `relevance`, `accessCount` and `lastAccess` — all three unchanged from after the
first merge.

`test/rpc.snapshot-merge-cap.spec.ts` is the cheaper host and its rig was read this run:

- `merge(svc, FROM, parsed(svc, body))` drives `mergeAnnounceSnapshot` directly on an **unstarted**
  service (`new CoreFretService(node, { profile, networkName: NETWORK })` in that file's per-profile
  `beforeEach`) — no stabilization loop scoring underneath the assertions, and the merge's detached
  tail is quiet on an unstarted service.
- `parsed(s, body)` runs the body through `makeSnapshotParser(capsOf(s))`, the same parser
  production wires in, and asserts the parse did not reject.
- Fixture ids come from `peerIdStr(n)`; seeds 60–184 are taken (`FROM` 60, `OVER_SUCC` 61–100,
  `OVER_PRED` 101–140, `OVER_SAMPLE` 141–160, `GOOD_1..4` 181–184). Use a fresh seed and keep the
  "fixture ids are distinct" test in that file true.
- Read the stored entry with `svc.getStore().getById(id)`.
- Driving the *registered* handler instead means minding the inbound announce token bucket; the
  merge method avoids that entirely. Prefer it.
- Note that block's `countUpserts` **stacks** wrappers and never restores — a flatness test does not
  need it, but do not install it twice.

A flatness test does not really belong to a file about *caps*, so a small new spec importing the
same helpers (`test/helpers/rpc-fuzz.ts` exports `NETWORK`, `peerIdStr`, `sampleCoord`, `json`,
`sleep`; `test/helpers/libp2p.ts` exports `createMemNode`, `stopAll`) is also reasonable. Either
host is acceptable — say which in the handoff.

### Eviction test, `test/relevance.eviction.spec.ts`

The user-visible half: a peer with many recorded successes must **survive** a capacity squeeze
against a never-contacted peer named in many snapshots. That spec already has the rig — build on it:

- `seededService({m, capacity})` — starts then immediately stops, so no stabilization tick scores
  underneath the assertions; self is seeded `member` at relevance 0 by the real `start()` path.
- `place(svc, peers)` — direct store writes (`upsert` then `update`), for state a snapshot cannot
  express; `records(peers)` builds `SerializedPeerEntry[]` via `serializedPeer` from
  `test/helpers/serialized-table.js`.
- `enforce(svc)` — `await svc.importTable(tableOf([], 'enforce-trigger'))`, an empty table purely to
  trigger the private `enforceCapacity`.
- `survivors(svc)` → `svc.getStore().list().map(e => e.id)`; plus `ringOffset` from
  `test/helpers/ring.js` and `standardLayout` / `NEAR_IDS` for placement far from self.
- Place both peers **outside the protection set** (`2m + 1` ids around self), or protection rather
  than relevance decides the outcome.
- `enforceCapacity` compares *stored* scores taken under different KDE states, so hold the sparsity
  model fixed or assert an ordering robust to it. The plan ticket measured 1.0449 (contacted) vs
  0.8619 (gossiped) on a shared model — same ordering, lower magnitudes than the isolated-model
  case.
- Every relevance in a fixture must be **distinct**: equal-relevance entries evict in
  `Array.prototype.sort` order, which is not a contract.

## Carry into the review handoff

- **`noteDiscovered` returning `boolean` was the optional improvement in the source ticket, and it
  was taken.** Worth a reviewer's eye: the four merge loops now push to their `discovered` /
  `announced` array on that return value instead of a pre-`upsert` `getById`. Behavior is
  equivalent because self is always already in the store (seeded `member`), so the self early-return
  cannot swallow a genuinely-new id.
- **An imported pre-change snapshot restores inflated frequency.** `accessCount` is already in
  `SerializedPeerEntry`, so there is no schema change, but the field now means "contacts" where it
  used to mean "contacts + mentions". Accepted and self-correcting — relevance is rewritten on the
  next scoring call — and deliberately not migrated.
- **The already-held arm no longer refreshes `coord`.** The five switched sites all passed a
  coordinate freshly derived from the peer id (`hashPeerId(peerIdFromString(pid))`), and a ring
  coordinate is *defined* as that hash, so the refresh was writing back the identical bytes. Stated
  because it is a real behavior difference, not because it is suspected to matter.
- **Not refreshing `lastAccess` on the already-held arm is the intended change, not a side effect.**
  It is the ordering key for the unknown-classification probe rotation (ascending `lastAccess`), so
  the old refresh sank a heavily-gossiped unknown peer to the back of its own probe queue.
- **The cross-arm test asserts ordering only.** Its comment says the flatness of repeated mentions
  is pinned on the wired announce-merge path — that claim is only true once the service-level
  flatness test above exists. If that test is dropped, the comment must be corrected.
