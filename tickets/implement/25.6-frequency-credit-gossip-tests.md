### `test/relevance.eviction.spec.ts` — rig, verified by reading

Helpers are exactly as the ticket described. Concretely:

- `seededService({m, capacity})` → `new FretService(node, {networkName: NETWORK, m, capacity})`,
  `start()` then `stop()`. Assigns the module-level `svc` so `afterEach` stops it.
- `place(svc, peers)` writes `store.upsert(id, coord)` then
  `store.update(id, {relevance, membership: p.membership ?? 'member', state: p.state ?? 'disconnected'})`.
  So **relevance is written as a literal number** — see the caveat below.
- `records(peers)` → `serializedPeer(id, coord, {relevance, membership})` from
  `test/helpers/serialized-table.js`; `tableOf(entries, label?)` wraps them.
- `enforce(svc)` = `await svc.importTable(tableOf([], 'enforce-trigger'))`.
- `survivors(svc)` = `svc.getStore().list().map(e => e.id)`.
- `Placed` interface: `{id, coord, relevance, membership?, state?}`.
- `standardLayout(self)` = near ±1/±2 at relevance 0.01–0.04 + `far-1..far-6` at
  `ringOffset(self, (i+1)*1000)` and relevance 1.0–6.0. `NEAR_IDS` names the four near ones.
- Existing cases all use `m: 3`, so the protected set is self + 3 live members clockwise + 3
  counter-clockwise. Under `standardLayout` the 3rd member each side is already a *far* peer
  (`far-1` clockwise, `far-6` by wrap counter-clockwise). **To sit outside protection, the two
  fixture peers must be at least the 4th live member on their side** — e.g. keep the four near
  peers in place and put the contacted/gossiped pair among the far ring at `*1000` offsets, or
  raise `capacity` and add more near peers. Do not reuse `far-1` / `far-6`.
- Every relevance in a fixture must be distinct (the file states this and the existing fixtures
  respect it).

**The one real design decision left.** `place()` takes a literal relevance, so a test that
hand-writes `1.0449` / `0.8619` would be asserting on numbers copied from the plan ticket rather
than on the code that produces them — it would pass even if `recordSuccess` / `initialRelevance`
were deleted. Compute the two values instead: import `recordSuccess` / `initialRelevance` (and
`createSparsityModel`) from `src/store/relevance.js`, build **one shared** model, derive the
contacted entry's relevance from N `recordSuccess` calls and the gossiped entry's from a single
`initialRelevance`, then feed those numbers into `place()`. A shared model is right here (unlike
the cross-arm test in `relevance.properties.spec.ts`, which needs isolated models): eviction
compares stored scores taken under a shared service-wide model, which is the property under test.
Then assert the contacted peer is in `survivors()` and the gossiped one is not. See
`test/relevance.properties.spec.ts`'s `describe('gossip vs proven contact')` block, written in
run 1, for the exact call shapes.

## Carry into the review handoff

- **`noteDiscovered` returning `boolean` was the optional improvement in the source ticket, and it
  was taken.** Worth a reviewer's eye: the four merge loops now push to their `discovered` /
  `announced` array on that return value instead of a pre-`upsert` `getById`. Behavior is
  equivalent because self is always already in the store (seeded `member`), so the self early-return
  cannot swallow a genuinely-new id.
- **An imported pre-change snapshot restores inflated frequency.** `accessCount` is already in
  `SerializedPeerEntry`, so there is no schema change, but the field now means "contacts" where it
  used to mean "contacts + mentions". Accepted and self-correcting — relevance is rewritten on the
  next scoring call — and deliberately not migrated.
- **The already-held arm no longer refreshes `coord`.** The five switched sites all passed a
  coordinate freshly derived from the peer id (`hashPeerId(peerIdFromString(pid))`), and a ring
  coordinate is *defined* as that hash, so the refresh was writing back the identical bytes. Stated
  because it is a real behavior difference, not because it is suspected to matter.
- **Not refreshing `lastAccess` on the already-held arm is the intended change, not a side effect.**
  It is the ordering key for the unknown-classification probe rotation (ascending `lastAccess`), so
  the old refresh sank a heavily-gossiped unknown peer to the back of its own probe queue.
- **The cross-arm test asserts ordering only.** Its comment says the flatness of repeated mentions
  is pinned on the wired announce-merge path — that claim is only true once the service-level
  flatness test above exists. If that test is dropped, the comment must be corrected.
