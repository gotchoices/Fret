## Work remaining

### Eviction test, `packages/fret/test/relevance.eviction.spec.ts`

The user-visible half of the whole change: a peer with many recorded successes must **survive** a
capacity squeeze against a never-contacted peer named in many snapshots. That spec already has the
rig; build on it. Rig facts, verified by reading in run 2 — do not re-read the file to rediscover
these:

- `seededService({m, capacity})` builds `new FretService(node, {networkName: NETWORK, m, capacity})`,
  calls `start()` then immediately `stop()`, so no stabilization tick scores underneath the
  assertions; self is seeded `member` at relevance 0 by the real `start()` path. It assigns the
  module-level `svc` so `afterEach` stops it.
- `place(svc, peers)` writes `store.upsert(id, coord)` then
  `store.update(id, {relevance, membership: p.membership ?? 'member', state: p.state ?? 'disconnected'})`.
  `Placed` is `{id, coord, relevance, membership?, state?}`.
- `records(peers)` builds `serializedPeer(id, coord, {relevance, membership})` from
  `test/helpers/serialized-table.js`; `tableOf(entries, label?)` wraps them.
- `enforce(svc)` is `await svc.importTable(tableOf([], 'enforce-trigger'))` — an empty table purely
  to trigger the private `enforceCapacity`.
- `survivors(svc)` is `svc.getStore().list().map(e => e.id)`.
- `standardLayout(self)` places near +-1/+-2 at relevance 0.01–0.04 plus `far-1..far-6` at
  `ringOffset(self, (i+1)*1000)` and relevance 1.0–6.0. `NEAR_IDS` names the four near ones.
  `ringOffset` comes from `test/helpers/ring.js`.
- Every relevance in a fixture must be **distinct** — equal-relevance entries evict in
  `Array.prototype.sort` order, which is not a contract. The file states this and its existing
  fixtures respect it.

**Placement — the protection trap.** Both fixture peers must sit **outside** the protection set
(self + `max(2, m)` live members each side), or protection rather than relevance decides the
outcome and the test proves nothing. Existing cases all use `m: 3`, and under `standardLayout` the
3rd live member on each side is already a *far* peer (`far-1` clockwise, `far-6` by wrap
counter-clockwise). So the pair must be at least the 4th live member on their side — e.g. keep the
four near peers and put the contacted/gossiped pair among the far ring at `*1000` offsets, and do
not reuse `far-1` / `far-6`.

**The one real design decision.** `place()` takes a *literal* relevance, so a test that hand-writes
the numbers from the plan ticket (1.0449 contacted vs 0.8619 gossiped) would be asserting on copied
constants and would still pass if `recordSuccess` / `initialRelevance` were deleted. Compute them
instead: import `recordSuccess` / `initialRelevance` / `createSparsityModel` from
`src/store/relevance.js`, build **one shared** model, derive the contacted entry's relevance from N
`recordSuccess` calls and the gossiped entry's from a single `initialRelevance`, then feed those
numbers into `place()`. A shared model is correct here — unlike the cross-arm test in
`relevance.properties.spec.ts`, which needs isolated ones — because `enforceCapacity` compares
*stored* scores taken under one service-wide model, which is the property under test. The plan
ticket measured 1.0449 vs 0.8619 on a shared model: same ordering as the isolated case, lower
magnitudes. See the `describe('gossip vs proven contact')` block in
`test/relevance.properties.spec.ts` for the exact call shapes (signatures:
`recordSuccess(entry, latencyMs, x, model, now)`, `initialRelevance(entry, x, model, now)`).

Then assert the contacted peer is in `survivors()` and the gossiped one is not.

## Carry into the review handoff

- **`noteDiscovered` returning `boolean` was the optional improvement in the source ticket, and it
  was taken.** Worth a reviewer's eye: the four merge loops (announce id lists ~1974 and sample
  ~1996; fetch ~2564 and ~2573 in `src/service/fret-service.ts`) now push to their `discovered` /
  `announced` array on that return value instead of a pre-`upsert` `getById`. Behavior is
  equivalent because self is always already in the store (seeded `member`), so the self
  early-return cannot swallow a genuinely-new id.
- **An imported pre-change snapshot restores inflated frequency.** `accessCount` is already in
  `SerializedPeerEntry`, so there is no schema change, but the field now means "contacts" where it
  used to mean "contacts + mentions". Accepted and self-correcting — relevance is rewritten on the
  next scoring call — and deliberately not migrated.
- **The already-held arm no longer refreshes `coord`.** The five switched sites all passed a
  coordinate freshly derived from the peer id (`hashPeerId(peerIdFromString(pid))`), and a ring
  coordinate is *defined* as that hash, so the refresh was writing back the identical bytes. Stated
  because it is a real behavior difference, not because it is suspected to matter.
- **Not refreshing `lastAccess` on the already-held arm is the intended change, not a side effect.**
  It is the ordering key for the unknown-classification probe rotation (ascending `lastAccess`), so
  the old refresh sank a heavily-gossiped unknown peer to the back of its own probe queue.
- **The cross-arm test asserts ordering only.** Its comment says the flatness of repeated mentions
  is pinned on the wired announce-merge path — that claim is now true, in
  `test/rpc.snapshot-merge-flatness.spec.ts`. If that file is ever dropped, the comment must be
  corrected.
- **The new flatness spec is core-profile only.** Stated in its header comment: every list in its
  fixture is one id long, so the profile-split merge caps are inert. Worth a reviewer's judgement
  on whether that is the right call.
