Second of two tickets split out of `stream-caps-profile-test` when that run crossed its token budget
before writing any test. **No `src/` change is asked for** — this is test-only. The sibling
`37.7-stream-caps-profile-spy-test` covers the profile-split spy test; the two are independent and
touch different new spec files.

## Why this arm is uncovered

`stream-caps-enforcement-test` landed `test/rpc.stream-caps.spec.ts`, which drives the **inbound**
cap for real over two transports (memory, and TCP + noise). It asserts the outbound arm only
*negatively* — a remote's refusal must not surface as `local-limit` — so nothing anywhere positively
drives this node's own outbound ceiling firing. That is the one arm of the stream-cap story with no
positive coverage at all, and it is the arm whose scoring rule (`local-limit` scores nothing) is the
one a regression would silently change.

## The test to write

Add one behavioral case (new spec, or a new `describe` in `test/rpc.stream-caps.spec.ts` — its
existing park-the-handler gate helper and two-transport table are directly reusable) that makes
`maxOutboundStreams` actually fire:

- Register a handler that parks (hold the reply on a gate, as the inbound case does).
- Open more concurrent **outbound** streams on **one connection** than the local cap allows. The cap
  is per protocol per connection, so dial once up front and reuse that connection — a second
  connection silently invalidates the case.
- Assert the refused sender gets `kind: 'local-limit'` — the `TooManyOutboundProtocolStreamsError`
  arm of `classify()` in `src/rpc/request.ts`, matched by `isStreamLimitError`.
- Assert it books **no contact strike**.
- Assert `diag.streamLimit` increments (single owner: `FretService.countStreamLimit`).

Rigging the local cap small (as the inbound case rigs `maxInboundStreams: 2`) keeps this a handful
of streams rather than a load test. Note the outbound cap is set on the **dialing** node's handler
registration for that protocol, not the responder's — confirm where libp2p reads it from before
building the rig.

## Also do: the symmetry sweep

`stream-caps-profile-test` also asked for a read-only confirm that "nothing in the codebase assumes
the two profiles are symmetric" — i.e. that no code path assumes a Core node's peer accepts as many
streams as it does. Neither prior ticket did it. It is a read-only sweep over `streamCaps()`'s
callers and the four registrar functions (`src/rpc/neighbors.ts`, `maybe-act.ts`, `leave.ts`,
`ping.ts`). If it turns up nothing, say so in the handoff; if it turns up an assumption, that is a
finding for a fresh ticket, not a fix to smuggle in here.
