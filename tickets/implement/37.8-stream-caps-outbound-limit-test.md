## Why this arm is uncovered

`stream-caps-enforcement-test` landed `test/rpc.stream-caps.spec.ts`, which drives the **inbound**
cap for real over two transports (memory, and TCP + noise). It asserts the outbound arm only
*negatively* — a remote's refusal must not surface as `local-limit` — so nothing anywhere positively
drives this node's own outbound ceiling firing. That is the one arm of the stream-cap story with no
positive coverage at all, and it is the arm whose scoring rule (`local-limit` scores nothing) is the
one a regression would silently change.

## The test to write

Add one behavioral case (new spec, or a new `describe` in `test/rpc.stream-caps.spec.ts` — its
existing park-the-handler gate helper and two-transport table are directly reusable) that makes
`maxOutboundStreams` actually fire:

- Register a handler that parks (hold the reply on a gate, as the inbound case does).
- Open more concurrent **outbound** streams on **one connection** than the local cap allows. The cap
  is per protocol per connection, so dial once up front and reuse that connection — a second
  connection silently invalidates the case.
- Assert the refused sender gets `kind: 'local-limit'` — the `TooManyOutboundProtocolStreamsError`
  arm of `classify()` in `src/rpc/request.ts`, matched by `isStreamLimitError`.
- Assert it books **no contact strike**.
- Assert `diag.streamLimit` increments (single owner: `FretService.countStreamLimit`).

Rigging the local cap small (as the inbound case rigs `maxInboundStreams: 2`) keeps this a handful
of streams rather than a load test. Note the outbound cap is set on the **dialing** node's handler
registration for that protocol, not the responder's — confirm where libp2p reads it from before
building the rig.

What that run established, so the next one does not re-derive it:

### Where libp2p reads `maxOutboundStreams` (the ticket's "confirm before building the rig")

`packages/fret/node_modules/libp2p/dist/src/connection.js:113-119`, inside `newStream`:

```js
const outgoingLimit = findOutgoingStreamLimit(muxedStream.protocol, this.components.registrar, options);
const streamCount = countStreams(muxedStream.protocol, 'outbound', this);
if (streamCount > outgoingLimit) {
    const err = new TooManyOutboundProtocolStreamsError(...);
    muxedStream.abort(err);
    throw err;
}
```

Three consequences for the rig:

- The limit comes from the **dialing** node's own `registrar` (its `node.handle` registration for
  that protocol), or from a `maxOutboundStreams` passed in the `newStream` options bag. FRET's
  `openRpcStream` does not pass one, so the rig must register the protocol **on the requester
  node** with a small `maxOutboundStreams` — a handler registration on the node that never serves
  a request. That is the mirror image of the existing inbound case, which registers on the
  responder. Worth a comment in the spec: registering a handler purely to set an outbound cap
  reads as a mistake otherwise.
- The comparison is `streamCount > outgoingLimit` over the connection's outbound streams for that
  protocol, exactly the shape the inbound case observed. Whether the stream being opened is
  already counted decides admit-`limit` vs admit-`limit + 1`; **observe it, do not derive it**, and
  write the number the test saw — the same rule the inbound case's `MAX_INBOUND` comment states.
- The check runs **after** `mss.select` negotiates the protocol, so a refused outbound stream has
  already reached the responder and its handler may have been entered before the local abort. The
  responder-side `entered` counter therefore may **not** equal the admitted count on this arm.
  Do not copy the inbound case's `admitted + refused === CONCURRENT` convergence poll unchanged —
  the sender-side settled outcomes are the reliable observable here.
- `findOutgoingStreamLimit`'s default when neither the registrar nor the options supply one was
  not read. Only matters if the rig ends up relying on a default; the rig should set the cap
  explicitly, so it should not.
