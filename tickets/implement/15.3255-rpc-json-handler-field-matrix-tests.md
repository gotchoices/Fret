Second of the two halves that `15.325-rpc-json-handler-tests` was split into. The `prereq:` is
purely a serialization hint — both halves edit `test/rpc.handler-fuzz.spec.ts` and would otherwise
collide; there is no logical dependency.

**Read the "Discovery" section of `15.325-rpc-json-handler-counter-tests` first.** It records the
seam's exact drop paths, the three `register*` signatures, which `validate.ts` rule rejects vs
normalizes per field, and the rig's helper line numbers. None of that is repeated here.

The one fact worth restating because it bounds this ticket's scope: **ping and the neighbors
request read no body**, so they have no body-level drop path. The field matrix therefore covers
exactly two inbound messages — the leave notice and the announce snapshot — plus maybeAct, whose
field-level rejections are already covered by the existing `parseRouteAndMaybeAct` unit table
(~line 484) and the wire `malformedMatrix()` (~line 698).

## Tests to add

- **Per field, per way of being wrong.** For the leave notice (`from`, `timestamp`,
  `replacements`) and the announce snapshot (`from`, `timestamp`, `successors`, `predecessors`,
  `sample`, `size_estimate`, `confidence`, `metadata`): wrong type, missing, and over cap. Each
  message must be dropped without throwing out of the handler and without leaking the stream, and
  the existing release-exactly-once invariant must hold. **Assert the arm, not merely the release
  count** — `close` on a body-level drop, `abort` on a frame-level failure. The count alone passes
  for both arms and so proves nothing about the rule.
  - Note the split: a *rejecting* field (`from`, `timestamp`) drops the whole message with no
    reply; a *normalizing* field (`replacements`, the id lists, `sample`, the advisory numerics,
    `metadata`) still answers `{ok: true}` with that field neutralized. Both are closes; assert
    what reached the callback (`onLeave` / `onAnnounce`) in the normalizing cases, not just the
    release arm.
  - Frame-level coverage for the abort arm: a truncated frame and an over-cap frame against
    `registerLeave`'s fixed 4096-byte cap. The over-cap case is refused at the length prefix
    (`readFramed`'s `onLength` hook), so it must **abort** and the body must never be pulled.
- **A snapshot carrying more ids than the profile cap.** Assert the parse+hash+upsert loop runs
  exactly `caps.*` times **by counting the loop's own work** — a spy on the store's `upsert` or on
  the hash — rather than by inferring it from the absence of a crash. This is the test that proves
  the parser's truncation and the merge loop's `slice` are the same numbers.
- **A `sample` entry with a short `coord`.** That entry is dropped (it fails
  `base64urlToCoord`) and the rest of the snapshot still merges — skip-and-log per entry, not
  reject-the-message. Assert both halves: the bad id is absent from what `onAnnounce` received, and
  the good ones are present.
