### What `validate.ts` does per field — reject vs normalize

**`parseLeaveNotice`** — a reject drops the whole message: the seam closes, no reply is written,
and `onLeave` never runs.

- `from` — must satisfy `isPeerIdString`. Wrong type, missing, or unparseable → **reject**.
- `timestamp` — must be a finite `number` (no coercion, so `'5'` and `null` both reject). Wrong
  type or missing → **reject**.
- `replacements` — `sanitizeReplacements`: any non-array (including missing) → `undefined`, i.e.
  the key is *deleted* from the notice rather than present-and-empty. Otherwise `slice(0, 12)`
  then a per-entry `isPeerIdString` filter; an empty or all-invalid result is also `undefined`.
  **Normalizes — the message still answers `{ok: true}`.**

**`makeSnapshotParser(caps)`** — same reject/normalize split.

- `from`, `timestamp` — **reject**, identical rules to leave.
- `successors` / `predecessors` — `boundedStringArray(value, cap)`: non-array (including missing)
  → `[]`; otherwise **truncate to `cap` first, then drop non-strings**. That order is deliberate
  and is itself worth a case: a crafted list of 100k non-strings must cost `cap` comparisons, not
  100k.
- `sample` — `parseSample`: non-array → `[]`; else `slice(0, cap)`, then each entry must be a plain
  object with `id: string`, `coord: string`, a finite `relevance`, and a `coord` that survives
  `base64urlToCoord` (exactly 32 decoded bytes). A failing entry is **skipped and logged**; it is
  never a message-level reject.
- `size_estimate` / `confidence` — `finiteNumberOr(..., undefined)`; when not finite the key is
  **deleted** from the outgoing object.
- `metadata` — kept only when it is a non-null, non-array object; otherwise **deleted**.
- `sig` and `v` — deliberately unchecked. Do not add cases asserting they reject.

So the matrix's three columns are not uniform: "over cap" is only meaningful for the four list
fields (`replacements`, `successors`, `predecessors`, `sample`), and "missing" collapses into
"wrong type" for every rejecting field. Write the table so each row states its own expectation
(`reject`, or `normalize-to <value>`) rather than assuming one shape per column.

### Frame-level arm (the aborts)

Body-level drops close. Frame-level failures abort:

- **Truncated frame** — a length prefix promising more bytes than follow. `readFramed` raises
  `FrameTruncationError`; `isFrameTruncationError` is already imported by the spec.
- **Over-cap frame against `registerLeave`'s fixed 4096** — refused in `readFramed`'s `onLength`
  hook the moment the varint prefix decodes, so it must abort **and the body must never be
  pulled**. `inboundStub` has no pull counter today; add one (increment inside the async
  iterator's `next()`, expose as `pulls`) so "never pulled" is *measured* rather than inferred.
  Same measure-do-not-infer rule `test/rpc.codec-properties.spec.ts` already applies to the codec.

### Counting the merge loop's own work

`onAnnounce` receives an already-parsed snapshot, so the parse+hash+upsert loop this ticket wants
to count is **not** inside `registerNeighbors` — it is `FretService.mergeAnnounceSnapshot`. Drive
that case at the service tier (the `CoreFretService` + `createMemNode()` rig at 727), spy on the
store's `upsert`, and send a snapshot carrying more ids than the Core merge caps (16 successors /
16 predecessors / 8 sample). The point of the case is that the parser's truncation and the merge
loop's `slice` are the same numbers, so it must count the loop's own calls rather than observe the
absence of a crash.

## Tests to add

- **Per field, per way of being wrong.** For the leave notice (`from`, `timestamp`,
  `replacements`) and the announce snapshot (`from`, `timestamp`, `successors`, `predecessors`,
  `sample`, `size_estimate`, `confidence`, `metadata`): wrong type, missing, and over cap. Each
  message must be dropped without throwing out of the handler and without leaking the stream, and
  the existing release-exactly-once invariant must hold. **Assert the arm, not merely the release
  count** — `close` on a body-level drop, `abort` on a frame-level failure. The count alone passes
  for both arms and so proves nothing about the rule.
  - Note the split: a *rejecting* field (`from`, `timestamp`) drops the whole message with no
    reply; a *normalizing* field (`replacements`, the id lists, `sample`, the advisory numerics,
    `metadata`) still answers `{ok: true}` with that field neutralized. Both are closes; assert
    what reached the callback (`onLeave` / `onAnnounce`) in the normalizing cases, not just the
    release arm.
  - Frame-level coverage for the abort arm: a truncated frame and an over-cap frame against
    `registerLeave`'s fixed 4096-byte cap. The over-cap case is refused at the length prefix
    (`readFramed`'s `onLength` hook), so it must **abort** and the body must never be pulled.
- **A snapshot carrying more ids than the profile cap.** Assert the parse+hash+upsert loop runs
  exactly `caps.*` times **by counting the loop's own work** — a spy on the store's `upsert` or on
  the hash — rather than by inferring it from the absence of a crash. This is the test that proves
  the parser's truncation and the merge loop's `slice` are the same numbers.
- **A `sample` entry with a short `coord`.** That entry is dropped (it fails
  `base64urlToCoord`) and the rest of the snapshot still merges — skip-and-log per entry, not
  reject-the-message. Assert both halves: the bad id is absent from what `onAnnounce` received, and
  the good ones are present.
