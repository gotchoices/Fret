## Determinism is the sharp trap

All scoring entry points default `now = Date.now()`. Every call must pass sim time explicitly or
same-seed replay diverges — surfacing as flaky thresholds, not errors. Writing
`lastAccess: simTime` *improves* determinism (`upsert` stamps wall-clock) but reorders
`reprobeDeadEntries`, which sorts ascending `lastAccess` — re-run
`test/simulation.partition.spec.ts`.

## Where sim time comes from at each site

Verified by reading the file: **`time` is not in scope at three of the four sites.**

- `processDeliveredMessage(msg)` takes only `msg`. Its caller `deliverMessages` holds the
  `const time`, but does not pass it down.
- `exchangeNeighborsDirect(peer, store, neighbors)` has no time parameter either.
- `handleConnect(peerId)` has no time parameter.

So each must read `this.scheduler.getCurrentTime()` itself. This is the main reason to build a
private helper `scoreMerge(storeOwnerId, store, id)` — it can read the clock once internally, so
the bus and instant merge paths cannot diverge on either the scoring rule or the timestamp.

## Required deviation from production; record it as a `NOTE:` at the merge sites (3 and 4)

The sim's kernel density estimate is fed by gossip because the sim has orders of magnitude fewer
contact events per peer than a real node does. Production's hearsay rule (score once at creation,
never observe the distance) degenerates here: only-proven-contact feeds at most about
`maxConnections` observations per peer, so at `alpha = 0.03` occupancy stays near 0, the ratio
stays above `sMax^(1/beta) ~= 2.63`, and every entry clamps at `sMax = 1.8` and ties — the same
degeneracy one layer down. Re-scoring an already-held entry on each merge (a deviation from
production's leave-it-alone rule for gossip) lets the bonus track growing occupancy.

## Edge cases (settled design; verify, don't re-derive)

- `capacity < 2m + 1`: protection outranks the cap — the store stays over capacity; the
  slice-based eviction cannot loop and must never evict a protected id. (Already true; keep it.)
- store smaller than `m`: the walk returns fewer per side; protection must not assume `m`.
- churn: a scoring call must tolerate `getById` returning `undefined`.
- a merge that skips a locally-`dead` entry skips its scoring too — otherwise the skip's point
  (no resurrection, deterministic `lastAccess`) is lost.
- bus mode and instant mode take the same scoring path (sites 3 and 4 must not diverge — hence the
  shared-helper suggestion).
- `capacity` unset (every existing sim spec): scoring writes relevance but nothing evicts —
  **no existing threshold may move**.

### Scoring idiom to copy (read off `test/simulation/liveness.ts`)

`LivenessModel.recordContactSuccess` is the shape to mirror — read it before writing `scoreMerge`:

```ts
const x = normalizedLogDistance(this.coordOf(selfId), entry.coord)
const scored = recordSuccess(entry, undefined, x, this.modelFor(selfId), time)
store.update(entry.id, { relevance: scored.relevance, /* …counters… */ })
```

Three details it settles that the body of this ticket only implies:

- the self-to-other distance is always `normalizedLogDistance(selfCoord, entryCoord)` — the peer
  whose store is being written is the "self" side, which is what makes site 4 need the per-side
  split the body calls for;
- `store.update(id, patch)` takes a partial patch, and the existing calls patch **only** the
  fields the helper actually recomputed (never spread the whole returned entry back);
- `time` is a **parameter**, not an injected clock, precisely because
  `scheduler.getCurrentTime()` and an event's own `time` are not the same number on the
  `processEvent` / `advanceTo` paths. `scoreMerge` reading the scheduler itself (what this
  ticket asks for) is therefore a deliberate difference from `LivenessModel`, not an oversight —
  say so in its doc comment, or the next reader will "fix" it to take a `time` argument.
