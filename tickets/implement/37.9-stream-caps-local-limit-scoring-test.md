Continuation of `stream-caps-outbound-limit-test`, which crossed its token budget after landing the
wire-behavior half. **No `src/` change is asked for** — this is test-only.

## What already landed (do not redo)

`packages/fret/test/rpc.stream-caps-outbound.spec.ts` — new spec, two cases (memory transport, and
TCP + noise), both passing, `npx tsc --noEmit` clean. It positively drives `maxOutboundStreams`:
the requester registers the protocol purely to declare its own outbound cap of 2, dials once, fires
4 concurrent requests against a parked handler on one connection, and asserts the 2 refused ones
come back `kind: 'local-limit'` while the 2 admitted ones answer once released.

Two things that run were **observed** there and are worth not re-deriving:

- libp2p counts the stream it is opening *before* comparing (`streamCount > outgoingLimit` in
  `Connection.newStream`), so a cap of N admits exactly N. A cap of **0** therefore makes a *single*
  outbound stream fire the limit — which is the lever that makes the arms below drivable without
  needing concurrency at all (see below).
- `findOutgoingStreamLimit` reads the cap off the **dialing** node's own `node.handle` registration
  for that protocol. FRET's `openRpcStream` passes no `maxOutboundStreams` option, so the registrar
  is the only lever.

## The symmetry sweep is DONE — result recorded here so nobody re-runs it

The prior ticket also asked for a read-only confirm that nothing in the codebase assumes a Core
node's peer accepts as many streams as it does. **Nothing does.** Evidence: `streamCaps()`
(`src/service/fret-service.ts:2087`) has exactly one caller, `registerRpcHandlers` (line 1277),
which forwards one object verbatim to all four registrar functions (`registerNeighbors`,
`registerMaybeAct`, `registerLeave`, `registerPing`). Each takes it as an opaque trailing
`StreamCaps` bag and spreads it straight into `registerRpcHandler` / `registerJsonHandler` →
`node.handle`. No site reads a *peer's* caps, derives one direction's number from the other, or
compares the two. This arm needs no further work.

## The two arms still uncovered

Both are about what the service does with a `local-limit` outcome, so both need a real
`FretService` rather than a bare `rpcRequest` — which is why they did not fit in the spec above.

- **It books no contact strike.** `local-limit` is our own ceiling firing before anything reached
  the wire, so it is evidence about this node, not the peer. Assert the peer's routing-table entry
  keeps `contactFailures: 0` and never reaches `dead`, across enough refusals to have crossed
  `deadAfterFailures` (3) had they been counted.
- **`diag.streamLimit` increments.** Single owner: `FretService.countStreamLimit`
  (`src/service/fret-service.ts:922`), reached from `noteRpcFailure` (~902), `pingWarmupTargets`
  (~1719) and `iterativeLookup` (~3407). Read it through the public `getDiagnostics()`.

### Rigging note (the part that needs a decision)

The service applies `this.streamCaps()` (Core 128/256, Edge 32/64) inside `registerRpcHandlers`, on
the `start()` path, and there is no config knob — so the rig has to override it. Two options, pick
whichever reads more honestly and say why in the handoff:

- after `start()`, `unhandle` one FRET protocol on the requester node and `handle` it again with
  `maxOutboundStreams: 0`; every outbound RPC on that protocol then refuses locally, with no
  concurrency needed. (This replaces that protocol's inbound handler on the requester, which is
  harmless if the requester never has to *serve* it in the case.)
- or stub `streamCaps` before `start()`.

Then drive an outbound RPC from the service to a peer it holds an entry for and assert both arms.
Prefer a path a real pass takes rather than reaching into a private method.
