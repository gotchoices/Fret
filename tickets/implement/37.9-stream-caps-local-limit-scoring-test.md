## What already landed (do not redo)

`packages/fret/test/rpc.stream-caps-outbound.spec.ts` — new spec, two cases (memory transport, and
TCP + noise), both passing, `npx tsc --noEmit` clean. It positively drives `maxOutboundStreams`:
the requester registers the protocol purely to declare its own outbound cap of 2, dials once, fires
4 concurrent requests against a parked handler on one connection, and asserts the 2 refused ones
come back `kind: 'local-limit'` while the 2 admitted ones answer once released.

Two observed facts worth not re-deriving:

- libp2p counts the stream it is opening *before* comparing (`streamCount > outgoingLimit` in
  `Connection.newStream`), so a cap of N admits exactly N. A cap of **0** therefore makes a *single*
  outbound stream fire the limit — the lever that makes the arms below drivable with no concurrency.
- `findOutgoingStreamLimit` reads the cap off the **dialing** node's own `node.handle` registration
  for that protocol. FRET's `openRpcStream` passes no `maxOutboundStreams` option, so the registrar
  is the only lever.

## The symmetry sweep is DONE — result recorded here so nobody re-runs it

Read-only confirm that nothing assumes a Core node's peer accepts as many streams as it does.
**Nothing does.** `streamCaps()` (`src/service/fret-service.ts:2087`) has exactly one caller,
`registerRpcHandlers` (line 1277), which forwards one object verbatim to all four registrar
functions (`registerNeighbors`, `registerMaybeAct`, `registerLeave`, `registerPing`). Each takes it
as an opaque trailing `StreamCaps` bag and spreads it into `registerRpcHandler` /
`registerJsonHandler` → `node.handle`. No site reads a *peer's* caps, derives one direction's
number from the other, or compares the two. This arm needs no further work.

## The two arms still uncovered

Both are about what the service does with a `local-limit` outcome, so both need a real
`FretService` rather than a bare `rpcRequest`.

- **It books no contact strike.** `local-limit` is our own ceiling firing before anything reached
  the wire — evidence about this node, not the peer. Assert the peer's routing-table entry keeps
  `contactFailures: 0` and never reaches `dead`, across enough refusals to have crossed
  `deadAfterFailures` (3) had they been counted.
- **`diag.streamLimit` increments.** Single owner: `FretService.countStreamLimit`
  (`src/service/fret-service.ts:922`). Read it through the public `getDiagnostics()`
  (line 534; `streamLimit` initialised at line 413).

## Confirmed code shapes (read this run — do not re-read the service)

- `noteRpcFailure` (line 881) holds **both** arms this ticket asserts, so one driven pass proves
  both at once: `unreachable` / `timeout` → `applyContactFailure`; `local-limit` → `countStreamLimit`
  and return.
- `applyContactStrike` (line ~775) carries a **500 ms spacing guard**
  (`CONTACT_FAILURE_MIN_SPACING_MS`): a strike landing within 500 ms of the last counted one is
  ignored. **This is load-bearing for the non-vacuity of the no-strike arm** — four refusals fired
  back-to-back would book at most *one* strike even on the strike path, so the assertion would pass
  against a broken implementation. Space the driven refusals ≥ 500 ms apart (4 passes ≥ 500 ms
  apart, i.e. > 1.5 s wall clock) so the strike path *would* have reached `deadAfterFailures` (3).
- `probeNeighborLatency` (line 2451), `local-limit` arm: calls `noteRpcFailure` and returns `false`,
  and increments **no** ping diagnostic at all — not `pingsSent`, not `pingsFail`. That is a second,
  free observable: after the driven refusals `diag.pingsSent === 0 && diag.pingsFail === 0` while
  `diag.streamLimit` is non-zero. Its `unreachable` / `timeout` arm *does* strike, so this pass is
  the honest place to prove "would have struck, didn't".
- `probeAndFetch` (line 2422) returns `[]` when the ping did not answer, so a `local-limit` ping
  produces no snapshot fetch — nothing else scores on that path.
- `nearProbeTargets` (line 2406): dialable live members nearest self, `≤ 4`, `isDialable`-filtered.
  The peer must be `membership: 'member'`, non-`dead`, and dialable to be a near target at all.
- Alternative driving path `probeMembership` (line 2671) — same shape, `local-limit` →
  `noteRpcFailure`, deliberately no backoff, while its failure arms strike *and* back off; adds a
  second observable (the backoff map stays empty for that peer).
- `pingWarmupTargets` (~1719) and `iterativeLookup` (~3407) call `countStreamLimit` **directly**,
  bypassing `noteRpcFailure`, and never strike for *any* outcome — so the no-strike arm asserted
  through them is **vacuous**. If `iterativeLookup` is used at all, use it only for the
  `diag.streamLimit` arm and say so in the handoff.

## Rigging note (still the first thing to settle)

`this.streamCaps()` is applied inside `registerRpcHandlers`, on the `start()` path, and there is no
config knob — so the rig must override it. Two options, pick whichever reads more honestly and say
why in the handoff:

- after `start()`, `unhandle` the ping protocol on the requester node and `handle` it again with
  `maxOutboundStreams: 0`; every outbound ping then refuses locally, no concurrency needed. (This
  replaces that protocol's inbound handler on the requester, harmless if the requester never serves
  it in the case.) The protocol id is `/optimystic/${networkName}/fret/1.0.0/ping` — see
  `src/rpc/protocols.ts` for how the service builds `this.protocols`.
- or stub `streamCaps` before `start()`.

Then drive an outbound RPC from the service to a peer it holds a `member` entry for and assert both
arms. Prefer a path a real pass takes over reaching into a private method.
