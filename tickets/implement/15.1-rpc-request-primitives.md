First slice of `15.2a-rpc-request-seam` (which now depends on this ticket). That ticket's `rpcRequest`
helper needs these three primitive changes; they are behavior-visible on their own and carry their
own tests, so they land first as a self-contained change to `src/rpc/protocols.ts`.

Nothing here touches the five senders (`ping.ts`, `neighbors.ts`, `maybe-act.ts`, `leave.ts`) —
they still arm their own two clocks; the single-clock migration is `15.2b`. Existing tests in
`test/rpc.stream-errors.spec.ts` should pass unchanged (its stubs resolve `close()` immediately,
so neither (b) nor (c) changes what they observe).

## (a) `readFramed` gains "no independent clock": `timeoutMs = Infinity`

Today each sender arms `deadline(timeoutMs, signal)` and then hands `readFramed` the *same*
`timeoutMs` a second time alongside that deadline's signal (`ping.ts:104`, `neighbors.ts:98`,
`maybe-act.ts:103`). Both clocks expire within a timer tick, so which error surfaces
(`DeadlineExpiredError` vs `read timed out after Xms`) and which release arm runs is a race —
measured: a review run of `test/rpc.stream-errors.spec.ts` failed a fixed `{ closes: 0, aborts: 1 }`
assertion having taken the `close()` arm. `Infinity` lets the coming `rpcRequest` make its deadline
signal the *only* clock.

Verified against current code (`protocols.ts:278-359`): the loop needs **no change** for
`Infinity` — `remaining` is `Infinity`, `remaining <= 0` never true, `Math.min(remaining,
EOF_POLL_MS)` still yields 20 ms, and the `read timed out after ${timeoutMs}ms` throw at
`protocols.ts:319` becomes unreachable. What it does need:

- A doc line on the function: `Infinity` means "bounded by `opts.signal` alone".
- A **throw at entry** when `timeoutMs === Infinity` and no `opts.signal` was supplied — an
  unbounded read is a caller bug; loud beats a hang.
- Default stays `RPC_TIMEOUT_MS` for direct public users (it is a pinned export).

*Rejected (do not re-derive):* a separate `bounded: false` parameter (grows a pinned public
signature for something the existing parameter expresses); deriving remaining time from the
deadline (that is the second clock again, merely synchronised).

## (b) `releaseRpcStream` bounds its `close()`

`Stream.close(options?: AbortOptions)` resolves only once pending data reached the transport
(`@libp2p/interface` v3.1.0 `stream.d.ts`), so a peer that accepts a stream and stops reading holds
it open with no budget. The signature already carries the deadline signal — pass it:
`await stream.close({ signal })` at `protocols.ts:456`. Worst case today is shutdown: `sendLeave` /
`announceNeighbors` run from `stop()`'s leave fan-out (`fret-service.ts:1485-1525`) whose entire
reason for a budget is bounded shutdown.

Two things found while reading, decide-and-document at the site:

- **When the bounded close rejects (signal fired mid-close), the stream is still unreleased** — the
  existing `catch { /* best effort */ }` swallows the rejection and returns. Follow the failed
  close with a best-effort `stream.abort(...)` inside that catch, mirroring the aborted-path arm,
  or the bound frees the *caller* but leaks the stream slot.
- Ordering trap the migration must preserve (state it in the doc comment): every sender calls
  `releaseRpcStream` from a `finally` *before* `d.cancel()`, so the deadline is still live at that
  point — which is what makes passing its signal meaningful.

## (c) `registerRpcHandler`'s reply tail gets a budget

`protocols.ts:96` awaits a bare `stream.close()`; the NOTE at `protocols.ts:91-95` says replies are
small enough today that the wait is unreachable, "if it ever is, pass an AbortOptions deadline".
Do that now: give the success-path close its own `deadline(RPC_TIMEOUT_MS)`, pass the signal,
`d.cancel()` in a `finally` (an uncleared timer fails the repo's mocha exit watchdog). Rewrite the
NOTE to state what it now does — drop the "if it ever is" clause.

Found while reading:

- `protocols.ts` imports only `abortReasonError` from `../utils/deadline.js` — add `deadline`.
- When the bounded close throws, control lands in the existing catch arm (`protocols.ts:97-102`),
  which aborts when `status === 'open' && writeStatus !== 'closed'`. A close aborted mid-flight
  leaves `writeStatus` at `'closing'`, so the abort arm runs and the stream is released — assert
  that in the test rather than assuming it.
- `RPC_TIMEOUT_MS` is fixed at 5000 and `registerRpcHandler` is **not** a pinned public export
  (absent from `src/index.ts`), so for testability it may grow an internal options parameter
  (e.g. `{ closeBudgetMs?: number }`) rather than a test spending 5 s of wall clock per case.
  Only the seam's success-path tail is in scope; handler bodies' own closes belong to `15.2b`.

## Key tests

Stub conventions to reuse: `test/rpc.stream-errors.spec.ts:117-215` has the scripted-read stub
(`makeStubStream` with `ReadStep[]`, `closes`/`aborts`/`sends`/`delivered` counters) and
`nodeServing` (:195-205); `test/rpc.protocols.spec.ts` has the bare release recorder its comments
call `makeReleasable`. No current stub has a `close()` that never resolves — write one (a promise
that never settles), it is the whole point of (b) and (c).

- `readFramed(stream, max, Infinity)` with no signal **throws synchronously-ish at entry**; with a
  signal it aborts on that signal and never on a timer (drive a stall stub, fire the signal, assert
  the abort reason surfaces and no `read timed out` message exists on this path).
- `releaseRpcStream` against a never-resolving `close()`: returns within the deadline budget once
  the signal fires, and the stream ends released (the follow-up abort ran).
- `registerRpcHandler` success tail against a remote that accepts the reply and stops reading
  (never-resolving `close()`): the handler promise settles within the (injected) budget and the
  stream is released via the catch arm's abort.
- No unhandled rejection escapes any of the above (reuse the `unhandledRejection` hook pattern from
  `rpc.stream-errors.spec.ts:288-299`).
