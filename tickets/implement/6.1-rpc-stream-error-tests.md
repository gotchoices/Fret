The read primitive is well covered — `test/payload-bounds-ttl.spec.ts:40-117` pins the byte cap,
the mid-stream stall, the deadline-over-truncation rule and the missed-EOF poll, and
`test/rpc.protocols.spec.ts:320-506` pins the whole-RPC deadlines. What is untested is the layer
above it: **what each sender does when the reply fails partway through**, and what the service
records about the peer as a result.

Three distinct failure shapes, none of which any current test produces:

1. **Reset mid-stream** — the reply iterator *throws* after some bytes (connection reset, muxer
   error, remote abort). Today's stubs either hang or yield cleanly; none rejects mid-iteration.
2. **Clean EOF mid-payload** — the peer closes tidily after half a JSON document. This is *not* a
   timeout: `readAllBounded` returns a short-but-complete buffer and `decodeJson` throws a
   `SyntaxError`. Each sender handles that differently and none of it is pinned.
3. **Partial then stall** — bytes arrive, then nothing. Pinned at the primitive
   (`payload-bounds-ttl.spec.ts:82`), never at a sender.

## Current behavior, so the implementer does not have to guess

Pin what ships today; do not change sender behavior in this ticket.

| Sender | Read throws (reset / timeout) | Bytes decode to nothing usable |
|---|---|---|
| `sendPing` (`ping.ts:77`) | propagates | empty buffer → `{ ok: false, rttMs }`; decode throw → logged, `{ ok: false, rttMs }` |
| `fetchNeighbors` (`neighbors.ts:86`) | swallowed → fabricated empty snapshot | same fabricated empty snapshot |
| `sendMaybeAct` (`maybe-act.ts:48`) | propagates | propagates (`decodeJson`'s `SyntaxError` / `empty response`) |
| `announceNeighbors` (`neighbors.ts:126`) | swallowed + logged (write-only, no read) | n/a |
| `sendLeave` (`leave.ts:68`) | propagates from the open/send (write-only, no read) | n/a |

That inconsistency is a known, already-owned finding — `tickets/plan/15-rpc-shared-helper`, arms
*"fetchNeighbors fabricates success on every failure"* and *"the liveness seam now has to guess
whether a peer was reached"*. **This ticket does not fix it.** It writes the safety net that makes
fixing it safe, so word every assertion to say which behaviors are invariants that must survive the
refactor and which are today's contract that the refactor is expected to change. A test that merely
restates the current return shape with no such note will be deleted rather than updated when the
shared helper lands, and the coverage will be lost.

## Invariants — must hold before and after `15-rpc-shared-helper`

- **A partial payload is never parsed as a whole message.** No sender returns an object built from
  a truncated buffer, on any of the three failure shapes.
- **The stream is always released exactly once.** `close()` on the un-aborted path, `abort()` on the
  aborted one (`releaseRpcStream`, `protocols.ts:311`), even when the read threw. Outbound stream
  caps are finite (64 Edge / 256 Core), so a leak is a real ceiling.
- **No unhandled rejection escapes**, including from the abandoned `iter.next()` the poll loop holds
  (`protocols.ts:196`).
- **Our own cancellation is never evidence about the peer** — a signal abort landing mid-stream
  records no contact strike, no backoff, no relevance decay (`docs/fret.md` → *Stabilization and
  churn handling*, the cancellation bullet).
- **A reset mid-stream is a failed contact; an answered-but-undecodable reply is not a
  negotiate-failure.** `noteRpcFailure` (`fret-service.ts:667`) only routes
  `UnsupportedProtocolError` to membership evidence; everything else becomes a contact strike. Pin
  that a decode error does **not** demote a peer to `foreign`.

## Today's contract — expected to change under the shared helper

Mark each of these with a comment naming `15-rpc-shared-helper` and the arm it belongs to:

- `fetchNeighbors` returning a fabricated empty snapshot rather than a distinguishable failure.
- `sendPing` collapsing "empty reply" and "undecodable reply" into `ok: false`, while
  `sendMaybeAct` throws on the same evidence — so the service books a *contact failure* for a
  maybeAct peer that merely replied badly, and books nothing for a ping peer that did the same.
  Assert the asymmetry as it stands; it is exactly what the discriminated result type will resolve.

## Test approach

New file `test/rpc.stream-errors.spec.ts`.

- **Stubs, not real transports, for the failure shapes.** Reuse the node-stub pattern from
  `rpc.protocols.spec.ts:252-302` (`hangsUntilAbort`, `makeSilentStreamNode`), adding stubs whose
  iterator yields N bytes and then rejects, and whose iterator yields half a JSON document and then
  reports `done`. The existing stubs deliberately omit `close`/`abort`; the new ones must implement
  both with call counters, since release-exactly-once is one of the invariants.
- **One real-transport case** using `test/helpers/libp2p.ts`'s in-memory node factory: a handler
  that writes half a snapshot and closes. This is what proves the stub shapes match what libp2p
  actually produces — the missed-EOF bug (`protocols.ts:130-135`) is precedent for a stub-only
  suite agreeing with itself and not with the transport.
- **Unhandled-rejection guard**: install a `process.on('unhandledRejection')` listener for the
  duration of the suite and fail the run if it fires; remove it in `after`. The repo's exit
  watchdog (`test/mocha-exit-watchdog.ts`) catches leaked handles, not leaked rejections.
- **Service-level scoring** is asserted through `FretService` with a stubbed node, reading
  `getStore().getById(id)` for `contactFailures`, `negotiateFailures`, `state` and `membership` —
  the shape `dead-state.spec.ts` and `ring-membership.spec.ts` already use.

## Key tests and expected outputs

Per failure shape × sender, plus the service arm:

- **Reset mid-stream.** `sendPing` rejects; `fetchNeighbors` resolves to the empty snapshot;
  `sendMaybeAct` rejects; every one of them called `close()` or `abort()` exactly once and no
  partial object was produced.
- **Clean EOF mid-JSON.** `sendPing` → `{ ok: false }` with a plausible `rttMs`, never a
  half-populated `PingResponseV1`; `fetchNeighbors` → empty snapshot with no successors,
  predecessors or sample from the truncated bytes; `sendMaybeAct` rejects rather than returning a
  half-decoded `NearAnchorV1`.
- **Partial then stall.** `sendPing` rejects within roughly its `timeoutMs` (bound the elapsed time,
  as `rpc.protocols.spec.ts:311-318` insists — "it rejected" would pass at ten minutes), and the
  error names the byte count read.
- **Caller cancels mid-stream.** The caller's own `AbortSignal` aborts after some bytes: the sender
  rejects with the caller's reason, the stream is released via `abort()` not `close()`, and the
  service records no strike, no backoff, no relevance decay for that peer.
- **Reset mid-stream at the service.** One failed maybeAct forward → `contactFailures` 1,
  `negotiateFailures` 0, `membership` unchanged. Three spaced ones → `state: 'dead'`.
- **Undecodable reply at the service.** Pin what actually happens today (a contact strike, per the
  table above) with the `15-rpc-shared-helper` reference inline, so the intended future behavior is
  visible next to the assertion that contradicts it.
- **Real-transport half-reply.** `fetchNeighbors` against a peer that writes half a snapshot and
  closes returns the empty snapshot, promptly (bounded well under the RPC timeout — a clean EOF is
  not a stall), with the stream released.

## Edge cases & interactions

- **Zero bytes then reset** versus **bytes then reset** — the first has no partial buffer to
  mis-return, the second does; cover both, they take different paths through `readAllBounded`.
- **Reset exactly at the byte cap** — `payload too large` must win over, or at least not be masked
  by, the reset; assert one specific outcome so the behavior is stated rather than incidental.
- **Double release.** `sendMaybeAct` closes the stream inside its `try` (`maybe-act.ts:64`) and then
  `releaseRpcStream` closes it again from the `finally`. Pin that this is harmless — a second
  `close()` neither throws nor is counted as a second release — since the "exactly once" invariant
  above must not be read as forbidding it.
- **A stream carrying neither `close` nor `abort`** is already covered
  (`rpc.protocols.spec.ts:241`); do not duplicate it, but do make sure the new stubs are not the
  only ones exercising release.
- **`releaseRpcStream`'s un-aborted arm is unbounded** — `await stream.close()` with no signal
  against a remote that stopped reading. That is an open arm of `15-rpc-shared-helper` ("closing the
  stream is the one step the time limit does not cover"). Do **not** write a test that hangs on it;
  if a case would, note it in the handoff instead.
- **Announce and leave are write-only.** They have no read to fail, so their arm is: a reset while
  writing is swallowed (announce) or propagates (leave), and the stream is released either way.
- **Wall-clock.** Use short `timeoutMs` values (~100 ms, as the deadline suite does) so the file
  stays well inside mocha's default per-test budget.
