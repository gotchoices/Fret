Found during review of `sim-joiner-placement`. That ticket fixed a real defect — peers joining a
simulation run mid-flight were all placed into a shrinking sliver of the ring instead of being
spread out — and added a test to stop it coming back. The fix is correct. The test is not.

## What is wrong

The test is the last case in `test/churn-scenarios.spec.ts`,
`it('uniform placement keeps joiners spread across the ring')`. It measures the **largest gap**
between adjacent live peers on the ring and fails if that gap is more than 10x the spacing an
evenly-spread population would have.

Largest gap does not detect this defect. The initial population is placed evenly and most of it
survives the run, so those peers alone hold the largest gap down no matter where the mid-run
joiners land. Piling every joiner into one sliver makes that sliver *denser*; it barely widens
the biggest hole elsewhere.

## Measured

Restoring the pre-fix placement (making the mid-run branch of `generateCoord` divide by the
post-increment counter again, as it did before the fix) and running only this test:

- pre-fix placement: largest gap / even spacing = **6.25** — passes, threshold is 10
- post-fix placement, seed 8008: **5.00**

So the guard admits the exact defect it was written for, with room to spare, and the two arms are
only 1.25x apart — no threshold on this statistic separates them safely.

For contrast, a statistic that counts how many peers fall inside any single even-spacing-wide arc
reads **4** on the fixed placement, and does so identically across five seeds (8008, 8009, 8010,
4242, 99), where largest-gap ranged 2.81–5.00 over the same seeds. That looks like the more
stable and more on-point measure — clumping is what the defect does — but its value under the
pre-fix placement was **not** measured, so treat it as a lead, not a conclusion.

## Expected behavior

- The test should fail when the pre-fix placement is restored, and pass on the current code, with
  a wide margin between the two.
- Whatever statistic is chosen, **the acceptance step is to temporarily put the old placement back
  and watch the test go red**. A calibration run on the fixed code alone cannot tell you whether a
  guard guards anything — that is precisely how this one shipped.
- Thresholds should be stated with the measurement that produced them, for both arms, in a comment
  beside the assertion.
- Ideally the case also covers steady trickle joins (churn-driven), not only the one batch-join
  burst it uses today — the original ticket asked for that and it is still uncovered.
