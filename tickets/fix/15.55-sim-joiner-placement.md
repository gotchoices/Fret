Found during review of `sim-churn-lazy`. That ticket paired every churn departure with a fresh
arrival, which turned mid-run joining from a rarely-taken path (only the batch-join test helpers
used it) into something that happens on every churn-enabled simulation run. Doing so exposed a
placement defect that was already in the harness.

## What is wrong

The simulation places a peer on the 256-bit ring by index. For the default `'uniform'` placement
that is `uniformCoord` (`fret-sim.ts`, inside `generateCoord`):

```ts
private uniformCoord(index: number): Uint8Array {
	const range = (1n << 256n) / BigInt(Math.max(1, this.nextPeerIndex))
	const val = BigInt(index) * range
	...
}
```

`nextPeerIndex` is the count of peers ever created. During `initialize()` it is fixed at `n` for
the whole loop, so the initial population lands at fractions `0/n, 1/n, ... (n-1)/n` — genuinely
uniform, which is the intent.

But `handleJoin()` increments it *before* placing:

```ts
private handleJoin(): void {
	const index = this.nextPeerIndex++      // nextPeerIndex is now index + 1
	const peer = this.addPeer(index)        // ... which uniformCoord then divides by
	...
}
```

So every mid-run joiner lands at fraction `index / (index + 1)` of the ring — 0.976, 0.976, 0.977,
0.978, … converging on 1.0 and packing ever more tightly as the run goes on. The divisor is meant
to be the population the index is being spread across; using the *incremented* counter makes it
the joiner's own index instead.

## Measured

Running the new `continuous churn keeps the population stationary` case
(`churn-scenarios.spec.ts`, seed 6006, n=40, 2 churn events/sec, 10s, default `'uniform'`
placement) and reading the alive peers' coordinates at the end:

- 16 of the 40 alive peers (40%) sit in the ring arc `[0.9756, 0.9831]` — **0.75% of the ring**.
- The other 24 are the surviving initial peers, still spread across the remaining 99.25%.
- Largest gap between adjacent peers: 10.0% of the ring. Uniform would be 2.5%.

## Why it matters

Every simulated quantity that depends on where peers sit — neighbor-set quality, cohort assembly,
routing hop counts, coverage, network-size estimation — is being measured on a ring with a dense
clump and a large void. This is not a cosmetic realism nit: a threshold calibrated on such a ring
is calibrated on the wrong network, and the two sibling tickets (`sim-route-local-selector`,
`sim-routing-guard-spec`) exist specifically to measure routing quality in this harness. Their
numbers will be taken against this ring unless it is fixed first.

The `'clustered'` and `'skewed'` placement strategies do not read `nextPeerIndex` and are
unaffected.

## Expected behavior

- A peer joining mid-run under `'uniform'` placement should land somewhere that keeps the live
  population roughly evenly spread, the same property the initial population has. (A real
  network's joiners are placed by the hash of their peer id, i.e. effectively at random — a
  seeded random coordinate is a closer model than any index arithmetic, and it removes the
  dependence on a mutable counter entirely. That is a design call for the implementer, not a
  requirement of this ticket.)
- The invariant should be pinned by a test rather than by the one scenario that happened to
  expose it: after an arbitrary mix of initial peers, batch joins and churn joins, the largest
  gap between adjacent live peers on the ring should stay within a small multiple of the uniform
  spacing `1/aliveCount`. Written as a generalized case it also covers the batch-join paths
  (`scheduleBatchJoin`, used by `churn-scenarios.spec.ts:72,130` and
  `simulation.partition.spec.ts:162,436`), which have the same defect and no coverage for it.

## Re-calibration

Fixing placement moves every seeded churn-enabled run's numbers again. The thresholds in the
churn suites were left untouched by `sim-churn-lazy` on measured evidence (routing under churn
came in at 95.0% success / 0.9 avg hops against ≥80% and ≤7.6 bars); those margins should be
re-checked after this lands, and any that no longer hold re-set from a measured run with the
measured number in a comment beside it.
