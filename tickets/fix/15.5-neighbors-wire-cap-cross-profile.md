## What is wrong

FRET runs two operating profiles, Edge (lightweight) and Core (server-grade). A recent change
replaced the neighbor-message size limit — previously a single generous 128 KiB for everyone —
with one number per profile: Core accepts 16 KiB, Edge accepts 8 KiB.

Each profile's number was derived from **the largest message that profile would produce**. But a
size limit on an incoming message has to cover the largest message *any peer* may legitimately
send, and peers of both profiles talk to each other. A Core node's largest legal snapshot does not
fit inside an Edge node's limit.

The failure is silent and one-directional: the Edge node refuses the message at its length prefix
and tears the stream down; the Core node sees a failed RPC and has no way to learn that its message
was simply too big for that peer.

### Arm A — a Core snapshot can exceed the Edge limit

A neighbor snapshot carries two parts: fixed fields (peer id lists and a sparsity sample) and an
optional application-supplied `metadata` blob set via `setMetadata`.

- Core fixed fields: 12 successors + 12 predecessors + 8 sample entries ≈ 2.5 KiB (measured by the
  encoding tests added alongside this change, which build the same shapes).
- Core `metadata` allowance: `MAX_SNAPSHOT_METADATA_BYTES_CORE` = 8 KiB.
- Worst legal Core snapshot ≈ 10.5 KiB.
- Edge inbound limit (`FretService.maxBytesNeighbors()`): 8 KiB.

So a Core node whose application sets more than roughly 5.5 KiB of metadata can no longer announce
to, or answer a neighbors request from, any Edge peer. With no metadata set the fixed fields alone
fit, which is why this does not show up in a default single-profile test run.

The encoding tests added with the change assert "the largest legal message of each protocol encodes
under its wire cap", but they build the snapshot **without** a `metadata` field — so they do not
exercise the part that overflows, and they compare each profile's message against *its own* limit
rather than against the smallest limit any peer could impose.

### Arm B — the same message type is checked against two different limits on one node

The same node reads neighbor snapshots on two paths, and they disagree:

- Announce path: `registerNeighbors` is given `FretService.maxBytesNeighbors()` — 16 KiB Core,
  8 KiB Edge.
- Fetch path: `fetchNeighbors` (`packages/fret/src/rpc/neighbors.ts`) passes a hard-coded
  `16 * 1024` and takes no profile input at all.

So an Edge node accepts a 12 KiB snapshot when it asked for one, and refuses the identical snapshot
when the same peer pushes it. Both arms live at the same decision — "what is the neighbors byte
limit" — which is why they are one ticket.

This is the same shape of defect the change was meant to retire for the maybeAct protocol (where two
limits disagreed by 4x). It was fixed there and reintroduced here.

## Expected behavior

- One place decides the neighbors byte limit, and every read path — announce handler and fetch reply
  alike — takes its number from that place. No literal byte counts anywhere else.
- The limit a node **accepts** covers the largest snapshot any profile can legitimately emit, not
  merely the largest this node emits. If Core and Edge are to keep different *emission* budgets,
  the acceptance limit is the maximum of them, not the local one.
- The relationship is pinned by a test that includes `metadata` at its full allowance, and that
  checks each profile's largest emitted snapshot against the *smallest* limit any peer may apply —
  so a future narrowing of either number fails the test instead of shipping.
- `docs/fret.md` *Stream management* currently states the neighbors cap as "16 KiB Core / 8 KiB
  Edge, sized to its profile's snapshot caps"; that sentence encodes the mistaken rule and needs to
  state the corrected one.

## Deciding what the numbers should be

Two directions are open and worth weighing rather than assuming:

- Raise the acceptance limit on both profiles to cover the largest Core snapshot. Simple, keeps the
  emission budgets as they are; costs Edge a larger worst-case read buffer.
- Cap `metadata` to one profile-independent number so every profile's snapshot fits a single limit.
  Keeps Edge's small buffer; costs Core applications metadata room they nominally have today
  (nothing in the tree uses metadata at that size, so this may be free in practice).

Note that over-cap metadata is currently *dropped* from the outgoing snapshot with an error log, so
whichever direction is taken, an application whose metadata exceeds the allowance still loses it
silently from the peer's point of view. See the `NOTE:` at `FretService.snapshot`.
