Third of three tickets split out of the former `15-rpc-shared-helper`. The receive half:
`registerJsonHandler` layered on the existing registration seam, per-message shape validators, and
the max-bytes tightening that `15.1`'s length prefix makes cheap.

## Already landed — do not re-implement

- **The transport/lifecycle half of handler registration is done.** `registerRpcHandler(node,
  protocol, serve)` (`src/rpc/protocols.ts:81-102`) is the single seam every inbound handler goes
  through — leave, ping, neighbors, neighbors-announce and maybeAct all register through it. It
  closes a stream the handler left open on success (`close()` early-returns when the write end is
  already closing, so a handler that replied and closed is not released twice) and `abort()`s
  synchronously on error, skipping the abort for a stream the remote already reset and for one
  whose write end the handler already closed — because that reply is committed and a reset would
  destroy it. The load-bearing subtlety: `status` alone cannot answer "did the handler already
  release this?", since a half-closable stream stays `open` until the *remote* closes its write end,
  which for every FRET sender happens only after it has read the reply — the **write-end** status is
  the one to branch on. Pinned by `test/rpc.handler-fuzz.spec.ts`. **Do not replace or re-derive
  this seam**; stack the decode/validate/reply-encode layer on top of it.
- **maybeAct already has its validator.** `validateRouteAndMaybeAct` (`maybe-act.ts:327-345`) checks
  field types, finite numbers, a base64url-decodable `key` (decoded once and handed down so neither
  `routeAct` nor `nearAnchorOnly` can throw on it again), and caps `key` at 1024 chars,
  `correlation_id` at 256 and `breadcrumbs` at 64 entries. It runs immediately after the rate-limit
  bucket and before every other guard — that position is load-bearing both ways (`docs/fret.md`,
  *Cheap-guard rejections*). **It is the style to copy**, and the `correlation_id` cap that was once
  an open arm of this work is already in it.
- **The leave notice's replacement list is already sanitized** — `sanitizeReplacements`
  (`leave.ts:407-418`) caps at 12, drops non-strings, and drops ids that do not parse as peer ids.
  The other model to copy.

## What remains

- **Three of the five wire messages have no shape validation at all.** `decodeJson`
  (`protocols.ts:124-143`) rejects a non-object top level and nothing more; every handler then casts
  blindly to its target type. Concretely:
  - `NeighborSnapshotV1`: `from` is never parsed as a peer id (only string-compared against
    `connection.remotePeer.toString()`, so a match is required but the field is otherwise untyped);
    `successors` / `predecessors` / `sample` are unbounded within the byte cap — thousands of ids
    fit under 128 KB. The merge loops slice to the profile caps (Core 16/16/8, Edge 8/8/6) *after*
    decoding, so the parse cost is paid on the full array. `sample[].coord` / `.relevance` types are
    unchecked.
  - `LeaveNoticeV1`: `from` and `timestamp` untyped beyond the identity comparison.
  - `PingResponseV1` / `BusyResponseV1` / `NearAnchorV1` — *reply* shapes, read by senders, equally
    uncast-checked. Decide whether replies get validators too (the `15.2` outcome type has a
    `decode-error` variant that a failed validator naturally produces).
  - maybeAct's `digest` is type-checked but has no length cap, unlike `key` and `correlation_id`.
- **`registerJsonHandler(node, protocol, fn, maxBytes)`** — the decode + validate + reply-encode
  layer, so a handler body receives an already-validated message and returns a reply object. Every
  handler currently repeats read → decode → identity-check → handle → encode → send → close.
- **Tighten each RPC's max-bytes to its real ceiling.** Today: maybeAct 512 KB Core / 256 KB Edge,
  neighbors 128 KB Core / 64 KB Edge, leave a fixed 4096. **The maybeAct wire cap and the service's
  own activity cap disagree by 4x on Core** — the wire admits 512 KB while `handleMaybeAct` refuses
  an `activity` over a fixed 128 KB, *after* the whole body has been buffered. With `15.1`'s length
  prefix the refusal moves before the body is read at all. Derive each cap from the message's actual
  maximum (caps x id length x profile), state the arithmetic, and make the wire cap and the service
  cap one number rather than two.

## Edge cases & interactions

- **Ordering is load-bearing.** The rate-limit bucket is taken *first*, before any per-message work,
  so a malformed flood is metered like any other; the validator runs next, before every other guard,
  so none of them can throw on a field of the wrong type. Preserve both, and preserve the
  static zero-computation reject reply (`NearAnchor` with empty lists, `estimatedClusterSize`/
  `confidence` 0) — computing real anchors on a rejection is the per-message cost the bucket exists
  to bound.
- A validator failure must be a **drop**, never an abort of a stream carrying a committed reply —
  the `registerRpcHandler` rules above decide which. Identity-mismatch drops close, never abort.
- Per-entry vs whole-message rejection: snapshot *sample* entries currently skip-and-log per entry
  (one bad sample drops that entry, not the message) while `importTable` rejects the whole snapshot.
  Pick a rule per field and state it; do not change the sample behavior silently.
- An array at exactly the cap, one over, and one entry that fails to parse inside an otherwise valid
  array.
- A `from` that is a valid peer id but not the transport-authenticated sender must still be dropped
  by the existing identity check and still increment `diag.rejected.identityMismatch`.
- `validateTimestamp`'s ±30s window is deliberately equal to the dedup TTL (`DEDUP_TTL_MS`); any
  slack between them is a replay window. Do not move one.
- Encode-side: `encodeJson` has three stated losses (`-0` to `0`, `NaN`/`Infinity` to `null`,
  `undefined` dropped) pinned by `test/rpc.codec-properties.spec.ts`. A validator that rejects
  `null` where `undefined` was meant would break a valid round trip.

## Key tests to expect

- Extend `test/rpc.handler-fuzz.spec.ts`: for every wire message, a body with each field wrong type
  / missing / over cap is dropped without throwing out of the handler and without leaking the
  stream. The existing release-exactly-once invariants must hold unchanged.
- A snapshot carrying more ids than the profile cap is refused (or truncated — state which) before
  the per-id hash+upsert loop runs, measured by counting the loop's work, not inferred.
- An over-cap message is refused after reading only its length prefix (depends on `15.1`).
- `from` that is not a parseable peer id is dropped.
- A round trip of every valid wire message still passes its own validator — the property that a
  validator never rejects what `encodeJson` produced from a legal value.
