### The dependency surface, enumerated (this was the claim to verify)

**The guard is genuinely narrow — verified.** `applyMembershipSignal` (815), `classifyByProtocols`
(898) and the membership half of `noteAnsweredOnProtocol` (709) touch exactly:

- `store.getById(id)`, `store.update(id, PeerPatch)`, `store.setMembership(id, …)`
- the entry fields `membership`, `negotiateFailures`, `lastNegotiateFailureAt`
- `Date.now()`
- `this.protocols` (for `classifyByProtocols`'s "is one of ours" test)
- two class constants, `NEGOTIATE_FAILURE_MIN_SPACING_MS` and `NEGOTIATE_FAILURE_THRESHOLD`

No network, no config profile, no ring walk, no backoff map, no connection state. That is a
`live-member.ts`-shaped dependency, and it is the piece with the strongest extraction case.

**Target selection is narrow-ish but needs three injected predicates.** `classifyTargets` /
`reprobeOffRingTargets` / `reprobeExcludedTargets` / `phaseTwoTargets` additionally read:

- `store.list()`, `store.countByMembership(label)`, `store.countByState('dead')`
- `this.selfIdStr`, `this.cfg.profile` (budgets 8/4 and 2/1)
- `this.isConnected(id)`, `this.hasAddresses(id)` — connectivity/dialability predicates
- `this.getBackoffPenalty(id)` and `this.backoffMap.get(id)?.factor` — **two different reads of the
  same map**, one a boolean gate and one an ordering key

**Probe execution stays.** `probeMembership` (2411) reaches `sendPing`, `this.node`, `this.diag`,
`applySuccess`, `noteRpcFailure`, `recordBackoff` / `clearBackoff` — i.e. most of the service. It is
pooled RPC work bound to the tick budget, exactly as this ticket predicted.

**`seedFromPeerStore` is not part of the seam.** Its membership involvement is a single
`classifyByProtocols(pidStr, p.protocols)` call inside a peerStore walk that is otherwise about
coordinates and the address set. It calls the guard; it does not contain policy.

### A sibling counter the design must not ignore

`applyContactStrike` (642) is the **same shape** as `applyMembershipSignal`'s `negotiate-failure`
arm — spacing guard, clamped increment, state transition at a threshold — with different constants,
a different counter and a different transition. There is an explicit `NOTE:` at line ~636 recording
that the duplication was weighed and kept, with a stated revisit condition: *"if a third spaced-run
counter ever appears, factor all three out rather than adding another copy."*

Per the accepted-tradeoffs rule, that decision stands and must not be re-litigated as a finding.
But it constrains this design directly: an extraction that moves the negotiate-failure arm into a
new module while `applyContactStrike` stays in the service **separates the two instances the NOTE
is about**, so the next reader can no longer see them side by side and the revisit condition
becomes unobservable. Whatever the seam turns out to be, the NOTE has to move or be rewritten to
point across the new boundary.

### Test surface

24 test files reference `membership` / `negotiateFailures` / `applyMembershipSignal`. The two that
exist *because* this policy is hard to reach are `test/ring-membership.spec.ts` and
`test/membership-identify.spec.ts`; `ring-membership.spec.ts` alone contains **20** `as any` /
`as unknown as` casts (`grep -c`). Those casts are the concrete cost this ticket is trying to
price, and the next run should read that file to say *what each one becomes* — that enumeration was
not reached.

## Still to settle

Narrowed by the findings above. These are the questions; none is answered yet.

- **Does the guard alone justify a module?** It is ~106 lines (mostly prose) with a store-and-clock
  dependency, and extracting it would make the whole evidence-strength table directly testable with
  a bare `DigitreeStore` and an injectable clock — no libp2p node, no casts. Against: it is already
  a single choke point, which is the property the doc actually cares about, and moving it splits it
  from `applyContactStrike` (see above). Decide, and say which of the 20 casts it retires.
- **Does target selection come too, or at all?** Three injected predicates plus a profile is a real
  interface, not a narrow one. Weigh a policy object owning both against extracting only the guard
  and leaving selection in the service.
- **Where does the clock live?** The guard needs `Date.now()` spacing. `SizeObserver` (23.1) already
  set a house pattern for an injectable clock — follow it rather than inventing a second one.
- **Dead/liveness seam.** Unchanged from the original framing: the dead arm shares mechanics with
  the foreign arm but belongs to liveness. The `backoffMap` NOTE at `reprobeExcludedTargets`
  already records that the two arms deliberately share one backoff map, so splitting them is a
  documented non-goal today.
- **Legitimate outcome: "no good seam."** Given the revised line count and the fact that the
  guard is already a single choke point, "the cost is the 20 casts, and the fix for those is a
  test helper rather than a module boundary" is a defensible answer. If that is the conclusion,
  write it up and close, rather than shipping an extraction that moves prose.

## Constraints any design must respect

Unchanged from the original ticket, and all four still hold against the code as read:

- **The store stays network-agnostic.** Verified: `digitree-store.ts` stores `membership`,
  `negotiateFailures`, `lastNegotiateFailureAt` and tallies per-label counts at its write seam, and
  never branches on what a label *means*. An extraction that teaches it is a violation.
- **One guard, stated once.** Any split producing two places a label can be set is a regression
  regardless of line count.
- **The probe arms' budgets stay separate.** Merging the candidate lists repeals the rule that a
  large foreign population cannot starve dead recovery.
- **`docs/fret.md` is the spec** — the *Ring membership* section is unusually complete; check the
  design against it line by line and record any divergence found while reading.
