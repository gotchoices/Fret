description: The code that sends a network message is copy-pasted across five places with four different ways of reporting failure, so an unreachable peer and a peer that merely answered badly are indistinguishable — one gets wrongly punished, another wrongly forgiven, and a third is reported as a successful empty answer. One shared send helper with one honest set of outcomes fixes all of them.

## Verified against the tree (do not re-derive)

`15.1` landed, so two premises of the previous version of this ticket are stale and are corrected
here:

- **`readAllBounded` no longer exists.** The reader is now `readFramed(stream, maxBytes, timeoutMs,
  { signal })` (`protocols.ts`), which delimits a message by its length prefix and polls
  `remoteFinishedWriting` every 20 ms (`EOF_POLL_MS`) to turn a truncated reply into
  `FrameTruncationError` promptly. Everywhere this ticket used to say `readAllBounded`, read
  `readFramed`.
- **`sendPing` already special-cases truncation.** `ping.ts:106-108` returns `{ ok: false }` for
  `isFrameTruncationError(err)` and rethrows everything else; the *decode* failures
  (`empty response` / `whitespace response` / `non-object JSON payload` / `SyntaxError`) are caught
  separately at `ping.ts:117-120` and also collapse to `{ ok: false }`. The ping row of the table
  below is therefore unchanged, but it is now two code paths, not one.

### The four disagreeing contracts (was "three" — `announceNeighbors` is a fourth)

| sender | reply undecodable / empty | unreachable | busy | site |
|---|---|---|---|---|
| `sendPing` | `{ ok: false }`, no strike | throws | `{ ok: false }` | `ping.ts:88-129` |
| `fetchNeighbors` | fabricated empty snapshot | fabricated empty snapshot | fabricated empty snapshot | `neighbors.ts:81-112` |
| `sendMaybeAct` | throws — service books a contact strike | throws | returns the busy object | `maybe-act.ts:91-110` |
| `announceNeighbors` | n/a (write-only) | **logs and swallows** — caller cannot tell | n/a | `neighbors.ts:120-149` |
| `sendLeave` | n/a (write-only) | throws | n/a | `leave.ts:75-92` |

`announceNeighbors` swallowing is why `announceToTargets` (`fret-service.ts:1300-1320`) carries a
comment saying a `wasCancelled` guard in its catch "would never fire".

### Live consequences, each confirmed at a named site

- **`fetchNeighbors` fabricates success on every failure** — `neighbors.ts:81-112`. Unreachable,
  busy, decode-error, foreign-protocol and the connection-only skip all return
  `emptySnapshot(peerIdOrStr)`, indistinguishable from a real empty answer. `diag.snapshotsFetched`
  books garbage (`fret-service.ts:2168-2170`), no failure or backoff is recorded, and swallowing the
  unsupported-protocol error means foreign classification can never happen on this path. The busy
  check (`'busy' in res`) sits *after* a decode that may throw, so an exception is control flow into
  the same fake snapshot.
- **The liveness seam guesses, and guesses wrong for a peer that answered badly.**
  `noteRpcFailure` (`fret-service.ts:669-680`) splits membership evidence from unreachability by
  `isUnsupportedProtocolError`; every other throw is a contact strike. `sendMaybeAct` lets
  `decodeJson`'s plain `Error`s propagate (`maybe-act.ts:104`), so a peer that opened a stream,
  replied, and merely replied *badly* is counted unreachable — three such replies mark it `dead`
  (call sites `fret-service.ts:2456`, `:2905`, `:2928`). The ping path classifies identical evidence
  the other way. **Static, not verified:** confirming it needs a peer whose maybeAct reply is empty
  or non-JSON while its stream still opens.
- **One budget, two independent clocks — still live after 15.1.** Each sender arms
  `deadline(timeoutMs, opts.signal)` and then hands `readFramed` *the same* `timeoutMs` a second
  time alongside that deadline's signal: `ping.ts:104`, `neighbors.ts:98`, `maybe-act.ts:103`. Both
  expire within a timer tick of each other, so which error surfaces (`DeadlineExpiredError` vs
  `read timed out after Xms`) and which release arm runs (`abort()` only if the signal already
  fired) is a race. **Measured, not inferred:** a review run of `test/rpc.stream-errors.spec.ts`
  failed on a fixed `{ closes: 0, aborts: 1 }` assertion having taken the `close()` arm; that spec
  now asserts release-*exactly-once* for budget-driven reads and pins the arm only where a caller's
  signal is the sole clock (helpers `expectStallRejection`, `expectReleasedOnce`). The fix is
  representational: the read is bounded by the deadline *already armed* — its signal, or its
  remaining time — never by a second copy of the budget. `readFramed`'s `timeoutMs = RPC_TIMEOUT_MS`
  default cannot express "no independent clock", so it needs a way to.
- **`close()` is the one step no budget covers.** `Stream.close(options?: AbortOptions)` resolves
  only once pending data reached the transport (`@libp2p/interface` v3.1.0 `stream.d.ts`), so a peer
  that accepts a stream and stops reading holds it open. Four FRET sites pass no signal:
  `releaseRpcStream`'s non-cancelled arm (`protocols.ts:451`, run from a `finally` *before*
  `d.cancel()`, so a call that already has its answer can sit past its budget); `sendMaybeAct`'s
  half-close flush (`maybe-act.ts:101`, inside the `try`, so a stall there skips the `finally`
  entirely and holds the stream as well as the caller); and both inbound tails
  (`registerRpcHandler`, `protocols.ts:92` — which already carries a `NOTE:` saying replies are
  small enough today that the wait is unreachable in practice). Worst case is shutdown: `sendLeave`
  / `announceNeighbors` run from `stop()`'s leave fan-out (`fret-service.ts:1485-1525`), whose whole
  reason for a budget is bounded shutdown. Static: read from the code and libp2p's `.d.ts`; no
  magnitude claimed beyond "not FRET's budget" — no muxer `inactivityTimeout` default exists in this
  repo's installed dependencies.
- **No single place decides whether a peer may be dialed at all.** `openRpcStream`
  (`protocols.ts:400-425`) takes a boolean `requireExisting` and otherwise dials a bare peer id.
  Today: `fetchNeighbors` passes `requireExisting: true`; `announceNeighbors` passes
  `requireExisting: opts.dial !== true`; ping / maybeAct / leave pass nothing and dial
  unconditionally. Each call site separately remembers to check dialability first, and a site that
  forgets produces a steady stream of `NoValidAddressesError`.
  `4-dialability-guard-on-outbound-rpc` fixed today's call sites; the shared helper is what stops the
  class returning, by owning "connection-only" / "dial if we have an address" / "dial
  unconditionally" as one explicit per-call **mode** rather than a convention each caller
  re-implements.
- **Backpressure is ignored.** `sendFramed` returns `stream.send`'s boolean (`protocols.ts:151-153`,
  whose comment explicitly defers backpressure to this ticket); no sender reads it. Recovery is
  `writableNeedsDrain` plus the `drain` event (`@libp2p/interface` `message-stream.d.ts:116,127,134`).
  Any wait for `drain` must itself be bounded by the call's deadline.

## Design to settle (the remaining work of this ticket)

- `RpcOutcome<T>` — a discriminated union distinguishing at minimum `ok`, `unreachable`,
  `foreign-protocol`, `decode-error`, `busy`, `timeout`, and (see the connection-only skip below)
  `skipped`. Every FRET failure mode must map onto exactly one variant, and `noteRpcFailure` must
  branch on the variant rather than sniffing an error. Decide whether `cancelled` is a variant or
  stays the caller's `wasCancelled` check — the existing rule is that the *caller's* signal is the
  discriminator (`fret-service.ts:704`), so do not duplicate it in two places without saying which
  wins.
- Whether `rpcRequest` is generic over the reply type with a validator callback (which is how `15.3`
  plugs in) or returns raw bytes for the caller to decode.
- Whether the five senders stay as thin named wrappers or the service calls `rpcRequest` directly.
  Note `openRpcStream` / `releaseRpcStream` / `readFramed` / `sendFramed` are **public exports** with
  a stated consumer contract (`src/index.ts`, `docs/fret.md` *Dialability*, pinned by
  `test/package-exports.spec.ts`); changing them is an API change to justify.
- How "no second clock" is expressed on `readFramed` — a sentinel `timeoutMs` (e.g. `Infinity`), a
  separate parameter, or deriving the remaining time from the deadline. Pick one and state why the
  other two lose.
- Whether the reply iterator is primed before the write. `15.1`'s framing makes the reader
  authoritative about message end, but `readFramed`'s own `EOF_POLL_MS` `NOTE:` says priming is the
  durable fix for the lost-close-event case and that the 20 ms poll is a floor under measured ping
  RTT. Say which, and do not do both without a reason.

## Edge cases & interactions

- A `stop()` landing mid-flight records nothing: no strike, no backoff, no relevance decay, no
  `pingsFail` — for every sender, and for a pooled task never started.
- Tick-budget expiry (`STABILIZE_TICK_BUDGET_MS`) is a child of the run signal and must behave
  identically to `stop()` at the seam.
- Concurrent calls to the same peer from the pooled stabilization tick: the four candidate sets are
  disjoint by construction (`test/stabilize-concurrency.spec.ts`), but `fetchAndMergeSnapshot`'s
  *merge* can still touch a peer another task is pinging. Do not make that race worse.
- The shutdown fan-out cannot reuse the run signal (it runs *after* that aborts, by design) and
  carries its own `SHUTDOWN_BUDGET_MS` / `LEAVE_NOTICE_TIMEOUT_MS`.
- `announceNeighbors` and `sendLeave` are write-only: their `close()` **is** the flush, so "release"
  and "send" are the same operation and the outcome type must not pretend a reply was read.
- A rate-limited leave is invisible on the wire today — `handleLeave` takes the token but
  `registerLeave` has already committed to `{ok: true}` (`docs/fret.md`, *Leave*). The discriminated
  type is what would let leave report busy; decide whether that lands here or is parked, and record
  the decision.
- `fetchNeighbors`' connection-only skip ("no connection, nothing attempted", `neighbors.ts:95-97`)
  is a **distinct** outcome from "reached and got nothing" — today both are the fabricated empty
  snapshot, and the `snapshotsFetched` overcount `NOTE:`d at `fetchAndMergeSnapshot`
  (`fret-service.ts:2145-2160`) ends when they separate.

## Key tests to expect

- `test/rpc.stream-errors.spec.ts`: update the assertions that deliberately pin today's inconsistent
  contract (each is commented as belonging to this ticket) — decode-error cases become
  `decode-error` outcomes and the contact strike on the maybeAct path goes away. These invariants
  must survive unchanged: a partial payload is never parsed as a whole message; the stream is
  released exactly once; no unhandled rejection escapes; our own cancellation scores nothing. The
  two release-arm helpers should collapse to one deterministic expectation.
- A peer that replies empty / non-JSON over an opened stream is **not** marked `dead` after three
  attempts (`test/dead-state.spec.ts`) — currently uncovered because no stub behaves this way.
- A remote that accepts a stream and then stops reading does not hold `stop()` past
  `SHUTDOWN_BUDGET_MS` — needs a new stub; no current one behaves this way either.
- A `send()` returning `false` is followed by a bounded `drain` wait rather than a hang.
- Each dial mode does what it says: connection-only never dials; address-gated never dials a peer
  with no address; unconditional dials.
- `announceNeighbors` reports its outcome instead of swallowing it, and `announceToTargets`'
  `wasCancelled` guard becomes reachable.
