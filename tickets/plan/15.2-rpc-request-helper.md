Second of three tickets split out of the former `15-rpc-shared-helper`. Introduces
`rpcRequest(node, peer, protocol, body, opts)` — the single owner of the outbound
open / write / read / close sequence — and one discriminated result type replacing today's three
disagreeing failure contracts. `15.3-rpc-message-validators` covers the receive half.

## Already landed — do not re-derive

- **Cancellation contract.** `7-rpc-abort-deadlines` shipped `deadline()` (`src/utils/deadline.ts`),
  a `{ signal, timeoutMs }` contract on `openRpcStream` / `readAllBounded` / all five senders, a
  shared `RPC_TIMEOUT_MS`, and `FretService.runAbort`. The rule *"our own abort is not evidence
  about the peer"* (`FretService.wasCancelled`) is a correctness rule the shared helper must
  preserve — the caller's signal is the discriminator because the sender's deadline is a **child**
  of it.
- **Ping's round-trip clock already starts after the stream opens** (`ping.ts:97-99`).
- **`releaseRpcStream`** already picks `abort()` when the signal fired and `close()` otherwise, and
  is exported from the package root paired with `openRpcStream` (`src/index.ts:146-150`), pinned by
  `test/package-exports.spec.ts`.

## The three disagreeing contracts

| sender | reply undecodable / empty | unreachable | busy |
|---|---|---|---|
| `sendPing` | `{ ok: false }`, no strike | throws | `{ ok: false }` |
| `fetchNeighbors` | fabricated empty snapshot | fabricated empty snapshot | fabricated empty snapshot |
| `sendMaybeAct` | throws — service books a contact strike | throws | returns the busy object |

Consequences to fix:

- **`fetchNeighbors` fabricates success on every failure** (`neighbors.ts:186-231`). Unreachable,
  busy, decode-error and foreign-protocol all return a synthetic empty snapshot indistinguishable
  from a real one, so `diag.snapshotsFetched` books garbage, failure and backoff are never recorded,
  and swallowing the unsupported-protocol error means foreign classification can never happen on
  this path. The busy check (`'busy' in res`) also depends on a decode that may throw, using an
  exception as control flow into the same fake snapshot.
- **The liveness seam has to guess, and guesses wrong for a peer that answered badly.**
  `FretService.noteRpcFailure` (`fret-service.ts:669-680`) splits "refuses our network's protocol"
  (membership evidence) from "could not be reached at all" (a strike toward `dead`) by
  name-matching `isUnsupportedProtocolError`; *every other* throw is treated as unreachability. But
  `decodeJson` throws a plain `Error('empty response')` / `Error('whitespace response')` /
  `SyntaxError` / `Error('non-object JSON payload')` (`protocols.ts:124-143`) and `sendMaybeAct`
  lets those propagate (`maybe-act.ts:373`) — so a peer that accepted the stream, replied, and
  merely replied *badly* is counted unreachable, and three such replies mark it `dead`. The ping
  path classifies identical evidence the other way (`ping.ts:102,105,114`). Established by reading,
  not by running: confirming it needs a peer whose maybeAct reply is empty or non-JSON while its
  stream still opens.
- **One budget, two independent clocks.** Each sender arms `deadline(timeoutMs, opts.signal)` and
  then hands `readAllBounded` *the same* `timeoutMs` a second time alongside that deadline's signal
  (`ping.ts:100`, `neighbors.ts:218`, `maybe-act.ts:372`). Both expire within a timer tick of each
  other, so which error surfaces (`DeadlineExpiredError`, no byte count, vs
  `read timed out after Xms (N bytes read)`) and which release arm runs (`abort()` only if the
  signal already fired) are a race. **Measured, not inferred:** a review run of
  `test/rpc.stream-errors.spec.ts` failed on a fixed `{ closes: 0, aborts: 1 }` assertion having
  taken the `close()` arm. That spec now asserts release-*exactly-once* for budget-driven reads and
  pins the arm only where a caller's signal is the sole clock; both helpers
  (`expectStallRejection`, `expectReleasedOnce`) carry the reasoning and should collapse to a single
  deterministic expectation once this lands. The fix is representational: the read is bounded by the
  deadline *already armed* — its signal, or its remaining time — never by a second copy of the
  budget. `readAllBounded`'s `timeoutMs = RPC_TIMEOUT_MS` default cannot express "no independent
  clock", so it needs a way to.
- **`close()` is the one step no budget covers.** `Stream.close(options?: AbortOptions)` resolves
  only once pending data has been passed to the underlying transport
  (`@libp2p/interface` v3.1.0 `stream.d.ts`), so a peer that accepts a stream and stops reading
  holds it open. Neither FRET site passes a signal: `protocols.ts:402` (`releaseRpcStream`'s
  non-cancelled arm, run from a `finally` *before* the deadline is cancelled, so a call that already
  has its answer can sit past its budget) and `maybe-act.ts:371` (the half-close flush, inside the
  `try`, so a stall there means the `finally` is never reached and the stream is held as well as the
  caller). The cancelled arm is fine — it uses the synchronous `abort()`, which is why it exists.
  Worst case is shutdown: `sendLeave` / `announceNeighbors` run from `stop()`'s leave fan-out, whose
  stated reason for a budget is to keep shutdown bounded. Established by reading the code and
  libp2p's type declarations; no magnitude is claimed beyond "not FRET's budget" — no muxer
  `inactivityTimeout` default was found in this repo's installed dependencies.
- **No single place decides whether a peer may be dialed at all.** `openRpcStream` dials a bare peer
  id whenever no connection exists, and each outbound call site separately remembers to check first —
  some pass `requireExisting: true`, some filter on connection state, several do neither. Sites
  dialing peers no address can exist for produce a steady stream of `NoValidAddressesError`.
  `4-dialability-guard-on-outbound-rpc` landed correct behavior at the existing call sites; the
  shared helper is what stops the class returning, by owning "connection-only" / "dial if we have an
  address" / "dial unconditionally" as one explicit per-call **mode** rather than a convention each
  caller re-implements.
- **Backpressure is ignored.** `Stream.send(data): boolean` returns `false` when the internal buffer
  fills; recovery is `writableNeedsDrain` plus the `drain` event
  (`@libp2p/interface` `message-stream.d.ts:116,127,134`). No sender checks the return value. Any
  wait for `drain` must itself be bounded by the call's deadline.

## Design to settle

- `RpcOutcome<T>` — a discriminated union distinguishing at minimum `ok`, `unreachable`,
  `foreign-protocol`, `decode-error`, `busy`, `timeout`. Every FRET failure mode must map onto
  exactly one variant, and `noteRpcFailure` must branch on the variant rather than sniffing an
  error. Decide whether `cancelled` is a variant or stays the caller's `wasCancelled` check — the
  existing rule is that the *caller's* signal is the discriminator, so do not duplicate it in two
  places without saying which wins.
- Whether `rpcRequest` is generic over the reply type with a validator callback (which is how
  `15.3` plugs in) or returns raw bytes for the caller to decode.
- Whether the five senders stay as thin named wrappers or the service calls `rpcRequest` directly.
  Note `openRpcStream` / `releaseRpcStream` / `readAllBounded` are **public exports** with a stated
  consumer contract (`docs/fret.md`, *Dialability*); changing them is an API change to justify.
- Whether the reply iterator is primed before the write. `15.1`'s framing makes the reader
  authoritative about message end, so this may be unnecessary — say which, and do not do both
  without a reason.

## Edge cases & interactions

- A `stop()` landing mid-flight records nothing: no strike, no backoff, no relevance decay, no
  `pingsFail` — for every sender, and for a pooled task never started.
- Tick-budget expiry (`STABILIZE_TICK_BUDGET_MS`) is a child of the run signal and must behave
  identically to `stop()` at the seam.
- Concurrent calls to the same peer from the pooled stabilization tick: the four candidate sets are
  disjoint by construction (`test/stabilize-concurrency.spec.ts`), but `fetchAndMergeSnapshot`'s
  *merge* can still touch a peer another task is pinging. Do not make that race worse.
- The shutdown fan-out cannot reuse the run signal (it runs *after* that aborts, by design) and
  carries its own `SHUTDOWN_BUDGET_MS` / `LEAVE_NOTICE_TIMEOUT_MS`.
- `announceNeighbors` and `sendLeave` are write-only: their `close()` **is** the flush, so "release"
  and "send" are the same operation and the outcome type must not pretend a reply was read.
- A rate-limited leave is invisible on the wire today — `handleLeave` takes the token but
  `registerLeave` has already committed to `{ok: true}` (`docs/fret.md`, *Leave*). The
  discriminated type is what would let leave report busy; decide whether that lands here or is
  parked, and record the decision.
- `fetchNeighbors`' connection-only skip ("no connection, nothing attempted") is a **distinct**
  outcome from "reached and got nothing" — today both are the fabricated empty snapshot, and the
  `snapshotsFetched` overcount noted at `fetchAndMergeSnapshot` ends when they separate.

## Key tests to expect

- `test/rpc.stream-errors.spec.ts`: update the assertions that deliberately pin today's inconsistent
  contract (each is commented as belonging to this ticket) — decode-error cases become
  `decode-error` outcomes and the contact strike on the maybeAct path goes away. These invariants
  must survive unchanged: a partial payload is never parsed as a whole message; the stream is
  released exactly once; no unhandled rejection escapes; our own cancellation scores nothing. The
  two release-arm helpers should collapse to one deterministic expectation.
- A peer that replies empty / non-JSON over an opened stream is **not** marked `dead` after three
  attempts (`test/dead-state.spec.ts`) — currently uncovered because no stub behaves this way.
- A remote that accepts a stream and then stops reading does not hold `stop()` past
  `SHUTDOWN_BUDGET_MS` — needs a new stub; no current one behaves this way either.
- A `send()` returning `false` is followed by a bounded `drain` wait rather than a hang.
- Each dial mode does what it says: connection-only never dials; address-gated never dials a peer
  with no address; unconditional dials.
