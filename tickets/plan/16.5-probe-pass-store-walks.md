### The waste

`stabilizeOnce` selects its phase-2 probe targets like this (~2016):

```ts
const targets = [...this.classifyTargets(), ...this.reprobeExcludedTargets()];
```

That is **three full `store.list()` walks per tick** — one per candidate set:

- `classifyTargets` (~2130): `membership === 'unknown' && state !== 'dead'`
- `reprobeOffRingTargets` foreign arm (~2188): `membership === 'foreign' && state !== 'dead'`
- `reprobeOffRingTargets` dead arm (~2189): `state === 'dead'`

`store.list()` materializes an array of every entry (up to C = 2048), which is then filtered down.
In single-network steady state every peer is `member` and non-dead, so all three walks produce
**empty** lists — the tick pays three full-table materializations to learn there is nothing to do,
at up to ~3 ticks/second in active mode. A `NOTE:` at `classifyTargets` already records this at the
code site; it is that NOTE's fix.

### Shape of the fix

Two halves, both cheap, and they compose:

1. **A count-based early return, so steady state costs zero walks.** If the store can answer "how
   many entries have `membership === 'unknown'`" (and the same for `foreign`, and for
   `state === 'dead'`) in O(1), each selector returns `[]` without walking. The counts do not need
   to match the compound predicates exactly — they only need to be *supersets*, which makes a zero
   count a sound proof that the compound set is empty too. Three separate single-field counts are
   therefore enough; no compound bookkeeping is needed.

2. **One shared walk when the counts are non-zero**, partitioned into the three candidate lists,
   instead of three independent walks. Each selector must keep its **own budget, ordering and
   predicate** — the separate budgets are a documented invariant (a large foreign population must
   not starve dead recovery), so only the *walk* is shared, never the candidate lists. Mechanically
   this is passing the already-materialized entry array into the selectors as a parameter.

### The decision this ticket exists to settle

**Where are the counts maintained, and are they provably correct across every mutation?**

The candidate answer is `DigitreeStore` itself, because `docs/fret.md` (*Routing store (Digitree) &
indices (A2)*) states that all mutation funnels through a single private write seam (`put`, plus its
delete half `remove`) — which would make the counts derivable at exactly one place and unable to
drift, the "make the bad state unrepresentable" rung rather than a hand-maintained tally. That is
the attraction, and it is why this should not be done in `FretService` with a hand-rolled map keyed
off every call site that flips a label.

What the planning pass must confirm before writing the implement ticket:

- Do `setState` (~264) and `setMembership` (~268) actually route through the `put` seam, or do they
  mutate an entry in place? If they mutate in place, the seam is not sufficient on its own and the
  counts need a second maintenance point — which is exactly the drift risk to design out, not
  accept. Read `src/store/digitree-store.ts:190-278`.
- `upsert`'s documented rule is that it **preserves** an existing entry's `membership` and `state`
  and refreshes only `coord` and `lastAccess`. A coordinate change is a *re-key* (drop + place), so
  confirm a re-key does not double-count or lose a count.
- Eviction (`enforceCapacity` → `store.remove`), `importTable` (bulk replace by id, including
  replacing an entry that already exists with different labels), and `stop()`/restart must all
  leave the counts consistent.
- Does the network-agnostic rule bar this? The store "stores and exposes both fields and never
  branches on them". A tally is bookkeeping over a field it already owns, not policy — but say so
  explicitly in the implement ticket, because the next reader will ask.
- Cheaper alternative to weigh and then reject or adopt in writing: skip the counts entirely and
  ship only half 2 (one shared walk). That is a 3x reduction with no new store state and no
  invariant to keep, but it leaves steady state paying one full walk per tick instead of zero. If
  the seam turns out not to be single-point, this fallback is likely the better ticket.

Settle it and emit **one** implement ticket; do not hand the choice to the implementer.

### Edge cases the implement ticket must carry

- Counts include self (seeded `member`, never dead) — a single-node ring must early-return on all
  three, not underflow.
- A peer that is *both* `foreign` and `dead` belongs to the dead arm alone (documented disjointness,
  pinned by `test/stabilize-concurrency.spec.ts`). Superset counts must not resurrect it into two
  arms.
- The four per-tick candidate sets stay disjoint — near / classify / foreign / dead. That
  disjointness is what makes pooled probing safe against the lost-increment race on the score and
  strike counters, so a shared walk must not merge or duplicate ids across arms.
- Ordering must survive the refactor: `classifyTargets` orders by ascending `lastAccess`;
  each re-probe arm orders by ascending backoff factor. Both exist to stop a budget-truncated tick
  re-deriving the same head every tick (`bug-discovery-scan-starves-ring-tail` is the same class of
  defect, already fixed once).
- Transitions in both directions must be exercised: `unknown → member` (a classification probe
  succeeding) must drop the unknown count to zero and re-arm the early return; `member → dead` (a
  contact-failure run) must lift the dead count off zero and make the arm walk again on the very
  next tick, not one tick later.
- A count that is wrong in the *low* direction is a correctness bug, not a perf regression: it makes
  a probe pass silently stop selecting, and a dead peer that never gets re-probed never recovers
  (the dead arm is documented as the only path back for a peer that recovers but never dials us).
  A count wrong in the *high* direction merely costs a wasted walk. Any test plan should target the
  low direction.
- `test/stabilize-concurrency.spec.ts` and `test/dead-state.spec.ts` are the specs most likely to
  bite; `test/digitree.invariants.spec.ts` is the model-based property test over arbitrary write
  sequences and is the natural home for a "counts match a full recount" invariant.
