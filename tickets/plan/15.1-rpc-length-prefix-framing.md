`docs/fret.md` has always specified "length-prefixed UTF-8 JSON" for all four protocols. The
implementation ships **bare** JSON and infers message end from stream close. Everything below is a
consequence of that one gap, and framing retires all of it at once. This is the first of three
tickets split out of the former `15-rpc-shared-helper` (see also `15.2-rpc-request-helper` and
`15.3-rpc-message-validators`).

## What the gap costs today

**End-of-stream is routinely missed.** libp2p's async-iterator adaptor subscribes to the one-shot
remote-close event only when iteration *starts*. Every sender opens, writes, closes, and only then
begins reading — so a responder that replies quickly (the norm for a small reply) closes before the
subscription exists and the event is lost. Measured on both transports in this repo (memory+plaintext
and TCP+noise+yamux): a ping reply arrives in under a millisecond and the read then never ends on
its own.

**The current workaround is a poll.** `readAllBounded` (`src/rpc/protocols.ts`, `remoteFinishedWriting`
+ `EOF_POLL_MS = 20`) races each `iter.next()` against a 20ms timer and, on each tick, consults the
stream's own `readBufferLength` / `remoteWriteStatus` / `readStatus`. Correct, but it reaches into
properties a read helper should not need to know, and it puts a ~20ms floor under every measured RPC
round-trip time — which feeds `applySuccess`'s latency EMA and therefore peer health scoring and
eviction order.

**The byte cap can only be enforced after the fact.** `readAllBounded` compares cumulative length
after each chunk, so an over-sized body is partly pulled through the receiver's memory before being
refused. A length prefix is checkable *before* a single body byte is read, which is what makes
`15.3`'s "tighten each RPC's max-bytes to its real ceiling" cheap rather than merely stricter.

## Shape of the change

Not yet designed — that is this ticket's job. Settle at minimum:

- **Prefix encoding.** Fixed-width vs unsigned varint. Note `@libp2p/interface` v3.1.0 gives
  `Stream.send(data): boolean` and a `Uint8ArrayList`, so a two-part write is cheap; `it-length-prefixed`
  is the ecosystem-standard varint implementation — decide use-it vs hand-roll (house rule: *no
  half-baked janky parsers*, so a hand-roll needs to be genuinely trivial and fully tested).
- **A prefix larger than `maxBytes` is refused without reading the body**, and the refusal must be
  the same shape of error as today's `payload too large`.
- **Partial-prefix and partial-body reads** are errors, never short-but-valid messages — the existing
  invariant from `test/rpc.stream-errors.spec.ts` ("a partial payload is never parsed as a whole
  message") must survive.
- **Both directions, all five protocols** — request and reply. There is no compatibility constraint
  (`AGENTS.md`: "Don't worry about backwards compatibility yet"), but the change is only correct if
  both halves land together.
- **Delete the poll.** `remoteFinishedWriting`, `EOF_POLL_MS`, `POLL_TICK` and the `ReadEndState`
  interface all exist solely to recover the lost close event; framing makes the reader authoritative
  and they go. Confirm the RTT floor is actually gone by measurement, not by inspection.
- **`readAllBounded` is exported from the package root** (`src/index.ts:150`) and pinned by
  `test/package-exports.spec.ts`. Decide whether it keeps its name with new semantics or a framed
  reader lands beside it, and update the export surface + that spec accordingly.

## Edge cases & interactions

- Reply arrives in one chunk containing prefix + whole body; prefix split across two chunks; body
  split across many; prefix arrives and body never does (must hit the deadline, not hang forever).
- Prefix declaring 0 bytes; prefix declaring more than `maxBytes`; prefix declaring less than what
  actually arrives (trailing bytes — decide: ignore or error, and state which).
- A muxer that pads a short frame — `decodeJson` currently trims NUL/tab/LF/CR/space from both ends
  for exactly this reason. With a length prefix the padding is now *inside or outside* the counted
  body; work out which and keep the trim only if it is still load-bearing.
- Write-side backpressure: `send()` returns `false` when the internal buffer fills (128–512 KiB) and
  `writableNeedsDrain` / the `drain` event are the recovery path. Framing does not fix this; it is
  `15.2`'s arm. Do not silently make it worse by splitting one `send` into two.
- Interaction with `registerRpcHandler` (`src/rpc/protocols.ts`) — the inbound release seam. Its
  rules (close on success, synchronous `abort()` on error, skip the abort for an already-reset stream
  or one whose write end the handler closed) are correctness rules pinned by
  `test/rpc.handler-fuzz.spec.ts`. Framing must not require re-deriving them.
- The maybeAct half-close (`maybe-act.ts:64`) is the write-side flush the responder waits on. With a
  length prefix the responder no longer *needs* the close to know the message ended — decide whether
  the half-close stays (it also bounds the responder) and say why.

## Key tests to expect

- Round-trip property over generated instances of all five wire types (extend
  `test/rpc.codec-properties.spec.ts`, which already proves the JSON codec's three stated losses).
- Chunk-boundary property: the same message split at every possible offset decodes identically.
- Over-sized prefix refused after reading **only the prefix** — measured by counting pulls on a
  source that reports them, exactly as the existing cap test does.
- A fast responder's reply is read without a 20ms floor; assert the measured RTT, since that floor is
  the headline symptom.
- `test/rpc.stream-errors.spec.ts`'s three failure shapes (reset mid-stream, clean close mid-JSON,
  stall after a partial payload) still yield an error and release the stream exactly once.
