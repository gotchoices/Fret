# Unreleased — since v1.0.1

## A peer with no address leaves the ring when it goes away

A peer that dials out and listens nowhere, such as a phone, used to stay a live ring member forever
after it disconnected. FRET marks a peer `dead` only after three failed contacts, and it never tried
to contact a peer it had no address for. The peer's own leave notice did not help: it was sent after
libp2p had already closed its connections, and a later peer-store update re-created the entry anyway.
All three ways a peer departs now take effect:

- **Vanished, no address.** A near-window member that is neither connected nor has an address counts
  as one failed contact per stabilization tick. It is `dead` after three, about 4.5 s in passive mode
  and about 1.5 s in active mode. Connecting again (`peer:connect`) or any inbound RPC brings it back.
- **Graceful stop.** The libp2p service sends its leave notices in `beforeStop()`, before libp2p
  closes connections, so neighbours receive them. `stop()` can now take up to 3 s longer when
  neighbours are slow to answer.
- **Leave received.** A leave notice marks the sender `dead` instead of deleting its entry, so a
  later peer-store update cannot bring it back as a live member. The entry stays until capacity
  eviction removes it, and no ring view includes it.

## Changed

- **Near-probe targets are now s1, p1, s2, p2** (both sides of the ring, closest first), instead of
  the first four successors.

## Known limitations

- A peer only strikes address-less members inside its own near window. On a ring with more than
  2·max(2, m) + 1 live members, members outside the window are struck by their own neighbours.

# v1.0.1

## Breaking

- **The peer-dependency floor is now the libp2p 3.3 line.** `p2p-fret` requires `libp2p` ^3.3.11, `@libp2p/interface` ^3.3.0 and `@libp2p/peer-id` ^6.0.15 (previously ^3.1.3, ^3.1.0 and ^6.0.4). A consumer still on libp2p 3.1 or 3.2 must upgrade libp2p before taking this release.

## Changed

- **Runtime dependencies moved to the releases libp2p 3.3 itself uses:** `uint8arraylist` ^3.0.2, `it-length-prefixed` ^11.0.1, `multiformats` ^14.0.5, `uint8arrays` ^6.1.1, `uint8-varint` ^3.0.0, `@libp2p/utils` ^7.4.1, `@libp2p/logger` ^6.2.13 and `@libp2p/peer-record` ^9.0.16. A libp2p 3.3 project now resolves one copy of each, with two effects:
  - The exported `readFramed` is typed over the same `uint8arraylist` 3 lists a libp2p 3.3 `Stream` yields, so passing one needs no type assertion.
  - A FRET checkout can be portal-linked into a libp2p 3.3 workspace again. Before, Yarn refused the link because FRET's `it-length-prefixed` and `uint8arraylist` ranges conflicted with the parent's.
- `main-event` (^1.0.1), which FRET's peer-discovery module imports at run time, is now a declared dependency. It used to resolve only because libp2p happened to install it, which a strict package manager (pnpm, Yarn PnP) would not allow.
- Ring coordinates are unchanged: `multiformats` 14's SHA-256 produces byte-identical digests, so every peer and key keeps its position on the ring.
